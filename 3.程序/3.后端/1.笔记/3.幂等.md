# 幂等

你想详细了解后台开发中接口的幂等性处理，包括它的核心概念、适用场景、具体实现方案以及开发中的注意事项，目的是保证接口在重复调用时不会产生错误数据（比如重复扣款、重复下单），且结果与单次调用完全一致。

## 一、先搞懂：什么是接口幂等性？

幂等性原本是数学概念（比如 $f(f(x)) = f(x)$），在后台接口中，定义是：**同一个接口，无论被调用多少次，产生的业务结果和副作用都与调用一次完全相同**。

举个通俗例子：

- 非幂等接口：用户点击“支付”按钮，网络卡顿导致重复点击，接口被调用2次，扣了2次钱；
- 幂等接口：即使调用2次，也只会扣1次钱，第二次调用直接返回“支付成功”的结果，不会重复扣款。

### 哪些接口天然幂等？哪些需要处理？

| 接口类型 | 幂等性 | 示例 |
|----------|--------|------|
| 查询类   | 天然幂等 | 根据订单号查订单详情，调用10次结果都一样 |
| 删除类   | 天然幂等 | 删除某个订单，第一次删成功，后续再删都返回“已删除” |
| 新增类   | 非幂等   | 创建订单、支付扣款，重复调用会生成多个订单/扣多次款 |
| 更新类   | 部分非幂等 | 直接修改库存（`stock = stock - 1`）非幂等；带版本号更新（`stock = stock - 1 where version = 1`）幂等 |

## 二、为什么必须做幂等处理？

接口重复调用是后台开发中无法避免的场景，常见原因：

1. 前端/客户端：用户重复点击提交按钮、页面刷新、网络重试（比如axios自动重试）；
2. 服务端：分布式系统中消息队列重复消费、定时任务重复执行、微服务间调用超时重试；
3. 第三方交互：支付回调、异步通知（比如微信支付回调可能多次推送）。

如果不做幂等处理，会导致：重复下单、重复扣款、库存多扣、数据脏写等严重问题。

## 三、核心实现方案（按场景分类，附代码示例）

不同业务场景适配不同的幂等方案，以下是最常用的6种方案，从简单到复杂逐一说明：

### 方案1：数据库唯一索引（最简单，适配新增类接口）

**原理**：给业务表的“唯一标识字段”加唯一索引（比如订单号、用户ID+业务流水号），重复插入时数据库会抛出`DuplicateKey`异常，捕获该异常并返回“操作成功”即可。
**适用场景**：创建订单、生成流水记录等“一次性新增”场景。

**代码示例（Java + MySQL）**：

```java
// 1. 数据库表设计（订单表）：order_no 加唯一索引
/*
CREATE TABLE `t_order` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `order_no` varchar(64) NOT NULL COMMENT '订单号（唯一）',
  `user_id` bigint NOT NULL COMMENT '用户ID',
  `amount` decimal(10,2) NOT NULL COMMENT '金额',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_order_no` (`order_no`) USING BTREE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
*/

// 2. 业务代码
@Service
public class OrderService {
    @Autowired
    private OrderMapper orderMapper;

    @Transactional(rollbackFor = Exception.class)
    public String createOrder(OrderDTO orderDTO) {
        String orderNo = generateOrderNo(); // 生成唯一订单号
        OrderDO order = new OrderDO();
        order.setOrderNo(orderNo);
        order.setUserId(orderDTO.getUserId());
        order.setAmount(orderDTO.getAmount());

        try {
            orderMapper.insert(order);
            return "创建订单成功，订单号：" + orderNo;
        } catch (DuplicateKeyException e) {
            // 捕获唯一索引冲突异常，说明是重复创建
            log.warn("订单已存在，订单号：{}", orderNo, e);
            return "创建订单成功，订单号：" + orderNo; // 结果与单次调用一致
        }
    }

    // 生成唯一订单号（简化版，实际可用雪花算法）
    private String generateOrderNo() {
        return System.currentTimeMillis() + "" + new Random().nextInt(1000);
    }
}
```

### 方案2：Token机制（适配前端主动提交场景）

**原理**：

1. 前端发起“提交请求”前，先调用“获取幂等Token”接口；
2. 后端生成唯一Token（比如UUID），存入Redis（设置过期时间），并返回给前端；
3. 前端提交业务请求时，携带该Token；
4. 后端验证Token：存在则删除Token并执行业务，不存在则拒绝（说明是重复请求）。
**适用场景**：支付提交、表单提交、下单等前端主动触发的操作。

**代码示例（Java + Redis）**：

```java
// 1. Token生成接口
@RestController
@RequestMapping("/api/token")
public class TokenController {
    @Autowired
    private StringRedisTemplate redisTemplate;

    @GetMapping("/generate")
    public Result<String> generateToken() {
        String token = UUID.randomUUID().toString();
        // 存入Redis，过期时间5分钟（避免内存泄漏）
        redisTemplate.opsForValue().set("idempotent:token:" + token, "1", 5, TimeUnit.MINUTES);
        return Result.success(token);
    }
}

// 2. 业务接口（下单）
@RestController
@RequestMapping("/api/order")
public class OrderController {
    @Autowired
    private StringRedisTemplate redisTemplate;
    @Autowired
    private OrderService orderService;

    @PostMapping("/create")
    public Result<String> createOrder(@RequestHeader("Idempotent-Token") String token, @RequestBody OrderDTO orderDTO) {
        // 1. 验证Token（Lua脚本保证原子性：查询+删除）
        String script = "if redis.call('exists', KEYS[1]) == 1 then return redis.call('del', KEYS[1]) else return 0 end";
        Long result = redisTemplate.execute(
            new DefaultRedisScript<>(script, Long.class),
            Collections.singletonList("idempotent:token:" + token)
        );

        // 2. Token验证失败：重复请求
        if (result == 0) {
            return Result.fail("操作重复，请不要重复提交");
        }

        // 3. Token验证成功：执行业务
        String res = orderService.createOrder(orderDTO);
        return Result.success(res);
    }
}
```

### 方案3：乐观锁（适配更新类接口）

**原理**：给业务表加“版本号（version）”或“更新时间戳”字段，更新时通过`WHERE`条件限定版本号，只有版本号匹配才执行更新，保证每次更新都是“基于最新状态”，重复调用不会重复生效。
**适用场景**：修改订单信息、扣减库存、更新用户余额等“更新类”操作。

**代码示例（Java + MySQL）**：

```java
// 1. 数据库表设计（库存表）：加version字段
/*
CREATE TABLE `t_stock` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `product_id` bigint NOT NULL COMMENT '商品ID',
  `stock_num` int NOT NULL COMMENT '库存数量',
  `version` int NOT NULL DEFAULT 0 COMMENT '版本号',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_product_id` (`product_id`) USING BTREE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
*/

// 2. 扣减库存的幂等代码
@Service
public class StockService {
    @Autowired
    private StockMapper stockMapper;

    @Transactional(rollbackFor = Exception.class)
    public boolean deductStock(Long productId, int deductNum) {
        // 1. 查询当前库存和版本号
        StockDO stock = stockMapper.selectByProductId(productId);
        if (stock == null || stock.getStockNum() < deductNum) {
            return false; // 库存不足
        }

        // 2. 乐观锁更新：只有version匹配才扣减
        int updateCount = stockMapper.deductStock(
            productId, 
            deductNum, 
            stock.getVersion() // WHERE version = ?
        );

        // 3. 更新成功=扣减成功；更新失败=重复调用/并发冲突（需重试）
        return updateCount > 0;
    }
}

// Mapper接口
public interface StockMapper {
    @Update("UPDATE t_stock SET stock_num = stock_num - #{deductNum}, version = version + 1 " +
            "WHERE product_id = #{productId} AND version = #{version}")
    int deductStock(@Param("productId") Long productId, 
                    @Param("deductNum") int deductNum, 
                    @Param("version") int version);
}
```

### 方案4：分布式锁（适配高并发更新场景）

**原理**：调用接口时，先通过Redis/ZooKeeper获取分布式锁（锁的Key是业务唯一标识，比如“deduct_stock:product_1001”），获取到锁才执行业务，未获取到则拒绝/重试，保证同一时间只有一个请求执行操作。
**适用场景**：高并发下的库存扣减、红包发放、秒杀等场景。

**代码示例（Java + Redis Redisson）**：

```java
@Service
public class StockService {
    @Autowired
    private RedissonClient redissonClient;
    @Autowired
    private StockMapper stockMapper;

    public boolean deductStock(Long productId, int deductNum) {
        // 1. 定义分布式锁Key（唯一标识本次业务）
        String lockKey = "lock:deduct_stock:" + productId;
        RLock lock = redissonClient.getLock(lockKey);

        try {
            // 2. 获取锁：等待10秒，持有锁30秒（避免死锁）
            boolean locked = lock.tryLock(10, 30, TimeUnit.SECONDS);
            if (!locked) {
                return false; // 未获取到锁，说明有其他请求在处理
            }

            // 3. 执行业务（扣减库存）
            StockDO stock = stockMapper.selectByProductId(productId);
            if (stock == null || stock.getStockNum() < deductNum) {
                return false;
            }
            stockMapper.updateStockNum(productId, stock.getStockNum() - deductNum);
            return true;
        } catch (InterruptedException e) {
            log.error("获取分布式锁异常", e);
            return false;
        } finally {
            // 4. 释放锁
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

### 方案5：请求编号（幂等号）机制（适配回调/异步通知场景）

**原理**：客户端发起请求时生成唯一的“请求编号”（比如`req_no`），后端接收请求后，先检查该编号是否已处理：

- 未处理：执行业务，记录“请求编号-处理结果”到数据库/Redis；
- 已处理：直接返回之前的处理结果，不重复执行业务。
**适用场景**：第三方回调接口（比如支付回调）、异步通知、批量处理接口。

### 方案6：状态机控制（适配有状态流转的业务）

**原理**：业务对象有明确的状态流转（比如订单：待支付→支付中→已支付→已发货），重复调用时检查当前状态：如果状态已超过“待处理”阶段（比如已支付），则拒绝执行操作。
**适用场景**：订单、支付、物流等有明确状态流转的业务。

## 四、幂等实现的关键注意事项

1. **幂等键的设计要唯一**：幂等键（比如Token、请求编号、锁Key）必须能唯一标识“一次业务操作”，比如组合键：`用户ID + 业务类型 + 业务流水号`，避免不同业务的幂等键冲突；
2. **保证原子性**：验证幂等和执行业务必须是原子操作（比如用Redis Lua脚本、数据库事务），否则会出现“验证通过但业务执行失败”的异常场景；
3. **设置过期策略**：Redis中存储的Token、请求编号等要设置过期时间，避免内存泄漏；
4. **异常处理**：业务执行失败时，要考虑是否回滚幂等标识（比如Token是否重新生成），比如支付接口调用失败，用户重新提交时需要新的Token；
5. **性能权衡**：分布式锁、Redis验证会增加接口开销，要根据业务并发量选择方案（比如低并发用唯一索引，高并发用乐观锁/分布式锁）。

## 总结

1. 接口幂等的核心目标是**重复调用结果一致**，核心处理场景是新增/更新类接口，查询/删除类接口天然幂等；
2. 不同场景适配不同方案：前端提交用Token、新增用唯一索引、更新用乐观锁、高并发更新用分布式锁、回调接口用请求编号；
3. 实现幂等的关键是**幂等键唯一+操作原子性+过期策略**，同时要平衡性能和业务需求。
