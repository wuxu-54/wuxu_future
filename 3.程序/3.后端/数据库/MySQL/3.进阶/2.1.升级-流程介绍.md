# MySQL 实际项目完整升级流程及注意事项

MySQL升级是项目迭代的核心环节，**不同升级类型（表结构/版本/架构）流程略有差异，但核心逻辑是“最小风险、可回滚、全验证”**。以下是覆盖「通用流程+分场景细化+全量注意事项+回滚预案」的完整指南，所有步骤均基于生产环境实战经验提炼。

## 一、先明确升级类型（针对性制定方案）

先界定升级类型，避免“一刀切”流程：

| 升级类型                | 场景示例                                  | 核心风险点                          |
|-------------------------|-------------------------------------------|-----------------------------------|
| 表结构升级（DDL）       | 新增字段、修改索引、拆分表、删除废弃字段   | 锁表阻塞业务、索引失效、数据截断    |
| 数据库版本升级          | MySQL 5.7 → 8.0、MariaDB 10.3 → 10.6      | 语法兼容、配置不兼容、性能波动      |
| 架构升级                | 单库 → 分库分表、主从架构调整（一主多从） | 数据不一致、路由错误、业务适配失败  |
| 数据层升级              | 字段类型变更（INT→BIGINT）、数据清洗迁移   | 数据丢失、转换错误、查询性能下降    |

## 二、MySQL通用完整升级流程（全类型适配）

### 阶段1：升级前准备（占比60%，决定升级成败）

核心目标：**把风险提前暴露，确保方案可落地、可回滚**。

#### 1.1 需求与影响分析（必须书面化）

- **明确升级目标**：
  例：“给`order`表新增`express_no`字段，支持物流跟踪；修改`user`表`phone`字段长度为20位”；
  禁止模糊需求（如“优化订单表性能”）。
- **范围评估**：
  - 涉及的库/表/字段：列出清单（如`ecommerce.order`、`ecommerce.user`）；
  - 关联系统：哪些微服务/接口依赖该表（如订单服务、用户服务）；
  - 数据量：目标表的总行数、单表大小（如`order`表500万行，占用10GB）；
  - 业务高峰：确认升级窗口（优先选凌晨2-4点，业务QPS低于日常10%的时段）。
- **风险评估（核心）**：

  | 风险点                | 评估结果                          | 应对措施                          |
  |-----------------------|-----------------------------------|-----------------------------------|
  | 大表ALTER锁表         | `order`表500万行，直接ALTER会锁表30+分钟 | 用pt-online-schema-change在线DDL |
  | 版本升级语法兼容      | MySQL8.0废弃`PASSWORD()`函数       | 提前修改代码中相关SQL             |
  | 数据迁移丢失          | INT→BIGINT可能截断超大值           | 迁移前校验数据最大值              |

#### 1.2 方案设计（必须落地为可执行文档）

- **核心内容**：
  1. 升级脚本：版本化命名（如`V20260118_01__add_order_express_field.sql`），包含“执行SQL+回滚SQL”；
  2. 执行方式：在线DDL/离线执行、分批/一次性执行；
  3. 时间窗口：开始/结束时间、超时阈值（如超过30分钟终止执行）；
  4. 责任人：执行方、验证方、应急联系人；
  5. 回滚触发条件：如“业务报错率＞0.1%”“数据不一致＞1%”“锁等待＞5分钟”。
- **脚本规范**：
  - 禁止用`SELECT *`，必须指定字段；
  - 所有DDL加`IF NOT EXISTS`/`IF EXISTS`（保证幂等）；
  - 大表操作加`LIMIT`/分批（如数据迁移每次10万行）；
  - 示例（表结构升级脚本）：

    ```sql
    -- 升级SQL：新增物流字段（加默认值，兼容老服务）
    ALTER TABLE `order` 
    ADD COLUMN IF NOT EXISTS `express_no` VARCHAR(50) DEFAULT '' COMMENT '物流单号' AFTER `amount`;
    -- 回滚SQL：删除新增字段
    ALTER TABLE `order` DROP COLUMN IF EXISTS `express_no`;
    ```

#### 1.3 环境准备

- **备份（核心中的核心）**：
  - 全量备份：用`mysqldump`+`--single-transaction`（InnoDB无锁），示例：

    ```bash
    # 备份指定库，包含存储过程/函数，输出到压缩文件
    mysqldump -u root -p --single-transaction --routines --triggers ecommerce > ecommerce_20260118_backup.sql.gz
    ```

  - binlog备份：确保`log_bin`开启，备份升级前的binlog文件（用于增量恢复）；
  - 备份校验：随机抽查备份文件中的表结构/数据，确认备份完整。
- **环境隔离**：
  - 测试环境：复刻生产数据（至少10%生产数据量）；
  - 预发环境：与生产配置（硬件/MySQL参数/业务流量）一致；
- **权限准备**：
  - 升级账号：仅授予“执行升级所需的最小权限”（如`ALTER`/`CREATE`），禁止用`root`执行；
  - 临时关闭只读：若主从架构，升级主库前确认`read_only=OFF`。

#### 1.4 脚本开发与预演

- **脚本开发**：
  - 表结构升级：小表用原生`ALTER`，大表用`pt-online-schema-change`/`gh-ost`（在线无锁）；
  - 版本升级：先整理《版本兼容差异清单》（如MySQL8.0的`sql_mode`默认包含`STRICT_TRANS_TABLES`）；
- **预演（必须执行）**：
  1. 在**测试环境**执行升级脚本，记录：执行耗时、锁等待时间、CPU/IO使用率；
  2. 验证业务功能：老版本服务是否兼容新结构、新版本功能是否正常；
  3. 验证回滚脚本：执行回滚，确认数据/结构恢复到升级前状态；
  4. 预演问题记录：如“`pt-online-schema-change`执行耗时超预期”，调整为分批执行。

### 阶段2：升级执行（核心是“可控、可暂停”）

核心目标：**在预定窗口内执行，实时监控，异常立即终止**。

#### 2.1 执行前最后检查（5分钟快速核对）

- 确认业务低峰期（通过监控平台看QPS/TP99）；
- 确认备份已完成且校验通过；
- 确认相关业务方已通知（如运维、开发、客服，准备应对用户咨询）；
- 关闭非必要定时任务（如数据同步、报表统计，避免干扰升级）。

#### 2.2 分批次执行（按“环境→流量”梯度）

| 执行阶段       | 操作内容                                                                 |
|----------------|--------------------------------------------------------------------------|
| 测试环境       | 执行升级脚本→验证功能→执行回滚→再次升级（验证回滚后可重升）|
| 预发环境       | 执行升级脚本→压测（模拟生产流量）→验证数据一致性→观察24小时               |
| 生产灰度（10%） | 仅升级生产1台从库→切10%读流量到该从库→监控报错/性能→无异常则继续          |
| 生产全量       | 升级主库→升级剩余从库→切全量流量→关闭灰度开关                             |

#### 2.3 执行中的实时监控

- 核心监控指标（通过Prometheus/Grafana/MySQL自带工具）：
  - 锁相关：`Innodb_row_lock_waits`（行锁等待数）、`Table_locks_waited`（表锁等待数）；
  - 性能相关：QPS/TPS、慢查询数、CPU/IO使用率、磁盘空间；
  - 业务相关：接口报错率、响应时间（TP99/TP95）；
- 异常处理：
  - 若锁等待＞5分钟/报错率＞0.1%，立即执行“暂停升级→触发回滚”；
  - 记录异常日志（时间、指标值、操作人），便于事后分析。

### 阶段3：升级后验证（覆盖“数据+功能+性能”）

核心目标：**确认升级达到预期，无隐性问题**。

#### 3.1 数据一致性验证

- 表结构验证：`DESC 表名`/`SHOW CREATE TABLE 表名`，确认字段/索引/字符集符合预期；
- 数据量验证：对比升级前后核心表的总行数（如`SELECT COUNT(*) FROM order`）；
- 数据内容验证：随机抽查100条数据（如新增字段是否有默认值、修改字段是否无截断）；
- 关联数据验证：多表联查（如`order`+`user`），确认关联逻辑正常。

#### 3.2 业务功能验证

- 核心流程全链路测试（如电商的“下单→支付→发货”）；
- 老功能验证：确保升级不影响历史功能（如老版本APP下单）；
- 新功能验证：确认升级带来的新功能正常（如物流单号写入/查询）。

#### 3.3 性能验证

- 对比升级前后的慢查询日志（用`pt-query-digest`分析）；
- 压测核心接口（如订单查询），确认响应时间无明显上升；
- 检查索引使用率（`sys.schema_unused_indexes`），避免新增索引未生效。

### 阶段4：升级后运维与归档

- **持续监控**：
  - 表结构升级：监控24小时；
  - 版本/架构升级：监控72小时（观察重启/峰值流量后的稳定性）；
- **日志归档**：
  - 记录升级全流程日志（需求→方案→执行步骤→验证结果→异常处理）；
  - 归档升级脚本（按版本号存储到Git/SVN）；
  - 更新数据库字典文档（同步字段/索引变更）；
- **权限回收**：
  - 回收升级时临时授予的高权限；
  - 恢复只读/定时任务等原有配置。

## 三、不同类型升级的细化流程

### 3.1 表结构升级（最常见）

#### 小表升级（＜100万行）

- 执行方式：直接用原生`ALTER TABLE`，选低峰期执行；
- 关键注意：
  - 新增字段必须加默认值（避免老服务插入报错）；
  - 修改字段长度时，先查`MAX(LENGTH(字段))`确认无截断；
  - 示例：

    ```sql
    -- 新增字段（带默认值）
    ALTER TABLE user ADD COLUMN avatar VARCHAR(255) DEFAULT '' COMMENT '头像URL' AFTER nickname;
    -- 修改字段长度（先查最大值）
    SELECT MAX(LENGTH(phone)) FROM user; -- 若最大值11，改为VARCHAR(20)无风险
    ALTER TABLE user MODIFY phone VARCHAR(20) NOT NULL COMMENT '手机号';
    ```

#### 大表升级（≥100万行）

- 执行方式：用**在线DDL工具**（避免锁表），推荐`pt-online-schema-change`（Percona）；
- 核心命令：

  ```bash
  # 给order表新增express_no字段，无锁执行
  pt-online-schema-change \
  D=ecommerce,t=order \
  --alter "ADD COLUMN express_no VARCHAR(50) DEFAULT '' COMMENT '物流单号'" \
  --execute \
  --no-drop-old-table \ # 暂不删除旧表，验证后手动删
  --chunk-size=1000 \ # 每次处理1000行，降低IO压力
  --sleep=0.1 \ # 每批处理后休眠0.1秒
  -u saas_admin -p '密码' -h 127.0.0.1
  ```

- 注意事项：
  - 执行前关闭表的触发器（避免双写冲突）；
  - 执行中监控`pt-osc`进程，避免中断；
  - 验证后再删除旧表（`--drop-old-table`）。

### 3.2 MySQL版本升级（如5.7→8.0）

#### 核心前置检查

- 检查兼容项：

  ```sql
  -- 检查废弃函数（如PASSWORD()、SHA1()）
  SELECT * FROM sys.schema_unused_indexes;
  -- 检查sql_mode兼容性（8.0默认严格模式）
  SHOW VARIABLES LIKE 'sql_mode';
  -- 检查字符集（8.0默认utf8mb4）
  SHOW VARIABLES LIKE 'character_set%';
  ```

- 升级依赖：更新JDBC驱动（如`mysql-connector-java`≥8.0）、代码中适配语法（如`GROUP BY`兼容）。

#### 执行步骤

1. 升级前：全量备份+停止写入→升级MySQL依赖包（如libmysqlclient）；
2. 灰度升级：先升级从库→将从库升级为独立实例→验证功能→切读流量；
3. 主库升级：停主库→升级→重启→重建主从同步（8.0的GTID需兼容5.7）；
4. 验证：检查主从同步状态（`SHOW SLAVE STATUS`）、业务功能、性能。

### 3.3 架构升级（单库→分库分表）

#### 核心流程

1. 准备阶段：部署分库分表中间件（Sharding-JDBC）→创建分库分表结构→配置路由规则（如按`user_id`分库）；
2. 双写阶段：修改代码，写入旧库的同时写入新库→分批迁移历史数据（用DataX）；
3. 灰度阶段：切10%读流量到新库→对比新旧库数据一致性；
4. 全量切换：切全量读写流量到新库→停止旧库写入→保留旧库1个月作为备份。

## 四、全量注意事项（避坑核心）

### 4.1 安全类

- **禁止无备份升级**：哪怕是“新增一个索引”，也必须先备份；
- **禁止生产直接执行手写SQL**：所有脚本必须在测试环境验证过，版本化管理；
- **禁止高峰期升级**：哪怕是小修改，也避免在业务高峰（如电商大促）执行；
- **密码/权限安全**：升级账号用完即回收，禁止明文存储密码。

### 4.2 性能类

- **大表操作避免一次性执行**：数据迁移/DDL分批处理，每次≤10万行；
- **索引新增需评估**：过多索引会拖慢写入，新增后检查使用率；
- **避免长事务**：升级期间禁止执行长事务（如`SELECT * FROM 大表`），会导致锁等待。

### 4.3 兼容类

- **向后兼容优先**：新增字段加默认值、修改字段兼容旧类型、删除字段先标记废弃再下线；
- **多版本服务兼容**：升级后确保老版本服务（如V1.0）能正常读写新结构；
- **字符集/校对规则统一**：避免库/表/字段字符集不一致（如部分utf8、部分utf8mb4）。

### 4.4 回滚类

- **所有升级必须有回滚脚本**：脚本与升级脚本一一对应，预演时验证可执行；
- **回滚触发条件明确**：量化指标（如报错率＞0.1%），避免“凭感觉”回滚；
- **回滚后验证**：回滚完成后，必须验证数据/功能恢复到升级前状态。

## 五、回滚预案（不同场景的回滚步骤）

| 升级类型       | 回滚步骤                                                                 |
|----------------|--------------------------------------------------------------------------|
| 表结构升级     | 1. 执行预编写的回滚SQL（如DROP COLUMN）；2. 恢复索引/约束；3. 验证表结构/数据 |
| 版本升级       | 1. 停止业务写入；2. 回滚MySQL二进制包到旧版本；3. 恢复备份数据；4. 重建主从 |
| 架构升级       | 1. 切回流量到旧库；2. 停止新库双写；3. 恢复旧库的读写权限；4. 校验数据一致性 |

## 六、总结

MySQL生产升级的核心是**“慢准备、快执行、可回滚”**：

1. 升级前：60%精力做需求分析、备份、预演，把风险提前暴露；
2. 执行中：按“环境→流量”梯度执行，实时监控核心指标，异常立即回滚；
3. 升级后：全维度验证（数据+功能+性能），持续监控72小时；
4. 核心原则：始终保留“回滚路径”，任何升级都不能“破釜沉舟”。
