# 数据库兼容处理

## 一、数据库升级迭代的完整流程

数据库升级不是“直接改表结构”，而是分阶段的工程化操作，流程如下：

### 1. 升级前：准备与评估

- **需求&影响分析**：
  - 明确升级目的（比如加字段、分表、优化索引）；
  - 评估影响范围：涉及哪些业务表、关联哪些服务、数据量多大、是否会锁表/阻塞业务。
- **方案设计**：
  - 写**可版本化的升级脚本**（用`Flyway`/`Liquibase`管理，每个版本对应一个脚本，支持回滚）；
  - 确定升级时机：选业务低峰期（比如凌晨），避免影响核心流量；
  - 制定**回滚预案**：升级前做全量数据备份（`mysqldump`+`binlog`），明确回滚触发条件（比如升级后业务报错率超过1%）。
- **测试验证**：
  - 在**测试环境**复现生产数据量，执行升级脚本，测试：
    - 升级耗时（避免生产环境超时）；
    - 新表结构是否符合预期；
    - 老版本服务连新数据库是否正常运行（兼容性测试）。

### 2. 升级中：灰度&分批执行

- **小流量灰度**：
  - 先升级**测试环境**→再升级**预发布环境**→最后升级生产环境的“部分节点”（比如先切10%流量到新数据库配置）；
  - 观察业务日志、监控（慢查询、错误率），确认无问题后再全量升级。
- **分批执行大操作**：
  - 若涉及大表（100万行以上）的`ALTER TABLE`/数据迁移，用**分批操作**避免锁表：
    - 比如分10次迁移数据，每次迁移10万行，中间加休眠（避免IO打满）；
    - 用在线DDL工具（`pt-online-schema-change`/`gh-ost`）做无锁表结构变更。

### 3. 升级后：验证&监控

- 验证数据一致性：对比升级前后核心数据（比如用户数、订单数）是否一致；
- 持续监控24小时：观察慢查询、锁等待、业务报错，确保升级无后遗症；
- 记录升级日志：包括脚本版本、执行时间、影响范围，方便后续追溯。

## 二、如何做到“兼容老版本”？

兼容的核心是**“向后兼容”**：新数据库结构能支持老版本服务的读写，老服务无需修改即可正常运行。具体方法分3类：

### 1. 表结构变更的兼容

#### （1）新增字段/索引：“加而不删”

- **规则**：只新增字段/索引，不删除旧字段（即使旧字段不再使用），避免老服务读取/写入时报错。
- **示例**：
  老版本`user`表有`id, username, password`，新版本要加`nickname`：

  ```sql
  -- 新增字段，加默认值（避免老服务插入时因“非空”报错）
  ALTER TABLE user ADD COLUMN nickname VARCHAR(50) DEFAULT '' COMMENT '昵称' AFTER username;
  ```

  老服务写入时不会传`nickname`，数据库会自动填默认值；老服务读取时忽略`nickname`，完全兼容。

#### （2）修改字段：“兼容旧类型/长度”

- **规则**：修改字段时，新类型要包含旧类型的取值范围，避免老数据无法存储。
- **示例**：
  - 旧字段`age TINYINT`→新字段`age INT`（`INT`能包含`TINYINT`的所有值，老数据无需转换）；
  - 旧字段`phone VARCHAR(11)`→新字段`phone VARCHAR(20)`（支持国际手机号，老数据的11位手机号可正常存储）。

#### （3）拆分/合并表：“双写+逐步切换”

- 若要拆分大表（比如`order`拆成`order_basic`和`order_extra`），先做“双写兼容”：
  1. 新建拆分后的表；
  2. 老服务写入旧表时，**同时写入新表**（通过代码/触发器实现双写）；
  3. 同步历史数据到新表（分批迁移，避免锁表）；
  4. 新服务优先读新表，老服务继续读旧表；
  5. 待老服务全部升级后，停止双写，下线旧表。

### 2. 数据层面的兼容

- **兼容旧数据格式**：
  若新功能需要新数据格式（比如旧版`address`是字符串，新版是JSON），可做“兼容解析”：

  ```sql
  -- 新增address_json字段存储新格式，旧address字段保留
  ALTER TABLE user ADD COLUMN address_json JSON COMMENT '地址（JSON格式）';
  
  -- 老服务写address，新服务写address_json；读取时优先读address_json，没有则读address
  SELECT IFNULL(address_json, JSON_OBJECT('old_address', address)) AS address FROM user;
  ```

- **避免数据截断**：
  修改字段长度时，先确认老数据的最大长度，比如旧`username VARCHAR(20)`，先查`MAX(LENGTH(username))`，若最大是15，则改为`VARCHAR(30)`（留冗余）。

### 3. 业务逻辑的兼容

- **接口/代码适配**：
  新服务用新字段，老服务用旧字段，通过“适配层”兼容：
  - 后端接口返回同时包含新旧字段（比如老接口返回`username`，新接口返回`username+nickname`）；
  - 前端根据版本选择显示字段，避免因字段缺失报错。
- **禁用“强依赖新结构”的逻辑**：
  升级后，新功能先灰度发布（仅对部分用户开放），老功能保持不变，直到老服务全部升级。

## 三、如果“无法兼容”，怎么处理？

有些场景必然不兼容（比如删旧字段、改主键、大表重构），此时需要“分阶段隔离+逐步迁移”，核心是**“让新老版本同时运行，最后下线老版本”**。

### 1. 场景1：必须删除旧字段/表

- **处理步骤**：
  1. **标记废弃**：先在旧字段加注释（`COMMENT '已废弃，2026-03-01下线'`），通知所有依赖服务停止使用；
  2. **监控使用情况**：通过慢查询日志/业务日志，确认没有服务再读写该字段；
  3. **删除字段**：在低峰期执行`ALTER TABLE 表名 DROP COLUMN 旧字段;`。

### 2. 场景2：修改主键/核心字段（比如`id`从`INT`改`BIGINT`）

- **处理步骤**：
  1. **新增新主键字段**：比如旧主键`id INT`，新增`new_id BIGINT AUTO_INCREMENT`；
  2. **双写+同步**：老服务写`id`，新服务写`new_id`，同时通过触发器/定时任务同步`id`和`new_id`的映射关系；
  3. **切换关联关系**：将所有关联表的外键从`id`改为`new_id`（分批修改）；
  4. **替换主键**：待所有服务都用`new_id`后，删除旧`id`字段，将`new_id`改名为`id`。

### 3. 场景3：数据库重构（比如分库分表）

- **处理步骤**：
  1. **新库并行部署**：搭建分库分表后的新数据库（比如用Sharding-JDBC）；
  2. **双写数据**：老服务写旧库，同时通过消息队列（Kafka）同步数据到新库；新服务直接写新库；
  3. **灰度切换流量**：先将部分读流量切到新库，验证无误后切写流量；
  4. **下线旧库**：待所有服务都切换到新库，且历史数据迁移完成后，下线旧库。

### 4. 极端情况：强制升级（无法兼容）

若业务要求必须立即升级（比如修复严重数据安全漏洞）：

- **提前通知**：告知用户/业务方“升级窗口”（比如凌晨2-4点停机维护）；
- **停机升级**：暂停所有业务写操作，执行升级脚本，验证通过后恢复服务；
- **补偿机制**：若升级导致数据丢失，用备份恢复，并补偿受影响的用户（比如发优惠券）。

## 四、实战工具与建议

- **版本化迁移工具**：用`Flyway`/`Liquibase`管理升级脚本，每个脚本对应一个版本号（比如`V1__add_nickname.sql`），支持`migrate`（升级）和`undo`（回滚）；
- **监控工具**：用`Prometheus+Grafana`监控数据库的`QPS`、锁等待、慢查询；用`pt-query-digest`分析慢查询日志；
- **文档同步**：每次升级后，更新数据库字典文档（比如用`Sqlyog`/`Navicat`导出表结构），通知所有依赖团队；
- **避免“一次性大变更”**：将大升级拆成多个小版本（比如先加字段，再迁移数据，最后删旧字段），降低风险。
