# 注意事项

## 一、「数据类型」相关坑

### 1. 字符集：误用`utf8`而非`utf8mb4`

- **坑**：MySQL里的`utf8`仅支持**3字节字符**，无法存储emoji、部分生僻字（比如“𠀀”），插入会报错或乱码。
- **注意点**：
  所有库/表/字段统一用`utf8mb4`（真正的UTF-8），搭配排序规则`utf8mb4_unicode_ci`（支持多语言排序）。

### 2. 时间类型：`datetime` vs `timestamp`的时区陷阱

- **坑**：
  - `datetime`：存储“绝对时间字符串”，不随MySQL时区设置变化；
  - `timestamp`：存储“Unix时间戳”，会随MySQL的`time_zone`参数自动转换时区。
  若混用两者，或时区配置不一致，会导致时间显示错乱。
- **注意点**：
  - 业务系统统一用`datetime`（避免时区依赖），或全局统一`time_zone`（比如`SET GLOBAL time_zone = '+8:00';`）。

### 3. 数值类型：`int(N)`的“显示长度”误区

- **坑**：新手误以为`int(11)`是“存储长度为11位”，实际`int`的存储长度固定4字节（范围`-2^31~2^31-1`），`N`只是**显示宽度**（仅当配合`ZEROFILL`时，不足N位补0）。
- **注意点**：
  无需纠结`int`的括号数字，根据实际范围选类型：
  - 非负用`INT UNSIGNED`（范围`0~4294967295`）；
  - 小数值用`TINYINT`（1字节）、`SMALLINT`（2字节），避免浪费空间。

### 4. 浮点类型：`float/double`的精度丢失

- **坑**：`float/double`是**近似浮点型**，存储金额、精度要求高的数值时，会出现`0.1+0.2≠0.3`的情况。
- **注意点**：
  金额类字段用`DECIMAL(M,D)`（精确小数型），比如`DECIMAL(10,2)`表示总长度10、小数位2。

## 二、「SQL语法」相关坑

### 1. `DELETE/UPDATE` 忘记加`WHERE`条件

- **坑**：执行`DELETE FROM 表名;`或`UPDATE 表名 SET 字段=值;`会**全表删除/更新**，生产环境直接导致数据灾难。
- **注意点**：
  - 执行前先加`LIMIT`测试：`DELETE FROM 表名 WHERE 条件 LIMIT 10;`（确认条件正确再放大）；
  - 开启MySQL的`sql_safe_updates=1`（禁止无`WHERE`/`LIMIT`的`DELETE/UPDATE`）。

### 2. `LIMIT`的分页性能陷阱（大偏移量）

- **坑**：`SELECT * FROM 表名 LIMIT 100000, 10;` 会先扫描前100010条数据再丢弃，偏移量越大越慢。
- **注意点**：
  用**主键/唯一索引分页**：

  ```sql
  SELECT * FROM 表名 WHERE id > 100000 LIMIT 10;  -- 基于上一页最后一条的id
  ```

### 3. `LIKE '%xxx'`导致索引失效

- **坑**：`WHERE 字段 LIKE '%zhangsan'` 中，`%`开头会让字段的索引完全失效，变成全表扫描。
- **注意点**：
  - 若要前缀模糊匹配，用`LIKE 'zhangsan%'`（可命中索引）；
  - 全模糊匹配用**全文索引**（`FULLTEXT`）或搜索引擎（比如Elasticsearch）。

### 4. `COUNT(*)`/`COUNT(1)`/`COUNT(字段)`的区别

- **坑**：
  - `COUNT(*)`：统计所有行数（包括`NULL`行），效率最高（InnoDB会优化）；
  - `COUNT(字段)`：统计“字段非NULL的行数”，若字段有`NULL`会少统计；
  - 新手常误用`COUNT(字段)`代替`COUNT(*)`，导致统计结果错误。
- **注意点**：统计行数优先用`COUNT(*)`。

### 5. `INSERT INTO ... SELECT` 无限制导致锁表

- **坑**：`INSERT INTO 新表 SELECT * FROM 旧表;` 若旧表数据量大，会长期占用锁，阻塞其他操作。
- **注意点**：
  分批插入：

  ```sql
  INSERT INTO 新表 SELECT * FROM 旧表 WHERE id BETWEEN 1 AND 1000;
  INSERT INTO 新表 SELECT * FROM 旧表 WHERE id BETWEEN 1001 AND 2000;
  ```

## 三、「事务与锁」相关坑

### 1. 事务未提交导致锁表

- **坑**：执行`UPDATE/DELETE`后忘记`COMMIT`，事务会一直持有行锁/表锁，导致其他请求阻塞。
- **注意点**：
  - 开启事务后及时`COMMIT`/`ROLLBACK`；
  - 用`SHOW PROCESSLIST;`查看阻塞进程，`KILL 进程ID;`紧急解锁。

### 2. InnoDB行锁升级为表锁

- **坑**：InnoDB的行锁依赖**索引**，若`WHERE`条件没命中索引（比如`WHERE 非索引字段=值`），会升级为**表锁**，阻塞全表写操作。
- **注意点**：
  - 所有`UPDATE/DELETE`的`WHERE`条件必须命中索引；
  - 用`EXPLAIN`查看SQL执行计划，确认`type`不是`ALL`（全表扫描）。

### 3. 隔离级别导致的“幻读”

- **坑**：默认隔离级别`REPEATABLE READ`下，同一事务中多次`SELECT`可能读到“幻象数据”（其他事务提交的新数据）。
- **注意点**：
  - 若业务要求“绝对一致性”，将隔离级别设为`SERIALIZABLE`（但性能会下降）；
  - 用`FOR UPDATE`加行锁避免幻读：`SELECT * FROM 表名 WHERE 条件 FOR UPDATE;`

## 四、「索引」相关坑

### 1. 复合索引的“最左匹配”失效

- **坑**：创建复合索引`idx_age_name(age, name)`后，`WHERE name='zhangsan'` 不会命中索引（违背最左匹配）。
- **注意点**：
  - 复合索引的字段顺序按“查询频率从高到低”排列；
  - 若要单独查`name`，需单独建`idx_name`索引。

### 2. 索引字段做函数运算导致失效

- **坑**：`WHERE DATE(create_time) = '2026-01-16'` 中，`DATE()`函数会让`create_time`的索引失效。
- **注意点**：
  改写为“字段本身参与条件”：

  ```sql
  WHERE create_time BETWEEN '2026-01-16 00:00:00' AND '2026-01-16 23:59:59';
  ```

### 3. 唯一索引允许多个`NULL`值

- **坑**：`UNIQUE KEY idx_email(email)` 中，`email`字段可以插入多个`NULL`（因为`NULL`不与任何值相等），导致“唯一约束失效”。
- **注意点**：
  若要禁止`NULL`，给字段加`NOT NULL`约束；若需允许`NULL`且唯一，用`COALESCE`处理：

  ```sql
  UNIQUE KEY idx_email (COALESCE(email, ''));  -- 将NULL转为空字符串，避免重复
  ```

### 4. 过多索引拖慢写入性能

- **坑**：给表加10+个索引，会导致`INSERT/UPDATE/DELETE`的性能急剧下降（每次写入要更新所有索引）。
- **注意点**：
  - 索引数控制在5个以内；
  - 优先给“查询频繁、区分度高”的字段建索引（比如`username`区分度高，`gender`区分度低，不适合建索引）。

## 五、「权限与安全」相关坑

### 1. 业务系统用`root`账号连接MySQL

- **坑**：`root`有“删库删表”的最高权限，若业务代码被注入SQL，会直接导致数据全失。
- **注意点**：
  给业务系统创建专用账号，仅授予必要权限：

  ```sql
  CREATE USER 'app_user'@'%' IDENTIFIED BY '安全密码';
  GRANT SELECT,INSERT,UPDATE,DELETE ON 业务库.* TO 'app_user'@'%';  -- 仅增删改查
  ```

### 2. 允许`%`任意IP远程登录

- **坑**：`'user'@'%'` 允许任意IP连接MySQL，若密码泄露，会被恶意攻击。
- **注意点**：
  限制登录IP为业务服务器的固定IP：

  ```sql
  CREATE USER 'app_user'@'192.168.1.100' IDENTIFIED BY '密码';  -- 仅允许192.168.1.100登录
  ```

### 3. 敏感数据明文存储

- **坑**：密码、手机号等敏感数据直接存明文，若数据库泄露，会导致信息泄露。
- **注意点**：
  - 密码用`BCrypt`/`Argon2`等哈希算法加密（不可逆）；
  - 手机号、身份证号用AES对称加密存储。

## 六、「备份与恢复」相关坑

### 1. `mysqldump`备份InnoDB表时锁表

- **坑**：直接执行`mysqldump -u root -p 库名 > 备份.sql`，会对InnoDB表加表锁，导致业务写入阻塞。
- **注意点**：
  加`--single-transaction`参数（利用事务一致性视图备份，无锁）：

  ```bash
  mysqldump -u root -p --single-transaction 库名 > 备份.sql
  ```

### 2. 恢复备份时字符集不匹配导致乱码

- **坑**：备份时数据库字符集是`utf8mb4`，恢复时目标库字符集是`latin1`，导致数据乱码。
- **注意点**：
  恢复前确认目标库字符集与备份一致，或在恢复命令中指定字符集：

  ```bash
  mysql -u root -p --default-character-set=utf8mb4 库名 < 备份.sql
  ```

### 3. 仅做全量备份，无增量备份

- **坑**：每天凌晨全量备份，若中午数据库崩溃，会丢失当天上午的数据。
- **注意点**：
  - 全量备份+`binlog`增量备份（MySQL开启`log_bin`）；
  - 用`mysqlbinlog`恢复增量数据：

    ```bash
    mysqlbinlog --start-datetime='2026-01-16 00:00:00' binlog.000001 | mysql -u root -p
    ```

## 七、「运维与性能」相关坑

### 1. `innodb_buffer_pool_size`设置太小

- **坑**：这个参数是InnoDB的“缓存池”（缓存表数据和索引），若设置太小（比如默认128M），会导致频繁磁盘IO，性能暴跌。
- **注意点**：
  生产环境设为物理内存的50%-70%（比如16G内存设为10G）：

  ```ini
  # my.cnf配置
  innodb_buffer_pool_size = 10G
  ```

### 2. 大表直接执行`ALTER TABLE`

- **坑**：对1000万行的大表执行`ALTER TABLE 表名 ADD 字段;`，会锁表数小时，业务完全不可用。
- **注意点**：
  用在线DDL工具（比如Percona的`pt-online-schema-change`），无锁修改表结构：

  ```bash
  pt-online-schema-change D=库名,t=表名 --alter="ADD COLUMN new_col INT" --execute
  ```

### 3. 忽略慢查询日志

- **坑**：没开启慢查询日志，无法发现“执行时间超过1秒”的慢SQL，导致系统逐渐变卡。
- **注意点**：
  开启慢查询日志，阈值设为1秒：

  ```ini
  slow_query_log = ON
  slow_query_log_file = /var/log/mysql/slow.log
  long_query_time = 1  # 执行超过1秒的SQL记录到日志
  ```

## 总结

MySQL的“坑”本质是**对特性的理解不足**，避免踩坑的核心是：

1. 操作前先测试（比如`DELETE`先加`LIMIT`）；
2. 用`EXPLAIN`分析SQL执行计划；
3. 生产环境遵循“最小权限、最小影响”原则；
4. 定期检查慢查询、索引、锁状态。
