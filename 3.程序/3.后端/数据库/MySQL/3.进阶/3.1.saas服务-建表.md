# SaaS服务-建表

在SaaS服务中，**数据隔离的核心是“在成本、隔离性、扩展性之间做平衡”**，不同的租户规模、数据量、合规要求对应不同的隔离方案。先讲清SaaS常见的3种数据隔离方案，再结合你的“拜访服务”场景给出具体建议：

## 一、SaaS数据隔离的3种核心方案

### 方案1：租户独立数据库（物理隔离）

- **实现方式**：给每个租户分配**独立的数据库实例**（比如每个公司对应一个MySQL库）。
- **隔离性**：物理级隔离，数据完全独立，租户之间无影响（符合金融、医疗等强合规场景）。
- **成本**：极高（每个库需要独立的服务器/资源），仅适合**租户数量少、付费高的大型企业客户**（比如SaaS服务的“企业版”客户）。
- **维护**：需要自动化的数据库创建/销毁工具（比如通过K8s动态创建库实例），否则运维成本爆炸。

### 方案2：共享数据库+租户独立表（逻辑隔离-分表）

- **实现方式**：多个租户共享一个数据库，但每个租户对应**独立的表**（比如拜访服务的表名是`visit_tenant_1001`、`visit_tenant_1002`，后缀是租户ID）。
- **隔离性**：逻辑级隔离，表之间相互独立，不会出现数据混查，但共享数据库资源（比如CPU/内存）。
- **成本**：中等（一个库承载多个租户表），适合**租户数量中等（几百到几千）、数据量较大**的场景。
- **维护**：需要“表路由规则”（比如按租户ID映射表名），且要避免表数量过多（一个库建议不超过1000张表，否则元数据管理压力大）。

### 方案3：共享数据库+共享表（逻辑隔离-字段标识）

- **实现方式**：所有租户共享同一个数据库、同一个表，通过**表中新增`tenant_id`字段**区分不同租户（比如拜访表的每一行都带`tenant_id=1001`表示属于公司1001）。
- **隔离性**：弱隔离（依赖代码逻辑保证`tenant_id`的过滤），但只要代码规范，能满足大部分普通场景。
- **成本**：极低（一个表承载所有租户数据），适合**租户数量多（几千到几万）、单租户数据量小**的场景（比如中小微企业客户）。
- **维护**：简单，但要注意“查询必须带`tenant_id`”（避免跨租户泄露数据），且需给`tenant_id`加索引（保证查询性能）。

## 二、你的“拜访服务”要不要分表？

需结合**租户规模、单租户数据量、隔离要求**来判断：

### 场景1：租户少（<100个）、单租户数据量大（每个租户年拜访量>10万）

→ **建议用“方案2（共享库+分表）”**

- 原因：单租户数据量大，共享表会导致表行数爆炸（比如100个租户×10万行=1000万行，后期查询变慢）；分表后每个租户表数据量可控，性能更稳定。
- 实现示例：
  - 表名规则：`visit_${tenant_id}`（比如`visit_1001`对应租户1001）；
  - 代码中按租户ID动态拼接表名，执行SQL：`SELECT * FROM visit_1001 WHERE ...`。

### 场景2：租户多（>1000个）、单租户数据量小（每个租户年拜访量<1万）

→ **建议用“方案3（共享库+共享表）”**

- 原因：单租户数据量小，共享表的总行数可控（比如1万租户×1万行=1亿行，加`tenant_id`索引后查询性能足够）；分表会导致表数量过多，运维成本高。
- 实现注意点：
  1. 表必须加`tenant_id`字段（作为租户标识）；
  2. 所有查询/写入SQL必须带`tenant_id`（比如`SELECT * FROM visit WHERE tenant_id=1001 AND ...`，禁止不带`tenant_id`的全表查询）；
  3. 索引必须包含`tenant_id`（比如建复合索引`idx_tenant_date(tenant_id, visit_date)`，保证租户内的查询效率）。

### 场景3：租户是大型企业（付费高、合规要求高）

→ **建议用“方案1（独立数据库）”**

- 原因：大型企业可能要求“数据物理隔离”（比如金融行业的监管要求），独立库能完全满足隔离性，且单租户资源独立，性能更有保障。

## 三、实践中的关键注意点

1. **避免跨租户数据泄露**：
   - 无论用哪种方案，代码层必须强制校验“当前登录用户所属的`tenant_id`”，确保只能操作本租户的数据；
   - 用ORM框架的“多租户插件”（比如MyBatis-Plus的多租户插件）自动给SQL加`tenant_id`条件，避免人工遗漏。

2. **性能优化**：
   - 共享表场景：`tenant_id`必须作为索引的前缀（比如复合索引`idx_tenant_user(tenant_id, user_id)`），否则会出现全表扫描；
   - 分表场景：用“租户ID哈希+固定分表数”（比如按`tenant_id % 64`分64张表），避免表数量无限膨胀。

3. **扩展性预留**：
   - 初期用共享表，后期数据量大了可升级为分表（通过“双写+迁移”：先给共享表加`tenant_id`，再分批迁移数据到分表，最后切换路由）；
   - 分表可升级为分库（按`tenant_id % N`分N个库，每个库再分表）。

## 总结你的拜访服务

- **中小租户、数据量小**：优先选“共享库+共享表+`tenant_id`字段”（成本低、易维护）；
- **租户较多、单租户数据量大**：选“共享库+分表”（平衡成本和性能）；
- **大型企业租户**：选“独立数据库”（满足隔离/合规要求）。
