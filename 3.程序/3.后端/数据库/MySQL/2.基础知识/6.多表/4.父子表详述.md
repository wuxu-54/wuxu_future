# 父表与子表

 SQL 中「父表」和「子表」的核心定义、它们之间的关系，以及在数据库设计和操作中的具体作用，希望通过清晰的解释和例子理解这两个基础但关键的概念。

## 一、父表 & 子表的核心定义

父表和子表是基于 **外键（Foreign Key）约束** 建立的一对多关系中的两个表，核心逻辑是「依赖与被依赖」：

- **父表（Parent Table）**：也叫“主表/参照表”，是被引用的表——包含**主键（Primary Key）**，存储“基础/公共”数据，是关系的“一方”。
- **子表（Child Table）**：也叫“从表/引用表”，是引用父表的表——包含**外键（Foreign Key）**，外键字段的值必须匹配父表的主键值，存储“从属/明细”数据，是关系的“多方”。

### 通俗比喻

可以把父表理解为“部门表”，子表理解为“员工表”：

- 一个部门（父表）可以有多个员工（子表），但一个员工只能属于一个部门；
- 员工表必须依赖部门表存在（不能有“不属于任何部门的员工”），部门表则可以独立存在。

## 二、核心关系：外键是连接的桥梁

父表和子表的关联完全依赖「外键约束」，外键的本质是：**子表的某个字段（外键）必须引用父表的主键字段，且值必须在父表主键中存在**（除非为 NULL，若允许）。

### 实战例子（最常见的“一对多”场景）

#### 1. 创建父表（部门表）

```sql
-- 父表：t_department（部门表，存储公共的部门信息）
CREATE TABLE t_department (
    dept_id INT PRIMARY KEY AUTO_INCREMENT, -- 主键（父表核心）
    dept_name VARCHAR(50) NOT NULL, -- 部门名称
    dept_desc VARCHAR(200) -- 部门描述
);

-- 插入父表数据
INSERT INTO t_department (dept_name, dept_desc) 
VALUES ('研发部', '负责产品开发'), ('人事部', '负责人力管理');
```

#### 2. 创建子表（员工表，含外键引用父表）

```sql
-- 子表：t_employee（员工表，存储从属的员工信息）
CREATE TABLE t_employee (
    emp_id INT PRIMARY KEY AUTO_INCREMENT, -- 员工主键
    emp_name VARCHAR(50) NOT NULL, -- 员工姓名
    dept_id INT, -- 外键：引用部门表的dept_id
    -- 定义外键约束：关联父表t_department的dept_id
    FOREIGN KEY (dept_id) REFERENCES t_department(dept_id)
    -- 可选：外键级联规则（下文解释）
    ON DELETE CASCADE -- 删除父表部门时，自动删除子表关联员工
    ON UPDATE CASCADE -- 更新父表dept_id时，自动更新子表关联值
);

-- 插入子表数据（dept_id必须是父表中存在的值，比如1/2）
INSERT INTO t_employee (emp_name, dept_id) 
VALUES ('张三', 1), ('李四', 1), ('王五', 2);
```

## 三、父表子表的核心规则（参照完整性）

外键约束强制保证「参照完整性」，这是父表子表的核心特性，违反会触发数据库错误：

| 规则                | 说明                                                                 |
|---------------------|----------------------------------------------------------------------|
| 子表引用规则        | 子表的外键值只能是：① 父表主键中已存在的值；② NULL（若外键字段允许NULL）。<br>❌ 错误示例：插入 `dept_id=3`（父表无此部门）会报错。 |
| 父表删除规则        | 删除父表记录时，需处理子表关联数据，否则报错：<br>1. `ON DELETE CASCADE`：级联删除（删部门同时删员工）；<br>2. `ON DELETE SET NULL`：子表外键置空；<br>3. 无配置：拒绝删除（默认）。 |
| 父表更新规则        | 更新父表主键值时，处理逻辑同删除：<br>1. `ON UPDATE CASCADE`：级联更新；<br>2. 无配置：拒绝更新（默认）。 |

### 违反规则的错误示例（MySQL）

```sql
-- 尝试插入子表数据，引用父表不存在的dept_id=3
INSERT INTO t_employee (emp_name, dept_id) VALUES ('赵六', 3);

-- 报错信息（核心：外键约束失败）
-- 1452 - Cannot add or update a child row: a foreign key constraint fails (`test`.`t_employee`, CONSTRAINT `t_employee_ibfk_1` FOREIGN KEY (`dept_id`) REFERENCES `t_department` (`dept_id`))
```

## 四、父表子表的常见应用场景

1. **一对多关系（最核心）**：
   - 订单表（父）- 订单项表（子）：一个订单包含多个订单项；
   - 分类表（父）- 商品表（子）：一个分类包含多个商品；
   - 用户表（父）- 收货地址表（子）：一个用户有多个收货地址。

2. **减少数据冗余**：
   父表存储“公共数据”（如部门名称），子表仅存储外键（dept_id），而非重复存储部门名称，避免数据冗余和不一致。

3. **保证数据一致性**：
   防止出现“孤儿数据”（如无所属部门的员工、无所属订单的订单项），确保数据逻辑完整。

## 五、易混淆点：父表子表 vs 一对一/多对多

- **一对一关系**：也有父表子表，但子表外键需加唯一约束（UNIQUE），比如“用户表（父）- 用户详情表（子）”；
- **多对多关系**：无直接的父表子表，需通过“中间表”实现（如学生表-选课表-课程表，选课表是中间表，同时引用学生和课程表的主键）。

## 总结

父表和子表的核心关键点：

1. **核心关联**：基于外键约束建立一对多关系，父表含主键，子表含外键引用父表主键；
2. **核心作用**：保证数据的「参照完整性」，避免冗余和脏数据（如孤儿数据）；
3. **核心规则**：子表不能引用父表不存在的主键值，操作父表需处理子表关联数据，否则触发约束错误。

简单来说：父表是“主数据”表，子表是“依赖主数据”的明细表，外键是连接两者的纽带，核心目的是让数据更规范、一致。
