# 创建

在 MySQL 中创建表的基本语法结构如下：

```txt
CREATE TABLE 表名 (
    字段1 字段类型 [约束] [comment注释],
    ...
)[comment注释];
```

>`[]`是可选项

```sql
CREATE TABLE table_name (
    column1 datatype constraints,
    column2 datatype constraints,
    column3 datatype constraints,
    ...
);
```

下面是各个部分的详细说明：

1. **CREATE TABLE**：这是创建新表的关键字。
2. **table_name**：这是你将要创建的表的名称。
3. **column1, column2, column3, ...**：这些是表中的列名。
4. **datatype**：这是列的数据类型，例如 `INT`、`VARCHAR`、`DATE` 等。
5. **constraints**：这是列的约束，如 `PRIMARY KEY`、`NOT NULL`、`UNIQUE` 等。

以下是一个具体的例子，创建一个名为 `employees` 的表，包含三个列：`id`、`name` 和 `salary`：

```sql
CREATE TABLE employees (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    salary DECIMAL(10, 2) NOT NULL
);
```

在这个例子中：

- `id` 列被指定为 `INT` 类型，并且是表的主键，它会自动递增。
- `name` 列被指定为 `VARCHAR` 类型，最长 100 个字符，且不能为空。
- `salary` 列被指定为 `DECIMAL` 类型，可以存储最多 10 位数字，其中 2 位在小数点后面，且不能为空。

你还可以为表添加更多的约束和选项，例如：

- **DEFAULT**：为列设置默认值。
- **COMMENT**：为表或列添加注释。
- **ENGINE**：指定存储引擎类型，如 InnoDB 或 MyISAM。
- **CHARSET**：指定表的字符集。

例如：

```sql
CREATE TABLE employees (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    salary DECIMAL(10, 2) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX name_index (name),
    INDEX salary_index (salary)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='Employee information table';
```

在这个例子中，我们添加了 `created_at` 列，它有一个默认值，即当前的时间戳。我们还为 `name` 和 `salary` 列创建了索引，指定了表的存储引擎为 InnoDB，字符集为 utf8mb4，并添加了一个注释来描述表的用途。

## 补充

### 解释`ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;`

#### 1. `ENGINE=InnoDB`：指定表的存储引擎为InnoDB

存储引擎是MySQL处理表数据的**底层核心组件**，不同引擎对应不同的存储机制、锁策略和功能支持。`InnoDB` 是目前MySQL（5.5.5版本后）的默认存储引擎，也是后台开发中业务表的首选。

##### InnoDB的核心特性（为什么后台开发必用）：

- **支持事务（ACID）**：这是最关键的特性，保证下单、支付、扣款等核心业务操作的原子性（要么全成，要么全败），比如你之前问的幂等场景中，事务是数据一致性的基础；
- **行级锁**：高并发场景下，只锁定修改的行，而非整张表，大幅提升并发性能（比如秒杀扣库存时，不会因为一个用户操作锁住所有库存）；
- **外键约束**：支持表之间的关联约束（比如订单表关联用户表），保证数据完整性；
- **崩溃恢复**：即使数据库异常宕机，重启后能恢复数据，避免数据丢失；
- **聚簇索引**：基于主键的索引结构，查询效率更高。

##### 对比旧引擎MyISAM（了解即可，现在几乎不用）：

MyISAM不支持事务、行级锁，只有表级锁，崩溃后无法恢复数据，仅适合纯只读的统计类表（比如日志归档表）。

#### 2. `DEFAULT CHARSET=utf8mb4`：指定表的默认字符集为utf8mb4

`CHARSET`（字符集）决定了表中字符串类型字段（VARCHAR、TEXT等）如何存储和解析字符，`DEFAULT` 表示该字符集是表中所有字段的默认值（字段级可单独覆盖）。

##### 关键说明：

- MySQL中的`utf8`是“伪UTF-8”：  
  MySQL原生的`utf8`实际是`utf8mb3`，最多只能存储3个字节的字符，无法支持emoji表情（😀）、部分生僻汉字或特殊符号，插入时会直接报错或乱码；
- `utf8mb4`是“真正的UTF-8”：  
  `mb4`即`most bytes 4`，支持4个字节的字符，覆盖所有Unicode字符（包括emoji、全量中文/外文），是目前后台开发的**标准配置**，彻底解决字符乱码问题。

#### 3. 注意事项

1. **字符集要全局统一**：数据库级、表级、字段级最好都用`utf8mb4`，避免混合字符集导致乱码；
2. **排序规则配套**：通常搭配`COLLATE=utf8mb4_unicode_ci`（不区分大小写）或`utf8mb4_bin`（区分大小写），比如：

   ```sql
   DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
   ```

3. **InnoDB的主键设计**：InnoDB推荐用自增主键（`AUTO_INCREMENT`），避免用UUID（会导致索引碎片，降低性能）。

#### 4.总结

1. `ENGINE=InnoDB` 是保证业务数据**事务一致性、高并发、崩溃恢复**的核心配置，后台业务表必须使用；
2. `DEFAULT CHARSET=utf8mb4` 解决了MySQL原生`utf8`不支持emoji/生僻字的问题，是避免字符乱码的标准方案；
3. 这两行是后台开发中MySQL建表的**标配**，尤其在电商、支付等核心业务表中不可省略。
