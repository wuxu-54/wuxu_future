# Flowable 核心概念：历史数据（History Data）全解析 + 实战查询 + 配置/避坑指南

历史数据是Flowable工作流对**流程全生命周期**的**永久化快照记录**，是流程**审计追溯、数据统计、业务复盘**的核心依据——Flowable会自动将流程实例、任务、变量、节点执行轨迹、人工批注等运行时数据，在实例/任务结束后生成历史快照，永久存储在`ACT_HI_*`系列表中，且历史数据为**只读**，无法通过API修改/删除（仅可通过配置清理策略）。

如果说之前的流程实例、任务、变量是**运行时的动态数据**（实例结束即清理），那历史数据就是**流程全生命周期的“黑匣子”**——比如企业需要追溯“张三2026年2月的请假流程是谁审批的、审批意见是什么、处理了多久”，或是统计“请假流程的平均处理时长、经理审批的驳回率”，这些需求都需要通过**HistoryService**（历史数据专属Service）查询历史数据实现。

本文延续之前的风格，基于**Spring Boot 2.7+Flowable 6.8.0+员工请假流程**案例，从**核心概念→存储表→历史级别配置→实战查询→高级统计→避坑指南**逐步讲解，所有代码可直接复用，覆盖生产环境审计、追溯、统计的所有高频场景，帮你彻底掌握历史数据的使用。

## 一、什么是历史数据？（通俗解释+核心特性）

### 1. 本质定义

Flowable的历史数据是引擎对**流程从启动到结束的全生命周期**中，所有**运行时数据的结构化快照**，包括流程实例、用户任务、流程变量、节点执行轨迹、人工批注、身份关联等信息，由引擎**自动生成、自动维护**，无需手动干预，永久存储在历史专用表中，核心服务为**HistoryService**（唯一操作入口，仅支持查询）。

### 2. 核心价值

历史数据是企业使用工作流的**必备能力**，核心解决三大问题：

- **审计追溯**：满足企业合规要求，追溯流程的全流程执行轨迹、处理人、处理意见、处理时间，定位流程问题；
- **数据统计**：统计流程的运行效率（如平均处理时长、各节点处理时长）、业务指标（如审批通过率、驳回率、各部门流程发起量）；
- **业务复盘**：基于历史数据分析流程瓶颈，优化业务流程（如某审批节点处理时长过长，需优化审批流程）。

### 3. 核心特性

Flowable的历史数据设计遵循**永久化、只读、全维度覆盖、可配置**原则，核心特性如下，是生产环境使用的基础：

1. **永久化存储**：历史数据默认永久存储在`ACT_HI_*`表中，即使流程实例/任务被删除，历史快照仍保留，仅可通过**历史清理策略**手动清理；
2. **完全只读**：无任何修改/删除历史数据的API，避免历史数据被篡改，保证审计的真实性；
3. **全生命周期覆盖**：覆盖流程从启动（开始事件）到结束（结束事件）的所有节点、操作、数据，无遗漏；
4. **与运行时数据强关联**：历史数据是运行时数据（ACT_RU_*）的快照，运行时数据的每一次关键变更，都会同步生成历史记录；
5. **历史级别可配置**：通过Flowable的**历史级别（History Level）**配置，可控制历史数据的存储详细程度（从无历史数据到全量详细数据），平衡**存储开销**和**追溯需求**；
6. **专属Service操作**：所有历史数据查询均通过**HistoryService**实现，提供多维度的查询器，支持条件筛选、分页、排序、关联查询。

### 4. 运行时数据 VS 历史数据（核心区别，必分清楚）

很多新手会混淆运行时数据（ACT_RU_*）和历史数据（ACT_HI_*），二者是**流程不同阶段的数据载体**，核心区别如下，是使用的基础：

| 对比维度         | 运行时数据（ACT_RU_*）| 历史数据（ACT_HI_*）|
|------------------|---------------------------------|---------------------------------|
| **数据状态**     | 动态变化，实时更新               | 静态快照，永久存储               |
| **生命周期**     | 与流程实例/任务绑定，结束即清理   | 永久存储，仅可通过配置清理       |
| **操作权限**     | 可CRUD（创建、查询、修改、删除）| 仅只读查询（无修改/删除API）|
| **核心作用**     | 支撑流程运行时的动态逻辑（网关、任务分配） | 流程审计、追溯、统计分析         |
| **管理Service**  | RuntimeService/TaskService等     | 专属HistoryService              |
| **数据量**       | 仅存储未结束的流程/任务数据，量小 | 存储所有流程/任务的历史数据，量大 |
| **查询优化**     | 轻量查询，无需复杂分页/筛选       | 高频分页/多条件筛选，需索引优化   |

**核心流转逻辑**：
流程实例启动→生成运行时数据（ACT_RU_PROCINST/ACT_RU_TASK等）→流程运行中（任务处理、变量修改）→运行时数据实时更新→流程实例结束→引擎**清理对应运行时数据**，并将**全量快照迁入历史数据**（ACT_HI_*）→历史数据永久存储，供查询审计。

## 二、历史数据核心存储表（ACT_HI_*，必知必记）

Flowable的历史数据全部存储在**ACT_HI_***前缀的表中，无其他关联表，所有表均由引擎自动创建、自动维护，无需手动操作。核心历史表共**6张**，覆盖流程全生命周期的所有维度，且表之间通过**流程实例ID（PROC_INST_ID_）**、**任务ID（TASK_ID_）**强关联，形成完整的历史数据链路。

以下是生产环境**高频使用的5张核心表**，按**关联关系**排序，讲清每张表的作用、关键字段、关联逻辑：

### 1. ACT_HI_PROCINST - 历史流程实例表【核心根表】

- **核心作用**：存储**所有流程实例**的历史快照（包括已结束、已删除、挂起的实例），是历史数据的**根表**，所有其他历史表均通过**PROC_INST_ID_**关联此表；
- **关键字段**：PROC_INST_ID_（流程实例ID，主键）、BUSINESS_KEY_（业务键，关联业务系统）、PROC_DEF_KEY_（流程定义Key）、START_USER_ID_（启动人）、START_TIME_（启动时间）、END_TIME_（结束时间）、DURATION_（流程总处理时长，毫秒）、DELETE_REASON_（删除原因，手动终止时填写）；
- **核心特性**：一个流程实例对应此表**一条记录**，流程结束后，END_TIME_和DURATION_会被引擎自动填充。

### 2. ACT_HI_TASKINST - 历史任务实例表【审计高频】

- **核心作用**：存储**所有用户任务（userTask）**的历史快照，包括已完成、已删除、挂起的任务，是**人工操作审计**的核心表；
- **关键字段**：ID_（任务历史ID）、TASK_ID_（运行时任务ID）、PROC_INST_ID_（关联流程实例）、NAME_（任务名称）、ASSIGNEE_（任务处理人）、CREATE_TIME_（任务创建时间）、END_TIME_（任务完成时间）、DURATION_（任务处理时长）；
- **核心特性**：一个运行时任务对应此表**一条记录**，任务完成后，END_TIME_和DURATION_会被自动填充；直配处理人/候选人/候选组的信息均存储在此表。

### 3. ACT_HI_VARINST - 历史流程变量表【数据追溯高频】

- **核心作用**：存储**所有流程变量**的历史快照，包括全局变量和任务局部变量，是**流程数据追溯**的核心表；
- **关键字段**：ID_（变量历史ID）、PROC_INST_ID_（关联流程实例）、TASK_ID_（关联任务，局部变量非空，全局变量为空）、NAME_（变量名）、VALUE_（变量值，序列化存储）、TYPE_（变量类型，如String/Integer）；
- **核心特性**：流程变量**每一次修改**都会生成**一条新的记录**（版本化存储），可追溯变量的修改轨迹；流程结束后，最终的变量值会永久保留。

### 4. ACT_HI_ACTINST - 历史活动实例表【轨迹追溯高频】

- **核心作用**：存储**流程中所有节点（活动）**的执行快照，包括开始事件、结束事件、用户任务、网关、自动任务等，是**流程执行轨迹追溯**的核心表（如查流程“走到了哪个节点、每个节点的执行时间”）；
- **关键字段**：ID_（活动历史ID）、PROC_INST_ID_（关联流程实例）、ACT_ID_（节点ID，对应BPMN中的节点id）、ACT_NAME_（节点名称）、ACT_TYPE_（节点类型，如startEvent/userTask/exclusiveGateway）、START_TIME_（节点启动时间）、END_TIME_（节点结束时间）、DURATION_（节点执行时长）；
- **核心特性**：流程中**每一个节点的执行**都会对应此表**一条记录**，即使是网关、自动任务这类无人工操作的节点，也会记录；是还原流程执行轨迹的唯一依据。

### 5. ACT_HI_COMMENT - 历史批注表【审批审计高频】

- **核心作用**：存储**人工操作任务时添加的所有批注/意见**，是**审批审计**的核心表（如查“某审批任务的处理意见是什么”）；
- **关键字段**：ID_（批注ID）、PROC_INST_ID_（关联流程实例）、TASK_ID_（关联任务）、USER_ID_（添加批注的用户ID）、TIME_（批注时间）、FULL_MSG_（批注完整内容）；
- **核心特性**：通过`TaskService.addComment`添加的批注，会自动存入此表；一个任务可添加多条批注，均会永久保留。

### 6. 表之间的核心关联逻辑

所有历史表通过**流程实例ID（PROC_INST_ID_）**形成**一级关联**，任务相关的表（ACT_HI_TASKINST/ACT_HI_COMMENT/ACT_HI_VARINST）再通过**任务ID（TASK_ID_）**形成**二级关联**，完整的关联链路为：
`ACT_HI_PROCINST（根）` → 关联 `ACT_HI_ACTINST（所有节点）`/`ACT_HI_TASKINST（所有任务）`/`ACT_HI_VARINST（全局变量）` → `ACT_HI_TASKINST` 再关联 `ACT_HI_COMMENT（任务批注）`/`ACT_HI_VARINST（任务局部变量）`。

**实战查询原则**：所有历史数据查询，**优先以业务键（BUSINESS_KEY_）或流程实例ID（PROC_INST_ID_）为入口**，再关联查询其他表的信息，形成完整的审计追溯链。

## 三、历史级别（History Level）配置【核心，生产必配】

Flowable提供**4个级别的历史数据配置**，通过**历史级别**可控制引擎存储的历史数据**详细程度**，平衡**存储开销**和**追溯需求**——级别越低，存储的历史数据越简略，存储开销越小；级别越高，数据越详细，存储开销越大。

这是Flowable历史数据的**核心配置项**，生产环境需根据企业的**审计需求**和**服务器存储能力**选择合适的级别，**默认级别为ACTIVITY**。

### 1. 4个历史级别详解（从低到高）

| 历史级别 | 常量值（Flowable枚举） | 核心存储内容 | 存储开销 | 适用场景 |
|----------|------------------------|--------------|----------|----------|
| **NONE** | HistoryLevel.NONE      | 无任何历史数据，所有ACT_HI_*表均无记录 | 无       | 测试环境/无需审计追溯的场景 |
| **ACTIVITY** | HistoryLevel.ACTIVITY | 核心历史数据：流程实例（ACT_HI_PROCINST）+ 所有节点执行轨迹（ACT_HI_ACTINST） | 小       | 仅需追溯流程执行轨迹，无需任务/变量/批注细节的场景 |
| **AUDIT** | HistoryLevel.AUDIT（默认） | 审计级数据：ACTIVITY级别 + 历史任务（ACT_HI_TASKINST） + 历史变量（ACT_HI_VARINST） + 历史批注（ACT_HI_COMMENT） | 中       | 企业常规审计追溯场景（90%以上企业适用，生产首选） |
| **FULL** | HistoryLevel.FULL      | 全量数据：AUDIT级别 + 流程变量的**版本化修改记录**（变量每修改一次生成一条记录） + 执行流的详细轨迹 | 大       | 需精细化追溯（如变量修改轨迹、执行流分支细节）的高合规场景（如金融、医疗、政务） |

**核心区别**：AUDIT和FULL的核心差异是**流程变量的存储方式**——AUDIT仅存储变量的**最终值**，FULL存储变量的**每一次修改值**（版本化），可追溯变量的修改轨迹。

### 2. 历史级别配置方式（Spring Boot/纯Java）

历史级别需在**引擎启动前配置**，引擎启动后无法动态修改，Spring Boot和纯Java工程的配置方式如下，**生产环境推荐配置为AUDIT**。

#### 方式1：Spring Boot工程（application.yml，推荐）

```yaml
flowable:
  # 历史级别配置：NONE/ACTIVITY/AUDIT/FULL，默认AUDIT
  history-level: AUDIT
  # 可选：开启历史数据的时间戳精度（毫秒），默认开启
  history:
    date-format: yyyy-MM-dd HH:mm:ss
    time-unit: MILLISECONDS
```

#### 方式2：纯Java工程（flowable.cfg.xml）

```xml
<bean id="processEngineConfiguration" class="org.flowable.engine.impl.cfg.StandaloneProcessEngineConfiguration">
    <!-- 其他配置：数据源、部署等 -->
    <property name="historyLevel" value="AUDIT"/>
</bean>
```

### 3. 生产环境选择建议

1. **测试环境**：可配置为NONE，减少存储开销，无需审计；
2. **常规企业业务**：配置为AUDIT（默认），满足90%的审计追溯需求，存储开销适中；
3. **高合规行业**（金融、医疗、政务、军工）：配置为FULL，实现精细化追溯，即使增加存储开销，也需满足合规要求；
4. **禁止在生产环境动态修改**：若需修改历史级别，需停止引擎，修改配置后重启，且原有历史数据不会因级别修改而变化。

## 四、历史数据核心实战操作（HistoryService，全覆盖）

历史数据的所有操作均通过**HistoryService**实现，Spring Boot中直接`@Autowired`注入即可，核心是**5个查询器**（对应核心历史表），支持**链式条件筛选、分页、排序、关联查询**，与之前的TaskQuery/ProcessInstanceQuery用法一致，上手成本低。

### 前置准备

1. 环境：沿用Spring Boot 2.7+Flowable 6.8.0，配置历史级别为AUDIT，已部署请假流程（leaveProcessExclusive），并**启动并完成至少一个流程实例**（生成历史数据）；
2. 基础数据：启动请假流程实例，业务键为`biz_leave_20260207_001`，启动人zhangsan，请假天数5天，总监wangwu审批通过，添加审批批注；
3. 注入HistoryService：

```java
import org.flowable.engine.HistoryService;
import org.flowable.engine.history.*;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.transaction.annotation.Transactional;

import java.util.List;

@SpringBootTest
public class HistoryDataTest {
    // 历史数据专属Service，唯一操作入口
    @Autowired
    private HistoryService historyService;
}
```

### 操作1：查询历史流程实例（HistoricProcessInstanceQuery）【根查询，高频】

基于`ACT_HI_PROCINST`表的查询，是所有历史查询的**根入口**，常用条件：业务键、流程定义Key、启动人、时间范围、结束状态，实战中**最常用按业务键查询**（关联业务系统）。

```java
/**
 * 历史流程实例查询：根查询，实战高频（按业务键/启动人/流程Key/时间范围）
 */
@Test
public void queryHistoricProcessInstance() {
    // 模拟业务参数（实战中从业务系统/前端获取）
    String businessKey = "biz_leave_20260207_001"; // 业务键（最常用）
    String processKey = "leaveProcessExclusive"; // 流程定义Key
    String startUserId = "zhangsan"; // 启动人
    String deleteReason = "撤回申请"; // 删除原因（手动终止时）

    // 场景1：按业务键精确查询（实战最高频，关联业务系统）
    HistoricProcessInstance hiProcInst = historyService.createHistoricProcessInstanceQuery()
            .processInstanceBusinessKey(businessKey)
            .singleResult();
    if (hiProcInst != null) {
        System.out.println("=== 按业务键查询历史流程实例 ===");
        System.out.println("流程实例ID：" + hiProcInst.getId());
        System.out.println("业务键：" + hiProcInst.getBusinessKey());
        System.out.println("流程定义Key：" + hiProcInst.getProcessDefinitionKey());
        System.out.println("启动人：" + hiProcInst.getStartUserId());
        System.out.println("启动时间：" + hiProcInst.getStartTime());
        System.out.println("结束时间：" + hiProcInst.getEndTime());
        System.out.println("总处理时长（毫秒）：" + hiProcInst.getDurationInMillis());
        System.out.println("删除原因：" + hiProcInst.getDeleteReason()); // 正常结束为null
    }

    // 场景2：按启动人查询（如查张三发起的所有请假流程）
    List<HistoricProcessInstance> hiProcInstByUser = historyService.createHistoricProcessInstanceQuery()
            .startedBy(startUserId)
            .processDefinitionKey(processKey)
            .finished() // 仅查询已结束的实例（未结束的用runtimeService查）
            .orderByProcessInstanceEndTimeDesc() // 按结束时间倒序
            .list();
    System.out.println("\n张三发起的已结束请假流程数：" + hiProcInstByUser.size());

    // 场景3：按时间范围查询（如查2026年2月的所有流程）
    // SimpleDateFormat sdf = new SimpleDateFormat("yyyy-MM-dd HH:mm:ss");
    // Date startDate = sdf.parse("2026-02-01 00:00:00");
    // Date endDate = sdf.parse("2026-02-28 23:59:59");
    // List<HistoricProcessInstance> hiProcInstByTime = historyService.createHistoricProcessInstanceQuery()
    //         .processDefinitionKey(processKey)
    //         .startedBetween(startDate, endDate)
    //         .list();

    // 场景4：分页查询（历史数据量大，必用分页）
    int pageNum = 1;
    int pageSize = 10;
    List<HistoricProcessInstance> hiProcInstPage = historyService.createHistoricProcessInstanceQuery()
            .processDefinitionKey(processKey)
            .finished()
            .listPage((pageNum - 1) * pageSize, pageSize);
    System.out.println("分页查询第1页流程数：" + hiProcInstPage.size());
}
```

#### 高频查询方法（熟记）

| 方法 | 作用 | 实战频率 |
|------|------|----------|
| `processInstanceBusinessKey(String key)` | 按业务键精确查询 | ★★★★★ |
| `processDefinitionKey(String key)` | 按流程定义Key筛选 | ★★★★★ |
| `startedBy(String userId)` | 按启动人筛选 | ★★★★ |
| `finished()` | 仅查询已结束的实例 | ★★★★★ |
| `unfinished()` | 仅查询未结束的实例（极少用，推荐RuntimeService） | ★★ |
| `startedBetween(Date start, Date end)` | 按启动时间范围筛选 | ★★★★ |
| `orderByProcessInstanceEndTimeDesc()` | 按结束时间倒序 | ★★★★★ |

### 操作2：查询历史任务实例（HistoricTaskInstanceQuery）【审批审计，高频】

### 用法2：流程业务统计分析（基于历史数据，生产高频）

生产中另一大核心需求：**基于历史数据做业务统计分析**，比如统计「请假流程的月均处理时长、各审批节点的平均处理时长、总监审批的通过率」，以下以**请假流程的核心统计指标**为例，讲解实现方式，可直接封装为统计报表接口。

#### 核心代码（统计分析，基于流式计算）

```java
/**
 * 生产级：流程业务统计分析，计算核心指标（平均处理时长、节点处理时长、审批通过率）
 */
@Test
public void processBusinessStatistics() {
    String processKey = "leaveProcessExclusive";
    System.out.println("========== 请假流程（" + processKey + "）业务统计分析 ==========");

    // 指标1：统计已结束的请假流程总数
    long totalProcess = historyService.createHistoricProcessInstanceQuery()
            .processDefinitionKey(processKey)
            .finished()
            .count();
    System.out.println("【指标1】已结束请假流程总数：" + totalProcess + "个");

    if (totalProcess == 0) {
        System.out.println("无历史数据，统计结束！");
        return;
    }

    // 指标2：计算请假流程的平均总处理时长（毫秒）
    List<HistoricProcessInstance> hiProcInstList = historyService.createHistoricProcessInstanceQuery()
            .processDefinitionKey(processKey)
            .finished()
            .list();
    long totalDuration = hiProcInstList.stream().mapToLong(HistoricProcessInstance::getDurationInMillis).sum();
    long avgTotalDuration = totalDuration / totalProcess;
    System.out.println("【指标2】流程平均总处理时长：" + avgTotalDuration + "毫秒（约" + avgTotalDuration / 60000 + "分钟）");

    // 指标3：计算「总监审批」节点的平均处理时长
    long directorApproveTotal = historyService.createHistoricActivityInstanceQuery()
            .processDefinitionKey(processKey)
            .activityName("部门总监审批")
            .finished()
            .count();
    long directorApproveDuration = historyService.createHistoricActivityInstanceQuery()
            .processDefinitionKey(processKey)
            .activityName("部门总监审批")
            .finished()
            .list()
            .stream()
            .mapToLong(HistoricActivityInstance::getDurationInMillis)
            .sum();
    long avgDirectorApproveDuration = directorApproveDuration / (directorApproveTotal == 0 ? 1 : directorApproveTotal);
    System.out.println("【指标3】总监审批节点平均处理时长：" + avgDirectorApproveDuration + "毫秒（共处理" + directorApproveTotal + "次）");

    // 指标4：计算请假流程的审批通过率（approve=true为通过）
    long approveSuccess = 0;
    for (HistoricProcessInstance hiProc : hiProcInstList) {
        HistoricVariableInstance approveVar = historyService.createHistoricVariableInstanceQuery()
                .processInstanceId(hiProc.getId())
                .variableName("approve")
                .singleResult();
        if (approveVar != null && Boolean.TRUE.equals(approveVar.getValue())) {
            approveSuccess++;
        }
    }
    double approveRate = (double) approveSuccess / totalProcess * 100;
    System.out.println("【指标4】流程审批通过率：" + approveSuccess + "/" + totalProcess + " = " + String.format("%.2f", approveRate) + "%");

    // 指标5：统计各处理人的任务处理数
    System.out.println("\n【指标5】各处理人任务处理数统计");
    historyService.createHistoricTaskInstanceQuery()
            .processDefinitionKey(processKey)
            .finished()
            .list()
            .stream()
            .collect(java.util.stream.Collectors.groupingBy(HistoricTaskInstance::getAssignee, java.util.stream.Collectors.counting()))
            .forEach((userId, count) -> System.out.println(userId + "：处理" + count + "个任务"));
    System.out.println("========== 统计分析结束 ==========");
}
```

## 六、历史数据的清理策略（生产必备，避免存储溢出）

Flowable的历史数据**默认永久存储**，随着业务运行，`ACT_HI_*`表的数据量会持续增大，导致**数据库存储溢出、查询性能下降**，因此生产环境**必须配置历史数据清理策略**，定期清理过期的历史数据。

Flowable提供**内置的历史清理器（HistoryCleanup）**，支持按**时间范围**清理过期的历史数据，核心是配置**清理时间窗口**和**过期时间**，以下是Spring Boot工程的配置方式。

### Spring Boot 历史清理配置（application.yml）

```yaml
flowable:
  history-level: AUDIT
  # 历史数据清理策略配置
  history:
    cleanup:
      # 开启历史数据清理，默认false（生产环境建议开启）
      enabled: true
      # 清理的时间窗口（CRON表达式），建议在凌晨低峰期执行，如每天凌晨2点
      cron-expression: 0 0 2 * * ?
      # 清理**已结束**超过N天的历史数据，单位：天，如清理3个月（90天）前的历史数据
      history-cleanup-after-days: 90
      # 批量清理的批次大小，避免单次清理数据量过大，导致数据库锁表
      batch-size: 1000
      # 仅清理流程实例，还是清理所有关联的历史数据（任务/变量/批注/活动），默认true（推荐）
      delete-all-related-history-data: true
```

### 核心配置说明

1. **enabled**：必须设为true，开启清理器；
2. **cron-expression**：清理任务的执行时间，建议在**业务低峰期**（如凌晨）执行；
3. **history-cleanup-after-days**：核心配置，清理**已结束**超过该天数的历史数据，根据企业的**审计保留期限**配置（如金融行业需保留5年，配置1825天）；
4. **batch-size**：批量清理的大小，建议设置为1000-5000，避免单次清理过多数据导致数据库锁表，影响业务；
5. **delete-all-related-history-data**：设为true，清理流程实例时，**级联清理所有关联的历史数据**（任务/变量/批注/活动），避免历史表数据不一致。

## 七、历史数据实战核心避坑指南（生产高频）

结合企业实战经验，整理了历史数据使用的**6个高频坑点**，覆盖**配置、查询、性能、清理**全流程，严格遵守可避免90%的问题，其中**历史级别配置、分页查询、索引优化**是新手最容易踩的坑。

### 1. 历史级别配置不当，导致审计数据缺失/存储溢出

- **坑点**：测试环境配置为NONE，上线生产后未修改为AUDIT/FULL，导致无任何历史数据，无法审计；或高并发业务配置为FULL，导致历史表数据量暴增，存储溢出、查询性能下降；
- **解决方案**：
  1. 生产环境**根据审计需求选择合适的历史级别**，90%的企业配置为AUDIT即可；
  2. 高并发、大流量的业务，**禁止配置为FULL**，如需精细化追溯，可通过业务系统记录变量修改轨迹，而非依赖Flowable的FULL级别；
  3. 上线前必须校验历史级别配置，避免测试环境配置直接上线。

### 2. 历史数据查询未分页，导致内存溢出/查询超时

- **坑点**：历史数据量巨大（如百万/千万级），查询时未使用`listPage`分页，直接调用`list()`，导致JVM内存溢出、数据库查询超时；
- **解决方案**：**所有历史数据查询必须分页**，即使是前端的“全部查询”，也需做**前端分页+后端分页**，分页大小建议设置为10/20/50，禁止无限制查询。

### 3. 混淆运行时和历史查询器，查询不到数据

- **坑点**：流程实例未结束时，用HistoryService查询历史数据，查询不到；或流程实例结束后，用RuntimeService查询运行时数据，查询不到；
- **解决方案**：明确二者的查询边界：
  - **未结束的流程/任务**：用**RuntimeService/TaskService**查询运行时数据（ACT_RU_*）；
  - **已结束/已删除的流程/任务**：用**HistoryService**查询历史数据（ACT_HI_*）。

### 4. 未对历史表做索引优化，导致查询性能低下

- **坑点**：历史表数据量持续增大，但未对核心字段做索引优化，导致多条件筛选、分页查询时性能低下，查询超时；
- **解决方案**：为历史表的**核心查询字段添加索引**，推荐索引如下：
  - ACT_HI_PROCINST：BUSINESS_KEY_、PROC_DEF_KEY_、START_USER_ID_、START_TIME_、END_TIME_；
  - ACT_HI_TASKINST：PROC_INST_ID_、TASK_ASSIGNEE_、CREATE_TIME_、END_TIME_；
  - ACT_HI_VARINST：PROC_INST_ID_、VARIABLE_NAME_；
  - ACT_HI_ACTINST：PROC_INST_ID_、ACTIVITY_TYPE_、START_TIME_；
  - ACT_HI_COMMENT：PROC_INST_ID_、TASK_ID_、USER_ID_。

### 5. 直接操作历史表，导致数据不一致/审计失效

- **坑点**：为了便捷，直接通过SQL删除/修改历史表（ACT_HI_*）的数据，导致历史数据不一致，甚至篡改审计记录，违反企业合规要求；
- **解决方案**：
  1. **禁止任何直接操作历史表的SQL**（包括删除、修改、新增）；
  2. 历史数据的清理**仅通过Flowable的内置清理器**实现，遵循配置的保留期限；
  3. 数据库为历史表设置**只读权限**，禁止应用账户有修改/删除权限。

### 6. 多租户场景未做历史数据隔离，导致数据泄露

- **坑点**：多租户系统中，查询历史数据时未指定`tenantId`，导致不同租户的历史数据相互混淆，A租户能查询到B租户的流程审计数据，引发数据泄露；
- **解决方案**：多租户场景下，**所有历史数据查询必须添加tenantId筛选**，Flowable的所有历史查询器均支持`tenantId`方法：

  ```java
  // 多租户查询历史流程实例
  historyService.createHistoricProcessInstanceQuery()
          .processDefinitionKey(processKey)
          .tenantId("tenant1")
          .finished()
          .list();
  ```

## 八、核心总结

1. **历史数据是流程的“审计黑匣子”**：Flowable自动生成、永久存储，是流程审计、追溯、统计的核心依据，专属Service为HistoryService，仅支持只读查询；
2. **核心历史表共5张**：以ACT_HI_PROCINST为根表，其他表通过PROC_INST_ID_/TASK_ID_关联，形成完整的历史数据链路；
3. **历史级别是核心配置**：4个级别（NONE/ACTIVITY/AUDIT/FULL），生产环境90%配置为AUDIT，平衡审计需求和存储开销，引擎启动后无法动态修改；
4. **查询的核心原则**：优先以**业务键**为入口，关联查询其他历史表，形成完整的审计链路；**所有查询必须分页**，避免内存溢出；
5. **生产必须配置清理策略**：历史数据默认永久存储，需通过内置清理器定期清理过期数据，配置时注意批次大小和执行时间，避免影响业务；
6. **性能优化是关键**：为历史表的核心查询字段添加索引，高并发业务禁止使用FULL级别，避免存储溢出、查询性能下降；
7. **多租户必须隔离**：所有历史查询必须添加tenantId筛选，避免数据泄露；禁止直接操作历史表，确保审计数据的真实性。

## 九、知识闭环：Flowable核心概念全串联

至此，你已经掌握了Flowable**所有核心概念**：**流程定义（静态模板）→流程实例（动态运行载体）→流程任务（人工交互节点）→网关（流程分流合流）→流程变量（数据中枢）→历史数据（审计追溯）**，这六个核心模块构成了Flowable企业级开发的**完整知识体系**，其核心流转逻辑为：

1. 基于BPMN编写**流程定义**，通过RepositoryService部署；
2. 通过RuntimeService启动**流程实例**，传入**流程变量**初始化数据；
3. 流程实例运行到userTask节点，引擎生成**流程任务**，通过TaskService处理（认领、完成、批注）；
4. 流程遇到网关，基于**流程变量**的条件判断实现分流/合流；
5. 任务完成时，通过流程变量回传处理结果，驱动流程继续推进；
6. 流程实例结束后，引擎清理运行时数据，生成**历史数据**永久存储；
7. 通过HistoryService查询历史数据，实现审计、追溯、统计分析。

结合这些知识点，灵活运用Flowable的核心API，即可实现**绝大多数企业复杂业务流程**的开发，后续只需补充**多租户、流程挂起/激活、异步任务、邮件任务**等高级特性，即可完成**企业级工作流系统**的全流程开发。
