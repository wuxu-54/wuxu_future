# 解答

问题

1. 任务是否一直在进程 ；
2. 重新部署服务（Flowable关闭），重启后还能正常运行吗？

本次总结围绕你核心关注的**两个关键问题**展开，整合两次回答的核心内容，先讲支撑所有特性的**Flowable底层核心设计原理**（这是理解两个问题的根基），再分别拆解每个问题的原理、结论与关键细节，最后补充生产环境的核心注意事项，让你从底层到应用彻底理解相关逻辑。

## 一、支撑所有特性的Flowable底层核心设计原理

Flowable作为成熟的企业级工作流引擎，其**执行机制**和**重启后正常运行**的能力，均基于三大核心设计原则，且这三大原则相互关联、形成闭环，也是所有工业级工作流引擎的通用设计思路：

### 1. 状态全持久化：所有关键状态落地数据库，进程不存核心数据

Flowable将流程运行的**所有运行时状态**、**历史状态**、**配置信息**全部持久化到关系型数据库中，进程仅作为“读取状态、执行操作、更新状态”的载体，自身不保存任何关键数据，这是**重启不丢状态、不占持续进程资源**的核心基础。
数据库表按功能严格划分，核心表分类如下：

| 表前缀   | 存储内容                | 核心作用                     | 与核心问题的关联                     |
|----------|-------------------------|------------------------------|--------------------------------------|
| ACT_RU_* | 运行时状态（流程实例、待办任务、流程变量、异步/定时器作业） | 维护当前未完成的流程全状态   | 无操作时仅存此表，重启后从这表恢复状态 |
| ACT_HI_* | 历史状态（已完成任务、已结束流程、历史变量、操作日志）     | 审计、统计、追溯             | 不影响运行，仅做历史查询             |
| ACT_RE_* | 流程定义、部署资源       | 存储流程的“蓝图”配置         | 重启后从这表读取流程定义，启动新实例 |
| ACT_ID_* | 内置用户/组（建议业务系统对接） | 任务分配基础                 | 按需使用，不影响核心流程运行         |

### 2. 事件驱动+触发-执行-暂停：非持续执行，仅按需触发流程逻辑

Flowable不会在进程中持续运行流程，而是遵循**「事件触发→短暂执行→遇到等待节点即暂停→更新数据库状态→释放所有进程资源」**的循环逻辑，无外部事件触发时，引擎完全“休眠”，进程中无任何针对流程的执行线程。

- **事件触发**：指用户/系统执行的显式操作（启动流程、完成任务、认领任务）或引擎内部触发（定时器到点、异步作业轮询）；
- **短暂执行**：触发后引擎同步执行流程逻辑，仅执行到**下一个等待节点**即停止；
- **暂停的核心**：等待节点是流程暂停的唯一标识，引擎会在数据库中生成对应的等待状态记录，后续需新的事件触发才能继续执行。

### 3. 无状态服务设计：进程是“操作工具”，重启仅恢复服务能力

Flowable的服务进程本身是**无状态**的，即多个进程实例（集群部署）、同一进程重启，其功能完全一致——仅提供流程操作的API能力（查询、完成任务、启动实例等），所有操作的入参和出参均基于数据库中的状态，进程的启动/关闭/重启，仅改变“是否能执行流程操作”，不会改变数据库中已存储的流程状态。

简单类比：Flowable进程像**超市收银员**，数据库像**超市账本+商品库存**；收银员下班（进程关闭），账本和库存仍完整保留；收银员上班（进程重启），只需读取账本和库存，就能继续完成收银、补货等操作，完全不受下班/上班的影响。

## 二、你关注的问题1：Flowable工作流是一直在进程中执行吗？

### 核心结论

**不是**。Flowable仅在**外部事件触发**时短暂执行流程逻辑，执行到**等待节点**后立即暂停，释放所有进程资源；无触发事件时，引擎休眠，进程中无任何流程执行线程，仅在数据库中维护任务及流程状态（你的理解“正常应该只维护任务及任务状态”完全正确）。

### 关键执行原理细节

Flowable的流程节点分为**等待节点**和**非等待节点**，流程的“暂停/执行”完全由节点类型决定，核心执行逻辑如下：

1. **遇到等待节点：必暂停，仅维护数据库状态**
    等待节点是流程暂停的核心，引擎执行到此类节点时，会在`ACT_RU_*`表中生成对应的状态记录，然后立即停止流程执行，释放线程资源，后续需**新的事件触发**才能继续执行。
    常见等待节点及暂停逻辑：
    - **用户任务（UserTask）**：如经理审批、填写请假单，生成待办任务记录（`ACT_RU_TASK`），需用户调用`completeTask`完成任务才触发继续执行；
    - **定时器任务（TimerEvent）**：如24小时审批超时提醒，生成定时器作业记录（`ACT_RU_TIMER_JOB`），需时间到达后引擎异步触发；
    - **接收任务（ReceiveTask）**：如等待外部系统回调，生成接收任务记录，需调用`runtimeService.signal`触发；
    - **并行网关**：多分支并行审批，需所有分支任务完成后才聚合继续执行。

2. **遇到非等待节点：同步执行，执行完即进入下一个节点**
    非等待节点不会让流程暂停，引擎会**同步、短暂**执行节点逻辑，执行完成后立即进入下一个节点，直到遇到**等待节点**才停止。此类节点的执行全程在一个触发事件中完成，无任何资源驻留。
    常见非等待节点：服务任务（调用接口、发送通知）、排他网关（分支条件判断）、开始/结束事件、脚本任务等。

3. **特殊场景：异步/定时器作业——按需触发，非持续运行**
    对于异步服务任务（标记`async="true"`）、定时器任务，Flowable通过**异步执行器（Async Executor）** 处理，但其仍非持续运行：
    - 异步执行器是一个**后台线程池**，仅**轮询**数据库中的`ACT_RU_JOB`/`ACT_RU_TIMER_JOB`表；
    - 发现待执行的作业（如异步任务、到点的定时器），则取出交给线程池执行，执行完成后更新数据库状态，继续执行流程到下一个等待节点；
    - 无待执行作业时，线程池中的核心线程会休眠，不会持续占用CPU/内存资源。

**典型执行示例（请假流程）**：
调用`startProcessInstanceByKey`启动流程→引擎同步执行到“填写请假单”用户任务（等待节点）→在`ACT_RU_TASK`生成待办记录，流程暂停，释放线程→无操作时引擎休眠→用户完成请假单后，调用`completeTask`触发事件→引擎同步执行到“经理审批”用户任务（等待节点）→再次暂停，以此类推。

## 三、你关注的问题2：重新部署服务（Flowable关闭），重启后还能正常运行吗？

### 核心结论

**完全可以正常运行**，这是Flowable基于「状态全持久化+无状态服务」设计的核心特性，也是生产环境中服务重启、扩容、缩容的基础——重启仅恢复Flowable的**服务操作能力**，所有未完成的流程状态均从数据库中读取，与重启前完全一致，无任何丢失或破坏。

### 重启后正常运行的核心原理与细节

服务重启的本质是**重启了一个无状态的Flowable进程**，进程启动后会自动连接数据库，读取`ACT_RU_*`/`ACT_RE_*`表中的所有状态，恢复所有服务能力，**所有核心组件和流程元素均能正常工作**，具体表现为：

1. **待办任务**：重启前的待办任务仍保存在`ACT_RU_TASK`表中，状态为「待办（READY）」，重启后可正常**查询、认领、完成**，完成后流程会从当前节点继续执行，不会从头开始；
2. **运行中流程实例**：流程实例状态（运行中/挂起）保存在`ACT_RU_EXECUTION`表中，重启后状态不变，流程变量（请假天数、申请人等）从`ACT_RU_VARIABLE`表中读取，可正常**读取、修改**；
3. **异步/定时器作业**：重启前未执行的异步作业、未到点的定时器作业，分别保存在`ACT_RU_JOB`/`ACT_RU_TIMER_JOB`表中，重启后**异步执行器会自动启动并轮询**，按配置执行作业，超时的定时器任务会在重启后立即触发；
4. **流程定义**：已部署的流程定义保存在`ACT_RE_PROCESSDEFINITION`表中，重启后可正常查询，启动新流程实例时会自动使用最新版本，旧流程实例仍沿用启动时的版本；
5. **失败作业**：重启前执行失败的作业（如调用接口超时），会按配置的重试策略（如重试3次、间隔5分钟），在重启后**继续自动重试**，保证流程最终一致性。

### 重启后可能出现的小概率异常（非核心功能损坏，可规避）

重启后流程核心运行不受影响，但部分边界场景可能出现小异常，**均为操作层面问题，非底层设计缺陷**，且有明确的规避方案：

1. **重启时正在执行的同步操作**：重启瞬间若有线程在执行`completeTask`等同步操作，事务可能未提交就被中断，**结果仅为操作回滚**（任务回到待办状态），重启后重新执行即可，无数据丢失；
2. **异步执行器未激活**：若配置`flowable.async-executor-activate=false`，重启后异步/定时器作业会“卡住”，只需将配置改为`true`（生产环境必配）即可；
3. **代码/流程定义版本不兼容**：若重启时修改了监听器、服务任务的代码，或流程定义未版本化就修改，旧流程实例执行到对应节点时可能抛出异常，需通过**流程定义版本化**（修改后重新部署生成新版本，旧实例用旧版本）、**代码兼容开发**（保留旧方法）规避；
4. **数据库连接异常**：重启后若数据库未启动、账号密码错误，Flowable无法读取数据库状态，所有操作报错，只需恢复数据库连接即可。

## 四、生产环境核心注意事项（整合执行机制+重启相关）

基于上述原理，结合生产环境的实际使用，需重点注意以下几点，保证Flowable稳定运行：

1. **执行机制相关**：耗时的业务逻辑（如调用外部接口、批量处理数据），需在服务任务中标记`async="true"`改为异步执行，避免同步执行时阻塞流程，且能利用Flowable的作业重试机制保证最终一致性；
2. **重启相关**：生产重启前需**优雅关闭服务**（`kill -15`进程，而非`kill -9`），让正在执行的事务正常提交；同时暂停外部请求（如关闭API网关），等待正在执行的任务完成后再重启，避免同步操作回滚；
3. **异步执行器配置**：生产环境必须开启异步执行器（`flowable.async-executor-activate=true`），并合理配置线程池大小、作业重试策略，保证异步/定时器任务正常执行；
4. **状态与代码隔离**：流程变量尽量使用基础类型（String、Integer），避免自定义对象（序列化易出问题）；大对象（如文件）不要存为流程变量，仅存业务系统的文件ID，由业务系统单独存储；
5. **版本管理**：修改流程定义或自定义逻辑（监听器、服务任务）时，必须做**版本化处理**，避免旧流程实例调用新代码导致异常；
6. **数据库维护**：定期监控`ACT_RU_*`表（无过期数据，仅存未完成流程），定期清理`ACT_HI_*`表（历史数据会持续增长）；给核心表加索引（如`ACT_RU_TASK.ASSIGNEE_`、`ACT_RU_EXECUTION.PROC_INST_ID_`），提升查询性能。

## 五、整体核心总结

你关注的两个问题，答案均由Flowable**「状态全持久化+事件驱动+无状态服务」**的底层核心设计决定，且两个问题的逻辑相互印证：

1. 正因为Flowable**仅维护数据库中的任务/流程状态**，而非在进程中持续执行，才让流程能支撑**长周期业务**（如审批流程跨天/跨周），且不占用持续的进程资源；
2. 正因为所有状态都落地数据库，进程仅为无状态的操作载体，才让**服务重启后能完全恢复运行**，成为生产环境中常规操作（重启、扩容）的基础。

简单来说，Flowable的核心职责**不是“在进程中跑流程”，而是“在数据库中管状态”**，所有流程执行逻辑都是“触发一次、执行一次、更新一次状态”，这也是其能成为企业级工作流引擎的核心原因。
