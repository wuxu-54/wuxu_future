# Flowable 核心概念：身份链接（IdentityLink）全解析 + 实战操作 + 避坑指南

身份链接（IdentityLink）是Flowable中**绑定流程任务/流程实例与用户/用户组**的**多对多关联桥梁**，本质是记录“谁对哪个流程任务/实例拥有什么权限/身份”的关联关系，核心用于实现**任务的候选人、候选组分配**（生产最高频场景），同时支持流程实例的负责人、参与人关联，是Flowable实现**任务权限分配**和**身份隔离**的核心机制。

如果说流程任务是“需要人工处理的工作项”，那身份链接就是“指定哪些人/哪些组有资格处理这个工作项”的**权限清单**——比如经理审批任务可设置候选组`dept-manager`（部门经理组），该组下的所有用户都能认领此任务；或设置候选人`lisi`、`wangwu`，仅这两个用户可认领，这都是通过身份链接实现的。

身份链接与`TaskService`强关联，同时联动`IdentityService`（身份管理）、`HistoryService`（历史身份链接追溯），本文延续之前的风格，基于**Spring Boot 2.7+Flowable 6.8.0+员工请假流程**案例，从**核心概念→类型→存储表→实战操作→生产流程→外部身份整合→避坑指南**逐步讲解，所有代码可直接复用，覆盖生产环境所有高频场景。

## 一、什么是身份链接？（通俗解释+核心特性）

### 1. 本质定义

身份链接（IdentityLink）是Flowable中用于**关联流程任务/流程实例**与**用户（User）/用户组（Group）**的**带类型的关联关系**，本质是存储在数据库中的多对多关联记录，核心回答两个问题：

- **谁**（哪个用户/用户组，用ID标识）；
- **对什么**（哪个流程任务/流程实例，用ID标识）；
- **拥有什么身份/权限**（如候选人、候选组成员、任务所有者、流程参与人）。

身份链接的核心价值是**实现任务的“待分配”权限管理**——区别于直接给任务设置`assignee`（确定的处理人），身份链接是构建**“候选人/候选组池”**，池中的用户/组拥有任务的认领权限，只有认领后，任务的`assignee`才会被赋值，实现任务的灵活分配。

### 2. 核心特性

Flowable的身份链接设计遵循**轻量、松耦合、生命周期绑定**原则，核心特性如下，是生产使用的基础：

1. **多对多关联**：一个任务/实例可关联多个用户/组，一个用户/组可关联多个任务/实例，满足“多人可处理一个任务”“一人可处理多个任务”的场景；
2. **类型化身份**：关联关系带**身份类型（IdentityLinkType）**，如候选人、候选组、任务所有者、流程参与人，不同类型对应不同的权限；
3. **运行时+历史双存储**：运行时身份链接存储在`ACT_RU_IDENTITYLINK`，任务/实例结束后，自动迁移到历史表`ACT_HI_IDENTITYLINK`永久存储，供审计追溯；
4. **生命周期绑定**：任务级身份链接的生命周期与**所属任务**绑定（任务完成则进入历史），实例级身份链接与**所属流程实例**绑定（实例结束则进入历史）；
5. **与外部身份系统松耦合**：Flowable仅存储**用户/组的ID**，不存储用户/组的详情（如姓名、密码、部门），生产中可无缝对接外部身份系统（如Spring Security、LDAP、企业统一认证），Flowable不做身份校验，仅做关联；
6. **无独立Service**：身份链接无专属的IdentityLinkService，所有操作通过**TaskService**（任务级，高频）和**RuntimeService**（实例级，低频）实现，历史身份链接通过**HistoryService**查询。

### 3. 与核心概念的关联（避坑必备，理清边界）

#### （1）身份链接 VS 任务`assignee`（处理人）

这是新手最容易混淆的点，二者是**“待分配权限池”**与**“确定处理人”**的关系，核心区别如下：

| 对比维度         | 身份链接（候选人/候选组）| 任务assignee（处理人）|
|------------------|---------------------------------|---------------------------------|
| **状态**         | 待分配，权限池阶段               | 已分配，确定处理人阶段           |
| **存储位置**     | 主要在ACT_RU_IDENTITYLINK表      | 直接在ACT_RU_TASK的ASSIGNEE_字段 |
| **操作时机**     | 任务创建时/运行中设置            | 任务认领（claim）后自动赋值      |
| **权限**         | 拥有**认领权限**，无直接处理权限 | 拥有**唯一处理权限**             |
| **数量**         | 一个任务可对应多个（多候选人/组）| 一个任务只能对应一个（唯一处理人）|
| **核心API**      | TaskService.addCandidateUser/Group | TaskService.claim/setAssignee    |

**核心流转**：设置候选人/候选组（身份链接）→ 用户认领任务（claim）→ 任务assignee自动赋值为认领用户ID → 身份链接保留（释放后可再次认领）。

#### （2）身份链接 VS Flowable内置`IdentityService`

`IdentityService`是Flowable提供的**基础身份管理服务**，支持用户/用户组的CRUD（`createUser`/`createGroup`），但**生产环境几乎不使用**，身份链接与它的关系是：

- Flowable内置的User/Group仅为**测试环境使用**，生产中对接外部身份系统（如企业的用户中心）；
- 身份链接**仅存储用户/组的ID**，不依赖Flowable内置的User/Group是否存在（引擎不做身份校验）；
- 即使Flowable中未创建User/Group，只要传入合法的ID，就能为任务添加候选人/组，身份校验由**外部系统**在前端/接口层完成。

## 二、核心身份链接类型（IdentityLinkType）

Flowable通过`org.flowable.engine.IdentityLinkType`定义了**标准的身份链接类型**，不同类型对应不同的**身份/权限**，分为**任务级**（高频）和**实例级**（低频），生产中**90%以上使用任务级的候选人/候选组类型**。

### 1. 任务级身份链接（生产高频，核心）

仅关联**流程任务**，`ACT_RU_IDENTITYLINK`的`TASK_ID_`有值，`PROC_INST_ID_`关联所属实例，核心类型：

- **`candidate`（候选人）**：指定**某个用户**为任务的候选人，该用户拥有任务的认领权限，对应API：`TaskService.addCandidateUser`；
- **`candidateGroup`（候选组）**：指定**某个用户组**为任务的候选组，组内所有用户都拥有任务的认领权限，对应API：`TaskService.addCandidateGroup`；
- **`owner`（任务所有者）**：任务的创建者/负责人，一般用于任务的管理权限（如转办、委派），生产中使用较少，对应API：`TaskService.setOwner`；
- **`assignee`（处理人）**：任务的确定处理人，虽`assignee`主要存储在任务表，但引擎也会为其生成一条身份链接记录，类型为`assignee`。

### 2. 实例级身份链接（生产低频，辅助）

关联**整个流程实例**，`ACT_RU_IDENTITYLINK`的`TASK_ID_`为null，`PROC_INST_ID_`有值，适用于标记流程实例的整体负责人、参与人，生产中使用较少，核心类型：

- **`owner`（实例所有者）**：流程实例的负责人，拥有实例的整体管理权限；
- **`participant`（实例参与人）**：参与流程实例的用户/组，可查看实例的所有信息，无处理权限；
- **`starter`（实例启动人）**：流程实例的启动人，引擎会自动为启动人生成一条实例级身份链接，类型为`starter`。

### 3. 生产常用类型总结

| 身份类型         | 关联对象 | 实战频率 | 核心作用                     | 核心API                          |
|------------------|----------|----------|------------------------------|----------------------------------|
| candidate        | 任务+用户 | ★★★★★    | 为任务添加单个候选人         | TaskService.addCandidateUser     |
| candidateGroup   | 任务+组  | ★★★★★    | 为任务添加候选组，组内用户可认领 | TaskService.addCandidateGroup   |
| owner            | 任务/实例 | ★★       | 标记任务/实例的所有者        | TaskService.setOwner/RuntimeService.addInstanceOwner |
| participant      | 实例     | ★★       | 标记实例的参与人             | RuntimeService.addInstanceParticipant |
| starter          | 实例     | ★★★      | 引擎自动标记实例启动人       | 无需手动操作，引擎自动生成       |

## 三、核心存储表（运行时+历史，必知）

身份链接的记录分为**运行时**和**历史**，分别存储在两张专用表中，引擎自动维护同步，无需手动操作，表结构简单，核心字段围绕“关联对象+身份类型”设计。

### 1. ACT_RU_IDENTITYLINK - 运行时身份链接表【核心】

- **核心作用**：存储**未完成的任务/未结束的实例**的身份链接记录，任务完成/实例结束后，自动迁移到历史表；
- **关键字段**（生产高频关注）：
  - `ID_`：身份链接唯一ID，引擎自动生成；
  - `TASK_ID_`：关联的流程任务ID，**任务级**身份链接有值，**实例级**为null；
  - `PROC_INST_ID_`：关联的流程实例ID，所有身份链接均有值；
  - `USER_ID_`：关联的用户ID，候选人/参与人/所有者为用户时非空；
  - `GROUP_ID_`：关联的用户组ID，候选组为组时非空（**USER_ID_和GROUP_ID_必居其一**）；
  - `TYPE_`：身份链接类型，如`candidate`、`candidateGroup`、`owner`；
  - `TENANT_ID_`：租户ID，多租户场景下的隔离标识。
- **核心特性**：`USER_ID_`和`GROUP_ID_`互斥，一条记录只能关联**一个用户**或**一个组**，不能同时关联。

### 2. ACT_HI_IDENTITYLINK - 历史身份链接表

- **核心作用**：存储**已完成的任务/已结束的实例**的身份链接快照，**永久存储**，供审计追溯；
- **关键字段**：与运行时表完全一致，无额外字段；
- **核心特性**：只读，无修改/删除API，仅由引擎在任务/实例结束时自动生成，历史数据清理时随关联的任务/实例一起清理。

## 四、身份链接核心实战操作（全覆盖生产场景）

身份链接的操作分为**任务级（高频）**、**实例级（低频）**和**历史查询（审计）**，所有操作基于之前的Spring Boot 2.7+Flowable 6.8.0环境，沿用请假流程案例（`leaveProcessExclusive`），注入核心Service即可直接测试。

### 前置准备

1. 环境：已部署请假流程，启动流程实例生成**经理审批任务**（未分配处理人，用于添加候选人/组）；
2. 注入Service：核心操作通过`TaskService`，实例级通过`RuntimeService`，历史查询通过`HistoryService`；
3. 模拟数据：用户ID（`zhangsan`、`lisi`、`wangwu`）、用户组ID（`dept-manager`-部门经理组、`hr-group`-人事组），无需在Flowable中创建，直接使用ID即可。

```java
import org.flowable.engine.HistoryService;
import org.flowable.engine.RuntimeService;
import org.flowable.engine.TaskService;
import org.flowable.engine.history.HistoricIdentityLink;
import org.flowable.engine.runtime.ProcessInstance;
import org.flowable.engine.task.IdentityLink;
import org.flowable.engine.task.Task;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.transaction.annotation.Transactional;

import java.util.HashMap;
import java.util.List;
import java.util.Map;

@SpringBootTest
public class IdentityLinkTest {
    // 任务级身份链接核心操作Service
    @Autowired
    private TaskService taskService;
    // 实例级身份链接操作Service
    @Autowired
    private RuntimeService runtimeService;
    // 历史身份链接查询Service
    @Autowired
    private HistoryService historyService;

    // 工具方法：启动请假流程实例，返回经理审批任务ID（通用）
    private String getApproveTaskId() {
        String processKey = "leaveProcessExclusive";
        Map<String, Object> vars = new HashMap<>();
        vars.put("applicantId", "zhangsan");
        vars.put("leaveDays", 3);
        vars.put("managerId", "lisi");
        // 启动实例
        ProcessInstance pi = runtimeService.startProcessInstanceByKey(processKey, vars);
        // 完成申请人提交任务，生成经理审批任务
        Task applyTask = taskService.createTaskQuery().processInstanceId(pi.getId()).taskName("申请人提交请假").singleResult();
        taskService.complete(applyTask.getId());
        // 获取经理审批任务ID
        Task approveTask = taskService.createTaskQuery().processInstanceId(pi.getId()).singleResult();
        System.out.println("生成经理审批任务，ID：" + approveTask.getId() + "，名称：" + approveTask.getName());
        return approveTask.getId();
    }
}
```

### 操作1：任务级身份链接核心操作（生产最高频，候选人/候选组）

任务级是生产中最常用的场景，核心包括**添加候选人/候选组、查询任务的身份链接、删除候选人/候选组、认领任务（身份链接→assignee）、释放任务（assignee→身份链接）**，覆盖任务分配的全流程。

```java
/**
 * 任务级身份链接核心操作：添加→查询→删除→认领→释放（生产全流程）
 */
@Test
@Transactional
public void testTaskIdentityLink() {
    // 1. 获取经理审批任务ID
    String taskId = getApproveTaskId();
    // 模拟候选人/组ID
    String candidateUser1 = "lisi";
    String candidateUser2 = "wangwu";
    String candidateGroup = "dept-manager";

    // ---------------------- 步骤1：添加候选人/候选组（核心） ----------------------
    // 添加单个候选人
    taskService.addCandidateUser(taskId, candidateUser1);
    // 再添加一个候选人（一个任务多个候选人）
    taskService.addCandidateUser(taskId, candidateUser2);
    // 添加候选组
    taskService.addCandidateGroup(taskId, candidateGroup);
    System.out.println("已为任务" + taskId + "添加候选人：" + candidateUser1 + "," + candidateUser2 + "，候选组：" + candidateGroup);

    // ---------------------- 步骤2：查询任务的所有身份链接（查看权限池） ----------------------
    System.out.println("=== 任务" + taskId + "的身份链接列表 ===");
    List<IdentityLink> identityLinks = taskService.getIdentityLinksForTask(taskId);
    for (IdentityLink link : identityLinks) {
        String target = link.getUserId() != null ? "用户：" + link.getUserId() : "组：" + link.getGroupId();
        System.out.println("身份类型：" + link.getType() + "，关联对象：" + target + "，任务ID：" + link.getTaskId());
    }

    // ---------------------- 步骤3：删除指定候选人/候选组（移除权限池） ----------------------
    taskService.deleteCandidateUser(taskId, candidateUser2); // 删除候选人wangwu
    System.out.println("=== 删除候选人" + candidateUser2 + "后，剩余身份链接 ===");
    taskService.getIdentityLinksForTask(taskId).forEach(link -> {
        String target = link.getUserId() != null ? "用户：" + link.getUserId() : "组：" + link.getGroupId();
        System.out.println(link.getType() + " - " + target);
    });

    // ---------------------- 步骤4：认领任务（从身份链接池→确定assignee，核心流转） ----------------------
    String claimUser = "lisi";
    taskService.claim(taskId, claimUser); // 认领任务
    Task claimedTask = taskService.createTaskQuery().taskId(taskId).singleResult();
    System.out.println("=== " + claimUser + "认领任务后 ===");
    System.out.println("任务处理人（assignee）：" + claimedTask.getAssignee()); // 已赋值为lisi
    // 认领后身份链接仍保留（释放后可再次认领）
    System.out.println("认领后身份链接是否保留：" + !taskService.getIdentityLinksForTask(taskId).isEmpty()); // true

    // ---------------------- 步骤5：释放任务（从assignee→身份链接池，取消处理人） ----------------------
    taskService.unclaim(taskId); // 释放任务
    Task unclaimedTask = taskService.createTaskQuery().taskId(taskId).singleResult();
    System.out.println("=== 释放任务后 ===");
    System.out.println("任务处理人（assignee）：" + (unclaimedTask.getAssignee() == null ? "未分配" : unclaimedTask.getAssignee())); // null
    System.out.println("释放后身份链接是否存在：" + !taskService.getIdentityLinksForTask(taskId).isEmpty()); // true
}
```

#### 核心API总结（任务级，熟记）

| 操作         | 核心API | 作用 |
|--------------|---------|------|
| 添加候选人   | `taskService.addCandidateUser(taskId, userId)` | 为任务添加单个候选人 |
| 添加候选组   | `taskService.addCandidateGroup(taskId, groupId)` | 为任务添加单个候选组 |
| 查询身份链接 | `taskService.getIdentityLinksForTask(taskId)` | 查询任务的所有身份链接 |
| 删除候选人   | `taskService.deleteCandidateUser(taskId, userId)` | 从任务移除指定候选人 |
| 删除候选组   | `taskService.deleteCandidateGroup(taskId, groupId)` | 从任务移除指定候选组 |
| 认领任务     | `taskService.claim(taskId, userId)` | 候选人认领任务，assignee自动赋值 |
| 释放任务     | `taskService.unclaim(taskId)` | 取消处理人，assignee置空，回到身份链接池 |
| 设置处理人   | `taskService.setAssignee(taskId, userId)` | 直接为任务设置处理人（跳过认领，生产慎用） |

### 操作2：实例级身份链接操作（生产低频，实例所有者/参与人）

实例级身份链接关联整个流程实例，用于标记实例的所有者、参与人，引擎会自动为**流程启动人**生成类型为`starter`的实例级身份链接，手动操作仅适用于特殊的实例管理场景。

```java
/**
 * 实例级身份链接操作：添加实例所有者/参与人 + 查询（生产低频）
 */
@Test
@Transactional
public void testProcessInstanceIdentityLink() {
    // 1. 启动流程实例，获取实例ID
    String processKey = "leaveProcessExclusive";
    ProcessInstance pi = runtimeService.startProcessInstanceByKey(processKey, new HashMap<>());
    String instanceId = pi.getId();
    // 模拟用户/组ID
    String ownerUser = "zhangsan"; // 实例所有者
    String participantUser = "lisi"; // 实例参与人
    String participantGroup = "hr-group"; // 实例参与组

    // ---------------------- 步骤1：添加实例所有者/参与人 ----------------------
    runtimeService.addInstanceOwner(instanceId, ownerUser); // 添加实例所有者
    runtimeService.addInstanceParticipant(instanceId, participantUser); // 添加实例参与人
    runtimeService.addInstanceParticipantGroup(instanceId, participantGroup); // 添加实例参与组
    System.out.println("已为实例" + instanceId + "添加所有者：" + ownerUser + "，参与人：" + participantUser + "，参与组：" + participantGroup);

    // ---------------------- 步骤2：查询实例的所有身份链接 ----------------------
    System.out.println("=== 实例" + instanceId + "的身份链接列表（含引擎自动生成的starter） ===");
    List<IdentityLink> instanceLinks = runtimeService.getIdentityLinksForProcessInstance(instanceId);
    for (IdentityLink link : instanceLinks) {
        String target = link.getUserId() != null ? "用户：" + link.getUserId() : "组：" + link.getGroupId();
        System.out.println("身份类型：" + link.getType() + "，关联对象：" + target);
    }
    // 注：引擎会自动为启动人生成type=starter的身份链接，USER_ID_为启动人（此处为null，因未设置启动人）
}
```

### 操作3：历史身份链接查询（审计追溯，生产必备）

任务完成/流程实例结束后，运行时身份链接会自动迁移到`ACT_HI_IDENTITYLINK`，通过`HistoryService`查询，用于**审计任务的候选人/处理人、实例的参与人**，是流程审计的重要组成部分。

```java
/**
 * 历史身份链接查询：任务级+实例级（审计追溯核心）
 */
@Test
@Transactional
public void testHistoricIdentityLink() {
    // 1. 启动流程，处理任务，生成历史数据
    String taskId = getApproveTaskId();
    String instanceId = taskService.createTaskQuery().taskId(taskId).singleResult().getProcessInstanceId();
    // 添加候选人并完成任务
    taskService.addCandidateUser(taskId, "lisi");
    taskService.claim(taskId, "lisi");
    taskService.complete(taskId); // 完成任务，身份链接进入历史

    // ---------------------- 步骤1：查询历史任务的身份链接 ----------------------
    System.out.println("=== 历史任务" + taskId + "的身份链接 ===");
    List<HistoricIdentityLink> historicTaskLinks = historyService.getHistoricIdentityLinksForTask(taskId);
    historicTaskLinks.forEach(link -> {
        String target = link.getUserId() != null ? "用户：" + link.getUserId() : "组：" + link.getGroupId();
        System.out.println("身份类型：" + link.getType() + "，关联对象：" + target);
    });

    // ---------------------- 步骤2：查询历史流程实例的身份链接 ----------------------
    System.out.println("=== 历史实例" + instanceId + "的身份链接 ===");
    List<HistoricIdentityLink> historicInstanceLinks = historyService.getHistoricIdentityLinksForProcessInstance(instanceId);
    historicInstanceLinks.forEach(link -> {
        String target = link.getUserId() != null ? "用户：" + link.getUserId() : "组：" + link.getGroupId();
        System.out.println("身份类型：" + link.getType() + "，关联对象：" + target);
    });
}
```

### 操作4：BPMN中静态配置身份链接（候选人/候选组）

除了通过API动态添加候选人/候选组，还可以在**BPMN文件中静态配置**，任务创建时引擎会自动生成对应的身份链接，适用于**固定的候选人/组规则**，如“所有经理审批任务的候选组都是dept-manager”。

#### BPMN配置片段（经理审批任务添加候选组）

```xml
<!-- 经理审批任务：静态配置候选组dept-manager，引擎自动生成身份链接 -->
<userTask id="managerApproveTask" name="直属经理审批">
    <extensionElements>
        <!-- 静态配置候选组 -->
        <flowable:candidateGroups>dept-manager</flowable:candidateGroups>
        <!-- 静态配置候选人，多个用逗号分隔 -->
        <!-- <flowable:candidateUsers>lisi,wangwu</flowable:candidateUsers> -->
    </extensionElements>
</userTask>
```

#### 核心注意点

1. BPMN中用`<flowable:candidateUsers>`配置候选人，多个用户ID用**逗号分隔**；
2. 用`<flowable:candidateGroups>`配置候选组，多个组ID用**逗号分隔**；
3. 静态配置的身份链接，任务创建时引擎自动生成，运行中可通过API**动态添加/删除**，实现“固定+动态”的混合分配。

## 五、生产核心场景：与外部身份系统的整合

Flowable的身份链接设计的最大优势是**与外部身份系统松耦合**，生产中**绝对不会使用**Flowable内置的`IdentityService`创建用户/组，而是对接企业的**统一身份认证系统**（如Spring Security、LDAP、企业用户中心、OAuth2.0认证系统），核心整合原则如下：

### 1. 核心整合原则

1. **仅传ID，不存详情**：外部身份系统维护用户/组的全量信息（姓名、密码、部门、角色），Flowable仅在身份链接中存储**用户/组的唯一ID**（如企业用户中心的user_id、group_id）；
2. **外部校验，内部关联**：身份的合法性校验（如用户是否存在、是否属于某组）由**外部系统**在**前端/接口层**完成，Flowable引擎不做任何校验，仅负责维护身份链接的关联关系；
3. **API无缝适配**：所有身份链接的API（`addCandidateUser`/`addCandidateGroup`）直接传入外部系统的用户/组ID即可，无需做任何适配；
4. **多租户隔离**：多租户场景下，在身份链接的`TENANT_ID_`字段添加租户标识，同时外部身份系统需做租户隔离，避免跨租户的身份ID冲突。

### 2. 典型整合流程（以企业用户中心为例）

1. **用户登录**：用户通过企业用户中心登录，前端获取用户的**ID、所属组ID**；
2. **查询可认领任务**：前端将用户ID/组ID传给后端，后端通过`TaskService.createTaskQuery().candidateUser(userId)/candidateGroup(groupId)`查询该用户可认领的任务；
3. **任务认领/处理**：用户选择任务认领，后端调用`taskService.claim(taskId, userId)`，任务assignee赋值为用户ID；
4. **审计追溯**：流程结束后，通过`HistoryService`查询历史身份链接，结合外部用户中心的ID查询用户/组详情，展示审计报表。

### 3. 关键避坑：用户/组ID的唯一性

跨系统整合时，**用户/组ID必须全局唯一**（如使用雪花算法、UUID），避免不同系统的ID冲突，若企业存在多租户，需在ID中添加租户前缀（如`tenant1_lisi`），或通过Flowable的`TENANT_ID_`字段做租户隔离。

## 六、身份链接实战核心避坑指南（生产高频）

结合企业实战经验，整理了身份链接使用的**6个高频坑点**，覆盖**配置、操作、整合、性能**全流程，严格遵守可避免90%的问题，其中**混淆assignee和候选人、生产使用内置IdentityService、直接操作身份链接表**是新手最容易踩的坑。

### 1. 混淆任务`assignee`和候选人，直接设置assignee跳过身份链接

- **坑点**：开发时为了便捷，直接通过`taskService.setAssignee(taskId, userId)`为任务设置处理人，跳过候选人/候选组的身份链接池，导致任务分配无权限控制，任何用户都能被设置为处理人；
- **解决方案**：
  1. 生产中**必须通过身份链接构建候选人/候选组池**，仅允许池中的用户认领任务；
  2. 禁止直接使用`setAssignee`（除了特殊的管理员转办场景），所有处理人必须通过**认领（claim）**生成；
  3. 前端仅展示用户可认领的任务（基于`candidateUser/candidateGroup`查询），避免无权限用户看到任务。

### 2. 生产环境使用Flowable内置的`IdentityService`创建用户/组

- **坑点**：在生产中使用`identityService.createUser/ createGroup`创建用户/组，导致Flowable的身份数据与企业外部身份系统不一致，出现“用户在Flowable中存在但在企业系统中不存在”的情况；
- **解决方案**：
  1. **生产环境彻底禁用**Flowable内置的`IdentityService`的CRUD操作；
  2. 仅在**测试环境**使用内置的User/Group做快速测试；
  3. 若需在Flowable中做身份校验，可通过**自定义拦截器**对接外部身份系统。

### 3. 添加候选人/组后，未在外部系统做身份合法性校验

- **坑点**：后端直接接收前端传入的用户/组ID，添加为任务候选人/组，未在外部系统校验该ID是否存在，导致无效的ID被存入身份链接，用户无法认领任务；
- **解决方案**：
  1. 所有添加候选人/组的操作，**后端必须先调用外部身份系统的接口**，校验用户/组ID的合法性；
  2. 校验失败则直接返回错误，不执行添加操作；
  3. 前端在选择候选人/组时，通过外部身份系统的接口加载**合法的用户/组列表**，避免手动输入无效ID。

### 4. 多租户场景下未做身份链接隔离，导致跨租户任务认领

- **坑点**：多租户系统中，身份链接未设置`TENANT_ID_`，不同租户的用户/组ID可能重复，导致A租户的用户能认领B租户的任务，引发数据泄露；
- **解决方案**：
  1. 所有身份链接的操作（添加/查询/删除）**必须指定租户ID**（`tenantId`）；
  2. Flowable的所有查询器均支持`tenantId`方法，如`taskService.createTaskQuery().tenantId("tenant1").candidateUser(userId)`；
  3. 外部身份系统的用户/组ID需做租户隔离，确保跨租户ID唯一。

### 5. 直接操作身份链接表（ACT_RU/HI_IDENTITYLINK），导致状态不一致

- **坑点**：为了便捷，直接通过SQL修改/删除身份链接表的记录，跳过Flowable的原生API，导致引擎的内存状态与数据库状态不一致，出现“候选人已删除但仍能认领任务”的问题；
- **解决方案**：
  1. **禁止任何直接操作身份链接表的SQL**，所有操作（添加/删除/查询）必须通过Flowable的原生API（TaskService/RuntimeService/HistoryService）；
  2. 引擎会自动维护身份链接与任务/实例的关联关系，原生API会做状态校验，避免数据不一致。

### 6. 大量任务的身份链接查询未分页，导致查询性能低下

- **坑点**：查询某用户/组的可认领任务时，未使用`listPage`分页，直接调用`list()`，当可认领任务数量巨大时，导致数据库查询超时、前端加载缓慢；
- **解决方案**：
  1. **所有可认领任务的查询必须分页**，前端做分页展示，后端设置合理的分页大小（如10/20/50）；
  2. 为身份链接表的核心查询字段添加**索引**，如`TASK_ID_`、`USER_ID_`、`GROUP_ID_`、`TYPE_`、`TENANT_ID_`，提升查询性能。

## 七、核心总结

1. **身份链接是“权限关联桥梁”**：本质是流程任务/实例与用户/组的多对多关联记录，核心作用是构建**候选人/候选组池**，实现任务的灵活分配，区别于确定的处理人（assignee）；
2. **任务级是生产核心**：90%以上的场景使用任务级的候选人（candidate）和候选组（candidateGroup），实例级仅用于特殊的实例管理场景，引擎自动为启动人生成starter类型的身份链接；
3. **核心流转是“池→人”**：添加候选人/组（身份链接池）→ 用户认领（claim）→ 任务assignee赋值 → 释放任务（unclaim）→ 回到身份链接池，禁止直接设置assignee跳过认领；
4. **与外部身份系统松耦合**：Flowable仅存储用户/组的ID，不做身份校验，生产中对接企业统一身份系统，校验由外部系统完成，API无缝适配；
5. **运行时+历史双存储**：运行时身份链接在ACT_RU_IDENTITYLINK，任务/实例结束后自动迁移到ACT_HI_IDENTITYLINK永久存储，供审计追溯；
6. **生产避坑三原则**：禁用内置IdentityService、禁止直接操作数据库表、所有查询必须分页，多租户场景必须做身份隔离；
7. **无专属Service**：所有操作通过TaskService（任务级）、RuntimeService（实例级）、HistoryService（历史查询）实现，无需额外的Service。

身份链接是Flowable实现**任务权限分配**的核心机制，掌握它后，你就能实现企业中灵活的任务分配场景（如多人可认领、组内认领），结合之前的流程变量、网关、历史数据等知识点，Flowable的**业务开发能力已完全覆盖**，后续只需补充异步任务、邮件任务、多租户等高级特性，即可完成企业级工作流系统的全流程开发。
