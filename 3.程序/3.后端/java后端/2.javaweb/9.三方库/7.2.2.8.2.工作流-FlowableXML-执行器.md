# Flowable 工作流执行对象（Execution）全维度深度详解

1. 执行对象贯穿整个流程，执行对象就是流程，其路过/停留的位置，就是节点。
2. 可以在xml任意节点设定执行监听器（注意这不是执行对象，而是监听器，流程节点变化可以触发监听）

## 一、基础定义与本质（先搞懂它到底是什么）

### 1. 核心定义

1. **Execution（执行对象）**
   Flowable 流程运行时的**核心实体**，可以把它理解为：**流程的执行指针 + 运行路线 + 状态载体**。
   它代表流程中**一条正在运行的执行路径**，是引擎调度流程的最小单元。
2. **ProcessInstance（流程实例）**
   是**根执行对象**（继承 Execution 接口），代表一次完整的流程启动，是所有子执行的「总指挥官」。
3. **子执行对象**
   并行网关、多实例任务、子流程会自动创建的分支执行，用于处理并发/批量逻辑。

### 2. 最本质的一句话

**线性流程 = 1个执行对象走完全程**
**并发/子流程/多实例 = 1个根执行 + N个子执行组成树形结构**
执行对象不是业务节点（不是任务、网关），而是**驱动节点流转的「灵魂」**。

### 3. 关键区分

- 执行对象 = 路线/指针（负责走流程）
- 流程节点 = 站点/关卡（等待执行对象经过）
- 执行监听器 = 监控钩子（监听指针的移动状态）

---

## 二、执行对象的核心作用（它存在的意义）

执行对象是 Flowable 引擎的**运行基石**，没有它流程无法运转，核心作用有5个：

1. **状态追踪**
   记录流程当前跑到哪个节点、是否运行中、是否挂起，是流程状态的唯一来源。
2. **流转控制**
   驱动流程从一个节点移动到下一个节点，处理分支、合并、子流程等逻辑。
3. **变量承载**
   流程变量（全局/局部）的唯一存储载体，实现数据在流程中的传递和隔离。
4. **并发管理**
   通过创建子执行，支持并行网关、会签、多实例等并发场景。
5. **事件触发**
   生命周期变化时触发执行监听器，实现日志、变量初始化、业务增强等无侵入扩展。

## 三、底层原理与实现方式（它是怎么工作的）

### 1. 数据存储原理

执行对象的运行时数据**永久存在 `ACT_RU_EXECUTION` 表**，流程结束后迁移到历史表 `ACT_HI_EXECUTION`。
核心字段（决定行为）：

- `ID_`：执行唯一ID
- `PROC_INST_ID_`：所属流程实例ID（根执行的ID=此字段）
- `ACT_ID_`：当前停留的节点ID
- `IS_ACTIVE_`：是否激活（运行中）
- `PARENT_ID_`：父执行ID（构建树形结构）
- `IS_CONCURRENT_`：是否为并行分支
- `IS_MI_ROOT_`：是否为多实例根执行

### 2. 生命周期原理（执行对象的一生）

1. **创建**：流程启动生成根执行；并发/子流程生成子执行
2. **流转**：沿连线（序列流）移动，更新当前节点
3. **等待**：进入用户任务/接收任务，暂停等待触发
4. **唤醒**：任务完成/事件触发，继续流转
5. **合并**：并行分支到达汇聚网关，子执行销毁
6. **销毁**：子执行完成直接销毁；根执行完成=流程结束

### 3. 树形结构原理

执行对象通过 `PARENT_ID_` 形成**父子树形结构**：

- 根执行（流程实例）：顶级节点
- 子执行：并行分支、子流程、多实例
- 变量继承：子执行默认继承父执行变量，局部变量仅自身可见

### 4. 与所有流程节点的交互原理（最关键！）

| 节点类型 | 执行对象行为 | 数量变化 |
|--------|--------------|----------|
| 开始事件 | 执行对象诞生（根执行） | 0→1 |
| 结束事件 | 执行对象销毁 | 1→0 |
| 序列流（连线） | 执行对象移动，触发`take`监听器 | 不变 |
| 用户任务 | 执行对象停留等待，1:1绑定任务 | 不变 |
| 服务/脚本任务 | 执行对象自动执行，瞬间通过 | 不变 |
| 接收任务 | 执行对象等待，`trigger`唤醒 | 不变 |
| 排他网关 | 选择一条路线，不创建子执行 | 不变 |
| 并行分叉 | 1个父执行克隆N个子执行 | 1→N |
| 并行汇聚 | 等待所有分支到达，合并为1个 | N→1 |
| 子流程 | 创建独立子执行树，父执行暂停 | 父暂停+子创建 |
| 多实例任务 | 创建根执行+N个实例子执行 | 1→1+N |
| 边界事件 | 寄生在宿主执行，触发后中断原执行 | 共用宿主执行 |

### 5. 执行监听器原理（你之前困惑的核心）

执行监听器**不是独立节点**，是依附在**流程/节点/连线**上的钩子，监听执行对象3个生命周期阶段：

1. **start**：执行对象**进入节点**时触发
2. **end**：执行对象**离开节点**时触发
3. **take**：执行对象**走连线**时触发
👉 监听器的作用：执行对象动一下，就自动跑你的自定义代码。

## 四、完整使用方式（开发中怎么用）

### 1. 核心API操作（RuntimeService）

#### （1）查询执行对象

```java
// 1. 查询流程所有执行对象（根+子执行）
List<Execution> executions = runtimeService.createExecutionQuery()
        .processInstanceId("流程实例ID")
        .list();

// 2. 仅查询根执行（流程实例）
Execution rootExec = runtimeService.createExecutionQuery()
        .processInstanceId("流程实例ID")
        .onlyProcessInstances()
        .singleResult();

// 3. 查询停在指定节点的执行
List<Execution> taskExec = runtimeService.createExecutionQuery()
        .activityId("节点ID")
        .list();
```

#### （2）执行对象控制

```java
// 唤醒接收任务/等待事件（仅限等待节点）
runtimeService.trigger("执行ID");
// 挂起执行
runtimeService.suspendExecution("执行ID");
// 安全终止流程（禁止直接删执行）
runtimeService.deleteProcessInstance("流程实例ID", "手动终止");
```

#### （3）变量操作（核心）

```java
// 全局变量：根执行存储，全流程可见
runtimeService.setVariable("执行ID", "key", "value");
// 局部变量：仅当前执行可见（并发必用）
runtimeService.setVariableLocal("执行ID", "key", "value");
```

### 2. 执行监听器使用（XML配置）

#### （1）节点上配置监听器

```xml
<userTask id="userTask1" name="审批">
  <extensionElements>
    <!-- 进入节点触发 -->
    <flowable:executionListener event="start" class="com.test.StartListener"/>
    <!-- 离开节点触发 -->
    <flowable:executionListener event="end" class="com.test.EndListener"/>
  </extensionElements>
</userTask>
```

#### （2）连线上配置监听器

```xml
<sequenceFlow id="flow1" sourceRef="start" targetRef="userTask1">
  <extensionElements>
    <!-- 执行对象走连线时触发 -->
    <flowable:executionListener event="take" class="com.test.TakeListener"/>
  </extensionElements>
</sequenceFlow>
```

#### （3）监听器代码

```java
public class MyListener implements ExecutionListener {
    @Override
    public void notify(DelegateExecution execution) {
        // 必须捕获异常！禁止抛异常
        try {
            String execId = execution.getId(); // 执行ID
            String procInstId = execution.getProcessInstanceId(); // 流程实例ID
            execution.setVariableLocal("localVar", "测试"); // 局部变量
        } catch (Exception e) {
            log.error("监听器异常", e);
        }
    }
}
```

### 3. 实战常用操作

1. 根据任务ID获取执行对象

```java
Task task = taskService.createTaskQuery().taskId("任务ID").singleResult();
Execution execution = runtimeService.createExecutionQuery().executionId(task.getExecutionId()).singleResult();
```

2. 获取多实例根执行

```java
Execution miRoot = runtimeService.createExecutionQuery()
        .processInstanceId("流程实例ID")
        .multiInstanceRoot()
        .singleResult();
```

## 五、必踩坑点 + 注意事项（生产避坑指南）

### 1. 概念类坑（90%的人 first 踩）

- ❌ 错误：把 `ProcessInstance` 和普通 `Execution` 当成同一个东西
  ✅ 正确：流程实例 = 根执行，子执行是分支，查询分支必须用 `ExecutionQuery`
- ❌ 错误：把执行监听器当成业务节点
  ✅ 正确：监听器是钩子，不是流程步骤，不影响流转

### 2. 操作类坑（最容易导致流程卡死）

- ❌ 错误：用 `trigger()` 完成用户任务
  ✅ 正确：用户任务用 `taskService.complete()`，`trigger()` 仅用于接收任务
- ❌ 错误：手动删除子执行对象
  ✅ 正确：终止流程用 `deleteProcessInstance()`，手动删执行会导致数据错乱
- ❌ 错误：并行网关少一个分支到达
  ✅ 正确：必须保证所有分支都走到汇聚网关，否则流程永久卡住

### 3. 变量类坑（数据丢失/覆盖）

- ❌ 错误：并行/多实例用全局变量
  ✅ 正确：并发场景**必须用局部变量（setVariableLocal）**，避免数据覆盖
- ❌ 错误：子流程变量默认回传父流程
  ✅ 正确：子流程变量独立，需手动配置输出映射

### 4. 监听器坑（流程卡死元凶）

- ❌ 错误：监听器抛出未捕获异常
  ✅ 正确：监听器必须`try-catch`，异常会回滚事务，流程直接卡死
- ❌ 错误：监听器中执行慢接口、长事务
  ✅ 正确：监听器只做轻量操作，避免阻塞引擎

### 5. 并发与性能坑

- ❌ 错误：多线程同时修改同一个执行对象
  ✅ 正确：加分布式锁，避免乐观锁异常（OptimisticLockingException）
- ❌ 错误：创建大量并行分支（上千个）
  ✅ 正确：控制并发数量，防止执行对象堆积导致性能下降

### 6. 绝对禁止行为

1. 禁止手动修改 `ACT_RU_EXECUTION` 表数据
2. 禁止在监听器中开启异步线程
3. 禁止用执行对象ID硬编码业务逻辑
4. 禁止依赖 `IS_ACTIVE_=false` 判断执行对象无效

---

## 终极总结（牢记这5句，永远不乱）

1. **执行对象 = 流程运行指针**，根执行=流程实例，子执行处理并发
2. **节点是站点，执行是路线**，执行驱动节点流转
3. **监听器是钩子**，监听执行的start（进门）、end（出门）、take（走路）
4. **用户任务用complete，等待节点用trigger**，并发必用局部变量
5. **监听器不抛异常，不手动删执行**，流程永远稳定不卡死
