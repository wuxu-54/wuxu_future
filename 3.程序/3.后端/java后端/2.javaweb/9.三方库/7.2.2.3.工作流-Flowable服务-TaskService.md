# Flowable TaskService 全API清单（作用+注意事项+避坑）

`TaskService`是Flowable**用户任务管理核心服务**，专门负责**BPMN中`userTask`（用户任务）**的全生命周期操作，包括任务查询、认领、完成、委派、转办、批注、变量管理等，所有操作围绕Flowable**运行时任务表（`ACT_RU_TASK`）**、**身份关联表（`ACT_RU_IDENTITYLINK`）**和**历史任务表（`ACT_HI_TASKINST`/`ACT_HI_COMMENT`）**展开。

其与其他核心服务的**功能边界清晰**：仅处理需要人工参与的`userTask`，自动执行的任务（如服务任务`serviceTask`、脚本任务`scriptTask`）由Flowable引擎自动处理，无需`TaskService`干预；流程实例的整体管理由`RuntimeService`负责，静态流程资源由`RepositoryService`负责。

以下基于**Flowable 6.8.0**（稳定版，兼容JDK8+）整理，沿用前序服务的说明格式，**按功能分类**列出核心API，包含**方法名、重载说明、核心作用、注意事项/避坑**，重点标注实战高频API和易踩坑点，纯原生API无封装，同时明确与`RuntimeService`的协作关系。

> 通用前置：所有API均通过`ProcessEngine.getTaskService()`获取实例，Spring Boot中直接`@Autowired`注入即可，流程引擎为**全局唯一重量级对象**，禁止重复创建。
>
> ```java
> // 纯Java工程
> TaskService taskService = ProcessEngines.getDefaultProcessEngine().getTaskService();
> // Spring Boot工程
> @Autowired
> private TaskService taskService;
> ```
>
> 核心特性：用户任务完成后，会从`ACT_RU_TASK`（运行时）迁移至`ACT_HI_TASKINST`（历史），同时流程实例由引擎自动推进至下一个节点，无需手动调用`RuntimeService`触发流转。

## 一、用户任务查询API（实战最高频基础）

`TaskQuery`是`TaskService`最基础、最常用的API，用于多条件查询**运行中**的用户任务（`ACT_RU_TASK`），是人工处理任务的**前置必用操作**（如查询“当前用户待办任务”“某流程实例的待办任务”）。

### 核心方法

```java
TaskQuery createTaskQuery();
```

- **作用**：创建任务查询器`TaskQuery`，支持多条件筛选、分页、排序，可精准查询指定范围的用户任务，返回`Task`实体（包含任务ID、处理人、流程实例ID、节点名称等核心信息）。
- **TaskQuery 核心筛选/执行方法**（链式调用，最终用`list()`/`singleResult()`/`count()`执行）：
| 方法 | 核心作用 | 实战说明/避坑 |
|------|----------|---------------|
| `taskId(String taskId)` | 按任务ID精确查询 | 最常用，针对单个任务的精准操作前置查询 |
| `assignee(String assignee)` | 按**已认领的处理人**查询 | 查“我的已办任务/待办任务”（认领后assignee为用户ID），**实战高频** |
| `candidateUser(String userId)` | 按**候选人**查询 | 查“我可认领的任务”（任务未被认领，当前用户在候选人列表），**实战高频** |
| `candidateGroup(String groupId)` | 按**候选组**查询 | 查“我所在角色的可认领任务”（如管理员组、经理组），**实战高频** |
| `processInstanceId(String instanceId)` | 按流程实例ID查询 | 查某流程实例下的所有待办任务，用于流程监控 |
| `processDefinitionKey(String processKey)` | 按流程Key查询 | 查某类流程的所有待办任务（如所有请假流程的审批任务） |
| `taskName(String taskName)` | 按任务名称精确查询 | 对应BPMN中`userTask`的`name`属性（如“经理审批请假”） |
| `taskNameLike(String taskNameLike)` | 按任务名称模糊查询 | 如`%审批%`查所有审批类任务 |
| `orderByCreateTimeDesc()` | 按任务创建时间倒序 | 最新创建的任务在前，符合用户操作习惯，**实战默认** |
| `active()` | 仅查询**激活状态**的任务 | 排除挂起的任务，默认筛选 |
| `suspended()` | 仅查询**挂起状态**的任务 | 极少用，仅用于异常任务排查 |
| `page(int firstResult, int maxResults)` | 分页查询 | 待办任务列表必用，避免大量数据加载导致内存溢出 |
| `singleResult()` | 查询单个任务 | 无结果/多结果会抛异常，仅确定唯一任务时使用 |

## 二、任务认领/释放API（实战高频）

任务**认领（Claim）**是指将**未被认领的任务**（assignee为null，有候选人/候选组）分配给指定用户，认领后任务成为该用户的**专属待办任务**；**释放（Unclaim）**是指将已认领的任务归还为未认领状态，重新进入候选人/候选组池，供其他用户认领，适用于任务分配错误、用户无法处理的场景。

### 核心方法

```java
// 任务认领：将未认领任务分配给指定用户
void claim(String taskId, String userId);

// 任务释放：将已认领任务归还为未认领状态
void unclaim(String taskId);
```

- **作用**：完成任务的“认领-释放”生命周期，实现任务在候选人/候选组中的分配与归还。
- **注意事项/避坑**：
  1. **认领前提**：任务必须**未被认领**（assignee为null）+ 当前用户**在候选人/候选组列表中**，否则直接抛`FlowableTaskException`，**生产环境必须做前置校验**（通过`candidateUser/candidateGroup`查询）；
  2. **释放前提**：任务必须**已被当前用户认领**（assignee为当前用户ID），否则抛异常；
  3. **认领后状态**：认领后`ACT_RU_TASK`的`ASSIGNEE_`字段设为用户ID，`ACT_RU_IDENTITYLINK`中保留候选人/候选组信息（便于释放后复用）；
  4. **无候选人任务**：BPMN中直接指定`assignee`的任务（如`<userTask flowable:assignee="zhangsan"/>`），创建后已绑定处理人，**无需认领**，直接用`assignee`查询即可。

## 三、任务完成API（实战最高频核心）

任务**完成（Complete）**是用户任务的核心操作，指用户完成人工处理后，提交任务结果并推进流程实例，完成后任务从运行时表（`ACT_RU_TASK`）迁移至历史表（`ACT_HI_TASKINST`），Flowable引擎会**自动推进流程实例至下一个节点**（无需手动调用`RuntimeService`）。

### 核心重载方法

```java
// 基础完成：无任务变量，直接提交
void complete(String taskId);

// 带变量完成：提交任务时传入**任务局部变量**，**实战首选**
void complete(String taskId, Map<String, Object> variables);

// 带变量+是否保存局部变量完成：控制变量是否仅作用于当前任务
void complete(String taskId, Map<String, Object> variables, boolean localScope);
```

- **作用**：提交用户任务的处理结果，推进流程实例，传入的变量会作为流程数据参与后续节点的执行（如网关条件判断、下一个任务的处理人分配）。
- **注意事项/避坑**：
  1. **完成前提**：任务必须**已被认领**（assignee为当前用户ID）或**直接指定了处理人**，且为**激活状态**，否则抛异常；
  2. **变量作用域**：`localScope=false`（默认）时，传入的变量会**从任务局部变量升级为流程全局变量**（存入`ACT_RU_VARIABLE`），供整个流程实例使用；`localScope=true`时，变量仅为当前任务的局部变量，完成后随任务进入历史，不影响后续流程，**实战一般用默认值**；
  3. **核心变量传递**：审批结果（如`approve=true/false`）、业务数据（如`approveOpinion="同意请假"`）必须通过`variables`传入，这是后续流程节点的核心判断依据，**禁止遗漏**；
  4. **完成后状态**：任务完成后，`ACT_RU_TASK`中该任务被删除，流程实例由引擎自动推进，若下一个节点仍为`userTask`，会自动创建新的运行时任务；
  5. **事务一致性**：完成操作必须放在**Spring事务（`@Transactional`）**中，避免任务完成但流程未推进的脏数据（如因网关条件错误导致引擎执行失败，需回滚任务完成操作）。

## 四、任务委派/转办/归还API（实战常用）

**委派（Delegate）**和**转办（Assign）**均为任务的重新分配操作，适用于用户无法处理任务时将任务交给其他用户，**二者核心区别**：委派是**临时分配**，被委派用户处理后需归还，原认领用户最终确认；转办是**永久分配**，直接将任务所有权转移给其他用户，无需归还。

### 核心方法

```java
// 任务委派：将已认领的任务临时委派给指定用户（被委派用户为delegateAssignee）
void delegateTask(String taskId, String delegateAssignee);

// 任务归还：被委派用户将任务归还给原委派用户
void resolveTask(String taskId);

// 任务归还并完成：被委派用户处理后，归还并直接完成任务（推进流程）
void resolveTask(String taskId, Map<String, Object> variables);

// 任务转办：将任务（未认领/已认领）永久分配给指定用户，**实战高频**
void setAssignee(String taskId, String assignee);
```

- **作用**：实现任务的灵活分配，适配企业中“代审批”“转审批”的业务场景。
- **注意事项/避坑**：
  1. **委派前提**：任务必须**已被当前用户认领**，委派后`ACT_RU_TASK`的`DELEGATE_ASSIGNEE_`字段为被委派用户ID，原assignee仍为原用户，**被委派用户可直接处理任务，但需归还**；
  2. **转办无前提**：`setAssignee`可操作**未被认领/已被认领**的任务，转办后原assignee被覆盖为新用户ID，**永久转移任务所有权**，是生产环境“转审批”的首选API；
  3. **归还前提**：任务必须**处于委派状态**（`DELEGATE_ASSIGNEE_`不为null），且由被委派用户执行归还操作；
  4. **转办权限控制**：生产环境必须为`setAssignee`添加严格的权限控制（如仅管理员、部门领导可转办），避免随意转办导致任务混乱。

## 五、任务批注（Comment）API（实战必备）

任务批注是指为用户任务添加**文字备注/审批意见**（如“同意请假，最多3天”“驳回，理由：未附证明材料”），批注会**永久持久化到历史表（`ACT_HI_COMMENT`）**，不可修改/删除，是流程审计、业务追溯的**核心依据**，与流程变量的区别：批注仅用于**审计说明**，不参与流程执行；变量用于**流程业务逻辑判断**。

### 核心方法

```java
// 添加任务批注：关联任务ID和流程实例ID，**实战首选**
Comment addComment(String taskId, String processInstanceId, String message);

// 添加带类型的批注：type为自定义类型（如“APPROVE_OPINION”“REJECT_REASON”）
Comment addComment(String taskId, String processInstanceId, String type, String message);

// 查询某任务的所有批注
List<Comment> getTaskComments(String taskId);

// 查询某流程实例的所有批注
List<Comment> getProcessInstanceComments(String processInstanceId);

// 根据批注ID获取单个批注
Comment getComment(String commentId);
```

- **作用**：记录任务处理的人工意见，实现流程操作的可追溯，是企业流程审计的必备功能。
- **注意事项/避坑**：
  1. **批注必传**：生产环境中，**任务完成时必须添加批注**（尤其是驳回/异常处理时），禁止空批注，否则无法追溯审批原因；
  2. **关联关系**：`addComment`必须同时传入`taskId`和`processInstanceId`，确保批注与任务、流程实例双向关联，便于后续查询；
  3. **不可修改/删除**：Flowable未提供批注的修改/删除API，若需修改，需手动操作历史表（不建议），**批注添加前需做内容校验**；
  4. **类型规范**：建议用`type`字段对批注分类（如`APPROVE`-同意、`REJECT`-驳回、`REMIND`-提醒），便于后续按类型筛选查询。

## 六、任务变量管理API（实战常用）

任务变量是**作用于用户任务的局部变量**，与`RuntimeService`的**流程全局变量**形成互补，用于存储仅与当前任务相关的临时数据（如任务处理的中间状态、临时意见）。`TaskService`仅负责任务局部变量的管理，流程全局变量仍由`RuntimeService`管理。

### 核心方法（与`RuntimeService`变量API逻辑一致，作用域不同）

```java
// 【设置变量】单个/批量设置任务局部变量
void setVariable(String taskId, String varName, Object varValue);
void setVariables(String taskId, Map<String, Object> variables);

// 【获取变量】单个/批量获取任务局部变量，支持指定返回类型
<T> T getVariable(String taskId, String varName, Class<T> varType);
Map<String, Object> getVariables(String taskId);

// 【删除变量】单个/批量删除任务局部变量
void removeVariable(String taskId, String varName);
void removeVariables(String taskId, Collection<String> varNames);

// 【检查变量】判断任务局部变量是否存在
boolean hasVariable(String taskId, String varName);
```

- **作用**：管理任务级别的局部数据，避免临时数据污染流程全局变量，任务完成后可选择将局部变量升级为全局变量（通过`complete`方法）。
- **注意事项/避坑**：
  1. **作用域优先级**：任务局部变量优先级高于流程全局变量，同名变量在任务中仅读取局部值，**避免变量名冲突**；
  2. **变量类型规范**：与全局变量一致，**仅使用基础类型（String/Integer/Date）**，禁止使用自定义对象，复杂数据序列化为JSON字符串；
  3. **与完成操作的协作**：任务完成时，若需将局部变量传递到流程全局，无需额外操作，通过`complete(taskId, variables)`传入即可（引擎自动合并）；
  4. **变量生命周期**：任务删除（完成/删除）后，任务局部变量会随任务进入历史表（`ACT_HI_VARIABLE`），不再参与流程执行。

## 七、任务挂起/激活API（实战少用，异常处理）

用户任务默认为**激活状态**，支持所有操作（认领、完成、委派等）；挂起后，任务进入不可操作状态，所有操作都会抛异常，适用于**任务异常、业务暂停**时的临时管控，激活后恢复正常操作。

### 核心方法

```java
// 挂起单个任务
void suspendTask(String taskId);

// 激活单个任务
void activateTask(String taskId);

// 按流程实例ID批量挂起/激活所有任务
void suspendTasksByProcessInstanceId(String instanceId);
void activateTasksByProcessInstanceId(String instanceId);
```

- **作用**：临时管控任务的可操作状态，适配业务暂停、任务异常的场景。
- **注意事项/避坑**：
  1. **与流程实例挂起的关联**：若通过`RuntimeService`挂起流程实例，该实例下的**所有任务会被引擎自动挂起**，激活流程实例时自动恢复，**无需手动挂起任务**；
  2. **批量挂起慎用**：`suspendTasksByProcessInstanceId`会挂起某流程实例下的所有任务，生产环境仅在流程异常时使用，避免误操作；
  3. **挂起后状态**：任务挂起后，`ACT_RU_TASK`的`SUSPENSION_STATE_`字段设为2，激活后恢复为1，挂起期间的所有操作都会抛`FlowableTaskException`。

## 八、任务删除API（实战少用，异常处理）

任务删除是指将**运行中的用户任务**从`ACT_RU_TASK`中移除，适用于**流程实例异常、任务创建错误**时的清理操作，**生产环境谨慎使用**。

### 核心方法

```java
// 基础删除：删除单个任务，带删除原因
void deleteTask(String taskId, String deleteReason);

// 批量删除：删除多个任务，带删除原因
void deleteTasks(Collection<String> taskIds, String deleteReason);

// 级联删除：删除任务并级联删除关联的身份信息、变量、批注等
void deleteTask(String taskId, String deleteReason, boolean cascade);
```

- **作用**：清理运行中的异常任务，删除原因会存入历史表，便于追溯。
- **注意事项/避坑**：
  1. **删除前提**：仅能删除**运行中的任务**（未完成），已完成的任务（在历史表）无法删除，否则抛异常；
  2. **与流程实例删除的关联**：若通过`RuntimeService`删除流程实例，该实例下的**所有任务会被引擎自动级联删除**，**无需手动删除任务**；
  3. **级联删除默认开启**：Flowable中`deleteTask`默认会级联删除任务的关联数据（身份信息、变量、批注），`cascade`参数仅为兼容低版本，一般直接使用`deleteTask(taskId, reason)`；
  4. **删除原因必填**：生产环境删除任务时，必须填写清晰的删除原因（如“流程实例异常，清理错误创建的审批任务”），原因会存入`ACT_HI_TASKINST`的`DELETE_REASON_`字段；
  5. **禁止随意删除**：任务是流程实例的核心节点，删除任务会导致流程实例**卡节点**（无法继续推进），仅在流程实例需整体删除时使用，单独删除任务需配合流程实例的人工干预。

## 九、任务身份关联API（实战进阶，动态配置）

任务身份关联是指为**未被认领的任务**动态添加/删除**候选人、候选组**，适配BPMN中未静态配置候选人/候选组，需**运行时动态分配**的业务场景（如根据请假天数动态分配不同的审批人组）。

### 核心方法

```java
// 为任务添加候选人
void addCandidateUser(String taskId, String userId);

// 为任务添加候选组
void addCandidateGroup(String taskId, String groupId);

// 从任务中删除候选人
void deleteCandidateUser(String taskId, String userId);

// 从任务中删除候选组
void deleteCandidateGroup(String taskId, String groupId);

// 查询任务的所有身份关联信息（候选人/候选组/处理人）
List<IdentityLink> getIdentityLinksForTask(String taskId);
```

- **作用**：运行时动态配置任务的候选人/候选组，突破BPMN静态配置的限制，实现更灵活的任务分配。
- **注意事项/避坑**：
  1. **操作前提**：仅能对**未被认领的任务**（assignee为null）进行身份关联操作，认领后添加/删除候选人/候选组无意义；
  2. **与BPMN的配合**：若BPMN中已静态配置候选人/候选组（如`<userTask flowable:candidateUsers="zhangsan,lisi"/>`），引擎会自动创建身份关联，无需手动添加，可通过该API做动态调整；
  3. **身份链接类型**：`IdentityLink`包含`candidate`（候选人）、`candidateGroup`（候选组）、`assignee`（处理人）等类型，可通过`getIdentityLinksForTask`查询任务的所有关联身份；
  4. **批量操作**：若需添加多个候选人/候选组，多次调用`addCandidateUser/addCandidateGroup`即可，Flowable无批量添加API，需自行封装。

## 十、通用工具API（实战辅助）

此类API为任务管理的辅助操作，适用于任务信息查询、异常排查，使用频率较低，但部分API为实战必备的辅助功能。

```java
// 根据任务ID获取任务完整实体
Task getTask(String taskId);

// 判断任务是否为挂起状态
boolean isTaskSuspended(String taskId);

// 获取任务的创建时间
Date getTaskCreateTime(String taskId);

// 为任务设置名称（动态修改任务名称）
void setTaskName(String taskId, String taskName);

// 为任务设置描述（动态添加任务描述）
void setTaskDescription(String taskId, String description);
```

- **实用重点**：`getTask(taskId)`可获取任务的完整信息（创建时间、流程实例ID、处理人、挂起状态等），是任务操作前的**精准校验**前置方法；`setTaskName/setTaskDescription`可实现任务名称/描述的动态修改，适配业务场景的动态调整需求。

## 十一、TaskService 通用避坑原则（所有API通用）

结合企业实战经验，整理`TaskService`所有操作的核心避坑点，**必须严格遵守**，否则会导致任务管理混乱、流程卡节点、审计数据缺失等严重问题：

### 1. 操作前置：必做任务状态与权限校验

所有任务操作（认领、完成、委派、转办）前，**必须执行3层前置校验**（通过`TaskQuery`/`getTask`实现）：

   1. 任务是否**存在**（运行中，`ACT_RU_TASK`中有记录）；
   2. 任务是否**为激活状态**（`!isTaskSuspended(taskId)`）；
   3. 当前用户是否**有操作权限**（认领/完成：assignee为当前用户；候选：当前用户在候选人/候选组；转办：有管理员权限）。
✅ 目的：避免操作不存在/挂起/无权限的任务，抛无意义的异常，提升系统健壮性。

### 2. 任务完成：强制添加批注+传递核心变量

- **批注必传**：无论同意/驳回/转办，任务完成时**必须添加批注**，且批注内容需清晰描述处理原因，禁止空批注（审计追溯必备）；
- **变量必传**：审批结果、业务参数等核心数据**必须通过`variables`传入**，确保流程引擎能根据变量推进至下一个节点，避免流程卡节点。

### 3. 变量管理：禁用自定义对象，统一基础类型

任务变量（局部）与流程全局变量遵循**同一规范**：**仅使用基础类型（String/Integer/Long/Date/Boolean）**，禁止使用自定义Java对象。
✅ 复杂数据解决方案：将对象序列化为**JSON字符串（String类型）**，读取后再反序列化为对象，避免序列化/反序列化失败的风险。

### 4. 任务分配：区分认领/委派/转办，按需使用

- 未认领任务→**认领（claim）**：专属个人处理；
- 已认领任务，临时交他人处理→**委派（delegateTask）**：需归还，原用户最终确认；
- 已认领/未认领任务，永久交他人处理→**转办（setAssignee）**：生产环境“代审批”首选，无需归还；
❌ 禁止用`setAssignee`做临时委派，避免任务所有权混乱。

### 5. 权限控制：为核心操作添加细粒度权限

生产环境必须为`TaskService`的核心操作添加**细粒度权限控制**，避免越权操作：

- 认领/释放：仅候选人/候选组用户可操作；
- 完成：仅任务的assignee可操作；
- 转办/批量挂起/删除：仅管理员/部门领导可操作；
- 动态添加候选人：仅流程发起人/管理员可操作。

### 6. 避免重复操作：防止任务被多次完成/认领

生产环境需通过**分布式锁/数据库唯一约束**防止任务的重复操作（高并发场景下）：

- 重复认领：同一任务被多个用户同时认领；
- 重复完成：同一任务被多次提交完成，导致流程重复推进。
✅ 解决方案：以`taskId`为锁标识，操作前加分布式锁（如Redis锁），操作完成后释放锁。

### 7. 与流程实例的协作：优先操作流程实例，而非单个任务

若需对**某流程实例的所有任务**进行管控（如挂起、删除），**优先使用`RuntimeService`操作流程实例**，而非`TaskService`逐个操作任务：

- 挂起流程实例→引擎自动挂起所有任务；
- 删除流程实例→引擎自动删除所有任务；
✅ 目的：避免手动操作遗漏任务，导致流程实例与任务状态不一致。

### 8. 历史数据：禁止修改/删除，保证审计完整性

`TaskService`的批注、历史任务、历史变量等**审计数据**，Flowable均未提供修改/删除API，生产环境**禁止手动操作历史表**（如`ACT_HI_COMMENT`/`ACT_HI_TASKINST`），确保流程操作的可追溯性，符合企业审计规范。

## 十二、TaskService 核心API速查（实战90%场景覆盖）

整理日常开发中**最常用的核心API**，按**用户处理任务的实际流程排序**，便于快速查阅和使用，覆盖90%的企业实战场景：

1. **查询待办任务**：`createTaskQuery().assignee(userId).orderByCreateTimeDesc().list()`；
2. **查询可认领任务**：`createTaskQuery().candidateUser(userId).orderByCreateTimeDesc().list()`；
3. **任务认领**：`claim(taskId, userId)`；
4. **添加审批批注**：`addComment(taskId, instanceId, message)`；
5. **设置任务变量**：`setVariable(taskId, varName, varValue)`；
6. **完成任务（核心）**：`complete(taskId, variables)`；
7. **任务转办**：`setAssignee(taskId, newUserId)`；
8. **任务释放**：`unclaim(taskId)`；
9. **查询流程实例所有批注**：`getProcessInstanceComments(instanceId)`；
10. **任务状态校验**：`getTask(taskId)` / `isTaskSuspended(taskId)`；
11. **动态添加候选人**：`addCandidateUser(taskId, userId)`。
