# Flowable 核心概念：流程变量（Process Variable）全解析 + 实战操作 + 避坑指南

流程变量是Flowable工作流的**核心数据中枢**，是贯穿流程定义、流程实例、流程任务、网关全生命周期的**动态数据载体**——所有动态逻辑（网关条件判断、任务动态分配、流程流转控制）都基于流程变量实现，人工操作的结果（审批通过/驳回）也通过流程变量回传给引擎，驱动流程继续推进。

如果说之前的流程实例是“业务流程的运行实例”、任务是“人工交互节点”、网关是“交通指挥中心”，那**流程变量就是指挥中心的“决策数据”、任务节点的“分配依据”**——比如请假流程中`leaveDays`（请假天数）决定网关走经理/总监审批、`managerId`（经理ID）决定任务分配给哪个用户、`approve`（审批结果）决定流程是通过还是驳回，这些都是流程变量的核心作用。

本文延续之前的风格，基于**Spring Boot 2.7+Flowable 6.8.0+员工请假流程**案例，从**核心概念→分类与区别→全生命周期操作→高级用法→生产避坑→综合实战**逐步讲解，所有代码可直接复用，覆盖生产环境所有高频场景，帮你彻底掌握流程变量的使用。

## 一、什么是流程变量？（通俗解释+核心特性）

### 1. 本质定义

流程变量是Flowable引擎为**每个流程实例**维护的**键值对（Key-Value）型动态数据**，存储了流程运行过程中所需的**业务数据、操作结果、配置参数**，是引擎执行**动态逻辑判断**和**人工操作结果传递**的唯一依据。

流程变量的核心价值：**让流程摆脱硬编码，实现全动态的业务适配**——无需修改BPMN文件，仅通过改变流程变量，就能实现不同的任务分配、网关分支、流程流转，完美适配企业复杂的业务场景（如不同部门、不同职级的流程差异化）。

### 2. 核心特性

Flowable的流程变量设计遵循**轻量、持久化、作用域隔离**原则，核心特性如下，也是生产环境使用的基础原则：

1. **实例级隔离**：**每个流程实例拥有独立的流程变量空间**，不同实例的变量互不干扰（如张三的请假实例`leaveDays=3`，李四的实例`leaveDays=5`，彼此无影响）；
2. **基础类型优先**：引擎对**Java基础类型/包装类+String+Date**提供原生完美支持，复杂对象需序列化，不推荐直接使用；
3. **全程持久化**：流程变量存储在数据库专用表中，流程暂停、重启、服务器宕机后，变量数据不会丢失，全程可追溯；
4. **多Service可操作**：可通过`RuntimeService`（全局操作）、`TaskService`（任务关联操作）、`HistoryService`（历史变量查询）操作，满足不同场景需求；
5. **生命周期与实例绑定**：流程变量的生命周期**与所属流程实例完全一致**——实例启动时创建、运行中修改、实例结束后变为历史变量，永久存储。

### 3. 核心存储表（运行时+历史，必知）

流程变量分为**运行时变量**（流程实例未结束，可修改）和**历史变量**（流程实例结束，只读），分别存储在专用表中，引擎自动维护二者的同步，无需手动干预：

#### 运行时变量表（实例未结束，可CRUD）

1. **ACT_RU_VARIABLE**：运行时流程变量核心表，存储所有未结束流程实例的**全局流程变量**和**任务局部变量**，Key为变量名，Value为序列化后的变量值；
2. **ACT_RU_TASK**：任务表中间接关联局部变量（通过`TASK_ID_`关联ACT_RU_VARIABLE），标记变量的作用域。

#### 历史变量表（实例结束，只读）

1. **ACT_HI_VARINST**：历史流程变量核心表，存储所有已结束流程实例的变量快照，**永久存储**，用于流程审计和追溯，无修改/删除API；
2. **ACT_HI_TASKINST**：历史任务表关联历史局部变量，记录任务执行时的变量状态。

**核心流转逻辑**：创建变量→存入ACT_RU_VARIABLE→流程运行中修改（更新该表）→流程实例结束→引擎自动将变量快照迁入ACT_HI_VARINST→ACT_RU_VARIABLE中对应记录删除。

## 二、流程变量核心分类（全局VS局部，必分清楚）

Flowable中将流程变量分为**全局流程变量（Process Variable）**和**任务局部变量（Task Variable）**，二者是**作用域的区别**（全局作用于整个实例，局部仅作用于单个任务），这是新手最容易混淆的点，**必须严格区分**，否则会导致变量污染、逻辑判断错误。

### 1. 核心对比表（一眼看懂区别）

| 对比维度         | 全局流程变量                | 任务局部变量                |
|------------------|-----------------------------|-----------------------------|
| **核心作用域**   | 整个流程实例全生命周期       | 仅所属单个任务的生命周期     |
| **管理Service**  | 主：RuntimeService；辅：TaskService | 仅TaskService               |
| **存储关联字段** | ACT_RU_VARIABLE中`TASK_ID_=null` | ACT_RU_VARIABLE中`TASK_ID_=任务ID` |
| **生命周期**     | 与流程实例绑定（实例结束则销毁） | 与任务绑定（任务完成则销毁，可手动升级为全局） |
| **使用场景**     | 全流程共享的核心数据（如申请人ID、请假天数、审批结果） | 单个任务的临时数据（如任务处理临时意见、中间状态） |
| **核心特点**     | 全流程可访问、可修改，驱动全局逻辑 | 仅当前任务可访问，避免污染全局变量 |
| **典型变量**     | applicantId、leaveDays、managerId、approve | tempComment（临时意见）、handleStep（处理步骤） |

### 2. 核心使用原则（生产必守）

**全局变量：少而精，仅存全流程共享的核心数据**——避免冗余，防止变量名冲突；
**局部变量：专而活，仅存单个任务的临时数据**——用完即销毁，不污染全局变量空间；
**局部升级全局**：仅当任务的临时数据需要被后续节点使用时，才将局部变量升级为全局变量（如任务处理意见需要后续节点查看）。

## 三、流程变量全生命周期实战操作（CRUD全覆盖）

流程变量的操作围绕**创建、查询、修改、删除（CRUD）**展开，全局变量主要通过`RuntimeService`操作，局部变量仅通过`TaskService`操作，以下所有代码基于之前的测试类（已注入`RuntimeService`/`TaskService`），直接复制即可测试，结合请假流程场景，贴合生产实际。

### 前置准备

1. 环境：沿用Spring Boot 2.7+Flowable 6.8.0，已部署基础请假流程（`leaveProcessExclusive`，排他网关版）；
2. 核心测试流程：启动实例（传变量）→查询变量→修改变量→完成任务（传/更新变量）→删除变量→流程结束；
3. 基础变量：`applicantId=zhangsan`（申请人）、`leaveDays=3`（请假天数）、`managerId=lisi`（经理）。

### 操作1：全局流程变量CRUD（RuntimeService，核心）

全局变量是生产中**使用最多**的类型，所有全流程共享数据都通过此方式操作，核心API为`RuntimeService`的`setVariable/setVariables`（创建/修改）、`getVariable/getVariables`（查询）、`removeVariable/removeVariables`（删除）。

```java
import org.flowable.engine.RuntimeService;
import org.flowable.engine.TaskService;
import org.flowable.engine.runtime.ProcessInstance;
import org.flowable.engine.task.Task;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.transaction.annotation.Transactional;

import java.util.HashMap;
import java.util.Map;

@SpringBootTest
public class ProcessVariableTest {
    @Autowired
    private RuntimeService runtimeService;
    @Autowired
    private TaskService taskService;

    /**
     * 全局流程变量CRUD实战：创建→查询→修改→删除
     */
    @Test
    @Transactional
    public void testGlobalVariableCRUD() {
        String processKey = "leaveProcessExclusive";
        // ---------------------- 1. 创建全局变量：启动流程实例时传入（最常用方式） ----------------------
        Map<String, Object> initVars = new HashMap<>();
        initVars.put("applicantId", "zhangsan");
        initVars.put("leaveDays", 3);
        initVars.put("managerId", "lisi");
        // 启动实例时传入变量，引擎自动创建全局变量
        ProcessInstance pi = runtimeService.startProcessInstanceByKey(processKey, initVars);
        String instanceId = pi.getId();
        System.out.println("流程实例启动成功，ID：" + instanceId);
        System.out.println("=== 启动实例时创建的全局变量 ===");

        // ---------------------- 2. 查询全局变量：单个查询/批量查询 ----------------------
        // 单个查询：指定实例ID+变量名，指定返回类型（避免类型转换）
        Integer leaveDays = runtimeService.getVariable(instanceId, "leaveDays", Integer.class);
        String applicantId = runtimeService.getVariable(instanceId, "applicantId", String.class);
        System.out.println("单个查询 - leaveDays：" + leaveDays + "，applicantId：" + applicantId);

        // 批量查询：查询该实例的所有全局变量
        Map<String, Object> allGlobalVars = runtimeService.getVariables(instanceId);
        allGlobalVars.forEach((k, v) -> System.out.println("批量查询 - " + k + "：" + v));

        // ---------------------- 3. 修改全局变量：单个修改/批量修改 ----------------------
        System.out.println("=== 修改全局变量后 ===");
        // 单个修改：实例ID+变量名+新值
        runtimeService.setVariable(instanceId, "leaveDays", 4); // 请假天数从3改为4
        // 批量修改：传入键值对Map
        Map<String, Object> updateVars = new HashMap<>();
        updateVars.put("managerId", "wangwu"); // 经理从lisi改为wangwu
        updateVars.put("leaveType", "ANNUAL"); // 新增全局变量：请假类型为年假
        runtimeService.setVariables(instanceId, updateVars);
        // 验证修改结果
        System.out.println("修改后 leaveDays：" + runtimeService.getVariable(instanceId, "leaveDays"));
        System.out.println("修改后 managerId：" + runtimeService.getVariable(instanceId, "managerId"));
        System.out.println("新增变量 leaveType：" + runtimeService.getVariable(instanceId, "leaveType"));

        // ---------------------- 4. 删除全局变量：单个删除/批量删除 ----------------------
        System.out.println("=== 删除全局变量后 ===");
        // 单个删除：实例ID+变量名
        runtimeService.removeVariable(instanceId, "leaveType");
        // 批量删除：传入变量名数组
        runtimeService.removeVariables(instanceId, new String[]{"applicantId"});
        // 验证删除结果（批量查询剩余变量）
        runtimeService.getVariables(instanceId).forEach((k, v) -> System.out.println("剩余变量 - " + k + "：" + v));
    }
}
```

#### 全局变量创建的3种常用方式

1. **启动实例时传入**（如上，最常用）：通过`startProcessInstanceByKey`的`variables`参数传入，引擎自动为流程实例创建全局变量，适用于**流程初始化的基础数据**；
2. **运行中手动设置**：通过`runtimeService.setVariable/setVariables`，适用于**流程运行中动态新增/修改变量**（如审批时新增审批结果）；
3. **完成任务时传入**：通过`taskService.complete`的`variables`参数传入，**默认会创建/更新全局变量**，适用于**人工操作后将结果回传为全局变量**（如审批结果`approve=true`）。

### 操作2：任务局部变量CRUD（TaskService，仅作用于单个任务）

任务局部变量仅作用于**指定任务**，其他任务/节点无法访问，核心API为`TaskService`的`setVariable/setVariables`（创建/修改）、`getVariable/getVariables`（查询）、`removeVariable/removeVariables`（删除），**操作前必须先获取任务ID**。

```java
/**
 * 任务局部变量CRUD实战：创建→查询→修改→删除→升级为全局变量
 */
@Test
@Transactional
public void testTaskVariableCRUD() {
    String processKey = "leaveProcessExclusive";
    Map<String, Object> initVars = new HashMap<>();
    initVars.put("applicantId", "zhangsan");
    initVars.put("leaveDays", 3);
    initVars.put("managerId", "lisi");
    ProcessInstance pi = runtimeService.startProcessInstanceByKey(processKey, initVars);
    String instanceId = pi.getId();
    // 第一步：获取任务ID（申请人提交请假任务）
    Task applyTask = taskService.createTaskQuery().processInstanceId(instanceId).singleResult();
    String taskId = applyTask.getId();
    System.out.println("获取任务ID：" + taskId + "，任务名称：" + applyTask.getName());

    // ---------------------- 1. 创建局部变量：为指定任务设置 ----------------------
    System.out.println("=== 创建任务局部变量 ===");
    // 单个创建：任务ID+变量名+值
    taskService.setVariable(taskId, "tempComment", "材料齐全，申请年假");
    // 批量创建：传入Map
    Map<String, Object> taskVars = new HashMap<>();
    taskVars.put("handleUser", "zhangsan");
    taskVars.put("handleStep", "提交申请");
    taskService.setVariables(taskId, taskVars);

    // ---------------------- 2. 查询局部变量：单个/批量 ----------------------
    // 单个查询：指定任务ID+变量名
    String tempComment = taskService.getVariable(taskId, "tempComment", String.class);
    System.out.println("单个查询局部变量 - tempComment：" + tempComment);
    // 批量查询：该任务的所有局部变量
    Map<String, Object> allTaskVars = taskService.getVariables(taskId);
    allTaskVars.forEach((k, v) -> System.out.println("批量查询局部变量 - " + k + "：" + v));

    // 关键验证：全局变量中无法查询到局部变量（作用域隔离）
    System.out.println("全局变量中是否存在tempComment：" + runtimeService.getVariables(instanceId).containsKey("tempComment")); // false

    // ---------------------- 3. 修改局部变量 ----------------------
    System.out.println("=== 修改任务局部变量 ===");
    taskService.setVariable(taskId, "tempComment", "材料齐全，申请3天年假，无外出");
    System.out.println("修改后tempComment：" + taskService.getVariable(taskId, "tempComment"));

    // ---------------------- 4. 局部变量升级为全局变量（生产常用） ----------------------
    System.out.println("=== 局部变量升级为全局变量 ===");
    // 方式：查询局部变量，通过RuntimeService设置为全局变量
    String comment = taskService.getVariable(taskId, "tempComment", String.class);
    runtimeService.setVariable(instanceId, "applyComment", comment);
    // 验证：全局变量中可查询到，局部变量仍保留
    System.out.println("全局变量新增applyComment：" + runtimeService.getVariable(instanceId, "applyComment"));
    System.out.println("局部变量tempComment仍存在：" + taskService.getVariable(taskId, "tempComment"));

    // ---------------------- 5. 删除局部变量 ----------------------
    System.out.println("=== 删除任务局部变量 ===");
    taskService.removeVariable(taskId, "handleStep");
    taskService.getVariables(taskId).forEach((k, v) -> System.out.println("删除后剩余局部变量 - " + k + "：" + v));

    // ---------------------- 6. 完成任务：局部变量默认销毁（未升级的话） ----------------------
    taskService.complete(taskId);
    // 验证：任务完成后，局部变量无法查询（引擎自动销毁）
    System.out.println("任务完成后，局部变量是否存在：" + taskService.getVariables(taskId).isEmpty()); // true
}
```

#### 局部变量的核心注意点

1. **作用域严格隔离**：仅所属任务可访问，全局变量和其他任务的局部变量均无法查询，避免数据污染；
2. **任务完成后自动销毁**：未升级为全局变量的局部变量，在任务`complete`后会被引擎自动删除，无需手动清理；
3. **升级全局变量需手动操作**：若需要后续节点使用局部变量，必须通过`RuntimeService`手动设置为全局变量（如上的`applyComment`）；
4. **无法通过RuntimeService操作**：局部变量的所有操作必须通过`TaskService`，且指定**任务ID**（而非实例ID）。

### 操作3：完成任务时传递变量（生产最高频，全局+局部结合）

人工完成任务时（如审批、提交），需要将**处理结果**（如审批通过/驳回、处理意见）回传给引擎，这是生产中**流程变量使用的最高频场景**——通过`taskService.complete`的`variables`参数传递，**默认更新/创建全局变量**，局部变量需单独设置。

该操作直接联动**任务处理**和**流程驱动**，是“人工操作→引擎决策”的核心桥梁，结合请假流程的**经理审批**场景实战：

```java
/**
 * 生产最高频场景：完成任务时传递变量（审批结果回传，驱动网关/流程流转）
 */
@Test
@Transactional
public void testCompleteTaskWithVariable() {
    String processKey = "leaveProcessExclusive";
    // 1. 启动实例，完成申请人提交任务
    Map<String, Object> initVars = new HashMap<>();
    initVars.put("applicantId", "zhangsan");
    initVars.put("leaveDays", 5); // 5天，网关默认走总监审批
    initVars.put("managerId", "lisi");
    initVars.put("directorId", "wangwu");
    ProcessInstance pi = runtimeService.startProcessInstanceByKey(processKey, initVars);
    String instanceId = pi.getId();
    // 完成提交任务
    Task applyTask = taskService.createTaskQuery().processInstanceId(instanceId).taskName("申请人提交请假").singleResult();
    taskService.complete(applyTask.getId());
    System.out.println("已完成申请人提交任务，流程进入审批阶段");

    // 2. 获取审批任务（总监审批，因leaveDays=5）
    Task approveTask = taskService.createTaskQuery().processInstanceId(instanceId).singleResult();
    System.out.println("当前审批任务：" + approveTask.getName() + "，处理人：" + approveTask.getAssignee());

    // ---------------------- 核心：完成审批任务时传递处理结果（全局变量） ----------------------
    Map<String, Object> approveResult = new HashMap<>();
    approveResult.put("approve", true); // 审批结果：通过
    approveResult.put("approveComment", "同意5天年假，注意工作交接"); // 审批意见
    approveResult.put("approveTime", System.currentTimeMillis()); // 审批时间
    // 完成任务时传入变量，引擎自动更新/创建全局变量，驱动流程继续推进
    taskService.complete(approveTask.getId(), approveResult);

    // 验证：全局变量中已包含审批结果
    System.out.println("=== 审批结果已回传为全局变量 ===");
    runtimeService.getVariables(instanceId).forEach((k, v) -> {
        if (k.startsWith("approve")) {
            System.out.println(k + "：" + v);
        }
    });
    // 验证流程：审批通过后流程结束
    boolean processEnd = runtimeService.createProcessInstanceQuery().processInstanceId(instanceId).singleResult() == null;
    System.out.println("审批通过后，流程是否结束：" + processEnd);
}
```

#### 该场景的核心原则

1. **必传核心结果变量**：如`approve=true/false`，是后续网关判断、流程流转的核心依据；
2. **必传审计变量**：如`approveComment`（审批意见）、`approveTime`（审批时间），是流程审计的关键数据，禁止空值；
3. **变量名规范**：建议按“业务类型+属性”命名（如`approveXXX`、`applyXXX`），避免变量名冲突。

## 四、流程变量高级用法（生产必备）

掌握基础CRUD后，针对生产中的**复杂对象存储、多实例任务变量、变量序列化**等场景，讲解对应的高级用法，同时明确**使用边界**（避免滥用导致问题）。

### 用法1：复杂对象的存储（谨慎使用，优先拆分为基础类型）

Flowable支持存储**自定义Java对象**作为流程变量，但**不推荐直接使用**（会导致序列化/反序列化问题、数据库存储冗余、网关表达式解析失败），生产中**优先将复杂对象拆分为多个基础类型变量**（如`applyInfo`拆分为`applicantId`、`leaveDays`、`leaveType`）。

若确需存储复杂对象，需满足**两个条件**：

1. 自定义类实现**java.io.Serializable**序列化接口（引擎默认使用Java序列化）；
2. 类的全限定名不变（否则反序列化失败，无法查询变量）。

#### 实战：存储自定义对象为全局变量

```java
// 1. 自定义业务类：必须实现Serializable
```

#### 自定义对象的避坑点

1. **仅用于存储，不用于判断**：网关条件表达式**禁止直接使用自定义对象的属性**（如`${leaveApplyInfo.leaveDays > 3}`），易导致解析失败，建议拆分为基础类型变量做判断；
2. **避免修改类结构**：类实现序列化后，若后续修改字段（如新增/删除），会导致历史变量反序列化失败（无法查询）；
3. **优先使用JSON字符串**：替代Java序列化，将复杂对象转为JSON字符串（String类型）存储，避免序列化问题，示例：

   ```java
   // 用FastJSON将对象转为JSON字符串
   String applyInfoJson = com.alibaba.fastjson2.JSON.toJSONString(applyInfo);
   vars.put("leaveApplyInfoJson", applyInfoJson);
   // 查询后转回对象
   String json = runtimeService.getVariable(instanceId, "leaveApplyInfoJson", String.class);
   LeaveApplyInfo info = com.alibaba.fastjson2.JSON.parseObject(json, LeaveApplyInfo.class);
   ```

### 用法2：多实例任务的变量传递（如并行网关任务）

并行网关的多个分支任务（如人事备案、部门备案）需要**共享全局变量**、**独立维护局部变量**，核心原则：

1. 多实例任务的**公共数据**（如申请人ID、请假天数）存在**全局变量**中，所有分支均可访问；
2. 每个任务的**独立处理结果**（如备案意见、备案人）存在**自身局部变量**中，避免相互覆盖；
3. 若需要汇总多实例任务的结果，将每个任务的局部变量**升级为全局变量**（命名区分，如`hrComment`、`deptComment`）。

### 用法3：历史流程变量查询（流程结束后，审计追溯）

流程实例结束后，运行时变量会被引擎自动迁移到**历史变量表ACT_HI_VARINST**，变为**只读的历史变量**，通过`HistoryService`查询，用于流程审计、数据追溯，核心API为`historyService.createHistoricVariableInstanceQuery()`。

```java
@Autowired
private HistoryService historyService;

/**
 * 历史流程变量查询：流程结束后，审计追溯核心
 */
@Test
public void testHistoricVariable() {
    String processKey = "leaveProcessExclusive";
    // 1. 启动并完成流程，让实例进入历史
    Map<String, Object> vars = new HashMap<>();

    vars.put("leaveDays", 3);
    vars.put("managerId", "lisi");
    ProcessInstance pi = runtimeService.startProcessInstanceByKey(processKey, vars);
    // 完成所有任务，流程结束
    Task applyTask = taskService.createTaskQuery().processInstanceId(pi.getId()).singleResult();
    taskService.complete(applyTask.getId());
    Task approveTask = taskService.createTaskQuery().processInstanceId(pi.getId()).singleResult();
    taskService.complete(approveTask.getId(), Map.of("approve", true));

    // 2. 查询历史变量：按实例ID/流程Key/变量名筛选
    System.out.println("=== 查询历史流程变量 ===");
    historyService.createHistoricVariableInstanceQuery()
            .processInstanceId(pi.getId()) // 按实例ID筛选（最常用）
            // .processDefinitionKey(processKey) // 按流程Key筛选
            // .variableName("approve") // 按变量名筛选
            .list()
            .forEach(var -> {
                System.out.println("变量名：" + var.getVariableName() +
                        "，值：" + var.getValue() +
                        "，类型：" + var.getVariableTypeName());
            });
}
```

## 五、流程变量生产核心避坑指南（高频坑点，必守）

流程变量是Flowable开发中**问题最多**的模块，新手容易因使用不当导致**流程卡节点、变量污染、序列化失败、审计追溯无依据**等问题，以下整理了**8个生产高频坑点**，附解决方案，严格遵守可避免90%的变量相关问题。

### 1. 网关/任务分配表达式使用自定义对象属性，导致解析失败

- **坑点**：在BPMN的网关条件（`${applyInfo.leaveDays > 3}`）、任务分配（`${applyInfo.managerId}`）中直接使用自定义对象的属性，引擎无法解析表达式，导致流程卡节点/任务分配失败；
- **解决方案**：**所有表达式仅基于基础类型变量**（String/Integer/Boolean/Date），复杂对象拆分为多个基础类型变量，禁止在表达式中使用自定义对象。

### 2. 局部变量与全局变量重名，导致数据覆盖/逻辑错误

- **坑点**：任务局部变量的变量名与全局变量一致（如全局有`comment`，局部也建`comment`），虽作用域隔离，但人工操作时易混淆，若误将局部变量升级为全局变量，会直接覆盖全局变量；
- **解决方案**：**变量名做作用域标识**，全局变量用业务名（`applyComment`），局部变量加`task_`前缀（`task_tempComment`），从命名上避免重名。

### 3. 全局变量冗余，存储大量临时/无用数据

- **坑点**：将所有数据都存入全局变量（包括单个任务的临时数据、中间状态），导致全局变量空间臃肿，变量名冲突概率增加，历史变量存储冗余；
- **解决方案**：严格遵循**全局变量少而精，局部变量专而活**的原则，仅将全流程共享的核心数据存入全局变量，临时数据一律用局部变量。

### 4. 存储自定义对象未实现Serializable，导致序列化失败

- **坑点**：直接将未实现`Serializable`的自定义对象存入流程变量，引擎抛出`NotSerializableException`，流程启动/任务完成失败；
- **解决方案**：若确需存储自定义对象，**必须实现Serializable接口**，且提供**无参构造方法**（反序列化必需）；**优先方案**：将对象转为JSON字符串（String类型）存储，避免Java序列化问题。

### 5. 修改变量类型，导致表达式判断/类型转换失败

- **坑点**：初始化时变量为Integer类型（`leaveDays=3`），运行中误改为String类型（`leaveDays="3"`），网关条件`${leaveDays > 3}`会因类型不匹配抛出异常，流程卡节点；
- **解决方案**：**变量类型一经定义，全程不变**，启动实例时明确变量类型，修改时保持类型一致，查询时使用**带类型的getVariable**（`getVariable(instanceId, "key", Class.class)`）做类型校验。

### 6. 并行任务的局部变量未做命名区分，导致升级时覆盖

- **坑点**：并行网关的人事备案、部门备案任务，局部变量都用`comment`，升级为全局变量时均存入`comment`，导致后升级的变量覆盖先升级的；
- **解决方案**：**并行任务的局部变量升级为全局变量时，加业务前缀**，如人事备案的`comment`升级为`hrComment`，部门备案的升级为`deptComment`。

### 7. 完成任务时未传递核心结果变量，导致流程卡节点

- **坑点**：审批任务完成时，未传递`approve`（审批结果）等核心变量，后续网关因无判断数据，无法匹配分支，流程卡在网关处；
- **解决方案**：**所有决策类任务完成时，必传核心结果变量**，前端做非空校验，后端做拦截，确保变量传递完整。

### 8. 直接操作变量数据库表，导致引擎状态混乱

- **坑点**：为了便捷，直接通过SQL修改ACT_RU_VARIABLE/ACT_HI_VARINST的字段（如修改变量值、删除变量），跳过引擎的原生校验，导致引擎内部变量状态与数据库不一致，流程运行时抛出异常；
- **解决方案**：**禁止直接操作变量相关的数据库表**，所有变量操作（CRUD）必须通过Flowable的原生API（RuntimeService/TaskService/HistoryService）实现，引擎会自动维护表的关联关系和状态。

## 六、流程变量综合实战（串联全流程，贴合生产）

结合之前的**排他网关+经理/总监审批**请假流程，串联流程变量的**全生命周期使用**，实现一个完整的生产级流程，核心逻辑：

1. 申请人启动流程，传入**基础全局变量**（申请人ID、请假天数、请假类型）；
2. 排他网关根据`leaveDays`判断分支（≤3天经理审批，>3天总监审批）；
3. 审批人完成任务，传入**审批结果变量**（是否通过、审批意见）；
4. 审批通过：流程结束，审批结果存入历史变量；
5. 审批驳回：流程驳回至申请人，驳回原因通过局部变量升级为全局变量。

### 核心BPMN配置（已含网关条件、任务动态分配）

复用之前的排他网关BPMN文件（`leaveProcessExclusive.bpmn20.xml`），核心配置片段：


```java
/**
 * 流程变量综合实战：串联请假流程全生命周期，实现动态任务分配、网关判断、审批结果回传
 */
@Test
@Transactional
public void testVariableComprehensive() {
    String processKey = "leaveProcessExclusive";
    // 1. 申请人启动流程：传入基础全局变量
    Map<String, Object> initVars = new HashMap<>();
    initVars.put("applicantId", "zhangsan"); // 申请人
    initVars.put("leaveDays", 5); // 5天，走总监审批
    initVars.put("leaveType", "ANNUAL"); // 年假
    initVars.put("managerId", "lisi"); // 经理
    initVars.put("directorId", "wangwu"); // 总监
    ProcessInstance pi = runtimeService.startProcessInstanceByKey(processKey, initVars);
    String instanceId = pi.getId();
    System.out.println("流程实例启动成功，ID：" + instanceId);

    // 2. 申请人完成提交任务：设置局部临时变量，升级为全局变量
    Task applyTask = taskService.createTaskQuery().processInstanceId(instanceId).taskName("申请人提交请假").singleResult();
    // 设置局部变量：临时申请说明
    taskService.setVariable(applyTask.getId(), "task_tempApplyDesc", "因家庭原因申请5天年假，已安排工作交接");
    // 局部变量升级为全局变量：申请说明（供审批人查看）
    String applyDesc = taskService.getVariable(applyTask.getId(), "task_tempApplyDesc", String.class);
    runtimeService.setVariable(instanceId, "applyDesc", applyDesc);
    // 完成提交任务
    taskService.complete(applyTask.getId());
    System.out.println("已完成申请人提交任务，流程进入审批阶段");

    // 3. 验证网关分支：5天年假→总监审批
    Task approveTask = taskService.createTaskQuery().processInstanceId(instanceId).singleResult();
    System.out.println("网关流转后审批任务：" + approveTask.getName() + "，处理人：" + approveTask.getAssignee()); // 部门总监审批，wangwu

    // 4. 总监完成审批任务：传入审批结果变量（驱动流程结束）
    Map<String, Object> approveVars = new HashMap<>();
    approveVars.put("approve", true); // 审批通过
    approveVars.put("approveComment", "同意5天年假，注意工作交接，返程后及时到岗"); // 审批意见
    approveVars.put("approveBy", "wangwu"); // 审批人
    approveVars.put("approveTime", System.currentTimeMillis()); // 审批时间
    taskService.complete(approveTask.getId(), approveVars);
    System.out.println("已完成总监审批任务，审批结果已回传");

    // 5. 流程结束：查询历史变量（审计追溯）
    System.out.println("=== 流程结束，查询历史变量（审计追溯） ===");
    historyService.createHistoricVariableInstanceQuery()
            .processInstanceId(instanceId)
            .list()
            .stream()
            .filter(var -> !var.getVariableName().startsWith("task_")) // 过滤局部变量
            .forEach(var -> System.out.println(var.getVariableName() + "：" + var.getValue()));

    // 6. 若审批驳回（修改approve=false，可驱动流程至驳回任务，此处略）
    // 核心：驳回时传入rejectReason变量，驳回任务中展示给申请人
}
```

## 七、流程变量核心总结

1. **流程变量是Flowable的“数据中枢”**：所有动态逻辑（网关判断、任务分配、流程流转）都基于流程变量实现，是引擎和人工操作的唯一数据桥梁；
2. **严格区分全局/局部变量**：全局变量作用于整个流程实例，存储核心共享数据；局部变量仅作用于单个任务，存储临时数据，**命名做标识，避免重名**；
3. **基础类型是第一选择**：引擎对String/Integer/Boolean/Date原生支持，**禁止在网关/任务表达式中使用自定义对象**，复杂对象优先拆分为基础类型或转为JSON字符串存储；
4. **三个高频变量传递场景**：启动实例时传入（初始化）、运行中手动设置（动态修改）、完成任务时传入（结果回传），其中**完成任务传结果**是生产最高频场景；
5. **必守使用原则**：变量名规范、类型全程一致、全局变量少而精、局部变量专而活、核心结果变量非空、禁止直接操作数据库表；
6. **历史变量是审计核心**：流程实例结束后，变量自动转为历史变量永久存储，通过`HistoryService`查询，满足企业流程审计、数据追溯需求。

至此，你已经掌握了Flowable**核心概念的全部内容**（流程定义→流程实例→流程任务→网关→流程变量），这五个核心模块构成了Flowable企业级开发的基础。结合这些知识点，灵活运用流程变量的动态数据能力，就能实现绝大多数企业复杂业务流程的开发，后续只需补充**历史数据追溯、多租户、流程挂起/激活**等高级特性，即可完成完整的工作流系统开发。
