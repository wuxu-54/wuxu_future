# Flowable 核心概念：流程定义（ProcessDefinition）全解析 + 实战代码 + 避坑指南

流程定义是Flowable工作流框架的**基础核心**，也是你学习Flowable的第一个关键节点——它是业务流程的**静态标准化模板**，所有流程的运行、任务的生成、引擎的调度，都基于流程定义展开。结合你之前学习的各类核心Service，流程定义的全生命周期管理由**RepositoryService**（之前未单独详细讲，本次会核心使用）负责，同时联动RuntimeService（启动实例）、ManagementService（底层配置）等，先把这个核心概念吃透，后续学习流程实例、任务处理会事半功倍。

## 一、什么是流程定义？（通俗解释+核心特性）

### 1. 本质定义

流程定义是**基于BPMN 2.0国际规范**，对企业业务流程的**静态、无状态、标准化描述**，本质是一个**BPMN格式的XML文件**（后缀通常为`.bpmn20.xml`或`.bpmn`），文件中定义了流程的**节点（事件/任务/网关）、节点流转规则、任务分配规则、流程变量规则**等所有静态信息。

简单说：**流程定义 = 业务流程的“模板/图纸”**，就像造房子的图纸，基于同一张图纸可以盖出多栋一模一样的房子，基于同一个流程定义可以启动多个**流程实例**（动态运行的流程，比如“张三的请假流程”“李四的请假流程”）。

### 2. 核心关联关系（新手必分清，避免混淆）

很多新手会混淆**流程定义、部署、流程实例**三个概念，这里直接讲清边界：

| 概念               | 性质       | 作用                     | 类比       | 管理Service       |
|--------------------|------------|--------------------------|------------|-------------------|
| 流程定义（ProcessDefinition） | 静态模板   | 定义流程的所有规则，是实例启动的唯一依据 | 建房图纸   | RepositoryService |
| 部署（Deployment） | 发布动作   | 将BPMN文件上传并固化到Flowable引擎，生成流程定义 | 图纸审核备案 | RepositoryService |
| 流程实例（ProcessInstance） | 动态运行实例 | 基于流程定义启动的具体业务流程（含运行状态、业务数据） | 具体的房子 | RuntimeService    |

**关键结论**：BPMN文件**必须经过「部署」操作**，才能被Flowable引擎解析并生成**流程定义**；只有存在有效的流程定义，才能启动对应的流程实例。

### 3. 流程定义的核心存储表（底层认知，避坑必备）

Flowable将流程定义的相关数据存储在**元数据表（ACT_RE_*）**中（`RE`=Repository，仓库），核心关联3张表，部署后会自动生成数据，新手无需手动操作，但要知道对应关系：

1. **ACT_RE_PROCDEF**：**流程定义核心表**，存储流程定义的所有元数据（ID、Key、版本、名称、部署ID等），后续所有操作（启动实例、查询定义）均基于此表；
2. **ACT_RE_DEPLOYMENT**：部署信息表，记录每一次部署的动作（部署ID、部署名称、部署时间、部署人等），一个部署可包含多个BPMN文件/表单文件；
3. **ACT_GE_BYTEARRAY**：资源存储表，以二进制形式存储BPMN文件、表单文件（.form）、流程图片（.png）等部署资源，关联部署ID和流程定义ID。

**关联逻辑**：部署BPMN文件 → 引擎在`ACT_GE_BYTEARRAY`存储二进制资源 → 在`ACT_RE_DEPLOYMENT`生成部署记录 → 解析BPMN并在`ACT_RE_PROCDEF`生成**流程定义记录**。

### 4. 流程定义的核心属性（ACT_RE_PROCDEF表关键字段）

这些属性是实战中**查询、使用、管理流程定义**的核心，必须熟记：

| 属性名          | 含义&实战作用                                                                 |
|-----------------|------------------------------------------------------------------------------|
| ID_             | 流程定义唯一ID，格式：`流程Key:版本号:随机唯一码`（如`leaveProcess:2:123456`），引擎自动生成，不可修改 |
| KEY_            | 流程定义**业务唯一标识**（如`leaveProcess`-请假流程、`buyProcess`-采购流程），**版本管理的核心**，相同Key重新部署版本号自动+1 |
| NAME_           | 流程定义显示名称（如`员工请假流程`），用于前端展示，可修改                     |
| VERSION_        | 版本号，**相同Key的流程定义，每次重新部署版本号自动递增**（首次部署为1，再次为2...） |
| DEPLOYMENT_ID_  | 关联的部署ID，通过此属性可追溯流程定义的部署记录/资源                          |
| RESOURCE_NAME_  | 关联的BPMN资源文件名（如`leave-process.bpmn20.xml`）                          |
| TENANT_ID_      | 租户ID，多租户场景下的隔离标识，非多租户为`null`                              |
| SUSPENSION_STATE_| 挂起状态：`1`=激活（可用），`2`=挂起（不可用），挂起后无法启动新的流程实例     |

**核心重点**：**`KEY_`是流程定义的核心标识**，实战中几乎所有操作（查询、启动实例、挂起）都是按`KEY_`而非`ID_`操作——因为`ID_`包含版本号，而`KEY_`代表“同一类业务流程”，引擎会自动管理其版本。

### 5. 流程定义的核心特性

1. **版本化管理**：相同`KEY_`的BPMN文件重新部署，**版本号自动递增**，引擎会保留所有历史版本，可指定版本启动实例；
2. **静态无状态**：流程定义仅存储规则，不包含任何业务数据/运行状态，业务数据由流程实例携带；
3. **唯一性**：同一部署中，相同`KEY_`的流程定义只能存在一个；不同部署的相同`KEY_`会生成不同版本；
4. **可挂起/激活**：挂起后的流程定义，**无法启动新的流程实例**，但已运行的流程实例不受影响；激活后恢复正常；
5. **不可修改**：流程定义部署后**无法直接修改**，若业务流程规则变更，需修改BPMN文件后**重新部署**，生成新的版本。

## 三、第一步：编写BPMN 2.0流程定义文件（核心模板）

流程定义的载体是**BPMN文件**，这是业务流程规则的具体体现，Flowable完全兼容BPMN 2.0规范，支持两种编写方式：

1. **可视化编写**：使用Flowable Modeler（官方可视化设计工具）、Activiti Modeler、IDEA BPMN插件，适合非开发人员/快速设计；
2. **手动编写**：直接写XML文件，适合开发人员/精细定制，实战中更常用（可版本控制、可自定义规则）。

### 1. BPMN文件存放位置

在`src/main/resources`下创建`processes`目录（Flowable默认扫描此目录的BPMN文件，可自定义），所有BPMN文件放在此目录下，示例：`src/main/resources/processes/leave-process.bpmn20.xml`。

### 2. 实战示例：员工请假流程（简单且覆盖核心节点）

编写一个**两步审批的请假流程**：开始事件 → 申请人提交请假（用户任务） → 经理审批（用户任务） → 结束事件，包含**任务分配、流程名称、流程Key**等核心配置，是实战中最基础的流程模板，代码带详细注释：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<definitions
        xmlns="http://www.omg.org/spec/BPMN/20100524/MODEL"
        xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xmlns:flowable="http://flowable.org/bpmn"
        xsi:schemaLocation="http://www.omg.org/spec/BPMN/20100524/MODEL http://www.omg.org/spec/BPMN/2.0/20100501/BPMN20.xsd"
        typeLanguage="http://www.w3.org/2001/XMLSchema"
        expressionLanguage="http://www.w3.org/1999/XPath"
        targetNamespace="http://flowable.org/bpmn">

    <!-- 流程定义核心配置：id=流程Key（核心），name=流程名称，isExecutable=true（可执行，必须设为true） -->
    <process id="leaveProcess" name="员工请假流程" isExecutable="true">
        <!-- 1. 开始事件：流程的起点，id唯一，name可选 -->
        <startEvent id="startEvent" name="开始请假"/>

        <!-- 2. 申请人提交请假：用户任务（userTask），Flowable核心任务类型 -->
        <userTask id="applyTask" name="申请人提交请假">
            <!-- 任务分配：指定处理人（assignee），也可指定候选组（candidateGroups），后续可通过流程变量动态分配 -->
            <extensionElements>
                <flowable:assignee>applicant</flowable:assignee>
            </extensionElements>
        </userTask>

        <!-- 3. 经理审批：用户任务 -->
        <userTask id="approveTask" name="经理审批"/>
            <!-- 此处暂不指定处理人，实战中可通过流程变量动态分配，如${managerId} -->

        <!-- 4. 结束事件：流程的终点 -->
        <endEvent id="endEvent" name="请假结束"/>

        <!-- 流程流转规则：顺序流（sequenceFlow），连接各个节点，指定流转方向 -->
        <sequenceFlow id="flow1" sourceRef="startEvent" targetRef="applyTask"/>
        <sequenceFlow id="flow2" sourceRef="applyTask" targetRef="approveTask"/>
        <sequenceFlow id="flow3" sourceRef="approveTask" targetRef="endEvent"/>
    </process>
</definitions>
```

### BPMN文件核心注意点（新手必看，避免部署失败）

1. **根节点`definitions`**：必须包含BPMN 2.0的命名空间和schema，直接复制模板即可，无需修改；
2. **`process`节点**：`id`=流程Key（**实战中命名规范，如业务名+Process**），`isExecutable="true"`（**必须设为true**，否则流程定义不可执行，无法启动实例），`name`为显示名称；
3. **节点ID唯一性**：所有节点（startEvent/userTask/endEvent）、顺序流的`id`必须**全局唯一**，禁止重复；
4. **用户任务`userTask`**：Flowable中人工处理的核心节点，可通过`flowable:assignee`（指定处理人）、`flowable:candidateGroups`（指定候选组）分配任务，支持**UEL表达式**（如`${userId}`）动态分配；
5. **顺序流`sequenceFlow`**：`sourceRef`（起点节点ID）、`targetRef`（终点节点ID）必须正确，否则流程流转失败；
6. **编码格式**：BPMN文件必须为**UTF-8编码**，否则部署时会出现中文乱码；
7. **避免中文ID**：节点、顺序流的`id`禁止使用中文，可用英文/下划线命名（如`applyTask`），`name`可使用中文（前端展示）。

### 操作1：部署流程定义（核心！BPMN文件生效的唯一方式）

部署是将BPMN文件从本地资源加载到Flowable引擎，生成**部署记录**和**流程定义**的过程，实战中分为**手动部署**（代码/接口）和**自动部署**（Flowable默认扫描`processes`目录，项目启动时自动部署），这里先讲**手动部署**（可控性高，实战常用）。

#### 核心代码

```java
/**
 * 部署流程定义：手动部署BPMN文件，实战中可封装为接口，供后台管理系统使用
 */
@Test
public void deployProcessDefinition() {
    // 构建部署器：指定部署名称、添加BPMN资源、部署
    Deployment deployment = repositoryService.createDeployment()
            .name("员工请假流程-V1部署") // 部署名称（自定义，便于追溯）
            .category("请假流程") // 部署分类（自定义，便于按分类查询）
            .addClasspathResource("processes/leave-process.bpmn20.xml") // 添加BPMN文件资源（路径必须正确）
            // .addInputStream("leave-process.png", inputStream) // 可选：添加流程图片（可视化展示）
            .deploy(); // 执行部署，返回部署对象

    // 打印部署信息
    System.out.println("流程定义部署成功！");
    System.out.println("部署ID：" + deployment.getId());
    System.out.println("部署名称：" + deployment.getName());
    System.out.println("部署时间：" + deployment.getDeploymentTime());

    // 部署后，查询生成的流程定义
    ProcessDefinition processDefinition = repositoryService.createProcessDefinitionQuery()
            .deploymentId(deployment.getId())
            .singleResult();
    System.out.println("生成的流程定义信息：");
    System.out.println("流程定义ID：" + processDefinition.getId());
    System.out.println("流程Key：" + processDefinition.getKey());
    System.out.println("流程版本：" + processDefinition.getVersion());
    System.out.println("流程名称：" + processDefinition.getName());
}
```

#### 部署后数据库变化

1. `ACT_RE_DEPLOYMENT`：新增1条部署记录，ID为1；
2. `ACT_GE_BYTEARRAY`：新增1条二进制资源记录，存储BPMN文件，关联部署ID=1；
3. `ACT_RE_PROCDEF`：新增1条流程定义记录，Key=leaveProcess，Version=1，关联部署ID=1。

#### 重复部署测试

修改BPMN文件（如将流程名称改为“员工请假流程-V2”），再次运行此方法，控制台会打印：

```

流程Key：leaveProcess
流程版本：2
```

**核心特性验证**：相同Flow Key，重新部署后**版本号自动递增**，引擎保留所有历史版本。

### 操作2：查询流程定义（实战高频，按多条件筛选）

流程定义查询是后台管理系统的核心功能，支持按**流程Key、名称、版本、分类、部署ID**等多条件筛选，核心是`ProcessDefinitionQuery`查询器（链式调用，与之前学习的HistoryService/IdentityService查询器用法一致）。

#### 核心代码（覆盖实战所有常用查询场景）

```java
/**
 * 查询流程定义：实战高频，覆盖单条查询、按Key查最新版本、批量查询、分页查询
 */
@Test
public void queryProcessDefinition() {
    // 场景1：按流程Key查询【最新版本】的流程定义（实战最常用！）
    ProcessDefinition latestProcessDef = repositoryService.createProcessDefinitionQuery()
            .processDefinitionKey("leaveProcess") // 按流程Key筛选
            .latestVersion() // 仅查询最新版本
            .singleResult(); // 返回单条结果
    System.out.println("【最新版本】流程定义：" + latestProcessDef.getKey() + "-V" + latestProcessDef.getVersion());

    // 场景2：按流程Key查询所有版本的流程定义
    List<ProcessDefinition> allVersionDefs = repositoryService.createProcessDefinitionQuery()
            .processDefinitionKey("leaveProcess")
            .orderByProcessDefinitionVersionDesc() // 按版本倒序
            .list();
    System.out.println("leaveProcess所有版本数：" + allVersionDefs.size());
    allVersionDefs.forEach(def -> System.out.println("版本：" + def.getVersion() + "，ID：" + def.getId()));

    // 场景3：批量查询所有激活的流程定义（分页，避免内存溢出）
    int pageNum = 1;
    int pageSize = 10;
    List<ProcessDefinition> processDefs = repositoryService.createProcessDefinitionQuery()
            .active() // 仅查询激活的流程定义（未挂起）
            .orderByDeploymentTimeDesc() // 按部署时间倒序
            .listPage((pageNum - 1) * pageSize, pageSize); // 分页查询
    System.out.println("第1页流程定义数：" + processDefs.size());

    // 场景4：按部署ID查询流程定义
    List<ProcessDefinition> defByDeployId = repositoryService.createProcessDefinitionQuery()
            .deploymentId("1")
            .list();
    System.out.println("部署ID=1的流程定义数：" + defByDeployId.size());

    // 场景5：查询流程定义总数
    long totalCount = repositoryService.createProcessDefinitionQuery().count();
    System.out.println("引擎中所有流程定义总数：" + totalCount);
}
```

| `processDefinitionKey(String key)` | 按流程Key筛选 | ★★★★★ |
| `latestVersion()` | 仅查询最新版本 | ★★★★★ |
| `active()` | 筛选激活的流程定义 | ★★★★ |
| `suspended()` | 筛选挂起的流程定义 | ★★★ |
| `deploymentId(String id)` | 按部署ID筛选 | ★★★ |
| `listPage(int first, int max)` | 分页查询 | ★★★★★ |
| `orderByProcessDefinitionVersionDesc()` | 按版本倒序 | ★★★★ |

### 操作3：挂起/激活流程定义（实战常用，流程规则变更时使用）

当业务流程规则需要临时禁用（如流程优化、故障修复），可**挂起**流程定义——挂起后，**无法启动新的流程实例**，但**已运行的流程实例不受影响**（继续执行）；规则恢复后，**激活**流程定义即可。

挂起/激活支持两种粒度：**按流程Key挂起所有版本**、**按流程定义ID挂起单个版本**，实战中优先按Key操作。

#### 核心代码

```java
/**
 * 挂起/激活流程定义：实战中用于禁用/启用流程
 */
@Test
public void suspendAndActivateProcessDefinition() {
    String processKey = "leaveProcess";
    // 1. 按流程Key挂起【所有版本】的流程定义
    repositoryService.suspendProcessDefinitionByKey(processKey);
    System.out.println("流程Key=" + processKey + "的所有版本已挂起！");

    // 验证：挂起后查询状态（suspensionState=2）
    ProcessDefinition suspendedDef = repositoryService.createProcessDefinitionQuery()
            .processDefinitionKey(processKey)
            .latestVersion()
            .singleResult();
    System.out.println("挂起后状态：" + (suspendedDef.isSuspended() ? "挂起" : "激活"));

    // 测试：挂起后启动流程实例（会抛异常）
    try {
        // repositoryService.getRuntimeService().startProcessInstanceByKey(processKey);
        System.out.println("挂起后启动实例成功（不会执行到这里）");
    } catch (Exception e) {
        System.out.println("挂起后启动实例失败，异常信息：" + e.getMessage());
    }

    // 2. 按流程Key激活【所有版本】的流程定义
    repositoryService.activateProcessDefinitionByKey(processKey);
    System.out.println("流程Key=" + processKey + "的所有版本已激活！");

    // 3. 按流程定义ID挂起【单个版本】的流程定义（实战少用）
    String processDefId = "leaveProcess:1:123456";
    repositoryService.suspendProcessDefinitionById(processDefId);
    System.out.println("流程定义ID=" + processDefId + "已挂起！");
    // 激活单个版本
    repositoryService.activateProcessDefinitionById(processDefId);
}
```

#### 核心方法

```java
// 按Key挂起/激活所有版本
void suspendProcessDefinitionByKey(String processDefinitionKey);
void activateProcessDefinitionByKey(String processDefinitionKey);

// 按ID挂起/激活单个版本
void suspendProcessDefinitionById(String processDefinitionId);
void activateProcessDefinitionById(String processDefinitionId);
```

### 操作4：删除流程定义（实战慎用，尤其是生产环境）

删除流程定义本质是**删除部署记录**，因为流程定义关联部署ID，Flowable提供**普通删除**和**级联删除**，核心区别：

- **普通删除**：仅删除部署记录、流程定义、资源文件，若该部署下有**正在运行的流程实例**，则删除失败（抛异常）；
- **级联删除**：删除部署记录的同时，**级联删除所有关联的运行时数据、历史数据**（流程实例、任务、历史记录等），**极度高危**！

#### 核心代码

```java
/**
 * 删除流程定义：实战慎用，生产环境禁止使用级联删除！
 */
@Test
public void deleteProcessDefinition() {
    String deploymentId = "1"; // 部署ID，可通过查询获取

    // 1. 普通删除：有运行实例则抛异常（推荐，生产环境使用）
    try {
        repositoryService.deleteDeployment(deploymentId);
        System.out.println("普通删除部署成功！");
    } catch (Exception e) {
        System.out.println("普通删除失败，原因：" + e.getMessage());
    }

    // 2. 级联删除：删除所有关联数据（极度高危，仅测试环境使用！）
    // repositoryService.deleteDeployment(deploymentId, true);
    // System.out.println("级联删除部署成功！");
}
```

#### 核心注意点

1. **生产环境仅用普通删除**：级联删除会导致**业务数据丢失、审计记录消失**，仅在清理测试数据时使用；
2. **删除前先校验**：删除前先查询该部署下是否有运行的流程实例，有则先处理实例（完成/终止），再删除；
3. **删除不可恢复**：删除后，部署记录、流程定义、资源文件会被**物理删除**，无法恢复，操作前必须备份。

### 操作5：Flowable自动部署（项目启动时部署BPMN文件）

Flowable提供**自动部署**功能，项目启动时会**自动扫描指定目录**（默认`src/main/resources/processes`）的BPMN文件，自动完成部署，无需编写部署代码，适合**开发/测试环境**，生产环境建议使用**手动部署**（可控性高，可记录部署人/部署时间）。

#### 自动部署配置（默认开启，无需额外配置）

Flowable Spring Boot Starter会**默认开启自动部署**，扫描`src/main/resources/processes`目录，若需要自定义扫描目录，可在`application.yml`中配置：

```yaml
flowable:
  # 自定义流程定义扫描目录，多个目录用逗号分隔
  process-definition-location-prefix: classpath:/custom-processes/
  # 扫描的文件后缀，默认**/*.bpmn,**/*.bpmn20.xml
  process-definition-location-suffixes:
    - **/*.bpmn
    - **/*.bpmn20.xml
  # 关闭自动部署（生产环境建议关闭）
  # auto-deployment-enabled: false
```

## 五、流程定义实战核心避坑点（新手必看，避免踩坑）

结合大量企业实战经验，整理了流程定义相关的**10个高频坑点**，涵盖BPMN编写、部署、管理、使用全流程，**严格遵守可避免90%的基础问题**。

### 1. 流程Key命名不规范，上线后随意修改

- **坑点**：流程Key命名混乱（如`qjlx`/`flow1`），后续业务变更时随意修改Key，导致版本管理失效、历史流程无法追溯；
- **解决方案**：
  1. 流程Key遵循**业务名+Process**规范（如`leaveProcess`/`purchaseProcess`），见名知意；
  2. **流程Key一旦上线，永久禁止修改**！业务规则变更时，修改BPMN文件后**重新部署**，引擎自动生成新版本。

### 2. BPMN文件`isExecutable="false"`，导致流程定义不可执行

- **坑点**：编写BPMN时忘记设置`process`节点的`isExecutable="true"`，部署后流程定义存在，但启动实例时抛`ProcessDefinitionNotExecutableException`；
- **解决方案**：所有需要运行的流程定义，`process`节点必须显式设置`isExecutable="true"`，这是Flowable执行流程的必要条件。

### 3. 重复部署BPMN文件，导致版本号无意义递增

- **坑点**：开发时频繁重启项目，Flowable自动部署每次都生成新版本，导致版本号混乱（如V1/V2/V3无实际差异）；
- **解决方案**：
  1. 开发环境：在`application.yml`中配置`flowable.auto-deployment-enabled=false`，关闭自动部署，使用手动部署；
  2. 生产环境：封装部署接口，添加**重复部署校验**（根据BPMN文件MD5/资源名判断，已部署则不重复部署）。

### 4. 挂起流程定义后，误以为已运行的实例会停止

- **坑点**：挂起流程定义后，认为正在运行的流程实例会立即停止，实际挂起仅影响**新实例的启动**，已运行实例不受影响；
- **解决方案**：若需要停止已运行的流程实例，需通过`RuntimeService`**终止流程实例**（`runtimeService.deleteProcessInstance(instanceId, "停止原因")`），而非挂起流程定义。

### 5. 直接操作流程定义ID，而非流程Key

- **坑点**：实战中按流程定义ID（如`leaveProcess:2:123456`）查询/启动实例，当流程升级为V3后，ID变更，代码需要修改；
- **解决方案**：**所有业务代码均按流程Key操作**（如`leaveProcess`），引擎默认使用**最新版本**启动实例，若需要指定版本，可通过`processDefinitionKeyAndVersion`启动：

  ```java
  // 指定版本启动流程实例（实战极少用，仅特殊场景）
  runtimeService.startProcessInstanceByKeyAndVersion("leaveProcess", 1);
  ```

### 6. BPMN文件节点ID使用中文，导致流转失败

- **坑点**：为了方便，将节点ID设为中文（如`<startEvent id="开始请假"/>`），部署时可能成功，但流程流转时抛XML解析异常；
- **解决方案**：节点ID、顺序流ID**仅使用英文/数字/下划线**，遵循**小驼峰/下划线**命名规范（如`startEvent`/`apply_task`），`name`属性可使用中文（前端展示）。

### 7. 生产环境使用级联删除，导致数据丢失

- **坑点**：生产环境误调用`deleteDeployment(deploymentId, true)`级联删除，导致该部署下的所有流程实例、任务、历史记录被永久删除，无法追溯；
- **解决方案**：
  1. 生产环境**禁止使用级联删除**，仅使用普通删除（`deleteDeployment(deploymentId)`）；
  2. 删除部署前，必须通过`RuntimeService`查询该部署下是否有运行的流程实例，有则先处理（完成/终止）；
  3. 给删除接口添加**多重权限校验**（仅超级管理员可操作），并添加**操作日志**。

### 8. 任务分配硬编码，未使用动态分配

- **坑点**：在BPMN中硬编码任务处理人（如`<flowable:assignee>zhangsan</flowable:assignee>`），导致所有流程实例的该任务都由张三处理，无法适配实际业务的动态分配（如不同部门的请假由不同经理审批）；
- **解决方案**：使用**UEL表达式**动态分配任务，通过**流程变量**传递处理人/候选组ID，示例：

  ```xml
  <!-- 动态指定处理人：流程变量中传递applicantId -->
  <flowable:assignee>${applicantId}</flowable:assignee>
  <!-- 动态指定候选组：流程变量中传递deptManagerGroup -->
  <flowable:candidateGroups>${deptManagerGroup}</flowable:candidateGroups>
  ```

  启动流程时传入流程变量：

  ```java
  Map<String, Object> variables = new HashMap<>();
  variables.put("applicantId", "zhangsan");
  variables.put("deptManagerGroup", "manager_group");
  runtimeService.startProcessInstanceByKey("leaveProcess", variables);
  ```

### 9. 多租户场景未做流程定义隔离

- **坑点**：多租户系统中，部署流程定义时未指定`tenantId`，导致不同租户的流程定义相互混淆，数据泄露；
- **解决方案**：多租户场景下，**所有部署/查询操作必须指定tenantId**：

  ```java
  // 多租户部署流程定义
  Deployment deployment = repositoryService.createDeployment()
          .name("租户1-请假流程部署")
          .tenantId("tenant1") // 指定租户ID
          .addClasspathResource("processes/leave-process.bpmn20.xml")
          .deploy();

  // 多租户查询流程定义
  ProcessDefinition processDef = repositoryService.createProcessDefinitionQuery()
          .processDefinitionKey("leaveProcess")
          .tenantId("tenant1") // 按租户筛选
          .latestVersion()
          .singleResult();
  ```

### 10. 部署后未生成流程图片，可视化展示失败

- **坑点**：流程管理系统需要可视化展示流程定义（如流程图），但部署时未添加流程图片，导致前端无法展示；
- **解决方案**：
  1. 使用Flowable Modeler设计BPMN时，**自动生成流程图片（.png）**；
  2. 部署时将图片与BPMN文件一起添加到部署器：

     ```java
     repositoryService.createDeployment()
             .name("请假流程部署-含图片")
             .addClasspathResource("processes/leave-process.bpmn20.xml")
             .addClasspathResource("processes/leave-process.png") // 添加流程图片
             .deploy();
     ```

  3. 通过RepositoryService获取流程图片资源：

     ```java
     // 获取流程图片输入流
     InputStream inputStream = repositoryService.getProcessDiagram(processDefId);
     // 将输入流转换为图片，返回给前端展示
     ```

## 六、流程定义与其他核心组件的联动（形成知识链）

结合你之前学习的`RuntimeService`/`HistoryService`/`TaskService`，流程定义是所有组件的**基础**，核心联动关系如下，帮助你形成完整的Flowable知识体系：

1. **与RuntimeService**：`RuntimeService`通过**流程Key**启动**流程实例**，`runtimeService.startProcessInstanceByKey(processKey)`；
2. **与TaskService**：流程实例运行到`userTask`节点时，`TaskService`基于流程定义中的**任务规则**生成用户任务，`taskService.createTaskQuery()`查询任务；
3. **与HistoryService**：流程实例完成后，`HistoryService`基于流程定义的**节点规则**生成历史记录，`historyService.createHistoricProcessInstanceQuery()`查询历史实例；
4. **与FormService**：流程定义可绑定**启动表单/任务表单**，`FormService`通过流程定义ID获取表单数据，`formService.getStartFormData(processDefId)`；
5. **与ManagementService**：`ManagementService`可查询流程定义的底层元数据、缓存，`managementService.getTableMetaData("ACT_RE_PROCDEF")`。

## 七、核心总结

1. **流程定义是静态模板**：基于BPMN 2.0规范，是业务流程的“图纸”，由RepositoryService管理全生命周期，部署后固化到`ACT_RE_PROCDEF`表；
2. **流程Key是核心标识**：上线后禁止修改，相同Key重新部署版本号自动递增，实战中所有操作优先按Key执行；
3. **部署是生效的唯一方式**：BPMN文件必须通过部署才能生成流程定义，支持手动部署（实战首选）和自动部署（开发环境）；
4. **挂起仅影响新实例**：挂起流程定义后，无法启动新实例，已运行实例不受影响，激活后恢复正常；
5. **删除需极度谨慎**：生产环境仅用普通删除，禁止级联删除，删除前必须校验运行实例，操作前备份；
6. **BPMN编写遵循规范**：`isExecutable=true`、节点ID唯一且非中文、任务分配使用动态UEL表达式，避免硬编码。

掌握流程定义后，你接下来的学习重点就是**基于流程定义启动流程实例**（RuntimeService）、**处理用户任务**（TaskService），这两个部分是Flowable业务开发的核心，后续会继续为你详细解析。
