# Flowable 核心概念：流程任务（Task）全解析 + 实战代码 + 避坑指南

流程任务（Task）是Flowable工作流**引擎与人工交互的唯一核心节点**，特指BPMN中定义的`userTask`（用户任务）——流程实例运行到`userTask`节点时，引擎会自动生成对应的流程任务，推送给指定处理人/候选人，**人工处理完任务后，引擎才会继续推进流程实例到下一个节点**。

如果说流程定义是“图纸”、流程实例是“具体房子”，那流程任务就是“房子建造中需要人工签字确认的工序节点”，是企业业务流程中**人工干预的唯一载体**（如请假审批、订单审核、合同盖章）。

流程任务的全生命周期管理由**TaskService**（核心专属Service）实现，同时联动RuntimeService（流程实例管控）、IdentityService（用户/组关联）、HistoryService（历史任务追溯），本文延续之前的风格，基于**Spring Boot 2.7+Flowable 6.8.0+员工请假流程**案例，从**概念区分→核心存储→实战操作→生命周期→避坑指南**逐步讲解，代码可直接复用运行，覆盖生产环境所有高频操作。

## 一、什么是流程任务（Task）？（通俗解释+核心关联）

### 1. 本质定义

流程任务（本文均指`userTask`，Flowable核心人工任务）是流程实例运行到BPMN中`userTask`节点时，引擎自动生成的**人工处理任务**，包含任务处理人、候选人、任务名称、关联流程实例、创建时间等信息，**只有人工完成/删除该任务，流程实例才能继续流转**。

Flowable中**无需人工处理的自动任务**（如`serviceTask`服务任务、`scriptTask`脚本任务）由引擎自动执行，不会生成流程任务，也无需TaskService干预。

**核心关联**：**1个流程实例可包含多个流程任务**（按BPMN节点顺序生成，并行网关会生成多个并行任务），**1个流程任务仅属于1个流程实例**，任务处理完成后，从运行时表迁移到历史表，不再参与流程运行。

举个例子：

- 流程实例：张三的请假流程（instanceId:5001）；
- 流程任务1：张三提交请假申请（taskId:1001，处理人：张三）；
- 流程任务2：经理审批请假（taskId:1002，处理人：李四）；
- 两个任务依次处理，全部完成后流程实例走到结束事件。

### 2. 新手必分清：4个核心概念边界（任务/实例/执行流/流程定义）

| 概念               | 性质       | 作用                     | 核心操作                     | 管理Service       | 核心存储表          |
|--------------------|------------|--------------------------|------------------------------|-------------------|---------------------|
| 流程定义（ProcessDefinition） | 静态无状态 | 业务流程规则模板         | 部署、查询、挂起/激活        | RepositoryService | ACT_RE_PROCDEF      |
| 流程实例（ProcessInstance） | 动态有状态 | 具体业务的运行载体       | 启动、查询、挂起/删除        | RuntimeService    | ACT_RU_PROCINST/ACT_HI_PROCINST |
| 执行流（Execution） | 动态最小执行单元 | 引擎调度的执行路径       | 触发、查询                   | RuntimeService    | ACT_RU_EXECUTION/ACT_HI_ACTINST |
| 流程任务（Task）| 动态人工任务 | 引擎与人工交互的节点     | 查询、认领、完成、委派、批注 | TaskService       | ACT_RU_TASK（运行）/ACT_HI_TASKINST（历史） |

**关键规则**：

1. 流程任务**仅由`userTask`节点生成**，自动任务无对应Task；
2. 流程任务的**分配规则**在BPMN中定义（直配处理人/候选人/候选组），也可通过流程变量动态分配；
3. 任务处理完成（`TaskService.complete`）后，引擎**自动推进执行流**，流程实例进入下一个节点；
4. 流程实例挂起后，其下所有未完成任务会被**自动挂起**，无法处理。

### 3. 流程任务核心存储表（运行时+历史，避坑必备）

流程任务的数同样分为**运行时数据**（未完成任务，ACT_RU_*）和**历史数据**（已完成/删除/挂起任务，ACT_HI_*），核心关联3张表，是TaskService操作的底层载体：

#### 运行时表（任务未完成时存在，核心2张）

1. **ACT_RU_TASK**：**流程任务运行时核心表**，存储未完成任务的所有元数据（任务ID、实例ID、处理人assignee、候选人、创建时间、挂起状态等），TaskService的所有写操作均针对此表；
2. **ACT_RU_IDENTITYLINK**：身份关联表，存储任务的**候选人、候选组**信息（若任务直配处理人，此表无记录），联动IdentityService的用户/组数据。

#### 历史表（任务完成/删除后永久存储，核心1张）

- **ACT_HI_TASKINST**：流程任务历史核心表，是ACT_RU_TASK的**快照备份**，存储所有任务的全量信息（包含完成时间、处理时长、删除原因），是**人工操作审计追溯的核心依据**，无修改/删除API。

**核心流转逻辑**：
流程实例运行到`userTask`节点 → 引擎在ACT_RU_TASK生成任务记录，ACT_RU_IDENTITYLINK生成候选人/组记录 → 人工处理任务（认领/完成/转办） → 引擎**清理ACT_RU_TASK和ACT_RU_IDENTITYLINK中对应记录**，将快照迁移到ACT_HI_TASKINST → 流程实例继续流转。

### 4. 流程任务核心属性（实战高频字段，熟记）

流程任务的核心属性对应ACT_RU_TASK/ACT_HI_TASKINST的关键字段，是**查询、分配、处理任务**的核心，其中**assignee（处理人）、candidateUser（候选人）、candidateGroup（候选组）**是任务分配的核心字段。

| 属性名          | 对应表字段       | 含义&实战作用                                                                 |
|-----------------|------------------|------------------------------------------------------------------------------|
| **id**          | ID_              | 任务唯一ID，引擎自动生成（如`1001`），是所有任务操作的核心标识                 |
| **name**        | NAME_            | 任务名称，对应BPMN中`userTask`的`name`属性（如“经理审批请假”），前端展示用     |
| **assignee**    | ASSIGNEE_        | 任务**已认领的处理人**，直配处理人时创建任务即赋值，候选人认领后赋值，null表示未认领 |
| **processInstanceId** | PROC_INST_ID_ | 关联的流程实例ID，通过此属性关联到具体业务流程                               |
| **executionId** | EXECUTION_ID_    | 关联的执行流ID，根执行流ID与实例ID一致                                       |
| **createTime**  | CREATE_TIME_     | 任务创建时间，引擎自动生成，用于任务超时提醒、按时间筛选                       |
| **completionTime** | END_TIME_    | 任务完成时间，仅历史表有，完成任务后引擎自动填充                             |
| **suspensionState** | SUSPENSION_STATE_ | 挂起状态：1=激活（可处理），2=挂起（不可处理）|
| **businessKey** | 关联实例的BUSINESS_KEY_ | 关联的业务键，需通过实例ID关联查询，业务系统联动核心                         |
| **tenantId**    | TENANT_ID_        | 租户ID，多租户场景隔离标识，非多租户为null                                    |

### 操作1：查询流程任务（实战最高频，前端待办列表核心）

任务查询是**前端待办/已办/可认领列表的核心操作**，通过`TaskQuery`查询器实现，支持按**处理人、候选人、候选组、业务键、流程Key、任务名称**等多条件筛选，**实战中最常用的是「我的待办（assignee=当前用户）」和「我可认领（candidateUser=当前用户）」**。

#### 核心代码（覆盖生产环境所有高频查询场景）

```java
/**
 * 流程任务查询：实战高频场景（我的待办、我可认领、按业务键查、按流程实例查、分页）
 * 核心：TaskQuery链式调用，前端待办列表核心
 */
@Test
public void queryTask() {
    // 模拟当前用户（实战中从登录态获取）
    String currentUser = "zhangsan"; // 张三（请假人）
    String managerUser = "lisi";     // 李四（经理）
    String businessKey = "leave_20260206_001"; // 业务键（请假单ID）
    String processKey = "leaveProcess"; // 流程Key

    // 场景1：我的待办任务（已认领，assignee=当前用户，实战最高频！）
    List<Task> myTodoTask = taskService.createTaskQuery()
            .assignee(currentUser) // 已认领的处理人
            .active() // 仅激活的任务（可处理）
            .orderByCreateTimeDesc() // 按创建时间倒序（最新的在前）
            .list();
    System.out.println("张三的待办任务数：" + myTodoTask.size());
    myTodoTask.forEach(task -> System.out.println("待办任务：ID=" + task.getId() + "，名称=" + task.getName() + "，实例ID=" + task.getProcessInstanceId()));

    // 场景2：我可认领的任务（未认领，candidateUser=当前用户，实战高频）
    // 先给经理李四添加候选人权限（模拟BPMN中配置候选组/人）
    Task approveTask = taskService.createTaskQuery().processDefinitionKey(processKey).taskName("经理审批").singleResult();
    if (approveTask != null) {
        taskService.addCandidateUser(approveTask.getId(), managerUser);
    }
    List<Task> myClaimTask = taskService.createTaskQuery()
            .candidateUser(managerUser) // 我是候选人
            .active()
            .list();
    System.out.println("李四可认领的任务数：" + myClaimTask.size());

    // 场景3：按业务键查询任务（业务系统根据主键查任务，核心联动）
    // 先通过业务键查实例ID，再通过实例ID查任务
    String instanceId = runtimeService.createProcessInstanceQuery().businessKey(businessKey).singleResult().getId();
    List<Task> taskByBusinessKey = taskService.createTaskQuery()
            .processInstanceId(instanceId) // 按实例ID查
            .active()
            .list();
    System.out.println("业务键" + businessKey + "对应的任务数：" + taskByBusinessKey.size());

    // 场景4：按任务名称模糊查询（如查所有审批任务）
    List<Task> approveTasks = taskService.createTaskQuery()
            .taskNameLike("%审批%")
            .active()
            .list();
    System.out.println("所有审批类任务数：" + approveTasks.size());

    // 场景5：分页查询（前端列表必用，避免内存溢出）
    int pageNum = 1;
    int pageSize = 10;
    List<Task> taskPage = taskService.createTaskQuery()
            .processDefinitionKey(processKey)
            .active()
            .listPage((pageNum - 1) * pageSize, pageSize);
    System.out.println("leaveProcess任务第1页数：" + taskPage.size());

    // 场景6：查询任务总数（统计用）
    long totalTodo = taskService.createTaskQuery().assignee(currentUser).active().count();
    System.out.println("张三的待办任务总数：" + totalTodo);
}
```

### 操作2：任务认领/释放（实战常用，未认领任务分配）

任务**认领（Claim）**：将**未认领任务**（assignee=null，有候选人/候选组）分配给指定用户，认领后任务成为该用户的**专属待办**（assignee=用户ID），其他用户无法再认领；
任务**释放（Unclaim）**：将**已认领任务**归还为未认领状态（assignee=null），重新进入候选人/候选组池，供其他用户认领（适用于分配错误、用户无法处理的场景）。

#### 核心代码（生产环境标准写法，含前置校验）

```java
/**
 * 任务认领/释放：实战标准写法，含前置权限校验
 * 核心：认领前校验是否为候选人，释放前校验是否为已认领人
 */
@Test
@Transactional
public void claimAndUnclaimTask() {
    // 模拟数据
    String taskId = "1002"; // 经理审批任务ID（实战中从查询结果获取）
    String claimUser = "lisi"; // 认领人：李四（经理）
    String wrongUser = "wangwu"; // 非候选人：王五（无认领权限）

    // 前置校验1：任务是否存在且为激活状态
    Task task = taskService.createTaskQuery().taskId(taskId).active().singleResult();
    if (task == null) {
        System.out.println("任务不存在或已挂起/完成！");
        return;
    }

    // 前置校验2：当前用户是否为候选人（认领必备，否则抛异常）
    boolean isCandidate = taskService.createTaskQuery()
            .taskId(taskId)
            .candidateUser(claimUser)
            .count() > 0;
    if (!isCandidate) {
        System.out.println(claimUser + "不是该任务的候选人，无法认领！");
        return;
    }

    // 1. 任务认领（核心）
    taskService.claim(taskId, claimUser);
    System.out.println("任务" + taskId + "已由" + claimUser + "认领！");
    // 校验认领结果
    Task claimedTask = taskService.createTaskQuery().taskId(taskId).singleResult();
    System.out.println("认领后处理人：" + claimedTask.getAssignee());

    // 2. 任务释放（核心，适用于认领错误/无法处理）
    // 前置校验：是否为当前认领人
    if (claimUser.equals(claimedTask.getAssignee())) {
        taskService.unclaim(taskId);
        System.out.println("任务" + taskId + "已由" + claimUser + "释放！");
        // 校验释放结果
        Task unclaimedTask = taskService.createTaskQuery().taskId(taskId).singleResult();
        System.out.println("释放后处理人：" + (unclaimedTask.getAssignee() == null ? "未认领" : unclaimedTask.getAssignee()));
    }

    // 测试：非候选人认领（会抛异常）
    try {
        taskService.claim(taskId, wrongUser);
    } catch (Exception e) {
        System.out.println("非候选人认领失败，异常：" + e.getMessage());
    }
}
```

#### 核心方法

```java
// 任务认领：taskId=任务ID，userId=认领人ID
void claim(String taskId, String userId);
// 任务释放：taskId=任务ID
void unclaim(String taskId);
```

#### 认领/释放核心注意点

1. **认领前置校验必做**：必须校验**任务存在且激活**+**当前用户是候选人/候选组**，否则直接抛`FlowableTaskException`；
2. **释放前置校验必做**：必须校验**当前用户是任务的已认领人**，否则抛异常；
3. **直配处理人任务无需认领**：BPMN中直接指定`assignee`的任务（如`<flowable:assignee>zhangsan</flowable:assignee>`），创建后assignee已赋值，无需认领，直接进入用户待办；
4. **认领后状态变更**：认领后ACT_RU_TASK的assignee字段赋值，ACT_RU_IDENTITYLINK的候选人记录保留（便于释放后复用）。

### 操作3：任务完成（实战最高频，核心中的核心）

任务**完成（Complete）**是流程任务的**最终核心操作**——用户处理完任务后，通过`TaskService.complete`提交处理结果，引擎会**自动推进流程实例到下一个节点**，同时将任务从运行时表迁移到历史表，生成历史任务记录。

实战中**完成任务必须携带2类信息**：**流程变量**（处理结果，如审批通过/驳回）+**审批批注**（处理意见，如“同意请假3天”），这是流程审计和后续节点流转的核心依据。

#### 核心代码（生产环境标准写法，含变量+批注，@Transactional必加）

```java
/**
 * 任务完成：实战标准写法（核心操作）
 * 核心：携带流程变量（处理结果）+ 添加审批批注 + 事务控制 + 前置校验
 * 必加@Transactional：避免任务完成但流程未推进的脏数据
 */
@Test
@Transactional
public void completeTask() {
    // 模拟数据（实战中从前端/业务系统获取）
    String taskId = "1001"; // 张三提交请假任务ID
    String handleUser = "zhangsan"; // 处理人（必须是已认领人）
    String instanceId = runtimeService.createProcessInstanceQuery().businessKey("leave_20260206_001").singleResult().getId();

    // 前置校验（必做，避免无效操作）
    Task task = taskService.createTaskQuery().taskId(taskId).assignee(handleUser).active().singleResult();
    if (task == null) {
        System.out.println("任务不存在/非当前用户待办/已挂起！");
        return;
    }

    // 1. 添加审批批注（实战必备，审计追溯核心，禁止空批注）
    String comment = "张三提交3天年假申请，材料齐全，请求经理审批！";
    taskService.addComment(taskId, instanceId, comment);
    System.out.println("任务" + taskId + "已添加批注：" + comment);

    // 2. 封装流程变量（处理结果，供后续节点使用，如网关判断、任务分配）
    Map<String, Object> variables = new HashMap<>();
    variables.put("applyStatus", "SUBMITTED"); // 申请状态：已提交
    variables.put("leaveType", "ANNUAL_LEAVE"); // 请假类型：年假
    variables.put("applyComment", comment); // 申请备注

    // 3. 完成任务（核心）：引擎自动推进流程实例到下一个节点（经理审批）
    taskService.complete(taskId, variables);
    System.out.println("任务" + taskId + "已由" + handleUser + "完成！");

    // 校验结果：运行时表中无该任务，下一个任务（经理审批）已生成
    Task completedTask = taskService.createTaskQuery().taskId(taskId).singleResult();
    List<Task> nextTask = taskService.createTaskQuery().processInstanceId(instanceId).active().list();
    System.out.println("完成的任务是否存在：" + (completedTask == null ? "不存在" : "存在"));
    System.out.println("流程实例下一个待办任务数：" + nextTask.size() + "，任务名称：" + nextTask.get(0).getName());
}
```

#### 核心方法（2个重载，实战首选带变量的重载）

```java
// 基础完成：无变量，仅完成任务（不推荐，无处理结果）
void complete(String taskId);
// 实战首选：带流程变量完成任务，变量供后续节点使用
void complete(String taskId, Map<String, Object> variables);
```

#### 任务完成核心注意点（生产必守，重中之重）

1. **必须加@Transactional事务**：任务完成包含“批注保存+变量更新+任务状态修改+流程实例推进”多个操作，无事务会导致**脏数据**（如任务已完成但流程未推进）；
2. **批注必加，禁止空批注**：批注会存入ACT_HI_COMMENT表，是**流程审计的核心依据**，尤其是审批驳回/异常处理时，必须填写清晰的处理原因；
3. **变量必传处理结果**：如`approve=true/false`（审批是否通过）、`handleResult=“同意”`，后续网关/任务分配会基于这些变量判断，无变量会导致流程卡节点；
4. **前置校验必做**：必须校验**任务存在+是当前用户的已认领待办+任务激活**，避免越权操作/重复完成；
5. **完成后引擎自动推进**：无需手动调用RuntimeService，引擎会根据BPMN规则自动将流程实例推进到下一个节点，生成新的任务（若为userTask）。

### 操作4：任务委派/转办（实战常用，任务重新分配）

实际业务中，用户常因“出差、无权限、业务归属”等原因无法处理任务，需要将任务重新分配，Flowable提供**委派（Delegate）**和**转办（Assign）**两种方式，**核心区别**：

- **委派**：临时分配，被委派用户处理后需**归还任务**，原认领用户最终确认（适用于“代处理”场景，如经理出差让助理代审）；
- **转办**：永久分配，直接将任务所有权转移给新用户，无需归还（适用于“业务归属变更”场景，如张三离职，任务转给李四）。

#### 核心代码（委派+归还+转办，含前置校验）

```java
/**
 * 任务委派/转办/归还：实战常用，任务重新分配
 * 委派：临时分配，需归还；转办：永久分配，无需归还（生产首选）
 */
@Test
@Transactional
public void delegateAndAssignTask() {
    // 模拟数据
    String taskId = "1002"; // 经理审批任务ID
    String originalUser = "lisi"; // 原认领人：李四（经理）
    String delegateUser = "wangwu"; // 被委派用户：王五（助理）
    String assignUser = "zhaoliu"; // 转办用户：赵六（新经理）

    // 前置校验：原用户是已认领人，任务激活
    Task task = taskService.createTaskQuery().taskId(taskId).assignee(originalUser).active().singleResult();
    if (task == null) {
        System.out.println("任务不存在/非原用户待办！");
        return;
    }

    // 1. 任务委派（核心）：原用户将任务临时委派给王五
    taskService.delegateTask(taskId, delegateUser);
    System.out.println("任务" + taskId + "已由" + originalUser + "委派给" + delegateUser + "！");
    // 校验委派状态：DELEGATE_ASSIGNEE_=王五，assignee仍为李四
    Task delegatedTask = taskService.createTaskQuery().taskId(taskId).singleResult();
    System.out.println("委派后被委派⼈：" + delegatedTask.getDelegateAssignee() + "，原认领人：" + delegatedTask.getAssignee());

    // 2. 任务归还（核心）：被委派用户王五处理后，归还任务给原用户李四
    // 前置校验：当前用户是被委派⼈
    if (delegateUser.equals(delegatedTask.getDelegateAssignee())) {
        // 归还并携带处理结果变量
        Map<String, Object> variables = new HashMap<>();
        variables.put("delegateComment", "王五代审：材料齐全，建议同意");
        taskService.resolveTask(taskId, variables);
        System.out.println("任务" + taskId + "已由" + delegateUser + "归还给" + originalUser + "！");
    }

    // 3. 任务转办（实战首选，永久分配，核心）：原用户李四将任务转给赵六
    // 无前置校验（管理员可跨用户转办），生产需加权限控制
    taskService.setAssignee(taskId, assignUser);
    System.out.println("任务" + taskId + "已由" + originalUser + "转办给" + assignUser + "！");
    // 校验转办结果：assignee=赵六
    Task assignedTask = taskService.createTaskQuery().taskId(taskId).singleResult();
    System.out.println("转办后处理人：" + assignedTask.getAssignee());
}
```

#### 核心方法

```java
// 任务委派：taskId=任务ID，delegateAssignee=被委派用户ID
void delegateTask(String taskId, String delegateAssignee);
// 任务归还：无变量
void resolveTask(String taskId);
// 任务归还：带处理结果变量
void resolveTask(String taskId, Map<String, Object> variables);
// 任务转办：永久分配，newAssignee=新处理人ID（实战首选）
void setAssignee(String taskId, String newAssignee);
```

#### 委派/转办核心注意点

1. **委派的前置条件**：任务必须**已被原用户认领**（assignee≠null），委派后assignee不变，仅`delegateAssignee`赋值；
2. **归还的前置条件**：当前用户必须是**被委派人**（`delegateAssignee`），归还后`delegateAssignee`置空，任务恢复为原用户的待办；
3. **转办是生产首选**：实际业务中“代处理”场景少，“永久分配”场景多，`setAssignee`支持对**未认领/已认领**任务操作，是转办的核心API；
4. **转办必须加权限控制**：生产环境需限制转办权限（如仅管理员/部门领导可转办），避免普通用户随意转办导致任务混乱；
5. **委派/转办后建议添加批注**：记录委派/转办原因（如“李四出差，委派王五代审”），便于审计追溯。

#### 5.2 任务变量管理（局部变量，避免污染全局变量）

任务变量是**仅作用于当前任务的局部变量**，与RuntimeService的流程全局变量互补，适用于存储任务处理的临时数据（如中间意见、处理状态），完成任务后可选择是否升级为全局变量。

```java
/**
 * 任务变量管理：局部变量，仅作用于当前任务，避免污染全局变量
 */
@Test
@Transactional
public void taskVariable() {
    String taskId = "1002";

    // 1. 设置任务局部变量（单个/批量）
    taskService.setVariable(taskId, "tempStatus", "PROCESSING"); // 单个
    Map<String, Object> varMap = new HashMap<>();
    varMap.put("handleUser", "lisi");
    varMap.put("handleTime", System.currentTimeMillis());
    taskService.setVariables(taskId, varMap); // 批量
    System.out.println("已设置任务局部变量！");

    // 2. 获取任务局部变量（单个/所有）
    String tempStatus = taskService.getVariable(taskId, "tempStatus", String.class);
    Map<String, Object> allVars = taskService.getVariables(taskId);
    System.out.println("单个变量：tempStatus=" + tempStatus);
    System.out.println("所有变量：" + allVars);

    // 3. 删除任务局部变量（单个/批量）
    taskService.removeVariable(taskId, "tempStatus");
    System.out.println("已删除任务局部变量tempStatus！");

    // 4. 完成任务时，局部变量可升级为全局变量（直接传入complete的变量中）
    Map<String, Object> completeVars = new HashMap<>();
    completeVars.putAll(allVars); // 局部变量升级为全局
    completeVars.put("approve", true);
    // taskService.complete(taskId, completeVars);
```

## 三、流程任务的完整生命周期（从创建到历史，全程梳理）

流程任务的生命周期由**引擎自动创建**开始，到**人工处理完成/删除**结束，全程联动TaskService和RuntimeService，无人工干预的情况下，任务会按BPMN规则依次创建、处理、流转，最终进入历史表。

### 标准生命周期（无重新分配，正常处理）

流程实例运行到`userTask`节点 → **引擎自动创建任务**（ACT_RU_TASK生成记录，分配处理人/候选人） → 任务进入**待处理状态**（已认领：assignee≠null；未认领：candidateUser/Group有值） → 人工**认领任务**（仅未认领任务） → 人工**处理任务**（添加批注、设置变量） → 人工**完成任务** → 引擎**清理运行时任务数据**，迁移到ACT_HI_TASKINST → 引擎自动推进流程实例到下一个节点 → 任务生命周期结束（可通过HistoryService查询）。

### 含重新分配的生命周期（委派/转办/释放）

引擎创建任务 → 待处理状态 → 人工**认领** → 因特殊原因**释放/委派/转办** → 新用户**认领** → 处理并**完成**任务 → 迁移到历史表 → 生命周期结束。

### 各阶段核心Service联动

| 任务生命周期阶段 | 核心操作               | 负责Service       | 数据存储状态               |
|------------------|------------------------|-------------------|----------------------------|
| 任务创建         | 引擎自动生成，分配处理人/候选人 | Flowable引擎      | ACT_RU_TASK/ACT_RU_IDENTITYLINK新增记录 |
| 任务待处理       | 查询、认领、释放       | TaskService       | ACT_RU_TASK（运行时，assignee=null/≠null） |
| 任务重新分配     | 委派、转办、归还       | TaskService       | ACT_RU_TASK/ACT_RU_IDENTITYLINK更新记录 |
| 任务处理         | 添加批注、设置变量     | TaskService       | ACT_RU_COMMENT/ACT_RU_VARIABLE新增记录 |
| 任务完成         | 提交结果，推进流程     | TaskService       | ACT_RU_TASK记录删除，ACT_HI_TASKINST新增快照 |
| 任务历史追溯     | 查询历史任务/批注/变量 | HistoryService    | ACT_HI_TASKINST/ACT_HI_COMMENT/ACT_HI_VARINST永久存储 |

## 四、流程任务实战核心避坑点（生产环境高频，必守规则）

结合大量企业实战经验，整理了流程任务相关的**10个高频坑点**，覆盖**查询、认领、完成、分配、变量**全流程，严格遵守可避免90%的生产环境问题，其中**任务完成的事务、批注、变量**是新手最容易踩的核心坑点。

### 1. 完成任务未加@Transactional，导致脏数据

- **坑点**：任务完成操作未放在事务中，若中间步骤（如变量更新、流程推进）出现异常，会导致**任务已完成但流程未推进**，或**批注已保存但任务未完成**；
- **解决方案**：所有任务的**写操作**（完成、委派、转办、设置变量、添加批注）必须放在**@Transactional**注解的方法中，事务传播行为使用默认的`REQUIRED`。

### 2. 完成任务不加批注，导致审计追溯无依据

- **坑点**：为了开发便捷，完成任务时不添加批注，尤其是审批驳回、异常处理时，无任何处理原因，后续审计无法追溯；
- **解决方案**：**强制要求所有任务完成时必须添加批注**，前端做非空校验，后端做拦截，禁止空批注提交，批注内容需包含**处理结果+原因**（如“同意请假3天，本年度剩余年假充足”）。

### 3. 认领/完成任务前未做权限校验，导致越权操作

- **坑点**：未校验当前用户是否为任务的**候选人/已认领人**，直接执行认领/完成操作，导致越权处理他人任务，引发业务混乱；
- **解决方案**：**所有任务操作前必须做3层前置校验**：
  1. 任务是否存在且为**激活状态**；
  2. 认领操作：当前用户是否为**候选人/候选组**；
  3. 完成/释放/转办操作：当前用户是否为**任务的已认领人**。

### 4. 混淆委派和转办，导致任务所有权混乱

- **坑点**：将需要永久分配的任务用**委派**实现，被委派用户处理后无法直接完成，需归还原用户，导致流程卡顿；
- **解决方案**：明确二者使用场景，**生产环境优先使用转办（setAssignee）**：
  - 临时代处理、需原用户最终确认 → 用**委派**（delegateTask+resolveTask）；
  - 永久分配、业务归属变更、无需原用户确认 → 用**转办**（setAssignee）。

### 5. 流程变量和任务变量混用，污染全局数据

- **坑点**：将任务处理的**临时数据、中间状态**存入流程全局变量，导致全局变量冗余，甚至出现变量名冲突，影响后续节点流转；
- **解决方案**：**临时数据用任务局部变量**（TaskService），**全局共享的业务数据用流程全局变量**（RuntimeService），任务完成时，仅将需要全局共享的局部变量升级为全局变量。

### 6. 重复完成任务，导致流程实例异常

- **坑点**：前端未做防重处理，用户多次点击“提交”按钮，导致**同一任务被多次完成**，引擎重复推进流程实例，出现节点跳过、数据错乱；
- **解决方案**：
  1. 前端：添加**按钮防重**（点击后置灰，禁止重复提交）；
  2. 后端：通过**分布式锁**（如Redis锁），以`taskId`为锁标识，操作前加锁，完成后释放锁。

### 7. 任务分配硬编码，未使用动态分配

- **坑点**：在BPMN中硬编码任务处理人（如`<flowable:assignee>lisi</flowable:assignee>`），导致所有流程实例的该任务都由李四处理，无法适配“不同部门的审批由不同经理处理”的实际业务；
- **解决方案**：使用**UEL表达式**通过**流程变量动态分配**处理人/候选人/候选组，示例：

  ```xml
  <!-- 动态分配处理人 -->
  <flowable:assignee>${managerId}</flowable:assignee>
  <!-- 动态分配候选组 -->
  <flowable:candidateGroups>${deptManagerGroup}</flowable:candidateGroups>
  ```

  启动实例/完成任务时传入对应变量即可。

### 8. 多租户场景未做任务隔离，导致数据泄露

- **坑点**：多租户系统中，查询/处理任务时未指定`tenantId`，导致不同租户的任务相互混淆，A租户能看到/处理B租户的任务，引发数据泄露；
- **解决方案**：多租户场景下，**所有任务操作必须指定tenantId**：

  ```java
  // 多租户查询任务
  taskService.createTaskQuery().tenantId("tenant1").assignee("zhangsan").list();
  // 多租户完成任务（Flowable 6.7+支持）
  taskService.complete(taskId, variables, "tenant1");
  ```

### 9. 直接操作任务运行时表，导致引擎状态混乱

- **坑点**：为了开发便捷，直接通过SQL修改ACT_RU_TASK表的字段（如修改assignee、suspensionState），跳过Flowable的原生校验，导致引擎内部状态混乱，任务处理时抛异常；
- **解决方案**：**禁止直接操作Flowable的运行时表**，所有任务操作必须通过**TaskService的原生API**实现，Flowable会自动维护表的关联关系和状态。

### 10. 忽略任务超时，未做超时提醒/处理

- **坑点**：未对任务做超时管控，部分任务长期无人处理，导致流程实例卡顿，业务无法推进；
- **解决方案**：
  1. 在BPMN中为`userTask`添加**定时边界事件**，设置超时时间，超时后自动触发提醒（如发邮件/短信）或自动处理（如驳回/转办）；
  2. 后端开发**定时任务**，扫描ACT_RU_TASK表，对超时未处理的任务进行预警/自动转办。

## 五、核心总结

1. **流程任务仅指userTask**：是Flowable引擎与人工交互的唯一节点，自动任务（serviceTask/scriptTask）由引擎自行处理，无对应Task；
2. **TaskService是唯一核心Service**：任务的查询、认领、完成、委派、转办、批注等所有操作均通过TaskService实现，是企业业务开发中使用频率最高的Service之一；
3. **任务完成是核心操作**：完成时必须**加事务、带变量、添批注**，三者缺一不可，完成后引擎自动推进流程实例，无需手动干预；
4. **前置校验是必做动作**：所有任务操作前必须校验**任务存在、状态激活、当前用户有权限**，避免越权、重复、无效操作；
5. **委派≠转办**：委派是临时代处理，需归还；转办是永久分配，无需归还，生产环境优先使用转办；
6. **变量分全局/局部**：流程全局变量（RuntimeService）用于共享业务数据，任务局部变量（TaskService）用于存储临时数据，避免混用污染全局；
7. **任务完成后进入历史表**：运行时数据被清理，历史数据永久存储在ACT_HI_TASKINST，审计追溯通过HistoryService实现；
8. **多租户/高并发需做特殊处理**：多租户必须指定tenantId隔离，高并发需做防重处理（分布式锁），避免重复完成任务。
