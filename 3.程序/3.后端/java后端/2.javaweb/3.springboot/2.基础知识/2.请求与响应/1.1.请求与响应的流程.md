# 请求与响应的流程

## 一、请求与响应完整处理链路（原子级步骤拆解）

以「客户端调用`GET http://localhost:8080/api/user/1`查询用户」为例，完整链路分为**12个核心步骤**，包含「正常流程（缓存命中/未命中）」和「异常流程」两个分支：

### 阶段1：客户端请求发起（链路起点）

1. **客户端构造并发送HTTP请求**
   - 客户端（浏览器/Postman/前端代码）发起GET请求，携带：
     - 请求行：`GET /api/user/1 HTTP/1.1`（请求方法、路径、协议版本）；
     - 请求头：`Host: localhost:8080`、`Accept: application/json`（期望返回JSON）等；
     - 无请求体（GET方法默认无请求体）。
   - 客户端通过TCP协议建立与服务器8080端口的连接，发送HTTP数据包。

### 阶段2：服务器端请求接收（Tomcat容器层）

2. **嵌入式Tomcat处理请求**
   - Spring Boot内置的Tomcat容器通过`Connector`组件监听8080端口，接收TCP连接和HTTP数据包；
   - Tomcat的`ProtocolHandler`解析HTTP协议，将原始数据包封装为**标准的`HttpServletRequest`对象**（包含路径参数`id=1`、请求方法GET、请求头等信息）和`HttpServletResponse`对象（用于封装响应）；
   - Tomcat将`HttpServletRequest`/`HttpServletResponse`传递给Spring MVC的核心入口`DispatcherServlet`。

### 阶段3：Spring MVC核心分发（前端控制器层）

3. **DispatcherServlet（前端控制器）接收请求**
   - `DispatcherServlet`是Spring MVC的“总入口”，所有请求都经过它分发，核心作用是“解耦请求与处理逻辑”；
   - 首先调用`HandlerMapping`组件匹配请求映射。

4. **HandlerMapping匹配Controller方法**
   - `HandlerMapping`（默认`RequestMappingHandlerMapping`）扫描所有标注`@RequestMapping`/`@GetMapping`的Controller方法，根据「请求路径`/user/1`+请求方法GET」匹配到`UserController.getUserById(Long id)`方法；
   - 返回包含该方法信息的`HandlerExecutionChain`（包含Controller方法、拦截器等）给`DispatcherServlet`。

5. **HandlerAdapter适配并解析参数**
   - `DispatcherServlet`调用`HandlerAdapter`（默认`RequestMappingHandlerAdapter`）适配执行Controller方法；
   - `HandlerAdapter`执行核心操作：
     ① 解析请求参数：识别`@PathVariable("id")`注解，从`HttpServletRequest`中提取路径参数`1`，转换为Long类型；
     ② 执行参数校验：检测到`@Validated`和`@Positive`注解，校验`id=1`是否为正整数（校验通过）；
     ③ 若参数校验失败，直接抛出`BindException`异常，进入「异常流程」。

### 阶段4：业务逻辑处理（Controller→Service→Redis/数据库）

6. **Controller层接收并转发请求**
   - `HandlerAdapter`调用`UserController.getUserById(1)`方法：
     - `@RestController`注解确保方法返回值会被转为JSON（而非视图）；
     - Controller层仅做“请求接收+结果封装”，不处理业务逻辑，直接调用`UserService.getUserById(1)`。

7. **Service层处理核心业务（缓存+数据库）**
   - `@Service`注解确保`UserService`已被Spring IOC容器管理，可通过`@RequiredArgsConstructor`注入`UserMapper`；
   - 触发`@Cacheable`注解的核心逻辑（Spring Cache拦截器执行）：
     ① **缓存命中分支**：
        - 根据`cacheNames="user"`+`key="#id"`生成缓存Key：`demo:user:1`（`demo:`是配置的key前缀）；
        - 访问Redis，查询Key=`demo:user:1`是否存在；
        - 若存在，直接返回Redis中的User缓存数据，跳过数据库查询，进入「结果返回流程」。
     ② **缓存未命中分支**：
        - 执行`getUserById`方法体：先校验`id=1`（非空且>0，校验通过）；
        - 调用`UserMapper.selectById(1)`，发起数据库查询；
        - MyBatis执行SQL：`SELECT id, user_name, age, email FROM user WHERE id = 1`；
        - 数据库返回查询结果，MyBatis将结果映射为`User`实体（下划线`user_name`转驼峰`userName`）；
        - 检测到`user!=null`（`unless="#result == null"`），将`User`对象序列化后写入Redis，设置过期时间1小时；
        - 返回`User`对象给Controller层。

8. **Mapper层操作数据库（MyBatis）**
   - `@Mapper`/`@MapperScan`注解确保`UserMapper`被MyBatis代理，生成`MapperProxy`代理对象；
   - 代理对象执行`selectById(1)`时，加载`UserMapper.xml`中的SQL，通过Spring管理的数据源（HikariCP）获取数据库连接；
   - 执行SQL并将结果集映射为`User`对象，关闭数据库连接（连接池回收）。

### 阶段5：响应封装与返回（正向流程）

9. **Controller层封装统一响应**
   - `UserController`接收`UserService`返回的`User`对象，通过`Result.success(user)`封装为统一响应体：

     ```json
     {
       "code": 200,
       "msg": "操作成功",
       "data": {"id":1,"userName":"张三","age":25,"email":"zhangsan@test.com"}
     }
     ```

10. **DispatcherServlet处理响应**
    - `DispatcherServlet`接收Controller返回的`Result`对象，调用`HttpMessageConverter`（默认`MappingJackson2HttpMessageConverter`）将`Result`对象序列化为JSON字符串；
    - 将JSON字符串写入`HttpServletResponse`的响应体，设置响应头`Content-Type: application/json;charset=UTF-8`。

11. **Tomcat返回响应给客户端**
    - Tomcat将`HttpServletResponse`中的响应数据转为HTTP数据包，通过TCP连接返回给客户端；
    - 关闭TCP连接（或复用，基于HTTP Keep-Alive）。

### 阶段6：异常流程（任意环节抛出异常）

12. **全局异常处理器捕获并处理异常**
    - 若链路中任意环节抛出异常（如参数校验失败、用户不存在、数据库连接失败）：
      ① 异常抛至`DispatcherServlet`，被`@RestControllerAdvice`标注的`GlobalExceptionHandler`捕获；
      ② 根据异常类型匹配对应的`@ExceptionHandler`方法（如`BusinessException`→`handleBusinessException`）；
      ③ 封装为异常响应体（如`{"code":404,"msg":"用户不存在","data":null}`）；
      ④ 按正向流程返回JSON响应给客户端。

## 三、关键链路节点补充说明（易忽略的核心细节）

1. **缓存注解的执行时机**：
   - `@Cacheable`是**先查缓存，后执行方法体**：若缓存命中，直接返回缓存数据，方法体不会执行；若未命中，执行方法体后将结果写入缓存。
   - 缓存Key的生成规则：默认Key = `缓存名称::SimpleKey[参数列表]`，指定`key="#id"`后，Key = `缓存名称::id值`（如`user::1`）。

2. **参数校验的执行顺序**：
   - `@Validated`触发的参数校验在**Controller方法执行前**（由`HandlerAdapter`执行），若校验失败，直接抛出异常，不会进入方法体。
   - `@RequestBody`参数的校验需配合`@Valid`/`@Validated`，否则校验注解（如`@NotBlank`）不生效。

3. **异常捕获的优先级**：
   - `@ExceptionHandler`按“异常类型精准度”匹配：先匹配自定义异常（如`BusinessException`），再匹配通用异常（如`Exception`）。
   - 若未匹配到对应的`@ExceptionHandler`，会触发兜底的`Exception.class`处理方法。

4. **数据库连接的管理**：
   - Spring Boot默认使用HikariCP连接池，`@Service`调用`Mapper`时，MyBatis从连接池获取连接，执行SQL后归还连接（而非关闭），提升性能。

## 四、总结

1. **完整链路核心逻辑**：
   客户端请求 → Tomcat解析HTTP → DispatcherServlet分发 → HandlerMapping匹配Controller → HandlerAdapter解析参数/校验 → Controller调用Service → Service查Redis（命中则返回，未命中则查数据库→写Redis） → Controller封装响应 → DispatcherServlet序列化JSON → Tomcat返回响应；异常则由`@RestControllerAdvice`统一处理。

2. **注解的核心价值**：
   所有注解的本质是“简化配置、解耦逻辑、标准化流程”——如`@RestController`简化JSON响应配置，`@Cacheable`简化缓存逻辑，`@RestControllerAdvice`简化异常处理，避免重复编写通用代码。

3. **最佳实践**：
   - 统一响应体+全局异常处理，确保所有接口返回格式一致；
   - 查询方法必加`@Cacheable`，更新/删除方法加`@CacheEvict`（清空缓存），保证缓存一致性；
   - 参数校验覆盖所有入参，避免脏数据进入业务层；
   - 用`final+@RequiredArgsConstructor`替代`@Autowired`，提升依赖注入安全性。

   - 调用`HandlerAdapter`组件适配执行Controller方法；
   - 处理响应结果或异常。

   `HandlerMapping`扫描所有标注`@RequestMapping`/`@GetMapping`的Controller方法，根据「请求路径`/user/1`+请求方法GET」匹配到`UserController.getUserById(Long id)`方法，返回包含该方法信息的`HandlerExecutionChain`（含方法对象、拦截器等）。

   - **缓存查询**：触发`@Cacheable`注解，Spring Cache拦截器先执行缓存逻辑：

        - **缓存命中**：直接返回Redis中的User序列化数据，跳过数据库查询；
        - **缓存未命中**：执行方法体逻辑。
   - **业务校验**：校验`id=1`是否为正整数（通过，失败则抛`BusinessException`）；
   - **数据库查询**：调用`UserMapper.selectById(1)`，发起数据库请求；

   - MyBatis将数据库返回的结果集映射为User实体（下划线`user_name`转驼峰`userName`）；
   - 关闭数据库连接（连接池回收，非真正关闭），返回User对象给Service层。

### 阶段5：响应封装与返回（正向流程）

9. **Controller层封装统一响应**
   `UserController`接收Service返回的User对象，通过`Result.success(user)`封装为统一响应体：

   ```json
   {
     "code": 200,
     "msg": "操作成功",
     "data": {"id":1,"userName":"张三","age":25,"email":"zhangsan@test.com"}
   }
   ```

10. **DispatcherServlet序列化响应**
    `DispatcherServlet`调用`HttpMessageConverter`（默认`MappingJackson2HttpMessageConverter`），将`Result`对象序列化为JSON字符串，写入`HttpServletResponse`的响应体，设置响应头`Content-Type: application/json;charset=UTF-8`。

11. **Tomcat返回响应给客户端**
    Tomcat将`HttpServletResponse`中的JSON响应转为HTTP数据包，通过TCP连接返回给客户端，完成一次请求-响应闭环。

### 阶段6：异常流程（任意环节抛异常）

12. **全局异常处理器捕获并处理异常**
    若链路中任意环节抛异常（如参数校验失败、用户不存在、数据库连接失败）：
    - 异常逐层抛至`DispatcherServlet`，被`@RestControllerAdvice`标注的`GlobalExceptionHandler`捕获；
    - 根据异常类型匹配对应的`@ExceptionHandler`方法（如`BusinessException`→`handleBusinessException`）；
    - 封装为异常响应体（如`{"code":404,"msg":"用户不存在","data":null}`）；
    - 按正向流程返回JSON响应给客户端。

## 二、全链路核心注解深度解析（作用+底层逻辑+使用场景）

按“链路执行顺序”拆解所有核心注解，说明每个注解在链路中的**具体作用**、**关键属性**和**底层实现**，确保覆盖“Controller→Service→Redis→数据库”全环节：

| 注解层级       | 注解名称                | 核心作用（链路中角色）                                                                 | 关键属性/底层逻辑                                                                 | 必知使用细节                                                                 |
|----------------|-------------------------|----------------------------------------------------------------------------------------|----------------------------------------------------------------------------------|------------------------------------------------------------------------------|
| 启动类         | `@SpringBootApplication` | 应用启动核心注解，整合3大能力：<br>1. `@Configuration`：标记启动类为配置类，可定义Bean；<br>2. `@EnableAutoConfiguration`：开启自动配置（如Redis、数据源、MVC）；<br>3. `@ComponentScan`：扫描Bean并注册到IOC容器 | 无显式属性，底层通过`SpringFactoriesLoader`加载自动配置类（如`RedisAutoConfiguration`） | 必须加在启动类上，是Spring Boot“约定优于配置”的核心体现                     |
| 启动类         | `@MapperScan`           | 批量扫描Mapper接口，自动生成MyBatis代理对象，替代单个`@Mapper`                           | `basePackages`：指定扫描路径（如`com.demo.mapper`）；<br>底层通过`MapperScannerConfigurer`注册代理 | 项目中Mapper数量>3个时优先用，避免重复加`@Mapper`                           |
| 启动类         | `@EnableCaching`        | 开启Spring Cache框架，使`@Cacheable`等缓存注解生效                                      | 底层注册`CacheInterceptor`拦截器，在Service方法执行前后处理缓存                  | 需配合Redis/本地缓存使用，仅注解无缓存实现时会报错                           |
| Controller层   | `@RestController`       | 组合注解：`@Controller`（注册为Bean）+ `@ResponseBody`（返回值序列化JSON）                 | 底层通过`RequestResponseBodyMethodProcessor`处理返回值序列化                      | 前后端分离项目必用，替代传统`@Controller`+方法级`@ResponseBody`              |
| Controller层   | `@GetMapping`           | 仅匹配GET请求的简化映射注解，等价于`@RequestMapping(method=RequestMethod.GET)`           | `value`：URL路径（如`/user/{id}`）；<br>支持`produces`指定响应格式                 | 查询类接口（查详情、查列表）必用，语义更清晰                                 |
| Controller层   | `@PathVariable`         | 绑定URL路径参数到方法参数（如`/user/{id}`→`Long id`）                                   | `value`：路径占位符名称（参数名与占位符一致时可省略）；<br>底层通过`PathVariableMethodArgumentResolver`解析 | 路径含动态值时使用，GET/DELETE请求常用                                       |
| Controller层   | `@Validated`            | 开启方法参数校验，触发`@Positive`/`@NotBlank`等校验注解                                   | 支持`groups`分组校验（如新增/更新用不同规则）；<br>底层通过`Hibernate Validator`执行校验 | 必须加在Controller类上，否则`@Positive`等注解不生效                           |
| Service层      | `@Service`              | 标记为服务层Bean，注册到IOC容器，支持依赖注入                                            | `value`：指定Bean名称（默认类名首字母小写）；<br>底层通过`ComponentScan`扫描注册    | 所有业务逻辑类必加，封装核心业务、调用Mapper、处理缓存                       |
| Service层      | `@Cacheable`            | 缓存方法返回值，优先查缓存，未命中则执行方法体并写入缓存                                  | `cacheNames`：缓存名称；<br>`key`：缓存Key（SpEL表达式）；<br>`unless`：不缓存条件 | 仅用于查询方法，更新/删除方法需用`@CacheEvict`清空缓存                       |
| Service层      | `@RequiredArgsConstructor` | Lombok注解，生成`final`属性的构造方法，替代`@Autowired`注入                              | 底层生成构造方法，Spring通过构造方法注入依赖（更安全）                             | 注入Mapper/Service时，用`final`+该注解，避免空指针                           |
| Mapper层       | `@Mapper`               | 标记为MyBatis Mapper接口，自动生成代理对象                                               | 底层通过`MapperFactoryBean`创建`MapperProxy`代理，执行SQL时调用MyBatis核心逻辑     | 单个Mapper接口使用，项目中Mapper少用更便捷                                   |
| 异常处理层     | `@RestControllerAdvice` | 全局异常处理器，拦截所有`@RestController`的异常，返回JSON响应                             | `basePackages`：指定仅处理某包下的异常；<br>底层通过`ExceptionHandlerExceptionResolver`注册 | 必加，保证所有接口异常返回格式一致                                           |
| 异常处理层     | `@ExceptionHandler`     | 捕获指定类型的异常，自定义响应逻辑                                                      | 参数为异常类型（如`BusinessException.class`）；<br>按异常类型精准匹配              | 按异常类型分类处理（业务异常/系统异常/参数异常）                             |
| 实体类         | `@Data`                 | Lombok注解，自动生成`get/set/toString`等方法                                             | 编译期生成字节码，不影响运行时性能                                               | 所有实体类必用，简化代码，避免手动编写重复方法                               |

## 三、链路核心细节补充（易踩坑点）

1. **缓存注解执行逻辑**：
   - `@Cacheable`是“先查缓存，后执行方法”：缓存命中时，方法体**不会执行**（包括数据库查询）；
   - 缓存Key默认生成规则：`缓存名称::SimpleKey[参数列表]`，指定`key="#id"`可简化为`user::1`。

2. **参数校验生效条件**：
   - `@PathVariable`/`@RequestParam`的校验需加`@Validated`在Controller类上；
   - `@RequestBody`参数的校验需加`@Valid`/`@Validated`在参数前（如`@Valid @RequestBody User user`）。

3. **异常捕获优先级**：
   - 先匹配自定义异常（如`BusinessException`），再匹配通用异常（如`Exception`）；
   - 未匹配到的异常会触发兜底的`Exception.class`处理方法。

## 四、总结

1. **核心链路逻辑**：
   客户端请求 → Tomcat解析 → DispatcherServlet分发 → Controller接收/校验 → Service查Redis（命中则返回，未命中查数据库→写Redis） → Controller封装响应 → Tomcat返回JSON；异常则由全局异常处理器统一处理。

2. **注解核心价值**：
   所有注解的本质是“简化配置、解耦逻辑”——如`@RestController`简化JSON响应，`@Cacheable`简化缓存逻辑，`@RestControllerAdvice`简化异常处理，避免重复编写通用代码。

3. **最佳实践**：
   - 统一响应体+全局异常处理，确保接口返回格式一致；
   - 查询方法加`@Cacheable`，更新/删除方法加`@CacheEvict`，保证缓存一致性；
   - 参数校验覆盖所有入参，避免脏数据进入业务层；
   - 用`final+@RequiredArgsConstructor`替代`@Autowired`，提升依赖注入安全性。
