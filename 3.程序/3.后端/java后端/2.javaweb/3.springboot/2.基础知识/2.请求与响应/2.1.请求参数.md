# 请求参数

Spring Boot中**不同类型请求参数的配置、处理逻辑**，并精准指出开发中高频出现的**坑点**和必须注意的**关键事项**，覆盖路径参数、查询参数、请求体参数等所有核心参数类型，结合实际代码案例说明问题场景和解决方案。

## 一、核心请求参数类型：配置与处理（分类型详解）

### 1. 路径参数（@PathVariable）

#### （1）配置与处理逻辑

路径参数是URL路径中的动态值（如`/user/1`中的`1`），核心通过`@PathVariable`绑定，适用于**标识资源唯一性**的场景（如查详情、删数据）。

- **基础配置**：

  ```java
  // 路径：/api/user/1 → 绑定id=1
  @GetMapping("/user/{id}")
  public Result<User> getUserById(@PathVariable Long id) { ... }
  ```

- **多参数配置**：

  ```java
  // 路径：/api/user/1/张三 → 绑定id=1，name=张三
  @GetMapping("/user/{id}/{name}")
  public Result<User> getUser(
          @PathVariable Long id, 
          @PathVariable String name) { ... }
  ```

- **非必传配置**（Spring 5.3+支持）：

  ```java
  // 路径：/api/user 或 /api/user/1 都可访问
  @GetMapping({"/user", "/user/{id}"})
  public Result<User> getUser(@PathVariable(required = false) Long id) { ... }
  ```

- **类型转换**：Spring自动将路径字符串转为指定类型（如`"1"`→`Long`）。

#### （2）高频坑点

| 坑点描述 | 案例 | 解决方案 |
|----------|------|----------|
| 参数名与路径占位符不匹配 | 路径是`/user/{uid}`，参数是`@PathVariable Long id`（未指定value） | ① 显式指定`value`：`@PathVariable("uid") Long id`；② 确保参数名与占位符一致（编译时开启`-parameters`参数，避免Lombok/编译优化导致参数名丢失） |
| 类型转换失败 | 路径是`/user/abc`，参数是`Long id` | ① 增加参数校验（如`@Positive`）；② 捕获`TypeMismatchException`，返回友好提示（如“用户ID必须为数字”） |
| 空值/非法值处理 | 路径是`/user/0`，参数是`Long id`，业务要求ID>0 | ① 用`@Positive(message = "ID必须为正整数")`校验；② 业务层二次校验，抛`BusinessException` |
| 中文路径参数乱码 | 路径是`/user/张三`，接收后是乱码 | ① 配置Tomcat编码：`server.tomcat.uri-encoding=UTF-8`；② 前端传递时URL编码（如`encodeURI("/user/张三")`） |

#### （3）注意点

- 路径参数仅适用于**短、无特殊字符**的参数（如ID、编码），不适合长文本（如备注）；
- 路径参数的语义要清晰（如`/user/{id}`表示“单个用户”，`/user/list`表示“用户列表”），避免滥用（如`/user/{name}/{age}/{email}`）；
- 非必传路径参数需配合多路径映射（`@GetMapping({"/user", "/user/{id}"})`），否则会报404。

### 2. 查询参数（@RequestParam）

#### （1）配置与处理逻辑

查询参数是URL中`?`后的键值对（如`/user/list?name=张三&page=1`），适用于**筛选、分页、条件查询**场景。

- **基础配置**：

  ```java
  // 请求：/api/user/list?name=张三 → name=张三
  @GetMapping("/user/list")
  public Result<List<User>> getUserList(@RequestParam String name) { ... }
  ```

- **非必传+默认值**：

  ```java
  // 请求：/api/user/list → pageNum=1，pageSize=10；请求：/api/user/list?pageNum=2 → pageNum=2
  @GetMapping("/user/list")
  public Result<List<User>> getUserList(
          @RequestParam(required = false) String name, // 非必传，默认null
          @RequestParam(defaultValue = "1") Integer pageNum, // 默认值1
          @RequestParam(defaultValue = "10") Integer pageSize) { ... }
  ```

- **多值参数（数组/集合）**：

  ```java
  // 请求：/api/user/list?ids=1&ids=2&ids=3 → ids=[1,2,3]
  @GetMapping("/user/list")
  public Result<List<User>> getUserList(@RequestParam List<Long> ids) { ... }
  ```

#### （2）高频坑点

| 坑点描述 | 案例 | 解决方案 |
|----------|------|----------|
| 默认值类型不匹配 | `@RequestParam(defaultValue = "1") Long pageNum` 正常，但`@RequestParam(defaultValue = "abc") Integer pageNum` | 默认值必须与参数类型兼容（如Integer类型默认值只能是数字字符串），启动时会直接报错，需严格匹配类型 |
| 多值参数接收错误 | 前端传`ids=1,2,3`，后端用`List<Long> ids`接收，结果是`["1,2,3"]`而非`[1,2,3]` | ① 前端改为多参数传递（`ids=1&ids=2`）；② 后端手动拆分：`String[] split = idsStr.split(",");` |
| 必传参数缺失 | `@RequestParam String name`，前端未传name，报400错误 | ① 非必传参数设置`required = false`；② 必传参数需在前端做非空校验，后端加`@NotBlank`校验 |
| 空字符串参数处理 | 前端传`name=`（空字符串），后端接收为`""`，业务误判为“无参数” | 后端统一处理：`if (StringUtils.isBlank(name)) { name = null; }`（用`org.springframework.util.StringUtils`） |
| 布尔类型参数解析错误 | 前端传`enabled=true`，后端用`Boolean enabled`接收正常；但传`enabled=1`，接收为`null` | ① 统一约定布尔参数值为`true/false`（而非1/0）；② 后端手动转换：`Boolean enabled = "1".equals(enabledStr) ? true : "0".equals(enabledStr) ? false : null;` |

#### （3）注意点

- 查询参数名建议用**小写+下划线**（如`page_num`）或**小驼峰**（如`pageNum`），前后端保持一致；
- 分页参数（pageNum/pageSize）必须设置默认值，避免前端未传导致空指针；
- 多值参数优先用`List`接收（而非数组），便于后续流式处理；
- 敏感参数（如密码）禁止通过查询参数传递（URL会被日志/浏览器记录）。

### 3. 请求体参数（@RequestBody）

#### （1）配置与处理逻辑

请求体参数是POST/PUT请求中`Content-Type: application/json`的JSON数据，适用于**新增、更新**等传递复杂对象的场景。

- **基础配置**：

  ```java
  // 前端传JSON：{"name":"张三","age":25} → 绑定到User对象
  @PostMapping("/user")
  public Result<User> addUser(@RequestBody User user) { ... }
  ```

- **嵌套对象配置**：

  ```java
  // 实体类：User包含Address属性
  @Data
  public class User {
      private String name;
      private Address address; // 嵌套对象
  }
  @Data
  public class Address {
      private String province;
      private String city;
  }
  // 前端传JSON：{"name":"张三","address":{"province":"北京","city":"北京"}}
  ```

- **集合配置**：

  ```java
  // 前端传JSON数组：[{"name":"张三"},{"name":"李四"}]
  @PostMapping("/user/batch")
  public Result<Void> batchAdd(@RequestBody List<User> userList) { ... }
  ```

- **日期类型配置**：

  ```java
  // 实体类日期字段，配置Jackson序列化/反序列化
  @Data
  public class User {
      @JsonFormat(pattern = "yyyy-MM-dd", timezone = "GMT+8")
      private LocalDate createTime;
  }
  // 前端传：{"createTime":"2024-01-01"}
  ```

#### （2）高频坑点

| 坑点描述 | 案例 | 解决方案 |
|----------|------|----------|
| GET请求使用@RequestBody | `@GetMapping("/user")` + `@RequestBody User user` | GET请求无请求体，会报`HttpMessageNotReadableException`；改为POST/PUT，或用查询参数传递 |
| 多个@RequestBody参数 | `public Result<User> addUser(@RequestBody User user, @RequestBody Address address)` | HTTP请求只有一个请求体，不支持多个`@RequestBody`；合并为一个DTO（如`UserAddDTO`包含User+Address） |
| JSON格式错误导致解析失败 | 前端传JSON少逗号：`{"name":"张三" "age":25}` | ① 前端校验JSON格式；② 后端捕获`JsonParseException`，返回“请求参数格式错误” |
| 字段类型不匹配 | 前端传`age:"25"`（字符串），后端User的age是Integer | ① 前端统一传对应类型（数字25）；② 后端配置Jackson兼容：`@JsonFormat(shape = JsonFormat.Shape.STRING)`（数字转字符串） |
| 下划线/驼峰映射失败 | 前端传`user_name:"张三"`，后端User的userName为null | ① 配置全局下划线转驼峰：`spring.jackson.property-naming-strategy=SNAKE_CASE`；② 实体类字段加`@JsonProperty("user_name")` |
| 必传字段缺失 | 前端传`{"age":25}`，后端User的name是必传但缺失 | ① 实体类加校验注解：`@NotBlank(message = "姓名不能为空")`；② 后端捕获`MethodArgumentNotValidException`，返回具体缺失字段 |

#### （3）注意点

- 仅POST/PUT/PATCH支持`@RequestBody`，GET/DELETE禁止使用；
- 复杂对象优先用DTO接收（而非直接用数据库实体类），避免暴露多余字段；
- 空值处理：前端传`null`或不传字段，后端实体类对应字段为`null`，需在业务层判断非空；
- 敏感字段（如密码）需在接收后加密（如MD5/Bcrypt），禁止明文存储/传输。

### 4. 表单参数（application/x-www-form-urlencoded）

#### （1）配置与处理逻辑

表单参数是`Content-Type: application/x-www-form-urlencoded`的键值对，适用于**简单表单提交**场景（如登录）。

- **单个参数配置**：

  ```java
  // 前端表单：username=admin&password=123456
  @PostMapping("/login")
  public Result<String> login(
          @RequestParam String username,
          @RequestParam String password) { ... }
  ```

- **实体类配置**：

  ```java
  // 直接绑定到实体类（参数名与实体属性一致）
  @PostMapping("/login")
  public Result<String> login(UserLoginDTO dto) { ... }
  ```

#### （2）高频坑点

| 坑点描述 | 案例 | 解决方案 |
|----------|------|----------|
| Content-Type不匹配 | 前端传`application/json`，后端按表单参数接收 | ① 前后端统一Content-Type；② 表单参数用`application/x-www-form-urlencoded`，JSON用`application/json` |
| 中文表单参数乱码 | 前端传中文用户名，后端接收乱码 | ① 配置全局编码：`spring.http.encoding.force=true`；② Tomcat编码：`server.tomcat.uri-encoding=UTF-8` |
| 大表单参数截断 | 表单参数过多/过长，后端接收不全 | 配置Tomcat最大参数长度：`server.tomcat.max-http-post-size=10MB` |

#### （3）注意点

- 表单参数不支持嵌套对象（如User包含Address），复杂对象改用JSON请求体；
- 文件上传需用`Content-Type: multipart/form-data`，而非`application/x-www-form-urlencoded`；
- 密码等敏感表单参数需加密传输（如HTTPS），避免抓包泄露。

### 5. 请求头/Cookie参数（@RequestHeader/@CookieValue）

#### （1）配置与处理逻辑

- **请求头参数**：通过`@RequestHeader`绑定请求头中的值（如Token、Content-Type）；

  ```java
  // 获取Token：请求头Authorization: Bearer xxx
  @GetMapping("/user/info")
  public Result<User> getUserInfo(@RequestHeader("Authorization") String token) { ... }
  ```

- **Cookie参数**：通过`@CookieValue`绑定Cookie中的值；

  ```java
  // 获取Cookie：userId=123
  @GetMapping("/user/info")
  public Result<User> getUserInfo(@CookieValue("userId") String userId) { ... }
  ```

#### （2）高频坑点

| 坑点描述 | 案例 | 解决方案 |
|----------|------|----------|
| 请求头名称大小写问题 | 前端传`authorization`，后端用`@RequestHeader("Authorization")` | HTTP头信息不区分大小写，Spring自动兼容，但建议前后端统一（如`Authorization`） |
| Cookie不存在导致报错 | `@CookieValue("userId")`，但前端未传userId Cookie | 设置`required = false`：`@CookieValue(value = "userId", required = false)` |
| Token格式错误 | 前端传Token无“Bearer ”前缀，后端解析失败 | 后端先校验格式：`if (!token.startsWith("Bearer ")) { throw new BusinessException(401, "Token格式错误"); }` |

#### （3）注意点

- 敏感信息（如Token）优先放在请求头，而非Cookie（Cookie易被CSRF攻击）；
- Cookie需设置`HttpOnly`和`Secure`属性（仅HTTPS传输），防止XSS攻击；
- 请求头参数建议加非必传配置，避免前端未传导致接口报错。

### 6. 文件上传参数（@RequestParam(MultipartFile)）

#### （1）配置与处理逻辑

- **单文件上传**：

  ```java
  @PostMapping("/upload")
  public Result<String> upload(@RequestParam("file") MultipartFile file) { ... }
  ```

- **多文件上传**：

  ```java
  @PostMapping("/batchUpload")
  public Result<String> batchUpload(@RequestParam("files") List<MultipartFile> files) { ... }
  ```

- **文件大小配置**：

  ```yaml
  spring:
    servlet:
      multipart:
        max-file-size: 10MB # 单个文件最大大小
        max-request-size: 50MB # 单次请求最大文件大小
  ```

#### （2）高频坑点

| 坑点描述 | 案例 | 解决方案 |
|----------|------|----------|
| 文件大小超限 | 上传20MB文件，配置max-file-size=10MB | ① 调整配置值；② 捕获`MaxUploadSizeExceededException`，返回“文件大小超过限制” |
| 文件类型未校验 | 上传.exe文件，后端直接存储 | ① 白名单校验：只允许jpg/png/pdf等；② 校验文件后缀+Content-Type：`file.getContentType().startsWith("image/")` |
| 空文件上传 | 前端传空文件，后端处理时报错 | 先校验：`if (file.isEmpty()) { throw new BusinessException(400, "文件不能为空"); }` |
| 临时文件未清理 | 上传大量文件后，服务器临时目录占满 | ① 配置临时目录：`spring.servlet.multipart.location=/tmp/upload`；② 处理完文件后手动删除临时文件 |

#### （3）注意点

- 文件上传需用`POST`请求，且`Content-Type: multipart/form-data`；
- 避免将文件存储在服务器本地（集群环境无法共享），优先用OSS/MinIO等对象存储；
- 文件名需重命名（如UUID+后缀），避免中文/特殊字符导致路径错误，或文件名重复覆盖。

## 二、通用坑点与核心注意点（所有参数类型通用）

### 1. 通用坑点

| 坑点 | 解决方案 |
|------|----------|
| 参数校验不充分 | 仅依赖前端校验，后端无校验 | 后端必须加JSR-380校验（`@Validated`+`@NotBlank`/`@Positive`），前端校验仅为体验优化 |
| 编码不统一 | 前端UTF-8，后端GBK，导致中文乱码 | 全局配置编码为UTF-8：<br>`spring.http.encoding.charset=UTF-8`<br>`spring.http.encoding.force=true`<br>`server.tomcat.uri-encoding=UTF-8` |
| 类型转换异常 | 前端传字符串，后端用数值类型接收 | ① 前后端统一参数类型；② 后端加类型转换逻辑，捕获`TypeMismatchException` |
| 空值/空字符串混用 | 后端将`null`和`""`视为同一状态 | 统一处理：用`StringUtils.isBlank()`判断（包含`null`、空字符串、全空格） |
| 日志打印敏感参数 | 日志中打印密码、Token等 | ① 日志过滤敏感参数；② 用`***`替换敏感值（如`token.replaceAll(".", "*")`） |

### 2. 核心注意点

1. **参数校验是必选项**：无论前端是否校验，后端必须通过`@Validated`+JSR-380注解做校验，防止脏数据进入业务层；
2. **不同参数类型的适用场景**：
   - 路径参数：标识资源（如ID）；
   - 查询参数：筛选/分页；
   - 请求体参数：复杂对象（新增/更新）；
   - 表单参数：简单键值对（登录）；
   - 文件参数：仅文件上传；
3. **编码统一为UTF-8**：全链路（前端→Tomcat→Spring→数据库）编码一致，避免乱码；
4. **敏感参数保护**：密码/Token禁止通过查询参数、Cookie（无HttpOnly）传递，优先用请求头+HTTPS；
5. **异常友好提示**：参数错误时返回具体提示（如“姓名不能为空”），而非系统异常栈；
6. **接口文档对齐**：参数名、类型、必传性需在Swagger/OpenAPI中明确，前后端同步；
7. **空值处理统一**：定义接口规范（如“未传字段为null，空字符串表示空值”），前后端严格遵守。

## 三、总结

1. **参数配置核心**：不同类型参数需匹配对应的HTTP方法、Content-Type，避免“GET用@RequestBody”“表单传嵌套对象”等基础错误；
2. **坑点规避核心**：编码统一、参数校验、类型匹配、敏感参数保护是避坑的四大关键；
3. **注意点核心**：后端校验是最后一道防线，无论前端是否校验，后端必须兜底；接口语义清晰，不同参数类型用在对应场景。

通过以上配置规范和坑点规避，可大幅减少参数处理中的线上问题，保证接口的稳定性和安全性。
