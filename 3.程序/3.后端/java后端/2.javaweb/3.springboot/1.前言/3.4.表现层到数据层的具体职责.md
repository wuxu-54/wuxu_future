# `Controller → Service → Repository`

三层架构的**核心职责、具体工作内容、边界划分、典型场景和最佳实践**，明确每一层该做什么、不该做什么，避免分层混乱。

---

## 一、整体分工总览

| 层级        | 核心定位                          | 核心目标                  | 对外交互对象       |
|-------------|-----------------------------------|---------------------------|--------------------|
| Controller  | 前端交互层（门面层）             | 接收请求、返回响应        | 前端（浏览器/APP） |
| Service     | 业务逻辑层（核心层）             | 处理业务规则、事务、组装数据 | Controller         |
| Repository  | 数据访问层（持久层）             | 仅做数据库CRUD            | Service            |

---

## 二、Controller 层：前端交互的“门面”

### 核心定位

Controller 是**前端请求的入口**，也是**响应的出口**，只负责“请求/响应的处理”，不碰任何业务逻辑，相当于系统对外的“接待员”。

### 具体要做的事（仅这5件！）

#### 1. 接收前端请求

- 映射 URL 路径（如 `/api/user/list`）、请求方法（GET/POST/PUT/DELETE）；
- 接收请求参数：路径参数（`@PathVariable`）、查询参数（`@RequestParam`）、JSON 体参数（`@RequestBody`）、请求头（`@RequestHeader`）。

#### 2. 参数校验

- 对前端传入的参数做**基础合法性校验**（非空、格式、长度），比如用户名不能为空、手机号格式正确；
- 推荐用 `javax.validation` 注解（`@NotBlank`/`@Pattern`）+ 全局异常处理器统一返回校验结果。

#### 3. 调用 Service 层

- 将校验后的参数传递给 Service 层，获取业务处理结果；
- 不做任何业务逻辑（比如“判断用户是否有权限”“计算用户积分”都交给 Service）。

#### 4. 封装统一响应

- 将 Service 返回的结果封装成**统一格式的响应体**（如 `{code:200, msg:"成功", data:{...}}`）；
- 处理异常：捕获 Service 抛出的业务异常，转换成前端能理解的提示信息。

#### 5. 权限/认证前置处理（可选）

- 结合 Shiro/Spring Security 做接口级权限校验（如 `@RequiresPermissions("user:list")`）；
- 不处理“数据级权限”（比如“只能看自己部门的用户”交给 Service）。

### 典型代码示例（Jeecg Boot 风格）

```java
package com.jeecg.modules.system.controller;

import com.jeecg.common.api.vo.Result;
import com.jeecg.modules.system.entity.SysUser;
import com.jeecg.modules.system.service.ISysUserService;
import io.swagger.annotations.Api;
import io.swagger.annotations.ApiOperation;
import org.apache.shiro.authz.annotation.RequiresPermissions;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.validation.annotation.Validated;
import org.springframework.web.bind.annotation.*;

import javax.validation.constraints.NotBlank;

/**
 * Controller 层示例（仅做请求/响应处理）
 */
@Api(tags = "用户管理")
@RestController
@RequestMapping("/api/user")
public class SysUserController {

    @Autowired
    private ISysUserService sysUserService;

    /**
     * 查询单个用户（GET请求，路径参数）
     */
    @ApiOperation("查询单个用户")
    @RequiresPermissions("user:view") // 接口级权限校验（Controller 仅做这个）
    @GetMapping("/{id}")
    public Result<SysUser> getUserById(@NotBlank(message = "用户ID不能为空") @PathVariable String id) {
        try {
            // 1. 调用 Service 层（核心：只传参，不处理业务）
            SysUser user = sysUserService.getById(id);
            // 2. 封装统一响应
            return Result.ok("查询成功", user);
        } catch (Exception e) {
            // 3. 异常转换
            return Result.error("查询失败：" + e.getMessage());
        }
    }

    /**
     * 新增用户（POST请求，JSON参数）
     */
    @ApiOperation("新增用户")
    @RequiresPermissions("user:add")
    @PostMapping
    public Result<String> addUser(@Validated @RequestBody SysUser user) {
        try {
            // 1. 参数已通过 @Validated 校验，直接调用 Service
            boolean success = sysUserService.saveUser(user);
            if (success) {
                return Result.ok("新增成功");
            } else {
                return Result.error("新增失败");
            }
        } catch (Exception e) {
            return Result.error("新增失败：" + e.getMessage());
        }
    }
}
```

### Controller 层绝对不能做的事

❌ 不写业务逻辑（比如“判断用户是否重复”“计算密码加密”）；
❌ 不直接操作数据库（比如调用 Mapper/Repository）；
❌ 不处理复杂的数据组装（比如“查询用户+角色+部门”交给 Service）；
❌ 不做事务管理（事务注解 `@Transactional` 只能加在 Service 上）。

### 最佳实践

1. 所有响应统一用 `Result` 封装（Jeecg Boot 已提供 `Result` 类）；
2. 参数校验用 `@Validated` + 注解，避免手写 `if (xxx == null)`；
3. 只捕获异常并转换，不处理异常的具体逻辑；
4. 接口文档用 Swagger 注解（`@Api`/`@ApiOperation`），方便前端对接。

## 三、Service 层：业务逻辑的“核心”

### 核心定位

Service 是系统的**业务大脑**，所有业务规则、事务管理、数据组装、权限判断都在这里处理，是三层架构中最核心的一层。

### 具体要做的事（核心6件）

#### 1. 接收 Controller 传递的参数

- 接收参数后可做**业务级校验**（比如“用户名已存在”“用户积分不足”）；
- 区别于 Controller 的“基础校验”：Controller 校验“参数格式”，Service 校验“业务规则”。

#### 2. 处理核心业务逻辑

- 实现业务规则：比如“用户注册时自动分配默认角色”“下单时扣减库存+增加订单”；
- 处理数据转换：比如“将前端传入的DTO转换为数据库实体DO”“组装返回给前端的VO”。

#### 3. 事务管理

- 用 `@Transactional` 注解管理事务，确保多步数据库操作的原子性（比如“新增用户 + 新增用户角色”要么都成功，要么都失败）；
- 可配置事务传播行为（如 `@Transactional(propagation = Propagation.REQUIRED)`）。

#### 4. 数据组装/聚合

- 多表关联查询的结果组装：比如“查询用户信息 + 所属角色 + 所属部门”；
- 复杂数据计算：比如“统计用户近7天的登录次数”“计算订单总金额（商品价+运费-优惠券）”。

#### 5. 数据级权限控制

- 处理“行级权限”：比如“普通管理员只能看自己部门的用户”“超级管理员能看所有用户”；
- 结合 Shiro/Spring Security 获取当前用户，过滤数据。

#### 6. 调用 Repository 层

- 调用 Repository/Mapper 做数据库CRUD；
- 多个 Repository 调用的组合（比如“先查用户，再查角色，再查部门”）。

### 典型代码示例（Jeecg Boot 风格）

```java
package com.jeecg.modules.system.service.impl;

import com.baomidou.mybatisplus.extension.service.impl.ServiceImpl;
import com.jeecg.common.util.SpringContextUtils;
import com.jeecg.common.util.UserContextUtil;
import com.jeecg.modules.system.entity.SysUser;
import com.jeecg.modules.system.entity.SysUserRole;
import com.jeecg.modules.system.mapper.SysUserMapper;
import com.jeecg.modules.system.service.ISysUserRoleService;
import com.jeecg.modules.system.service.ISysUserService;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

/**
 * Service 层实现类（核心业务逻辑）
 */
@Service
public class SysUserServiceImpl extends ServiceImpl<SysUserMapper, SysUser> implements ISysUserService {

    @Autowired
    private ISysUserRoleService sysUserRoleService;

    /**
     * 新增用户（包含业务逻辑 + 事务）
     */
    @Override
    @Transactional(rollbackFor = Exception.class) // 事务注解（必须加在 Service）
    public boolean saveUser(SysUser user) {
        // 1. 业务级校验（Controller 做不到的）
        SysUser existUser = this.lambdaQuery().eq(SysUser::getUsername, user.getUsername()).one();
        if (existUser != null) {
            throw new RuntimeException("用户名已存在");
        }

        // 2. 业务逻辑处理：密码加密（Jeecg 自带加密工具）
        String encryptPwd = SpringContextUtils.getBean("passwordEncoder").encode(user.getPassword());
        user.setPassword(encryptPwd);
        user.setStatus("1"); // 默认启用

        // 3. 数据级权限：设置创建人（当前登录用户）
        SysUser currentUser = UserContextUtil.getCurrentUser();
        user.setCreateBy(currentUser.getUsername());

        // 4. 第一步：保存用户（调用 Repository 层，MyBatis-Plus 自带）
        boolean saveUser = this.save(user);
        if (!saveUser) {
            return false;
        }

        // 5. 第二步：保存用户-角色关联（多表操作，事务保证原子性）
        SysUserRole userRole = new SysUserRole();
        userRole.setUserId(user.getId());
        userRole.setRoleId("1"); // 默认角色
        boolean saveRole = sysUserRoleService.save(userRole);

        // 6. 事务内的多操作，只要有一个失败就回滚
        return saveRole;
    }

    /**
     * 查询用户+角色+部门（数据组装）
     */
    @Override
    public SysUser getUserWithRoleAndDept(String id) {
        // 1. 调用 Repository 查用户
        SysUser user = this.getById(id);
        if (user == null) {
            throw new RuntimeException("用户不存在");
        }

        // 2. 调用其他 Repository 查角色（数据组装）
        String roleName = sysUserRoleService.getRoleNameByUserId(id);
        user.setRoleName(roleName); // 组装到用户对象

        // 3. 调用部门 Service 查部门名称（跨 Service 调用）
        String deptName = SpringContextUtils.getBean(ISysDeptService.class).getDeptNameById(user.getDeptId());
        user.setDeptName(deptName);

        // 4. 数据级权限过滤（比如普通管理员只能看自己部门的用户）
        SysUser currentUser = UserContextUtil.getCurrentUser();
        if (!"admin".equals(currentUser.getUsername()) 
                && !currentUser.getDeptId().equals(user.getDeptId())) {
            throw new RuntimeException("无权限查看该用户");
        }

        return user;
    }
}
```

### Service 层绝对不能做的事

❌ 不直接接收前端请求参数（必须通过 Controller 传递）；
❌ 不封装前端响应格式（比如返回 `Result` 是 Controller 的事）；
❌ 不做接口级权限校验（比如 `@RequiresPermissions` 加在 Controller）；
❌ 不处理 HTTP 相关逻辑（比如请求头、Cookie）。

### 最佳实践

1. 业务异常用自定义异常（如 `BusinessException`），Controller 统一捕获；
2. 事务注解 `@Transactional` 要指定 `rollbackFor = Exception.class`（默认只回滚运行时异常）；
3. 复杂业务拆分成多个小方法（比如 `saveUser()` 调用 `encryptPassword()` + `saveUserRole()`）；
4. 数据组装用 VO（视图对象），避免直接返回数据库实体 DO。

## 四、Repository 层：数据访问的“桥梁”

### 核心定位

Repository（也叫 DAO/Mapper）是**系统与数据库的唯一交互层**，只做最纯粹的数据库 CRUD，不包含任何业务逻辑，相当于“数据库操作的工具人”。

> 注：在 Jeecg Boot 中，Repository 层通常是 MyBatis 的 Mapper 接口（或 MyBatis-Plus 的 BaseMapper），也可以是 Spring Data JPA 的 Repository 接口。

### 具体要做的事（仅3件！）

#### 1. 定义数据库操作方法

- 对应 SQL 语句：查询（SELECT）、新增（INSERT）、更新（UPDATE）、删除（DELETE）；
- 简单操作：用 MyBatis-Plus 的 BaseMapper 自带方法（`getById()`/`save()`/`updateById()`）；
- 复杂操作：自定义 Mapper 接口 + XML/注解写 SQL（比如多表关联、分页查询）。

#### 2. 传递参数给 SQL

- 将 Service 层传递的参数绑定到 SQL 中（比如 `WHERE id = #{id}`）；
- 处理参数类型转换（比如 Java 的 `LocalDateTime` 转数据库的 `DATETIME`）。

#### 3. 返回数据库查询结果

- 将数据库返回的 ResultSet 转换为 Java 实体类（DO）；
- 不做任何数据加工（比如“将查询结果的角色ID转换为角色名”交给 Service）。

### 典型代码示例（Jeecg Boot 风格）

#### 方式1：MyBatis-Plus BaseMapper（简单CRUD）

```java
package com.jeecg.modules.system.mapper;

import com.baomidou.mybatisplus.core.mapper.BaseMapper;
import com.jeecg.modules.system.entity.SysUser;
import org.apache.ibatis.annotations.Mapper;

/**
 * Repository 层（MyBatis-Plus Mapper）
 */
@Mapper
public interface SysUserMapper extends BaseMapper<SysUser> {
    // 继承 BaseMapper 后，自带：getById()、save()、updateById()、removeById() 等方法
    // 无需写 SQL，MyBatis-Plus 自动生成
}
```

#### 方式2：自定义 Mapper + XML（复杂查询）

```java
// Mapper 接口
package com.jeecg.modules.system.mapper;

import com.jeecg.modules.system.entity.SysUser;
import org.apache.ibatis.annotations.Param;
import java.util.List;

public interface SysUserMapper extends BaseMapper<SysUser> {
    // 自定义复杂查询：根据部门ID查用户（只定义方法，业务逻辑交给 Service）
    List<SysUser> selectByDeptId(@Param("deptId") String deptId);
}
```

```xml
<!-- SysUserMapper.xml -->
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN" "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.jeecg.modules.system.mapper.SysUserMapper">
    <!-- 仅做 SQL 映射，无任何业务逻辑 -->
    <select id="selectByDeptId" resultType="com.jeecg.modules.system.entity.SysUser">
        SELECT id, username, nickname, dept_id 
        FROM sys_user 
        WHERE dept_id = #{deptId} 
        AND status = '1'
    </select>
</mapper>
```

### Repository 层绝对不能做的事

❌ 不写任何业务逻辑（比如“判断用户是否存在”“加密密码”）；
❌ 不做事务管理（事务是 Service 的职责）；
❌ 不做数据组装（比如“查询用户+角色”）；
❌ 不做权限判断（比如“过滤数据权限”）；
❌ 不返回 VO 对象（只能返回数据库实体 DO）。

### 最佳实践

1. 简单 CRUD 用 MyBatis-Plus BaseMapper，避免重复写 SQL；
2. 复杂 SQL 写在 XML 中（比注解更易维护）；
3. 参数绑定用 `#{}`（防 SQL 注入），避免 `${}`（仅在动态表名/字段名时用）；
4. 分页查询用 MyBatis-Plus 的 `Page` 对象，统一分页逻辑；
5. Mapper 接口加 `@Mapper` 注解，或在启动类加 `@MapperScan` 扫描包。

## 五、三层调用流程完整示例（新增用户）

```
前端请求 → Controller 层 → Service 层 → Repository 层 → 数据库
   │          │              │              │              │
   │          │              │              │              │
   ▼          ▼              ▼              ▼              ▼
1. POST /api/user 
   参数：{"username":"test","password":"123456"}
   → 2. Controller 校验参数非空 → 调用 saveUser(user)
       → 3. Service 做：
           a. 校验用户名是否重复
           b. 加密密码
           c. 设置创建人
           d. 事务注解保证：保存用户 + 保存角色
               → 4. Repository 做：
                   a. insert into sys_user(...) values(...)
                   b. insert into sys_user_role(...) values(...)
               ← 5. Repository 返回影响行数
           ← 6. Service 返回操作结果
       ← 7. Controller 封装 Result 响应
   ← 8. 前端收到：{"code":200,"msg":"新增成功","data":null}
```

## 六、核心总结（关键点回顾）

### 1. 分层核心原则

- **Controller**：轻量，只做“请求/响应”，不碰业务；
- **Service**：厚重，做所有“业务逻辑”，管事务和数据组装；
- **Repository**：纯粹，只做“数据库CRUD”，无任何业务。

### 2. 核心边界

- 数据流向：前端 → Controller → Service → Repository → 数据库（反向同理）；
- 逻辑边界：Controller 管“交互”，Service 管“业务”，Repository 管“数据”；
- 异常边界：Service 抛业务异常，Controller 捕获并转换为前端响应。

### 3. 最佳实践

- 每层职责单一，不越界；
- 统一响应格式（Controller）；
- 事务只加在 Service 上；
- Repository 只返回 DO，Service 组装 VO，Controller 返回 Result<VO>；
- 用 MyBatis-Plus 简化 Repository 层开发。

这套分层方式适配 99% 的业务场景（包括 Jeecg Boot 项目），严格遵守的话，代码会更清晰、易维护、易测试。
