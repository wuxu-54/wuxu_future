# 高并发处理常见方式

高并发处理的核心目标是：**在大量请求同时涌入时，保证系统的响应速度、可用性和数据一致性**，优化需从「应用层→缓存层→数据层→架构层」由浅入深展开，以下是企业级常用的高并发处理方式，附 SpringBoot 落地示例：

## 一、服务端层优化（应用内，最易落地）

针对应用本身的性能瓶颈，减少不必要的资源消耗，提升单实例处理能力。

### 1. 接口限流（防请求过载）

- **核心思路**：限制单位时间内接口的请求量，避免大量请求压垮应用（比如限制每秒最多处理 1000 次请求），是高并发的「第一道防线」。
- **常用实现方式**：
  - 令牌桶算法（推荐）：Guava 的 `RateLimiter`（本地限流）、Sentinel/Nacos（分布式限流）；
  - 漏桶算法：适合控制请求发送速率（如接口调用第三方的场景）。
- **SpringBoot 落地示例（Guava 本地限流）**：

  ```java
  import com.google.common.util.concurrent.RateLimiter;
  import org.springframework.web.bind.annotation.GetMapping;
  import org.springframework.web.bind.annotation.RestController;

  @RestController
  public class LimitController {
      // 初始化令牌桶：每秒生成 100 个令牌（即每秒最多处理 100 次请求）
      private final RateLimiter rateLimiter = RateLimiter.create(100.0);

      @GetMapping("/api/limit")
      public String limitTest() {
          // 尝试获取令牌，无令牌则直接返回限流提示（非阻塞）
          if (!rateLimiter.tryAcquire()) {
              return "请求过于频繁，请稍后再试";
          }
          // 正常业务逻辑
          return "处理成功";
      }
  }
  ```

- **适用场景**：秒杀、活动页、高频查询接口（如商品列表）。

### 2. 异步处理（提升接口响应速度）

- **核心思路**：将非核心、耗时的操作（如发送短信、日志记录、数据统计）异步执行，接口快速返回结果，避免用户等待。
- **SpringBoot 落地（@Async 注解）**：

  ```java
  // 1. 启动类开启异步
  @SpringBootApplication
  @EnableAsync
  public class AppApplication {
      public static void main(String[] args) {
          SpringApplication.run(AppApplication.class, args);
      }

      // 2. 配置自定义线程池（避免默认线程池耗尽）
      @Bean
      public Executor asyncExecutor() {
          ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
          executor.setCorePoolSize(10); // 核心线程数
          executor.setMaxPoolSize(20); // 最大线程数
          executor.setQueueCapacity(100); // 队列容量
          executor.setThreadNamePrefix("async-");
          executor.initialize();
          return executor;
      }
  }

  // 3. 业务层异步方法
  @Service
  public class AsyncService {
      // 指定使用自定义线程池
      @Async("asyncExecutor")
      public void sendSms(String phone) {
          // 耗时操作：调用短信接口（无需等待结果）
          System.out.println("发送短信：" + phone + "，线程：" + Thread.currentThread().getName());
      }
  }

  // 4. 控制器调用
  @RestController
  public class AsyncController {
      @Resource
      private AsyncService asyncService;

      @PostMapping("/send-sms")
      public String sendSms(@RequestParam String phone) {
          // 异步发送短信，接口立即返回
          asyncService.sendSms(phone);
          return "短信发送中";
      }
  }
  ```

- **适用场景**：短信/邮件发送、日志落库、数据同步、统计报表生成。

### 3. 线程池优化（避免线程频繁创建销毁）

- **核心思路**：高并发下频繁 `new Thread()` 会导致线程创建销毁的开销，通过自定义线程池复用线程，控制线程数量（避免 OOM）。
- **关键配置**：核心线程数、最大线程数、队列容量、拒绝策略（如请求过载时直接拒绝/重试）。
- **拒绝策略选择**：高并发场景优先用 `CallerRunsPolicy`（让调用线程执行，避免直接丢弃）或自定义拒绝策略（返回友好提示）。

### 4. 无状态设计（支持水平扩展）

- **核心思路**：应用实例不存储用户会话、请求状态等数据（如登录信息），所有状态存储在 Redis/数据库中，保证多实例可无缝扩展。
- **SpringBoot 落地**：用 Spring Session 把 Session 存入 Redis：

  ```xml
  <!-- 引入依赖 -->
  <dependency>
      <groupId>org.springframework.session</groupId>
      <artifactId>spring-session-data-redis</artifactId>
  </dependency>
  ```

  ```yaml
  # application.yml 配置
  spring:
    session:
      store-type: redis
      timeout: 3600s # Session 过期时间
  ```

- **适用场景**：多实例部署、微服务架构。

### 5. 资源隔离（避免单点故障）

- **核心思路**：将不同业务的资源（线程池、连接池）隔离，比如「下单接口」和「商品查询接口」用不同的线程池，避免一个业务崩溃导致全系统不可用。
- **示例**：下单接口用 `orderExecutor` 线程池，商品查询用 `goodsExecutor` 线程池。

## 二、缓存层优化（减少数据库压力，核心手段）

高并发下数据库是最大瓶颈，通过缓存将热点数据加载到内存，提升查询速度。

### 1. 合理的缓存策略（核心）

- **核心思路**：遵循「先查缓存，再查数据库，查完数据库更新缓存」的基本逻辑，针对不同场景选择缓存粒度：
  - 热点数据全量缓存：如商品详情、用户信息（缓存整个对象）；
  - 分页/列表缓存：缓存分页结果（如 `goods_list_1` 对应第 1 页商品）；
  - 缓存过期时间：热点数据设置较短过期时间（5-10 分钟），非热点数据可设较长时间。
- **SpringBoot 落地（Redis 缓存）**：

  ```java
  @Service
  public class GoodsService {
      @Resource
      private RedisTemplate<String, Object> redisTemplate;
      @Resource
      private GoodsMapper goodsMapper;

      public GoodsVO getGoodsById(Long id) {
          String key = "goods:" + id;
          // 1. 先查缓存
          GoodsVO goodsVO = (GoodsVO) redisTemplate.opsForValue().get(key);
          if (goodsVO != null) {
              return goodsVO;
          }
          // 2. 缓存未命中，查数据库
          GoodsEntity goodsEntity = goodsMapper.selectById(id);
          if (goodsEntity == null) {
              return null;
          }
          goodsVO = BeanCopyUtil.copyBean(goodsEntity, GoodsVO.class);
          // 3. 更新缓存（设置 10 分钟过期）
          redisTemplate.opsForValue().set(key, goodsVO, 10, TimeUnit.MINUTES);
          return goodsVO;
      }
  }
  ```

### 2. 解决缓存常见问题（必做）

高并发下缓存易出现「击穿、穿透、雪崩」，需针对性防护：

| 问题类型       | 核心原因                | 解决方案                                                                 |
|----------------|-------------------------|--------------------------------------------------------------------------|
| 缓存击穿       | 热点 key 过期，大量请求直击数据库 | 1. 热点 key 设置永不过期；2. 加分布式锁（Redis/Zookeeper），保证只有一个请求更新缓存； |
| 缓存穿透       | 请求不存在的 key，直击数据库    | 1. 缓存空值（如 key 不存在则缓存 `null`，设置短过期时间）；2. 布隆过滤器过滤无效 key； |
| 缓存雪崩       | 大量 key 同时过期，数据库压力剧增 | 1. 过期时间加随机值（如 10 分钟 ± 1 分钟）；2. 缓存集群部署，避免单点故障； |

### 3. 本地缓存（补充）

针对极高频访问的热点数据（如秒杀商品库存），在应用内存中做本地缓存（Caffeine/Guava Cache），减少 Redis 网络开销：

```java
@Service
public class SeckillService {
    // Caffeine 本地缓存：最大容量 1000，过期时间 5 分钟
    private final Cache<Long, Integer> seckillStockCache = Caffeine.newBuilder()
            .maximumSize(1000)
            .expireAfterWrite(5, TimeUnit.MINUTES)
            .build();

    public Integer getSeckillStock(Long goodsId) {
        // 先查本地缓存
        Integer stock = seckillStockCache.getIfPresent(goodsId);
        if (stock != null) {
            return stock;
        }
        // 查 Redis/数据库，更新本地缓存
        stock = queryStockFromRedis(goodsId);
        seckillStockCache.put(goodsId, stock);
        return stock;
    }
}
```

### 4. 缓存集群（高可用）

单 Redis 实例易单点故障，部署 Redis 集群（主从+哨兵/Redis Cluster），保证缓存服务高可用，同时提升缓存吞吐量。

## 三、数据库层优化（数据层瓶颈突破）

### 1. 读写分离（核心）

- **核心思路**：将数据库分为「主库（写）」和「从库（读）」，写操作走主库，读操作走从库，分散数据库压力。
- **SpringBoot 落地**：用 MyBatis-Plus 或 Sharding-JDBC 实现读写分离，配置多数据源，自动路由读写操作。

### 2. 分库分表（海量数据场景）

- **核心思路**：当单表数据量超过 1000 万/单库数据量超过 100G 时，将表拆分为多个子表（分表）、库拆分为多个子库（分库），比如按用户 ID 哈希分表。
- **常用框架**：Sharding-JDBC（应用层分库分表）、MyCat（中间件层）。

### 3. 索引优化（基础）

- 核心：为高频查询字段（如 `user_id`、`goods_id`）建立索引，避免全表扫描；
- 避坑：避免过度索引（影响写入速度）、避免在大字段/频繁更新字段建索引。

### 4. 数据库连接池优化

- 核心：合理配置 Druid/HikariCP 连接池参数，避免连接数不足或过多：

  ```yaml
  spring:
    datasource:
      hikari:
        maximum-pool-size: 20 # 最大连接数（根据 CPU 核心数调整，一般 10-20）
        minimum-idle: 5 # 最小空闲连接数
        connection-timeout: 30000 # 连接超时时间
        idle-timeout: 600000 # 空闲连接超时时间
  ```

### 5. SQL 优化

- 避免 `SELECT *`，只查需要的字段；
- 避免 `JOIN` 多表（可通过缓存预聚合数据）；
- 批量操作：用 `MyBatis 批量插入/更新` 替代循环单条操作。

## 四、架构层优化（横向扩展，高并发终极方案）

当单实例/单库优化到极限时，通过架构扩展提升系统吞吐量。

### 1. 微服务拆分（解耦+扩展）

- **核心思路**：将单体应用拆分为多个独立的微服务（如用户服务、订单服务、商品服务），每个服务可独立部署、扩容，避免单点瓶颈。
- **核心组件**：Spring Cloud/Spring Cloud Alibaba（注册中心 Nacos、网关 Gateway、配置中心 Nacos）。

### 2. 负载均衡（分发请求）

- **核心思路**：通过 Nginx/Spring Cloud Gateway 将请求分发到多个应用实例，避免单实例过载：
  - Nginx 负载均衡配置：

    ```nginx
    upstream backend {
        server 192.168.1.100:8080 weight=1; # 实例1，权重1
        server 192.168.1.101:8080 weight=1; # 实例2，权重1
    }
    server {
        listen 80;
        location /api/ {
            proxy_pass http://backend; # 请求转发到后端实例
        }
    }
    ```

### 3. 消息队列削峰填谷（核心）

- **核心思路**：将高并发的同步请求转为异步消息，比如秒杀下单时，先将请求发送到 RocketMQ/Kafka，应用消费消息处理下单逻辑，避免请求直接压垮数据库：
- **SpringBoot 落地（RocketMQ）**：

  ```java
  // 1. 发送秒杀消息
  @Service
  public class SeckillController {
      @Resource
      private RocketMQTemplate rocketMQTemplate;

      @PostMapping("/seckill")
      public String seckill(@RequestParam Long goodsId) {
          // 发送消息到队列，接口立即返回
          rocketMQTemplate.send("seckill_topic", MessageBuilder.withPayload(goodsId).build());
          return "秒杀请求已接收，请等待结果";
      }
  }

  // 2. 消费消息处理下单
  @Service
  @RocketMQMessageListener(topic = "seckill_topic", consumerGroup = "seckill_group")
  public class SeckillConsumer implements RocketMQListener<Long> {
      @Override
      public void onMessage(Long goodsId) {
          // 处理秒杀下单逻辑（扣库存、生成订单）
          handleSeckill(goodsId);
      }
  }
  ```

- **适用场景**：秒杀、下单、支付回调、数据同步。

### 4. 分布式锁（保证数据一致性）

- **核心思路**：高并发下多实例同时操作同一数据（如扣库存），需用分布式锁保证原子性，常用 Redis/Zookeeper 实现：
- **Redis 分布式锁示例**：

  ```java
  public boolean deductStock(Long goodsId) {
      String lockKey = "lock:stock:" + goodsId;
      // 获取锁（设置 30 秒过期，避免死锁）
      Boolean locked = redisTemplate.opsForValue().setIfAbsent(lockKey, "1", 30, TimeUnit.SECONDS);
      if (!locked) {
          return false; // 未获取到锁，重试
      }
      try {
          // 扣减库存逻辑
          GoodsEntity goods = goodsMapper.selectById(goodsId);
          if (goods.getStock() <= 0) {
              return false;
          }
          goods.setStock(goods.getStock() - 1);
          goodsMapper.updateById(goods);
          return true;
      } finally {
          // 释放锁
          redisTemplate.delete(lockKey);
      }
  }
  ```

## 五、基础设施层优化（兜底）

### 1. Web 容器优化（Tomcat/Jetty）

- 调整 Tomcat 线程池参数，提升并发处理能力：

  ```yaml
  server:
    tomcat:
      max-threads: 200 # 最大工作线程数
      min-spare-threads: 50 # 最小空闲线程数
      accept-count: 100 # 等待队列长度
  ```

### 2. JVM 调优（避免内存溢出）

- 合理配置 JVM 堆内存、垃圾回收器，避免频繁 Full GC：

  ```bash
  # 启动参数示例（8G 内存服务器）
  -Xms4g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=200
  ```

### 3. CDN 加速（静态资源）

将前端静态资源（图片、JS、CSS）部署到 CDN，减少应用服务器的静态资源请求压力。

## 总结

1. 高并发处理遵循「**先应用内优化→再缓存优化→再数据库优化→最后架构扩展**」的顺序，优先落地低成本、高收益的方案（如限流、缓存、异步）；
2. 核心手段：接口限流防过载、缓存减少数据库压力、消息队列削峰填谷、分布式锁保证数据一致性；
3. 兜底保障：数据库读写分离/分库分表、微服务拆分+负载均衡、JVM/容器参数调优。

这些方式可根据项目并发量级灵活组合：中小并发（QPS 1000 以内）只需做应用内+基础缓存优化；高并发（QPS 1 万+）需结合消息队列、读写分离；超高并发（QPS 10 万+）需微服务+分库分表+缓存集群。
