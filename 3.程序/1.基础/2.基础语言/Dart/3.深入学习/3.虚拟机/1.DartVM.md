# Dart VM

我们从 Dart 语言最底层的运行支撑环境—— **Dart VM** 开始，把它的对象、内存、编译、异步、并发等机制一一拆解清楚。内容会比较硬核，但我会尽量用清晰的逻辑串联起来。

---

## 一、Dart VM 是什么，以及为什么重要

Dart VM 是运行 Dart 代码的一整套运行时，包括：

- 一个**对象模型**和类层次结构的运行时表示
- 一个**垃圾收集器**（分代 GC）
- **JIT/AOT 两种编译流水线**：从 Dart 源码到机器码
- **运行时核心库**（如 `dart:core`、`dart:async`）的底层实现
- **Isolate 并发模型**的实现
- 调试、性能分析、热重载的服务协议（VM Service）

在 Flutter 架构中，Dart VM 被嵌入到 C++ 引擎里，作为 UI 线程的核心执行环境。理解 VM 的细节，能让你：

- 知道为什么热重载这么快
- 知道为什么自定义 Paint 可能导致 GC 卡顿
- 了解异步函数在底层如何不阻塞线程
- 写出对 AOT 优化友好的代码

---

## 二、VM 整体架构

VM 的内部流程可以简化为：

```
Dart 源码
  → [CFE 解析器] → Kernel 二进制 (AST 的序列化形式)
       → VM 加载 Kernel，创建 Class、Function、Library 等内部对象
         → 运行时执行：
              JIT模式:  Kernel  → 未优化机器码 (收集类型反馈)
                                 → 优化编译 (基于反馈的 AOT/JIT 共享后端)
              AOT模式:  Kernel  → 全局类型流分析 (TFA)
                                 → 优化编译为机器码 → 快照
```

**关键中间表示：Kernel**  
Kernel 是 Dart 的一种中间语言，相当于平台无关的字节码，但不是栈式，而是树形结构。所有运行模式（调试/发布、JIT/AOT）都从 Kernel 开始。  

- 热重载就是通过“增量 Kernel 文件”注入 VM 实现。
- AOT 预编译时，`gen_snapshot` 读取 Kernel，执行全程序分析和优化。

## 三、对象模型（Object Model）

### 3.1 一切皆对象，包括小整数

Dart VM 中，每个值都是一个“对象指针”，即使是 `int`、`double` 也不例外。核心设计：

- **小整数 (Smi)**：在 64 位平台上，对象指针利用**标记位（tag bit）** 直接存储 63 位有符号整数，不需要堆分配。如果指针最低位为 0 表示 Smi，为 1 表示堆对象指针（因为对象地址对齐到 2 字节）。

  ```c++
  // 伪表示
  #define Smi_Tag  0
  #define HeapObject_Tag 1

  bool IsSmi(Value v) => (v & Smi_Tag) == 0;
  intptr_t SmiValue(Value v) => v >> 1;  // 算术右移
  ```

- **Mint（中等整数）**：超出 63 位范围时，使用堆上分配的 `Mint` 对象，内部存储 64 位有符号整数。
- **Double**：堆上对象，包含 IEEE 754 双精度浮点数。
- **String**：支持 ASCII、Latin-1、UTF-16、UTF-8 多种内部编码，以平衡内存和访问速度。
- **List**：用连续数组存储，泛型类型参数被具体化（reified），`List<int>` 运行时内部会用紧凑的 `int` 存储（如果全 Smi 则直接存 Smi）。
- **Map/Set**：基于哈希表实现。
- **Instance/Class**：类本身也是对象，存储字段偏移表、方法表等。

### 3.2 对象内存布局

每个堆对象都有一个统一的对象头：

```
+------------------+
| tags (class id,   |   // 32 位或 64 位，包含哈希码、GC 标记等
|   hash, size,  etc)|
+------------------+
| Class*           |  // 指向描述该对象所属类的 Class 对象
+------------------+
| ... 实例字段 ... |
+------------------+
```

- **Class id** 用来快速查表，比如类型检查、方法分派。
- **Hash code** 在首次调用 `identityHashCode` 时生成并缓存在对象头中。
- **大小信息** 用于 GC 扫描，指示对象包含多少个指针（或纯数据）。

### 3.3 指针压缩

在 64 位 CPU 上，为了节省内存并提高缓存效率，Dart VM 在堆内使用 **32 位压缩指针**（Compressed Pointer），基址加上偏移，得到完整 64 位地址。这个对开发者透明，但影响 JIT 代码生成。

## 四、内存管理与垃圾回收

### 4.1 分代堆

Dart VM 使用**分代垃圾回收**，堆分为：

- **新生代（New Space）**：刚分配的对象在这里，假设大部分对象很快死亡。划分为 From 和 To 两个半区，采用**复制算法**。
- **老年代（Old Space）**：在新生代存活过几次 GC 后，对象被**晋升（promote）** 到这里。老年代使用**标记-清除/标记-整理**算法。

这种设计利用了“弱分代假说”：年轻对象死得快，年老对象活得久。

### 4.2 新生代 GC：Scavenger

Scavenger 是新生代的垃圾回收器，工作流程：

1. 分配只在 From 区，利用**指针碰撞（Bump-pointer）** 极速分配，通过 TLAB（线程本地分配缓冲）避免竞争。
2. From 区满 → 触发 Scavenge。
3. 从根集（寄存器、栈、全局变量）扫描 From 区的存活对象，拷贝到 To 区（或直接晋升到老年代，如果对象已存活超过一定次数）。
4. 复制后，From 和 To 角色互换。
5. 复制过程中更新所有指向该对象的引用（通过**写屏障**记录的跨代引用也需扫描）。

**特点**：速度快，停顿时间短，但需要额外一半内存作为保留区。

### 4.3 老年代 GC：Mark-Sweep 与 Mark-Compact

老年代 GC 分为几个阶段：

- **并发标记（Concurrent Mark）**：大部分标记工作与 Mutator（执行 Dart 代码的线程）并行进行，减少停顿。使用三色标记法，通过**写屏障**拦截对象图的变化。
- **重新标记（Remark）**：短暂暂停所有线程，处理标记期间的残留变更。
- **清除（Sweep）**：将未标记对象的空间加入空闲列表，用于后续分配。
- **整理（Compact）**：如果碎片化严重，会执行压缩，移动对象以消除碎片，此时需暂停并更新引用。

Dart VM 中，老年代 GC 主要由 **并发标记+并行清除** 实现，最大限度降低 UI 线程掉帧风险。

### 4.4 写屏障（Write Barrier）

为了正确跟踪跨代引用（老年代对象引用新生代对象），VM 在每次对象字段写入时插入一小段代码：

```c++
// 伪代码
if (old_object->field = new_object) {
  // 如果 old 在老年代，且 new 在新生代，则需要记录该引用
  if (old_in_old_space && new_in_new_space)
    remember_card(old_object);  // 在 Remembered Set 中标记
}
```

这些记录在新生代 GC 时会被扫描，确保不会错误回收被老年代引用的年轻对象。在 AOT 模式下，部分屏障可以被类型流分析优化掉。

### 4.5 弱引用与终结器

- **WeakReference** 与 `Finalizer` 都在 VM 内具有特殊处理：标记阶段发现弱引用对象无其他强可达路径时，它们不会被保留，之后统一清除。
- 终结器（`Finalizer`）在对象被回收后，异步调用附带的回调，用于清理外部资源。

## 五、运行时系统细节

### 5.1 方法调用与内联缓存（Inline Cache, ICC）

Dart 作为动态类型语言，调用 `obj.method()` 时，VM 不会立刻知道调用哪个具体函数。优化手段：

每个调用点都拥有一个**内联缓存状态机**：

- **未初始化** → 第一次调用，查找实际接收者的方法。
- **单态 (Monomorphic)** → 缓存上次的类 ID 和方法入口，如果再次命中同类，直接跳转。
- **多态 (Polymorphic)** → 遇到不同类时，扩展为一个小的查表逻辑（常见 4 个以内）。
- **巨态 (Megamorphic)** → 类型过多，回退到全局哈希表查找，类似普通动态分派。

JIT 模式下，未优化代码会收集这些类型反馈；优化编译时，会根据反馈将单态/多态调用点**内联**或者**直接调用**，甚至完全去虚拟化（devirtualize）。

### 5.2 去优化（Deoptimization）

优化编译器基于运行时反馈大胆特化（例如：假设 `x` 一定是 `int`）。但当假设失效（比如传入一个 `String`），需要**回退**到未优化状态：

- VM 把优化帧反向翻译为未优化栈帧（`DeoptInfo` 记录在代码边表中）。
- 随后继续在未优化代码中执行（解释器/未优化机器码），并收集新的类型反馈。
- 当热点再次触发，可能会用新的反馈重新优化。

去优化会导致瞬间性能下降，这就是为什么避免大量多态代码和保持稳定的类型很重要。

### 5.3 类型检查与健全空安全

空安全（Sound Null Safety）保证类型系统在运行时不需要额外除零检查，因为静态分析已证明变量不可能为 null。但在 JIT 模式下的热重载或与 `dynamic` 混用时，仍需要一些运行时断言。  
AOT 模式通过 TFA（类型流分析）可以消除 90% 以上的运行时类型检查，包括空检查、类型转换、边界检查等。

### 5.4 协程：`async/await` 的底层实现

Dart 的 `async/await` 不是原生线程，而是由编译器将函数转化为一个**状态机**：

```dart
Future<int> fetch() async {
  var a = await getA();
  var b = await getB(a);
  return b + 1;
}
```

被转换为类似：

```dart
class _FetchFuture extends _FutureImpl {
  int _state = 0;
  late int a, b;

  void _resume(result) {
    switch (_state) {
      case 0: getA().then((v) { a = v; _state = 1; _resume(); });
              break;
      case 1: getB(a).then((v) { b = v; _state = 2; _resume(); });
              break;
      case 2: _complete(b + 1); break;
    }
  }
}
```

- 每次 `await` 都暂停并注册回调，恢复时继续执行下一个状态。
- 底层依赖于 **`_microtask` 队列** 和 **事件循环** 来调度这些回调，全部由 VM 在单个线程内完成，不阻塞线程。

### 5.5 异常处理

Dart 的异常不使用 C++ 异常，而是通过**栈展开**机制。VM 为每个函数记录了异常处理表（PC 范围 → 对应的 catch 块）。发生异常时，遍历调用栈，根据当前 PC 找到处理块，并通过去优化栈帧或直接跳转的方式执行 catch。

## 六、Isolate：Dart 的并发模型

### 6.1 完全隔离的内存

Isolate 是 Dart 的并发单元，每个 Isolate：

- 拥有**独立的堆**（新生代+老年代）
- 拥有独立的 GC 线程
- 拥有独立的 MessageLoop（端口消息队列）
- **没有任何共享可变状态**，通信靠消息传递（`SendPort` / `ReceivePort`）

这种设计使得单个 Isolate 永远不需要加锁，对象分配和 GC 都无需考虑并发，极大地简化了 VM 设计并提升了性能。

### 6.2 Isolate 的创建与启动

创建一个 Isolate 的过程：

1. 从现有的快照（JIT 模式下的 Kernel 快照，或 AOT 模式下的指令/数据快照）克隆一份内存映像，作为初始堆。
2. 初始化新的线程、消息循环。
3. 执行指定的入口函数。

在 JIT 模式，多个 Isolate 可以**共享代码和类型反馈**，但堆完全独立。这使得 Flutter 能用 `compute` 非常轻量地启动后台 Isolate 处理 JSON 解析等任务。

### 6.3 Isolate 组（Isolate Groups）

Dart 2.15 引入的概念：同一组内的 Isolate 共享**代码堆**（机器码、类元数据等），以节省内存。  

- 例如，Flutter 的 UI Isolate 和多个 `compute` Isolate 可以属于同一组。
- 代码共享，但数据隔离，依然无锁。

## 七、编译管线：从 Kernel 到机器码

### 7.1 Kernel 的角色

Kernel 二进制由 `package:front_end` (CFE) 生成，它是一个包含库、类、过程、类型注解的树结构。无论 JIT 还是 AOT，VM 都先反序列化 Kernel，构建内部 Runtime 对象（`Class`, `Function`, `Field` 等）。

### 7.2 JIT 模式编译流水线

1. **加载 Kernel** → 创建函数体未编译的 `Function` 对象。
2. 首次调用函数时，触发**未优化编译器（Unoptimized Compiler）**：
   - 直接从 Kernel 生成未优化机器码（跳过解释器）。
   - 代码中插入收集 IC 反馈的桩代码。
3. 函数变热（调用次数或循环迭代计数超过阈值）→ 触发**优化编译器（AOT-compiler backend）**：
   - 将未优化代码和收集到的 IC 反馈转换为**流图（Flow Graph）**，是基于 SSA 的中间表示。
   - 应用经典编译器优化：内联、逃逸分析、加载消除、死代码消除等。
   - 根据 IC 反馈进行**推测性内联和去虚拟化**。
   - 生成高质量机器码。
4. 如果推测失败，进行**去优化**，回退到未优化版本。

这个过程就是 JIT 能“越跑越快”的原因。

### 7.3 AOT 模式编译流水线

AOT 编译在开发机上通过 `gen_snapshot` 完成：

1. **TFA（Type Flow Analysis）**：全程序静态类型分析，推导所有变量、返回值的具体类型和可能值。与 JIT 的 IC 反馈类似，但是静态且全程序。
2. 基于 TFA 结果，大量消除运行时类型检查、多态调用、边界检查。
3. 进行激进的**内联**：甚至可以将 `bool get isEmpty => length == 0;` 这种 getter 直接内联到调用处。
4. 移除所有未使用的代码（Tree Shaking），大幅缩小二进制体积。
5. 将流图编译为 ARM/x64 等机器的绝对机器码，并生成 **AOT 快照**（ELF 或 Mach-O 片段）。
6. 运行时，直接将快照映射进内存，跳转到入口运行，**无解释器、无 JIT 编译器**。

## 八、Dart VM 在 Flutter 引擎中的集成

Flutter Engine 初始化时，会：

1. 加载 `libflutter.so`（内含 Dart VM）。
2. 启动 Platform、UI、Raster、IO 线程。
3. 在 UI 线程中创建一个 Dart VM 实例，加载 AOT 快照（或 Kernel 快照）。
4. 生成主 Isolate，运行 `main()`。
5. `dart:ui` 中的每个 API（如 `Canvas.drawRect`）底层都是 **Native Binding**，由 VM 通过 `dart:ffi` 或原生扩展直接调进 C++ 引擎，完成 UI 提交。

### 8.1 热重载在 VM 层的实现

热重载是 JIT 模式下独有的杀手级功能：

1. 开发者修改源码保存。
2. Flutter 工具调用 CFE 生成**增量 Kernel 文件**（仅包含变更的库和类）。
3. VM 收到增量 Kernel 后，对内部类、函数重新加载：
   - 替换旧的 `Function` 代码入口为新的未优化代码。
   - 通过“轻量级重置”，将所有状态对象（如 Widget State）迁移到新类定义下，保留其字段值。
   - 丢弃旧代码，去优化栈帧，然后从新的 build 方法重新执行。
4. 整个过程在几百毫秒内完成，且不丢失应用状态。

## 九、性能观测与工具

- **DevTools / Observatory**：通过 VM Service 协议（WebSocket）暴露 Isolate 内部状态、堆快照、CPU 采样、GC 统计。
- **分配采样**：追踪对象分配轨迹，发现内存抖动或泄漏。
- **时间线**：可叠加 VM 的 GC 事件、编译事件、去优化事件到帧图中，辅助定位卡顿。

## 十、总结

Dart VM 是一个为移动端 UI 专门优化过的现代语言运行时：

| 特性 | 实现方式 |
|------|----------|
| 快速对象分配 | TLAB + Bump-pointer 新生代 |
| 低延迟 GC | 并发标记老年代、复制式新生代 |
| 动态调用性能 | 内联缓存 + 推测内联 + 去优化 |
| 极致 AOT 性能 | 全程序类型流分析 + 积极内联和树摇 |
| 异步无阻塞 | 状态机 + 事件循环 + 微任务队列 |
| 并行模型 | Isolate 隔离堆 + 消息传递 |

只有深刻理解 VM 的内存模型、编译方式和并发特性，才能真正写出对引擎友好、低抖动、高响应速度的 Flutter 应用。
