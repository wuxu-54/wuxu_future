# std::lock_guard / std::unique_lock / std::scoped_lock 笔记

>
> 头文件：`<mutex>`
> 三者都是 **RAII 锁包装器**：构造时获取锁，析构时自动释放锁，避免忘记unlock导致死锁。
> 底层锁一般是 `std::mutex`。

## 1. std::lock_guard

### 核心特点

- 最简单、最轻量。**只支持构造上锁，析构解锁。**
- 不支持手动 `lock()` / `unlock()`；不能延时加锁；不能move转移锁所有权。
- 不能用于 `std::condition_variable::wait()`（wait需要中途unlock/relock）。

### 语法

```
std::mutex mtx;
{
    std::lock_guard<std::mutex> lk(mtx);
    // 临界区代码
} // 出作用域，lk析构，自动unlock
```

### 适用场景

只需要保护一段连续代码块，**不需要中途解锁、不用条件变量**。

>
> 推荐优先使用，开销最小。

### 缺点

灵活性差；不能传给cv.wait。

---

## 2. std::unique_lock

### 核心特点

功能最强，内部保存一个标记，记录当前**是否持有锁（owns_lock）**

- ✅ 支持手动 `lock()` / `unlock()`
- ✅ 支持**延时加锁** `std::defer_lock`（构造不锁，后面再lock）
- ✅ 支持锁所有权移动 `std::move`
- ✅ **可以传入 std::condition_variable::wait()**（线程池必备）>

> wait内部会自动unlock休眠，唤醒后重新lock。

### 语法示例

```
std::mutex mtx;
// 方式1：构造直接上锁
std::unique_lock<std::mutex> lk(mtx);

// 方式2：延时加锁，构造不上锁
std::unique_lock<std::mutex> lk2(mtx, std::defer_lock);
lk2.lock(); // 手动上锁

// 配合条件变量（你线程池worker代码）
std::unique_lock<std::mutex> lk(mtx_);
cv_.wait(lk, [&](){ return stop_flag_ || !tasks_.empty(); });
```

### 适用场景

1. 需要配合 `std::condition_variable` 的 wait
2. 需要**提前手动unlock**（例如队列操作完成，解锁后再notify）
3. 需要转移锁所有权

### 缺点

比lock_guard多一点开销（内部维护bool标记）。

>
> ⚠️误区：unique_lock名字里的unique，是**锁所有权可转移**，不是互斥独占；mutex本身才是互斥。

---

## 3. std::scoped_lock（C++17新增）

### 核心特点

**专门用于同时锁定多个互斥量，自动避免死锁**。

- 支持**一次性锁住多个mutex**，内部使用 `std::lock` 算法，按无死锁顺序加锁。
- 构造上锁，析构解锁；**不支持手动lock/unlock，不能move**。
- 不能用于 `cv.wait()`。
- 可以只传单个锁，此时等价lock_guard。

### 语法示例

```
std::mutex m1, m2;
{
    // 同时锁住 m1、m2，自动防死锁
    std::scoped_lock lk(m1, m2); 
    // 临界区，同时持有两把锁
}
// 析构，自动释放m1、m2
```

>
> 不需要写模板参数，类模板参数推导（CTAD），C++17特性。

### 适用场景

需要同时持有**多个互斥锁**，防止人工顺序写错造成死锁。
单个锁场景也能用，但一般用lock_guard更直观。

### 缺点

C++17及以上才能用；不能手动解锁，不能配合cv.wait。

# 汇总对比表（直接复制到笔记）

| 特性 | std::lock_guard | std::unique_lock | std::scoped_lock(C++17) |
| --- | --- | --- | --- |
| C++版本 | C++11 | C++11 | C++17 |
| 支持多个锁 | ❌ 只能1个 | ❌ 只能1个 | ✅ 支持同时锁多个mutex，自动防死锁 |
| 手动lock/unlock | ❌ 不支持 | ✅ 支持 | ❌ 不支持 |
| 延时加锁 defer_lock | ❌ | ✅ | ❌ |
| 锁所有权move转移 | ❌ | ✅ | ❌ |
| 可传入 cv.wait | ❌ 编译报错 | ✅ ✅ | ❌ |
| 开销 | 最小 | 略大（带状态标记） | 小，多锁场景优势巨大 |
| 核心定位 | 单锁简单RAII | 灵活单锁，配合条件变量 | 多锁场景，自动防死锁RAII |

# 选型口诀（记笔记）

1. **单锁，简单临界区，不用cv → lock_guard**
2. **单锁，要cv.wait / 手动unlock → unique_lock**
3. **≥2个mutex，需要同时加锁 → scoped_lock**

# 常见面试考点

1. 为什么lock_guard不能传给cv.wait？

>
> cv.wait需要锁对象支持中途unlock，lock_guard不支持手动解锁。unique_lock内部维护锁状态，可以满足。

2. scoped_lock相比手动std::lock(m1,m2)的好处？

>
> RAII，异常安全。就算临界区抛异常，析构自动释放所有锁，不会锁泄漏。

3. unique_lock可以move，lock_guard不能move。

# 踩坑清单

1. unique_lock调用unlock前，必须是持有锁状态；否则抛异常。
2. scoped_lock是C++17，老编译器不支持。
3. 三个都只是**锁管理器**，真正互斥能力来自std::mutex。
4. 不要用unique_lock当默认首选；优先lock_guard，只有需要灵活性才上unique_lock。
