# std::condition_variable

```
std::condition_variable cv_;
```

`cv_` 是**条件变量对象**，头文件：`<condition_variable>`。

>
> 作用：用于多线程之间，**让线程阻塞等待某个条件成立，被其他线程唤醒**，典型用于生产者‑消费者、任务队列。

## 底层是什么类型

`std::condition_variable` 是一个类（class），封装操作系统原生条件变量：

- Linux：封装 pthread_cond_t
- Windows：封装 Windows 条件变量内核对象

它**不存储数据、不存条件本身！！只是一个线程等待/通知的信号工具**。
条件（比如队列不为空）要你自己用变量 + mutex保存。

>
> ⚠️重要规则：`std::condition_variable`**必须搭配 `std::unique_lock<std::mutex>` 使用，不能用lock_guard**。

## 主要成员API

### 1. wait() 系列

```
// 1.基础wait
void wait(std::unique_lock<std::mutex>& lk);

// 2.带谓词（最推荐，防止虚假唤醒）
template<class Predicate>
void wait(std::unique_lock<std::mutex>& lk, Predicate pred);

// 超时等待
std::cv_status wait_for(std::unique_lock<std::mutex>& lk, std::chrono::duration<...> dur);
std::cv_status wait_until(...);
```

**wait做的内部动作（重点面试）**

1. 拿到传入的 `unique_lock`，**自动unlock解锁mutex**；
2. 当前线程陷入阻塞休眠，等待被通知；
3. 收到notify唤醒后，**重新lock锁住mutex**，wait函数才返回。

>
> 为什么必须unique_lock：wait中途需要手动unlock/relock，lock_guard不支持手动解锁，所以不能传lock_guard。

**虚假唤醒(spurious wakeup)**：线程没有收到notify，也可能从wait返回。
👉 解决方案：永远用第二个谓词参数 `wait(lk, []{return 条件;})`；如果条件不满足，内部会继续wait。

#### 谓词

**谓词（返回 bool 的可调用对象）**

1. **调用谓词`pred()`**
   - 如果`pred == true`：不阻塞，wait 直接返回，继续往下执行代码。
   - 如果`pred == false`：
     1. `lk.unlock()`：释放 mutex 锁
     2. 线程进入阻塞休眠，等待 notify 信号
     3. 收到`notify_one`/`notify_all`唤醒之后，**重新 lock 获取 mutex**
     4. **再次调用谓词判断**
        - pred 为 true → wait 返回
        - pred 为 false → 再次解锁，继续休眠（解决**虚假唤醒**）

### 2. notify_one()

```
void notify_one() noexcept;
```

唤醒**某一个**正在这个cv上等待的线程；如果没有等待线程，调用什么也不发生。

### 3. notify_all()

```
void notify_all() noexcept;
```

唤醒**所有**正在这个cv上等待的线程。

## 典型代码模板（任务队列）

```
std::mutex mtx_;
std::condition_variable cv_;
std::queue<int> task_q;

//消费者线程
void consumer(){
    std::unique_lock<std::mutex> lk(mtx_);
    // wait：队列为空就休眠；队列非空才往下走
    cv_.wait(lk, [&](){ return !task_q.empty(); });

    int task = task_q.front();
    task_q.pop();
    lk.unlock(); //可以提前解锁，做业务逻辑
}

//生产者线程
void producer(int v){
    {
        std::lock_guard<std::mutex> lk(mtx_);
        task_q.push(v);
    }
    cv_.notify_one(); //通知等待线程
}
```

## std::condition_variable 几个关键属性

1. **不可拷贝、不可移动**

```
std::condition_variable cv1;
std::condition_variable cv2 = cv1; // ❌编译报错，删除拷贝构造
std::condition_variable cv3 = std::move(cv1); //❌也不能move
```

条件变量对象一般作为类的成员变量，直接定义为成员，不要复制转移。

2. 和mutex是逻辑配对，**语法上没有强制绑定**。你代码上要保证：wait的时候，传入的就是保护这个条件的mutex。不要乱传别的mutex，UB未定义行为。
3. notify不需要持有mutex锁；可以加锁内调用，也可以锁外调用。工程上一般：修改完共享数据之后，释放锁，再notify。

## 还有一个兄弟：std::condition_variable_any

`std::condition_variable_any`：可以接受**任何可锁类型**，不强制要求unique_lock，lock_guard、自定义锁都可以。
代价：性能略差；普通场景一律用`std::condition_variable`。

## 高频踩坑总结

1. wait传lock_guard ❌ 编译报错，必须unique_lock
2. wait不加谓词，不判断条件：会遭遇虚假唤醒，逻辑bug
3. 修改条件变量对应的共享变量的时候，**必须被同一个mutex保护**
4. cv对象不能拷贝/move，只能作为成员变量原样存在
5. notify_one不保证一定有线程在等；没有等待线程调用notify，信号直接丢掉，不会保存信号！条件变量**信号不缓存**。>

> 重点：notify只是一个唤醒信号，如果此时没有线程wait，这个通知直接消失，不会存下来。

### 简单比喻

`cv_`就像一个门铃。

- `wait()`：人在屋里睡觉，守着门（mutex），松开门锁睡觉，门铃响才醒过来重新拿锁。
- `notify_one()`：按一下门铃，叫醒一个睡觉的人。
门铃本身不存消息；没人睡觉的时候按门铃，什么效果都没有。门外的东西（队列、flag条件）要靠mutex保护。

# notify_one() vs notify_all()

```
void notify_one() noexcept;
void notify_all() noexcept;
```

两者都是 `std::condition_variable` 的通知接口，**作用是唤醒正在该cv上wait的线程**，头文件 `<condition_variable>`。

## 核心区别

1. **`notify_one()`**：最多唤醒**一个**处于等待的线程。
   - 如果有多个线程在等待，调度器选其中某一个；
   - 如果当前**没有任何线程在wait**：调用什么都不做，信号直接丢失。
2. **`notify_all()`**：唤醒**所有当前正在这个cv上阻塞等待的线程**。
   - 全部线程都会从wait处被唤醒，然后去竞争mutex锁；
   - 没有等待线程时，同样什么都不发生。

>
> ⚠️注意：条件变量**信号不保存**。notify先执行、线程后才wait，收不到这次通知。

## 举个生产者‑消费者例子

假设队列里放入1个任务，此时有3个消费者线程都在 `cv.wait()` 休眠。

### notify_one()

```
q.push(task);
cv.notify_one();
```

只会唤醒**其中1个消费者**。被唤醒的线程拿到锁，取走任务；另外2个继续睡。
✅适合：**只需要处理1个任务，只需要一个线程干活**。

### notify_all()

```
q.push(task);
cv.notify_all();
```

**3个消费者全部被唤醒**。

- 3个线程抢同一个mutex，只有1个抢到锁，发现队列有任务，取走执行；
- 剩下2个线程拿到锁后执行谓词判断 `!q.empty()`，此时队列已经空了，条件不满足，**重新回到wait休眠**。

>
> 这种现象叫**惊群效应(thundering herd)**：大量线程被唤醒，但大部分没事干，又继续休眠，带来不必要的锁竞争、CPU开销。

## 什么时候用 notify_one

场景：生产**一个资源，只需要一个线程处理**。

- 普通生产者‑消费者，push一个任务 → `notify_one()`
- 线程池，来了一个新任务，唤醒一个工作线程。

优点：避免惊群，减少CPU争抢，性能更好。

>
> 注意：notify_one 不指定唤醒哪一个，由操作系统调度器选择。

## 什么时候用 notify_all

场景：**状态发生变化，所有等待线程都有可能可以继续工作**。

典型场景：

1. 程序退出，要唤醒全部工作线程，让它们检测退出标记，结束循环。

```
exit_flag = true;
cv.notify_all(); // 全部线程醒来看到exit_flag=true，退出
```

2. 一次性放入多个任务，多个线程都可以干活。
3. 某个共享状态改变，**每一个等待线程都要检查条件**，例如：资源数量足够，多个线程都可以获取资源。

>
> 退出线程池几乎固定写法：设置退出标记 + `notify_all()`。如果你用notify_one，只会唤醒一个线程，其他线程永远睡死。

## 常见误区

### 误区1：notify_one 发送一个信号，notify_all发送多个信号

❌错误。条件变量没有信号队列。
notify_one：唤醒一个；notify_all：唤醒全部；没有等待线程，则通知直接消失。

### 误区2：notify_all代表所有线程同时跑

❌不是并行执行。唤醒之后所有被唤醒线程**要争抢同一个mutex锁**，同一时刻只有一个线程持有锁执行，其余被唤醒线程阻塞在lock处。

### 误区3：notify必须放在mutex锁内部

✅锁内、锁外调用notify语法都合法。
工程上更推荐：**修改完共享数据，释放mutex之后，再调用notify**。

>
> 如果notify在锁内：线程被唤醒后，马上又要抢还没释放的锁，会多一次上下文切换。

```
//推荐写法
{
    std::lock_guard lk(mtx);
    q.push(item);
}
cv.notify_one(); //锁释放后通知
```

## 对比简表

| 接口 | 行为 | 适用场景 | 潜在问题 |
| --- | --- | --- | --- |
| notify_one | 唤醒最多1个等待线程 | 产生1份资源，只需要一个线程处理 | 如果目标线程还没wait，通知丢失；不会唤醒全部 |
| notify_all | 唤醒全部等待线程 | 状态变更影响所有等待者，例如退出、批量资源 | 惊群效应，多线程抢锁，CPU开销变大 |

## 面试小问答

>
> Q：线程池关闭为什么用notify_all，不能notify_one？
> A：线程池有N个worker全部在wait休眠。notify_one只能叫醒一个；其余N‑1个线程会永远阻塞等待，程序无法正常退出。所以要notify_all全部唤醒，让大家检查退出标记。

>
> Q：notify_all一定会造成性能很差吗？
> A：不一定。例如程序退出只执行一次notify_all，惊群代价可以忽略。只有高频业务路径频繁notify_all才需要警惕惊群。

### 补充伪代码演示惊群

```
// 3个消费者
cv.wait(lk, [&]{ return !q.empty(); });

//生产者执行 notify_all()，队列只有1个任务
//全部3个线程唤醒
//线程A拿到锁：取走任务，队列变空
//线程B拿到锁：判断队列空 → 再次wait
//线程C拿到锁：判断队列空 → 再次wait
```

B、C白白被唤醒，又回去睡觉，就是惊群。这种场景应该用 notify_one。
