# C++ 文件编译+链接完整流程 + CMakeLists 详解

先区分3个核心概念，很多人混淆：

1. **预处理 + 编译**：`.cpp` → `.obj/.o` 目标文件（每个cpp单独编译，互相不知道对方存在）
2. **头文件 #include**：预处理器文本粘贴，**只参与编译阶段，不参与链接**
3. **链接**：把多个 `.o` 目标文件、静态库合并，解析函数符号，生成可执行程序/库。

> 头文件（`.h`）**不会被编译成obj**！只有`.cpp`源文件会编译成obj。
> `.h` 里面放**声明**；`.cpp`放**实现（定义）**。

## 一、基础概念

### 1）声明 vs 定义

- **声明**：告诉编译器“有这个类/函数”，没有实体代码。放在 `.h`

```cpp
// logger.h 声明
namespace nexus {
class Logger {
public:
    static Logger* get_instance();
    void set_level(int lvl);
};
}
```

编译器看到声明就允许你调用函数，**编译main.cpp可以通过**。

- **定义（实现）**：函数真正的代码，生成机器符号。放在`.cpp`

```cpp
// logger.cpp 定义
#include "logger.h"
namespace nexus{
Logger* Logger::get_instance(){
    static Logger ins;
    return &ins;
}
void Logger::set_level(int lvl){
    // 函数体
}
}
```

`logger.cpp` 编译产出 `logger.o`，里面包含 `nexus::Logger::get_instance()` 的机器码符号。

> 报错 `undefined reference`：编译过了，**链接器在所有obj里找不到这个函数的定义符号**。

### 2）#include 的本质（编译阶段，和链接无关）

`#include "xxx.h"`：预处理器把整个`.h`文本粘贴到当前cpp。
> ⚠️ `#include` **不会自动编译对应的xxx.cpp**！
> 你`#include "logger.h"`，只是把声明拿过来，**logger.cpp仍然必须手动交给编译器编译**。

### 3）链接做什么

链接器收集所有参与构建的`.o`目标文件：

- main.o 里面调用了 `nexus::Logger::get_instance()`，留下一个**未解析符号**
- 如果同时有 logger.o，链接器找到该符号地址，填入main.o，生成exe
- 如果没有logger.o → `undefined reference`

# 二、项目示例目录结构

```
NexusLM/                     # ${PROJECT_SOURCE_DIR} 项目根目录
├── CMakeLists.txt           # 顶层cmake
└── src/
    ├── main.cpp             # 业务入口
    ├── net/
    │   └── socket.h
    │   └── socket.cpp
    └── utils/
        ├── logger.h
        └── logger.cpp
```

目标：生成可执行程序 `NexusLM`，main.cpp 使用 utils/logger、net/socket。

## 方案A：全部源文件直接加到 add_executable（小项目）
>
> add_executable 的参数：**所有需要编译的 .cpp 文件**，h不要写进去（写了也无害，但没必要）

CMakeLists.txt

```cmake
cmake_minimum_required(VERSION 3.16)
project(NexusLM LANGUAGES C CXX)

# 1. 创建可执行目标，列出全部cpp源文件，这些cpp各自编译成.o，最后参与链接
add_executable(NexusLM
    src/main.cpp
    src/utils/logger.cpp
    src/net/socket.cpp
)

# 2. 设置头文件搜索路径！解决 #include 查找头文件
# PRIVATE：只给 NexusLM 这个目标编译时用，对外不暴露
target_include_directories(NexusLM
    PRIVATE
        ${PROJECT_SOURCE_DIR}/src   # 根到src目录
)
```

现在在任意cpp中：

```cpp
// main.cpp
#include "utils/logger.h"   // 不再写 ../ ！因为搜索路径包含 src/
#include "net/socket.h"

int main(){
    auto log = nexus::Logger::get_instance();
    return 0;
}
```

工作流程：

1. cmake解析，收集3个cpp
2. 分别编译：`main.cpp→main.o`；`logger.cpp→logger.o`；`socket.cpp→socket.o`
3. 链接器把3个`.o`合并为 `NexusLM` 可执行文件。

> 如果你漏掉 `src/utils/logger.cpp`：main.o生成，但是没有logger.o，链接阶段 undefined reference。

> `target_include_directories` 只管 **编译器找.h**，不管编译哪些cpp。

### 路径变量说明

- `${PROJECT_SOURCE_DIR}`：**顶层CMakeLists所在目录，绝对路径，强烈推荐，不要用 `../`**
- `${CMAKE_CURRENT_SOURCE_DIR}`：**当前正在执行cmake脚本的目录**（子cmake用）

# 方案B：拆分成静态库（大项目推荐）

当文件很多，按模块打包成静态库 `.a/.lib`。

```cmake
cmake_minimum_required(VERSION 3.16)
project(NexusLM LANGUAGES C CXX)

# 1. 工具模块静态库，把utils下面的cpp编译成静态库 libutils.a
add_library(utils STATIC
    src/utils/logger.cpp
)
# PUBLIC：使用utils库的外部目标，也会继承这个头文件搜索路径
target_include_directories(utils
    PUBLIC
        ${PROJECT_SOURCE_DIR}/src
)

# 2. net模块静态库
add_library(net STATIC
    src/net/socket.cpp
)
target_include_directories(net
    PUBLIC
        ${PROJECT_SOURCE_DIR}/src
)

# 3. 可执行程序
add_executable(NexusLM
    src/main.cpp
)

# 链接：NexusLM 需要依赖 utils、net静态库
target_link_libraries(NexusLM
    PRIVATE
        utils
        net
)
```

关键点：

1. `add_library(xxx STATIC files.cpp)`：编译源文件生成静态库（一堆.o打包）
2. `target_link_libraries`：告诉链接器，要把这个库链接进目标。
3. 库用 **PUBLIC** 设置头文件路径：链接这个库的exe，自动继承include路径，main.cpp不用再写一遍`target_include_directories`。

#### PUBLIC / PRIVATE / INTERFACE 彻底讲明白

|修饰符|作用对象|说明|
|---|---|---|
|`PRIVATE`|add_executable / add_library|头文件路径**仅本目标自己编译用**；依赖我的其他目标看不到。exe一般用PRIVATE。|
|`PUBLIC`|add_library|我自己编译要用；**同时所有链接我的其他目标也会获得该头文件路径**。库对外接口用PUBLIC。|
|`INTERFACE`|add_library|**我自己不用**；只有链接我的外部目标需要这个头文件。比如只有头文件的header‑only库。|

> 可执行程序没有别的目标来链接它，所以exe的target_include_directories永远用PRIVATE。

# 三、各种常见错误场景复盘

## 场景1：只include头文件，CMake没加对应的cpp

```cpp
// main.cpp
#include "utils/logger.h"
```

```cmake
add_executable(NexusLM src/main.cpp)
# 漏掉 src/utils/logger.cpp
```

✅ main.cpp编译成功（有头文件声明）
❌ 链接错误 `undefined reference`，没有logger.o。

## 场景2：CMake加了cpp，但是没有设置target_include_directories

```cmake
add_executable(NexusLM
    src/main.cpp
    src/utils/logger.cpp
)
# 没有 target_include_directories
```

main.cpp写 `#include "utils/logger.h"` → **编译报错，找不到头文件**。
只能丑陋写 `#include "../utils/logger.h"`，脆弱，移动文件就崩。

## 场景3：命名空间不匹配，链接找不到符号

头文件在 `namespace nexus`，cpp实现没包namespace。
编译正常，链接undefined reference。
> 头文件和cpp实现必须在完全一样的命名空间。

## 场景4：target_include_directories写在add_executable前面

```cmake
target_include_directories(NexusLM PRIVATE ${PROJECT_SOURCE_DIR}/src)
add_executable(NexusLM src/main.cpp)
```

❌报错，目标还未创建。**顺序：先创建目标，再设置属性**。

## 场景5：静态库链接顺序错（旧gcc ld）

```cmake
target_link_libraries(NexusLM PRIVATE utils net)
add_executable(NexusLM src/main.cpp)
```

❌ 目标还不存在。正确顺序：先add_executable，再target_link_libraries。

> 传统ld链接器：依赖库放在被使用者后面。现代CMake会帮你处理，但是代码顺序依然要求：**先创建目标，再操作目标属性**。

# 四、头文件的特殊情况：Header‑Only 库

全部代码写在h，没有cpp（模板库如eigen）。
不需要add_executable/add_library添加源文件，只需要设置include目录。

```cmake
add_library(my_header_lib INTERFACE)
target_include_directories(my_header_lib INTERFACE ${PROJECT_SOURCE_DIR}/include)
```

其他目标 `target_link_libraries(xxx PRIVATE my_header_lib)`，自动拿到头文件路径。

> 模板代码必须放头文件，实例化在编译阶段完成，不需要链接。

# 五、完整总结工作流

1. `.h`：放类、函数**声明**；参与预处理；**不会编译成obj**。cpp通过`#include`引入声明。
2. `.cpp`：放**实现定义**；CMake必须把cpp加到add_executable / add_library，编译为`.o`目标文件。
3. `target_include_directories()`：告诉C++编译器去哪里搜索`#include <>"xxx.h"`，**只管编译，不参与链接**。
4. `target_link_libraries()`：告诉**链接器**，把静态库/动态库合并进最终程序。
5. 编译阶段报错：找不到头文件、语法错误。
6. 链接阶段报错：`undefined reference`，缺少cpp参与编译/命名空间错误/库没链接。

## 记忆口诀
>
> `#include` 拿声明，只管编译不管链；
> add‑exe加cpp，编译obj供链接；
> target‑include找头文件；
> target‑link 干链接。
