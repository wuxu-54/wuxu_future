# 不同库类型的简单说明

这五种目标类型，代表了从**“原始编译产物”**到**“最终交付物”**的不同阶段。理解它们的核心区别，关键在于搞清楚**“编译（Compile）”**和**“链接（Link）”**这两个阶段发生了什么。

为了让你一目了然，我先用一句“大白话”总结，再逐层深入：

- **可执行文件**：**终点**，有 `main`，能独立运行。
- **静态库**：**搬运工**，编译好的代码被打包，但在链接时会被**完整或部分地复制**进最终的可执行文件里。
- **动态库**：**临时工**，编译好的代码独立存在，链接时只记录地址，**运行时**才加载进来。
- **接口库**：**空壳子**，没有 `.cpp` 代码，只用来传递头文件路径、宏定义和编译选项。
- **对象库**：**半成品池**，只编译成 `.o/.obj`，既不打包也不链接，专门用来**喂给**其他目标，避免重复编译。

---

## 1. 可执行文件 (`add_executable`)

这是最直观的目标。

- **产物**：`.exe`（Windows）或无后缀（Linux/macOS）。
- **入口**：必须包含 `main` 或 `WinMain` 函数。
- **行为**：链接器会把所有引用的库（静态库中的代码、动态库的符号表）全部解析，生成一个可以直接被操作系统加载运行的文件。
- **依赖传递**：它是终点，不传播依赖给其他目标。

## 2. 静态库 (`STATIC`) vs 动态库 (`SHARED`)

这是传统意义上两种完全不同的二进制复用方式。

| 特性 | **静态库 (`STATIC`)** | **动态库 (`SHARED`)** |
| :--- | :--- | :--- |
| **产物** | `.lib`（Windows）或 `.a`（Linux/macOS） | `.dll`（Windows）或 `.so`（Linux）或 `.dylib`（macOS） |
| **链接时机** | **构建时（Build time）**：链接器把库中用到的代码拷贝进你的 exe。 | **运行时（Runtime）**：链接器只检查符号是否存在，真正的代码在程序启动时由系统动态加载。 |
| **物理体积** | 你的 exe 体积会**变大**。 | 你的 exe 体积**较小**，但必须带着独立的 `.dll/.so` 文件一起分发。 |
| **更新维护** | 修改了库的代码，必须**重新编译整个 exe**。 | 只要接口（头文件）不变，替换 `.dll/.so` 文件即可，**无需重编 exe**（热更新）。 |
| **内存占用** | 多进程各自拷贝，内存占用高。 | 多进程可共享同一份内存中的代码段，内存占用低。 |
| **链接时的坑** | 相对简单，只需要把 `.a/.lib` 喂给链接器。 | Windows 下需要导出表（`__declspec(dllexport)`），Linux 下需注意隐藏符号；且必须解决循环依赖问题（链接器顺序敏感）。 |

---

## 3. 接口库 (`INTERFACE`)

这是 CMake 中非常“现代”且“轻量”的设计，它在物理磁盘上**不产生任何编译产物**（没有 `.o`，没有 `.a`，也没有 `.so`）。

- **它用来干什么**？专门为了**仅有头文件的库（Header-Only Library）**设计的，比如大名鼎鼎的 `Eigen` 或 `nlohmann/json`。
- **工作原理**：它像一个“容器”，用来存放 `target_include_directories`、`target_compile_definitions` 和 `target_link_libraries`。当你的可执行文件 `target_link_libraries` 链接这个接口库时，实际上**不是链接二进制文件**，而是**继承了接口库里设置的所有编译参数和头文件路径**。
- **经典用法**：

    ```cmake
    add_library(Eigen INTERFACE)
    target_include_directories(Eigen INTERFACE ${CMAKE_CURRENT_SOURCE_DIR}/include)
    # 之后 main_app 只要 link Eigen，就能自动找到 include 下的头文件
    ```

---

## 4. 对象库 (`OBJECT`) —— 性能优化的利器

这是大多数开发者容易忽视但极其好用的类型。它位于**编译（Compile）**和**链接（Link）**的中间夹层。

- **产物**：生成 `.o`（Linux）或 `.obj`（Windows）**目标文件**，但**不进行**归档（`ar`）或链接（`ld`）操作。
- **核心价值**：**“一次编译，多处链接”**。
- **痛点解决**：假设你有一个 `common.cpp`，既要放进静态库 `libA.a`，又要放进动态库 `libB.so`，还想让 `my_app.exe` 用一份。如果不用对象库，`common.cpp` 会被反复编译 3 次（编译极其耗时）。如果用了对象库：

    ```cmake
    add_library(my_objects OBJECT src/common.cpp)
    # 该命令会生成 common.o，但不打包

    # 直接在多个目标中复用这些 .o 文件
    add_library(static_lib STATIC $<TARGET_OBJECTS:my_objects>)
    add_library(shared_lib SHARED $<TARGET_OBJECTS:my_objects>)
    add_executable(my_app main.cpp $<TARGET_OBJECTS:my_objects>)
    ```

    此时，`common.cpp` 只会被**编译 1 次**，生成的 `.o` 被同时喂给了静态库、动态库和可执行文件，极大加快了大型项目的构建速度。

---

## ⚠️ 特别警告：对象库与位置无关代码 (`-fPIC`)

这是使用对象库时最容易踩的坑。在 Linux 上编译动态库（SHARED）时，**必须**加上 `-fPIC` 编译选项（位置无关代码），而静态库通常不需要。

如果直接用对象库编译出的 `.o` 去构建动态库，可能会报错 `relocation R_X86_64_32 against ... cannot be used when making a shared object`。

**解决方案**：创建对象库时，显示开启 `POSITION_INDEPENDENT_CODE` 属性：

```cmake
add_library(my_objects OBJECT src/common.cpp)
set_target_properties(my_objects PROPERTIES POSITION_INDEPENDENT_CODE ON)
```

这样生成的 `.o` 既可以被静态库链接，也可以安全地被动态库链接。

## 📊 终极对比总结表

| 目标类型 | 是否编译 `.o` | 是否链接/归档 | 是否产出独立文件 | 是否有 `main` | 主攻场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **可执行文件** | ✅ 是 | ✅ 是（最终链接） | ✅ `.exe`/无后缀 | **必须有** | 最终交付给用户运行 |
| **静态库** | ✅ 是 | ✅ 是（归档打包） | ✅ `.a`/`.lib` | 不需要 | 分发源码编译产物，追求简单部署 |
| **动态库** | ✅ 是（需 `-fPIC`）| ✅ 是（生成动态符号表） | ✅ `.so`/`.dll` | 不需要 | 多进程共享、减少内存、热更新 |
| **接口库** | ❌ 否 | ❌ 否 | ❌ 无 | 不需要 | 纯头文件库，或抽象依赖组合 |
| **对象库** | ✅ 是 | ❌ **只编译，不链接** | ✅ `.o`/`.obj` | 不需要 | **构建提速**，避免重复编译公共源码 |

**一句话落地建议**：
如果项目不大，只用 `EXE` + `STATIC`/`SHARED` 就够了；如果项目编译耗时严重（比如几百个 `.cpp` 被多个库共用），**优先考虑把公用部分抽出来做成 `OBJECT` 库**；如果引入的是只带 `.h` 的第三方库，**坚决使用 `INTERFACE` 库**来传递路径，不要画蛇添足地生成空 `.a` 文件。
