# 前向声明（forward‑declaration）

```
namespace nexus {
class MetricsCollector;   // ✅这就是前向声明
}
```

>
> **只告诉编译器：在 `nexus` 命名空间下，有一个叫 `MetricsCollector` 的类存在。不给类的完整定义，不写类里面有什么成员、方法。**

对比完整类定义：

```
// 完整定义（需要#include头文件才会得到）
namespace nexus {
class MetricsCollector
{
public:
    void collect();
private:
    int a;
    std::mutex mtx;
};
}
```

## 前向声明能干什么 / 不能干什么

### ✅可以做（只需要“知道这是一个类名”，不需要知道类大小和内部结构）

1. 定义**指针**：`MetricsCollector* ptr;`
2. 定义**引用**：`MetricsCollector& func();`
3. 函数形参是指针/引用：`void set_collector(MetricsCollector* c);`
4. 函数返回值是指针/引用
5. 用作 `std::unique_ptr<MetricsCollector>` 的模板参数（PIMPL就是靠这个）

>
> 这些场景编译器**不需要知道这个类占多大内存，内部有什么成员**。只知道这是一个类类型即可。

### ❌绝对不能做（需要类完整定义）

1. 创建对象：`MetricsCollector obj;` 编译器不知道类大小，无法分配栈内存
2. 访问成员：`ptr->collect();`，编译器不知道有这个成员函数
3. 继承它：`class A : public MetricsCollector {};`
4. 按值传参：`void f(MetricsCollector obj);` 需要拷贝，需要知道类大小
5. `std::vector<MetricsCollector>` 容器要构造对象，需要完整定义

👉 只要做上面这些操作，就必须 `#include "metrics_collector.h"`，拿到类完整定义。

# 放到你这段注释的业务场景理解

```
namespace nexus {
class MetricsCollector;
// 注意：此文件仅用于前向声明。
// 实际的 C API 指标接口请使用 nexus_api.h 中的 nexus_get_metrics()
// C++ 层请使用 NexusEngine::get_metrics()
} // namespace nexus
```

业务意图解读：

1. 这里**不include MetricsCollector真正的头文件**，仅仅告诉编译器“有这么个类”。
2. 代码里只会用到 `MetricsCollector*` / `MetricsCollector&` / `unique_ptr<MetricsCollector>`，典型就是 **PIMPL模式**。
3. **不让使用者直接使用 MetricsCollector 这个C++类本身！**>

> 注释写得很清楚：不要直接操作这个类；
>
>
> - C语言调用方：用C API函数 `nexus_get_metrics()`
> - C++调用方：通过 `NexusEngine::get_metrics()` 获取接口。

`MetricsCollector` 是**内部实现类**，对外不暴露完整头文件。对外只给前向声明，用户拿的只能是指针/引用，不能直接实例化、访问内部成员。

>
> 这就是PIMPL/不透明类型（opaque‑type）的玩法，常见于SDK、JNI动态库。

## 举个例子，你的对外头文件中可以写：

```
// 对外头文件，不include MetricsCollector真正的h
namespace nexus {
class MetricsCollector;

class NexusEngine{
public:
    // 返回引用/指针，只需要前向声明，不需要完整类定义
    MetricsCollector& get_metrics();
};
}
```

使用者：

```
#include "nexus_engine.h"

int main(){
    auto& metrics = nexus::NexusEngine::get_metrics();
    // metrics.collect(); // ❌编译报错！这里只有前向声明，看不到类成员！
    // 用户不能直接调用内部方法，只能走封装好的API
}
```

真正的 `MetricsCollector` 完整定义放在 `.cpp` 文件内部，或者内部私有头文件，SDK使用者拿不到。

## 前向声明 vs #include

| 方式 | 作用 | 代价 |
| --- | --- | --- |
| `class MetricsCollector;` 前向声明 | 告诉编译器类名字；**不给实现** | 不会引入别的头文件，减少编译依赖；但只能用指针、引用 |
| `#include "metrics_collector.h"` | 拿到类完整定义，可以实例化、调用成员 | 引入整个头文件，触发依赖链，头文件一变，所有引用文件重编译 |

>
> 工程原则：能前向声明就不要include，减少编译耦合。只有当你要创建对象、访问成员时，才必须include。

## 面试一句话总结

>
> 前向声明仅仅向编译器告知类/函数名字，**不提供完整定义**，仅支持指针、引用语义；不能实例化对象、访问成员；用来降低头文件依赖，是PIMPL模式的基础。

### 补充小坑

1. 前向声明**必须放在同一个namespace**。

```
class MetricsCollector; // 错误！全局命名空间，不是 nexus::MetricsCollector
namespace nexus {
class MetricsCollector; // ✅正确
}
```

2. 只可以前向声明类；**类的成员函数、成员变量不能前向声明**。
3. C语言的不透明类型：`typedef struct MetricsCollector MetricsCollector;`，思想等价C++前向声明。
