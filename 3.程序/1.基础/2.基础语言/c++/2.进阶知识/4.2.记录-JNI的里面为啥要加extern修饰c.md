# `#ifdef __cplusplus extern "C" { #endif`

这是 **C/C++混合编程、JNI场景必见的代码**，JNI的C API头文件大量使用这个写法。

```c
#ifdef __cplusplus
extern "C" {
#endif

// 这里放函数声明

#ifdef __cplusplus
}
#endif
```

## 核心背景：名字修饰（name‑mangling）

- **C++编译器**：会对函数名做**名字改编(mangling)**。
比如函数 `int add(int a,int b)`，C++编译后符号变成类似 `_Z3addii`。支持重载、类、命名空间。
- **C编译器**：**不做mangling**，函数符号就是原始函数名 `add`。

> JVM（Java）调用JNI动态库，它是按 **C语言符号名** 去找函数。
> 如果JNI头文件不加 `extern "C"`，C++编译器把函数名mangle改乱，so库里面符号名字变了 → Java运行时报 `UnsatisfiedLinkError`，找不到native函数。

## 逐段拆解

```cpp
#ifdef __cplusplus
```

`__cplusplus` 是**C++编译器内置宏**。

- 使用g++/clang++编译（C++模式）：该宏被定义，进入条件内代码。
- 使用gcc编译（纯C模式）：没有这个宏，跳过里面的`extern "C"`。

```cpp
extern "C" {
```

`extern "C"` 告诉**C++编译器**：**大括号里面的函数，按C语言规则编译，不要做C++名字mangling**。
> ⚠️注意：`extern "C"` 只对**函数、变量的链接符号名生效**，里面依然可以写C++语法代码，只是导出符号是C风格。

大括号 `{ }` 是作用域，里面所有函数声明都受extern "C"影响。

```cpp
#ifdef __cplusplus
}
#endif
```

C++编译的时候，补上右大括号，结束`extern "C"`作用域；C编译直接忽略这一行。

## 示例对比

### 头文件 `nexus_api.h`

```c
#ifdef __cplusplus
extern "C" {
#endif

// C API，给JNI / C调用
int nexus_get_metrics(char* out_buf, int buf_len);

#ifdef __cplusplus
}
#endif
```

1. **用C++编译器(g++)编译此头文件**
展开后：

```cpp
extern "C" {
int nexus_get_metrics(char* out_buf, int buf_len);
}
```

→ 导出符号名：`nexus_get_metrics`（C原始名字，JVM可以找到）

2. **用C编译器(gcc)编译**
`__cplusplus`未定义，直接得到：

```c
int nexus_get_metrics(char* out_buf, int buf_len);
```

C编译器不认识`extern "C"`，所以这一段被完全跳过。

> ✅一份头文件，可以同时给C代码、C++代码使用，兼容性处理。

## ⚠️重要限制（面试高频）

1. `extern "C"` **不能写C++重载函数**。C没有函数重载，多个同名函数会冲突。

```c
extern "C" {
void foo(int);
void foo(double); // ❌ 编译错误！C不支持重载
}
```

2. `extern "C"` 只改**链接符号名**，**不会把C++代码变成C代码**。

```cpp
extern "C" {
// 声明是C链接，但实现cpp内部依然可以写完整C++代码！
void nexus_get_metrics(char* out_buf, int buf_len)
{
    std::string str; // ✅ 这里面随便写C++，std::string、类都能用
}
}
```

> 你的JNI场景就是这样：函数导出符号是C，函数体内全部写C++业务逻辑。

3. **类、成员函数不能直接放在extern "C"大括号内部**。只能放全局函数、全局变量。

```cpp
extern "C" {
class AAA {}; // ❌非法，类不能放extern"C"里面
}
```

4. JNI的 `Java_com_xxx_xxx()` JNI导出函数，**必须包在extern "C"里面**！

> 不包的话 g++会mangle函数名，动态库符号名字错乱，Java直接报找不到实现。

### JNI典型完整示例

```cpp
#ifdef __cplusplus
extern "C" {
#endif

JNIEXPORT jint JNICALL
Java_com_example_NativeBridge_nativeDoWork(JNIEnv* env, jobject thiz)
{
    // 内部调用C++ PIMPL的NexusEngine业务代码
    nexus::NexusEngine engine;
    return 0;
}

#ifdef __cplusplus
}
#endif
```

## 常见误区
>
> ❌误区：`extern "C"`代表代码会被C编译器编译。
✅真相：只是告诉C++编译器：**导出符号使用C的命名规则**，函数体依旧是C++编译。

> ❌误区：加了extern"C"就可以在C里面调用C++类。
✅真相：C只能调用extern"C"修饰的**全局C链接函数**；C代码看不到C++类、引用、重载。C只能拿到普通C函数接口，作为C++的外层包装。

# 和你之前项目的结合

你项目的设计：

1. `nexus/xxx.h`：C++对外头文件，namespace nexus，PIMPL，C++接口，给C++代码调用。
2. `nexus_api.h`：C风格API头文件，套上 `#ifdef __cplusplus extern "C"`，**剥离C++特性，提供纯C全局函数**。

> JNI的cpp文件include这个`nexus_api.h`，实现C接口；Java通过JNI调用这些C‑linkage函数，函数内部再去调用C++的`nexus::NexusEngine` C++类。

> 分层：Java ↔ JNI(C链接函数) ↔ C++ PIMPL业务层。

## 一句话总结

`#ifdef __cplusplus extern "C" { #endif`
> 兼容头文件写法：**当被C++编译器编译时，把大括号内全局函数按C语言符号规则导出，关闭C++名字mangling；C编译器编译时直接忽略这部分。主要用于JNI、给C调用的C++库，防止动态库符号找不到。**
