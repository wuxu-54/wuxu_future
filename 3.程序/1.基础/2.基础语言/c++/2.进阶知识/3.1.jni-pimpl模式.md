# PIMPL 模式（Pointer‑to‑Implementation，指向实现的指针）

也叫 **d‑pointer（d指针）**、**防火墙模式**。

>
> 核心思想：**把类的全部私有成员（私有变量、私有函数），全部挪到另外一个实现类里面；对外暴露的接口类，只持有一个指向实现类的指针。**

对外头文件只留**公开接口**，实现细节全部隐藏到 `.cpp` 文件内部。

## 为什么要用 PIMPL（解决什么痛点）

传统写法问题：

- 头文件 `.h` 里面会放所有私有成员变量、私有函数。
- 只要**私有成员改动**，头文件就要修改 → **所有include这个头文件的全部源文件，都要重新编译**（编译爆炸）。
- 内部依赖的头文件全部暴露给调用方，污染依赖。
- 做SDK库的时候，不想暴露内部私有数据结构。

PIMPL收益：

1. **减少编译依赖，缩短编译时间**：修改私有实现，对外`.h`不动，使用者不需要重编译。
2. **完全隐藏内部实现细节**：对外头文件干净，内部结构体、私有成员放在cpp，不对外暴露。
3. 可以做到**ABI稳定**（做动态库 `.so`/`.dll` 非常重要，JNI动态库场景非常适合），升级库，头文件不变，二进制可以直接替换so。
4. 隔离复杂第三方头文件，对外头文件干净。

代价：

- 多一次堆内存分配（实现类在堆上）；
- 间接指针访问，微小运行时开销；
- 需要手写析构、拷贝/移动语义，容易出错。

# 传统写法（反例，没有PIMPL）

```
// nexus_logger.h 对外头文件
#include <mutex>   // ❌ 内部锁，却暴露给所有include本头文件的使用者
#include <string>

namespace nexus {

class Logger {
public:
    void info(const std::string& msg);
    void set_level(int lvl);
private:
    std::mutex m_mtx;        // 私有成员，写在头文件！
    int m_log_level;         // 私有成员
    void write_file(const std::string& s); // 私有方法
};

}
```

问题：
只要我修改私有成员：比如增加一个成员变量，或者删掉`write_file`。
👉 `nexus_logger.h`发生变化。**只要#include这个头文件的所有cpp全部要重新编译**。
同时使用者被迫间接引入`<mutex>`、`<string>`等头文件。

# PIMPL完整标准写法

>
> 对外头文件：只放公开接口，前向声明内部实现类，持有唯一指针。
> 所有私有变量、私有函数，全部放在cpp文件里面的实现类。

## 头文件 `nexus_logger.h`（对外，includes目录）

```
#pragma once
#include <string>

namespace nexus {

// ✅前向声明！不包含实现，不需要#include一堆内部头文件
class LoggerImpl;

class Logger {
public:
    Logger();
    ~Logger();

    // 接口
    void info(const std::string& msg);
    void set_level(int lvl);

    // ------------------------------
    // PIMPL类，拷贝、移动必须显式处理！
    // 指针成员默认拷贝是浅拷贝，会double free！
    // 方案1：禁止拷贝，只允许移动
    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;
    Logger(Logger&&) noexcept;
    Logger& operator=(Logger&&) noexcept;

private:
    LoggerImpl* m_impl; // ⭐指向实现的指针，仅此一个私有成员！
};

}
```

>
> 头文件看不到任何`std::mutex`，看不到内部成员。
> 就算LoggerImpl内部成员疯狂修改，这个头文件**完全不变**！所有使用者不需要重编译。

## cpp实现文件 `nexus_logger.cpp`（内部源码，不对外）

```
#include "nexus_logger.h"
#include <mutex>
#include <fstream>

namespace nexus {

// ✅真正的实现类，全部私有成员放这里，只在cpp内部可见
class LoggerImpl
{
public:
    std::mutex m_mtx;
    int m_log_level{0};
    std::ofstream m_out_file;

    void info(const std::string& msg)
    {
        std::lock_guard<std::mutex> lock(m_mtx);
        // 写日志逻辑
    }

    void set_level(int lvl)
    {
        m_log_level = lvl;
    }
};

// Logger对外类的实现
Logger::Logger()
    : m_impl(new LoggerImpl()) // 堆上创建实现对象
{
}

Logger::~Logger()
{
    delete m_impl;
}

// 移动构造
Logger::Logger(Logger&& other) noexcept
    : m_impl(other.m_impl)
{
    other.m_impl = nullptr;
}

// 移动赋值
Logger& Logger::operator=(Logger&& other) noexcept
{
    if(this == &other) return *this;
    delete m_impl;

    m_impl = other.m_impl;
    other.m_impl = nullptr;
    return *this;
}

// 对外接口全部转发调用impl
void Logger::info(const std::string& msg)
{
    m_impl->info(msg);
}

void Logger::set_level(int lvl)
{
    m_impl->set_level(lvl);
}

}
```

## 使用方代码

```
#include "nexus_logger.h"

int main()
{
    nexus::Logger log;
    log.set_level(1);
    log.info("hello pimpl");
    return 0;
}
```

使用者完全感知不到`LoggerImpl`的存在。

# 用unique_ptr简化PIMPL（现代C++，C++11及以后）

原始裸指针要手动管理内存，容易内存泄漏、double‑free，推荐`std::unique_ptr`。

>
> ⚠️重要坑：如果头文件只用unique_ptr前向声明类，**析构函数不能写在头文件内，必须在cpp实现！**
> 因为unique_ptr的默认删除器需要看见完整类定义。

### 头文件

```
#pragma once
#include <string>
#include <memory>

namespace nexus {
class LoggerImpl;

class Logger {
public:
    Logger();
    ~Logger(); // ❗只声明，绝对不要写 ~Logger() = default; 在头文件！

    void info(const std::string& msg);
    void set_level(int lvl);

    // unique_ptr不支持拷贝，拷贝直接delete；可以支持移动
    Logger(Logger&&) noexcept;
    Logger& operator=(Logger&&) noexcept;
    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;

private:
    std::unique_ptr<LoggerImpl> m_impl;
};

}
```

cpp里面：

```
#include "nexus_logger.h"
// LoggerImpl完整定义在这里
class LoggerImpl { /* ... */ };

Logger::Logger()
    : m_impl(std::make_unique<LoggerImpl>())
{}

// 析构函数的default写在cpp里面！！
Logger::~Logger() = default;

Logger::Logger(Logger&&) noexcept = default;
Logger& Logger::operator=(Logger&&) noexcept = default;

// 接口转发
void Logger::info(const std::string& msg) { m_impl->info(msg); }
```

>
> 千万不要：头文件写`~Logger() = default;`，此时编译器看不到LoggerImpl完整类型，编译报错。析构必须放到cpp。

# PIMPL 单例结合你的JNI场景（你项目的实际场景）

你之前写的`nexus::Logger`单例，如果用PIMPL：

- `includes/nexus_logger.h`对外头文件，JNI代码include这个头；
- 内部`LoggerImpl`全部实现在cpp；
- 你编译动态库`libNexusLM.so`；
- Java JNI调用这个库；
- 后续修改日志内部逻辑、增加成员变量，对外头文件不变，**不需要重新编译JNI的调用代码，直接替换so即可**。非常适合JNI动态库，ABI稳定。

## PIMPL 核心坑清单（面试高频）

1. **前向声明的类，unique_ptr析构不能放在头文件**，否则编译报错。
2. 裸指针版本：默认拷贝构造会浅拷贝两个对象指向同一个Impl，析构两次 → double free崩溃。所以必须delete拷贝构造，或者实现深拷贝。
3. Impl对象是new在堆上，多了一次堆分配开销。
4. 所有对外接口只是简单**转发调用impl的同名函数**，有一层间接。
5. ABI稳定：对外类的大小永远固定（只是一个指针/unique_ptr，8字节64位），不管Impl里面加多少成员，对外对象大小不变，动态库ABI兼容。

>
> ABI稳定关键点：对外暴露的类，**大小不能变化**。PIMPL对外类永远只有一个指针，大小固定；如果不用PIMPL，头文件加一个私有成员，类大小改变，旧的二进制调用so直接崩溃。做JNI动态库这个点非常重要。

## PIMPL对比其他模式

1. **Opaque type（不透明类型，C语言方式）**：C里面`typedef struct Logger Logger;`，和PIMPL思想几乎一样。
2. 桥接模式Bridge设计模式：PIMPL是Bridge模式在C++的一个特殊轻量化实现。

## 什么时候不建议PIMPL

- 很小的数据类、值语义类（简单DTO结构体），没必要。
- 极致性能，大量高频调用，不能承受指针间接开销。

## 一句话总结PIMPL

>
> 对外类头文件只保留公开接口，前向声明实现类；把所有私有成员、私有逻辑全部放到cpp内部实现类；对外类只保存一个指向实现类的指针；修改内部实现不用改动对外头文件，降低编译耦合，动态库实现ABI稳定。
