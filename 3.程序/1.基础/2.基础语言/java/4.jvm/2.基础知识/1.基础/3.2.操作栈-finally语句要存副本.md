# 为什么必须 2:iload_1 + 3:istore_2

源码片段：

```java
public int foo() {
    int x;
    try {
        x = 1;
        return x;// 最终返回仍是1，不会是3
    } catch (Exception e) {
        x = 2;
        return x;// 最终返回仍是2，不会是3
    } finally {
        x = 3;
    }
}
```

编译后的class结构：

```java
public int foo();
  descriptor: ()I
  flags: ACC_PUBLIC
  Code:
    stack=1, locals=4, args_size=1
       0: iconst_1          // 常量1压栈
       1: istore_1          // x = 1  slot1=x
       2: iload_1           // 把x=1压入栈，【保存返回值副本！】
       3: istore_2          // ✅关键点：返回值临时保存到slot2！！
       4: iconst_3          // finally逻辑 x=3
       5: istore_1          // x =3
       6: iload_2           // 取出预先存好的返回副本 1
       7: ireturn           // return 1

       8: astore_3          // catch(Exception e)，异常存入slot3(e)
       9: iconst_2          // x=2
      10: istore_1          // slot1 x=2
      11: iload_1           // x=2压栈，准备返回
      12: istore_2          // 返回值副本保存 slot2 = 2
      13: iconst_3          // finally：x=3
      14: istore_1          // x=3
      15: iload_2           // 取出副本2
      16: ireturn           // return 2

      17: astore_2          // 其他所有异常Throwable存入slot2
      18: iconst_3          // finally x=3
      19: istore_1          // x=3
      20: aload_2           // 加载原始异常
      21: athrow            // 把异常继续抛出
    Exception table:
       from    to  target type
           0     4     8   Class java/lang/Exception   //0‑3发生Exception跳8
           0     4    17   any                       //0‑3其他异常跳17
           8    13    17   any                       //catch块内部抛异常跳17
```

> 1. Java语法逻辑：**执行return之前，必须先完整跑完finally，才能真正return退出方法**。
> 2. **finally 给 x 赋值 3，但是不会改变 return 返回值！**
> 3. Java 的规则：执行 return 前，会**预先把返回值保存副本**，之后 finally 再修改局部变量 x，不影响已经保存好的返回副本。

❗矛盾来了：

- `return x`：我要返回此刻x的值（=1）。 注意：实际返回的是1,finally对变量的修改不影响原有结果，这是java的语义要求。
- 但是！JVM不能立刻执行`ireturn`返回！**必须先跳过去跑finally代码块（偏移4‑5）**
- finally代码会修改 slot1(x)，把x改成3。

如果没有2、3这两条指令，设想错误版本：

```java
0: iconst_1
1: istore_1   // slot1(x)=1
// ❌这里不能直接 iload_1 + ireturn！！因为还没跑finally！
4: iconst_3
5: istore_1   // slot1(x)=3
6: iload_1    // 这时x已经变成3！
7: ireturn
```

那最后返回就变成`3`，**违背Java语言语义！**

---

## 指令2、3到底做了什么

```
2: iload_1   // 把slot1(x=1)压入操作数栈
3: istore_2  // 把栈顶1保存到 slot2【临时缓存槽】
```

👉**提前把要返回的结果复制一份，存到独立的slot2！**

- slot1：原始变量x，接下来会被finally肆意修改（变成3）
- slot2：**副本，死死保存住我们要返回的值 1，不受finally代码任何改动影响**

执行时序：

1. `x=1` 存入slot1
2. 把返回值1拷贝副本 → slot2固定死
3. 跑去执行finally：修改slot1 x=3（**只改原变量，碰不到slot2副本**）
4. 全部finally跑完，真正要返回的时候：`iload_2`，拿出副本`1`，`ireturn`返回。

> slot2是javac编译器自动生成的临时局部变量，你的Java源代码看不见。

## 用通俗人话讲
>
> “我现在打算返回1，但是我不能直接走，我得先把finally里面的代码跑完。
> 但是finally会把x改掉，我先把答案抄写一份放到别的地方锁起来。
> 等finally折腾完，我再拿出抄写好的答案返回，不理会x现在变成啥。”

### 流程图

```
x(slot1)=1
    ↓
【复制返回结果副本 slot2 = 1】 ←-- 就是iload_1 + istore_2
    ↓
执行finally → x(slot1)=3（原变量被改，副本不动）
    ↓
读取副本slot2=1 → ireturn 返回1
```

## 再思考：为什么不能把返回值放操作数栈？

操作数栈是临时的！一旦跳转到finally的指令序列，中间会执行iconst_3、istore_1，**操作数栈会被清空、复用**。栈上的值保存不住。
> 操作数栈：函数执行中间临时空间；局部变量表slot才可以长期保存数据。
所以必须存进局部变量表slot2，把返回结果“持久化”下来，熬过finally代码块的执行。

## 补充：如果没有finally，字节码是什么样？

```java
public int foo(){
    int x=1;
    return x;
}
```

字节码：

```
0: iconst_1
1: istore_1
2: iload_1
3: ireturn
```

这里**没有istore_2，没有slot2副本**。
没有finally，不需要插入额外代码，读到栈顶直接返回完事，不需要保存副本。

> ✔有finally的return，编译器才会插入这对指令，预拷贝返回值到额外slot。

## 延伸：catch分支也是一模一样

```java
catch(Exception e){
    x=2;
    return x;
}
finally{x=3;}
```

字节码：

```
11: iload_1     //x=2压栈
12: istore_2    //副本存入slot2=2
13: iconst_3
14: istore_1    //finally修改x=3
15: iload_2     //拿副本
16: ireturn
```

逻辑完全一样：**先拷贝返回结果副本，再跑finally，最后返回副本**。

## 面试一句话总结
>
> 因为return后必须先执行finally，finally会修改原始局部变量x；
> 操作数栈不能保存值，所以编译器用`iload_1 + istore_2`，**提前把返回值拷贝到独立局部变量slot2做副本**；
> finally修改原来的slot1，不会影响副本；等finally执行完毕，读取副本返回。

### 灵魂坑点
>
> 很多人误以为return直接返回；在带finally的场景，return不是立刻返回，是**先保存预期返回值，执行finally，再真正返回**。
> 如果finally内部写return，会覆盖slot2里预先保存好的副本，造成bug。
