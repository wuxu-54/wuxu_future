# Android Binder 核心原理详解

## 一、Binder定位

Binder 是 Android 自研的**进程间通信IPC框架**，基于Linux内核驱动`/dev/binder`，主打 **RPC远程过程调用**，采用C/S架构。
> 核心目标：让客户端可以像调用本地方法一样调用另一个进程中的函数；解决传统Linux IPC多次拷贝、缺少RPC语义、安全弱的问题。
> 前提：进程之间虚拟内存空间隔离，进程A不能直接访问进程B内存，必须借助内核中转。

## 二、Binder四大核心角色

1. **Binder驱动（内核模块，/dev/binder）**
    整个Binder通信的中转站、管理者。
    - 管理内核Binder节点`binder_node`、引用`binder_ref`、句柄handle
    - `mmap`内存映射，实现**一次内存拷贝**
    - 接收客户端事务，唤醒服务端Binder线程
    - 传递Binder引用（跨进程传递IBinder）、引用计数管理
    - 权限校验、死亡通知分发
    > 驱动本身**不解析业务数据**，只负责数据转发、线程调度、对象生命周期管理。

2. **ServiceManager（独立Native进程，特殊Binder服务）**
    Binder的**全局注册表**，开机由init启动。
    - 维护：`服务名字（字符串） ↔ Binder节点handle`
    - 对外仅2个接口：`addService`注册服务，`getService`查询服务
    - 固定handle=0，所有进程都知道这个特殊服务；**单线程串行处理请求**
    - 只存Binder引用，**不转发业务调用**。App拿到AMS的BinderProxy之后，App直接和AMS通信，不再经过ServiceManager。

3. **Server 服务端**
    提供服务、暴露可供远程调用接口的进程。
    Java层：`Stub extends Binder`；Native层：`BBinder`
    - 持有真正业务对象；
    - Binder驱动收到请求后回调`onTransact()`；
    - 服务端自带**Binder线程池**，处理客户端的IPC请求（默认最多16条线程）。
    例子：AMS、WMS属于SystemServer进程里的Binder服务；App中的`ApplicationThread`是App进程内的Binder服务。

4. **Client 客户端**
    发起远程调用的进程。
    Java层：`BinderProxy`；Native层：`BpBinder`
    - 拿到远端服务代理；调用代理方法触发IPC；
    - `transact()`发起事务，默认阻塞等待服务端返回。

> ✅ 重要：C/S是**接口维度**，不是进程维度。同一个进程，既可以是A接口的客户端，同时是B接口的服务端。
> 例：App进程
>
> - 作为客户端，调用AMS（IActivityManager）
> - 作为服务端，提供ApplicationThread（IApplicationThread）给AMS回调。

## 三、关键内核概念：binder_node / binder_ref / handle

1. **binder_node（Binder节点）**
    在内核中，**每一个Binder服务对象对应唯一binder_node**，代表服务本体。
    > AMS的Stub在内核就是一个binder_node，存在SystemServer进程一侧。

2. **binder_ref（Binder引用）**
    当别的进程拿到这个node，内核会在**客户端进程**创建`binder_ref`，代表“我引用了远端这个node”。

3. **handle**
    `handle`是**客户端侧的整数编号**，是binder_ref的id。客户端只知道handle，不知道node。
    - ServiceManager保存的就是名字→handle映射；
    - 客户端调用transact时，传入handle，驱动找到对应的binder_node。

简单一句话：
`binder_node`：服务本体（服务进程内核）
`binder_ref + handle`：客户端这边对服务的引用。

## 四、内存模型 & 为什么只一次拷贝（核心考点）

传统IPC（管道、Unix Socket）：
客户端用户空间 → 内核缓冲区（拷贝1）→ 服务端用户空间（拷贝2），**两次拷贝**。

Binder的mmap机制：

1. **服务端进程初始化Binder时调用binder_mmap**，在内核开辟一块共享缓冲区（内核buffer），并把这块内核缓冲区**映射到服务进程用户虚拟地址空间**。

> 这块内存，内核和服务进程可以直接访问。

2. 客户端发起IPC，将数据从**客户端用户空间拷贝到内核buffer**：**1次拷贝**。
3. 内核buffer已经映射在服务端虚拟地址，**不需要再拷贝**，服务进程直接读取这块内存。

> ⚠️ 注意：mmap只映射在**服务端**，客户端没有这块映射。数据只能客户端→内核一次拷贝。
> 限制：这块缓冲区大小默认 **1MB**，单次IPC传输数据不能超过该上限；大文件用ashmem。

> COW写时复制是fork的机制；mmap是Binder内存拷贝优化，不要把两者混淆。

## 五、Java层 Binder核心类关系

1. `IBinder`：顶层接口。定义`transact()`、`queryLocalInterface()`、linkToDeath（死亡监听）。
2. `Binder`：服务端基类（Stub父类），实现IBinder。
    - `onTransact()`：**服务端入口**，Binder驱动回调这个方法。
    - `attachInterface()` 绑定接口描述符。
3. `BinderProxy`：客户端代理类，实现IBinder。
    - 跨进程场景下，`ServiceManager.getService()`返回的IBinder实际就是BinderProxy；
    - `transact()` 调用native方法，进入内核发起IPC。
4. `IInterface`：业务接口父接口，AIDL生成的接口继承它。
5. AIDL自动生成3部分代码：
    - IXXXInterface：业务接口；
    - Stub extends Binder implements IXXXInterface：服务端；
    - Proxy implements IXXXInterface：客户端代理，持有BinderProxy。

### AIDL的asInterface核心逻辑

```java
public static IXXXInterface asInterface(IBinder obj) {
    if(obj == null) return null;
    IInterface local = obj.queryLocalInterface(DESCRIPTOR);
    if(local != null){
        // 同进程，直接返回本地Stub对象，不走IPC
        return (IXXXInterface)local;
    }
    //跨进程，new Proxy，包裹BinderProxy
    return new Proxy(obj);
}
```

## 六、一次标准同步Binder RPC完整流程（App调用AMS.startActivity）
>
> Client=App进程；Server=SystemServer，服务是AMS（IActivityManager.Stub）

1. App先拿到AMS代理：
    `ServiceManager.getService("activity")` → Binder IPC访问ServiceManager，查到AMS对应的binder_node，内核在App进程生成BinderProxy。
    `IActivityManager.Stub.asInterface(binderProxy)` → 得到IActivityManager.Proxy。

2. App调用`proxy.startActivity()`
    - 创建Parcel对象`_data`（存放入参）、`_reply`（接收返回值）；
    - 将接口token、Intent、IBinder等参数序列化写入`_data`；
    - 调用`mRemote.transact(TRANSACTION_startActivity, _data, _reply, 0)`
    - mRemote就是BinderProxy；**App线程阻塞在这里**。

3. BinderProxy进入native层，调用ioctl，陷入内核Binder驱动
    - 封装Binder事务包：目标handle、事务code、data；
    - 驱动根据handle找到SystemServer进程中的binder_node；
    - 将事务放入SystemServer的待处理队列，唤醒Binder线程池的一条线程。

4. SystemServer的Binder线程被唤醒
    - 读取内核缓冲区中的Parcel数据；
    - 回调AMS Stub的`onTransact(code, data, reply, flags)`。

5. onTransact内部
    - 根据code匹配`TRANSACTION_startActivity`；
    - 从data反序列化取出Intent、调用方等参数；
    - 执行AMS本地`startActivity`业务逻辑（权限校验、PMS查询、判断是否创建App进程等）；
    - 业务执行完，将返回结果写入reply，返回true。

6. 驱动把reply数据包原路送回App进程
7. App阻塞的transact调用返回，App线程恢复执行
    - App读取_reply中的返回值；
    - Parcel回收，调用结束。

时序简图：

```
App(Client)                Binder驱动                 SystemServer(Server,AMS)
proxy.startActivity()
    ↓
BinderProxy.transact()阻塞
    ↓ 数据拷贝到内核buffer
---------------------------->
                                            唤醒Binder线程池
                                            Stub.onTransact()
                                            AMS业务处理
                                            结果写入reply
    <----------------------------
transact返回，App线程继续运行
```

## 七、Binder线程池

1. **服务端进程在初始化Binder时，会预先启动Binder线程池**（SystemServer、App进程都有）。
2. 所有远端IPC请求，都在线程池中的线程执行，**不是主线程！**
    > ApplicationThread的回调跑在App的Binder线程，不能操作UI，必须Handler切主线程。
3. 线程池上限默认16个；线程由Binder驱动统一调度。
4. ServiceManager例外：**单线程，没有线程池**，请求串行排队。

## 八、Parcel & Binder引用传递 writeStrongBinder

`Parcel`是Android序列化载体，专门用于Binder通信，**不是Java Serializable**。
`writeStrongBinder(IBinder)`：跨进程传递Binder对象的核心API。
场景：`am.attachApplication(mAppThread)`，App把ApplicationThread（Stub）传给AMS。
底层逻辑：

1. App本地mAppThread是Stub（BBinder，binder_node在App进程内核）；
2. writeStrongBinder把这个Binder节点信息写入Parcel；
3. Binder驱动在接收方（AMS所在SystemServer）创建binder_ref和handle；
4. AMS这边读出来得到BinderProxy，包装成IApplicationThread.Proxy；
5. AMS后续就可以用这个Proxy，发起IPC回调App的ApplicationThread。

> 这就是**Binder引用跨进程传递**，是双向通信的基础。

## 九、DeathRecipient 死亡代理

当Binder服务端进程意外死亡（App crash），客户端可以收到通知。
原理：

1. 客户端调用`binder.asBinder().linkToDeath(deathRecipient, 0)`注册监听；
2. Binder驱动监控目标进程；
3. 如果服务进程死亡，驱动主动向客户端推送binderDied回调；
AMS给每一个App的ApplicationThread都注册DeathRecipient。App崩溃，AMS收到回调，清理任务栈、记录进程死亡信息。

## 十、两种事务模式：同步 / oneway异步

1. **默认（双向同步，flags=0）**
    client调用transact阻塞，等待server处理完返回reply。前面startActivity就是这种。
2. **oneway（单向异步）**
    AIDL接口加oneway关键字。
    - 客户端transact**不阻塞，不等返回结果**；
    - 服务端依旧在线程池执行；
    - 服务端处理完不会回包。
    > 注意：oneway只是客户端不阻塞，**服务端调用顺序串行**，服务端还是按顺序处理oneway请求。

## 十一、Binder的优缺点

✅ 优点

1. 一次内存拷贝，相比管道/Unix Socket性能更好；
2. 天然RPC模型，AIDL封装，像本地调用一样跨进程调用；
3. 内核支持pid/uid鉴权，安全可控；
4. 内核自动管理Binder引用计数，支持死亡通知；
5. 系统原生支持，Android系统服务全部基于Binder。

❌ 缺点

1. Android专属，非标准Linux IPC；
2. 传输上限1MB，不适合超大文件；
3. Binder驱动bug、线程池阻塞容易出现ANR（服务端线程卡住，客户端一直阻塞）。

## 十二、高频面试区分

1. Binder：RPC，一次拷贝；用于App ↔ AMS/WMS/PMS；
2. Unix域Socket：普通数据流，两次拷贝；AMS ↔ Zygote（fork进程场景，App进程还不存在，没有Binder线程）；
3. 共享内存shmem：无拷贝，无同步，需要自己加锁；适合大量数据。

## 十三、完整串联（App启动链路里Binder角色回顾）

1. init启动servicemanager；
2. SystemServer启动AMS，调用`ServiceManager.addService`注册AMS Binder；
3. AMS需要新建App进程，**Unix Socket通知Zygote fork**；
4. Zygote fork出新App进程，App执行ActivityThread.main，attach；
5. App调用`ServiceManager.getService("activity")`（Binder IPC）拿到AMS代理；
6. App调用`am.attachApplication(mAppThread)`（Binder IPC，传递App侧Binder服务ApplicationThread）；
7. AMS拿到ApplicationThread的Proxy，通过Binder IPC回调App，执行Activity生命周期。
