# ONNX

- 中文文档：<https://onnx.ai/onnx/intro/index.html>

## 一、ONNX 基础定义

ONNX（Open Neural Network Exchange，开放神经网络交换格式）是**跨训练框架、跨推理引擎**的中立神经网络存储标准，由微软、Meta、阿里、谷歌等联合推出。
核心作用：**一次训练，到处部署**
PyTorch/TensorFlow/Paddle → 导出ONNX → MNN/ORT/TFLite/NCNN/芯原NPU/苹果CoreML 全部可读取转换。

### 1. 文件本质结构

后缀 `.onnx`，底层是 **Protobuf 二进制序列化文件**
分层结构：

1. **ModelProto**：顶层模型容器
2. **GraphProto**：核心计算图（网络主体）
3. **NodeProto**：算子节点（Conv、ReLU、MatMul、Attention等）
4. **TensorProto**：权重/常量张量
5. **ValueInfoProto**：输入、输出张量形状、数据类型定义
6. **AttributeProto**：算子超参（卷积核大小、步幅、padding等）

可视化工具：**Netron**（必用，排查模型结构、输入输出shape、算子异常）

## 二、核心字段拆解（Graph）

### 1. inputs / outputs

记录输入输出张量名称、维度、dtype。
常见坑：

- PyTorch导出默认固定shape，移动端需要动态尺寸（摄像头画面不定宽高），必须配置 `dynamic_axes`
示例动态导出参数：

```python
torch.onnx.export(
    model, dummy_input, "model.onnx",
    opset_version=17,
    dynamic_axes={
        "input": {0: "batch", 2: "H", 3: "W"}, # batch、高、宽动态
        "output": {0: "batch"}
    }
)
```

### 2. initializers

存储全部权重、偏置、常量张量，FP32原始权重都存在这里，量化后会存储量化零点、缩放系数。
大模型（Qwen、Whisper）initializers体积占整个文件95%以上。

### 3. nodes 算子列表

计算顺序拓扑排序，每个node包含：

- op_type：算子类型 `Conv` / `Add` / `MatMul` / `Softmax` / `LayerNormalization`
- input：依赖张量名
- output：输出张量名
- attribute：算子配置

## 三、Opset 版本关键（极易踩坑）

Opset 是ONNX算子标准版本，不同版本支持算子有差异：

1. 越高Opset → 支持新算子越多（Transformer、GQA、RoPE等大模型算子）
2. 推理框架对高Opset兼容参差不齐：
   - MNN稳定适配：op15~op18
   - ONNX Runtime Mobile：op17+完美支持
   - TFLite转换上限偏低，高op容易算子不匹配

**实操规范**

- CV小模型(YOLO/MobileNet)：op15~17
- LLM/多模态(Qwen-VL、Whisper)：op17~19
禁止用最新op20+，极易出现推理框架算子缺失。

## 四、数据类型体系

| 类型 | 场景 | 端侧使用 |
|------|------|----------|
| FLOAT(1) | 默认训练权重FP32 | 精度最高、体积最大、速度慢 |
| FLOAT16(10) | 半精度FP16 | GPU/NPU加速常用 |
| INT8(3) | 量化整型 | 移动端主流，体积÷4，速度×2~4 |
| UINT8(2) | 无符号8位 | 图像输入专用 |
| INT4 | 4bit大模型量化 | LLaMA/Qwen端侧大模型专用 |

## 五、端智能全链路 ONNX 工作流（你项目标准流程）

### 步骤1：训练框架导出ONNX（PyTorch举例）

```python
import torch
model = torch.load("yolov8n.pt").eval()
dummy = torch.randn(1,3,640,640)
torch.onnx.export(
    model, dummy, "yolov8n.onnx",
    opset_version=17,
    do_constant_folding=True, # 常量折叠，提前固化常量计算
    input_names=["images"],
    output_names=["output0"]
)
```

`do_constant_folding=True` 必开：把图中可静态计算的常量提前算完，减少推理时节点数量。

### 步骤2：ONNX 模型优化（onnx-simplifier）

原始导出模型经常存在冗余节点、Identity、重复Conv、未融合BN；必须简化：

```bash
pip install onnx-simplifier
python -m onnxsim yolov8n.onnx yolov8n_simplified.onnx
```

简化收益：节点数量减少30%~60%，转换MNN/ORT时报错大幅降低。

### 步骤3：量化（INT8/4bit）

1. CV静态INT8量化（需要校准图片）

```python
from onnxruntime.quantization import quantize_static, CalibrationDataReader
quantize_static(simplified.onnx, int8.onnx, calibration_reader)
```

2. LLM动态4bit量化：使用llama.cpp/onnxruntime-genai输出GGUF/量化ONNX

### 步骤4：转端侧框架格式

1. MNN：`MNNConvert -f ONNX --modelFile xxx.onnx --MNNModel xxx.mnn`
2. ONNX Runtime Mobile：直接加载优化后onnx，无需转格式
3. NCNN：`onnx2ncnn`
4. TensorFlow Lite：`onnx_tf` 中转再tflite转换

## 六、ONNX 量化原理（端智能核心）

### 1. INT8量化公式

浮点 ↔ 整型双向映射：
$$x_{float} = (x_{int} - zero\_point) \times scale$$

- scale：缩放系数浮点数
- zero_point：量化零点（对称量化zp=0，非对称zp≠0）
量化后权重存进TensorProto，推理时实时反算浮点计算。

### 对称 vs 非对称量化

1. **对称量化（推荐大模型/Transformer）**
zero_point=0，正负数值均衡，精度损失小，4bit LLM全部对称
2. **非对称量化（推荐CNN图像）**
图像像素0~255非负，节省取值空间，CNN速度略优

## 七、常见线上/转换报错&解决方案（你工程高频坑）

1. **算子不支持: Unsupported ONNX op type 'XXX'**
原因：Opset过高/过低；框架未适配新算子
修复：降低opset到17；升级MNN/ORT版本；onnxsim化简；替换模型结构规避冷门算子

2. **输入shape mismatch 推理崩溃**
原因：导出固定维度，摄像头画面尺寸变化
修复：导出开启dynamic_axes，推理代码动态适配输入尺寸

3. **量化后精度暴跌5%+**

- 改用**量化感知训练QAT**再导出ONNX
- 换静态量化+足量校准集（至少200张真实业务图片）
- 关键层保留FP32不量化（部分Conv/Attention）

4. **模型体积巨大（LLM几个GB）**

- 4bit量化压缩75%体积
- 分片存储、按需下载
- LoRA单独存小权重文件，base模型基础量化

5. **BN层未融合，推理速度慢**
onnxsim自动融合Conv+BN；如果失效，PyTorch导出前执行 `model.eval()` 固化BN均值方差

## 八、ONNX Runtime Mobile（ORT-M）跨平台方案对比MNN

1. ORT-M优势：
   - 原生100%支持标准ONNX，转换零损耗
   - iOS/Android/鸿蒙三端一套API
   - 内置完整量化、图优化、NNAPI/Metal/GPU/NPU加速
2. MNN优势：
   - ARM CPU极致优化，同等硬件速度略高于ORT
   - LLM推理专项深度优化（MNN-LLM）
3. 你的SDK选型建议：
   - 通用CV/语音：ORT-M 跨平台省心
   - 端侧大模型：MNN-LLM性能更强

## 九、大模型ONNX特殊点（Qwen2/Whisper）

1. Transformer包含大量MatMul、LayerNorm、RoPE、GQA算子，低opset不兼容
2. KV缓存是动态输入shape，导出必须全程开dynamic
3. 4bit量化ONNX不能直接裸跑，需要推理框架内置量化解码内核
4. 多模态Qwen-VL：图像编码器+文本LLM两个子图，可拆分为两个独立ONNX分别优化部署

## 十、安全加固（对应你SDK加密需求）

原生onnx明文存储权重，极易被Netron打开窃取模型；工程落地防护手段：

1. 优化后ONNX二进制AES加密，运行时内存解密加载
2. 打包进自定义容器格式，篡改文件头直接加载失败
3. 模型内部插入水印节点，逆向溯源侵权
