# MCP（模型上下文协议）完整详解：AI时代的"通用USB接口"

MCP（Model Context Protocol，模型上下文协议）是**Anthropic于2024年11月推出的开放标准协议**，它彻底解决了大模型工具调用碎片化的行业痛点，被誉为"**AI世界的USB-C接口**"。截至2026年5月，MCP已成为业界事实标准，获得了OpenAI、Google、微软等所有主流厂商的原生支持，是构建生产级AI Agent和智能应用的核心基础设施。

## 一、什么是MCP？为什么需要它？

### 1. 核心定义

MCP是一个**基于JSON-RPC 2.0的轻量级应用层协议**，它定义了大模型应用（Host）与外部工具/数据源（Server）之间的标准化通信方式。它不是一个框架或SDK，而是一套中立的协议规范，任何语言、任何平台都可以实现。

**官方类比**：就像USB-C统一了电子设备的接口，让任何设备都能连接任何外设；MCP统一了AI应用的接口，让任何大模型都能"即插即用"地连接任何工具和数据源。

### 2. 诞生背景：工具调用的碎片化噩梦

在MCP出现之前，大模型工具调用处于严重的碎片化状态：

- **标准不统一**：OpenAI用Function Calling格式，Anthropic用Tools格式，Google Gemini又是另一套
- **重复开发**：同一个工具需要为每个平台写一个适配层，维护成本极高
- **中心化控制**：插件系统由平台垄断，开发者没有自主权
- **安全隐患**：权限控制粗糙，容易导致数据泄露和滥用
- **能力有限**：只能支持简单的函数调用，无法处理复杂的上下文交换

MCP的出现彻底终结了这种混乱局面，它提供了一个**供应商中立、模型无关、安全可控**的统一标准。

### 3. MCP vs 传统工具调用/插件系统

| 维度 | 传统Function Calling | ChatGPT Plugins | MCP协议 |
|------|----------------------|-----------------|---------|
| **标准性** | 厂商私有 | OpenAI私有 | 开放行业标准 |
| **跨平台性** | 不支持 | 仅ChatGPT | 所有主流模型和应用 |
| **去中心化** | 否 | 否 | 是（任何人都可以运行服务器） |
| **核心能力** | 仅函数调用 | 函数调用+网页浏览 | 工具调用+资源读取+提示词模板 |
| **安全模型** | 粗糙 | 平台控制 | 细粒度权限+用户确认+沙箱隔离 |
| **传输方式** | HTTP | HTTP | stdio+HTTP+SSE |
| **开发成本** | 高（每个平台适配） | 中（OpenAI规范） | 极低（一次开发，到处运行） |

## 二、MCP核心架构与组件

MCP采用**三层解耦的客户端-服务器架构**，包含三个核心角色：Host（宿主）、Client（客户端）和Server（服务器）。

```
┌─────────────────────────────────────────────────────────┐
│                     MCP Host（AI应用）                  │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐     │
│  │ MCP Client 1│  │ MCP Client 2│  │ MCP Client 3│     │
│  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘     │
└─────────┼────────────────┼────────────────┼─────────────┘
          │                │                │
┌─────────▼────────┐ ┌─────▼──────────┐ ┌───▼────────────┐
│  MCP Server 1    │ │  MCP Server 2  │ │  MCP Server 3  │
│（文件系统/CLI）  │ │（数据库/API）  │ │（云服务/第三方）│
└──────────────────┘ └────────────────┘ └────────────────┘
```

### 1. Host（宿主）

**角色**：用户直接交互的AI应用，是MCP生态的入口。
**核心功能**：

- 管理用户交互和大模型推理
- 发现和配置MCP服务器
- 执行安全策略和用户授权
- 协调多个MCP客户端的工作
- 聚合上下文并生成最终回答

**典型代表**：Claude Desktop、Cursor、VS Code、ChatGPT Desktop、Cherry Studio

### 2. Client（客户端）

**角色**：集成在Host内部的协议适配器，每个Client与一个Server建立1:1的连接。
**核心功能**：

- 处理协议协商和能力交换
- 双向路由JSON-RPC消息
- 管理会话状态和订阅通知
- 维护服务器之间的安全隔离
- 转换工具调用格式

### 3. Server（服务器）

**角色**：能力提供者，封装外部工具和数据源。
**核心功能**：

- 暴露自身的能力清单（工具、资源、提示词）
- 处理客户端的请求并返回结构化结果
- 实现安全控制和资源隔离
- 支持流式响应和实时通知

**技术特点**：

- 轻量级：通常只有几十KB到几MB
- 多语言支持：Python、TypeScript、Go、Java等
- 多传输方式：stdio（本地）、HTTP/SSE（远程）
- 无状态：便于水平扩展和部署

## 三、MCP协议规范核心（技术细节）

MCP协议通过四个层面的精确约束来落地：**消息格式**、**传输层**、**生命周期**和**功能原语**。协议的完整规范由TypeScript架构（schema.ts）定义，这是所有消息和结构的权威来源。

### 1. 消息格式（基于JSON-RPC 2.0）

MCP中的所有通信都必须遵循JSON-RPC 2.0规范，使用UTF-8编码。协议定义了以下三类消息：

#### 请求（Request）

- **作用**：发起方（客户端或服务器）发送的、期望对方做出响应的操作指令。
- **数据结构**：

```json
{
  "jsonrpc": "2.0",          // 必须为"2.0"
  "id": string | number,     // 必须，唯一标识，不能为null
  "method": string,          // 必须，要调用的方法名
  "params": object           // 可选，方法参数
}
```

#### 响应（Response）

- **作用**：对请求的回复，包含结果或错误信息。
- **数据结构**：

```json
{
  "jsonrpc": "2.0",           // 必须为"2.0"
  "id": string | number,      // 必须与对应的请求ID相同
  "result": object,           // 成功时存在，与error互斥
  "error": {                  // 失败时存在，与result互斥
    "code": number,           // 必须，整数错误码
    "message": string,        // 必须，错误简短描述
    "data": unknown           // 可选，附加错误信息
  }
}
```

#### 通知（Notification）

- **作用**：单向消息，用于发送无需回复的信息，如日志或状态变更。
- **数据结构**：

```json
{
  "jsonrpc": "2.0",           // 必须为"2.0"
  "method": string,           // 必须，通知方法名
  "params": object            // 可选，参数
  // 注意：不能包含id字段
}
```

### 2. 传输层

MCP定义了两种标准传输机制，客户端和服务器也可以实现自定义传输。

#### stdio（标准输入/输出）

- **使用场景**：客户端将MCP服务器作为**子进程**启动。
- **通信规则**：
  - 客户端通过子进程的`stdin`写入消息
  - 服务器通过`stdout`读取消息并写入响应
  - 消息**必须**由换行符分隔，且每条消息不能包含内嵌换行符
  - 日志**应该**写入`stderr`，客户端可以选择捕获
- **特点**：实现简单，是本地命令行工具和本地集成的首选。

#### Streamable HTTP（流式HTTP）

- **使用场景**：独立运行的网络服务，支持多个客户端连接。
- **通信规则**：
  - 服务器**必须**提供单一HTTP端点
  - 客户端**必须**通过HTTP POST请求发送JSON-RPC消息
  - 可选支持Server-Sent Events（SSE）实现服务器主动推送
- **安全约束**：
  - **必须**验证`Origin`头以防止DNS重绑定攻击
  - 本地运行时**应该**绑定到`localhost`而非`0.0.0.0`
- **特点**：支持远程部署，扩展性强。

### 3. 生命周期

MCP为客户端与服务器之间的连接定义了完整的生命周期。

| 阶段 | 行为 | 核心作用 |
|------|------|----------|
| **初始化** | 客户端发送`initialize`请求（含协议版本和能力）；服务器响应自身能力和版本；客户端发送`notifications/initialized`通知 | 确保双方就协议版本和功能范围达成一致 |
| **操作** | 正常交换消息（请求、响应、通知） | 执行核心业务逻辑 |
| **关闭** | 良好行为的客户端应先发送`shutdown`请求，收到响应后再发送`exit`通知 | 确保连接被优雅终止 |

### 4. 授权与安全（HTTP传输）

对于基于HTTP的传输，MCP采用**OAuth 2.1**授权框架。

- **角色定义**：
  - MCP服务器：资源服务器，使用访问令牌保护资源
  - MCP客户端：OAuth客户端，代表用户发起请求
  - 授权服务器：独立实体，颁发令牌
- **流程约束**：
  - 无令牌访问受保护资源时，服务器**必须**返回`HTTP 401`
  - 客户端**必须**启动标准OAuth 2.1授权流程
  - **必须**强制使用PKCE（Proof Key for Code Exchange）和HTTPS
  - 服务器**必须**实现`RFC 9728`（OAuth 2.0受保护资源元数据）
- **注意**：对于本地stdio传输，应从环境变量中获取凭据，不应用此规范。

### 5. 服务器功能原语

服务器通过以下三种核心原语向客户端公开能力。

| 功能 | 描述 | 客户端调用方式 |
|------|------|----------------|
| **工具（Tools）** | 可执行的函数，供AI模型调用 | `tools/list`发现；`tools/call`执行 |
| **资源（Resources）** | 可读取的数据内容，以URI标识 | `resources/list`发现；`resources/read`读取 |
| **提示词（Prompts）** | 预定义的提示词模板 | `prompts/list`发现；`prompts/get`获取 |

资源列表变更时，服务器**应该**发送`notifications/resources/list_changed`通知。

### 6. 辅助机制

MCP提供了以下横切关注点的辅助功能。

| 机制 | 消息/通知 | 作用 |
|------|-----------|------|
| **日志** | `logging/setLevel`（请求）；`notifications/message`（通知） | 设置日志级别；发送日志内容 |
| **取消** | `$/cancelRequest`（通知） | 取消正在进行的长时间操作 |
| **进度跟踪** | 请求中设置`meta.progressToken`；服务器发送`notifications/progress` | 报告长时间操作的执行进度 |
| **完成（补全）** | `completion/complete`（请求） | 为提示词或工具参数提供自动补全建议 |

### 7. 标准错误码

| 代码 | 含义 |
|------|------|
| -32700 | 解析错误（Parse error） |
| -32600 | 无效请求（Invalid Request） |
| -32601 | 方法未找到（Method not found） |
| -32602 | 无效参数（Invalid params） |
| -32603 | 内部错误（Internal error） |
| 32000 | 服务器未初始化（Server not initialized） |
| 32001 | 请求已取消（Request cancelled） |

## 四、MCP的三大核心能力

MCP超越了传统工具调用的范畴，提供了三大核心能力，覆盖了大模型与外部世界交互的所有场景。

### 1. 工具调用（Tools）

**功能**：让大模型调用外部函数执行操作，是最基础也是最常用的能力。
**特点**：

- 标准化的工具定义格式（基于JSON Schema）
- 支持同步和异步调用
- 支持流式响应（实时返回结果）
- 支持参数校验和错误处理

**示例工具定义**：

```json
{
  "name": "get_weather",
  "description": "获取指定城市的天气预报",
  "inputSchema": {
    "type": "object",
    "properties": {
      "city": {"type": "string", "description": "城市名称"},
      "days": {"type": "integer", "description": "预报天数", "default": 1}
    },
    "required": ["city"]
  }
}
```

### 2. 资源读取（Resources）

**功能**：让大模型读取外部资源的内容，这些资源会自动注入到大模型的上下文中。
**特点**：

- 资源有唯一的URI标识（如`file:///home/user/doc.txt`）
- 支持资源列表和资源内容的读取
- 支持资源变更通知（当资源变化时主动通知客户端）
- 可以自动将大文件分块注入上下文

**典型应用**：

- 读取本地文件系统的文件
- 查询数据库中的记录
- 获取API返回的结构化数据
- 访问Git仓库的代码

### 3. 提示词模板（Prompts）

**功能**：让服务器提供预定义的提示词模板，大模型可以直接使用这些模板生成符合要求的响应。
**特点**：

- 提示词可以包含参数，由大模型动态填充
- 可以定义提示词的使用场景和示例
- 支持多轮对话提示词
- 便于标准化任务的执行

**示例提示词模板**：

```json
{
  "name": "code_review",
  "description": "代码审查提示词模板",
  "arguments": [
    {"name": "code", "description": "需要审查的代码"},
    {"name": "language", "description": "编程语言"}
  ],
  "prompt": "请审查以下{language}代码，从以下几个方面给出反馈：\n1. 代码正确性\n2. 代码风格\n3. 性能优化\n4. 安全隐患\n\n代码：\n{code}"
}
```

## 五、MCP完整工作流程

### 1. 服务器发现与配置

- 用户在Host中配置MCP服务器的地址（本地进程或远程URL）
- Host启动MCP Client进程
- Client与Server建立连接（stdio或HTTP）

### 2. 初始化与能力交换

- Client向Server发送`initialize`请求，协商协议版本和能力
- Server返回自身的能力清单（支持的工具、资源、提示词）
- Client向Server发送`initialized`通知，连接建立完成

### 3. 工具调用流程

1. 用户输入查询
2. Host将查询和可用工具列表发送给大模型
3. 大模型决定调用某个工具，并生成参数
4. Host通过Client向Server发送工具调用请求
5. Server执行工具逻辑，返回结果
6. Host将结果注入上下文，再次发送给大模型
7. 大模型基于工具结果生成最终回答

### 4. 资源读取流程

1. 大模型请求读取某个资源（如`file:///data/report.pdf`）
2. Client向Server发送`read_resource`请求
3. Server读取资源内容，分块返回给Client
4. Client将资源内容自动注入到大模型的上下文中
5. 大模型基于资源内容生成回答

## 六、MCP的安全机制

安全是MCP设计的首要考虑因素，它提供了多层次的安全防护体系。

### 1. 沙箱隔离

- 每个MCP服务器运行在独立的进程中，相互隔离
- 本地服务器只能访问用户授权的目录和资源
- 远程服务器只能访问其自身的资源，无法访问本地系统

### 2. 细粒度权限控制

- 可以为每个服务器单独设置权限（如是否允许读取文件、执行命令）
- 可以为每个工具单独设置权限
- 可以限制资源的访问范围（如只允许读取`/home/user/documents`目录）

### 3. 用户确认机制

- 对于敏感操作（如执行命令、写入文件、发送网络请求），必须经过用户确认
- 用户可以选择"允许一次"、"始终允许"或"拒绝"
- 所有操作都会记录日志，便于审计

### 4. 透明审计

- 所有工具调用和资源访问都会被记录
- 用户可以查看完整的操作历史
- 支持导出审计日志

## 七、MCP落地方式

MCP采用主机-客户端-服务器三层架构，这种设计将AI应用的核心能力与工具服务解耦：

- **主机（Host）**：核心协调层，负责维护对话上下文和管理工具调用权限（如Claude Desktop）。
- **客户端（Client）**：交互入口层，提供UI与协议解析（如Cursor IDE、VS Code等）。
- **服务器（Server）**：工具适配层，封装具体业务逻辑，为AI模型提供可调用的能力。

在通信层面，MCP支持两种传输方式：

- **Stdio**：MCP Server作为本地进程运行，Client通过标准输入输出与其通信，适用于本地部署，延迟低、调试方便。
- **HTTP/SSE**：Server作为网络服务运行，Client通过HTTP请求与Server通信，支持远程部署和服务器推送事件，扩展性强。

每个MCP Server都需遵循协议规范来实现**工具（Tools）**、**资源（Resources）**和**提示词（Prompts）**等功能。这种方式带来三大核心价值：

1. **标准化统一接口**：一次开发，所有支持MCP的AI应用均可调用，避免重复"造轮子"。
2. **开发与使用解耦**：工具团队专注实现Server，Agent团队只需引入Client，双方无需协调接口细节。
3. **生态共享**：MCP Server可发布到公共仓库，社区工具可直接复用，无需重复开发。

### 完整搭建MCP服务端

#### 1.Python（FastMCP）—— 推荐新手

FastMCP是目前最轻量、上手最快的Python框架。

- **1. 安装FastMCP**

  ```bash
  pip install fastmcp
  ```

- **2. 编写服务端脚本 `weather_server.py`**

  ```python
  from fastmcp import FastMCP

  # 初始化服务端实例
  mcp = FastMCP("weather-service")

  @mcp.tool
  def get_weather(city: str) -> dict:
      """获取指定城市的天气信息"""
      mock_data = {
          "beijing": {"temp": 25, "condition": "sunny"},
          "shanghai": {"temp": 28, "condition": "cloudy"},
          "guangzhou": {"temp": 30, "condition": "rainy"}
      }
      normalized = city.lower()
      if normalized in mock_data:
          return {"city": city, **mock_data[normalized]}
      return {"city": city, "temp": 20, "condition": "unknown"}

  if __name__ == "__main__":
      # 开发模式使用stdio传输
      mcp.run(transport="stdio")
      # 生产环境建议使用：mcp.run(transport="tcp", host="0.0.0.0", port=8080)
  ```

  通过装饰器注册工具，函数文档字符串会自动成为工具描述，供LLM判断调用时机。

- **3. 启动服务端**

  ```bash
  python weather_server.py
  ```

- **4. 验证工具调用**（新建 `test_client.py`）

  ```python
  from fastmcp import FastMCPClient

  client = FastMCPClient("weather-service")
  result = client.call("get_weather", city="Shanghai")
  print(f"上海天气：{result['temp']}°C，{result['condition']}")
  ```

#### 1.1 通用MCP客户端（Python示例）

```python
import requests

class MCPClient:
    def __init__(self, server_url: str):
        self.server_url = server_url

    def discover_services(self):
        response = requests.get(f"{self.server_url}/discover")
        return response.json()

    def fetch_context(self, query_params: dict):
        payload = {"query": query_params, "max_results": 5}
        response = requests.post(f"{self.server_url}/fetch", json=payload)
        return response.json()

# 使用示例
client = MCPClient("http://localhost:3000")
services = client.discover_services()
context = client.fetch_context({"location": "Beijing"})
```

### 协议通信流程

MCP客户端与服务端的完整交互分为四步：

1. **连接建立**：Client发送初始化请求，协商协议版本和capabilities，Server返回支持的功能列表。
2. **工具发现**：Client向Server请求工具列表，获取所有可用工具的名称、描述和参数schema。
3. **工具调用**：Agent决定调用某个工具时，Client将请求转发给Server（包含工具名称和参数），Server执行后返回结果。
4. **结果处理**：Client将结果包装为模型可理解的格式，追加到对话上下文中继续推理。

整个过程自动编排，开发者只需关注Server的配置和工具实现细节。

## 九、MCP的核心优势

- 大幅降低了开发和维护成本

### 2. 去中心化与开放

- 没有中央平台控制，任何人都可以运行自己的MCP服务器
- 不需要平台审核，开发者拥有完全的自主权
- 促进了创新和生态的繁荣

### 3. 安全可控

- 多层次的安全防护体系
- 用户完全掌控数据和权限
- 透明的审计机制

### 4. 轻量级与高性能

- 基于JSON-RPC 2.0，协议开销极小
- 支持流式响应，实时性好
- 本地服务器的延迟可以忽略不计

### 5. 可扩展性强

- 协议设计具有良好的可扩展性
- 可以根据需要添加新的能力和原语
- 支持自定义扩展
