# Tool Use 完整详解：从基础原理到生产级落地

Tool Use（工具使用）是大模型从"**文本生成器**"进化为"**任务执行者**"的核心技术，也是所有Agent、智能体和行动增强系统的基础。它不是简单的Function Calling（函数调用），而是一个包含**意图理解、工具选择、参数生成、执行调度、错误处理、结果融合**的完整闭环系统。

## 一、什么是Tool Use？与Function Calling的本质区别

很多人会混淆Tool Use和Function Calling，实际上Function Calling只是Tool Use的一个基础组件。

### 1. 核心定义

Tool Use是大模型**自主理解用户意图、选择合适的外部工具、生成正确的调用参数、处理执行结果并最终完成任务**的能力。它的本质是建立了"**自然语言意图 → 可执行操作 → 结果反馈 → 最终回答**"的完整闭环。

### 2. Function Calling vs Tool Use 全面对比

| 维度 | Function Calling | Tool Use |
|------|------------------|----------|
| **本质** | 大模型的一个输出格式能力 | 完整的任务执行系统 |
| **能力范围** | 单次函数调用 | 多轮、多工具、链式/并行调用 |
| **核心组件** | 函数Schema解析、结构化输出 | 工具选择器、执行引擎、错误处理器、结果融合器 |
| **错误处理** | 无，需要开发者手动实现 | 内置自动重试、错误诊断、降级策略 |
| **上下文管理** | 无，需要开发者手动维护 | 自动维护工具调用历史和执行状态 |
| **规划能力** | 无 | 支持简单的任务分解和执行规划 |
| **典型应用** | 天气查询、计算器 | 数据分析、文档处理、自动化工作流 |

**一句话总结**：Function Calling是大模型的一个"技能"，而Tool Use是一个完整的"系统"，它将Function Calling与其他技术结合起来，实现了真正的任务执行能力。

## 二、Tool Use的核心架构与组件

一个完整的Tool Use系统由以下6个核心组件组成：

```
用户输入 → 意图理解器 → 工具选择器 → 参数生成器 → 执行引擎 → 结果融合器 → 最终回答
                ↑                     ↓
                └──── 反馈处理器 ─────┘
```

### 1. 工具注册表（Tool Registry）

存储所有可用工具的元数据，包括：

- 工具名称、描述、使用场景
- 参数定义（名称、类型、描述、是否必填、默认值）
- 返回值格式
- 权限要求、调用限制、超时时间

### 2. 意图理解器（Intent Understander）

解析用户输入的自然语言，提取：

- 用户的核心需求
- 任务的类型和复杂度
- 隐含的约束条件（如时间、地点、格式要求）

### 3. 工具选择器（Tool Selector）

根据用户意图，从工具注册表中选择最合适的一个或多个工具。

- 简单场景：直接匹配工具描述
- 复杂场景：使用向量检索或大模型打分选择
- 多工具场景：生成工具调用序列

### 4. 参数生成器（Parameter Generator）

根据工具的参数定义，从用户输入和上下文中提取或生成正确的参数值。

- 处理必填参数和可选参数
- 进行参数类型转换和格式校验
- 处理参数缺失的情况（主动询问用户）

### 5. 执行引擎（Execution Engine）

负责实际调用工具并管理执行过程：

- 同步/异步执行工具调用
- 支持并行调用多个工具
- 处理超时和网络错误
- 记录调用日志和指标

### 6. 结果融合器（Result Fuser）

将工具返回的结果整合为自然语言回答：

- 解析工具返回的结构化数据
- 过滤无关信息
- 按照用户要求的格式组织回答
- 处理多个工具结果的融合

### 7. 反馈处理器（Feedback Handler）

根据工具执行结果调整后续操作：

- 如果执行成功，继续下一步或生成最终回答
- 如果执行失败，分析错误原因并进行重试
- 如果需要更多信息，主动询问用户
- 如果工具选择错误，重新选择工具

## 三、Tool Use的完整工作流程（7步闭环）

一个标准的Tool Use执行过程分为以下7个步骤，形成一个完整的闭环：

### 步骤1：用户输入与意图解析

- 接收用户的自然语言查询
- 解析用户的核心意图和隐含需求
- 判断是否需要使用工具（简单问题可以直接回答）

### 步骤2：工具检索与选择

- 如果不需要工具，直接生成回答
- 如果需要工具，从工具注册表中检索最相关的工具
- 对于复杂任务，生成工具调用计划（调用顺序、依赖关系）

### 步骤3：参数生成与校验

- 为选中的工具生成调用参数
- 进行参数格式和类型校验
- 如果有缺失的必填参数，主动询问用户补充

### 步骤4：工具调用与执行

- 调用工具API或执行本地函数
- 处理调用过程中的超时、网络错误等异常
- 记录调用日志和执行时间

### 步骤5：结果解析与评估

- 解析工具返回的结果
- 评估结果是否满足用户需求
- 判断是否需要进一步调用工具

### 步骤6：多轮迭代（如果需要）

- 如果结果不完整或需要更多信息，回到步骤2
- 继续调用其他工具或重新调用当前工具
- 直到获得足够的信息来回答用户问题

### 步骤7：结果融合与回答生成

- 将所有工具返回的结果整合在一起
- 按照用户要求的格式生成自然语言回答
- 提供回答的来源和依据（可选）

## 四、核心技术详解

### 1. 工具定义的最佳实践

工具定义的质量直接决定了Tool Use的效果。一个好的工具定义应该清晰、准确、完整。

**标准工具定义格式（JSON Schema）**：

```json
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "获取指定城市未来几天的天气预报。使用这个工具来回答关于天气的问题，如'明天北京会下雨吗？'、'上海下周的气温是多少？'",
    "parameters": {
      "type": "object",
      "properties": {
        "city": {
          "type": "string",
          "description": "城市名称，如'北京'、'上海'、'深圳'"
        },
        "days": {
          "type": "integer",
          "description": "预报天数，默认为1天，最多支持7天",
          "default": 1,
          "minimum": 1,
          "maximum": 7
        },
        "include_hourly": {
          "type": "boolean",
          "description": "是否包含逐小时预报，默认为false",
          "default": false
        }
      },
      "required": ["city"],
      "additionalProperties": false
    }
  }
}
```

**工具定义黄金法则**：

- **名称清晰**：使用动词+名词的格式，如`get_weather`、`calculate_math`
- **描述详细**：不仅说明工具做什么，还要说明什么时候使用它
- **参数完整**：为每个参数提供清晰的描述、类型、默认值和约束
- **避免歧义**：不要使用模糊的术语，确保大模型能够准确理解
- **限制范围**：明确工具的能力边界，不要让大模型尝试用它做超出能力范围的事情

### 2. 参数校验与错误处理

参数错误是Tool Use中最常见的问题，必须在调用工具之前进行严格的校验。

**常见参数错误类型**：

- 缺失必填参数
- 参数类型错误（如字符串代替数字）
- 参数值超出范围（如天数超过7天）
- 参数格式错误（如日期格式不正确）

**参数校验实现示例**：

```python
from pydantic import BaseModel, Field, ValidationError
from typing import Optional

class GetWeatherInput(BaseModel):
    city: str = Field(..., description="城市名称")
    days: int = Field(1, ge=1, le=7, description="预报天数")
    include_hourly: bool = Field(False, description="是否包含逐小时预报")

def validate_parameters(tool_name: str, parameters: dict):
    """校验工具调用参数"""
    try:
        if tool_name == "get_weather":
            return GetWeatherInput(**parameters)
        # 其他工具的校验
        else:
            raise ValueError(f"未知工具: {tool_name}")
    except ValidationError as e:
        raise ValueError(f"参数校验失败: {e.errors()}")
```

**错误处理策略**：

- **自动重试**：对于临时错误（如网络超时），自动重试2-3次
- **参数修正**：对于轻微的参数错误，尝试自动修正
- **降级处理**：如果工具调用失败，使用备用方案或告知用户
- **错误上报**：记录所有错误，用于后续分析和优化

### 3. 并行工具调用

当任务需要调用多个独立的工具时，使用并行调用可以显著提高执行效率。

**并行调用示例**：

```python
import asyncio

async def call_tool_async(tool_name: str, parameters: dict):
    """异步调用工具"""
    # 实现工具调用逻辑
    pass

async def parallel_tool_calls(calls: list):
    """并行调用多个工具"""
    tasks = [call_tool_async(call["name"], call["parameters"]) for call in calls]
    results = await asyncio.gather(*tasks)
    return results

# 并行调用天气和新闻工具
calls = [
    {"name": "get_weather", "parameters": {"city": "北京"}},
    {"name": "get_news", "parameters": {"topic": "科技"}}
]

results = asyncio.run(parallel_tool_calls(calls))
```

### 4. 工具检索（Tool Retrieval）

当工具数量超过大模型的上下文窗口限制时（通常超过50个工具），需要先进行工具检索，找到与当前任务最相关的工具，再让大模型选择调用。

**工具检索实现步骤**：

1. 为每个工具生成描述向量
2. 构建工具向量索引
3. 查询时，将用户输入向量化
4. 检索最相关的Top-K个工具
5. 只将这些工具的描述提供给大模型

**代码示例**：

```python
from sentence_transformers import SentenceTransformer
import faiss
import numpy as np

# 加载嵌入模型
model = SentenceTransformer('all-MiniLM-L6-v2')

# 工具列表
tools = [
    {"name": "get_weather", "description": "获取指定城市的天气预报"},
    {"name": "get_news", "description": "获取指定主题的最新新闻"},
    {"name": "calculate_math", "description": "解决数学计算问题"},
    {"name": "search_web", "description": "搜索网络获取最新信息"}
]

# 生成工具描述向量
tool_descriptions = [f"{tool['name']}: {tool['description']}" for tool in tools]
tool_embeddings = model.encode(tool_descriptions)

# 构建FAISS索引
index = faiss.IndexFlatL2(tool_embeddings.shape[1])
index.add(tool_embeddings)

def retrieve_tools(query: str, top_k: int = 3):
    """检索与查询最相关的工具"""
    query_embedding = model.encode([query])
    distances, indices = index.search(query_embedding, top_k)
    return [tools[i] for i in indices[0]]

# 测试工具检索
query = "明天北京的天气怎么样？"
relevant_tools = retrieve_tools(query)
print("相关工具:", [tool["name"] for tool in relevant_tools])
```

### 5. 工具链规划

对于复杂任务，需要将其分解为多个步骤，形成一个工具调用链。

**工具链规划示例**：
任务："帮我分析一下2024年中国人工智能市场的规模和增长趋势，并生成一个简单的报告。"

工具链：

1. `search_web`：搜索"2024年中国人工智能市场规模"
2. `search_web`：搜索"2024年中国人工智能市场增长趋势"
3. `extract_data`：从搜索结果中提取关键数据
4. `generate_report`：根据提取的数据生成报告

## 五、生产级Tool Use代码实战

以下是一个完整的、可直接运行的生产级Tool Use系统实现，包含工具定义、参数校验、错误处理、并行调用和日志记录。

### 1. 环境准备

```bash
pip install openai pydantic python-dotenv asyncio
```

### 2. 完整代码实现

```python
import asyncio
import json
import logging
from typing import Optional, List, Dict, Any
from pydantic import BaseModel, Field, ValidationError
from openai import OpenAI
from dotenv import load_dotenv
import os

# 配置日志
logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

load_dotenv()
client = OpenAI(api_key=os.getenv("OPENAI_API_KEY"))

# ---------------------- 工具定义 ----------------------
class Tool(BaseModel):
    name: str
    description: str
    parameters: Dict[str, Any]
    function: Any

# 工具实现
def get_weather(city: str, days: int = 1, include_hourly: bool = False) -> str:
    """获取指定城市的天气预报"""
    logger.info(f"调用get_weather: city={city}, days={days}, include_hourly={include_hourly}")
    # 模拟API调用
    return f"{city}未来{days}天的天气预报：晴天，气温20-25度"

def calculate_math(expression: str) -> str:
    """解决数学计算问题"""
    logger.info(f"调用calculate_math: expression={expression}")
    try:
        result = eval(expression)
        return f"计算结果: {result}"
    except Exception as e:
        return f"计算错误: {str(e)}"

def search_web(query: str) -> str:
    """搜索网络获取最新信息"""
    logger.info(f"调用search_web: query={query}")
    # 模拟搜索结果
    return f"关于'{query}'的搜索结果：..."

# 工具注册表
tools = [
    Tool(
        name="get_weather",
        description="获取指定城市未来几天的天气预报。使用这个工具来回答关于天气的问题。",
        parameters={
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市名称"},
                "days": {"type": "integer", "description": "预报天数，默认为1天", "default": 1}
            },
            "required": ["city"]
        },
        function=get_weather
    ),
    Tool(
        name="calculate_math",
        description="解决数学计算问题。使用这个工具来回答数学问题，如'2+2等于多少？'。",
        parameters={
            "type": "object",
            "properties": {
                "expression": {"type": "string", "description": "数学表达式，如'2+2'、'3*4'"}
            },
            "required": ["expression"]
        },
        function=calculate_math
    ),
    Tool(
        name="search_web",
        description="搜索网络获取最新信息。使用这个工具来回答需要最新信息的问题。",
        parameters={
            "type": "object",
            "properties": {
                "query": {"type": "string", "description": "搜索关键词"}
            },
            "required": ["query"]
        },
        function=search_web
    )
]

# 工具名称到工具的映射
tool_map = {tool.name: tool for tool in tools}

# 转换为OpenAI格式的工具定义
openai_tools = [
    {
        "type": "function",
        "function": {
            "name": tool.name,
            "description": tool.description,
            "parameters": tool.parameters
        }
    } for tool in tools
]

# ---------------------- Tool Use 核心逻辑 ----------------------
async def call_tool(tool_name: str, parameters: Dict[str, Any]) -> str:
    """调用单个工具"""
    try:
        tool = tool_map.get(tool_name)
        if not tool:
            return f"错误：未知工具 '{tool_name}'"
        
        # 校验参数
        # 这里可以使用Pydantic进行更严格的校验
        return tool.function(**parameters)
    except Exception as e:
        logger.error(f"调用工具 {tool_name} 失败: {str(e)}")
        return f"调用工具 {tool_name} 失败: {str(e)}"

async def run_tool_use(query: str, max_iterations: int = 5) -> str:
    """运行Tool Use系统"""
    messages = [
        {"role": "system", "content": "你是一个有用的助手，可以使用工具来回答用户的问题。如果需要使用工具，请调用合适的工具；如果不需要，直接回答用户的问题。"},
        {"role": "user", "content": query}
    ]
    
    for i in range(max_iterations):
        logger.info(f"第 {i+1} 轮迭代")
        
        # 调用大模型
        response = client.chat.completions.create(
            model="gpt-3.5-turbo-1106",
            messages=messages,
            tools=openai_tools,
            tool_choice="auto"
        )
        
        message = response.choices[0].message
        messages.append(message)
        
        # 如果不需要调用工具，直接返回回答
        if not message.tool_calls:
            return message.content
        
        # 并行调用所有工具
        tasks = []
        for tool_call in message.tool_calls:
            tool_name = tool_call.function.name
            parameters = json.loads(tool_call.function.arguments)
            tasks.append(call_tool(tool_name, parameters))
        
        results = await asyncio.gather(*tasks)
        
        # 将工具结果添加到消息中
        for tool_call, result in zip(message.tool_calls, results):
            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "name": tool_call.function.name,
                "content": result
            })
    
    return "抱歉，我无法在规定的迭代次数内完成你的请求。"

# ---------------------- 测试 ----------------------
async def main():
    # 测试单工具调用
    print("测试1：天气查询")
    result = await run_tool_use("明天北京的天气怎么样？")
    print(result)
    print("\n" + "="*50 + "\n")
    
    # 测试多工具调用
    print("测试2：多工具调用")
    result = await run_tool_use("北京今天的天气怎么样？2+2等于多少？")
    print(result)
    print("\n" + "="*50 + "\n")
    
    # 测试不需要工具的问题
    print("测试3：不需要工具的问题")
    result = await run_tool_use("你好，介绍一下你自己。")
    print(result)

if __name__ == "__main__":
    asyncio.run(main())
```

## 六、进阶优化技巧

### 1. 上下文管理

随着工具调用轮次的增加，上下文会越来越长，导致成本增加和效果下降。可以使用以下方法优化：

- **截断历史**：只保留最近的几轮对话
- **摘要历史**：用大模型生成历史对话的摘要
- **过滤无关信息**：只保留与当前任务相关的信息

### 2. 成本优化

- **缓存机制**：缓存常用工具的调用结果
- **批量处理**：将多个相似的工具调用合并为一个
- **模型路由**：简单任务使用小模型，复杂任务使用大模型
- **限制迭代次数**：设置最大迭代次数，避免无限循环

### 3. 安全控制

- **权限控制**：为不同的用户设置不同的工具访问权限
- **输入验证**：对所有用户输入和工具参数进行严格验证
- **沙箱执行**：在隔离的沙箱中执行代码和工具
- **审计日志**：记录所有工具调用和用户操作，便于审计和追溯

### 4. 监控与可观测性

- **指标监控**：监控工具调用成功率、延迟、错误率
- **日志记录**：记录详细的执行日志，便于调试
- **告警机制**：当错误率超过阈值时发出告警
- **效果评估**：定期评估Tool Use系统的效果

## 七、常见坑与解决方案

### 1. 参数幻觉

**问题**：大模型生成不存在的参数或错误的参数值。
**解决方案**：

- 使用Pydantic进行严格的参数校验
- 在工具描述中明确参数的取值范围
- 对于常见的参数错误，尝试自动修正

### 2. 工具选择错误

**问题**：大模型选择了错误的工具来完成任务。
**解决方案**：

- 优化工具描述，明确每个工具的使用场景
- 使用工具检索，只提供最相关的工具
- 增加示例，在提示词中提供工具使用的示例

### 3. 无限循环

**问题**：大模型反复调用同一个工具，陷入无限循环。
**解决方案**：

- 设置最大迭代次数
- 检测重复的工具调用，提前终止
- 在提示词中明确要求避免重复调用

### 4. 上下文溢出

**问题**：工具调用历史过长，导致上下文窗口溢出。
**解决方案**：

- 实现上下文管理机制，截断或摘要历史
- 使用支持更长上下文的模型
- 分阶段执行任务，每个阶段只保留必要的信息

## 八、Tool Use的评估方法

评估Tool Use系统的效果需要从多个维度进行：

### 1. 功能指标

- **工具选择准确率**：正确选择工具的比例
- **参数生成准确率**：正确生成参数的比例
- **任务成功率**：成功完成用户任务的比例
- **平均迭代次数**：完成任务平均需要的工具调用轮次

### 2. 性能指标

- **平均响应时间**：从用户输入到返回回答的平均时间
- **工具调用延迟**：每个工具调用的平均延迟
- **吞吐量**：系统每秒能够处理的请求数

### 3. 成本指标

- **平均Token消耗**：每个请求平均消耗的Token数
- **平均API调用成本**：每个请求平均花费的API成本

### 4. 质量指标

- **回答准确率**：回答正确的比例
- **回答相关性**：回答与用户问题相关的比例
- **用户满意度**：用户对回答的满意程度

## 九、最佳实践与落地建议

1. **从简单开始**：先实现几个核心工具，验证效果后再逐步扩展
2. **工具粒度适中**：工具不要太细（每个操作一个工具）也不要太粗（一个工具做所有事情）
3. **明确能力边界**：清楚地告诉大模型每个工具能做什么、不能做什么
4. **完善错误处理**：考虑所有可能的错误情况，提供友好的错误提示
5. **持续优化**：根据用户反馈和日志数据，不断优化工具定义和提示词
6. **安全第一**：始终将安全放在首位，严格控制工具的访问权限

## 十、Tool Use与RAG/Agent的关系

- **RAG是一种特殊的Tool Use**：RAG本质上是调用一个"知识库检索工具"来获取信息
- **Tool Use是Agent的基础**：所有Agent系统都建立在Tool Use之上
- **Agent是Tool Use的扩展**：Agent增加了长期记忆、自主规划和多智能体协作能力

在实际应用中，通常会将三者结合起来：用RAG获取知识，用Tool Use执行操作，用Agent进行规划和协调，构建完整的智能系统。
