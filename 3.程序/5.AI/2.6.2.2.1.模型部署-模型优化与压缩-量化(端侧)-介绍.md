# 移动端/嵌入式场景量化详解

移动端和嵌入式场景的量化与云端量化有着本质不同。云端可以靠更多GPU、更大显存和更高功耗来换取性能，而移动端/嵌入式设备面临**算力有限、内存极小、功耗敏感、无风扇散热**的四重约束。因此，端侧量化不只是把FP32变成INT8/INT4这么简单，而是一整套围绕**硬件指令集、内存带宽、功耗控制**的系统性优化。

## 一、为什么端侧量化比云端更有挑战？

云端GPU（如H100、A100）有专门的低精度计算单元（Tensor Core），高位宽内存带宽，功耗可以高达数百瓦。而移动端/嵌入式端：

- **芯片是资源受限的**：手机SoC（如骁龙、天玑）的内存带宽通常只有云端GPU的几十分之一，CPU和GPU共享有限的热设计功耗（TDP，通常仅3-5W）。
- **没有万能加速器**：不同手机的NPU（神经网络处理单元）架构各异（高通Hexagon、联发科APU、华为达芬奇），算子支持程度参差不齐。
- **用户体验要求苛刻**：推理不能长时间占用CPU/GPU导致手机发烫、掉电快，首Token延迟必须控制在几百毫秒内。

**端侧量化的核心矛盾**：要在极低的功耗预算和内存带宽下，用有限的硬件指令集跑出可接受的速度和精度。

## 二、端侧硬件加速指令集

移动端CPU（ARM架构）从几十毫瓦到几瓦，是端侧量化的主力执行单元。近几代ARM架构陆续加入了专门的低精度计算指令：

| 指令集 | 出现代际 | 作用 | 加速效果 |
|--------|----------|------|----------|
| **SDOT** | ARMv8.2-A (2017) | 一次指令完成4个INT8乘加运算（4×INT8 → INT32） | 比标量指令快4倍 |
| **I8MM** | ARMv8.6-A (2020) | 一次指令完成8个INT8乘加运算（8×INT8 → INT32） | 比SDOT再快2倍，理论吞吐量翻倍 |
| **SME/SME2** | ARMv9 (2021+) | 支持矩阵外积运算，可同时处理多个精度（FP32/FP16/INT8） | INT8矩阵乘可达传统方案的数倍性能 |

LLaMA.cpp、MNN、XNNPack等端侧推理引擎都在底层调用了这些指令。ARM通过KleidiAI库将这些优化整合进XNNPack，开发者无需改代码就能享受加速。MNN-LLM也专门针对i8mm指令做了优化，理论算力可达sdot的两倍。

此外，**ARM CPU的缓存层级（L1/L2/L3）和数据布局**对量化性能也有巨大影响。量化后的INT8权重虽然体积小，但如果数据排布不合理（未做pack/重排），会导致频繁的cache miss，实际访存延迟可能抵消掉计算加速。主流推理引擎都会根据ARM的缓存结构对权重矩阵做**分块(tiling)和重排(packing)**，最大化缓存命中率。

## 三、移动端/嵌入式量化的核心方案

### 3.1 模型格式

端侧推理引擎通常不直接吃ONNX或PyTorch模型，而是转换为各自的高效格式：

| 引擎 | 模型格式 | 量化支持 | 特点 |
|------|----------|----------|------|
| **TFLite** | `.tflite` | INT8 / FP16 | FlatBuffer格式，零解析延迟 |
| **NCNN** | `.param` + `.bin` | INT8 对称/非对称 | 腾讯开源，轻量级视觉模型首选 |
| **MNN** | `.mnn` | INT8 / INT4 / FP16 | 阿里出品，淘宝钉钉30+App落地 |
| **llama.cpp** | `.gguf` | 2-8 bit 分组量化 | CPU上跑LLM的事实标准 |
| **Core ML** | `.mlpackage` | INT8 / FP16 | Apple生态，iOS/macOS专用 |

TFLite的`.tflite`格式基于FlatBuffers，无需反序列化即可直接内存映射，加载速度极快。NCNN的`ncnn2int8`工具支持`kl`和`aciq`两种校准算法，推荐`kl`对抗离群值更鲁棒。

### 3.2 量化比特位的选择

| 比特位 | 压缩比 | 精度损失 | 推荐场景 |
|--------|--------|----------|----------|
| **INT8** | 4倍（vs FP32） | <1% | 视觉模型（YOLO、ResNet），大多数端侧任务的首选 |
| **INT4** | 8倍（vs FP32） | 1-3% | 端侧大语言模型（LLM），<4GB内存设备 |
| **FP16** | 2倍（vs FP32） | 可忽略 | 部分NPU原生支持浮点加速（如Apple Neural Engine） |
| **混合精度** | 灵活 | 可控 | 权重INT4 + 激活FP16，兼顾精度与速度 |

学术研究表明，INT8对于MobileNetV2这类轻量级视觉模型是帕累托最优——比FP16节能2.8倍，或同功耗下精度高10%。

### 3.3 量化策略：PTQ vs QAT

| 策略 | 是否需要重新训练 | 数据需求 | 精度 | 开发效率 |
|------|----------------|----------|------|----------|
| **PTQ（训练后量化）** | 否 | 100-500张校准图 | 中高 | 高 |
| **QAT（量化感知训练）** | 是 | 完整训练集 | 高 | 中低 |

对于移动端大部分视觉模型，**PTQ足矣**。YOLOv8这类目标检测模型，用100-500张代表性图片做校准，INT8量化后精度损失通常在1-2%以内。如果精度损失超标，或量化到INT4以下，才需要考虑QAT。

移动端LLM常用的量化算法：

- **GPTQ**：训练后权重量化，无需数据，适合INT4/INT8，7B模型可压缩至4GB以内。
- **GGUF（llama.cpp的量化格式）** ：支持2-8位量化，K系列（KQ4/KQ8）采用分组量化策略，每个子矩阵独立缩放，精度优于全局量化。

### 3.4 主流端侧推理引擎对比

| 维度 | **TFLite** | **NCNN** | **MNN** | **llama.cpp** |
|------|------------|----------|---------|---------------|
| **开发者** | 理想汽车 | 腾讯 | 阿里巴巴 | ggerganov（社区） |
| **定位** | 移动端通用推理 | 移动端视觉模型 | 端侧全场景+大模型 | CPU端大语言模型 |
| **量化支持** | INT8/FP16 | INT8 | INT4/INT8/FP16 | 2-8 bit GGUF |
| **NPU加速** | NNAPI/Qualcomm delegate | 有限支持 | 华为HiAI、高通SNPE等 | 无 |
| **包体积** | ~1MB | ~500KB | ~3MB (Android .so) | <10MB编译后 |
| **大模型支持** | 弱 | 弱 | 强（MNN-LLM已适配Qwen/DeepSeek等） | 最强（LLM事实标准） |
| **Android单线程** | 基准 | 约1.8倍TFLite | 约1.8倍TFLite | 一般 |
| **Android多线程** | 基准 | 约3.5倍TFLite | 约3.5倍TFLite | 较好 |

**选型快速指引**：

| 你的需求 | 首选方案 |
|----------|----------|
| 移动端视觉模型（人脸检测、OCR、物体识别） | NCNN或TFLite |
| 移动端LLM（1-7B参数，4GB内存以内） | llama.cpp (GGUF INT4) 或 MNN-LLM |
| iOS/macOS生态 | Core ML |
| 跨平台全场景通用 | MNN |
| 手机本地智能客服、文档分析 | MNN + DeepSeek-6.7B-INT4 |

## 四、端侧量化完整工作流程

### 步骤1：模型准备（PyTorch → ONNX）

```python
import torch
model = ...  # 已训练好的模型
dummy_input = torch.randn(1, 3, 224, 224)
torch.onnx.export(model, dummy_input, "model.onnx", 
                  input_names=["input"], output_names=["output"])
```

### 步骤2：格式转换

以NCNN为例：

```bash
# ONNX → NCNN FP32
onnx2ncnn model.onnx model.param model.bin

# 优化模型结构（融合算子、去冗余）
ncnnoptimize model.param model.bin model.opt.param model.opt.bin 0

# 生成量化校准表（INT8）
ncnn2table model.opt.param model.opt.bin calibration.list model.table \
           method=kl mean=[104,117,123] norm=[0.017,0.017,0.017] \
           shape=[224,224,3] pixel=BGR thread=8

# 转换为 INT8 模型
ncnn2int8 model.opt.param model.opt.bin model.table model.int8.param model.int8.bin
```

### 步骤3：校准数据集准备

校准集必须代表真实推理场景的输入分布。YOLOv8目标检测模型建议100-500张，采用**分层采样**确保覆盖不同场景（大小目标、光照条件、背景复杂度）。校准图片不需要标签，只需做一次前向传播统计激活值分布。

### 步骤4：精度评估与验证

在同一验证集上跑FP32和INT8模型，对比mAP/准确率。重点关注边缘场景（小目标、弱光照），如果精度下降超过可接受范围（如>2%），考虑换用method=aciq或升级到QAT。

### 步骤5：端侧集成与优化

```bash
# Android集成NCNN
android.loadLibrary("ncnn")
val net = ncnn.Net()
net.opt.use_vulkan_compute = true   # 启用GPU加速
net.load_param("model.int8.param")
net.load_model("model.int8.bin")

# 启用内存池减少动态分配
net.opt.use_vulkan_compute = true
# 设置合理的线程数（通常等于CPU小核数）
net.opt.num_threads = 4
```

### 步骤6：整型推理（TFLite完整INT8）

TFLite支持**完整INT8推理**，即权重和激活值均为INT8，输入输出也为INT8：

```python
converter = tf.lite.TFLiteConverter.from_saved_model("float_model")
converter.optimizations = [tf.lite.Optimize.DEFAULT]
converter.representative_dataset = representative_data_gen
converter.target_spec.supported_ops = [tf.lite.OpsSet.TFLITE_BUILTINS_INT8]
converter.inference_input_type = tf.uint8   # 输入强制INT8
converter.inference_output_type = tf.uint8  # 输出强制INT8
quantized_model = converter.convert()
```

这种模式下，输入图片需预处理为[0,255]整数并转为uint8格式，无需浮点转换，完全利用NPU的INT8专用算力单元。

## 五、实战建议与决策表

| 部署场景 | 推荐量化方案 | 预期精度损失 | 推荐引擎 |
|----------|--------------|--------------|----------|
| 移动端人脸检测（≤10MB模型） | INT8 PTQ (KL) | <0.5% | NCNN / TFLite |
| 移动端目标检测（YOLOv8） | INT8 PTQ + 分层采样校准 | <1% | NCNN / TFLite |
| 移动端 OCR 文本识别 | INT8 PTQ (Per-channel) | <1% | MNN / NCNN |
| 手机端LLM（1-3B，<4GB内存） | INT4 GGUF (KQ4) | 1-2% | llama.cpp / MNN-LLM |
| 手机端LLM（7B，旗舰机） | INT4 GGUF (KQ4_K_M) | 1-3% | llama.cpp |
| IoT 语音唤醒（极低功耗） | INT8 + NPU delegate | 1-2% | TFLite + SNPE/HiAI |
| 树莓派边缘推理 | INT8 或 INT4 GGUF | 1-3% | NCNN / llama.cpp |
| iOS 端 LLM | FP16 / INT8 | 可忽略 | Core ML + llama.cpp |

**精度优先原则**：如果INT8 PTQ后精度不达标，优先排查校准集代表性而非直接上QAT。校准集未能覆盖实际推理场景的所有激活分布，是PTQ精度下降的最常见原因。

## 六、端侧量化的未来趋势

- **更低比特（INT2/INT3）** ：MNN已探索2-bit量化，进一步压缩模型，精度损失可控。
- **硬件加速增强**：ARM SME2指令集为INT8矩阵乘带来显著性能提升，未来端侧CPU跑LLM将更快。
- **NPU标准化**：随着Google的AI Edge、Qualcomm QNN等统一接口推进，跨芯片的量化部署将不再碎片化。
- **混合精度自动化**：未来引擎将自动识别敏感层保留高精度，非敏感层压到低比特，无需人工调参。

量化是端侧部署的**必选项**而非可选项。对于移动端/嵌入式场景，**INT8 + NCNN/TFLite** 是视觉模型的稳妥起点，**INT4 + llama.cpp/MNN** 是大语言模型落地的成熟路径。校准数据的质量往往决定量化成败——花时间准备覆盖真实场景的100-500张图片，比调参一天更有效。
