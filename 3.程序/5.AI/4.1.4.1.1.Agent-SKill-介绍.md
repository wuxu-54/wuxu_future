# 大模型应用工程中的 SKILL：从理论到实战全指南（工程级 + 规范级）

大模型应用工程中的 **SKILL（技能）** 是将大模型的通用推理能力转化为特定、可复用、可组合任务单元的核心抽象。它不是简单的 prompt，也不是单一的工具调用，而是封装了**意图理解、输入输出契约、执行逻辑、安全控制、错误处理**的完整能力模块。

在生产环境中，Skill 存在两种主流开发方式：**工程级 Skill** 和 **规范级 Skill**。理解两者的区别与联系，是从“会写 prompt”到“能构建生产级大模型应用”的关键一步。

---

## 一、SKILL 基础理论：核心概念与心智模型

### 1.1 什么是真正的 SKILL？

SKILL 是大模型应用的“乐高积木”，定义了大模型“能做什么”和“怎么做”。它与以下概念有本质区别：

| 概念 | 核心 | 特点 | SKILL 的不同之处 |
|------|------|------|------------------|
| Prompt | 文本指令 | 一次性、无结构、难复用 | 封装 prompt，提供标准化接口 |
| Tool | 外部能力 | 执行确定性操作（计算、搜索） | SKILL 可以调用多个 Tool，包含模型推理 |
| Agent | 自主决策者 | 规划-执行-反思循环 | Agent 由多个 SKILL 组合而成，SKILL 是 Agent 的执行单元 |
| Chain | 执行链路 | 固定顺序的步骤组合 | SKILL 是 Chain 的组成部分，可独立存在 |

**SKILL 的本质**：将模糊的自然语言需求转化为**有明确边界、可预测输出、可测试验证**的标准化能力单元。

### 1.2 SKILL 的核心三要素

任何一个完整的 SKILL 都必须包含这三个部分：

1. **能力契约（Contract）**  
   - 技能名称：简洁明确的动词+名词结构（如 `SummarizeText`、`ExtractEntities`）  
   - 技能描述：清晰说明技能的用途、适用场景和限制  
   - 输入 Schema：定义接受的参数类型、格式和必填项  
   - 输出 Schema：定义返回结果的结构、格式和含义

2. **执行逻辑（Logic）**  
   - 核心 prompt 模板：针对特定任务优化的系统提示和用户提示  
   - 模型参数配置：temperature、max_tokens、top_p 等  
   - 前处理逻辑：输入验证、格式化、上下文组装  
   - 后处理逻辑：结果解析、校验、格式化、错误修正

3. **质量保障（Quality）**  
   - 异常处理：模型调用失败、输出格式错误、结果无效的处理  
   - 重试机制：针对瞬时错误的自动重试策略  
   - 验证逻辑：检查输出是否符合预期和 Schema  
   - 日志记录：记录输入、输出、耗时和错误信息

### 1.3 为什么需要 Skill？传统方式的三大痛点

在 Skill 出现之前，大模型应用开发主要依赖“提示词堆砌 + 零散工具调用”，这种方式在生产环境中存在致命缺陷：

**① 提示词爆炸与维护噩梦**  

- 随着功能增加，系统提示词会膨胀到几千甚至上万 token  
- 不同功能的提示词混杂在一起，相互干扰  
- 修改一个功能可能影响其他所有功能  
- 没有版本管理，无法回滚

**② 工具调用混乱**  

- 所有工具都全局暴露给大模型，容易出现工具选择错误  
- 没有权限控制，一个简单任务可能调用危险工具  
- 没有统一的错误处理和重试机制

**③ 业务逻辑无法复用**  

- 相同的业务逻辑需要在不同的地方重复编写  
- 团队成员之间无法共享最佳实践  
- 新功能开发需要从零开始

Skill 通过**模块化封装**完美解决了这些问题：  

- 每个 Skill 只负责一个特定的业务任务，职责单一  
- 按需加载，只有相关的 Skill 才会被注入上下文  
- 标准化的接口和格式，便于团队共享和复用  
- 支持版本管理和灰度发布

## 二、SKILL 的两种形态：工程级 vs 规范级

> 我在做 SKILL 的 Demo 学习时，AI 给的都是代码级的实现，但我疑惑为什么我整理的 SKILL 介绍文档里却有很多复杂结构？如果你也有类似困惑，那看这篇文章可以解惑。

1. **工程级 Skill**（`@tool`）：将普通函数通过装饰器注册为 Agent 可直接调用的工具对象，运行在 Agent 同一进程内，依赖特定框架（如 LangChain）。  
2. **规范级 Skill**（`SKILL.md`）：通过文件夹 + `SKILL.md` 元数据文件声明技能的用途、输入输出及执行方式。Agent 扫描发现技能，按描述启动子进程或外部调用执行，与 Agent 框架解耦、跨平台复用。

**核心区别**：前者是“函数直接嵌入”，后者是“文件声明 + 独立执行”。两者可共存，规范级 Skill 可调用代码级 Skill。

### 2.1 工程级 Skill（代码直接封装）

**本质**：将普通函数或类方法通过特定框架的装饰器（如 LangChain 的 `@tool`）或注册机制，转换为 Agent 可直接调用的**工具（Tool）**。

- **表现形式**：Python 函数 + 类型注解 + docstring（作为工具描述）。  
- **运行机制**：Agent 根据函数签名和描述，决定何时调用，并传入参数执行，返回结果。整个过程在 Agent 进程内完成。  
- **优点**：与框架深度集成，开发效率高，支持复杂逻辑和状态共享。  
- **缺点**：与特定框架强绑定，难以跨平台复用；需要编码，非技术人员无法参与。

**示例**（LangChain 风格）：

```python
from langchain.tools import tool

@tool
def calculate_bmi(weight_kg: float, height_m: float) -> str:
    """计算体重指数（BMI）并给出健康建议。"""
    bmi = weight_kg / (height_m ** 2)
    return f"BMI: {bmi:.1f}"
```

### 2.2 规范级 Skill（声明式文件封装）

**本质**：一种**目录结构规范 + SKILL.md 元数据文件**，用于描述技能的用途、输入输出、执行方式。Agent 通过读取 `SKILL.md` 理解技能功能，并按说明调用相应的脚本或 API。

- **表现形式**：一个文件夹，包含 `SKILL.md`（必需）和可选的脚本、资源文件等。  
- **运行机制**：Agent 扫描技能目录，解析 YAML frontmatter 和 Markdown 正文，将技能注册为“元工具”。当用户触发时，Agent 根据描述执行外部脚本或调用 API（通常运行在独立进程或容器中）。  
- **优点**：框架无关，可跨平台复用（Cline、Claude Code、Continue 等均支持）；非技术人员可编写/修改描述；支持多语言实现。  
- **缺点**：执行开销稍高；复杂状态管理不如直接代码方便。

**示例目录结构**：

```
bmi-calculator/
├── SKILL.md
└── scripts/
    └── calculate.py
```

**SKILL.md 示例**：

```markdown
---
name: bmi-calculator
description: 计算体重指数并给出健康建议。当用户提供身高体重时使用。
inputs:
  - name: weight_kg
    type: number
  - name: height_m
    type: number
outputs:
  - type: string
---
# 执行方法
运行 `python scripts/calculate.py --weight {{weight_kg}} --height {{height_m}}`
```

### 2.3 两者的关系与选择

| 维度 | 工程级 Skill | 规范级 Skill |
|------|-------------|--------------|
| 实现方式 | 代码函数 + 装饰器 | 文件夹 + SKILL.md 文件 |
| 框架依赖 | 强（如 LangChain、LlamaIndex） | 弱（仅依赖文件规范） |
| 跨平台复用 | 困难 | 容易（复制文件夹即可） |
| 执行环境 | Agent 进程内 | 独立子进程或外部 API |
| 多语言支持 | 仅限 Python | 任意语言（脚本、二进制） |
| 适用场景 | 内部工具、高速调用、复杂状态 | 通用能力库、跨平台分享、低代码维护 |

**实际项目中，两者可以并存**：核心业务逻辑用工程级 Skill 保证性能；对外共享或需要非技术人员维护的功能用规范级 Skill 封装。

> 下文将重点围绕**规范级 Skill**（`SKILL.md` 方式）展开详细讲解，因为它是当前社区跨平台复用的事实标准。同时会补充工程级 Skill 的关键实现要点。

## 三、Skill 的核心组成与标准规范

本节以**规范级 Skill**（`SKILL.md` 为基础）为主，补充工程级 Skill 的对应概念。

### 3.1 规范级 Skill 的目录结构（事实标准）

```
pdf-form-filler/
├── SKILL.md           # 核心文件，包含元数据和执行流程（必须）
├── config.json        # 配置文件（可选）
├── schema.json        # 输入输出 Schema（可选，强烈推荐）
├── templates/         # 模板文件目录（可选）
│   └── form_template.pdf
├── scripts/           # 辅助脚本目录（可选，支持任意语言）
│   └── pdf_utils.py
├── references/        # 参考资料目录（可选）
│   └── pdf_spec.md
└── tests/             # 测试用例目录（可选）
    └── test_cases.md
```

### 3.2 SKILL.md 文件规范（三级加载机制）

SKILL.md 是规范级 Skill 的核心，分为 **YAML Frontmatter**（元数据）和 **Markdown 正文**（指令）两部分。

- **YAML 头部**：总是加载（约 100~200 token），用于技能匹配和路由。  
- **Markdown 正文**：当技能被触发时才加载，包含详细的执行流程、输入输出示例、错误处理等。  
- **链接资源**（如 `references/` 下的文档）：按需加载，只有需要时才读取。

**标准 SKILL.md 示例**：

```markdown
---
name: pdf-form-filler
version: 1.0.0
description: 自动识别PDF表单中的字段并填写内容。支持文本、复选框、单选按钮。
author: 张三
tags: [PDF, 表单, 办公自动化]
dependencies: [file-reader]
privileges: [file_read, file_write]
---

# PDF表单填写技能

## 功能描述
本技能用于自动填写PDF表单。它会先读取PDF文件，识别所有可填写字段，然后根据用户提供的数据填充这些字段，最后生成填写好的PDF文件。

## 执行流程
1. 接收用户输入：PDF文件路径和要填写的数据
2. 调用file-reader工具读取PDF文件
3. 识别表单字段
4. 验证用户提供的数据是否匹配字段要求
5. 填写表单字段
6. 保存填写好的PDF文件
7. 返回文件路径给用户

## 输入要求
- pdf_path: 本地PDF文件的路径（必填）
- data: 字典，键为字段名，值为要填写的内容（必填）
- flatten: 是否扁平化表单，默认为true（可选）

## 输出格式
输出应为JSON格式，结构如下：
{
  "status": "success",
  "message": "表单填写成功",
  "output_path": "/path/to/filled.pdf",
  "filled_fields": ["name", "email", "phone"]
}

## 错误处理
- 如果PDF文件不存在，返回错误："文件不存在"
- 如果字段不匹配，返回错误："缺少以下字段：xxx"
- 如果填写失败，返回错误："表单填写失败：xxx"

## 示例
用户输入：
请填写这个表单：/tmp/form.pdf
数据：
{
  "name": "张三",
  "email": "zhangsan@example.com",
  "phone": "13800138000"
}

期望输出：
{
  "status": "success",
  "message": "表单填写成功",
  "output_path": "/tmp/filled_form.pdf",
  "filled_fields": ["name", "email", "phone"]
}
```

### 3.3 工程级 Skill 的核心能力组件（7 层结构）

对于工程级 Skill（如 LangChain 的 `@tool`），生产环境必须包含以下 7 层：

| 层级 | 核心职责 | 关键技术 | 失败处理 |
|------|----------|----------|----------|
| 元数据层 | 让大模型理解 SKILL | `@tool` 装饰器、docstring | 大模型不调用或调用错误 |
| 输入模型层 | 参数校验与标准化 | Pydantic、Field、@validator | 返回参数错误 |
| 安全校验层 | 防止未授权操作 | 权限校验、输入过滤、幂等性 | 返回权限错误 |
| 日志审计层 | 记录调用行为 | logging、脱敏处理 | 不影响业务执行，但无法审计 |
| 核心业务逻辑层 | 实现核心功能 | 业务代码、API调用 | 抛出异常，进入错误处理层 |
| 错误处理层 | 统一异常处理 | try-except、分级错误 | 返回结构化错误信息 |
| 输出规范层 | 统一返回格式 | 字典、JSON | 大模型无法解析结果 |

> 规范级 Skill 也建议遵循类似的分层思想，但实现上更依赖 `SKILL.md` 中的指令和外部脚本的自身质量。

## 四、Skill 的完整工作流程

### 4.1 规范级 Skill 的工作流程（6 步）

规范级 Skill 的执行遵循“**元数据路由 + 按需加载 + 流程化执行**”的核心原理，分为 6 个标准步骤：

**步骤1：技能注册**  
系统启动时扫描所有 Skill 目录，读取每个 Skill 的 YAML 头部元数据，构建技能索引（名称、描述、标签），验证依赖和权限。

**步骤2：意图理解与技能匹配**  
用户输入任务后，系统不会加载所有 Skill 的完整内容，而是先进行技能匹配：  

- **语义路由**：将用户输入向量化，与所有 Skill 的描述向量进行相似度匹配。  
- **LLM 分发员**：使用一个轻量级模型专门负责选择最合适的 Skill。  
- **混合路由**：先用语义路由快速筛选，再用 LLM 确认。

**步骤3：技能激活与加载**  
匹配到目标 Skill 后，加载 SKILL.md 的完整正文，加载该 Skill 依赖的其他 Skill 和工具，注入专属系统提示和工具集，初始化运行环境。

**步骤4：流程化执行**  
大模型按照 SKILL.md 中定义的执行流程逐步执行，框架调度工具调用并处理返回结果，自动进行输入验证和输出校验，处理执行过程中的错误和异常。

**步骤5：结果生成与格式化**  
按照 Skill 定义的输出格式生成结果，过滤敏感信息和无关内容，进行合规性检查，返回最终结果给用户。

**步骤6：技能卸载与清理**  
任务完成后卸载 Skill 的上下文，清理临时文件和资源，记录执行日志和指标，关闭不需要的工具连接。

### 4.2 工程级 Skill 的工作流程

工程级 Skill 的工作流程类似，但跳过了“扫描目录”和“加载 Markdown”步骤，直接通过代码注册函数，运行时由 Agent 根据函数描述进行调用。其核心步骤为：  

1. 工具注册（代码中显式添加）  
2. 意图匹配（基于函数名和 docstring）  
3. 参数生成与校验  
4. 函数执行  
5. 结果返回

## 五、Skill 的分类与编排

### 5.1 Skill 的常见分类

按照复杂度和功能，Skill 可以分为以下 4 类：

| 类型 | 特点 | 示例 |
|------|------|------|
| **原子技能** | 单一功能，不可再分 | 文本提取、数据清洗、格式转换 |
| **复合技能** | 由多个原子技能组合而成 | 文档解析、数据可视化、邮件发送 |
| **工作流技能** | 包含复杂的分支和循环逻辑 | 代码审查、周报生成、项目管理 |
| **领域技能** | 针对特定行业或领域的专业技能 | 医疗诊断、法律咨询、财务分析 |

### 5.2 多 Skill 编排方式

当系统拥有多个 Skill 时，需要合适的编排方式来协调它们的工作：

**(1) 顺序编排**  
Skill 按照固定的顺序依次执行，前一个 Skill 的输出作为后一个 Skill 的输入。  

- **适用场景**：线性流程的任务  
- **示例**：数据采集 → 数据清洗 → 数据分析 → 报告生成

**(2) 并行编排**  
多个独立的 Skill 同时执行，最后合并结果。  

- **适用场景**：没有依赖关系的任务  
- **示例**：同时查询多个数据源、同时生成多个图表

**(3) 依赖链编排**  
Skill 之间有明确的依赖关系，只有所有依赖都执行完成后，目标 Skill 才会执行。  

- **适用场景**：有复杂依赖关系的任务  
- **示例**：生成销售报告需要先执行“销售数据查询”和“用户数据查询”

**(4) 技能图编排（GraSP）**  
将 Skill 组织成有向无环图（DAG），节点是 Skill，边是依赖关系。系统按照拓扑顺序执行 Skill，失败时只需要重新执行受影响的部分。  

- **适用场景**：非常复杂的业务流程  
- **优势**：支持局部重试、增量执行、动态调整

其中规范级 Skill 更容易通过文件声明组成 DAG，工程级 Skill 则通常由 LangGraph 等框架进行编排。

## 六、主流 Skill 框架与平台

### 1. Anthropic Claude Skills

- **发起者**：Skill 概念的提出者，事实标准的制定者  
- **特点**：基于文件系统的 Skill，纯声明式定义，不需要编写代码  
- **生态**：拥有最大的社区 Skill 库，支持 MCP 协议  
- **适用场景**：Claude 生态应用、快速原型开发  
- **对两种形态的支持**：规范级原生支持；工程级可通过 MCP 调用代码

### 2. LangChain Tools & LangGraph

- **特点**：最成熟的 Skill/工具生态，支持所有主流大模型  
- **优势**：组件丰富，集成了 600+ 现成的工具和 Skill  
- **LangGraph**：专门用于复杂工作流和多 Skill 编排  
- **适用场景**：企业级复杂应用、生产环境部署  
- **对两种形态的支持**：工程级原生支持（@tool、StructuredTool）；规范级可通过自定义 Loader 支持

### 3. OpenAI Swarm

- **特点**：轻量级多智能体和 Skill 编排框架  
- **优势**：API 简洁，上手容易，与 OpenAI 模型深度集成  
- **核心概念**：将 Agent 和 Skill 统一抽象为“Agent”  
- **适用场景**：OpenAI 生态应用、多智能体系统  
- **对两种形态的支持**：工程级原生支持（函数作为工具）；规范级不直接支持，可封装

### 4. MCP（模型上下文协议）服务器

- **特点**：跨平台的标准化 Skill/工具协议  
- **优势**：一次开发，到处运行，支持所有主流 AI 应用  
- **定位**：Skill 的底层传输和交互协议  
- **适用场景**：跨平台应用、生态建设  
- **对两种形态的支持**：工程级和规范级均可通过 MCP 协议暴露

### 5. 微软 Semantic Kernel

- **特点**：企业级 Skill 框架，支持 C#、Python、Java  
- **优势**：与微软生态深度集成，支持插件化 Skill  
- **核心概念**：“Semantic Function”（语义函数）即 Skill  
- **适用场景**：微软生态企业应用  
- **对两种形态的支持**：工程级原生支持（插件式技能）；规范级不直接支持

## 七、Skill 的数据协议约束

以下数据协议主要适用于**规范级 Skill** 以及基于 MCP 的跨平台交换。工程级 Skill 的数据约束主要由框架（如 Pydantic）和类型系统保证，无需额外遵循 MCP 规范。

数据协议约束是确保 Skill 在不同平台和框架间能够互操作的关键。随着 MCP（Model Context Protocol）成为行业标准，Skill 的数据交换必须遵循严格的协议规范。

### 7.1 MCP（模型上下文协议）核心规范

MCP 是 Skill 数据交换的底层标准协议，定义了统一的数据格式、传输机制和安全约束。

#### (1) 消息格式约束

| 约束类型 | 规范要求 | 优点 | 缺点 | 适用场景 |
|----------|----------|------|------|----------|
| **统一 JSON Schema** | 所有 Skill 的输入输出必须符合预定义的 JSON Schema | 确保数据结构一致性，便于验证和解析 | 需要额外的 Schema 维护成本 | 所有生产环境 Skill |
| **消息头规范** | 包含 `skill_id`、`version`、`timestamp`、`correlation_id` 等元数据 | 支持完整的追踪和调试能力 | 增加消息体积约 50-100 字节 | 分布式系统、微服务架构 |
| **内容编码** | 支持 UTF-8 编码，二进制数据必须 Base64 编码 | 兼容性好，避免编码问题 | Base64 编码增加 33% 数据体积 | 跨平台数据交换 |

#### (2) 序列化要求

| 要求类型 | 规范说明 | 技术实现 | 重要性 | 注意事项 |
|----------|----------|----------|--------|----------|
| **确定性序列化** | 相同数据必须产生相同的序列化结果 | 使用确定性 JSON 库（如 json-stable-stringify） | ⭐⭐⭐⭐⭐ | 避免使用默认 JSON.stringify |
| **字段排序** | JSON 对象的字段必须按字典序排列 | 序列化前对对象键进行排序 | ⭐⭐⭐⭐ | 影响哈希计算和缓存 |
| **空值处理** | 显式 null 值必须保留，不能省略字段 | 配置序列化器保留 null 值 | ⭐⭐⭐ | 确保 Schema 验证通过 |

#### (3) 数据类型约束

```json
{
  "type": "object",
  "properties": {
    "skill_id": {"type": "string", "pattern": "^[a-z][a-z0-9-]*$"},
    "version": {"type": "string", "pattern": "^\\d+\\.\\d+\\.\\d+$"},
    "input": {"type": "object"},
    "context": {
      "type": "object",
      "properties": {
        "user_id": {"type": "string"},
        "session_id": {"type": "string"},
        "permissions": {"type": "array", "items": {"type": "string"}}
      }
    }
  },
  "required": ["skill_id", "version", "input"]
}
```

### 7.2 输入输出数据约束

#### (1) 输入数据约束

| 约束维度 | 具体要求 | 验证方式 | 错误处理 | 最佳实践 |
|----------|----------|----------|----------|----------|
| **必填字段验证** | 所有必填字段必须在输入中提供 | JSON Schema 验证 | 返回 400 错误码 | 在 SKILL.md 中明确标注必填字段 |
| **类型安全** | 严格验证数据类型，禁止隐式类型转换 | 类型检查库（如 zod、pydantic） | 返回类型错误信息 | 使用强类型语言或运行时验证 |
| **长度限制** | 字符串 ≤10KB，数组 ≤1000 项，嵌套深度 ≤10 层 | 递归验证函数 | 返回大小超限错误 | 分页处理大数据集 |
| **字符集限制** | 仅允许 UTF-8 字符，特殊字符必须转义 | 正则表达式验证 | 返回编码错误 | 统一使用 UTF-8 编码 |

#### (2) 输出数据约束

| 约束维度 | 具体要求 | 实现方案 | 监控指标 | 优化建议 |
|----------|----------|----------|----------|----------|
| **结构一致性** | 成功和失败情况下的输出结构必须保持一致 | 统一响应包装器 | 结构变更告警 | 定义标准响应接口 |
| **错误码标准化** | 使用统一的错误码体系（如 HTTP 状态码映射） | 错误码枚举类 | 错误码分布统计 | 建立错误码文档 |
| **敏感信息过滤** | 自动过滤 PII（个人身份信息）和敏感数据 | 敏感词检测+正则匹配 | 数据泄露事件数 | 定期更新敏感词库 |
| **大小限制** | 单次输出不超过 1MB，超过时必须分页或截断 | 流式输出+分页机制 | 响应大小分布 | 压缩大文本数据 |

### 7.3 上下文数据协议

Skill 执行过程中涉及的上下文数据也必须遵循协议约束。

#### (1) 会话上下文

| 上下文元素 | 规范要求 | 存储方式 | 生命周期 | 安全考虑 |
|------------|----------|----------|----------|----------|
| **thread_id** | 唯一标识会话，用于状态持久化 | UUID v4 格式 | 会话结束时清理 | 不包含用户标识信息 |
| **message_history** | 消息历史必须按时间戳排序 | 时间序列数据库 | 可配置保留天数 | 敏感消息自动脱敏 |
| **state_snapshot** | 状态快照必须包含完整的上下文信息 | JSON 序列化存储 | 任务完成后保留 24 小时 | 加密存储敏感状态 |

#### (2) 权限上下文

| 权限要素 | 约束规则 | 验证时机 | 审计要求 | 最佳实践 |
|----------|----------|----------|----------|----------|
| **最小权限原则** | 只传递必要的权限信息 | Skill 加载时 | 记录权限授予日志 | 定期审查权限范围 |
| **权限继承** | 子 Skill 只能继承父 Skill 的权限子集 | 子 Skill 激活时 | 记录权限继承链 | 避免过度授权 |
| **权限验证** | 每次工具调用前必须验证权限 | 工具调用前 | 记录权限验证结果 | 失败时提供详细原因 |

### 7.4 跨平台兼容性约束

为了确保 Skill 在不同框架间的兼容性，必须遵循以下约束：

#### (1) 通用数据类型兼容性

| 数据类型 | 标准格式 | 兼容性保障 | 转换策略 | 注意事项 |
|----------|----------|------------|----------|----------|
| **字符串** | UTF-8 编码 | 所有平台支持 | 直接传递 | 避免 BOM 标记 |
| **数字** | IEEE 754 双精度 | 高精度场景需注意 | 大数使用字符串 | 避免精度丢失 |
| **布尔值** | true/false | 完全兼容 | 直接传递 | 避免字符串 "true"/"false" |
| **时间戳** | ISO 8601 格式 | 广泛支持 | 统一时区为 UTC | 包含毫秒精度 |
| **数组/对象** | 标准 JSON | 完全兼容 | 直接传递 | 注意循环引用 |

#### (2) 工具调用协议标准化

| 协议要素 | 标准要求 | 实现示例 | 兼容性测试 | 常见问题 |
|----------|----------|----------|------------|----------|
| **参数 Schema** | 必须包含完整的参数定义 | OpenAPI 3.0 格式 | 跨框架调用测试 | 参数类型不匹配 |
| **返回结构** | 必须包含 status、data、error 三个字段 | `{status: "success", data: {...}, error: null}` | 响应解析测试 | 字段缺失 |
| **异步回调** | 支持 callback_url 和 webhook 机制 | 标准 HTTP POST 回调 | 网络连通性测试 | 回调地址验证 |

#### (3) 错误处理标准化

统一的错误响应格式：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "输入数据验证失败",
    "details": {
      "field": "email",
      "reason": "邮箱格式不正确"
    }
  }
}
```

| 错误类型 | HTTP 状态码 | 错误码前缀 | 重试策略 | 用户提示 |
|----------|-------------|------------|----------|----------|
| **验证错误** | 400 | VALIDATION_ | 不重试 | 显示具体字段错误 |
| **权限错误** | 403 | PERMISSION_ | 不重试 | 提示权限不足 |
| **资源不存在** | 404 | NOT_FOUND_ | 不重试 | 提示资源不存在 |
| **服务器错误** | 500 | SERVER_ | 指数退避重试 | 通用错误提示 |
| **限流错误** | 429 | RATE_LIMIT_ | 延迟重试 | 提示稍后重试 |

### 7.5 安全数据协议

数据协议还包含重要的安全约束：

#### (1) 数据完整性保障

| 安全机制 | 实现方式 | 验证流程 | 性能影响 | 适用级别 |
|----------|----------|----------|----------|----------|
| **数字签名** | HMAC-SHA256 签名 | 接收方验证签名 | 增加 5-10ms 延迟 | 生产环境必需 |
| **防重放令牌** | nonce + timestamp | 检查 nonce 唯一性和时效性 | 需要存储已用 nonce | 敏感操作必需 |
| **二次确认** | 临时授权令牌 | 用户确认后生成执行令牌 | 增加用户交互步骤 | 高危操作必需 |

#### (2) 数据加密要求

| 加密场景 | 加密标准 | 密钥管理 | 合规要求 | 实施建议 |
|----------|----------|----------|----------|----------|
| **传输加密** | TLS 1.3+ | 系统证书管理 | GDPR、CCPA | 强制启用 HSTS |
| **存储加密** | AES-256-GCM | KMS 服务管理 | 行业合规要求 | 敏感数据必选 |
| **密钥管理** | 零信任原则 | 硬件安全模块(HSM) | FIPS 140-2 | 金融级应用 |

#### (3) 审计追踪能力

| 审计要素 | 记录内容 | 存储要求 | 保留期限 | 查询能力 |
|----------|----------|----------|----------|----------|
| **操作日志** | 操作者、时间、操作类型、数据摘要 | 不可变存储 | ≥180 天 | 支持时间范围查询 |
| **数据血缘** | 数据来源、转换过程、使用去向 | 图数据库存储 | ≥365 天 | 支持血缘追溯 |
| **访问记录** | IP 地址、用户代理、访问路径 | 安全日志存储 | ≥90 天 | 支持异常检测 |

## 八、生产级 Skill 开发最佳实践

### 8.1 Skill 设计原则（两种形态通用）

- **单一职责**：一个 Skill 只做一件事，并且把它做好。  
- **高内聚低耦合**：Skill 内部逻辑紧密，与其他 Skill 的依赖尽可能少。  
- **明确边界**：清晰定义 Skill 的输入、输出和能力范围。  
- **可测试性**：提供完整的测试用例，便于自动化测试。  
- **可观测性**：记录详细的日志和指标，便于调试和监控。

### 8.2 常见坑与解决方案（结合两种形态）

| 问题 | 工程级 Skill 解决方案 | 规范级 Skill 解决方案 |
|------|----------------------|----------------------|
| 技能匹配错误 | 优化 docstring，添加更多示例 | 优化 SKILL.md 的 description 和 tags |
| 参数生成错误 | 使用 Pydantic 严格校验 | 在 SKILL.md 中明确定义 input schema，并使用脚本内部校验 |
| 上下文溢出 | 按需加载，使用摘要 | 利用三级加载机制，避免在正文中放置过多内容 |
| 执行不稳定 | 降低 temperature，增加确定性逻辑 | 在脚本中实现确定性处理，避免依赖 LLM 的自由发挥 |
| 安全风险 | 权限校验 + 沙箱执行 | 使用独立进程隔离，限制脚本权限 |
| 无限循环 | 设置最大迭代次数、检测重复调用 | 在 SKILL.md 中明确循环终止条件，Agent 框架实现断路 |

### 8.3 安全与权限控制（两种形态通用）

- **最小权限原则**：每个 Skill 只授予完成任务所需的最小权限。  
- **用户确认机制**：对于敏感操作（如写入文件、发送邮件），必须经过用户确认。  
- **沙箱隔离**：规范级 Skill 更容易实现独立沙箱；工程级 Skill 可借助容器或子进程。  
- **审计日志**：记录所有 Skill 的调用和执行情况，便于审计和追溯。

### 8.4 版本管理与发布

- 使用语义化版本号（MAJOR.MINOR.PATCH）。  
- 支持多版本共存，便于灰度发布和回滚。  
- 每个版本都有完整的变更日志。  
- 废弃的 Skill 保留一段时间，平滑过渡。

## 九、企业级 Skill 标准规范

企业级 Skill 是在生产级 Skill 基础上，针对企业级应用场景（金融、医疗、政务等）制定的更高标准规范，强调安全性、合规性、可审计性和稳定性。由于 Skill 存在两种不同的实现形态，企业级要求也相应分为**工程级企业 Skill** 和**规范级企业 Skill**，两者不可混同。

### 9.1 工程级企业 Skill 的七层代码架构

适用于 LangChain `@tool`、自定义 `BaseTool` 等工程实现。**所有企业级工程 Skill 必须严格遵循以下代码层结构，缺一不可：**

```
┌─────────────────────────────────────────────────┐
│ 1. 元数据层（大模型理解入口）                    │
│    - 函数名（语义化命名，动词+名词）             │
│    - docstring（包含功能、参数、返回值示例）     │
│    - 版本号、作者、最后更新时间（通过装饰器扩展） │
├─────────────────────────────────────────────────┤
│ 2. 输入模型层（参数标准化与校验）                │
│    - Pydantic BaseModel 定义                    │
│    - 每个参数：类型、描述、默认值、校验规则      │
│    - 枚举值、正则约束、范围限制                  │
├─────────────────────────────────────────────────┤
│ 3. 安全校验层（生产环境强制要求）                │
│    - 权限校验（用户是否有权调用该Skill）         │
│    - 输入安全过滤（防注入、防敏感内容）          │
│    - 幂等性校验（防止重复调用，尤其写操作）      │
├─────────────────────────────────────────────────┤
│ 4. 日志审计层（可观测性基础）                    │
│    - 调用入参（脱敏后）、调用时间、调用用户ID    │
│    - 执行结果、执行耗时、错误信息                │
│    - 全链路追踪ID                               │
├─────────────────────────────────────────────────┤
│ 5. 核心业务逻辑层（实际功能实现）                │
│    - 单一职责，只做一件事                        │
│    - 调用内部业务系统API/数据库                  │
│    - 业务规则处理                               │
├─────────────────────────────────────────────────┤
│ 6. 错误处理层（统一错误返回）                    │
│    - 捕获所有异常，不直接抛出给大模型            │
│    - 返回结构化错误信息（错误码、错误描述）      │
│    - 分级错误处理（可重试/不可重试）             │
├─────────────────────────────────────────────────┤
│ 7. 输出规范层（大模型可解析输出）                │
│    - 固定JSON格式返回                           │
│    - 包含 status、data（成功）或 error（失败）   │
│    - 结果描述清晰，无歧义                        │
└─────────────────────────────────────────────────┘
```

### 9.2 规范级企业 Skill 的强制目录与约束

规范级 Skill 基于 `SKILL.md` + 脚本实现，企业级场景下必须附加以下结构和要求。

#### 9.2.1 目录结构

```
enterprise-skill/
├── SKILL.md                     # 必须，包含完整YAML元数据和执行说明
├── schema/                      # 必须
│   ├── input.schema.json        # 输入JSON Schema
│   ├── output.schema.json       # 输出JSON Schema
│   └── error.schema.json        # 错误响应Schema
├── scripts/                     # 必须，至少一个可执行入口
│   └── run.py                   # 主脚本，必须实现权限校验、日志、审计
├── references/                  # 必须，包含企业级文档
│   ├── compliance.md            # 合规说明（GDPR/SOX等）
│   ├── security.md              # 安全设计文档
│   └── sla.md                   # 服务等级承诺
├── tests/                       # 必须
│   ├── unit/                    # 单元测试
│   ├── integration/             # 集成测试
│   └── security/                # 安全测试（渗透、注入）
├── audit_logs/                  # 运行时输出审计日志的目录
└── config/                      # 环境配置
    ├── production.json
    └── staging.json
```

#### 9.2.2 强制约束

1. **输入输出必须经过 JSON Schema 校验**：脚本执行前校验 `input.schema.json`，执行后校验 `output.schema.json`。  
2. **全链路审计**：脚本必须记录 `user_id`、`trace_id`、`timestamp`、`input_hash`、`output_size`，并写入审计日志（文件或远程服务）。  
3. **权限控制**：脚本必须根据 `user_id` 查询权限服务，拒绝无授权调用。  
4. **数据加密**：所有持久化的敏感数据（如用户文件、结果）必须使用 AES-256 或以上加密。  
5. **幂等性**：写操作必须支持幂等（通过请求去重表或业务键）。  
6. **错误标准化**：所有错误必须返回符合 `error.schema.json` 的 JSON，包含 `error_code`、`message`、`retryable` 字段。  
7. **SLA 监控**：脚本必须主动上报耗时、成功/失败指标到企业监控系统（如 Prometheus）。

#### 9.2.3 示例：脚本中的审计日志实现（伪代码）

```python
import logging, uuid, time, hashlib

def audit_log(user_id, input_data, output_data, error=None):
    trace_id = str(uuid.uuid4())
    record = {
        "trace_id": trace_id,
        "user_id": user_id,
        "timestamp": time.time(),
        "input_hash": hashlib.sha256(json.dumps(input_data).encode()).hexdigest(),
        "output_size": len(json.dumps(output_data)),
        "error": error
    }
    logging.getLogger("audit").info(json.dumps(record))
```

### 9.3 企业级通用约束（两种形态均适用）

## 总结

Skill 是大模型应用从“玩具”走向“生产工具”的关键抽象。  

- **工程级 Skill** 适合与框架深度集成、追求性能和复杂状态的内部场景。  
- **规范级 Skill** 适合跨平台共享、低代码维护、多语言实现的开放生态。

两者不是二选一，而是可以根据实际需求混合使用。例如：核心算法用工程级 Skill 封装，再通过一个规范级 Skill 的描述文件暴露给外部 Agent 使用。

对于新项目，建议优先采用**规范级 Skill** 定义能力边界，再用**工程级 Skill** 实现具体逻辑，从而兼顾可复用性和执行效率。

掌握 Skill 开发是构建生产级 AI 应用的必备技能。在实际开发中，应该遵循“**技能驱动**”的范式：先将业务能力拆解为独立的 Skill，再通过编排组合这些 Skill 来完成复杂任务，而不是写死流程或堆砌提示词。
