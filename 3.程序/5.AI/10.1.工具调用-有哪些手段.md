# 大模型工具调用全技术手段全景图

大模型工具调用是连接大模型与外部世界的桥梁，经过两年多的快速发展，已经形成了从**基础提示词驱动**到**标准化协议**、从**单工具调用**到**多智能体协作**的完整技术体系。不同的工具调用手段适用于不同的场景、模型和需求，选择合适的手段是构建生产级AI应用的关键。

## 一、工具调用技术演进路线

工具调用技术经历了四个清晰的发展阶段，每个阶段都解决了前一阶段的核心痛点：

1. **提示词工程阶段（2023年初）**：通过精心设计的提示词让大模型输出工具调用格式，适用于所有大模型
2. **原生支持阶段（2023年中）**：OpenAI推出Function Calling，大模型原生支持结构化工具调用输出
3. **标准化阶段（2024年底）**：Anthropic推出MCP协议，统一了跨平台工具调用标准
4. **智能编排阶段（2025年至今）**：多工具自动规划、反思纠错、多智能体协作成为主流

## 二、第一类：提示词驱动的工具调用（通用基础手段）

这是最基础、最通用的工具调用手段，**不需要大模型有任何原生工具调用能力**，任何开源或闭源大模型都能使用。它的核心原理是通过提示词约束大模型的输出格式，让它按照预定义的规则生成工具调用请求。

### 1. 零样本提示词调用

**原理**：在系统提示词中明确告诉大模型工具的定义、调用格式和使用规则，让它直接生成工具调用。

**示例**：

```
你是一个有用的助手，可以使用以下工具来回答用户的问题：

工具1：get_weather(city: str, days: int)
功能：获取指定城市未来几天的天气预报
参数：
- city: 城市名称，如"北京"
- days: 预报天数，默认为1

工具2：calculate(expression: str)
功能：解决数学计算问题
参数：
- expression: 数学表达式，如"2+2*3"

调用格式：
[{"name":"工具名称","parameters":{"参数名":"参数值"}}]

如果需要使用工具，请严格按照上述格式输出；如果不需要，直接回答用户的问题。
```

**优点**：

- 通用性极强，支持所有大模型
- 实现简单，不需要任何额外依赖
- 灵活度高，可以自定义任何格式

**缺点**：

- 输出格式不稳定，容易出现语法错误
- 工具选择和参数生成准确率较低
- 不支持复杂的多工具调用

**适用场景**：快速原型、简单工具、开源小模型

### 2. 少样本提示词调用

**原理**：在零样本的基础上，添加几个工具调用的示例，让大模型学习正确的调用方式。

**示例**：

```
示例1：
用户：明天北京的天气怎么样？
助手：[{"name":"get_weather","parameters":{"city":"北京","days":2}}]

示例2：
用户：2+2等于多少？
助手：[{"name":"calculate","parameters":{"expression":"2+2"}}]
```

**优点**：

- 显著提高工具调用的准确率和格式稳定性
- 仍然保持了良好的通用性

**缺点**：

- 会增加提示词长度和Token消耗
- 对于复杂工具仍然容易出错

### 3. XML标签调用

**原理**：使用XML标签来包裹工具调用，这种格式比JSON更容易被大模型正确生成，是目前开源模型最常用的提示词驱动方式。

**示例**：

```xml

<function=get_weather>
<parameter=city>北京</parameter>
<parameter=days>1</parameter>
</function>

```

**代表模型**：Llama 3、Qwen2、Mistral等绝大多数开源模型都原生支持这种格式。

### 4. 思维链工具调用（CoT-Tool）

**原理**：让大模型先思考为什么要调用这个工具，再生成工具调用请求。这能显著提高工具选择的合理性和参数的准确性。

**示例**：

```
用户：明天北京的天气怎么样？我需要穿什么衣服？
助手：
思考：用户想知道北京明天的天气，然后根据天气推荐衣服。我需要先调用get_weather工具获取北京明天的天气信息。
[{"name":"get_weather","parameters":{"city":"北京","days":2}}]
```

## 三、第二类：模型原生工具调用（主流生产手段）

这是目前工业界最主流的工具调用手段，大模型在预训练和微调阶段就专门学习了工具调用的能力，能够稳定地输出结构化的工具调用请求。

### 1. OpenAI Function Calling

**原理**：OpenAI在2023年6月推出的原生工具调用功能，是行业事实标准。开发者向大模型提供JSON Schema格式的工具定义，大模型会输出结构化的工具调用对象。

**代码示例**：

```python
from openai import OpenAI

client = OpenAI()

tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "获取指定城市的天气预报",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名称"},
                    "days": {"type": "integer", "description": "预报天数", "default": 1}
                },
                "required": ["city"]
            }
        }
    }
]

response = client.chat.completions.create(
    model="gpt-3.5-turbo",
    messages=[{"role": "user", "content": "明天北京的天气怎么样？"}],
    tools=tools,
    tool_choice="auto"
)

tool_call = response.choices[0].message.tool_calls[0]
print(tool_call.function.name)  # get_weather
print(tool_call.function.arguments)  # {"city":"北京","days":2}
```

**优点**：

- 输出格式极其稳定，几乎不会出现语法错误
- 工具选择和参数生成准确率高
- 支持并行调用多个工具
- 生态完善，所有框架都原生支持

**缺点**：

- 只能在OpenAI系列模型上使用
- 工具定义格式是OpenAI私有标准

### 2. Anthropic Tool Use

**原理**：Anthropic推出的原生工具调用功能，与OpenAI类似但有自己的格式和特点。它特别擅长处理长上下文和复杂的多工具调用。

**特点**：

- 支持在工具调用中包含思考过程
- 对长工具列表的处理能力更强
- 支持更复杂的参数类型

### 3. 结构化输出增强

**原理**：使用Pydantic等数据验证库来定义工具参数，然后让大模型输出符合Pydantic模型的JSON。这能彻底解决参数错误的问题。

**代码示例**：

```python
from pydantic import BaseModel, Field
from openai import OpenAI

class GetWeatherInput(BaseModel):
    city: str = Field(description="城市名称")
    days: int = Field(1, description="预报天数", ge=1, le=7)

client = OpenAI()

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "明天北京的天气怎么样？"}],
    response_format={"type": "json_object", "schema": GetWeatherInput.model_json_schema()}
)

params = GetWeatherInput.model_validate_json(response.choices[0].message.content)
print(params.city)  # 北京
print(params.days)  # 2
```

## 四、第三类：标准化协议与框架（跨平台通用手段）

这是解决工具调用碎片化问题的未来方向，通过标准化协议和抽象框架，实现"一次开发，到处运行"。

### 1. MCP（模型上下文协议）

**原理**：Anthropic于2024年11月推出的开放标准协议，是目前最先进的工具调用标准。它定义了大模型应用与外部工具之间的统一通信方式，支持工具调用、资源读取和提示词模板三大核心能力。

**核心优势**：

- 跨平台：支持所有主流大模型和AI应用（Claude、ChatGPT、Cursor、VS Code等）
- 去中心化：任何人都可以运行自己的MCP服务器
- 安全可控：细粒度权限控制和用户确认机制
- 能力全面：超越简单的函数调用，支持资源自动注入

**简单MCP服务器示例**：

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("天气服务器")

@mcp.tool()
def get_weather(city: str, days: int = 1) -> str:
    """获取指定城市的天气预报"""
    return f"{city}未来{days}天晴天，气温20-25度"

if __name__ == "__main__":
    mcp.run()
```

### 2. LangChain/LlamaIndex工具抽象

**原理**：主流RAG和Agent框架提供的工具调用抽象层，将不同模型的原生工具调用格式统一起来，开发者只需要定义一次工具，就可以在任何模型上使用。

**LangChain工具示例**：

```python
from langchain.tools import tool
from langchain_openai import ChatOpenAI
from langchain.agents import AgentExecutor, create_openai_tools_agent

@tool
def get_weather(city: str, days: int = 1) -> str:
    """获取指定城市的天气预报"""
    return f"{city}未来{days}天晴天，气温20-25度"

tools = [get_weather]
llm = ChatOpenAI(model="gpt-3.5-turbo")
agent = create_openai_tools_agent(llm, tools, prompt)
agent_executor = AgentExecutor(agent=agent, tools=tools)

agent_executor.invoke({"input": "明天北京的天气怎么样？"})
```

### 3. OpenAI Swarm

**原理**：OpenAI推出的轻量级多智能体和工具编排框架，专门用于构建复杂的工具调用和多智能体系统。它提供了简单的API来定义工具、智能体和它们之间的交互。

## 五、第四类：高级工具调用增强技术（生产优化手段）

以上基础手段解决了"能不能调用"的问题，而这些高级技术解决了"调用得好不好、快不快、准不准"的问题，是生产级应用必须掌握的。

### 1. 工具检索（Tool Retrieval）

**解决的问题**：当工具数量超过大模型的上下文窗口限制（通常>50个工具）时，大模型无法记住所有工具的功能，导致工具选择错误。

**原理**：

1. 为每个工具生成描述向量
2. 构建工具向量索引
3. 查询时先检索与用户意图最相关的Top-K个工具
4. 只将这些工具提供给大模型

**代码示例**：

```python
from sentence_transformers import SentenceTransformer
import faiss

model = SentenceTransformer('all-MiniLM-L6-v2')

# 工具列表
tools = [
    {"name": "get_weather", "description": "获取城市天气预报"},
    {"name": "get_news", "description": "获取最新新闻"},
    {"name": "calculate", "description": "数学计算"},
    # ... 100个其他工具
]

# 构建工具索引
tool_embeddings = model.encode([f"{t['name']}: {t['description']}" for t in tools])
index = faiss.IndexFlatL2(tool_embeddings.shape[1])
index.add(tool_embeddings)

def retrieve_tools(query: str, top_k: int = 5):
    """检索与查询最相关的工具"""
    query_embedding = model.encode([query])
    _, indices = index.search(query_embedding, top_k)
    return [tools[i] for i in indices[0]]
```

### 2. 并行工具调用

**解决的问题**：当任务需要调用多个独立工具时，串行调用会导致响应时间过长。

**原理**：让大模型一次生成多个工具调用请求，然后并行执行这些调用，最后将结果合并。

**代码示例**：

```python
import asyncio

async def call_tool(tool_name, params):
    # 工具调用逻辑
    pass

async def parallel_tool_calls(calls):
    tasks = [call_tool(call.name, call.parameters) for call in calls]
    return await asyncio.gather(*tasks)
```

### 3. 工具链规划

**解决的问题**：复杂任务需要多个工具按顺序调用，后面的工具依赖前面工具的结果。

**原理**：让大模型先生成一个详细的工具调用计划，明确每个步骤需要调用什么工具、需要什么参数、以及参数如何从前面的结果中获取。

**示例计划**：

```
任务：帮我查一下北京明天的天气，然后根据天气推荐合适的衣服。
计划：
1. 调用get_weather(city="北京", days=2)获取天气信息
2. 根据天气信息调用recommend_clothes(weather=结果1)推荐衣服
```

### 4. 反思与纠错

**解决的问题**：工具调用经常出现参数错误、工具选择错误或执行失败的情况。

**原理**：在工具调用执行后，让大模型对结果进行反思和评估，如果发现错误，分析原因并重新调用工具。

**工作流程**：

1. 生成工具调用并执行
2. 评估结果是否正确和完整
3. 如果有错误，分析错误原因
4. 修正参数或重新选择工具
5. 再次调用工具

### 5. 检索增强工具调用（RAA）

**原理**：结合RAG技术，先检索相关的工具使用文档、最佳实践和历史案例，再让大模型生成工具调用。这能显著提高复杂工具的调用准确率。

## 六、第五类：特殊场景的工具调用

### 1. 代码解释器（Code Interpreter）

**原理**：最强大的通用工具，让大模型编写和执行Python代码来解决任何计算、数据处理和文件操作问题。

**核心能力**：

- 数学计算和统计分析
- 数据清洗和可视化
- 文件格式转换和处理
- 代码调试和生成

### 2. 浏览器自动化

**原理**：让大模型控制浏览器，模拟人类操作网页，如搜索信息、填写表单、点击按钮等。

**代表工具**：Playwright、Selenium、Browser Use

### 3. 数据库工具调用

**原理**：让大模型自然语言查询数据库，自动生成SQL语句并执行。

**工作流程**：

1. 用户输入自然语言查询
2. 大模型根据数据库Schema生成SQL
3. 执行SQL并返回结果
4. 大模型将结果转换为自然语言回答

### 4. 多模态工具调用

**原理**：让大模型调用处理图片、音频、视频等多模态数据的工具，如OCR、图像生成、语音识别等。

## 七、工具调用手段对比与选型指南

| 手段 | 准确率 | 通用性 | 实现难度 | 适用工具数量 | 适用场景 |
|------|--------|--------|----------|--------------|----------|
| 提示词驱动 | 低 | 极高 | 低 | <10 | 快速原型、开源小模型 |
| 原生Function Calling | 高 | 低 | 中 | <50 | 生产级应用、主流模型 |
| MCP协议 | 高 | 极高 | 中 | 任意 | 跨平台应用、生态建设 |
| 工具检索+原生调用 | 极高 | 中 | 高 | >50 | 大型应用、工具数量多 |

**选型最佳实践**：

1. **优先使用MCP协议**：如果你的应用需要支持多个客户端或模型
2. **其次使用原生Function Calling**：如果只需要支持OpenAI或Anthropic模型
3. **最后使用提示词驱动**：如果使用的是没有原生工具调用能力的开源模型
4. **工具数量>50个时必须加工具检索**
5. **复杂任务必须加工具链规划和反思纠错**

## 八、常见问题与解决方案

| 问题 | 表现 | 解决方案 |
|------|------|----------|
| 参数幻觉 | 生成不存在的参数或错误的参数值 | 使用Pydantic结构化输出、严格参数校验 |
| 工具选择错误 | 选择了不相关的工具 | 优化工具描述、添加少样本示例、使用工具检索 |
| 无限循环 | 反复调用同一个工具 | 设置最大迭代次数、检测重复调用 |
| 上下文溢出 | 工具调用历史过长导致上下文窗口满 | 实现上下文管理、截断或摘要历史 |
| 响应时间长 | 多工具串行调用导致延迟高 | 使用并行工具调用、缓存常用结果 |

## 九、总结

工具调用技术已经从早期的"技巧"发展为成熟的"工程体系"。对于开发者来说，不需要掌握所有的手段，而是要根据自己的场景、模型和需求选择最合适的组合。

目前来看，**MCP协议+工具检索+反思纠错**是最具前瞻性和通用性的技术栈，它解决了跨平台、大规模工具管理和调用质量的问题，代表了工具调用技术的未来发展方向。
