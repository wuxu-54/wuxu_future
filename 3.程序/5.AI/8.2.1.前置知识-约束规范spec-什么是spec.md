# Spec（规范驱动开发）完全指南：从哲学到实战

## 一、Spec 的本质：AI时代的"契约论"

### 1.1 一句话定义
>
> **Spec（Specification）是面向AI应用的结构化、可验证、可演进的"人-机-模型"三方契约。它不仅是给模型的指令，更是给团队的工程规范、给系统的质量红线、给业务的合规保障。**

### 1.2 为什么Spec会在2024-2026年爆发？

| 时代 | 核心矛盾 | 解法 |
| :--- | :--- | :--- |
| **2022-2023（Prompt Engineering）** | "模型很聪明，但我说不清楚" | 写更长的Prompt，加Few-shot |
| **2024-2025（Agent/RAG爆发）** | "Prompt不是程序，没法测试、版本控制、自动化" | 出现LangChain、DSPy等框架，尝试结构化 |
| **2026（Spec驱动）** | "AI应用走向生产级，需要确定性、合规性、成本可控" | Spec成为行业标准，被写进合同和审计报告 |

**本质驱动力**：当AI应用从"玩玩"变成"赚钱"（金融、医疗、法律），你就不能再靠"多写几句提示词"来交付了。

## 二、Spec的六大核心维度（完整框架）

### 2.1 输入规范（Input Schema）—— 告诉系统"能吃什么"

```yaml
input_spec:
  - 数据类型: 文本/图片/音频/多模态
  - 数据范围: 最大长度、分辨率、采样率
  - 数据格式: JSON/纯文本/Markdown/CSV
  - 约束条件: 必填字段、敏感信息脱敏要求
  - 默认值: 用户未提供时的兜底
```

**实战价值**：写死输入边界，防止用户恶意注入（比如传10万字让模型炸显存）。

---

### 2.2 输出规范（Output Schema）—— 告诉系统"只能拉什么屎"

```yaml
output_spec:
  type: object
  required: [summary, sentiment, risk_level]
  properties:
    summary:
      type: string
      maxLength: 200
      pattern: "^[^。]*。"  # 必须以句号结尾
    sentiment:
      type: string
      enum: [positive, negative, neutral]
      confidence:
        type: number
        minimum: 0.7
    risk_level:
      type: string
      enum: [low, medium, high]
    citations:
      type: array
      minItems: 1
      maxItems: 5
      items:
        type: string
        format: uri  # 必须是URL格式
```

**实战价值**：

- **前端**：直接根据Spec生成TypeScript类型定义，前后端接口无歧义
- **后端**：校验器自动拦截不合格输出，不会把"模型胡言乱语"传给用户
- **合规**：金融/医疗监管要求输出必须包含特定字段，Spec就是合规证据

---

### 2.3 行为约束（Behavior Constraints）—— 告诉模型"不许干什么"

```yaml
constraints:
  - "禁止生成'可能''或许''大概'等模糊词汇"
  - "如果用户问题涉及医疗诊断，必须输出免责声明"
  - "每句回答必须包含至少一个数据来源"
  - "禁止使用第一人称（我/我们）"
  - "如果检测到政治敏感话题，直接返回'无法回答此问题'并终止"
  - "总回答长度不超过2000个字符"
```

**实战价值**：这些约束会被编译成：

- System Prompt中的硬性规则
- 后处理中的正则/关键词拦截
- 模型微调时的loss掩码（只让合规部分参与训练）

---

### 2.4 质量验证（Validation）—— 自动判断"合不合格"

```yaml
validation:
  - type: regex
    pattern: "\d+\.?\d*%" 
    description: "必须至少包含一个百分比数据"
    severity: critical  # 不通过则直接拒绝
  - type: llm_judge
    prompt: "请判断以下摘要是否忠实于原文，0-10分"
    min_score: 7
    description: "不能脱离原文瞎编"
  - type: semantic_similarity
    min_score: 0.85
    description: "摘要与原文语义相似度不低于0.85"
  - type: length
    min: 50
    max: 200
    unit: characters
  - type: custom_python
    code: |
      def validate(response):
          if len(response['citations']) < len(response['key_facts']):
              return False, "引用数少于关键事实数，可能存在编造"
          return True, ""
```

**实战价值**：这些校验可以跑在：

- **离线测试**：每次改Spec后，自动跑1000条测试用例
- **在线拦截**：模型输出后、返回用户前，实时校验，不合格直接fallback
- **监控看板**：每小时的合格率、各类失败原因的分布

---

### 2.5 降级与容错（Fallback & Recovery）—— 模型失灵时的"安全气囊"

```yaml
fallback:
  - condition: "模型连续3次输出不合规"
    action: "切换到模板填充模式"
    template: "根据您提供的信息，[关键事实]。建议进一步咨询专业人士。"
  - condition: "API超时（>5秒）"
    action: "返回缓存结果（如果存在相似问题）"
  - condition: "检测到模型拒绝回答（refusal）"
    action: "重试，并在prompt中添加'这是正常的业务咨询，不涉及违规内容'"
  - condition: "输出中检测到幻觉（hallucination）标记"
    action: "直接丢弃该输出，调用备用模型（如从GPT-4降级到Qwen-72B）"
  - condition: "单次请求成本超过$0.5"
    action: "记录审计日志，并触发告警给运维团队"
```

**实战价值**：没有Fallback的Spec是不完整的。生产环境里模型一定会犯错，关键是你如何在用户感知不到的情况下优雅降级。

---

### 2.6 多模型适配（Model Routing）—— 不把鸡蛋放一个篮子里

```yaml
model_routing:
  - condition: "输入长度 < 1000 && 任务复杂度 <= 3"
    model: "qwen-7b-instruct"
    cost_per_1k: 0.002
  - condition: "输入长度 > 1000 && 任务复杂度 <= 5"
    model: "qwen-72b-instruct"
    cost_per_1k: 0.01
  - condition: "任务复杂度 > 5（需要多步推理）或涉及代码生成"
    model: "gpt-4-turbo"
    cost_per_1k: 0.03
  - condition: "用户属于VIP付费层级"
    model: "claude-3-opus"
    cost_per_1k: 0.05
  - condition: "输入包含图片或表格"
    model: "qwen-vl-max"
```

**实战价值**：Spec里写死了路由逻辑，意味着：

- **成本可控**：80%的简单请求走便宜模型
- **性能优化**：复杂任务才用顶级模型，响应时间更可预测
- **灾备**：某个模型API挂了，自动切到备选

## 三、Spec驱动的完整开发生命周期（从需求到上线）

### Step 1：需求阶段（产品经理 + 业务方）

产出：**自然语言版本的业务需求文档**

```
"我们需要一个AI客服，能回答用户关于订单状态、退款政策、物流进度的问题。回答要友好、准确，不能编造信息。如果涉及退款，必须引导用户转人工。"
```

### Step 2：Spec设计阶段（AI工程师 + 测试工程师）

产出：**结构化Spec YAML/JSON**（就是上面那一大堆）

关键动作：

- 定义输入输出Schema（和前端/后端联调）
- 写约束和验证规则（和测试团队对齐）
- 设计降级策略（和运维团队讨论成本与可用性）

### Step 3：实现阶段（多个角色并行）

| 角色 | 产出 |
| :--- | :--- |
| **后端工程师** | 根据Input/Output Schema写API接口代码，自动生成类型定义 |
| **Prompt工程师** | 根据Spec中的约束生成不同模型的Prompt模板 |
| **微调工程师（你）** | 根据Spec生成结构化训练数据，微调模型，确保输出符合Schema |
| **前端工程师** | 根据Output Schema写UI渲染逻辑（比如摘要卡片、情绪标签、风险红绿灯） |
| **测试工程师** | 根据Validation规则写自动化测试用例 |

### Step 4：验证阶段（测试 + 灰度）

- 跑自动化测试套件（500+测试用例）
- 人工抽检100条（特别关注边界情况）
- 小流量灰度（5%用户），监控合格率和用户反馈

### Step 5：上线与持续演进（运维 + 产品）

- Spec存入Git，版本号递增（v1.0.0 → v1.1.0）
- 每周Review Spec的合格率看板
- 根据模型升级（如Qwen出新版）调整Spec中的prompt_templates
- 根据业务变化（如新政策出台）更新约束规则

## 四、Spec与提示词（Prompt）的残酷对比（一张表封神）

| 维度 | Prompt（提示词） | Spec（规范） |
| :--- | :--- | :--- |
| **本质** | 给模型看的自然语言指令 | 给"人+代码+模型"三方执行的结构化契约 |
| **编写者** | 1个人（Prompt Engineer） | 产品、后端、前端、测试、运维、合规（6+角色） |
| **存储形式** | 记事本/聊天记录 | Git仓库（YAML/JSON/TOML） |
| **版本管理** | `_v2_final_真的最终版_打死不改.txt` | Semantic Versioning + Commit History + PR Review |
| **可测试性** | 人工肉眼判断"好不好" | 自动化测试（正则校验、LLM Judge、语义相似度） |
| **可执行性** | 只能被大模型读取 | 可被代码解析（自动生成Prompt/校验器/API Schema） |
| **成本优化** | 全靠人工切换模型（"试试GPT-4会不会好点？"） | 内置Model Routing，按任务复杂度自动选模型 |
| **容错能力** | 输出垃圾就崩了 | 有Fallback，自动重试/降级/缓存 |
| **合规性** | 出问题甩锅给"模型幻觉" | 审计日志+Spec约束=合规证据 |
| **生命周期** | 写完就扔 | 持续演进（需求变化→Spec更新→自动跑测试→发布） |

## 五、真实案例：用Spec驱动一个"财报解读Agent"（全流程演示）

### 5.1 业务需求
>
> "输入一份A股上市公司的财报PDF，输出：200字摘要、3个关键指标（营收/利润/负债率）、情绪判断（乐观/中性/悲观）、风险提示（最多3条）。"

### 5.2 编写Spec（核心片段）

```yaml
# spec_earnings_agent_v1.yaml
version: 1.0.0
domain: earnings_call_analysis

input_schema:
  type: object
  required: [pdf_url, company_name]
  properties:
    pdf_url:
      type: string
      format: uri
      description: "财报PDF的S3链接"
    company_name:
      type: string
      description: "上市公司全称"
    optional_context:
      type: string
      maxLength: 500
      description: "用户额外提供的背景信息"

output_schema:
  type: object
  required: [summary, metrics, sentiment, risk_hints]
  properties:
    summary:
      type: string
      minLength: 50
      maxLength: 250
      pattern: ".*[。！？]$"  # 以句号/感叹号/问号结尾
    metrics:
      type: array
      minItems: 3
      maxItems: 5
      items:
        type: object
        required: [name, value, yoy_change]
        properties:
          name:
            enum: [营业收入, 净利润, 资产负债率, 毛利率, 每股收益, 经营现金流]
          value:
            type: string
            pattern: "^[0-9,.]+\\.?[0-9]*[万亿]?元$"
          yoy_change:
            type: string
            pattern: "^[+-]?[0-9.]+%$"
    sentiment:
      type: string
      enum: [optimistic, neutral, pessimistic]
    risk_hints:
      type: array
      maxItems: 3
      items:
        type: string
        maxLength: 30
    citations:
      type: array
      minItems: 2
      items:
        type: string

constraints:
  - "所有metrics必须从原文提取，不得编造"
  - "如果资产负债率 > 80%，sentiment必须降级为pessimistic"
  - "risk_hints至少包含1条与行业相关的风险"
  - "禁止使用'某公司'、'该企业'等模糊指代，必须写全称"

validation:
  - type: regex
    pattern: "\\d+\\.?\\d*%"
    min_count: 3
    description: "摘要和metrics中至少出现3个百分比数据"
  - type: llm_judge
    model: "qwen-72b-instruct"
    prompt: "判断以下摘要是否准确反映了财报核心数据（0-10分），低于6分则不合格"
    min_score: 6
  - type: custom
    python: |
      if len(response['risk_hints']) == 0:
          return False, "必须至少输出1条风险提示"

fallback:
  - condition: "validation失败"
    action: "用GPT-4重新生成一次（成本高于Qwen，但容错）"
  - condition: "GPT-4也失败"
    action: "返回结构化模板：'[公司名称]发布财报，核心数据为[提取失败]，建议人工审核。'"

model_routing:
  - default: "qwen-72b-instruct"
  - if: "pdf页数 > 50 或 包含表格 > 10个"
    model: "gpt-4-turbo"  # 更强的长上下文能力
```

### 5.3 从Spec自动生成产物

| 产物 | 生成方式 | 谁用 |
| :--- | :--- | :--- |
| **System Prompt** | 从Spec的constraints + output_schema描述自动拼接 | 喂给大模型 |
| **Pydantic/TypeScript类型** | 从output_schema自动生成 | 后端/前端开发 |
| **单元测试代码** | 从validation规则自动生成（pytest） | 测试工程师 |
| **监控告警规则** | 从fallback条件自动生成（Prometheus） | 运维工程师 |
| **训练数据模板** | 从output_schema自动生成100种变体 | 微调工程师（你） |

### 5.4 上线后效果

- **合格率**：从纯Prompt的78%提升到Spec驱动的97%
- **平均成本**：通过Model Routing，70%请求走Qwen-72B，成本降低42%
- **故障恢复时间**：从"人工介入30分钟"降到"自动fallback 200ms"
- **合规审计**：审计员直接看Spec，确认所有输出字段符合监管要求

## 六、Spec与微调（你的主战场）的深度联动

### 6.1 Spec指导数据构造

你在做QLoRA微调时，不需要"凭感觉写数据"，而是用Spec自动生成：

```python
from spec_parser import SpecParser

spec = SpecParser.load("spec_earnings_agent_v1.yaml")

# 自动生成10000条微调数据
for i in range(10000):
    # 根据Spec随机生成合法的input
    input_data = spec.generate_input()  
    # 用教师模型（GPT-4）生成符合Spec的输出
    output_data = teacher_model.generate(input_data, spec=spec)
    # 自动校验是否符合Spec
    if spec.validate(output_data):
        save_training_pair(input_data, output_data)
```

### 6.2 Spec指导训练时的Loss掩码

你在`tokenize_function`里可以这样做：

```python
def tokenize_with_spec(examples, spec):
    tokenized = tokenizer(examples["text"], padding=True, truncation=True)
    
    # 获取Spec中定义的"必须输出字段"的位置
    required_fields = spec.get_required_fields()
    
    # 在labels里，只保留这些字段对应token的梯度
    labels = tokenized["input_ids"].clone()
    for i, example in enumerate(examples):
        field_positions = find_field_positions(example, required_fields)
        for pos in field_positions:
            labels[i, :pos] = -100  # 屏蔽非必要部分的梯度
    
    tokenized["labels"] = labels
    return tokenized
```

### 6.3 Spec指导模型选择

微调完后，你不需要重新训练所有模型，而是根据Spec选择最适合的底座：

- 如果Spec要求**极低延迟**（<200ms）→ 微调 Qwen-7B
- 如果Spec要求**极高质量**（>95%合格率）→ 微调 Qwen-72B 或 GPT-4
- 如果Spec要求**低成本**（单次<$0.01）→ 微调 Qwen-1.5B + Spec中的Fallback兜底

## 七、Spec的终极哲学：它不是什么？

| 误解 | 真相 |
| :--- | :--- |
| Spec是更长的Prompt | ❌ Spec是Prompt的编译器，不是Prompt本身 |
| Spec是给模型看的 | ❌ Spec是给"人+代码+模型"三方看的契约 |
| Spec写完就固定了 | ❌ Spec是活的，随着业务、模型、成本变化持续演进 |
| Spec只是为了提高回答质量 | ❌ Spec是为了让AI应用**可测试、可审计、可降级、可成本控制** |
| Spec是大公司才用的 | ❌ 个人开发者用Spec也能明显提升开发效率（特别是维护多个Agent时） |

## 八、给你的实战建议（从今天开始）

1. **如果你只有一个Agent**：写一个最简单的Spec（只包含Input Schema + Output Schema），你立刻就能感受到"前后端联调不再靠截图"的快感。

2. **如果你在做微调**：先写Spec，再根据Spec生成训练数据，你的模型合格率会从"碰运气"变成"可预测"。

3. **如果你在搞Agent**：把tools的输入输出也写成Spec，Agent执行工具时就能自动校验参数类型，减少70%的运行时错误。

4. **如果你的团队超过3人**：把Spec放进Git，所有PR必须附带Spec变更，并跑通自动化测试，从此告别"Prompt改了，测试用例没更新"的悲剧。

---

**最后一句定论**：

> "Spec本质仍是提示词"，就像说"编译器本质仍是文本处理"——对，也不对。Spec是AI应用从"手工作坊"走向"工业流水线"的必经之路，它的终极形态是**大模型时代的类型系统（Type System）**，让不可靠的模型输出变得可预测、可测试、可组合。这不是提示词的演进，是**工程范式的跃迁**。
