## 🎨 代码风格与规范

### 通用原则

- 代码必须具有可读性和可维护性
- 所有函数和类必须有清晰的文档字符串
- 避免重复代码，遵循 DRY 原则
- 保持函数短小精悍，单一职责

### Python 规范

- 使用 Ruff 作为代码检查和格式化工具（默认配置）
- 最大行长度: 88
- 所有函数必须添加类型提示
- 文档字符串使用 Google 风格
- 导入顺序: 标准库 > 第三方库 > 本地库

### TypeScript/JavaScript 规范

- 使用 ESLint + Prettier 进行代码检查和格式化
- 优先使用 TypeScript
- 使用箭头函数代替普通函数
- 避免使用 `any` 类型

### 命名规范

- 变量和函数: snake_case（Python）/ camelCase（TypeScript）
- 类名: PascalCase
- 常量: UPPER_SNAKE_CASE
- 文件名: snake_case

## 📝 提交与 PR 规范

### Commit 信息格式

```txt
<type>(<scope>): <subject>

<body>

<footer>
```

**Type 类型**:

- `feat`: 新功能
- `fix`: 修复 bug
- `docs`: 文档更新
- `style`: 代码风格调整
- `refactor`: 代码重构
- `test`: 测试相关
- `chore`: 构建工具或辅助工具的变动

### PR 流程

1. 从 `main` 分支创建新分支
2. 完成开发并提交代码
3. 确保所有测试通过
4. 创建 PR，填写 PR 模板
5. 至少获得一位代码审查者的批准
6. 合并到 `main` 分支

## ⚠️ 重要规则与安全注意事项

- **绝对禁止**提交任何密钥、API 密钥、密码或其他敏感信息到代码仓库
- 所有环境变量必须通过 `.env` 文件或环境变量管理工具配置
- 所有用户输入必须进行验证和清理，防止 SQL 注入和 XSS 攻击
- 数据库操作必须使用参数化查询
- 敏感操作必须添加日志记录
- 发布前必须更新 `CHANGELOG.md` 文件

## 二、标准 SKILL.md 模板（以智能代码审查为例）

```markdown
---
name: code-review-skill
version: 1.0.0
author: [你的名字/团队]
description: 智能审查代码变更，检查 bug、安全漏洞、性能问题、代码风格和最佳实践，返回结构化的问题列表和可直接应用的修复建议。
inputs:
  - name: code_diff
    type: string
    required: true
    description: Git diff 格式的代码变更内容
  - name: language
    type: string
    required: true
    enum: [python, javascript, typescript, java, go, rust]
    description: 代码的编程语言
  - name: review_level
    type: string
    required: false
    default: standard
    enum: [quick, standard, deep]
    description: 审查深度，quick 只检查严重问题，standard 全面检查，deep 深入检查架构和设计
outputs:
  - name: review_result
    type: json
    description: 结构化的代码审查结果
tags:
  - code-review
  - quality
  - security
---

# 执行流程
1. 接收输入的 code_diff、language 和 review_level 参数
2. 解析 Git diff 内容，提取变更的文件和代码行
3. 根据 review_level 执行相应深度的审查
4. 按照严重程度分类问题
5. 为每个问题提供详细的描述和修复建议
6. 生成指定格式的 JSON 结果

# 审查维度
## 1. 正确性与 Bug
- 逻辑错误
- 边界条件处理不当
- 空指针异常
- 类型错误
- 资源泄漏

## 2. 安全问题
- SQL 注入
- XSS 攻击
- CSRF 攻击
- 敏感信息泄露
- 权限控制不当

## 3. 性能问题
- 低效的算法
- 不必要的数据库查询
- 内存泄漏
- 循环中的耗时操作

## 4. 代码风格与规范
- 不符合项目代码风格
- 命名不规范
- 缺少文档字符串
- 代码冗余
- 过长的函数或类

## 5. 最佳实践
- 错误处理不当
- 测试覆盖不足
- 硬编码值
- 重复代码
- 不合理的依赖

# 输出格式
```json
{
  "summary": {
    "total_issues": 3,
    "critical": 1,
    "high": 1,
    "medium": 0,
    "low": 1,
    "review_time": "2026-06-04T12:00:00Z"
  },
  "issues": [
    {
      "id": "CR-001",
      "severity": "critical",
      "file": "src/api/users.py",
      "line": 45,
      "category": "security",
      "title": "SQL 注入漏洞",
      "description": "使用字符串拼接构建 SQL 查询，存在 SQL 注入风险。",
      "current_code": "query = f\"SELECT * FROM users WHERE id = {user_id}\"",
      "suggested_fix": "query = \"SELECT * FROM users WHERE id = %s\"\nparams = (user_id,)",
      "explanation": "使用参数化查询可以有效防止 SQL 注入攻击。"
    }
  ],
  "overall_suggestions": [
    "建议添加更多的错误处理逻辑",
    "考虑将重复的代码提取为工具函数"
  ]
}
```

# 错误处理

- 如果 code_diff 为空，返回错误信息：`{"error": "代码变更内容不能为空"}`
- 如果不支持输入的编程语言，返回错误信息：`{"error": "不支持的编程语言：{language}"}`
- 如果 review_level 无效，使用默认值 "standard"
- 如果解析 code_diff 失败，返回错误信息：`{"error": "无法解析 Git diff 内容"}`

# 注意事项

- 只审查变更的代码，不要审查未变更的代码
- 优先关注严重和高优先级的问题
- 提供具体、可操作的修复建议，而不是泛泛而谈
- 保持客观和建设性的语气
- 如果没有发现问题，返回一个空的 issues 列表和积极的总结

## 使用说明

1. 将 `AGENTS.md` 复制到你的项目根目录
2. 替换所有 `[占位符]` 内容为你的项目实际信息
3. 根据你的项目特点，添加或删除相应的部分
4. 在 `.agents/skills/` 目录下为每个技能创建一个文件夹
5. 将 `SKILL.md` 模板复制到对应的技能文件夹中
6. 修改技能的元数据和内容，使其符合你的需求
7. 启动你的 Agent 工具，它会自动发现并加载这些配置
