# RAG检索阶段完整指南

检索阶段是RAG系统的"**大脑中枢**"，它连接着用户查询和知识库，直接决定了大模型能否获得准确、相关的上下文信息。这个阶段的核心目标是：**在海量知识库中，以毫秒级速度找到与用户查询语义最相关的Top-K个文档块**。

## 一、检索阶段完整流程总览

现代RAG检索系统已经从早期的"单向量检索"进化为"**多路召回+融合+精排**"的三级架构：

```
用户查询 → 查询预处理 → 查询向量化 → 多路召回 → 结果融合 → 重排序 → 上下文压缩 → 最终上下文
```

## 二、检索基础知识

### 1. 查询预处理（Query Preprocessing）

**核心目的**：优化用户原始查询，使其更适合检索系统，解决"用户表达不清晰"和"检索系统理解偏差"的问题。这是**成本最低但收益最高的优化手段**。

#### 细分流程与处理手段

| 预处理技术 | 核心原理 | 适用场景 | 效果提升 |
|-----------|---------|---------|---------|
| 查询重写 | 让LLM将模糊、口语化的查询转换为清晰、专业的检索式 | 口语化查询、歧义查询 | 显著提升召回率 |
| 查询扩展 | 为原始查询添加相关的同义词、近义词和相关术语 | 专业领域查询、术语不统一 | 提升覆盖度 |
| 查询分解 | 将复杂的多问题查询分解为多个简单的子查询 | 多跳问题、复杂推理问题 | 解决长上下文和多跳推理难题 |
| HyDE（假设文档嵌入） | 让LLM先生成一个假设的答案文档，再用这个文档进行检索 | 语义差距大的查询 | 大幅提升语义匹配准确性 |

#### 具体示例：查询重写与分解

```
from openai import OpenAI

client = OpenAI(api_key="your_api_key")

def rewrite_and_decompose_query(query):
    prompt = f"""
    请对以下用户查询进行优化，用于RAG系统检索：
    1. 将口语化表达转换为专业、清晰的检索式
    2. 如果查询包含多个问题，请分解为独立的子查询
    3. 每个子查询单独一行，不要编号
    
    用户查询：{query}
    """
    
    response = client.chat.completions.create(
        model="gpt-3.5-turbo",
        messages=[{"role": "user", "content": prompt}],
        temperature=0
    )
    
    optimized_queries = response.choices[0].message.content.strip().split('\n')
    return optimized_queries

# 测试
original_query = "我想知道大模型是怎么工作的，还有它和传统AI有什么不一样？"
optimized_queries = rewrite_and_decompose_query(original_query)
print("优化后的查询：")
for q in optimized_queries:
    print(f"- {q}")
```

**输出示例**：

```
优化后的查询：
- 大语言模型的工作原理
- 大语言模型与传统人工智能技术的区别
```

### 2. 查询向量化（Query Embedding）

**核心目的**：将预处理后的查询文本转换为与文档块相同向量空间的高维向量表示。

#### 关键注意事项

- **必须使用与文档向量化完全相同的嵌入模型**，否则向量空间不一致，相似度计算毫无意义
- 对于中文查询，优先使用专门针对中文优化的嵌入模型（如bge-large-zh-v1.5）
- 可以对多个优化后的查询分别向量化，然后进行多路检索

#### 具体示例

```python
from sentence_transformers import SentenceTransformer

# 加载与文档向量化相同的嵌入模型
model = SentenceTransformer('BAAI/bge-large-zh-v1.5')

# 原始查询和优化后的查询
original_query = "大模型怎么工作？"
optimized_queries = ["大语言模型的工作原理", "Transformer架构的核心机制"]

# 生成查询向量
original_query_vector = model.encode(original_query)
optimized_query_vectors = [model.encode(q) for q in optimized_queries]

print(f"原始查询向量维度：{original_query_vector.shape}")
print(f"优化后查询向量数量：{len(optimized_query_vectors)}")
```

### 3. 基础检索策略

基础检索策略是RAG系统的起点，主要包括两种核心方法：

#### (1) 稠密向量检索（Dense Retrieval）

- **核心原理**：计算查询向量与文档向量的语义相似度
- **优点**：理解语义、支持模糊匹配
- **缺点**：对专有名词和精确术语匹配差
- **适用场景**：通用语义查询

#### (2) 稀疏向量检索（Sparse Retrieval - BM25/TF-IDF）

- **核心原理**：基于关键词出现频率和重要性打分
- **优点**：精确匹配关键词、速度快
- **缺点**：无法理解语义、同义词问题
- **适用场景**：包含专有名词、型号的查询

## 三、高级检索知识

### 1. 多路召回机制（Multi-way Retrieval）

**核心目的**：使用多种不同的检索策略，从不同角度召回相关文档，最大化召回率。单一检索策略总会有盲区，多路召回是解决这个问题的最佳方案。

#### 主流召回策略对比

| 召回策略 | 核心原理 | 优点 | 缺点 | 适用场景 |
|---------|---------|------|------|---------|
| **稠密向量检索** | 计算查询向量与文档向量的语义相似度 | 理解语义、支持模糊匹配 | 对专有名词和精确术语匹配差 | 通用语义查询 |
| **稀疏向量检索（BM25/TF-IDF）** | 基于关键词出现频率和重要性打分 | 精确匹配关键词、速度快 | 无法理解语义、同义词问题 | 包含专有名词、型号的查询 |
| **元数据过滤检索** | 先根据元数据过滤文档，再进行语义检索 | 大幅缩小搜索空间、提高速度和精度 | 需要高质量的元数据 | 有明确分类、时间、作者等属性的文档 |
| **图检索** | 基于知识图谱的实体和关系进行检索 | 支持多跳推理、复杂关系查询 | 构建知识图谱成本高 | 知识密集型、需要推理的查询 |
| **多向量检索** | 为同一文档生成多个向量（标题、摘要、全文） | 全面捕捉文档语义、提高召回率 | 存储和计算成本增加 | 长文档、结构化文档 |
| **ANN近似检索** | 使用HNSW、IVF等算法加速大规模检索 | 亿级文档毫秒响应、内存效率高 | 精度略有损失 | 超大规模知识库 |

#### 具体示例：混合检索（向量+BM25）

这是目前工业界最常用的召回策略，结合了语义匹配和关键词匹配的优点。

```python
from langchain.retrievers import EnsembleRetriever
from langchain_community.retrievers import BM25Retriever
from langchain_community.vectorstores import Chroma
from langchain_community.embeddings import HuggingFaceEmbeddings

# 准备文档
documents = [
    "大语言模型基于Transformer架构，使用自注意力机制处理文本",
    "Transformer架构于2017年由Google在论文《Attention Is All You Need》中提出",
    "传统机器学习模型需要人工设计特征，而大语言模型可以自动学习特征"
]

# 初始化BM25检索器
bm25_retriever = BM25Retriever.from_texts(documents)
bm25_retriever.k = 3

# 初始化向量检索器
embeddings = HuggingFaceEmbeddings(model_name="BAAI/bge-large-zh-v1.5")
vectorstore = Chroma.from_texts(documents, embeddings)
vector_retriever = vectorstore.as_retriever(search_kwargs={"k": 3})

# 创建混合检索器
ensemble_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, vector_retriever],
    weights=[0.5, 0.5]  # 两个检索器的权重
)

# 执行混合检索
query = "Transformer架构是谁提出的？"
results = ensemble_retriever.get_relevant_documents(query)

print("混合检索结果：")
for result in results:
    print(f"- {result.page_content}")
```

### 2. 结果融合（Result Fusion）

**核心目的**：将多路召回得到的多个文档列表合并为一个统一的列表，同时去除重复文档。

#### 常用融合算法详解

##### (1) Reciprocal Rank Fusion (RRF) - 推荐使用

- **优势**：无需调整参数，效果稳定，对异常值鲁棒
- **公式**：`RRF_score(d) = Σ(1 / (k + rank_i(d)))`
- **参数**：`k`通常取60，`rank_i(d)`是文档d在第i个检索器中的排名

##### (2) 加权求和融合

- **优势**：可以根据业务场景调整权重
- **公式**：`Final_score = w1 * score1 + w2 * score2`
- **权重调优建议**：
  - 通用场景：向量:BM25 = 0.6:0.4
  - 精确查询（产品型号、错误码）：向量:BM25 = 0.3:0.7
  - 语义查询（概念解释、工作原理）：向量:BM25 = 0.8:0.2

##### (3) RRF算法原理

```
RRF_score(d) = Σ(1 / (k + rank_i(d)))
```

其中：

- `rank_i(d)`是文档d在第i个检索器结果中的排名
- `k`是常数，通常取60

### 3. 重排序（Reranking）

**核心目的**：对融合后的文档列表进行更精细的相关性打分和排序，这是**提升检索精度最有效的手段**。重排序模型会将查询和每个文档进行联合编码，计算它们的相关性，比召回阶段的粗排要精准得多。

#### 主流重排序模型对比

| 模型类型 | 代表模型 | 特点 | 适用场景 |
|---------|---------|------|---------|
| 交叉编码器 | BAAI/bge-reranker-large | 中文效果最好、精度最高 | 中文为主的应用 |
| 交叉编码器 | cross-encoder/ms-marco-MiniLM-L-12-v2 | 速度快、效果好 | 英文为主的应用 |
| LLM重排序 | GPT-3.5-turbo、Qwen-7B | 理解能力最强、但成本高 | 对精度要求极高的小批量场景 |

#### 具体示例：使用bge-reranker进行重排序

```
from sentence_transformers import CrossEncoder

# 加载重排序模型
reranker = CrossEncoder('BAAI/bge-reranker-base')

# 查询和初步检索结果
query = "Transformer架构是谁提出的？"
initial_results = [
    "大语言模型基于Transformer架构，使用自注意力机制处理文本",
    "Transformer架构于2017年由Google在论文《Attention Is All You Need》中提出",
    "传统机器学习模型需要人工设计特征，而大语言模型可以自动学习特征"
]

# 生成查询-文档对
pairs = [[query, doc] for doc in initial_results]

# 计算相关性得分
scores = reranker.predict(pairs)

# 按得分排序
reranked_results = sorted(zip(scores, initial_results), key=lambda x: x[0], reverse=True)

print("重排序结果：")
for score, doc in reranked_results:
    print(f"得分：{score:.4f}，内容：{doc}")
```

**输出示例**：

```
重排序结果：
得分：0.9876，内容：Transformer架构于2017年由Google在论文《Attention Is All You Need》中提出
得分：0.6543，内容：大语言模型基于Transformer架构，使用自注意力机制处理文本
得分：0.1234，内容：传统机器学习模型需要人工设计特征，而大语言模型可以自动学习特征
```

### 4. 上下文压缩（Contextual Compression）

**核心目的**：从每个相关文档中提取与查询最相关的核心片段，剔除冗余信息，减少输入给大模型的token数量，同时提高回答的精准度。

#### 常用压缩技术

- **文档提取器**：使用LLM从文档中提取与查询相关的句子
- **嵌入过滤器**：计算文档中每个句子与查询的相似度，过滤掉低相似度的句子
- **重排序压缩**：只保留重排序后得分最高的Top-N个文档

#### 具体示例：使用LangChain的上下文压缩

```
from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import LLMChainExtractor
from langchain_openai import OpenAI

# 初始化基础检索器（这里使用之前的混合检索器）
# base_retriever = ensemble_retriever  # 来自前面的示例

# 初始化LLM用于压缩
llm = OpenAI(temperature=0, api_key="your_api_key")

# 创建文档压缩器
compressor = LLMChainExtractor.from_llm(llm)

# 创建上下文压缩检索器
compression_retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=base_retriever
)

# 执行压缩检索
query = "Transformer架构是谁提出的？"
compressed_docs = compression_retriever.get_relevant_documents(query)

print("压缩后的上下文：")
for doc in compressed_docs:
    print(f"- {doc.page_content}")
```

### 5. 查询路由（Query Routing）

**核心原理**：根据查询的类型或意图，动态选择最适合的检索策略或知识库子集。

#### 路由策略

| 路由类型 | 判断依据 | 目标检索器 |
|---------|---------|-----------|
| 语义路由 | 查询的语义特征 | 稠密向量检索器 |
| 关键词路由 | 是否包含专有名词 | BM25检索器 |
| 意图路由 | 查询意图分类 | 对应领域的专用检索器 |
| 混合路由 | 综合多种特征 | 多路召回组合 |

#### 实现示例

```python
from langchain.chains import LLMRouterChain
from langchain_openai import ChatOpenAI

def create_query_router():
    llm = ChatOpenAI(temperature=0, model="gpt-3.5-turbo")
    
    # 定义路由描述
    routing_descriptions = {
        "semantic_search": "用于通用语义查询，理解用户意图",
        "keyword_search": "用于包含具体型号、人名、日期等专有名词的查询",
        "technical_search": "用于技术文档和API相关查询"
    }
    
    router_chain = LLMRouterChain.from_llm_and_routes(
        llm=llm,
        routes=routing_descriptions
    )
    
    return router_chain
```

## 四、检索应用实践

### 1. 混合检索深度解析

#### (1) 混合检索的核心价值

混合检索通过结合**稠密检索**（Dense Retrieval）和**稀疏检索**（Sparse Retrieval）的优势，解决了单一检索策略的根本性局限：

- **稠密检索的短板**：对精确关键词（如产品型号MX-7823、错误码ERR_CERT_AUTHORITY_INVALID、人名张伟）匹配效果差
- **稀疏检索的短板**：无法理解语义，对同义词、多义词处理能力弱

#### (2) 混合检索的实际效果

根据2026年行业实践数据，混合检索相比单一检索策略的效果提升：

| 场景 | 纯向量检索准确率 | 混合检索准确率 | 提升幅度 |
|------|------------------|----------------|----------|
| 精确查询（配置项/错误码） | 45% | 92% | +104% |
| 语义查询（"怎么优化"） | 78% | 80% | +2.6% |
| 短查询（<10字） | 65% | 85% | +31% |
| 混合查询（关键词+描述） | 70% | 88% | +26% |

#### (3) 混合检索最佳实践

- **权重调优策略**：
  - **政策/条款/代码等精确匹配重的场景**：BM25权重调高至0.6-0.7
  - **开放式问答、概念解释**：向量检索权重调高至0.7-0.8
  - **通用场景**：默认权重0.5:0.5，通过A/B测试微调

- **融合算法选择**：
  - **首选RRF**：无需标注数据，效果稳定
  - **避免MinMax归一化**：容易受极端值影响
  - **加权求和**：需要标注数据进行权重校准

- **性能优化**：
  - **粗排阶段**：BM25 + 向量 → Top-20-30候选
  - **精排阶段**：RRF融合 → Rerank → Top-3-5最终结果

### 2. 不同业务场景的检索策略选择

| 业务场景 | 推荐检索策略 | 关键配置 |
|----------|--------------|----------|
| **电商商品搜索** | 混合检索 + 元数据过滤 | BM25权重0.7，过滤品牌/价格/库存 |
| **法律文档检索** | 混合检索 + 图检索 | BM25权重0.6，构建法律实体关系图 |
| **技术支持知识库** | 混合检索 + 多向量检索 | 向量权重0.6，标题向量+内容向量 |
| **企业内部文档** | 混合检索 + 权限过滤 | 默认权重0.5，按部门/角色过滤 |
| **学术论文检索** | 向量检索 + 元数据过滤 | 向量权重0.8，按年份/领域/引用数过滤 |

### 3. 向量数据库选型与优化

#### 主流向量数据库对比

| 数据库 | 特点 | 适用场景 | 性能表现 |
|-------|------|---------|---------|
| **Chroma** | 轻量级、易用、开源 | 原型开发、小规模应用 | 中等，适合快速启动 |
| **Milvus** | 高性能、分布式、功能丰富 | 大规模生产环境、企业级应用 | 极高，支持亿级向量 |
| **Pinecone** | 全托管服务、无需运维 | 不想维护基础设施的团队 | 高，延迟低，但成本较高 |
| **Elasticsearch** | 成熟生态、混合搜索能力强 | 已有ES集群、需要复杂过滤和全文检索 | 高，混合搜索场景首选 |
| **Faiss** | Facebook开源、底层引擎 | 需要极致性能定制、嵌入其他系统 | 极高，但需自行封装和管理 |

#### 选型建议

1. **初创/原型阶段**：首选 **Chroma** 或 **LanceDB**，集成简单，本地运行方便。
2. **大规模生产环境**：首选 **Milvus** 或 **Zilliz Cloud**，支持水平扩展和高可用。
3. **混合搜索需求**：如果既需要关键词精确匹配又需要语义搜索，**Elasticsearch** (8.x+版本支持向量) 或 **OpenSearch** 是最佳选择。
4. **云原生/Serverless**：如果希望零运维，**Pinecone** 或 **Weaviate Cloud** 是不错的选择。

#### 优化技巧

- **索引类型选择**：
  - **HNSW**：默认首选，平衡了速度和精度，适合大多数场景。
  - **IVF_FLAT**：适合内存受限场景，通过聚类减少搜索范围。
  - **DiskANN**：适合超大规模数据集，将索引存储在磁盘上以节省内存。
- **量化技术**：使用 **PQ (Product Quantization)** 或 **SQ (Scalar Quantization)** 压缩向量，可将内存占用降低 4-8 倍，对精度影响极小。
- **分区与分片**：根据元数据（如租户ID、文档类型）进行分区，提高查询效率和管理便利性。

### 4. 缓存机制（Caching）

**核心目的**：减少重复的嵌入计算和向量检索请求，降低延迟和API成本。RAG系统中存在大量的重复查询或相似查询，缓存能带来显著收益。

#### 缓存层级

1. **查询缓存（Query Cache）**：
   - **原理**：存储 `查询文本 -> 检索结果` 的映射。
   - **适用**：完全相同的重复查询。
   - **实现**：使用 Redis 或 Memcached，Key 为查询文本的 Hash 值。

2. **语义缓存（Semantic Cache）**：
   - **原理**：存储 `查询向量 -> 检索结果` 的映射。如果新查询与缓存中的查询语义相似度超过阈值（如 0.95），直接返回缓存结果。
   - **适用**：表述不同但意图相同的查询（如 "怎么重置密码" 和 "密码忘了怎么办"）。
   - **实现**：使用专门的语义缓存库（如 GPTCache）或在向量数据库中开辟独立的缓存集合。

3. **嵌入缓存（Embedding Cache）**：
   - **原理**：存储 `文本 -> 向量` 的映射。避免对相同文本重复调用嵌入模型。
   - **适用**：文档入库时的去重和加速，以及高频查询的向量化。

#### 具体示例：使用 GPTCache

```
from gptcache import cache
from gptcache.adapter.api import init_similar_cache
from gptcache.processor.pre import get_prompt

# 初始化语义缓存
init_similar_cache(
    data_dir="local_cache",
    similar_threshold=0.95,  # 相似度阈值
    pre_func=get_prompt
)

# 模拟检索函数
def mock_retrieval(query):
    print(f"执行实际检索: {query}")
    return ["相关文档内容"]

# 包装检索函数
def cached_retrieval(query):
    # 检查缓存
    result = cache.get(query)
    if result:
        print(f"命中缓存: {query}")
        return result
    
    # 执行实际检索
    docs = mock_retrieval(query)
    
    # 存入缓存
    cache.put(query, docs)
    return docs

# 测试
print("第一次查询：")
cached_retrieval("如何学习Python？")

print("\n第二次查询（语义相似）：")
cached_retrieval("Python该怎么学？")  # 将命中缓存
```

## 五、前沿进展与最佳实践

### 1. 2026年RAG检索前沿进展

#### (1) 自适应RAG（Adaptive RAG）

- **智能检索路由**：基于查询意图自动选择最适合的检索策略（向量检索、关键词检索、图检索或混合检索）
- **动态分块策略**：根据查询复杂度自动调整分块粒度

#### (2) 神经符号RAG（Neuro-Symbolic RAG）

- **形式化验证**：对生成的答案进行形式化逻辑验证，确保推理过程的正确性
- **可解释性增强**：提供完整的推理链和证据溯源

#### (3) 多智能体RAG（Multi-Agent RAG）

- **分工协作**：多个专业化智能体协同工作，分别负责检索、验证、生成、优化等任务
- **辩论机制**：不同智能体对同一问题提出不同答案，通过辩论机制选择最优解

### 2. 安全性与权限控制

在企业和多租户场景中，RAG 检索必须考虑数据安全和访问控制。

#### (1) 文档级权限过滤（Document-Level Security）

- **原理**：在向量数据库中存储文档时，同时存储权限元数据（如 `allowed_users`, `allowed_groups`, `visibility`）。
- **实施**：在检索时，将当前用户的 ID 或组信息作为**过滤条件（Filter）**传递给向量数据库。
- **注意**：必须在向量检索阶段就进行过滤，而不是检索后再过滤，以防止通过精心构造的查询窃取无权访问的数据。

#### (2) 输入注入防护（Prompt Injection Protection）

- **风险**：用户可能在查询中插入恶意指令，试图绕过系统限制或获取敏感信息。
- **防御**：
  - **输入清洗**：去除特殊字符、HTML标签等。
  - **指令隔离**：在 Prompt 中明确区分系统指令、上下文和用户查询。
  - **LLM 防火墙**：使用专门的模型或规则检测恶意输入。

#### (3) 输出脱敏（Output Redaction）

- **原理**：在将检索结果发送给大模型之前，或对大模型生成的答案进行后处理时，识别并替换敏感信息（如身份证号、手机号、API Key）。
- **工具**：可以使用 Presidio 等开源库进行实体识别和脱敏。

### 3. 错误处理与降级策略

RAG 系统依赖多个外部组件（嵌入模型、向量库、LLM），任何环节都可能失败，必须设计健壮的降级策略。

#### 常见故障与应对

| 故障点 | 可能原因 | 降级策略 |
|--------|----------|----------|
| **嵌入服务超时** | 网络波动、服务过载 | 1. 重试机制（Exponential Backoff）<br>2. 使用本地轻量级嵌入模型备用<br>3. 返回通用错误提示 |
| **向量库连接失败** | 数据库宕机、网络中断 | 1. 切换到只读副本<br>2. 使用本地缓存的最新索引<br>3. 降级为纯关键词搜索（BM25） |
| **检索结果为空** | 知识库缺失、查询太偏 | 1. 触发查询重写/扩展<br>2. 告知用户未找到相关信息，避免幻觉<br>3. 提供通用性回答或引导用户换个问法 |
| **LLM 生成失败** | Token 超限、服务不可用 | 1. 截断上下文，保留最相关的 Top-K<br>2. 切换到更小的本地模型<br>3. 直接返回检索到的原始片段 |

#### 代码示例：带重试和降级的检索

```
import time
import logging
from tenacity import retry, stop_after_attempt, wait_exponential

logger = logging.getLogger(__name__)

@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=2, max=10))
def robust_retrieval(query, vector_store, bm25_retriever):
    try:
        # 尝试向量检索
        docs = vector_store.similarity_search(query, k=5)
        if not docs:
            logger.warning("向量检索无结果，降级为BM25")
            docs = bm25_retriever.get_relevant_documents(query)
        return docs
    except Exception as e:
        logger.error(f"向量检索失败: {e}，尝试降级...")
        # 如果向量库彻底挂了，直接用BM25
        try:
            return bm25_retriever.get_relevant_documents(query)
        except Exception as be:
            logger.critical(f"所有检索方式均失败: {be}")
            raise Exception("检索服务暂时不可用，请稍后重试")
```

### 4. 检索效果评估指标

量化评估检索系统的性能是优化的基础，常用指标有：

| 指标 | 核心含义 | 计算公式 | 适用场景 |
|-----|---------|---------|---------|
| Recall@K | 前K个结果中包含相关文档的比例 | 相关文档在Top-K中的数量 / 总相关文档数 | 评估召回能力 |
| Precision@K | 前K个结果中相关文档的比例 | 相关文档在Top-K中的数量 / K | 评估精准度 |
| MRR（平均倒数排名） | 第一个相关结果排名的倒数的平均值 | MRR = (1/|Q|) × Σ(1/rank_i) | 评估"找得快"的能力 |
| NDCG@K（归一化折损累计增益） | 综合考虑相关度等级和排名的指标 | NDCG@K = DCG@K / IDCG@K | 评估整体排序质量 |

#### 具体示例：计算Recall@K和MRR

```
def calculate_recall_at_k(retrieved_docs, relevant_docs, k):
    """计算Recall@K"""
    retrieved_top_k = retrieved_docs[:k]
    relevant_in_top_k = [doc for doc in retrieved_top_k if doc in relevant_docs]
    return len(relevant_in_top_k) / len(relevant_docs) if relevant_docs else 0

def calculate_mrr(retrieved_docs, relevant_docs):
    """计算MRR"""
    for i, doc in enumerate(retrieved_docs, 1):
        if doc in relevant_docs:
            return 1.0 / i
    return 0.0

# 测试
retrieved_docs = ["doc1", "doc2", "doc3", "doc4", "doc5"]
relevant_docs = {"doc3", "doc5"}

print(f"Recall@3: {calculate_recall_at_k(retrieved_docs, relevant_docs, 3):.4f}")
print(f"MRR: {calculate_mrr(retrieved_docs, relevant_docs):.4f}")
```

```
MRR: 0.3333
```

### 5. 检索阶段最佳实践

1. **永远使用混合检索**：向量检索+BM25是标配，能显著提升整体效果
2. **重排序是必须的**：在任何生产环境中都应该加入重排序步骤，它能带来30%-50%的效果提升
3. **合理设置K值**：召回阶段K=20-50，重排序后保留Top-3-5个文档给大模型
4. **优化查询预处理**：这是成本最低但收益最高的优化手段
5. **持续评估和调优**：建立评估数据集，定期测试不同检索策略的效果
6. **监控关键指标**：持续跟踪Recall@K、MRR等指标，确保系统性能稳定
