# Agent 外部接入的的三种方式

| 接口形态 | 对Agent来说是什么 | 调用者 | 一句话解释 |
| :--- | :--- | :--- | :--- |
| **API** | Agent变成一个HTTP接口 | 任何系统 | “Agent as a Service” |
| **Step** | Agent变成一个Pipeline组件 | 流水线开发者 | “Agent as a Step” |
| **Gateway** | Agent变成一个多平台机器人 | 聊天工具里的用户 | “Agent as a Bot” |

## 1. API 形态 → Agent 变成“可调用的网络服务”

- **本质**：把Agent封装成一个标准的REST API端点（或gRPC、WebSocket）。
- **谁在调用**：任何能发HTTP请求的系统（前端、后端微服务、脚本、低代码平台）。
- **Agent如何被使用**：调用方发送一个POST请求（如`/invoke`），带上用户问题或上下文，API层负责唤醒Harness内核，执行Agent的推理-行动循环，最后返回结果。
- **典型场景**：把Agent能力集成到自己的业务系统里（例如客服机器人后台、智能报表生成服务）。

---

## 2. Step 形态 → Agent 变成“CI/CD 流水线里的一个原子步骤”

- **本质**：将Agent包装成Harness平台（或类似Jenkins、GitLab CI）中的一个**可拖拽、可配置的Step**。
- **谁在调用**：流水线的开发者（通过UI拖拽或YAML配置）。
- **Agent如何被使用**：当流水线运行到该Step时，平台会触发Agent执行，例如：审查PR → 调用“代码评审Agent” → 得到审查意见 → 决定流水线继续还是失败。
- **典型场景**：DevOps自动化（代码审查、智能测试生成、自动修复构建错误）。

---

## 3. Gateway 形态 → Agent 变成“多平台消息机器人”

- **本质**：在Agent外围加一个**协议适配层**（Gateway），让它能同时接入多个IM平台（飞书、钉钉、Slack、企业微信、Discord等）。
- **谁在调用**：各个IM平台上的最终用户（通过@机器人或私聊）。
- **Agent如何被使用**：用户在飞书发消息 → Gateway接收并转换成统一格式 → 转发给Harness内核 → Agent处理后返回 → Gateway再转换回飞书格式 → 用户收到回复。
- **典型场景**：企业智能助手（查工单、问知识库、执行简单运维命令），统一接入多个聊天工具。
