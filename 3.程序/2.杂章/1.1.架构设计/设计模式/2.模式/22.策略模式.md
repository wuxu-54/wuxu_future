# 策略模式

一个类的行为或算法可以在运行时动态更改。将每个算法封装起来，使它们可以互换使用，无需修改客户端代码。

类型：行为型

目的：**定义一系列可互换的算法（或行为），将每个算法封装起来，使它们可以独立于使用它们的客户端而变化**。这种模式通过分离算法的定义与使用，解决了“在多种算法中动态选择”时的代码耦合问题。

## 一、核心定义与设计意图

- **定义**：定义一系列算法，把它们一个个封装起来，并且使它们可相互替换。本模式使得算法可独立于使用它的客户端而变化。
- **意图**：
  - 避免在客户端代码中使用多重条件判断（`if-else`/`switch-case`）来选择不同算法，降低代码耦合。
  - 使算法的定义与使用分离，客户端无需知道算法的具体实现，只需通过统一接口调用。
  - 方便新增或替换算法（符合开闭原则），无需修改使用算法的客户端代码。

## 二、核心角色与职责

策略模式包含3个核心角色，它们的协作关系是理解模式的关键：

### 1. 策略接口（Strategy）

- **定义**：声明所有具体策略必须实现的接口（或抽象类），规定了算法的统一方法签名。
- **职责**：
  - 作为所有具体策略的抽象，提供客户端调用算法的统一入口（如`execute()`方法）。
  - 确保不同具体策略的方法签名一致，使客户端可以无差别地使用任何策略。

### 2. 具体策略（Concrete Strategy）

- **定义**：实现策略接口，封装具体的算法逻辑。
- **职责**：
  - 实现策略接口中声明的方法，提供具体的算法实现（如“冒泡排序”“快速排序”“支付宝支付”“微信支付”等）。
  - 算法逻辑独立于其他策略和客户端，仅通过策略接口与外部交互。

### 3. 上下文（Context）

- **定义**：持有一个策略接口的引用，是客户端与策略对象之间的中间层。
- **职责**：
  - 维护当前使用的策略对象（可通过构造函数、setter方法动态设置）。
  - 提供客户端调用的接口（如`doOperation()`），但自身不实现算法，而是**委托给当前策略对象**执行。
  - 可能包含策略执行所需的公共数据或辅助方法，供策略对象使用。

## 三、工作流程（核心逻辑）

策略模式的运行流程可概括为“**设置策略-委托执行**”两步：

1. **客户端选择并设置策略**：客户端根据需求创建具体策略对象，并通过上下文的`setStrategy()`方法（或构造函数）将其设置为上下文的当前策略。
2. **上下文委托策略执行**：客户端调用上下文的业务方法（如`doAction()`），上下文将请求转发给当前持有的策略对象，由具体策略执行实际算法逻辑。

**示例流程**：  
支付系统（Context）→ 客户端选择“支付宝支付”（ConcreteStrategyA）→ 设置为上下文的当前策略 → 客户端调用“支付”方法 → 上下文委托给“支付宝支付”策略 → 执行支付宝支付逻辑 → 若需切换为“微信支付”（ConcreteStrategyB），客户端只需通过`setStrategy()`更新策略，无需修改上下文或客户端其他代码。

## 四、优缺点分析

### 优点

1. **消除条件判断**：用策略的动态切换替代`if-else`/`switch-case`，代码更简洁、可读性更高。
2. **符合开闭原则**：新增算法只需添加新的具体策略类，无需修改上下文或客户端代码。
3. **算法复用性高**：每个具体策略封装独立算法，可在不同场景中复用。
4. **客户端与算法解耦**：客户端只需知道策略接口和所需具体策略，无需了解算法细节。

### 缺点

1. **客户端需了解所有策略**：客户端必须知道所有具体策略的存在，才能选择合适的策略（可通过工厂模式弥补）。
2. **类数量增加**：每个算法对应一个具体策略类，策略过多时会导致类膨胀。
3. **策略切换的复杂性**：若策略切换需要复杂的条件判断，可能需要额外的逻辑（如策略选择器）来管理。

## 五、适用场景

策略模式适用于以下场景：

1. **多种算法完成同一任务**：且算法之间可以互换（如排序算法、加密算法、支付方式）。
2. **避免多重条件判断**：代码中出现大量`if-else`/`switch-case`用于选择不同行为（如“根据用户类型执行不同折扣计算”）。
3. **算法需要动态切换**：运行时根据条件动态选择或切换算法（如“白天用A算法，夜间用B算法”）。
4. **算法细节需隐藏**：希望客户端屏蔽算法的具体实现（如第三方接口调用的不同适配方案）。

## 六、实现步骤（以“支付系统”为例）

假设一个电商系统需要支持多种支付方式（支付宝、微信支付、银联支付），且支付逻辑可能随业务扩展而增加，适合用策略模式实现。

### 步骤1：定义策略接口（Strategy）

声明支付算法的统一方法（如`pay()`）。

```java
// 支付策略接口
public interface PaymentStrategy {
    // 执行支付，参数为支付金额
    void pay(double amount);
    // 获取支付方式名称
    String getPaymentName();
}
```

### 步骤2：实现具体策略（Concrete Strategy）

为每种支付方式实现策略接口，封装具体支付逻辑。

```java
// 支付宝支付策略
public class AlipayStrategy implements PaymentStrategy {
    private String username; // 支付宝用户名
    
    public AlipayStrategy(String username) {
        this.username = username;
    }
    
    @Override
    public void pay(double amount) {
        System.out.println("支付宝用户[" + username + "]支付了" + amount + "元");
        // 实际场景中会调用支付宝API完成支付
    }
    
    @Override
    public String getPaymentName() {
        return "支付宝";
    }
}

// 微信支付策略
public class WechatPayStrategy implements PaymentStrategy {
    private String openId; // 微信openId
    
    public WechatPayStrategy(String openId) {
        this.openId = openId;
    }
    
    @Override
    public void pay(double amount) {
        System.out.println("微信用户[" + openId + "]支付了" + amount + "元");
        // 实际场景中会调用微信支付API完成支付
    }
    
    @Override
    public String getPaymentName() {
        return "微信支付";
    }
}

// 银联支付策略（类似实现）
public class UnionPayStrategy implements PaymentStrategy {
    private String cardNumber; // 银行卡号
    
    public UnionPayStrategy(String cardNumber) {
        this.cardNumber = cardNumber;
    }
    
    @Override
    public void pay(double amount) {
        System.out.println("银联卡[" + cardNumber + "]支付了" + amount + "元");
    }
    
    @Override
    public String getPaymentName() {
        return "银联支付";
    }
}
```

### 步骤3：定义上下文（Context）

维护当前支付策略，并提供客户端调用的支付接口。

```java
// 支付上下文（订单支付系统）
public class PaymentContext {
    private PaymentStrategy strategy; // 当前支付策略
    
    // 构造函数设置初始策略
    public PaymentContext(PaymentStrategy strategy) {
        this.strategy = strategy;
    }
    
    // 动态切换支付策略
    public void setStrategy(PaymentStrategy strategy) {
        this.strategy = strategy;
        System.out.println("已切换支付方式为：" + strategy.getPaymentName());
    }
    
    // 客户端调用的支付方法（委托给当前策略）
    public void payOrder(double amount) {
        System.out.println("开始支付...");
        strategy.pay(amount);
        System.out.println("支付完成！");
    }
}
```

### 步骤4：客户端使用

客户端创建具体策略，通过上下文完成支付，并可动态切换策略。

```java
public class Client {
    public static void main(String[] args) {
        // 1. 创建订单，初始选择支付宝支付
        PaymentContext payment = new PaymentContext(
            new AlipayStrategy("zhangsan@alipay.com")
        );
        // 支付100元
        payment.payOrder(100.0);
        
        // 2. 切换为微信支付
        payment.setStrategy(new WechatPayStrategy("wx1234567890"));
        // 支付200元
        payment.payOrder(200.0);
        
        // 3. 切换为银联支付
        payment.setStrategy(new UnionPayStrategy("6222xxxxxx1234"));
        // 支付300元
        payment.payOrder(300.0);
    }
}
```

## 七、与其他模式的对比

### 1. 策略模式 vs 状态模式

| 维度         | 策略模式                     | 状态模式                     |
|--------------|------------------------------|------------------------------|
| **核心意图** | 封装可互换的算法/行为        | 封装对象状态及状态对应的行为  |
| **策略/状态关系** | 策略之间相互独立，无依赖    | 状态之间可能存在依赖（如状态流转） |
| **切换主体** | 策略由客户端主动选择切换    | 状态由状态对象自身决定切换    |
| **行为与上下文** | 策略不依赖上下文（或弱依赖） | 状态通常持有上下文引用（用于切换状态） |

### 2. 策略模式 vs 模板方法模式

- **策略模式**：通过组合方式（上下文持有策略引用）实现算法替换，算法是完整独立的，客户端可动态选择。
- **模板方法模式**：通过继承方式（子类实现父类抽象方法）固定算法骨架，仅允许修改算法的部分步骤，算法结构由父类控制。

### 3. 策略模式 vs 简单工厂模式

- **策略模式**：关注“算法的使用与切换”，客户端需知道策略的存在，上下文负责委托执行。
- **简单工厂模式**：关注“对象的创建”，客户端无需知道具体产品类，工厂负责创建对象。
- **结合使用**：可通过工厂模式创建具体策略对象，降低客户端对策略的感知（如“支付策略工厂”根据参数返回对应支付策略）。

## 八、高级应用与变体

1. **策略工厂**：用工厂模式封装策略的创建逻辑，客户端只需传入策略类型（如“ALIPAY”“WECHAT”），由工厂返回具体策略，减少客户端与具体策略的耦合。

   ```java
   // 支付策略工厂
   public class PaymentStrategyFactory {
       public static PaymentStrategy createStrategy(String type, String account) {
           switch (type) {
               case "ALIPAY": return new AlipayStrategy(account);
               case "WECHAT": return new WechatPayStrategy(account);
               case "UNIONPAY": return new UnionPayStrategy(account);
               default: throw new IllegalArgumentException("不支持的支付方式");
           }
       }
   }
   
   // 客户端使用工厂
   PaymentStrategy strategy = PaymentStrategyFactory.createStrategy("ALIPAY", "zhangsan@alipay.com");
   ```

2. **策略链**：当需要按顺序尝试多个策略（如“先尝试支付宝，失败则用微信”），可将策略组成链，上下文依次调用直到成功。

3. **无状态策略**：若策略无需维护状态（如纯算法逻辑），可将具体策略设计为单例，减少对象创建开销。

## 九、注意事项

1. **避免过度设计**：若策略数量极少（如2种）且无需扩展，使用`if-else`可能更简单，不必强行使用策略模式。
2. **策略的粒度控制**：每个策略应专注于单一算法，避免一个策略类实现多个相关算法（违背单一职责原则）。
3. **策略的选择逻辑**：复杂的策略选择逻辑（如根据用户等级、时间动态选择）应封装在单独的“策略选择器”中，而非客户端。
4. **文档化策略**：需清晰说明每个策略的适用场景，避免客户端误用（如“银联支付支持信用卡，支付宝支持余额宝”）。

## 总结

策略模式通过“封装算法、动态切换”的思想，解决了多算法场景下的代码耦合问题，核心是**策略接口定义规范、具体策略实现细节、上下文委托执行**。它特别适合算法多变、需要灵活扩展的场景，虽然会增加类数量，但能显著提升代码的可维护性和扩展性。实际应用中，常与工厂模式结合使用，进一步降低客户端的使用复杂度。
