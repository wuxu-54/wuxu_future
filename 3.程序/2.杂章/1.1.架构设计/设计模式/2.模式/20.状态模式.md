# 状态模式

允许一个对象在其内部状态改变时改变其行为，看起来就像是改变了其类一样。

类型：行为型

目的：**将对象在不同状态下的行为封装到不同的状态对象中，让对象的行为随着其内部状态的变化而改变**。这种模式通过分离状态与行为，解决了对象在多状态下因大量条件判断（如`if-else`或`switch-case`）导致的代码臃肿、可维护性差的问题。

## 一、核心定义与设计意图

- **定义**：允许一个对象在其内部状态改变时改变它的行为，对象看起来似乎修改了它的类。
- **意图**：
  - 将与特定状态相关的行为局部化，避免在一个类中堆砌所有状态的行为。
  - 将状态转换的逻辑封装在具体状态中，而非上下文（Context）中，使状态转换更清晰。
  - 使新增状态或修改状态行为时，无需修改已有代码（符合开闭原则）。

## 二、核心角色与职责

状态模式包含3个核心角色，它们的职责和协作关系是理解模式的关键：

### 1. 上下文（Context）

- **定义**：维护一个当前状态的引用，是客户端直接交互的对象。
- **职责**：
  - 提供客户端调用的接口（如业务方法），但自身不处理具体行为，而是**委托给当前状态对象**。
  - 提供方法（如`setState()`）允许状态对象修改其当前状态（用于状态转换）。
  - 可能持有状态转换所需的全局数据（供所有状态对象共享）。

### 2. 状态接口（State）

- **定义**：声明一个接口，用于封装与上下文相关的所有状态的**行为**（即状态下可执行的操作）。
- **职责**：
  - 定义所有具体状态需要实现的方法（如`handle()`），这些方法对应上下文在该状态下的行为。
  - 接口的方法参数通常会包含上下文对象（或由具体状态持有上下文引用），以便状态转换时修改上下文的当前状态。

### 3. 具体状态（Concrete State）

- **定义**：实现状态接口，封装与特定状态相关的具体行为。
- **职责**：
  - 实现状态接口中定义的方法，即该状态下上下文应执行的具体操作。
  - **决定状态转换逻辑**：在完成当前状态的行为后，根据条件判断是否需要切换到其他状态（通过修改上下文的`currentState`实现）。
  - **通常持有上下文的引用**：因为状态转换需要修改上下文的当前状态，所以具体状态对象需要知道上下文（通过构造函数传入或方法参数传入）。

## 三、工作流程（核心逻辑）

状态模式的运行流程可概括为“**委托-执行-转换**”三步：

1. **客户端调用上下文的方法**：客户端不直接操作状态对象，而是通过上下文提供的接口发起请求（如`doAction()`）。
2. **上下文委托给当前状态**：上下文将请求转发给其内部持有的“当前状态对象”，由具体状态对象执行实际逻辑。
3. **具体状态执行并决定转换**：具体状态对象完成自身行为后，根据业务规则判断是否需要切换状态（如“待支付”状态完成支付后切换到“已支付”状态），并通过上下文的`setState()`方法更新上下文的当前状态。

**示例流程**：  
订单（Context）→ 当前状态为“待支付”（ConcreteStateA）→ 客户端调用“支付”方法 → 上下文委托给“待支付”状态 → “待支付”状态执行支付逻辑 → 支付成功后，“待支付”状态调用订单的`setState(已支付状态)` → 订单的当前状态变为“已支付”（ConcreteStateB）。

## 四、优缺点分析

### 优点

1. **消除大量条件判断**：将不同状态的行为分散到具体状态类中，替代了`if-else`或`switch-case`，代码更清晰。
2. **符合单一职责原则**：每个具体状态类只负责自身状态的行为和转换逻辑，职责单一。
3. **符合开闭原则**：新增状态只需添加新的具体状态类，无需修改已有上下文或其他状态类。
4. **状态转换逻辑内聚**：状态转换的规则封装在具体状态中，而非上下文，便于维护和理解。

### 缺点

1. **类数量增加**：每个状态都需要一个具体状态类，当状态数量过多时，会导致类膨胀。
2. **状态逻辑分散**：状态转换逻辑分布在多个具体状态类中，若需全局把握状态流转，可能需要遍历多个类。
3. **可能引入循环依赖**：具体状态持有上下文引用，上下文又持有状态引用，若设计不当可能导致循环依赖（需通过合理的接口设计避免）。

## 五、适用场景

状态模式适用于以下场景：

1. **对象行为依赖于其状态**：且状态数量较多，不同状态下行为差异较大（如订单状态、电梯状态、游戏角色状态）。
2. **存在大量条件判断**：代码中出现多个`if-else`或`switch-case`用于判断状态，并根据状态执行不同行为（此时可考虑用状态模式重构）。
3. **状态转换频繁且规则复杂**：状态之间的转换规则需要灵活修改或扩展（如工作流引擎中的审批状态流转）。

## 六、实现步骤（以“订单状态”为例）

### 步骤1：定义状态接口（State）

声明订单在不同状态下可执行的行为（如支付、发货、取消等）。

```java
// 订单状态接口
public interface OrderState {
    // 支付订单
    void pay(OrderContext order);
    // 发货
    void ship(OrderContext order);
    // 取消订单
    void cancel(OrderContext order);
    // 获取当前状态名称
    String getStateName();
}
```

### 步骤2：实现具体状态（Concrete State）

为每个状态（待支付、已支付、已发货等）实现状态接口，封装该状态下的行为和转换逻辑。

```java
// 待支付状态
public class PendingPaymentState implements OrderState {
    @Override
    public void pay(OrderContext order) {
        System.out.println("订单支付成功！");
        // 支付后切换到"已支付"状态
        order.setState(new PaidState());
    }

    @Override
    public void ship(OrderContext order) {
        System.out.println("错误：未支付的订单不能发货！");
    }

    @Override
    public void cancel(OrderContext order) {
        System.out.println("订单已取消（待支付状态）");
        order.setState(new CancelledState());
    }

    @Override
    public String getStateName() {
        return "待支付";
    }
}

// 已支付状态
public class PaidState implements OrderState {
    @Override
    public void pay(OrderContext order) {
        System.out.println("错误：订单已支付，无需重复支付！");
    }

    @Override
    public void ship(OrderContext order) {
        System.out.println("订单已发货！");
        order.setState(new ShippedState());
    }

    @Override
    public void cancel(OrderContext order) {
        System.out.println("订单已取消（已支付状态，将发起退款）");
        order.setState(new CancelledState());
    }

    @Override
    public String getStateName() {
        return "已支付";
    }
}

// 其他状态（已发货、已取消等）类似实现...
```

### 步骤3：定义上下文（Context）

维护当前状态，并提供客户端调用的接口（委托给当前状态）。

```java
// 订单上下文
public class OrderContext {
    // 维护当前状态（初始状态为待支付）
    private OrderState currentState;
    // 订单相关数据（如订单号）
    private String orderId;

    public OrderContext(String orderId) {
        this.orderId = orderId;
        this.currentState = new PendingPaymentState(); // 初始状态
    }

    // 切换状态（供具体状态调用）
    public void setState(OrderState state) {
        this.currentState = state;
        System.out.println("订单状态已更新为：" + state.getStateName());
    }

    // 客户端调用的支付方法（委托给当前状态）
    public void pay() {
        currentState.pay(this); // 将自身引用传给状态对象
    }

    // 客户端调用的发货方法
    public void ship() {
        currentState.ship(this);
    }

    // 客户端调用的取消方法
    public void cancel() {
        currentState.cancel(this);
    }

    // 获取当前状态
    public String getCurrentStateName() {
        return currentState.getStateName();
    }
}
```

### 步骤4：客户端使用

客户端只需与上下文交互，无需关心具体状态。

```java
public class Client {
    public static void main(String[] args) {
        // 创建订单（初始状态：待支付）
        OrderContext order = new OrderContext("ORD_12345");
        System.out.println("当前订单状态：" + order.getCurrentStateName()); // 待支付

        // 支付订单
        order.pay();
        System.out.println("当前订单状态：" + order.getCurrentStateName()); // 已支付

        // 发货
        order.ship();
        System.out.println("当前订单状态：" + order.getCurrentStateName()); // 已发货

        // 尝试再次支付（已发货状态不允许支付）
        order.pay(); // 输出错误信息
    }
}
```

**输出结果**：

```txt
当前订单状态：待支付
订单支付成功！
订单状态已更新为：已支付
当前订单状态：已支付
订单已发货！
订单状态已更新为：已发货
当前订单状态：已发货
错误：订单已支付，无需重复支付！
```

## 七、与其他模式的对比

### 1. 状态模式 vs 策略模式

- **结构相似**：都通过接口封装行为，具体实现类提供不同逻辑，上下文持有接口引用。
- **核心区别**：
  - **意图不同**：状态模式关注“对象内在状态的变化导致行为变化”，状态之间通常存在依赖关系（如“待支付”→“已支付”）；策略模式关注“算法/策略的替换”，策略之间相互独立（如排序算法的选择）。
  - **状态转换**：状态模式中，状态转换由具体状态自行决定；策略模式中，策略的选择由客户端决定。

### 2. 状态模式 vs 状态机

- **状态机**：是一种数学模型（或工具），用于描述对象在不同状态下的转换规则（通常用状态图表示）。
- **状态模式**：是实现状态机的一种设计模式，通过面向对象的方式将状态机的状态和行为封装为类，更灵活、可扩展。

## 八、注意事项

1. **状态数量控制**：若状态数量极少（如2-3个），使用`if-else`可能比状态模式更简单，避免过度设计。
2. **状态转换的可见性**：状态转换逻辑封装在具体状态中，可能导致全局状态流转不直观，可通过状态图辅助理解。
3. **避免循环依赖**：具体状态持有上下文引用时，需确保两者通过接口交互（而非具体实现），降低耦合。
4. **共享状态对象**：若多个上下文可共享同一状态（无状态差异），可使用单例模式创建具体状态对象，减少内存占用。

## 总结

状态模式通过将状态与行为分离，解决了多状态对象的代码臃肿问题，核心是“**状态决定行为，行为改变状态**”。它适用于状态多、行为差异大、转换频繁的场景，虽然会增加类数量，但能显著提升代码的可维护性和扩展性。理解状态模式的关键是把握“上下文委托行为”和“具体状态控制转换”这两个核心机制。
