# Configuration

在Gradle中，`Configuration`是依赖管理的核心概念，代表一组具有特定用途的依赖项集合（包括库、模块、文件等），并定义了这些依赖项的行为规则（如传递性、可见性、解析方式等）。每个`Configuration`由`ConfigurationContainer`管理，是控制依赖“从声明到使用”全流程的关键对象。

## 一、基本定义与核心作用

### 1. 定义

`Configuration`是一个**命名的依赖项集合**，它不仅包含依赖坐标（如`group:name:version`），还包含对这些依赖的“行为约定”（如是否传递、能否被其他项目使用、如何解析为本地文件等）。

### 2. 核心作用

- **依赖集合**：集中管理一组相关依赖（如编译期依赖、运行时依赖、测试依赖）。
- **行为控制**：通过属性定义依赖的传递性、可见性、解析规则。
- **依赖解析**：将依赖坐标转换为本地文件（如JAR包），供编译、运行等任务使用。
- **跨项目协作**：作为“接口”向其他项目暴露当前项目的输出（如类文件、资源）。

## 二、核心属性（详解与示例）

`Configuration`的行为由其属性决定，以下是最关键的属性及使用场景：

| 属性名               | 类型        | 核心作用                                                                 | 默认值  | 重要性 |
|----------------------|-------------|--------------------------------------------------------------------------|---------|--------|
| `canBeResolved`      | `boolean`   | 是否允许将配置中的依赖解析为本地文件（如JAR）                             | `false` | 极高   |
| `canBeConsumed`      | `boolean`   | 是否允许被其他项目作为依赖消费（即其他项目可通过`project(':xxx')`依赖它） | `false` | 极高   |
| `transitive`         | `boolean`   | 是否包含传递依赖（依赖的依赖是否被自动加入）                             | `true`  | 高     |
| `extendsFrom`        | `Set<Configuration>` | 继承的其他配置（自动包含被继承配置的所有依赖）                        | 空集合  | 高     |
| `description`        | `String`    | 配置的描述信息（用于文档化，无功能影响）                                 | `null`  | 中     |
| `visible`            | `boolean`   | 是否在`buildEnvironment`等任务的输出中可见                               | `true`  | 中     |
| `attributes`         | `AttributeContainer` | 配置的属性（用于变体匹配，如指定Java版本、操作系统等）                 | 空      | 高     |
| `resolutionStrategy` | `ResolutionStrategy` | 依赖解析策略（如版本冲突解决、强制版本等）                              | -       | 高     |

### 1. `canBeResolved`：控制依赖解析能力

- **作用**：决定配置是否能被“解析”（即从仓库下载依赖并转换为本地文件）。
- **场景**：仅对需要获取依赖文件的配置开启（如编译、运行时类路径）。
- **示例**：

  ```groovy
  // 创建可解析配置（用于获取依赖文件）
  configurations.create("myResolvableConfig") {
      canBeResolved = true  // 允许解析
      canBeConsumed = false // 不允许被其他项目消费
  }
  ```

- **注意**：`canBeResolved = true`的配置必须满足：无循环依赖、不包含“可消费配置”的继承关系。

### 2. `canBeConsumed`：控制跨项目消费能力

- **作用**：决定当前项目的该配置是否能被其他项目作为依赖引用。
- **场景**：用于暴露项目输出给外部（如Java项目的`apiElements`暴露编译产物）。
- **示例**：

  ```groovy
  // 创建可消费配置（供其他项目依赖）
  configurations.create("myConsumableConfig") {
      canBeConsumed = true  // 允许被消费
      canBeResolved = false // 不需要解析（本身是输出，而非依赖）
      // 关联项目输出（如类文件）
      outgoing.artifact(file("build/classes")) 
  }
  ```

- **其他项目引用**：

  ```groovy
  dependencies {
      implementation project(path: ':otherProject', configuration: 'myConsumableConfig')
  }
  ```

### 3. `transitive`：控制传递依赖

- **作用**：是否自动包含依赖的依赖（传递依赖）。
- **默认值**：`true`（大多数场景需要传递依赖）。
- **示例**：关闭传递依赖（仅保留直接声明的依赖）：

  ```groovy
  configurations.implementation {
      transitive = false // 不包含传递依赖
  }
  ```

- **注意**：关闭传递依赖后，需手动声明所有间接依赖，否则可能出现类缺失。

### 4. `extendsFrom`：配置继承（依赖复用）

- **作用**：通过继承其他配置，自动包含其所有依赖，避免重复声明。
- **示例**：

  ```groovy
  // 基础配置：包含通用依赖
  configurations.create("baseConfig") {
      dependencies {
          implementation "com.google.guava:guava:31.1-jre"
      }
  }
  
  // 业务配置：继承baseConfig的依赖
  configurations.create("businessConfig") {
      extendsFrom configurations.baseConfig
      canBeResolved = true
      // 新增业务依赖
      dependencies {
          implementation "org.springframework:spring-context:5.3.20"
      }
  }
  
  // businessConfig将包含guava和spring-context
  ```

### 5. `attributes`：变体匹配（高级）

- **作用**：通过属性标记配置的“变体”（如Java版本、操作系统、构建类型），用于多变体项目的依赖匹配。
- **常见属性**：
  - `TargetJvmVersion.TARGET_JVM_VERSION`：指定JVM版本（如8、11）。
  - `Usage.USAGE`：指定用途（如`java-api`、`java-runtime`）。
  - `Category.CATEGORY`：指定类型（如`library`、`application`）。
- **示例**：定义一个仅支持JVM 11的可解析配置：

  ```groovy
  configurations.create("java11Config") {
      canBeResolved = true
      attributes {
          attribute(Usage.USAGE, objects.named(Usage, Usage.JAVA_RUNTIME))
          attribute(TargetJvmVersion.TARGET_JVM_VERSION, 11)
          attribute(Category.CATEGORY, objects.named(Category, Category.LIBRARY))
      }
  }
  ```

- **作用**：当依赖多变体库（如同时提供JVM 8和11版本）时，Gradle会根据属性匹配最合适的变体。

### 6. `resolutionStrategy`：依赖解析策略

- **作用**：控制依赖解析过程中的规则（如版本冲突解决、强制版本、组件选择等）。
- **常用配置**：
  - `force`：强制使用特定版本。
  - `preferProjectModules`：优先使用项目内模块而非仓库依赖。
  - `failOnVersionConflict`：版本冲突时失败（而非默认选最高版本）。
- **示例**：

  ```groovy
  configurations.implementation {
      resolutionStrategy {
          // 强制使用guava 31.1-jre，即使有其他版本冲突
          force "com.google.guava:guava:31.1-jre"
          
          // 版本冲突时抛出错误（而非自动选择）
          failOnVersionConflict()
          
          // 优先使用项目内模块
          preferProjectModules()
      }
  }
  ```

## 三、生命周期（从创建到解析）

`Configuration`的生命周期分为**配置阶段**和**执行阶段**，其状态会随生命周期变化：

1. **配置阶段（Configuration Phase）**：
   - 时机：构建脚本加载时（执行`build.gradle`中的代码）。
   - 行为：创建配置、设置属性（`canBeResolved`等）、添加依赖、定义继承关系。
   - 限制：此时依赖尚未解析，无法获取本地文件路径。

2. **解析阶段（Resolution Phase）**：
   - 时机：首次调用`resolve()`、`files`等方法时（通常在任务执行时）。
   - 行为：Gradle会从仓库下载依赖、处理传递依赖、解决版本冲突，最终生成依赖文件集合。
   - 状态变化：解析后配置不可修改（若修改会抛出异常）。

3. **解析触发方式**：

   ```groovy
   def myConfig = configurations.create("myConfig") { canBeResolved = true }
   dependencies { myConfig "com.google.guava:guava:31.1-jre" }
   
   // 触发解析（获取依赖文件）
   def files = myConfig.files // 或 myConfig.resolve()
   ```

## 四、与依赖的关系（依赖的添加与管理）

`Configuration`的核心功能是管理依赖，依赖通过`dependencies`块添加到配置中：

### 1. 依赖的添加方式

```groovy
dependencies {
    // 1. 仓库依赖（Maven/Gradle仓库）
    implementation "group:name:version" // 如 "org.slf4j:slf4j-api:1.7.36"
    
    // 2. 项目依赖（依赖当前构建中的其他项目）
    implementation project(":other-module")
    
    // 3. 文件依赖（本地文件）
    implementation fileTree(dir: 'libs', include: ['*.jar'])
    implementation files('libs/local.jar', 'libs/another.jar')
    
    // 4. 自定义配置的依赖
    myConfig "com.fasterxml.jackson:jackson-databind:2.13.3"
}
```

### 2. 依赖的查询

通过`Configuration`的方法可查询依赖信息：

```groovy
def implConfig = configurations.implementation

// 1. 获取直接声明的依赖（不包含传递依赖）
implConfig.dependencies.each { dep ->
    println("直接依赖：${dep.group}:${dep.name}:${dep.version}")
}

// 2. 获取解析后的所有依赖文件（包含传递依赖，需canBeResolved = true）
if (implConfig.canBeResolved) {
    implConfig.files.each { file ->
        println("依赖文件：${file.absolutePath}")
    }
}

// 3. 获取解析后的依赖组件信息（包含坐标、版本、来源）
implConfig.resolvedConfiguration.resolvedArtifacts.each { art ->
    println("解析后的依赖：${art.moduleVersion.id}")
}
```

### 3. 依赖排除（Exclude）

排除配置中不需要的传递依赖：

```groovy
configurations.implementation {
    // 方式1：排除特定group和module（适用于所有依赖）
    exclude group: "org.slf4j", module: "slf4j-log4j12"
    
    // 方式2：仅对单个依赖排除传递依赖
    dependencies {
        implementation("org.springframework.boot:spring-boot-starter") {
            exclude group: "logback-classic" // 排除spring-boot-starter中的logback
        }
    }
}
```

## 五、Configuration的类型（按功能分类）

根据`canBeResolved`和`canBeConsumed`的组合，`Configuration`可分为3类，各自承担不同角色：

| 类型               | `canBeResolved` | `canBeConsumed` | 核心用途                                  | 示例（Java插件）          |
|--------------------|-----------------|-----------------|-------------------------------------------|---------------------------|
| 可解析配置         | `true`          | `false`         | 供当前项目解析依赖文件（如编译、运行）    | `compileClasspath`、`runtimeClasspath` |
| 可消费配置         | `false`         | `true`          | 供其他项目依赖（暴露当前项目的输出）      | `apiElements`、`runtimeElements` |
| 双向配置（罕见）   | `true`          | `true`          | 同时支持解析和被消费（特殊场景，如测试）  | 无预定义，需自定义        |

### 1. 可解析配置（Resolvable Configurations）

- **核心能力**：将依赖解析为本地文件，供任务使用（如`JavaCompile`任务需要`compileClasspath`的文件进行编译）。
- **Java插件示例**：
  - `compileClasspath`：编译主代码所需的类路径（包含`api`、`implementation`等依赖）。
  - `runtimeClasspath`：运行主代码所需的类路径（包含`implementation`、`runtimeOnly`等依赖）。
  - `testCompileClasspath`：编译测试代码所需的类路径。

### 2. 可消费配置（Consumable Configurations）

- **核心能力**：向其他项目暴露当前项目的输出（如编译后的类文件、资源文件）。
- **Java插件示例**：
  - `apiElements`：供其他项目编译时依赖的输出（包含主类文件、`api`依赖的传递信息）。
  - `runtimeElements`：供其他项目运行时依赖的输出（包含主类文件、资源、`runtimeOnly`依赖的传递信息）。
- **工作原理**：其他项目依赖当前项目时，Gradle会根据自身的配置类型（如`implementation`）匹配当前项目的可消费配置（如`runtimeElements`）。

## 六、预定义配置（主流插件提供）

大多数配置由插件预定义（遵循“约定优于配置”），无需手动创建。以下是常见插件的核心配置：

### 1. Java插件（`java`）

| 配置名称               | 类型         | 用途                                  |
|------------------------|--------------|---------------------------------------|
| `implementation`       | 基础配置     | 主代码的编译和运行时依赖，不向外部暴露传递依赖 |
| `api`                  | 基础配置     | 主代码的编译和运行时依赖，向外部暴露传递依赖（供上层项目编译使用） |
| `compileOnly`          | 基础配置     | 仅编译时依赖（不包含在运行时）          |
| `runtimeOnly`          | 基础配置     | 仅运行时依赖（不包含在编译时）          |
| `testImplementation`   | 基础配置     | 测试代码的编译和运行时依赖             |
| `testCompileOnly`      | 基础配置     | 仅测试编译时依赖                       |
| `testRuntimeOnly`      | 基础配置     | 仅测试运行时依赖                       |
| `compileClasspath`     | 可解析       | 主代码编译类路径（继承`api`/`implementation`/`compileOnly`等） |
| `runtimeClasspath`     | 可解析       | 主代码运行类路径（继承`implementation`/`runtimeOnly`等） |
| `testCompileClasspath` | 可解析       | 测试代码编译类路径（继承`testImplementation`等） |
| `testRuntimeClasspath` | 可解析       | 测试代码运行类路径（继承`testImplementation`/`testRuntimeOnly`等） |
| `apiElements`          | 可消费       | 暴露给外部的编译时依赖信息和类文件      |
| `runtimeElements`      | 可消费       | 暴露给外部的运行时依赖信息和类文件      |

### 2. Java Library插件（`java-library`）

在Java插件基础上新增：

- `api`：替代Java插件的`compile`，明确控制依赖传递性（推荐使用）。
- `implementation`：与Java插件一致，但语义更清晰（不传递依赖）。

### 3. Android插件（`com.android.application`）

新增Android特有的配置：

- `implementation`：与Java一致。
- `api`：与Java一致。
- `compileSdkVersion`：编译SDK依赖（特殊配置，非传统依赖）。
- `implementation 'com.android.support:appcompat-v7:28.0.0'`：Android库依赖。
- `testImplementation`：单元测试依赖。
- `androidTestImplementation`： instrumentation测试依赖。

## 七、高级功能与实践技巧

### 1. 配置的禁用与移除

- 禁用：通过`enabled = false`临时禁用配置（依赖不会被解析）。

  ```groovy
  configurations.implementation.enabled = false
  ```

- 移除：从`ConfigurationContainer`中彻底删除配置。

  ```groovy
  configurations.remove(configurations.findByName("oldConfig"))
  ```

### 2. 依赖约束（Dependency Constraints）

通过约束强制依赖版本，优先级高于传递依赖：

```groovy
configurations.implementation {
    constraints {
        // 强制所有模块的guava版本为31.1-jre
        implementation("com.google.guava:guava") {
            version {
                strictly "31.1-jre" // 严格匹配，不允许更高版本
                prefer "31.1-jre"   // 优先选择该版本
            }
            because "旧版本存在安全漏洞" // 说明原因（可选）
        }
    }
}
```

### 3. 配置的文件集合操作

可将配置作为文件集合传递给任务（如`Copy`、`JavaCompile`）：

```groovy
task copyDependencies(type: Copy) {
    from configurations.runtimeClasspath // 源：runtimeClasspath的依赖文件
    into "$buildDir/deps" // 目标目录
}
```

### 4. 查看配置详情

通过Gradle任务查看配置信息：

```bash
# 查看所有配置及其依赖
./gradlew buildEnvironment

# 查看特定配置的依赖树
./gradlew dependencies --configuration implementation
```

## 八、最佳实践与注意事项

1. **优先使用插件预定义配置**：如`implementation`、`api`，避免自定义配置（减少维护成本）。
2. **明确`canBeResolved`和`canBeConsumed`**：
   - 仅对需要解析文件的配置开启`canBeResolved = true`（如`compileClasspath`）。
   - 仅对需要被其他项目依赖的配置开启`canBeConsumed = true`（如`apiElements`）。
3. **避免在配置阶段解析依赖**：解析会触发网络请求和文件IO，拖慢构建速度。应在任务执行阶段（如`doLast`）解析。

   ```groovy
   task resolveDeps {
       doLast {
           def files = configurations.runtimeClasspath.files // 执行阶段解析
       }
   }
   ```

4. **谨慎关闭传递依赖**：`transitive = false`会导致依赖缺失风险，仅在明确不需要传递依赖时使用。
5. **使用`api`和`implementation`区分依赖传递性**：
   - `api`：依赖需要暴露给上层项目（如框架API）。
   - `implementation`：依赖仅内部使用（避免上层项目依赖）。
6. **通过`dependencies`任务排查冲突**：版本冲突是常见问题，使用`./gradlew dependencies`查看依赖树，定位冲突来源。

## 总结

`Configuration`是Gradle依赖管理的“原子单元”，它通过属性控制依赖的解析、传递和消费行为，是连接依赖声明与实际使用的桥梁。理解`Configuration`的核心属性（如`canBeResolved`、`transitive`）、类型分类（可解析/可消费）及预定义配置（如`implementation`），能帮助你构建清晰、高效的依赖管理体系，避免常见的依赖冲突和构建性能问题。实际开发中，应优先遵循插件约定，结合项目需求灵活配置，而非盲目自定义。
