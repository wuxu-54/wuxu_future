# ConfigurationContainer

在Gradle中，`ConfigurationContainer`是管理项目依赖配置（`Configuration`）的核心容器，它负责定义、组织和访问项目中所有的依赖配置。理解`ConfigurationContainer`是掌握Gradle依赖管理的关键，以下从概念、API、特性、实践等方面详细说明。

## 一、基本概念

### 1. 定义

`ConfigurationContainer`是一个**命名领域对象容器（NamedDomainObjectContainer）**，用于存储和管理`Configuration`对象。每个`Configuration`代表一组依赖项（如库、模块）的集合，以及这些依赖项的相关规则（如传递性、可见性等）。

### 2. 作用

- 集中管理项目中所有依赖配置（如`implementation`、`runtimeOnly`等）。
- 提供创建、查询、修改配置的API。
- 维护配置之间的继承关系（如`api`继承自`implementation`）。
- 支持依赖的解析（将配置中的依赖坐标转换为具体文件）和消费（供其他项目依赖）。

### 3. 访问方式

在构建脚本（`build.gradle`）中，通过`project.configurations`访问`ConfigurationContainer`实例，简化写法为`configurations`（因`project`是隐式对象）。

## 二、核心API

`ConfigurationContainer`继承自`NamedDomainObjectContainer<Configuration>`，因此包含其所有方法，同时扩展了配置管理的特有能力。以下是常用API：

### 1. 创建配置

通过`create()`方法创建自定义配置，支持命名和配置闭包：

```groovy
// 创建名为"myConfig"的配置
configurations.create("myConfig") {
    // 配置属性（可选）
    description = "自定义配置，用于特殊依赖"
    canBeResolved = true // 允许解析（获取具体依赖文件）
    canBeConsumed = false // 不允许被其他项目消费
}
```

- 参数：`name`（配置名称，唯一）+ 闭包（配置`Configuration`的属性）。
- 注意：配置名称需遵循命名规范（字母、数字、`-`、`_`）。

### 2. 获取/查找配置

- `getByName(String name)`：获取指定名称的配置，若不存在则抛出`UnknownConfigurationException`。

  ```groovy
  def compileConfig = configurations.getByName("implementation")
  ```

- `findByName(String name)`：查找配置，不存在则返回`null`（安全获取）。

  ```groovy
  def testConfig = configurations.findByName("testRuntimeOnly")
  if (testConfig != null) {
      // 处理逻辑
  }
  ```

- `getAt(String name)`：通过索引语法获取（等价于`getByName`）。

  ```groovy
  def runtimeConfig = configurations["runtimeClasspath"]
  ```

### 3. 遍历配置

通过`each()`或流式API遍历所有配置：

```groovy
// 遍历所有配置并打印名称
configurations.each { config ->
    println("配置名称：${config.name}，描述：${config.description}")
}

// 过滤可解析的配置
def resolvableConfigs = configurations.findAll { it.canBeResolved }
```

### 4. 检查配置是否存在

```groovy
if (configurations.names.contains("myConfig")) {
    println("myConfig存在")
}
```

### 5. 移除配置

```groovy
configurations.remove(configurations.findByName("oldConfig"))
```

## 三、Configuration的核心属性（通过容器管理）

`ConfigurationContainer`管理的`Configuration`对象有多个关键属性，决定了依赖的行为：

| 属性                | 作用                                                                 | 默认值  |
|---------------------|----------------------------------------------------------------------|---------|
| `canBeResolved`     | 是否允许解析（将依赖坐标转换为本地文件）                             | `false` |
| `canBeConsumed`     | 是否允许被其他项目消费（作为依赖提供）                               | `false` |
| `transitive`        | 是否传递依赖（依赖的依赖是否被包含）                                 | `true`  |
| `extendsFrom`       | 继承的其他配置（继承其所有依赖）                                     | 空集合  |
| `description`       | 配置的描述信息                                                       | `null`  |
| `visible`           | 是否在`buildEnvironment`等任务中可见                                 | `true`  |
| `attributes`        | 配置的属性（用于变体匹配，如Java版本、操作系统等）                   | 空集合  |

## 四、配置的类型与用途

通过`canBeResolved`和`canBeConsumed`的组合，`Configuration`可分为以下类型（由`ConfigurationContainer`管理）：

### 1. 可解析配置（Resolvable）

- 特征：`canBeResolved = true`，`canBeConsumed = false`。
- 用途：用于当前项目内部解析依赖（如编译、运行时需要的依赖文件）。
- 示例：`compileClasspath`（编译类路径）、`runtimeClasspath`（运行类路径）。

### 2. 可消费配置（Consumable）

- 特征：`canBeResolved = false`，`canBeConsumed = true`。
- 用途：供其他项目依赖时使用（暴露当前项目的输出给依赖者）。
- 示例：Java插件的`apiElements`（供编译时依赖）、`runtimeElements`（供运行时依赖）。

### 3. 双向配置（罕见）

- 特征：`canBeResolved = true` 且 `canBeConsumed = true`。
- 用途：极少使用，通常用于测试或特殊场景。

## 五、配置之间的继承关系

`ConfigurationContainer`支持配置通过`extendsFrom`继承其他配置的依赖，形成依赖复用。例如：

```groovy
// 定义基础配置
configurations.create("baseConfig") {
    dependencies {
        implementation "com.google.guava:guava:31.1-jre"
    }
}

// 自定义配置继承baseConfig
configurations.create("myConfig") {
    extendsFrom configurations.baseConfig
    canBeResolved = true
}

// myConfig将包含baseConfig的所有依赖
println("myConfig的依赖：${configurations.myConfig.dependencies}")
```

- 常见预定义继承：Java插件中，`api`继承自`implementation`，`compileClasspath`继承自`api`和`implementation`。

## 六、预定义配置（由插件提供）

`ConfigurationContainer`中的配置通常由插件（如Java、Android插件）预定义，无需手动创建。以**Java插件**为例，常用预定义配置包括：

| 配置名称           | 类型         | 用途                                  |
|--------------------|--------------|---------------------------------------|
| `implementation`   | 基础配置     | 编译和运行时依赖，不暴露给上层项目    |
| `api`              | 基础配置     | 编译和运行时依赖，暴露给上层项目（传递） |
| `compileClasspath` | 可解析       | 编译时需要的类路径（包含`api`/`implementation`等） |
| `runtimeClasspath` | 可解析       | 运行时需要的类路径（包含`implementation`等） |
| `testImplementation` | 基础配置   | 测试编译和运行时依赖                  |
| `apiElements`      | 可消费       | 供其他项目编译时依赖的输出（如类文件） |
| `runtimeElements`  | 可消费       | 供其他项目运行时依赖的输出            |

## 七、依赖管理实践

通过`ConfigurationContainer`管理的配置，可配合`dependencies`块添加依赖：

```groovy
// 给implementation配置添加依赖
dependencies {
    implementation "org.springframework:spring-core:5.3.20"
}

// 给自定义配置myConfig添加依赖
dependencies {
    myConfig "com.fasterxml.jackson:jackson-databind:2.13.3"
}
```

### 解析依赖文件

对`canBeResolved = true`的配置，可通过`files`获取依赖文件：

```groovy
// 获取runtimeClasspath配置中的所有依赖文件
def runtimeFiles = configurations.runtimeClasspath.files
runtimeFiles.each { file ->
    println("依赖文件：${file.absolutePath}")
}
```

## 八、高级特性

### 1. 配置属性（Attributes）

用于变体匹配（如多模块项目中，不同Java版本的依赖分离）：

```groovy
configurations.create("myConfig") {
    canBeResolved = true
    attributes {
        attribute(TargetJvmVersion.TARGET_JVM_VERSION, 11) // 指定依赖的JVM版本
    }
}
```

### 2. 依赖约束（Dependency Constraints）

通过配置限制依赖版本：

```groovy
configurations.implementation {
    constraints {
        implementation("com.google.guava:guava") {
            version {
                strictly "31.1-jre" // 强制使用该版本
            }
        }
    }
}
```

### 3. 排除依赖

在配置中排除不需要的传递依赖：

```groovy
configurations.implementation {
    exclude group: "org.slf4j", module: "slf4j-log4j12" // 排除特定依赖
}
```

## 九、最佳实践

1. **优先使用插件预定义配置**：如Java插件的`implementation`替代自定义配置，遵循约定优于配置。
2. **明确配置的可解析/可消费性**：避免滥用`canBeResolved = true`，仅对需要解析文件的配置开启。
3. **合理设计继承关系**：通过`extendsFrom`复用依赖，减少重复配置。
4. **避免过早解析**：配置解析（如`files`方法）会触发依赖下载，应在任务执行阶段（而非配置阶段）进行。
5. **使用最新Gradle版本**：新版本对配置管理有优化（如`api`/`implementation`替代旧的`compile`）。

## 总结

`ConfigurationContainer`是Gradle依赖管理的中枢，通过它可以灵活定义、组织和控制项目的依赖配置。理解其API、配置类型、继承关系及最佳实践，能帮助你构建清晰、高效的依赖管理体系。实际开发中，需结合具体插件（如Java、Android）的预定义配置，减少自定义配置的使用，同时合理利用继承和属性匹配满足复杂场景需求。
