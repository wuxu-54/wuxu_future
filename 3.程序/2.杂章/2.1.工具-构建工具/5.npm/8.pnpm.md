# pnpm

## 一、核心区别（分维度对比）

### 1. 底层安装机制（最核心差异）

| 特性                | npm (v3+)                          | pnpm                              |
|---------------------|------------------------------------|-----------------------------------|
| 依赖存储方式        | **扁平化安装**：将所有依赖（包括子依赖）平铺到`node_modules`根目录，重复依赖会多次复制。<br>例：A依赖lodash@1，B依赖lodash@2，`node_modules`会同时有lodash@1和lodash@2，各自独立存储。 | **硬链接+符号链接（软链接）**：<br>1. 全局缓存：所有项目共享一个全局依赖缓存（默认在`~/.pnpm-store`），同一个版本的依赖仅存储1份；<br>2. 项目内：`node_modules`中仅存放项目直接依赖的包（真实文件），子依赖通过**符号链接**指向全局缓存，避免重复复制。<br>例：多个项目用lodash@4，全局缓存仅存1份，所有项目通过链接引用。 |
| 通俗比喻            | 每个项目单独买一套同款工具，哪怕工具一样，也重复花钱/占空间。 | 所有项目共享一套工具库，用的时候只拿“快捷方式”，不重复买。 |

### 2. 磁盘空间占用

- **npm**：重复依赖会被多次复制到不同项目的`node_modules`，磁盘占用大。比如10个项目都用lodash@4，磁盘里会有10份lodash@4的文件。
- **pnpm**：同一个版本的依赖仅在全局缓存存1份，所有项目通过硬链接/符号链接引用，磁盘占用通常只有npm的1/5~1/10。

### 3. 安装速度

- **npm**：
  - 安装时需下载并复制依赖到项目`node_modules`，重复依赖会重复下载/复制；
  - 虽然后续版本（v7+）优化了速度，但仍远慢于pnpm。
- **pnpm**：
  - 首次安装：下载依赖到全局缓存，项目内仅创建链接，速度比npm快2~3倍；
  - 非首次安装：直接从全局缓存链接，无需重新下载，速度提升更明显（甚至快10倍以上）。

### 4. 依赖树与“幽灵依赖”

- **幽灵依赖**：项目未在`package.json`中声明，但能通过`require/import`引入的依赖（因npm扁平化安装，子依赖被平铺到根目录导致）。
  - **npm**：存在严重的幽灵依赖问题，比如项目依赖A，A依赖B，npm会把B平铺到`node_modules`根目录，项目能直接用B，但`package.json`中无声明，易导致部署/协作时依赖缺失。
  - **pnpm**：彻底解决幽灵依赖！`node_modules`中仅存在项目直接声明的依赖，子依赖不会平铺，无法直接引用未声明的依赖，保证依赖树的完整性和可预测性。

### 5. 锁文件与安全性

| 特性                | npm                          | pnpm                              |
|---------------------|------------------------------|-----------------------------------|
| 锁文件名称          | `package-lock.json`          | `pnpm-lock.yaml`（YAML格式，更易读） |
| 校验机制            | 仅校验依赖版本，完整性校验弱 | 强制校验依赖的`integrity`（哈希值），确保依赖包未被篡改，锁文件损坏会直接报错（如你之前遇到的`ERR_PNPM_TARBALL_INTEGRITY`） |
| 跨平台兼容性        | 锁文件易因换行符（CRLF/LF）出问题 | 锁文件默认强制LF格式，跨Windows/Mac/Linux更稳定 |

### 6. 功能特性对比

| 功能                | npm                          | pnpm                              |
|---------------------|------------------------------|-----------------------------------|
| 工作区（Monorepo）  | v7+支持，但配置复杂          | 原生支持，配置简单（`pnpm-workspace.yaml`），是Monorepo项目的首选 |
| 离线模式            | 弱，需手动缓存               | 强，`pnpm install --offline`可完全离线安装（依赖已在全局缓存） |
| 依赖过滤            | 无原生支持                   | 支持`pnpm add <pkg> --filter <project>`，精准给Monorepo子项目装依赖 |
| 别名依赖            | 需手动改`package.json`       | 原生支持`pnpm add alias@npm:pkg@version`，方便替换依赖版本 |
| 全局包管理          | `npm install -g`（易污染全局） | `pnpm add -g`（全局包也存缓存，且支持`pnpm dlx`临时运行包，无需安装） |

### 7. 兼容性

- **npm**：Node.js官方标配，兼容性100%，所有npm包都能正常安装（无兼容问题）。
- **pnpm**：完全兼容`package.json`和`npm`的语法，能直接替换npm使用；极少数老旧包因依赖路径写法不规范（依赖幽灵依赖），可能需要少量适配（如添加`.pnpmfile.cjs`），但99%的现代项目无问题。

## 二、适用场景建议

| 场景                  | 推荐选择 | 原因                                  |
|-----------------------|----------|---------------------------------------|
| 个人小项目/快速验证    | npm      | 无需额外安装，Node.js自带，足够用      |
| 大型项目/多项目（Monorepo） | pnpm | 速度快、省空间、无幽灵依赖，Monorepo支持好 |
| 团队协作项目          | pnpm     | 锁文件更严格，避免依赖不一致导致的“我本地能跑”问题 |
| 对磁盘/速度敏感（如低配机器） | pnpm | 磁盘占用少，安装速度快，提升开发效率  |

---

### 总结

1. **核心差异**：pnpm通过“硬链接+符号链接”实现依赖共享，解决了npm的磁盘占用大、速度慢、幽灵依赖三大痛点；
2. **安全性**：pnpm的锁文件校验更严格，能避免依赖篡改，但锁文件损坏时需手动修复（如删除重装）；
3. **选择原则**：小项目用npm（便捷），中大型/团队/Monorepo项目用pnpm（性能+稳定性更优），且pnpm完全兼容npm生态，迁移成本极低。

简单来说：pnpm是“更高效、更严谨的npm”，几乎保留了npm的所有功能，同时解决了它的核心缺点。
