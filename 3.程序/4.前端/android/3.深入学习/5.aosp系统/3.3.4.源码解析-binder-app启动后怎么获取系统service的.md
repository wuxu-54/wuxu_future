# 整体链路：App获取AMS服务 + 调用startActivity 完整拆解

我的理解：

1. 有个第三方进程进行服务管理：源码在ServiceManagerd的ServiceManagerNative，在native是封装好的Binder
2. APP与SystemServer都可以获取这个进程（本质也是通过IPC获取）
3. ServiceManager只有两个方法，注册service与获取service
4. APP通过ServiceManager获取SystemServer的IBinder，通过AIDL能力（即：`IActivityManager.Stub.asInterface`转换）获取获取代理对象进行方法调用
5. 那为什么Appliction也要继承IBinder呢？原因是在具体业务逻辑层，比如启动Activiy的Service，需要传入的一个Binder对象作为结果的回调。源码中就是一个caller。同理，任何类似业务都需要使用AIDL方式进行跨进程通信。

整体描述：

>
> 前提回顾：
> `ServiceManager` 是一个**特殊的Binder服务**（单独native进程），维护一个「名字 → Binder节点」注册表。
> AMS在SystemServer启动时，执行：`ServiceManager.addService("activity", mActivityManagerService)`，把AMS的Binder对象注册进去。

App进程起来后，代码：

```
// App内获取AMS
IActivityManager am = ActivityManager.getService();
// 然后发起调用
am.startActivity(...)
```

我们分**3大段**：

1. `ServiceManager.getService("activity")` 底层发生了什么（App向ServiceManager查AMS）
2. `asInterface` 把拿到的IBinder转为 IActivityManager.Proxy
3. App调用`proxy.startActivity()`，完整Binder IPC流程

## 1. ServiceManager.getService("activity")

`ServiceManager.getService()` 本身就是一次Binder IPC。
ServiceManager对外提供的Binder接口只有几个核心方法：

- `getService(String name)`：查询服务
- `addService(String name, IBinder binder)`：注册服务（AMS/WMS用这个）

### 源码：ServiceManager.java

```
public static IBinder getService(String name) {
    try {
        IBinder service = sCache.get(name);
        if (service != null) {
            return service;
        } else {
            // 【IPC调用 ServiceManager 的getService】
            return BinderInternal.getContextObject().transactGetService(name);
        }
    } catch (RemoteException e) {
        return null;
    }
}
```

1. 首先查本地缓存`sCache`，如果之前拿过AMS，直接返回，不用走IPC。
2. 没有缓存，就**跨进程调用ServiceManager进程的getService**（Binder IPC）。
   - App是客户端；ServiceManager进程是服务端。
   - 参数：传入字符串`"activity"`。
3. ServiceManager（注册表）内部查找：
 根据name=`activity`，找到AMS对应的**Binder节点**，把这个Binder节点引用，通过Binder驱动传回App进程。
4. Binder驱动在App进程这边**自动生成一个 BinderProxy 对象**，返回给App。>

> ⚠️ App拿到的返回值`IBinder`本质就是 `BinderProxy`，代表远端SystemServer里AMS的Binder对象。

>
> 重要：ServiceManager**只返回Binder引用，不返回AMS对象本身**；对象在SystemServer，App只有代理。

## 2. IActivityManager.Stub.asInterface(binder)

`ActivityManager.getService()` 内部完整代码：

```
public static IActivityManager getService() {
    return IActivityManager.Stub.asInterface(ServiceManager.getService("activity"));
}
```

把上一步拿到的`BinderProxy`传入`asInterface`，看AIDL生成的Stub里的asInterface：

```
public static IActivityManager asInterface(IBinder obj) {
    if (obj == null) return null;
    IInterface iin = obj.queryLocalInterface(DESCRIPTOR);
    if (iin != null) {
        // 同进程，直接返回本地Stub（App和AMS不同进程，不会进这里）
        return (IActivityManager) iin;
    }
    // 跨进程场景：new Proxy，把BinderProxy塞进去
    return new IActivityManager.Stub.Proxy(obj);
}
```

- obj：就是`BinderProxy`（来自ServiceManager返回）
- 跨进程，`queryLocalInterface`返回null
- 新建`Proxy`对象，保存`BinderProxy`，返回给App。

✅ 现在App拿到了 `IActivityManager` 接口的Proxy代理对象，**准备调用AMS的方法**。

## 3. App调用 `am.startActivity()` （Proxy内部逻辑）

Proxy类（AIDL自动生成）：

```
private static class Proxy implements IActivityManager {
    private IBinder mRemote; // 就是BinderProxy

    Proxy(IBinder remote) {
        mRemote = remote;
    }

    @Override
    public int startActivity(IApplicationThread caller, Intent intent, ...) throws RemoteException {
        Parcel _data = Parcel.obtain();
        Parcel _reply = Parcel.obtain();
        try {
            _data.writeInterfaceToken(DESCRIPTOR);
            // 把参数序列化写入Parcel
            _data.writeStrongBinder(caller);
            intent.writeToParcel(_data, 0);
            // =========发起IPC核心=========
            boolean status = mRemote.transact(TRANSACTION_startActivity, _data, _reply, 0);
            if (!status) throw new RemoteException();
            _reply.readException();
            int _result = _reply.readInt();
            return _result;
        } finally {
            _data.recycle();
            _reply.recycle();
        }
    }
}
```

### 逐步骤拆解这次IPC调用：

1. App主线程调用`proxy.startActivity()`
2. 创建Parcel：`_data` 存放**请求参数**；`_reply`用来接收远端返回结果
3. `writeStrongBinder(caller)`：如果传IBinder（比如IApplicationThread），Binder驱动负责跨进程传递Binder引用（这个就是attachApplication传递ApplicationThread的原理）
4. **`mRemote.transact()`**
 mRemote是BinderProxy，调用native方法，陷入内核Binder驱动，把下面三样东西打包发送：
   - transaction code：`TRANSACTION_startActivity`（方法编号）
   - _data：序列化好的参数
   - flags：0，代表双向调用，客户端阻塞等待返回

>
> 📌 **App线程在这里阻塞！** 等待AMS处理完，返回结果。

5. Binder驱动根据Binder节点，找到目标进程：SystemServer，唤醒SystemServer里的**Binder线程池**中的一条线程。
6. SystemServer进程，AMS的Stub（`IActivityManager.Stub`）的`onTransact`被驱动回调：

```
// AMS侧Stub onTransact
@Override
public boolean onTransact(int code, Parcel data, Parcel reply, int flags) {
    switch(code) {
        case TRANSACTION_startActivity:
            data.readInterfaceToken();
            // 读取参数
            IApplicationThread caller = IApplicationThread.Stub.asInterface(data.readStrongBinder());
            Intent intent = Intent.CREATOR.createFromParcel(data);
            // 调用AMS本地实现的startActivity
            int ret = startActivity(caller, intent, ...);
            reply.writeNoException();
            reply.writeInt(ret);
            return true;
    }
}
```

7. AMS执行业务逻辑：
   - 权限校验
   - 查询PMS解析Activity信息
   - 判断目标App进程是否存在
     - 不存在：走Zygote Socket创建新进程（前面讲的fork流程）
     - 已存在：直接通知App进程启动Activity
8. AMS把返回结果写入`reply`，onTransact返回true。
9. Binder驱动把reply数据传回App进程，App阻塞的`transact`函数返回。
10. App读取`_reply`里面的返回值，Parcel回收，`startActivity`调用结束，App线程解除阻塞继续跑。

# 4. 区分2次完全不同的Binder通信，不要混淆

1. **App ↔ ServiceManager**：`getService("activity")`
 目的：拿到AMS的BinderProxy。**只在第一次获取的时候走IPC，之后缓存复用。**
2. **App ↔ AMS**：`IActivityManager.startActivity()`
 目的：请求AMS启动Activity，每次调用都会IPC。

>
> ServiceManager**只负责查Binder引用，不参与后面startActivity业务调用**。拿到AMS代理之后，App直接和AMS通信，不再经过ServiceManager。

# 5. 缓存 sCache 的作用（ServiceManager里面）

ServiceManager.getService 有静态缓存`static HashMap<String,IBinder> sCache`

- 第一次getService：IPC去ServiceManager查询，拿到BinderProxy放入缓存。
- 后续再次调用`getService("activity")`：直接从缓存拿，**不再和ServiceManager通信**，减少IPC开销。

>
> 注意：缓存存的是BinderProxy引用。当远端服务进程crash，这个BinderProxy会失效，后续调用抛RemoteException。

# 6. 和你前面学习的ApplicationThread串起来

当App进程创建，`ActivityThread.attach()`的时候：

```
mAppThread = new ApplicationThread(); // App侧 IApplicationThread.Stub（服务端Binder）
IActivityManager am = ActivityManager.getService(); // 上面这套逻辑拿到AMS代理
am.attachApplication(mAppThread, startSeq); 
```

这里`attachApplication`的参数 `mAppThread` 是IBinder，在`writeStrongBinder`的时候，Binder驱动会把App本地的Stub（ApplicationThread）生成代理，传递到AMS进程。AMS保存这个IApplicationThread Proxy，后续AMS就可以主动IPC回调App。

# 完整时序合并（从App获取AMS到启动Activity）

```
App进程
├─ ActivityManager.getService()
│  ├─ ServiceManager.getService("activity")
│  │  ├─ 第一次：Binder IPC查询ServiceManager
│  │  └─ 返回AMS对应的BinderProxy，存入sCache
│  └─ IActivityManager.Stub.asInterface → 生成IActivityManager.Proxy
└─ proxy.startActivity()
    ├─ Parcel序列化参数
    ├─ BinderProxy.transact() 阻塞，进入Binder驱动
SystemServer（AMS）
    ├─ Binder线程池，AMS Stub.onTransact()
    ├─ AMS业务逻辑：校验，判断目标App进程不存在
    ├─ 通过Unix Socket通知Zygote fork新App进程
    └─ 处理完成，写回reply，返回给App
App进程解除阻塞
```

# 高频面试点

1. Q：getService是一次Binder调用吗？
A：是的。第一次调用会IPC访问ServiceManager；之后读取本地缓存，不IPC。
2. Q：ServiceManager拿到的是AMS对象吗？
A：不是，拿到的是Binder节点引用，App得到BinderProxy，只是代理。AMS对象在SystemServer。
3. Q：writeStrongBinder传递IBinder的时候，Binder驱动做了什么？
A：如果传递的是本地Stub（ApplicationThread），Binder驱动会在接收方进程创建对应的BinderProxy，实现跨进程传递Binder引用。
4. Q：如果AMS挂了，App拿到的BinderProxy会怎么样？
A：后续调用transact会抛出RemoteException；一般会注册DeathRecipient监听AMS死亡。

# 对比：

- `ServiceManager.addService`：服务端（AMS）主动注册Binder到注册表。
- `ServiceManager.getService`：客户端（App）查询注册表拿到远端BinderProxy。

如果你想，我们继续讲 **`writeStrongBinder`底层Binder引用传递**，这个是理解ApplicationThread怎么传给AMS的关键。
