# Binder驱动详细工作原理
>
> Binder驱动是一个Linux内核模块，文件节点`/dev/binder`。
> Binder的**内存管理、事务分发、线程调度、Binder节点/引用管理、死亡通知**全部由驱动实现。
> Java层、Native层的Binder（BBinder/BpBinder、BinderProxy）都只是用户态封装，真正IPC转发全部依赖驱动。

## 一、驱动初始化

内核加载binder驱动模块后：

1. 注册字符设备`/dev/binder`。
2. 定义`file_operations`：`open`、`mmap`、`ioctl`、`poll`等，用户态进程通过这几个入口和驱动交互。
3. 每一个进程打开`/dev/binder`，内核会为该进程创建一个 **`binder_proc`** 结构体，代表该进程在Binder驱动中的上下文。
    - `binder_proc`：进程维度信息，包含本进程所有`binder_ref`、内存映射信息、待处理事务队列、线程池信息。
4. 进程打开binder设备后，调用`binder_mmap`做内存映射：
    - 在**内核**分配一块内核缓冲区（默认1MB）；
    - 通过mmap，把这块内核缓冲区映射到**服务进程用户虚拟地址空间**；
    - 这块区域就是Binder通信的数据缓冲区，实现**一次拷贝**的核心。

> 每个进程独立拥有自己的binder_proc；每个进程独立映射一块内核buffer。

### 核心内核结构体（必须理解）

1. **`binder_proc`**：一个进程对应一个，保存该进程所有Binder相关状态
    - `refs`：该进程所有`binder_ref`（远端Binder引用）
    - `nodes`：该进程创建的所有`binder_node`（本进程发布的Binder服务节点）
    - `todo`：待处理事务队列（事务放到这里，等待Binder线程处理）
    - `wait`：等待队列，用来阻塞/唤醒Binder线程
2. **`binder_node`**：Binder服务节点
    > **服务对象本体在内核的代表，一个Binder服务（AMS Stub、ApplicationThread Stub）对应唯一binder_node，归属服务端的binder_proc**
    - 引用计数；
    - 归属哪个进程；
    - 保存用户态BBinder对象的地址；
3. **`binder_ref`**：Binder引用
    > 当进程A要使用进程B的`binder_node`，内核会在A的`binder_proc`里创建`binder_ref`，代表A对远端node的引用
    - `handle`：**客户端侧的整数句柄**，客户端只使用handle，不知道node；
    - 指向远端的`binder_node`；
    - 引用计数。

> 一句话记忆：
> `binder_node`：服务本体，在服务进程内核；
> `binder_ref+handle`：客户端这边对远端node的引用。

4. **`binder_thread`**：Binder线程
    服务端进程每一条Binder线程，在内核对应一个`binder_thread`。
    Binder线程循环阻塞在驱动，等待事务到来。线程池就是一堆`binder_thread`。

5. **`binder_transaction`**：Binder事务
    一次IPC调用，内核就构建一个`binder_transaction`，保存：
    - 源进程、目标进程
    - 目标handle（客户端），对应到binder_node
    - 数据缓冲区指针、事务flags（oneway、双向同步）
    - 用于同步返回的reply事务

## 二、进程打开Binder设备的流程（Server端，如SystemServer）

1. 用户态进程（SystemServer）调用`open("/dev/binder")`
2. 驱动`binder_open`：创建`binder_proc`，初始化队列
3. 用户态调用`mmap`（binder_mmap）
    - 内核分配内核buffer；
    - 将内核buffer映射到SystemServer的用户虚拟地址；
4. 用户态启动Binder线程池：线程调用`ioctl(BINDER_LOOPER_ENTER)`进入循环
    - 线程注册为`binder_thread`；
    - 调用`ioctl(BINDER_WAIT_FOR_WORK)`阻塞，进入等待队列，**等待事务**。

> Binder线程池所有线程都阻塞在内核，无事可做时休眠，有事务才被驱动唤醒。

## 三、客户端发起一次IPC（transact），驱动内部完整流程

Client：App进程；Server：SystemServer（AMS）

1. 用户态App调用`BinderProxy.transact()` → JNI → `ioctl(BINDER_TRANSACTION)`，进入内核。
    用户态已经把序列化数据写入Parcel，准备好事务信息：目标handle、code、data、flags。
2. 驱动创建`binder_transaction`事务。
3. 根据Client传入的handle，在**Client的binder_proc.refs**找到`binder_ref`，拿到远端`binder_node`。
    > handle是客户端本地编号，驱动通过ref找到真正的binder_node，找到归属的目标进程（SystemServer的binder_proc）。
4. **数据拷贝（唯一一次拷贝）**
    将App用户空间Parcel数据，**拷贝到内核缓冲区**。
    > 内核缓冲区已经mmap映射在SystemServer用户地址空间，服务进程直接读取这块内存，不再二次拷贝。
5. 将这个`binder_transaction`放入目标进程（SystemServer）的`proc->todo`待处理队列。
6. 驱动唤醒SystemServer中休眠的Binder线程池中的一条`binder_thread`。
7. 被唤醒的Binder线程，从todo队列取出`binder_transaction`。
8. 驱动回到用户态，回调BBinder的`onTransact`（Java层就是Binder Stub.onTransact），执行业务逻辑。

### 同步调用（flags=0，需要返回结果）

- 客户端的`binder_thread`在驱动内部阻塞，等待服务端返回reply事务。
- Server业务执行完成，构造reply事务，再次调用ioctl进入驱动。
- 驱动将reply数据传回客户端，唤醒客户端阻塞线程。
- 客户端transact返回，用户态继续执行。

### oneway异步调用

- 客户端提交事务后，**驱动直接返回，客户端线程不阻塞**；
- Server依旧在线程池串行处理；
- Server处理完**不会构造reply回包**。

> oneway只是客户端不阻塞，服务端todo队列依旧串行执行，不是并发。

## 四、跨进程传递Binder对象 writeStrongBinder（驱动如何处理Binder引用）

典型场景：`am.attachApplication(mAppThread)`
App把自己的ApplicationThread Stub传给AMS。

1. App用户态`writeStrongBinder(mAppThread)`写入Parcel。
2. 进入驱动，驱动识别这是一个本地`binder_node`（App进程内的BBinder）。
3. 在接收方（SystemServer）的`binder_proc`中新建`binder_ref`，分配一个新的handle。
4. 把这个handle写入事务数据，传给SystemServer。
5. SystemServer收到事务，读到这个handle，在本地构造`BinderProxy`，对应这个`binder_ref`。

> 本质：传递Binder对象，不是拷贝对象，只是**在内核目标进程创建引用**。
> 驱动自动维护引用计数；引用计数为0，自动释放节点资源。

## 五、引用计数管理（驱动负责）

`binder_node`和`binder_ref`都有引用计数。

- addref：增加引用；release：减少引用。
- 用户态调用`incStrong/decStrong`（native BBinder强引用）最终会通知驱动增减计数。
- 当`binder_node`引用计数降到0，驱动销毁node。
- 当`binder_ref`引用计数降到0，驱动销毁ref。

> 这就是Binder自动生命周期管理的底层，避免内存泄漏。

## 六、DeathRecipient 进程死亡通知底层原理

AMS监听App进程死亡，底层由Binder驱动实现：

1. Client（AMS）调用`linkToDeath`，注册死亡回调，通知驱动监听目标`binder_node`。
2. 驱动记录：AMS监听这个node归属的目标进程。
3. 如果App进程crash退出，内核销毁App的`binder_proc`，里面所有`binder_node`失效。
4. Binder驱动扫描所有监听这个node的客户端，主动往客户端投递**死亡事务**。
5. 客户端Binder线程收到死亡事务，回调`DeathRecipient.binderDied()`。

> 进程死亡检测，**是驱动主动推送**，不是客户端轮询。

## 七、Binder线程池在内核的调度逻辑

1. 服务进程启动时，预先创建多条线程，进入`BINDER_LOOPER`循环，调用`BINDER_WAIT_FOR_WORK`阻塞在内核。
2. 驱动收到IPC事务，放到目标进程`todo`队列。
3. 如果有休眠线程，唤醒其中一条线程去处理todo中的事务。
4. 线程处理完一个事务，再次进入循环阻塞，等待下一个任务。
5. 线程池上限默认16个；驱动不会无限创建线程。

> 注意：todo队列是每个进程独立。同一个进程所有Binder事务排队在本进程todo队列，由本进程线程池消费。
> ServiceManager是特例：只有**单条Binder线程**，todo队列串行处理addService/getService。

## 八、Binder mmap 一次拷贝的详细拆解

传统IPC：用户A → 内核buffer拷贝1次；内核buffer→用户B拷贝2次。

Binder：

1. Server进程打开binder后mmap，**内核分配一块物理内存，映射到内核地址 和 Server用户虚拟地址**。
2. Client发起IPC：将用户态数据拷贝到这块内核buffer（**唯一一次拷贝**）。
3. Server的用户虚拟地址直接映射这块物理内存，Server可以直接读取，**不需要拷贝**。

⚠️ 重点误区：

- mmap只在**服务端**建立映射；客户端没有映射这块内存。
- 数据只能从client用户空间拷贝到内核。
- 缓冲区上限1MB，是这块内核buffer的大小，超出抛出`TransactionTooLargeException`。

## 九、ioctl 是用户态和驱动交互的入口

所有用户态与Binder驱动交互，都通过ioctl命令：

- `BINDER_WAIT_FOR_WORK`：线程阻塞等待事务
- `BINDER_TRANSACTION`：发起IPC事务
- `BINDER_LOOPER_ENTER`：注册进入looper循环（Binder线程）
- `BINDER_GET_NODE_INFO`、引用计数相关命令、死亡通知相关命令等。

ioctl是系统调用，触发从用户态切换到内核态。

## 十、一次完整同步IPC的全链路汇总（用户态 ↔ Binder驱动）

```
【Client 用户态】
BinderProxy.transact → JNI → ioctl(BINDER_TRANSACTION)
        ↓（陷入内核）
【Binder驱动】
1. 构建 binder_transaction
2. 通过handle找到binder_node，找到目标Server进程binder_proc
3. Client用户数据拷贝到内核buffer（唯一拷贝）
4. 将事务放入Server进程todo队列
5. 唤醒Server侧休眠的binder_thread
6. Client线程阻塞，等待reply事务
        ↓
【Server 内核】
binder_thread取出todo里的事务
        ↓（切回Server用户态）
BBinder.onTransact（Java Stub.onTransact）执行业务，写reply
        ↓（再次ioctl进入驱动）
【Binder驱动】
将reply打包，投递回Client，唤醒阻塞的Client线程
        ↓（切回Client用户态）
transact返回，继续执行
```

## 十一、驱动层面常见问题

1. **TransactionTooLarge**：传输数据超过mmap映射的内核buffer上限1MB。
2. **Binder线程阻塞（ANR）**：Server端Binder线程在onTransact卡住（锁、耗时操作），todo队列堆积，新IPC请求无法处理，客户端一直阻塞超时ANR。
3. Binder内存泄漏：Binder引用计数没有释放，binder_ref/node无法被驱动回收。
4. 驱动日志`binder: failed to allocate transaction`：内核内存不足。

## 十二、一句话总结Binder驱动

Binder驱动是内核模块，维护每个进程`binder_proc`、`binder_node`、`binder_ref`；管理mmap缓冲区实现一次内存拷贝；接收用户态ioctl提交的事务，投递到目标进程todo队列，唤醒Binder线程；自动管理引用计数、进程死亡通知；**驱动不解析业务数据，只负责转发、调度、内存管理**。
