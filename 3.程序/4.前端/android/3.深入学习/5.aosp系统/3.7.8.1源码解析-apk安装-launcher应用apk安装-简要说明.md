# launcher 安装升级

**Launcher本身就是一个普通Android App（系统预置App），它自己的安装/更新，完完全全走咱们前面讲的7阶段APK安装全流程（包含V2/V3签名校验）；**
**但Launcher的角色是【接收PMS的包变更广播，去查询PMS获取其他App的包信息】，Launcher**不参与**别的App的安装解析、签名校验流程。**

## 一、Launcher自己的安装&更新（Launcher作为被安装的APK）

Launcher（AOSP Launcher3、厂商定制桌面）本质是APK，分两种场景：**出厂预置**、**后续OTA/应用市场更新**。

### 1）出厂预置（刷机时放入system/priv-app）

开机的时候，PMS在开机扫描分区，扫描`system/priv-app/Launcher3/Launcher3.apk`：

1. PackageParser解析这个APK；
2. PMS做V2/V3签名校验（系统签名）；
3. 分配UID、权限预处理；
4. installd部署，dex2oat；
5. PMS写入mPackages内存缓存、packages.xml；
6. 发送`PACKAGE_ADDED`广播。>

> 预置系统应用**不是通过PackageInstaller安装**，是开机PMS扫描系统分区加载，**但解析、签名校验、dex2oat逻辑完全一样**。
> 预置系统App的特点：放在system分区；更新后会在/data分区存放updated-package；可以卸载更新，恢复回原厂版本。

### 2）Launcher后续升级（OTA、应用商店更新Launcher APK）

**和普通App更新完全一模一样，完整走7阶段安装流程：**

1. 下载Launcher新版APK，放到`/data/app-staging`；
2. PackageParser解析Launcher的AndroidManifest；
3. PMS执行V2/V3签名校验：**系统预置的Launcher升级，新版APK必须和原系统签名一致，或者使用V3证书轮换**；
4. PMS判断是覆盖升级，**复用原有UID，保留桌面布局、图标位置、用户设置（/data/data）**；
5. installd移动APK、提取so、dex2oat；
6. PMS更新内存缓存+packages.xml；
7. PMS发送`PACKAGE_REPLACED`广播，**这个广播会发给Launcher自己**。

>
> 关键点：更新Launcher APK的时候，**PMS会杀死旧Launcher进程**，安装完成后，系统重新拉起新版Launcher。

>
> 面试高频：系统预置App更新之后，packages.xml里面会出现`<updated-package>`标签，记录/data分区的更新版本，原始APK仍然保存在system分区。卸载更新，就删掉/data里这个新版本，回退到system分区原厂Launcher。

## 二、Launcher如何获取**其他App**的包信息（图标、名称、Launcher入口Activity）

>
> 注意：别的App安装，PMS走完7阶段，发送广播；Launcher只是**监听者，不是安装参与者**。

### 1. 两种时机获取包信息

#### 时机1：手机开机，Launcher第一次启动

Launcher启动后，直接调用`PackageManager`（Binder跨进程调用PMS），拉取**所有已安装应用列表**：

```
pm.getInstalledPackages()
pm.queryIntentActivities(Intent(Intent.ACTION_MAIN, Intent.CATEGORY_LAUNCHER))
```

- queryIntentActivities：查询所有包含`LAUNCHER` category的Activity；
- 拿到ResolveInfo/ApplicationInfo；
- `loadLabel(pm)`：获取应用名称；
- `loadIcon(pm)`：获取应用图标；
- 缓存到Launcher自己的本地数据库（桌面数据库，保存图标位置、文件夹信息）。

>
> ⚠️ 图标、label不是Launcher自己解析APK！**PMS的mPackages缓存里已经提前存好了应用资源ID，PackageManager接口直接读取，不需要重新解析APK**。

#### 时机2：新App安装/卸载/更新，PMS发送广播（就是前面阶段7的广播）

PMS在别的App安装成功后，发送：

- 新增App：`ACTION_PACKAGE_ADDED`
- App更新：`ACTION_PACKAGE_REPLACED`
- 卸载App：`ACTION_PACKAGE_REMOVED`

Launcher静态注册接收这个广播：

1. 收到广播，拿到`package:xxx`的包名；
2. Launcher调用PackageManager，向PMS查询该包的信息（label、icon、LAUNCHER Activity）；
3. 更新Launcher自己的本地桌面数据库；
4. 刷新UI，新增/更新/移除桌面图标。

### 2. 核心要点（面试重点）

1. **广播本身不带图标、应用名称**，广播只通知【包状态变化】；所有应用信息都需要Launcher主动跨进程向PMS查询。
2. PMS的`mPackages`全局内存缓存是数据源；PackageManager只是Binder接口，是Launcher和PMS之间的桥梁。
3. Launcher有自己独立的本地数据库：记录图标摆放位置、文件夹、widget信息；**这个数据库是Launcher私有，和PMS/packages.xml无关**。PMS只管包信息，不管桌面布局。
4. 如果App没有`<activity>`带`android.intent.category.LAUNCHER`，就算安装成功，Launcher查询不到，桌面不会生成图标（SDK、后台服务类应用）。

## 三、容易混淆的两个场景区分（必背）

1. **Launcher作为被安装的APK**：走完整APK安装流程，PMS、PackageParser、V2/V3签名校验、installd全部参与。
2. **Launcher作为桌面，监听别的App**：**不参与安装流程**；只监听PMS发出的包变更广播，调用PackageManager查询PMS的包缓存，更新桌面图标。

## 四、高频面试追问

### Q1：安装新App的时候，是Launcher解析APK校验签名吗？

A：**不是**。APK解析、V2/V3签名校验全部是PMS（system_server）做。Launcher只是接收PMS广播，查询结果展示图标。

### Q2：更新Launcher的时候，签名校验规则是什么？

A：和普通覆盖升级规则一致。原厂预置Launcher是系统签名；新版APK必须：

- V2方案：新版公钥和原厂系统公钥完全一致；
- V3方案：可以配置证书轮换链表，允许更换证书。
签名不匹配直接报`INSTALL_FAILED_UPDATE_INCOMPATIBLE`。

### Q3：Launcher的图标缓存，是PMS管理的吗？

A：**不是**。PMS只保存应用基础包信息、资源ID；图标位图、桌面图标摆放位置，是Launcher自己的数据库维护。

### Q4：开机的时候，为什么桌面能一次性展示所有App图标？

A：开机PMS提前扫描所有应用，把包信息加载进mPackages缓存；Launcher启动后一次性通过PackageManager批量查询PMS缓存，不用逐个解析APK。

## 时序简图（新App安装，Launcher侧视角）

```
PMS完成该App完整7阶段安装
    ↓
PMS发送 ACTION_PACKAGE_ADDED 系统广播
    ↓
Launcher收到广播，拿到包名
    ↓
Launcher Binder调用 PackageManager，向PMS查询该包ApplicationInfo、Launcher Activity、icon、label
    ↓
Launcher更新自己本地桌面数据库
    ↓
UI刷新，桌面出现新图标
```

# Launcher **本质就是普通App**

1. Launcher **本质就是普通App**（只是预置在系统分区，拥有部分特殊权限）；
2. 所有App名称、图标、启动Activity信息，**Launcher都要主动跨进程通过PackageManager向PMS查询，广播只做事件通知，不带任何包数据**。

## 1. Launcher：它是普通App，特殊点在哪？

从Android框架视角：

>
> Launcher = 一个有`HOME` intent-filter的普通Android应用，遵循Android App所有生命周期、沙盒、Binder通信规则。

### ✅ 和普通App一样的地方

- 有自己的`AndroidManifest.xml`、自己的进程、独立UID、私有`/data/data`目录；
- 进程会被系统杀掉、会重启；
- 它不能直接读取`packages.xml`（`/data/system/packages.xml`权限是system_server独有，普通App包括Launcher**没有权限直接读这个文件**）；
- **不能直接访问PMS内部的mPackages内存HashMap**，必须走`PackageManager` Binder接口跨进程通信拿数据。

>
> 重点：`PackageManager`是应用层API，底层是`IPackageManager` Binder代理，通信对端就是system_server里面的PMS。Launcher和微信、抖音调用PackageManager，底层机制完全一样。

### ⚠️ 仅有的少量特殊能力（不是特权后门）

1. Manifest里配置了：

```
<intent-filter>
    <action android:name="android.intent.action.MAIN" />
    <category android:name="android.intent.category.HOME" />
    <category android:name="android.intent.category.DEFAULT" />
</intent-filter>
```

系统识别它为默认桌面，按HOME键会拉起它。
2. 一般放在`system/priv-app`目录，拥有**privileged权限**（部分普通第三方App拿不到的权限，比如读取已安装应用列表，新版Android普通App需要QUERY_ALL_PACKAGES）；
3. 可以接收`PACKAGE_ADDED / PACKAGE_REPLACED / PACKAGE_REMOVED`这类系统包变更广播（普通App高版本有限制）。

>
> 但是！**特权只影响能不能调用接口，不会绕过Binder，不能直接访问PMS内存、packages.xml**。

## 2. 为什么必须Launcher主动跨进程查询？广播为什么不带包信息？

PMS发送的`ACTION_PACKAGE_ADDED`广播，Intent只携带一个Uri：`package:com.xxx.app`，**只有包名字符串**。

### 设计原因

1. **数据量大**：图标是图片，label是字符串，还有Activity、intent-filter一大堆信息。如果广播把所有App信息塞进去，广播数据会非常庞大，广播是IPC消息，容易造成内存、性能问题；
2. **权限校验**：当Launcher调用PackageManager接口查询包信息时，PMS在system_server内部**做权限校验**，判断当前调用进程（Launcher的UID）是否有权限读取这个应用信息；
3. **数据统一源头**：唯一数据源是PMS的`mPackages`缓存。所有应用（包括Launcher）统一向PMS查询，保证全系统包信息一致；
4. 广播只是**事件通知**：「有个包变了，你自己来查详情」。

## 3. 两个场景：Launcher拉取应用信息

### 场景1：手机开机，Launcher第一次启动

1. Launcher进程启动；
2. Launcher调用 `pm.queryIntentActivities()`，查询所有带`MAIN + LAUNCHER`的Activity；
3. Binder调用进入system_server，PMS遍历自己内存里`mPackages`和组件Intent Filter索引；
4. PMS返回ResolveInfo列表（包含ApplicationInfo，资源id）；
5. Launcher拿到结果，调用`applicationInfo.loadIcon(pm)` / `loadLabel(pm)`
   - loadIcon内部仍然继续通过PackageManager Binder请求PMS的AssetManager，读取对应APK资源；
6. Launcher把图标、名称、包名、启动Activity保存到**Launcher自己本地SQLite数据库**（存放图标位置、文件夹、widget）；
7. 加载数据库，渲染桌面UI。

>
> 注意：PMS在安装阶段已经提前解析好了资源ID，**查询时不需要重新解析APK**，直接返回预存的资源ID。

### 场景2：新App安装完成，PMS发广播

1. PMS安装流程走完，发送`ACTION_PACKAGE_ADDED`广播；
2. Launcher的BroadcastReceiver收到广播，取出包名；
3. Launcher发起Binder调用，`getApplicationInfo` / `queryIntentActivities`查询该包；
4. PMS返回这个App信息；
5. Launcher更新自己本地数据库，刷新桌面图标。

## 4. 高频面试点（精简）

1. Launcher是**普通App**，只是带HOME属性、priv-app特权，**不能直接读取packages.xml，不能直接访问PMS的mPackages**。
2. 包变更广播只传递**包名**，不携带图标、应用名称、组件信息。
3. 所有应用信息，Launcher都必须通过`PackageManager`跨进程Binder向PMS主动查询，和第三方App调用PackageManager机制一致。
4. Launcher本地数据库只存**桌面布局、图标缓存**，**不保存系统完整包元数据**；系统权威数据源永远是PMS。
5. PMS负责解析APK、签名校验、维护全系统应用信息；Launcher只负责展示图标和启动应用，**不参与任何APK安装校验逻辑**。

## 5. 容易踩坑的误区

❌ 误区：Launcher权限很高，可以直接读packages.xml
✅ 正解：`/data/system/`目录只允许system_server访问，Launcher进程UID是普通app uid，没有读权限。

❌ 误区：广播会把图标一起传给Launcher
✅ 正解：广播只有事件+包名；图标资源需要Launcher主动IPC查询。

❌ 误区：Launcher会解析APK拿图标
✅ 正解：解析APK、资源提取是PMS安装阶段一次性完成；Launcher只是远程查询PMS缓存的资源ID。
