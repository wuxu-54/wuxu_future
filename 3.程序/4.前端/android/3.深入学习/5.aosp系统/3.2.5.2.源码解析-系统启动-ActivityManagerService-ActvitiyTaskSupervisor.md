# ActivityTaskSupervisor（ATSupervisor，Android10+，前身ActivityStackSupervisor）
>
> 一句话定位：**ATMS 内部的 Activity/Task 调度总指挥，负责协调页面切换、生命周期流转、进程状态判断；ActivityStarter 负责“决定创建哪个Activity/Task”，ActivityTaskSupervisor负责“调度页面跑起来、管理栈焦点与状态流转”**

## ✅ 主要功能

### 1. Activity 启动调度（最核心，你前面看的startSpecificActivity）

- `startSpecificActivity()`：入口，**判断目标应用进程是否存活**
  - 进程存在：调用`realStartActivityLocked`，组装`ClientTransaction`，通过IApplicationThread通知App进程启动Activity
  - 进程不存在：通知ATMS去fork Zygote创建应用进程；进程就绪后再次回来执行启动
- 强制前置检查：**等待上一个Activity pause完成**，保证页面切换时序不乱；pause没完成就延后重试

### 2. 页面焦点 & Task/Stack 切换管理

- 管理全局Task、Activity栈的**焦点、前台后台状态**，决定哪个Task/Activity是当前用户可见
- 处理页面resume/pause流转：前台页面resume，旧前台页面pause；多窗口、分屏场景下多Task焦点调度
- 管理栈的层级、Task顺序，控制任务切换、返回导航的页面出栈逻辑

### 3. 应用进程状态协同

- 通过`WindowProcessController`监控App进程存活状态
- 进程crash时，处理Activity清理、栈恢复；进程重启后恢复页面
- 区分冷启动（新建进程）、热启动（进程复用）两种场景

### 4. 生命周期事务分发（ClientTransaction）

- `realStartActivityLocked`构造`ClientTransaction`事务，打包LaunchActivityItem、ResumeActivityItem
- 交给`LifecycleManager`，一次性Binder下发到App端ActivityThread，驱动onCreate/onStart/onResume

> Android P之后，不再是多次单独binder调用，而是事务批量下发，减少IPC

### 5. 处理返回、finish、页面销毁逻辑

- Activity调用finish后，ATSupervisor调度页面pause、stop、destroy，调整Task栈
- 页面退出后，恢复栈中下一个Activity到前台

### 6. 多任务/多窗口支持

- 负责分屏、自由窗口下多Task的调度，管理多个Stack、Task之间的页面切换、焦点抢占

## 📌 和ActivityStarter的区分（面试高频）

1. **ActivityStarter**：**决策层**。解析Intent、launchFlags、launchMode；决定新建Task还是复用已有Task，生成ActivityRecord；**只做“要不要创建、放哪个task”**
2. **ActivityTaskSupervisor**：**调度执行层**。拿到ActivityRecord后，判断进程、协调pause/resume、发送ClientTransaction、控制页面生命周期流转；**负责“能不能跑、怎么跑起来”**

## 📌 和ATMS的关系

`ActivityTaskManagerService`持有`mTaskSupervisor`，ATMS对外提供Binder接口，**复杂栈调度、页面生命周期流转委托给ActivityTaskSupervisor**。

## 面试精简背诵版
>
> ActivityTaskSupervisor是ATMS的核心调度器，负责Activity启动调度、页面焦点与Task栈切换、进程存活判断；协调Activity pause/resume生命周期，组装ClientTransaction下发给App进程，处理页面finish和进程崩溃恢复；ActivityStarter负责决定Activity放哪个Task，ATSupervisor负责调度页面真正启动和切换。

## realStartActivityLocked 发送消息到 ActivityThread（Android P+）
>
> 核心：**不再是多次Binder单独调用scheduleLaunchActivity，而是打包成 ClientTransaction，一次性通过 IApplicationThread Binder 发送给App进程**

### 1. 拿到Binder对象：IApplicationThread

`proc = WindowProcessController`

```java
// proc.getThread() → IApplicationThread（AIDL接口，Binder代理）
final ClientTransaction clientTransaction = ClientTransaction.obtain(proc.getThread(), r.token);
```

- App进程里：`ApplicationThread extends IApplicationThread.Stub`（Binder服务端，ActivityThread内部类）
- system_server（ATMS/ATSupervisor这边）拿到的是 **IApplicationThread 代理Proxy**，跨进程通信载体
- 在AMS绑定APP的IApplicationThread时，将其代理设置给WindowProcessController的。所以WindowProcessController可以直接取到Binder代理对象。（Android12以后新版本在SystemService里都通过ClientTrancsaction类向APP发送消息，避免多次IPC操作，原来是通过scheduleActivity方法）

### 2. 组装事务 ClientTransaction

ClientTransaction 可以一次性打包多个生命周期动作（TransactionItem）

```java
// 添加启动Activity的动作：LaunchActivityItem
clientTransaction.addTransactionItem(LaunchActivityItem.obtain(...));

// 如果andResume=true，再加ResumeActivityItem
if (andResume) {
    clientTransaction.addTransactionItem(ResumeActivityItem.obtain());
}
```

> LaunchActivityItem：对应App端 `handleLaunchActivity`（onCreate、onStart）
> ResumeActivityItem：对应App端 `handleResumeActivity`（onResume）

### 3. ClientLifecycleManager.scheduleTransaction 发起Binder调用

```java
mService.getLifecycleManager().scheduleTransaction(clientTransaction);
```

`ClientLifecycleManager` 内部：

```java
void scheduleTransaction(ClientTransaction transaction) throws RemoteException {
    final IApplicationThread client = transaction.getClient();
    // ✅ Binder跨进程调用！！
    client.scheduleTransaction(transaction);
}
```

👉 **IApplicationThread.scheduleTransaction(ClientTransaction)** 是AIDL方法，把整个事务一次性传给App进程

> Android 8及更早版本：直接调用 `app.thread.scheduleLaunchActivity(xxx)`，单独Binder调用；Android P重构为ClientTransaction事务模型

老版本是以下方式，进行两次ipc通信。

```java
// ========== 重点！没有ClientTransaction！直接调用app.thread的Binder方法 ==========
    app.thread.scheduleLaunchActivity(
            new Intent(r.intent),
            r.appToken,
            System.identityHashCode(r),
            r.info,
            // ...一大堆参数：configuration、referrer、options等
            r.mergedConfig,
            r.compat,
            r.info.applicationInfo,
            r.packageName,
            r.task.voiceInteractor,
            app.getProfilerInfo()
    );

    // 如果andResume=true，**再单独一次Binder调用！**
    if (andResume) {
        app.thread.scheduleResumeActivity(r.appToken, ...);
    }
```

### 4. App进程：ApplicationThread收到Binder调用

App进程的 `ApplicationThread`（Binder服务端）收到 `scheduleTransaction`：

```java
@Override
public void scheduleTransaction(ClientTransaction transaction) {
    // ApplicationThread运行在App的Binder线程池，不能直接操作UI
    ActivityThread.this.scheduleTransaction(transaction);
}
```

### 5. ActivityThread → 交给主线程Handler执行

```java
// ActivityThread.java
void scheduleTransaction(ClientTransaction transaction) {
    transaction.preExecute(this);
    // 发送消息到主线程 H Handler
    sendMessage(ActivityThread.H.EXECUTE_TRANSACTION, transaction);
}
```

- H 是ActivityThread主线程Handler；
- 主线程收到 `EXECUTE_TRANSACTION`，用`TransactionExecutor`按顺序执行事务里面所有Item：
    1. LaunchActivityItem → `handleLaunchActivity` → new Activity，onCreate / onStart
    2. ResumeActivityItem → `handleResumeActivity` → onResume

### 完整链路（一句话串起来）

```
ActivityTaskSupervisor.realStartActivityLocked
    → 构造ClientTransaction（Launch+Resume）
    → ClientLifecycleManager
    → IApplicationThread（Binder Proxy）.scheduleTransaction() 【跨进程Binder】
    → App进程 ApplicationThread（Binder服务端）收到
    → ActivityThread发送 EXECUTE_TRANSACTION 消息到主线Handler
    → TransactionExecutor执行Launch/Resume生命周期回调
```

ActivityThread是继承了ClientTransactionHandler类，这个父类有做事务解析执行的操作。

```java
// ClientTransactionHandler.java 抽象父类
public abstract class ClientTransactionHandler {
    // 这个就是你找不到的scheduleTransaction！
    void scheduleTransaction(ClientTransaction transaction) {
        transaction.preExecute(this);
        sendMessage(ActivityThread.H.EXECUTE_TRANSACTION, transaction);
    }
    // 还有sendMessage是抽象方法，由子类ActivityThread实现
    protected abstract void sendMessage(int what, Object obj);
}
```

### 面试要点

1. 通信载体：**IApplicationThread AIDL Binder**；ATMS在system_server，ActivityThread在app进程
2. P版本最大改动：**ClientTransaction批量事务**，合并多次Binder调用，减少IPC次数
3. Binder线程不能操作UI：收到事务后，**抛消息到ActivityThread主线Handler**，再执行onCreate/onResume
4. 异常：Binder调用抛出RemoteException，代表App进程已死亡，回到startSpecificActivity，去fork新进程

### 对比旧版本（Android O及以下）

旧版本没有ClientTransaction：

```java
// 老代码，直接Binder调用scheduleLaunchActivity
app.thread.scheduleLaunchActivity(intent, token,...);
```

每一次生命周期都单独一次Binder，效率低，Android P重构。

## Android O（8.x）及更早：**没有 ClientTransaction**，AMS/ActivityStackSupervisor 直接多次 Binder 调用 IApplicationThread
>
> 旧版本类名：**ActivityStackSupervisor**（Android10 才改名叫 ActivityTaskSupervisor）
> 旧版本进程对象：**ProcessRecord**（没有 WindowProcessController，WPC是Android10新增拆分出来的）

### 1. 旧版 realStartActivityLocked 核心代码（Android8.1）

```java
// ActivityStackSupervisor.java
final boolean realStartActivityLocked(ActivityRecord r, ProcessRecord app,
        boolean andResume, boolean checkConfig) throws RemoteException {

    // 同样先要等上一个Activity pause完成，和新版逻辑一致
    if (!allPausedActivitiesComplete()) {
        return false;
    }

    // ========== 重点！没有ClientTransaction！直接调用app.thread的Binder方法 ==========
    app.thread.scheduleLaunchActivity(
            new Intent(r.intent),
            r.appToken,
            System.identityHashCode(r),
            r.info,
            // ...一大堆参数：configuration、referrer、options等
            r.mergedConfig,
            r.compat,
            r.info.applicationInfo,
            r.packageName,
            r.task.voiceInteractor,
            app.getProfilerInfo()
    );

    // 如果andResume=true，**再单独一次Binder调用！**
    if (andResume) {
        app.thread.scheduleResumeActivity(r.appToken, ...);
    }

    return true;
}
```

- `app.thread`：就是 `IApplicationThread`（和新版一样，App attachApplication传上来保存在ProcessRecord）
- **没有打包事务，每一个生命周期动作都是独立的Binder IPC**
  1. `scheduleLaunchActivity()` 一次Binder → App端执行`onCreate`、`onStart`
  2. 如果需要resume，再来一次Binder `scheduleResumeActivity()` → `onResume`

> Android P 引入 ClientTransaction，就是为了解决**多次Binder调用**的问题，把多个生命周期打包成一次IPC。

### 2. App进程这边：ApplicationThread收到单独的AIDL方法

旧版 IApplicationThread.aidl 是分开定义多个接口，不是统一的scheduleTransaction

```aidl
// IApplicationThread.aidl（O及更早）
interface IApplicationThread {
    void scheduleLaunchActivity(Intent intent, IBinder token, int ident, ...);
    void scheduleResumeActivity(IBinder token, boolean isForward, ...);
    void schedulePauseActivity(IBinder token, boolean finished, boolean userLeaving, ...);
    void scheduleStopActivity(IBinder token, boolean showWindow, ...);
    // 一堆独立的生命周期方法
}
```

App进程的 ApplicationThread（Binder服务端）：

```java
@Override
public void scheduleLaunchActivity(Intent intent, IBinder token, int ident, ...) {
    // Binder线程收到，发送消息到ActivityThread主线H Handler
    sendMessage(H.LAUNCH_ACTIVITY, ...);
}

@Override
public void scheduleResumeActivity(IBinder token, boolean isForward, ...) {
    sendMessage(H.RESUME_ACTIVITY, ...);
}
```

ActivityThread的H Handler，收到不同消息，分别处理：

- LAUNCH_ACTIVITY → handleLaunchActivity → onCreate / onStart
- RESUME_ACTIVITY → handleResumeActivity → onResume

### 3. 旧版完整调用链路对比新版

#### 旧版（Android O-，ActivityStackSupervisor）

```
AMS.startActivity
→ ActivityStarter
→ ActivityStackSupervisor.startSpecificActivityLocked
    → realStartActivityLocked
        → app.thread.scheduleLaunchActivity() 【Binder #1】
        → if(andResume) app.thread.scheduleResumeActivity() 【Binder #2】
```

> **两次独立IPC**

#### 新版（Android P+ ATMS / ActivityTaskSupervisor）

```
ATMS.startActivity
→ ActivityStarter
→ ActivityTaskSupervisor.startSpecificActivity
    → realStartActivityLocked
        → 构建ClientTransaction，加入Launch+Resume Item
        → mService.getLifecycleManager().scheduleTransaction()
        → mClient.scheduleTransaction(transaction) 【仅1次Binder】
```

> **一次IPC，批量执行多个生命周期**

### 4. 旧版没有这些东西

1. ❌ ClientTransaction / ClientTransactionItem / LaunchActivityItem / ResumeActivityItem
2. ❌ ClientLifecycleManager
3. ❌ WindowProcessController，使用 `ProcessRecord`，`ProcessRecord.thread` 保存IApplicationThread
4. ❌ IActivityClientController（这个是Android12以后再加的）
5. ❌ TransactionExecutor；主线程Handler是一堆独立Message类型（LAUNCH_ACTIVITY、PAUSE_ACTIVITY等）

### 5. 新旧核心差异面试背诵

1. **O及更早**：IApplicationThread定义一堆独立生命周期AIDL方法，**每一步生命周期一次Binder调用**；AMS直接调用scheduleLaunchActivity、scheduleResumeActivity。ActivityThread H Handler收到不同类型Message分别处理。
2. **P及以后**：废弃一堆单独AIDL，只保留`scheduleTransaction(ClientTransaction)`；多个生命周期打包进事务对象，**一次Binder**传到App，App端TransactionExecutor串行执行事务里面所有Item。

### 6. 额外：旧版的pause也是单独Binder

比如上一个页面Pause：

```java
app.thread.schedulePauseActivity(r.appToken, ...); // 单独一次Binder
```

每一次pause/stop/destroy都是单独IPC，页面切换频繁时Binder开销大，这就是P版本重构的动机。
