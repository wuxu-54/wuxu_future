# LoadedApk 是什么？一句话概括

`LoadedApk`：**代表在当前进程里，已经被加载进内存的一个APK包的管理对象**，是重量级包信息容器。
> 名字直译：**已经加载完毕的APK**。
> 一个进程可以有多个LoadedApk（比如Instrumentation测试：被测App + 测试Runner两个APK，就有2个LoadedApk）

## LoadedApk里面存了哪些核心东西（核心职责）

1. **ClassLoader（PathClassLoader）**
    APK里dex代码的类加载器，`new Application`、`new Activity`、`new Service`全部靠它加载类。**这是最重要成员**。
2. **Resources / AssetManager**
    资源管理器，加载res资源、图片、布局、字符串，读取APK里resources.arsc。
3. **ApplicationInfo**
    包名、uid、版本、sourceDir（APK文件路径）、native库路径、签名信息等清单信息。
4. **Application实例缓存 mApplication**
    `makeApplication()` 方法负责创建Application对象，并且缓存，保证**一个APK在进程里只创建一个Application单例**。
5. **组件相关缓存（ReceiverDispatcher等）**
    广播接收器的Binder分发器、Provider信息缓存，管理当前APK的四大组件相关运行记录。
6. 兼容配置、overlay资源、split apks（App Bundle分片apk）相关管理。

> 一句话总结LoadedApk的定位：**把APK的代码、资源、包元信息全部打包管理的容器**。
> ApplicationInfo只是**安装时PackageManager解析出来的静态清单元数据**，**没有ClassLoader、没有Resources，不能用来加载类和资源**。

## 为什么 ContextImpl 必须传入 LoadedApk，不能只传ApplicationInfo？

看`ContextImpl.createAppContext`方法签名：

```java
static ContextImpl createAppContext(ActivityThread mainThread, LoadedApk packageInfo)
```

`ContextImpl`是Context接口的真正实现类，它内部会保存 `mPackageInfo = packageInfo`，**Context几乎所有能力都依赖LoadedApk提供**：

### 1. Context获取资源 `context.getResources()`

`context.getResources()` → 内部调用 `mPackageInfo.getResources()`。
Resources对象**保存在LoadedApk**，不是ContextImpl。ContextImpl只是代理。

### 2. Context加载类 `context.getClassLoader()`

`getClassLoader()` 直接返回 `mPackageInfo.mClassLoader`。
Context要实例化四大组件、读取类，必须拿到LoadedApk里面的ClassLoader。

### 3. Context启动组件（startActivity、startService、sendBroadcast）

调用AMS的时候，需要携带当前App的包名、uid、进程归属，全部从LoadedApk获取。

### 4. Context获取Application

`getApplicationContext()` 底层：`mPackageInfo.makeApplication()`，拿到Application单例。

### 5. 多包场景支持（Instrumentation测试 / SDK Sandbox）

一个进程里可以同时加载**两个APK**：被测App + 测试Runner。

- 被测App ContextImpl 绑定被测App的LoadedApk
- 测试Runner的ContextImpl绑定Runner对应的LoadedApk
如果只传ApplicationInfo，无法区分两套ClassLoader、两套Resources。

> 一句话：
> **ContextImpl是一个轻量“代理门面”，它本身不持有代码、资源、类加载器；所有重量级的APK运行信息，全部托管在LoadedApk。没有LoadedApk，Context就没法加载类、读取资源，完全无法工作。**

## 区分两个容易混淆对象

- `ApplicationInfo`：**静态清单元数据**（PackageManager安装解析出来），只有包名、版本、APK路径等基础信息，**没有ClassLoader，没有Resources**，AMS跨进程传递用这个。
- `LoadedApk`：**进程运行期的APK运行容器**，拿着dex类加载器、资源管理器，**只有App进程内部才会创建**，AMS进程里不存在LoadedApk对象。

## 结合你前面的启动流程串起来

1. AMS通过Binder把`ApplicationInfo`传给App进程（放在AppBindData）
2. `getPackageInfoNoCheck(appInfo, compatInfo)`：**用ApplicationInfo创建LoadedApk**，去打开APK、初始化PathClassLoader、Resources
3. `ContextImpl.createAppContext(thread, loadedApk)` → ContextImpl持有LoadedApk引用
4. 后续：`loadedApk.makeApplication()`，利用内部ClassLoader反射创建Application对象
5. Instrumentation再调用`callApplicationOnCreate(app)`

## 补充：为什么注释写 Instrumentation info affects the class loader

因为Instrumentation测试场景，**测试Runner是另一个独立APK，有独立的LoadedApk+ClassLoader**。
所以必须**先解析Instrumentation信息**，再创建AppContext（AppContext绑定被测App的LoadedApk）。
两套LoadedApk、两套ClassLoader互相隔离。
