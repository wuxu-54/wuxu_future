# Binder 详细原理 + 核心源码解析

## 一、Binder核心定位

Android Binder 是**跨进程通信（IPC）框架**，采用**C/S架构**，基于Linux内核驱动`/dev/binder`。
> 传统IPC管道/消息队列：拷贝2次数据；Binder只**一次内存拷贝**（核心优势）。
> 核心角色：**服务端(Stub)、客户端(BinderProxy)、Binder驱动、ServiceManager**。

> 关键认知：**C/S是针对接口的，不是进程**。
> 同一个进程，可以同时是A接口的客户端、B接口的服务端。前面的`IActivityManager` / `IApplicationThread`就是典型。

## 二、四大角色

1. **Binder驱动（内核态，/dev/binder）**
    整个IPC的中转站，负责：
    - 管理Binder节点、引用计数
    - 内存映射mmap（减少拷贝）
    - 接收客户端请求，唤醒服务端Binder线程池
    - 传递数据，跨进程传递IBinder对象
2. **ServiceManager（native进程，Binder全局注册表）**
    特殊Binder服务。作用：**服务注册 + 服务查询**。
    - `addService(String name, IBinder binder)`：服务端把自己Binder注册进去
    - `getService(String name)`：客户端按名字查询拿到Binder代理
    > ⚠️ ServiceManager本身也是Binder服务。AMS/WMS/PMS注册在这里；`ApplicationThread`**不注册在这里，一对一传递**。
3. **Server 服务端**
    实现AIDL Stub（继承`Binder`），运行服务进程，等待客户端调用。
4. **Client 客户端**
    拿到`BinderProxy`（服务端的远程代理），调用方法触发IPC。

## 三、AIDL自动生成代码（最核心Java层源码）

写AIDL文件，编译后自动生成`IXXXInterface.java`，包含3部分：

1. 接口 `IXXXInterface`：定义IPC方法
2. `Stub extends Binder implements IXXXInterface`：**服务端基类**
3. `Proxy implements IXXXInterface`：**客户端代理类，持有BinderProxy**

举例子，模拟`IApplicationThread.aidl`：

```aidl
// IApplicationThread.aidl
interface IApplicationThread {
    void scheduleLaunchActivity(Intent intent);
}
```

编译自动生成代码，精简版源码（重点看Stub和Proxy）

```java
public interface IApplicationThread extends android.os.IInterface {
    public static abstract class Stub extends android.os.Binder implements IApplicationThread {
        // 事务ID，每个方法分配唯一编号
        private static final int TRANSACTION_scheduleLaunchActivity = (android.os.IBinder.FIRST_CALL_TRANSACTION + 0);

        public Stub() {
            this.attachInterface(this, DESCRIPTOR);
        }

        // 将IBinder转为IApplicationThread接口
        public static IApplicationThread asInterface(android.os.IBinder obj) {
            if ((obj == null)) {
                return null;
            }
            android.os.IInterface iin = obj.queryLocalInterface(DESCRIPTOR);
            if (((iin != null) && (iin instanceof IApplicationThread))) {
                // ✅ 同进程！直接返回本地对象，不走IPC
                return ((IApplicationThread) iin);
            }
            // ✅ 跨进程：返回Proxy，内部持有BinderProxy
            return new IApplicationThread.Stub.Proxy(obj);
        }

        // ========= 核心：服务端的transact方法【内核驱动回调这个函数！】=========
        @Override public boolean onTransact(int code, android.os.Parcel data, android.os.Parcel reply, int flags) throws android.os.RemoteException {
            switch (code) {
                case TRANSACTION_scheduleLaunchActivity: {
                    // 从Parcel读取客户端传过来的参数
                    android.content.Intent _arg0;
                    _arg0 = data.readParcelable(android.content.Intent.class.getClassLoader());
                    // 调用本地实现的方法！就是ApplicationThread重写的scheduleLaunchActivity
                    this.scheduleLaunchActivity(_arg0);
                    reply.writeNoException();
                    return true;
                }
            }
            return super.onTransact(code, data, reply, flags);
        }

        // 客户端代理类
        private static class Proxy implements IApplicationThread {
            // proxy持有远程Binder的引用：BinderProxy
            private android.os.IBinder mRemote;

            Proxy(android.os.IBinder remote) {
                mRemote = remote;
            }

            @Override public android.os.IBinder asBinder() {
                return mRemote;
            }

            // 客户端调用这个方法 → 发起IPC
            @Override public void scheduleLaunchActivity(android.content.Intent intent) throws android.os.RemoteException {
                android.os.Parcel _data = android.os.Parcel.obtain();
                android.os.Parcel _reply = android.os.Parcel.obtain();
                try {
                    _data.writeInterfaceToken(DESCRIPTOR);
                    _data.writeParcelable(intent, 0);
                    // =========核心！transact 发起IPC调用，阻塞等待服务端返回=========
                    boolean _status = mRemote.transact(TRANSACTION_scheduleLaunchActivity, _data, _reply, 0);
                    if (!_status) {
                        throw new android.os.RemoteException("Method scheduleLaunchActivity failed");
                    }
                    _reply.readException();
                }
                finally {
                    _data.recycle();
                    _reply.recycle();
                }
            }
        }
    }
    void scheduleLaunchActivity(android.content.Intent intent) throws android.os.RemoteException;
}
```

### 源码关键点解读

1. **Stub extends Binder**
`Binder`是Java层对native Binder的封装。`onTransact`：**服务端入口**。
当Binder驱动收到客户端请求，就回调服务端Stub的`onTransact`，根据code匹配方法，从Parcel读出参数，调用我们重写的业务函数。

> `onTransact`运行在**服务进程的Binder线程池**，不是主线程！！！

2. **Proxy 客户端代理**
Proxy里面持有`IBinder mRemote`，跨进程场景，`mRemote`实际类型是`BinderProxy`。
客户端调用`scheduleLaunchActivity`，内部调用`mRemote.transact()`，把方法编号+参数打包进Parcel，**发给Binder驱动**，当前客户端线程阻塞，等待返回结果。

3. **同进程优化**
`asInterface`中`queryLocalInterface`，如果发现是同一个进程，直接返回本地Stub对象，**不走Binder驱动，没有IPC开销**。

## 四、IBinder / Binder / BinderProxy 三个类区分（Java层）

1. **IBinder**：接口。定义Binder基础能力：`transact()`、`queryLocalInterface()`。
2. **Binder（Stub父类）**：服务端本地对象，实现IBinder。`onTransact`是核心回调。
    - 在服务进程，new出来就是Stub实例
3. **BinderProxy**：远程代理，实现IBinder。**客户端拿到的跨进程IBinder本质就是BinderProxy**
    - Binder驱动自动在客户端进程生成BinderProxy。
    - BinderProxy.transact() → 调用native方法，进入内核Binder驱动。

> 一句话：
>
> - 服务进程：`Binder(Stub)` 本地对象
> - 客户端进程：`BinderProxy` 远程代理，代表远端的Binder对象

## 五、`ApplicationThread`源码（结合上面AIDL，App作为Binder服务端）

`ActivityThread`内部类，就是IApplicationThread.Stub的实现

```java
// ActivityThread.java
private class ApplicationThread extends IApplicationThread.Stub {
    @Override
    public void scheduleLaunchActivity(Intent intent) throws RemoteException {
        // ⚠️ 当前运行在App的Binder线程池，不能操作UI！
        // 通过Handler把消息切到App主线程
        sendMessage(H.LAUNCH_ACTIVITY, intent);
    }
}
```

- `new ApplicationThread()` 实例 = Binder服务端对象
- 在`ActivityThread.attach()`，App作为`IActivityManager`的客户端，调用AMS的`attachApplication`，把这个IBinder传给AMS。

```java
// ActivityThread.attach
mAppThread = new ApplicationThread();
IActivityManager am = ActivityManager.getService();
am.attachApplication(mAppThread, startSeq); // 将IBinder传给AMS
```

AMS收到这个IBinder，在AMS进程调用`IApplicationThread.Stub.asInterface(binder)`，得到Proxy。
AMS保存这个Proxy，后续AMS就可以调用`proxy.scheduleLaunchActivity()`跨进程通知App。

## 六、AMS这边：IActivityManager（AMS作为Binder服务端）

AMS实现`IActivityManager.Stub`：

```java
public class ActivityManagerService extends IActivityManager.Stub {
    @Override
    public int startActivity(IApplicationThread caller, Intent intent) throws RemoteException {
        // AMS进程内执行，处理启动Activity逻辑

    }

```

AMS启动时注册到ServiceManager：

```java
ServiceManager.addService(Context.ACTIVITY_SERVICE, mActivityManagerService);
```

App想要调用AMS，就从ServiceManager查询，拿到BinderProxy，转成IActivityManager.Proxy。

```java
    return IActivityManager.Stub.asInterface(ServiceManager.getService("activity"));
}
```

## 七、一次完整Binder调用流程（AMS调用App scheduleLaunchActivity）
>
> 场景：SystemServer(AMS) 调用 App进程的scheduleLaunchActivity

1. AMS持有`IApplicationThread`的Proxy，调用`proxy.scheduleLaunchActivity(intent)`
2. Proxy内部：参数写入Parcel，调用`mRemote.transact(code, data, reply, flags)`，`mRemote`是BinderProxy
3. BinderProxy调用native方法，陷入内核，把数据交给Binder驱动
4. Binder驱动：找到目标App进程，唤醒App进程里的**Binder线程池**中的一条线程
5. App进程Binder线程，进入`ApplicationThread(Stub).onTransact()`
6. onTransact匹配事务code，读取Parcel参数，执行`scheduleLaunchActivity()`
7. App的ApplicationThread发送Message到主线程Handler，主线程执行启动Activity逻辑
8. 方法执行完，把返回值写入reply Parcel，原路返回给Binder驱动
9. 驱动把结果传回AMS进程，AMS阻塞的transact返回，调用结束

```
AMS进程                    Binder驱动内核                  App进程
Proxy.scheduleLaunchActivity()
        ↓
BinderProxy.transact()
        ↓ 数据打包，陷入内核
        ─────────────>
                                                    唤醒Binder线程
                                                    Stub.onTransact()
                                                    scheduleLaunchActivity
                                                    sendMessage切主线程
        <────────────  返回结果
transact函数返回，调用完成
```

## 八、native层简要（Java Binder底层）

Java的`Binder` / `BinderProxy` 底层都封装native C++代码：

1. `android_os_Binder.cpp`：Java Binder映射native `BBinder`（服务端）
2. `android_os_BinderProxy.cpp`：Java BinderProxy映射native `BpBinder`（客户端）
3. libbinder：C++ Binder库，和驱动交互
    - BBinder：native服务端对象，对应Java Binder
    - BpBinder：native客户端代理，对应Java BinderProxy

Java `transact`最终调用native `IBinder::transact`，通过ioctl和/dev/binder驱动通信。

## 九、关键机制：Binder内存mmap（为什么只一次拷贝）

1. 服务进程启动时，调用`mmap`，在服务进程开辟一块内核共享缓冲区。
2. 客户端数据：**客户端用户空间 → 内核缓冲区（1次拷贝）**
3. 内核缓冲区直接映射到服务进程地址空间，**不需要再拷贝到服务进程用户空间**

> 传统管道：客户端→内核（拷贝1），内核→服务端（拷贝2），两次拷贝。Binder仅一次。
> ⚠️ mmap只映射服务端，**只有服务端才有这块共享内存**。

## 十、Binder线程池

- **服务端进程在初始化Binder时，会启动Binder线程池**
- 所有Binder IPC请求都在线程池的线程执行，**不是主线程！**
- 所以ApplicationThread的回调方法跑在Binder线程，必须用Handler切主线程，否则不能操作UI。

> 面试高频：Binder线程池，默认最多16个线程。

## 十一、死亡代理 DeathRecipient

当Binder服务端进程意外死亡（App崩溃），客户端收到通知。
AMS给每个App的IApplicationThread注册DeathRecipient。App进程crash，AMS收到回调，做清理任务栈、回收资源。

```java
// AMS保存App的IApplicationThread时注册death监听
mAppThreadProxy.asBinder().linkToDeath(new DeathRecipient(){
    @Override
    public void binderDied() {
        // App进程挂了，AMS收到通知
    }
},0);
```

## 十二、两种IBinder传递方式，再次区分

1. **ServiceManager.addService**：全局注册，AMS/WMS/PMS。任意进程getService查询。
2. **参数传递IBinder**（attachApplication）：一对一传递。
    App新建ApplicationThread，作为参数传给AMS，AMS保存代理。**不注册ServiceManager**。
    bindService返回的Service IBinder也是这种方式。

## 十三、高频面试问题总结

1. Q：Binder客户端服务端怎么判断？
A：看接口。谁持有Stub，谁就是该接口服务端；持有Proxy就是客户端。App对于IApplicationThread是服务端；对于IActivityManager是客户端。

2. Q：onTransact运行在哪个线程？
A：服务进程的Binder线程池，**非主线程**，UI操作必须Handler切换。

3. Q：Binder内存拷贝几次？
A：一次，得益于mmap共享内存。

4. Q：ServiceManager作用？
A：Binder全局注册表，只负责注册和查询Binder，**本身不转发业务调用**。

5. Q：Binder和Socket的区别（AMS-Zygote是Unix Socket）
A：
Binder：IPC，内存共享，一次拷贝，适合高频小数据；
Unix Socket：文件读写，两次拷贝，适合进程创建前通信（此时App进程不存在，无Binder线程池）

# 十四、整体串联（Binder和App启动流程合并）

```
1. SystemServer启动AMS：AMS(IActivityManager.Stub) 注册到ServiceManager
2. Launcher(App)调用startActivity
    Launcher拿到AMS的BinderProxy(IActivityManager.Proxy)
    Binder IPC调用AMS.startActivity()
3. AMS发现App进程不存在，Unix Socket通知Zygote fork App进程
4. App进程ActivityThread.main() → attach()
    new ApplicationThread（IApplicationThread.Stub，App侧Binder服务）
    App调用AMS.attachApplication(mAppThread)，把IBinder传给AMS
5. AMS拿到IBinder，转为IApplicationThread.Proxy保存
6. AMS使用这个Proxy，Binder调用scheduleBindApplication、scheduleLaunchActivity
7. App的ApplicationThread.onTransact收到请求，Handler切主线程创建Application、Activity
```
