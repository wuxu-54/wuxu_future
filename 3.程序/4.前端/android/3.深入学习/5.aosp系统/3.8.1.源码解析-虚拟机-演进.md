# Android虚拟机（运行时）演进 + 升级原因（可合并进上面APK安装大笔记）
>
> 重点：Android 不是标准JVM，早期是**Dalvik虚拟机(DVM)**，Android5.0后正式换成 **ART（Android Runtime）**；ART后续持续迭代（纯AOT → AOT+JIT混合 → PGO配置文件引导编译、APEX模块化）
> 统一概念：Dalvik / ART 一般口语叫“Android虚拟机”，官方术语是**托管运行时**，执行DEX字节码。

## 一、完整时间线演变

1. **Android1.0 ~ Android2.1：Dalvik，纯解释执行**
    Java源码 → javac → class → dx工具合并优化 → dex；Dalvik直接解释dex字节码，**无JIT**。
    特点：启动慢、执行慢，适合早期极低性能手机。

2. **Android2.2(Froyo) ~ Android4.4(KitKat)：Dalvik + JIT即时编译**
    加入JIT（Just-In-Time）**运行时编译**：App运行的时候，解释执行，同时采样热点方法，把频繁调用的方法**实时翻译成机器码**，缓存到内存。
    - 缺点：每次打开App都要重新分析、编译热点代码；编译占用CPU、耗电；GC是全暂停STW，卡顿明显。
    - Android4.4：**ART作为实验选项内置**，用户可在开发者选项手动切换Dalvik/ART，默认仍然是Dalvik。

3. **Android5.0(Lollipop) ~ Android6.0：ART 默认，纯AOT预编译**
    彻底废弃Dalvik，ART成为唯一默认运行时；**AOT Ahead-of-Time，安装阶段用dex2oat，把整个DEX全部一次性编译成机器码oat文件**（ELF格式），存放在`/data/dalvik-cache`。
    > 👉 这就是我们上一节APK安装阶段2里面，PMS调用`dex2oat`做dex预编译！
    - 优点：App打开直接跑原生机器码，启动快、运行性能高、运行期不再消耗CPU做编译，省电。
    - 缺点：**安装时间大幅变长；oat文件体积大，占用更多磁盘空间；系统OTA升级，所有App全部重新AOT编译，开机等待很久**。

4. **Android7.0(Nougat) 重大改版：ART 混合模式 AOT + JIT + PGO（Profile Guided Optimization）**
    解决纯AOT的痛点，不再全量编译：
    - 安装阶段：**只做dex校验，不做全量AOT编译**，安装速度变快。
    - App首次运行：解释执行 + JIT，一边跑一边收集热点方法，生成`profile`配置文件（记录哪些方法是高频热点）。
    - 手机空闲、充电状态：系统后台读取profile，**只对profile标记的热点方法做AOT预编译**。
    > 只编译经常跑的代码，冷代码不编译，平衡安装速度、存储空间、运行性能。

5. **Android8.0+：ART GC升级为并发压缩GC**
    GC改进：**一次短暂STW、并发标记、支持堆压缩，减少内存碎片**，大幅降低大堆场景卡顿；同时dexlayout优化类加载速度。

6. **Android10/11之后：ART做成APEX模块**
    ART打包成`com.android.art` APEX，**可以独立升级ART运行时，不用完整OTA整包升级系统**；可以单独修复runtime漏洞、优化GC、编译器，不用等大版本系统更新。

## 二、Dalvik vs ART 核心对比

|项目|Dalvik虚拟机(Android2.2~4.4)|ART（Android5+，现代AOT+JIT混合）|
|---|---|---|
|编译方式|解释 + JIT（运行时动态编译热点）|AOT(安装/空闲预编译热点)+JIT(运行期收集profile)|
|字节码|DEX|**同样DEX，字节码兼容，所以老App可以直接跑ART**|
|编译时机|App运行过程中，边跑边编译|充电空闲时，根据profile只编译热点方法|
|文件产物|odex（优化dex）|oat（机器码ELF）、profile配置文件|
|GC|基础GC，长时间STW，容易卡顿|并发压缩GC，STW极短，可压缩堆减少碎片|
|安装速度|快（不做全量编译）|Android5/6慢；Android7+恢复较快|
|App启动速度|慢，每次启动需要重新JIT采样|热点代码提前AOT，冷启动更快|
|功耗|JIT持续占用CPU，耗电|运行期无持续编译，功耗更低|
|存储占用|小|oat占用额外空间，7+只编译热点，空间压力下降|

> 关键：Dalvik是**基于寄存器虚拟机**（不是JVM栈式），ART同样执行DEX，**字节码层面兼容，所以不用重新编译APK**。

## 三、为什么Google要把Dalvik升级成ART（面试重点，分4大理由）

### 1. 性能瓶颈：Dalvik JIT的先天缺陷

Dalvik JIT是**每次App启动，重新分析、重新编译热点代码**。

- App退出后，JIT编译出来的机器码只存在内存，App被杀就全部丢失；下次打开App，一切重来，重复消耗CPU。
- 动画、列表滑动等UI场景，一边渲染一边做JIT编译，抢占CPU，造成掉帧、卡顿。
- Dalvik GC长时间Stop-The-World，堆越大，暂停时间越长，滑动卡顿明显。

> 移动设备CPU弱、电池宝贵，**不能在用户使用App的时候持续消耗CPU做编译**。

### 2. 用户体验：App启动速度、流畅度、续航提升

ART AOT预先把热点代码翻译成ARM原生机器码：

- 启动不用现场翻译，App冷启动更快；代码执行效率更高，计算类应用（游戏、图片处理）性能提升明显；
- 运行期间不再持续做JIT编译，减少CPU占用，**省电，延长续航**。
- 新版ART并发压缩GC，减少长时间停顿，减少UI卡顿、掉帧。

### 3. 硬件发展，权衡发生变化

早期安卓手机：存储很小，CPU极弱。Dalvik优先节省磁盘。
2013年后手机：CPU多核、闪存容量提升，Google可以牺牲**磁盘空间+安装时间**，换取运行期流畅度和省电。
> Android7之后的PGO混合模式，进一步折中：**不编译全部代码，只编译热点，解决纯AOT安装慢、占用空间大的问题**。

### 4. 安全性与可维护性，更强校验+模块化能力

1. ART在dex2oat阶段**严格校验DEX文件**，Dalvik会容忍很多非法畸形dex，容易被恶意代码利用；ART安装期强校验，提升安全。
2. ART架构更干净，编译器、GC、解释器解耦；Android10后做成APEX模块，独立升级runtime，修复安全漏洞，不需要整包OTA升级系统。

## 四、补充易错考点（面试高频坑）

❌ 误区1：ART不再执行dex字节码
✅ 正解：**ART依然读取APK内的dex，dex是输入；dex2oat把dex编译成机器码oat**，字节码保持兼容，Dalvik的APK不用重编就能跑ART。

❌ 误区2：Android7之后完全没有AOT了
✅ 正解：Android7是**混合模式**：JIT收集profile，充电空闲后台做AOT编译热点代码。不是抛弃AOT，是**按需AOT**。

❌ 误区3：ART是解释器，Dalvik是编译器
✅ 正解：Dalvik=解释+JIT；ART同时拥有**解释器、JIT编译器、AOT编译器**三套执行引擎。

❌ 误区4：Zygote和ART是同一个东西
✅ 正解：Zygote是**进程孵化器**；ART是**App进程内部的托管代码运行时**。Zygote进程预加载ART、基础类，fork出各个App进程，每个App进程都有独立ART实例。

## 五、和前面APK安装阶段联动（衔接笔记）
>
> 前面APK安装阶段1：上传APK到/data/app-staging；阶段2：解析APK、签名校验，**然后调用dex2oat**。
> Android5/6：dex2oat在安装时**全量AOT编译**，所以安装慢；
> Android7+：安装阶段dex2oat**只做dex合法性校验，不生成完整oat**；等App运行生成profile，手机空闲充电后台再执行AOT编译热点方法。
