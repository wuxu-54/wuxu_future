# API 29（Android 10 / Q）Handler 消息机制改动 + 「异步消息/同步屏障」完整解释
>
> 一句话前置：**同步屏障、异步消息这套底层机制在API29之前早就存在，一直是系统内部使用（ViewRootImpl绘制消息）；API29最大改动：把创建异步Handler的API正式开放给应用层使用，同时加强Message的状态校验、内存泄漏警告、加固消息池。**

## 一、先搞懂：什么是同步屏障、异步消息（API29之前系统内部就有的机制）

### 1）同步消息（默认，我们普通Handler发的）

`handler.sendMessage / post()` 默认都是**同步消息**。
> 遇到**同步屏障**的时候，同步消息会被跳过、暂时不执行，排在屏障后面的同步消息全部卡住。

### 2）异步消息（系统绘制用的）

`msg.setAsynchronous(true)`，**不受同步屏障拦截**。
> 一旦队列插入同步屏障，Looper在next()遍历的时候，**只找异步消息执行，同步消息全部跳过**。

### 3）同步屏障 SyncBarrier

屏障本质是一个特殊Message：`target == null`，没有对应的Handler，**只是一个标记，不会被dispatchMessage执行**。

- ViewRootImpl调用`scheduleTraversals()`准备UI绘制时，会往主线程MessageQueue插入同步屏障；
- 插入屏障后：**屏障之后所有普通同步消息全部暂停，优先执行异步消息（绘制、VSync回调）**；
- 绘制完成`doTraversal()`，移除屏障，同步消息才恢复正常执行。

> 核心目的：**保证UI渲染、VSync帧回调最高优先级，不能被队列前面一堆普通业务消息阻塞，防止掉帧**。

> 老版本（API<29）限制：
> 同步屏障`postSyncBarrier()`是**@hide私有API，应用不能直接调用**；
> 虽然你可以反射`message.setAsynchronous(true)`把单个消息标记成异步，但是**Handler构造函数里的async参数是隐藏的，应用层没有官方API直接创建一个“所有发送消息自动是异步”的Handler**。
> 只能手动对每一条msg单独`setAsynchronous(true)`，很麻烦，而且非官方，容易踩坑。

## 二、API 29（Android Q）核心改动清单

### 改动1：新增公开静态方法 `Handler.createAsync()`（最重要改动）

```java
public static Handler createAsync(@NonNull Looper looper)
public static Handler createAsync(@NonNull Looper looper, @NonNull Callback callback)
```

作用：**创建异步Handler**。这个Handler发送的所有Message/Runnable，**自动标记为异步消息（msg.setAsynchronous(true)）**，不用每次手动设置。

源码内部逻辑：

```java
// Handler构造函数，第三个参数 mAsynchronous
public Handler(@NonNull Looper looper, @Nullable Callback callback, boolean async) {
    mLooper = looper;
    mQueue = looper.mQueue;
    mCallback = callback;
    mAsynchronous = async; // createAsync 传入 true
}

// 发送消息的时候
private boolean enqueueMessage(MessageQueue queue, Message msg, long uptimeMillis) {
    msg.target = this;
    if (mAsynchronous) {
        msg.setAsynchronous(true); // 自动标记异步
    }
    return queue.enqueueMessage(msg, uptimeMillis);
}
```

> API29之前这个带`async`布尔参数的构造函数是`@hide`，应用无法直接调用；API29开放`createAsync`，作为官方入口。

### 改动2：Message消息状态校验大幅增强，防止非法复用

1. 加强`isInUse()`状态检查；
2. **禁止同一个Message对象多次入队**，一旦重复enqueue直接抛异常；
3. 加固消息池`obtain()`/`recycleUnchecked()`，防止脏数据、野引用；

> 以前很多代码bug：复用同一个Message多次sendMessage，会导致链表错乱、内存异常，现在直接强校验拦截。

### 改动3：强化Handler内存泄漏警告日志

当创建**非静态内部类Handler**（隐式持有外部Activity/Fragment引用），在API29上log会输出更详细的泄漏风险堆栈，提醒开发者静态Handler+WeakReference。

### 改动4：native层 MessageQueue 少量bug修复（epoll/wake逻辑）

修复少数场景：唤醒丢失、超时时间计算错误；**但是底层依然是 Legacy 单锁链表模型，没有DeliQueue！DeliQueue是API37**。

### 改动5：IdleHandler 回调行为微调

修复部分边界场景，IdleHandler在队列空闲时触发时机异常的bug。

> ⚠️ 重要区分：API29**没有新增同步屏障机制**，只是开放异步Handler给App。同步屏障从很早版本就存在，一直是Framework内部给UI绘制使用。

## 三、核心问题：**为什么要做异步消息？为什么需要createAsync？**

### 场景：主线程消息队列排队，普通业务消息阻塞UI绘制

举个真实场景：
主线程MessageQueue里面消息顺序：
> 【业务同步消息A】→【同步屏障】→【业务同步消息B】→【绘制异步消息】

当View需要刷新UI，ViewRootImpl插入**同步屏障**。
按照Legacy next()逻辑：
Looper读到屏障，**跳过所有同步消息（A、B），只找异步消息执行绘制**。

如果绘制消息是普通同步消息：插入屏障之后，绘制消息也会被屏障拦住，UI永远无法渲染，App卡死。
所以**绘制消息必须是异步消息，才能穿过屏障，优先执行**。

### 那应用层什么时候需要自己创建异步Handler（API29新增能力）？

适合的场景：**高优先级事件，不能被同步屏障卡住**

1. 实时传感器回调、触摸/输入事件回调；
2. 音视频帧回调、播放器控制事件；
3. 必须及时响应、不允许被UI刷新屏障阻塞的高优先级业务。

> 举例子：
> App在播放视频，同时界面滑动触发invalidate，系统插入同步屏障。
> 如果视频帧回调用普通Handler，消息是同步消息 → 被屏障拦住，视频卡顿。
> 如果用`Handler.createAsync()`创建异步Handler发送帧回调消息 → 异步消息，**穿过同步屏障，正常执行，不被UI绘制阻塞**。

⚠️ 但是有代价：
异步消息**不遵守同步屏障的优先级管制**，如果滥用异步Handler大量发消息，会抢占UI绘制资源，反而造成掉帧。官方提示：**异步Handler谨慎使用，只用于真正高优先级实时事件，不要拿来做普通业务逻辑**。

### 异步消息的两条重要特性（面试常问）

1. **同一个异步Handler发出的多条异步消息，相对顺序保持不变**；
2. 异步消息和其他Handler（普通/其他异步Handler）的消息之间，**不再保证全局顺序**。

> 也就是说：异步消息可以插队穿过屏障，打破全局排队顺序。

## 四、容易混淆的误区澄清

1. ❌ 误区：异步消息=子线程执行
✅ 完全不是！**异步消息仍然在Looper所在主线程执行**。
`同步/异步`描述的是**消息在MessageQueue中遇到同步屏障时，是否会被拦截**，**和执行线程无关**。

> 名字非常容易误导人，这里的异步不是多线程异步，只是消息队列调度层面的标记。

2. ❌ 误区：API29新增同步屏障
✅ 错，同步屏障很早就有，API29只是开放**异步Handler**给App使用；同步屏障本身仍然是系统私有API，App不能自己postSyncBarrier。

3. ❌ 误区：异步消息优先级永远最高
✅ 不是。**只有队列存在同步屏障的时候，异步消息才会优先放行；没有屏障的时候，同步消息和异步消息一样，严格按when时间顺序排队执行**。

## 五、API29前后对比表

| 特性 | API<29 | API >=29 |
|---|---|---|
| 同步屏障 | 存在，系统内部ViewRootImpl使用，@hide，App无法调用 | 不变，仍然是系统私有API |
| 异步消息标记msg.setAsynchronous(true) | 底层支持，可反射调用，但不推荐 | 底层不变，官方提供createAsync API |
| 一键创建异步Handler | 构造async参数被@hide，无法直接创建；只能逐个msg手动setAsynchronous | ✅ Handler.createAsync()公开API，自动标记消息为异步 |
| Message复用校验 | 校验弱，重复入队容易引发链表异常 | 强校验，重复enqueue直接抛异常 |
| Handler泄漏警告 | 简单日志 | 详细堆栈日志，警告增强 |
| MessageQueue底层 | 单锁synchronized+单向链表（Legacy） | **完全不变，依然Legacy，无DeliQueue** |

## 六、API29 vs API37改动一句话区分（面试高频）

1. **API29 Android10**：上层API能力开放，新增`createAsync`异步Handler；**队列底层实现不变，还是单锁链表**；解决「应用层无法方便创建不受同步屏障阻塞的消息」。
2. **API37 Android17**：**不改动上层Handler/同步屏障/异步消息的行为**，完全重写MessageQueue内部，DeliQueue无锁队列；解决「Legacy全局锁竞争，主线程被后台子线程阻塞卡顿」。

> 简单记：
> API29 → **开放异步消息能力（调度优先级）**
> API37 → **优化队列锁竞争（并发入队性能）**

## 七、同步屏障源码片段（nextLegacy，API29和API37之前共用）

```java
// MessageQueue nextLegacy
Message msg = mMessages;
if (msg != null && msg.target == null) {
    // 遇到同步屏障，跳过所有同步消息，只找异步消息
    do {
        prevMsg = msg;
        msg = msg.next;
    } while (msg != null && !msg.isAsynchronous());
}
```

逻辑：发现屏障，循环向后遍历，只拿`isAsynchronous=true`的消息。
