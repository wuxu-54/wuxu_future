# App Bundle（AAB）与 Split APK（拆分APK）完整详解

> **一句话区分核心概念**
>
> - **AAB（Android App Bundle，`.aab`）：开发者上传到Google Play的**发布包**，**不能直接安装到手机**，是代码+资源的模块化容器。
> - **Split APK（拆分APK）：Google Play从AAB生成出来，**真正安装到手机上的多个小APK**；Android系统把多个split看成**同一个App**（包名相同，UID相同，代码资源互通），API>=21（Android5.0）支持Split APK机制。
> - 传统单体Monolithic APK：一个APK打包**全部ABI、全部分辨率资源、全部语言**，所有用户下载一模一样大包。

> ⚠️ 重点区分：**Multidex（多dex）≠ Split APK**
> Multidex：**单个APK内部，多个dex文件，解决65536方法上限**，还是**一个APK文件**；
> Split APK：**同一个App，磁盘上存在多个独立APK文件（base.apk + 各种split.apk）**，每个split本身可以是multidex。

小米、OPPO、vivo、应用宝等绝大多数国内安卓市场，都不支持 Google 原生 AAB；只有华为应用市场（AppGallery）支持上传 AAB，但和 Google Play 的 AAB 不是完全一套体系，国内业务极少真正使用 AAB 分发，国内主流交付格式仍然是 APK

## 一、Split APK 的底层原理（Android系统层面）

Android 5.0引入Split APK机制：

1. 多个APK拥有**完全相同的packageName、签名**；
2. 系统安装时，把它们合并成**一个应用**，共享ClassLoader、资源索引；
3. 每个split APK有独立AndroidManifest，独立资源、dex、so库；
4. 系统可以**单独下载、单独更新、单独删除某一个split**，不用全包更新。

Split APK一共分为3大类，全部由Google Play根据AAB自动生成：

1. **Base APK（基础包 base.apk）【必须，核心骨架】**
    应用主入口：Application、四大组件、核心业务dex代码、通用资源。**没有base.apk，App无法运行**。
2. **Configuration splits（配置拆分APK，自动生成，最常用）**
    根据设备硬件/语言，按需分发，**只下发当前设备匹配的那一份**：
    - ABI拆分：arm64-v8a / armeabi-v7a / x86 / x86_64（so原生库拆分）
    - 屏幕密度：xxhdpi/xhdpi/mdpi等图片资源拆分
    - 语言locale：values-zh、values-en 多语言字符串资源拆分
    > 用户手机只会下载**base.apk + 当前设备对应的ABI+分辨率+语言split**，其余资源不下发，直接大幅减少下载包体积（普遍减少30%~40%）
3. **Dynamic Feature splits（动态功能模块，Play Feature Delivery）【可选，业务模块化】**
    业务功能独立打包成split APK，支持三种交付模式：
    - 安装时交付（install-time）：安装App时一起下载
    - 按需下载（on-demand）：App运行后，用户点击功能才下载；用完可以删除，释放空间
    - 免安装Instant体验：Instant App，不用完整安装即可打开页面

> 额外还有 Asset Pack（资源资产包，Play Asset Delivery），专门放超大资源（贴图、视频），不属于split APK，是配套资源交付方案。

## 二、AAB完整打包&分发流程（串联R8、ReDex、multidex）

```
源码 → javac/kotlinc → class文件
→ R8（代码缩减、混淆、class优化，输出dex）
→ Android Studio构建AAB（.aab）：把模块打包进bundle，包含base模块 + 动态feature模块
→ 开发者上传 .aab 到Google Play后台
→ Play服务器【bundletool】解析AAB，**针对每一台设备生成对应的一组split APK**
→ 用户手机下载：base.apk + 匹配的配置split（ABI/分辨率/语言），按需下载动态feature split
→ Android系统安装这一批split，系统识别为同一个App
```

> bundletool：官方工具，本地也可以用它把aab生成apks（一堆split apk打包成apks文件，本地测试）

## 三、AAB模块结构（AAB内部不是APK，是模块目录）

AAB本质是zip压缩包，内部按**模块**组织：

1. base模块（必选）：核心代码dex、主manifest、通用资源
2. feature模块（动态功能模块，可选）：独立业务代码、资源，可以单独下发
每个模块内部有：dex、res、lib、assets、模块自己的manifest、BundleConfig.pb全局配置文件。

> AAB**不会提前拆好不同ABI/分辨率的包**；拆分这件事**在Google Play云端实时完成**，开发者只需要上传**唯一一份aab**，不用像旧的多APK方案，自己构建多套apk上传。

## 四、AAB / Split APK 的收益

1. **下载包体积显著降低**
    最核心收益。比如App包含4套ABI、5套图片分辨率，单体APK全部打包；AAB只会给用户下发当前手机对应的一套so、一套图片、一套语言资源。
2. **增量更新更高效**
    只修改base代码 → 只更新base.apk；只是图片资源修改 → 只更新分辨率split；不用全包下载。
3. **按需模块化（动态功能）**
    低频大功能（比如图片编辑器、AR模块）不随主包下载，用户使用时再拉，减小初始下载包。
4. **开发交付简化**
    只构建、签名、上传**单个aab**，Google Play自动为成千上万设备生成适配split，替代旧的“多APK上传方案”。

## 五、AAB + Split APK 的局限与坑（面试高频）

1. **最低Android版本API21**，5.0以下设备不支持split APK，Play会自动生成传统单体APK给老设备。
2. **国内应用商店基本不支持AAB**：国内Android市场没有Google Play的bundle解析服务，国内一般还是直接上传单体APK；AAB主要用于海外Google Play上架。
3. **动态Feature模块开发成本高**
    - 跨模块类访问，需要反射/接口隔离；
    - 模块间代码解耦，不能直接强依赖；
    - 要处理模块下载、安装、失败重试、权限、降级逻辑。
4. **资源ID冲突风险**：base模块和feature模块资源id要处理，避免冲突。
5. **更新机制限制**：所有split的版本号必须同步，版本号不一致无法安装。
6. 配置拆分粒度有限：只能按ABI、分辨率、语言；**不能按业务代码做配置拆分**，业务代码拆分要靠动态Feature模块。

## 六、重要对比：Split APK vs Multidex vs ReDex（串联你前面所有知识点）

|方案|作用层级|目标|本质|
|---|---|---|---|
|Multidex|**单个APK内部**，多个dex文件|突破单dex 65536 method_id上限|**一个APK文件，多个dex**|
|ReDex InterDexPass|**multidex场景，同一个APK内部多个dex之间重排类**|减少跨dex引用，降低dex索引冗余体积|仍然**单个APK**，内部dex类重排|
|Split APK(AAB)|**一个App，多个独立APK文件**（base+split）|按设备裁剪资源/so、按需下发业务模块，减少用户下载包|**多个APK文件，系统合并为一个App**|
|R8/Proguard|class阶段，dex生成之前|删除死代码、内联、混淆，减少总代码/方法数量|代码瘦身，在打包前期执行|

> 大厂海外链路完整组合：
源码 → R8（代码摇树、优化、混淆，生成dex）→ ReDex（InterDex多dex重排优化）→ 打包AAB → 上传Google Play → Play云端生成Split APK，下发给用户。

## 七、容易混淆：旧的“Google Play多APK” vs AAB Split APK

- 旧多APK：开发者**本地手动构建多个完整单体APK**（arm64包、x86包），分别签名，全部上传Play；维护成本极高。
- AAB Split APK：开发者**只上传一份aab**，Play云端自动生成所有设备对应的split组合，不需要开发者维护多套apk。

## 八、bundletool常用命令（本地调试AAB）

```bash
# 将aab生成apks压缩包（里面包含所有split apk组合）
bundletool build-apks --bundle=app.aab --output=app.apks

# 从apks中提取当前设备匹配的split集合并安装到手机
bundletool install-apks --apks=app.apks
```

## 九、一句话总结

AAB（.aab）是**Google Play的发布格式，不是安装包**；Split APK是AAB在云端拆分生成的一组小APK，Android5.0+系统可以把多个split APK合并当成同一个App运行；
Split APK分三类：base基础包、配置资源split（ABI/图片/语言）、动态业务feature split；它的核心价值是**只下发设备真正需要的资源，大幅减少用户下载包大小，支持按需动态功能**；
> 区分关键点：Multidex是**一个APK里面多个dex**；Split APK是**同一个App，多个独立APK文件**。
