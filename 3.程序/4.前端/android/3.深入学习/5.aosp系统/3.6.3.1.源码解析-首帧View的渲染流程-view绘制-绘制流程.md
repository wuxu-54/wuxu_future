# 从 performTraversals() 开始 → measure → layout → draw → Surface 缓冲区提交 → SurfaceFlinger合成 → 屏幕点亮（完整细致拆解）
>
> 前置上下文（T+版本，Activity冷启动尾段）
> handleResumeActivity → wm.addView → new ViewRootImpl → setView() → requestLayout() → scheduleTraversals()
> scheduleTraversals 插入**同步屏障**，向Choreographer注册回调，等待VSync信号。
> VSync信号到来，`mTraversalRunnable.run()` → **ViewRootImpl.performTraversals()**，这是整个View绘制+渲染流水线总入口。

> 先理清两个关键概念：
>
> 1. **App绘制（CPU端）**：measure/layout/draw，全部运行在App主线Java层，把内容画到`Surface`里面的GraphicBuffer（图形缓冲区）
> 2. **SurfaceFlinger合成（GPU/HWC端，native进程）**：App只是填充buffer，**多个App的图层叠加、最终送到屏幕是SurfaceFlinger负责**

---

# 阶段1：performTraversals 前置准备（ViewRootImpl）

```java
private void performTraversals() {
    // 1. 检查窗口属性、窗口大小、配置是否变化
    // 2. 和WMS做relayout窗口信息同步（跨进程Binder调用）
    //    mWindowSession.relayout() 非常关键！
    //    → WMS确定窗口最终大小、z-order，返回Surface给App
    //    ⚠️ 如果Surface还没有创建，relayout内部会创建Surface
    relayoutResult = mWindowSession.relayout(...)

    // relayout返回后，mSurface 就持有了这块Surface对象（App和SurfaceFlinger共享的缓冲区载体）
    mSurface = relayoutResult.getSurface();

    // 3. 判断是否需要measure / layout / draw
    boolean needMeasure = ...;
    boolean needLayout = ...;
    boolean needDraw = ...;

    if (needMeasure) {
        performMeasure(childWidthMeasureSpec, childHeightMeasureSpec);
    }
    if (needLayout) {
        performLayout(lp, mWidth, mHeight);
    }
    if (needDraw) {
        performDraw();
    }
}
```

> ✅ 重点：**mWindowSession.relayout**
> App通过IWindowSession向WMS询问窗口大小，WMS根据窗口布局、状态栏、窗口层级计算窗口尺寸；
> 同时，**Surface就是在这一步建立**。Surface本质是跨进程共享的一块图形缓冲区管理对象，App和SurfaceFlinger都可以访问里面的GraphicBuffer。

## 1. performMeasure() 【测量阶段，CPU主线】

```java
private void performMeasure(int childWidthMeasureSpec, int childHeightMeasureSpec) {
    mView.measure(childWidthMeasureSpec, childHeightMeasureSpec);
}
```

`mView`就是DecorView，**深度优先递归遍历整棵View树**。

### MeasureSpec

`MeasureSpec = mode(2bit) + size(30bit)`
mode三种：

- EXACTLY：精确尺寸（match_parent、固定dp）
- AT_MOST：最多不超过size（wrap_content）
- UNSPECIFIED：无约束（ScrollView、RecyclerView）

#### View.measure() 源码逻辑

```java
public final void measure(int widthMeasureSpec, int heightMeasureSpec) {
    // 1. 判断是否需要重新测量
    if (needsMeasure || ...) {
        // 回调onMeasure，子类在这里计算自己期望宽高
        onMeasure(widthMeasureSpec, heightMeasureSpec);
        // 保存测量结果 mMeasuredWidth / mMeasuredHeight
        setMeasuredDimension(w, h);
    }
}
```

> 注意：`measure()`是final，不能重写；**onMeasure才是留给控件重写的方法**。

ViewGroup在onMeasure内部，循环遍历所有子View，**计算子View的MeasureSpec，调用子View.measure()**。
👉 从DecorView往下，父View约束子View，递归全部View，每个View算出自己需要的`mMeasuredWidth/mMeasuredHeight`。

> 此时：View只有**测量宽高**，还没有left/top/right/bottom屏幕坐标。

## 2. performLayout() 【布局阶段，CPU主线】

```java
private void performLayout(WindowManager.LayoutParams lp, int desiredWindowWidth, int desiredWindowHeight) {
    mView.layout(0, 0, desiredWindowWidth, desiredWindowHeight);
}
```

调用DecorView.layout(l,t,r,b)，**递归布局整棵View树**。

```java
public final void layout(int l, int t, int r, int b) {
    // 保存当前View的四个边界坐标
    mLeft = l; mTop = t; mRight = r; mBottom = b;
    onLayout(true, l, t, r, b);
}
```

- View：onLayout空实现；
- **ViewGroup必须重写onLayout**，遍历子View，调用 `child.layout(left, top, right, bottom)`，分配子View位置。

✅ **layout结束之后：每一个View的大小 + 屏幕坐标全部确定**。
> 但是！**画布上还没有任何像素，没有绘制内容**。

## 3. performDraw() 【绘制阶段，CPU主线，往Surface缓冲区画内容】

```java
private void performDraw() {
    boolean canUseAsync = drawSoftware();
}
```

> Android有两种绘制路径：软件绘制(CPU) / HWUI硬件加速绘制（GPU，绝大多数手机默认开启）
> 现代设备默认走 **HWUI硬件加速**，下面重点讲HWUI，顺带区分软件绘制。

### drawSoftware()

```java
private boolean drawSoftware() {
    // 锁定Surface的GraphicBuffer，拿到Canvas
    Canvas canvas = mSurface.lockCanvas(dirty);
    try {
        // 从DecorView开始递归绘制View树
        mView.draw(canvas);
    } finally {
        // 解锁，提交buffer给SurfaceFlinger
        mSurface.unlockCanvasAndPost(canvas);
    }
    return true;
}
```

#### View.draw(canvas) 标准4步

```java
public void draw(Canvas canvas) {
    // step1：绘制背景 drawBackground()
    // step2：onDraw()，控件自身绘制内容（TextView文字、Button、自定义View图形）
    onDraw(canvas);
    // step3：dispatchDraw() 递归绘制子View（ViewGroup核心）
    dispatchDraw(canvas);
    // step4：绘制前景、滚动条、overlay
    drawForeground(canvas);
}
```

> 所有draw操作，本质是向Canvas记录**绘制命令**（不是直接画像素）。
> ⚠️ HWUI硬件加速模式：Canvas不是软件画布，而是`RecordingCanvas`。**它不会生成像素，而是把绘制操作记录成DisplayList（显示列表，GPU绘制指令）**。

##### HWUI（硬件加速）细节

1. RecordingCanvas 收集draw调用，保存DisplayList（绘制指令：画矩形、文字、图片）
2. unlockCanvasAndPost不会直接渲染，而是**把DisplayList交给RenderThread（渲染线程，App进程内独立native线程）**
3. RenderThread把DisplayList转成GPU指令，在GPU上执行渲染，填充到Surface对应的GraphicBuffer

> 软件绘制（关闭硬件加速）：Canvas是Bitmap，主线CPU计算像素，直接填充到GraphicBuffer，性能差，现在很少用。

#### unlockCanvasAndPost(canvas) 【提交缓冲区，非常关键】

当绘制命令记录完毕，调用这个方法：

1. 解除GraphicBuffer锁定；
2. 将**填充完成的GraphicBuffer入队，发送到SurfaceFlinger（跨进程）**；

> App进程工作到此结束：App只负责生产buffer，**App不能直接控制屏幕**。

> 这里是**双缓冲机制**：
> Surface一般有2块GraphicBuffer（front/back buffer）
>
> - back buffer：App正在绘制的缓冲区
> - front buffer：SurfaceFlinger正在拿来显示在屏幕上的缓冲区
> App绘制back buffer，post之后交换缓冲区。

# 阶段2：SurfaceFlinger（独立native系统进程）接收图层Buffer，合成

SurfaceFlinger 会**监听所有Surface的buffer队列**。
> 每个窗口（Activity、状态栏、导航栏、输入法）对应独立Surface，每一个Surface是独立图层（Layer）。

1. App post buffer → Surface的BufferQueue入队一块新GraphicBuffer；
2. SurfaceFlinger收到buffer可用的信号；
3. SurfaceFlinger收集**全部可见Layer**：当前Activity窗口Layer、SystemUI状态栏Layer、导航栏Layer、弹窗Layer等；
4. 计算每一层的：Z序（层级，上层盖下层）、透明度、裁剪区域、矩阵变换；
5. 合成分支二选一：**HWC硬件合成 / GPU OpenGL合成**
    - HWC（Hardware Composer，首选）：把图层交给显示芯片硬件，硬件直接叠加图层，功耗更低；
    - 如果HWC无法合成（太多图层、特殊效果），SurfaceFlinger使用OpenGL在GPU做图层混合，生成一个最终的FrameBuffer。
6. 合成完成，生成**最终一帧画面的缓冲区**，交给显示驱动。

> ⚠️ SurfaceFlinger只在VSync信号到来时，才把合成好的画面推给屏幕。
> App的VSync和SurfaceFlinger的VSync是同一组硬件垂直同步信号。

# 阶段3：显示驱动 + 屏幕硬件刷新

1. 显示驱动拿到最终合成后的帧buffer；
2. 在硬件VSync的消隐期（vertical blanking），把像素数据输出到屏幕面板；
3. 屏幕面板逐行刷新像素。
✅ **到这一步，用户眼睛真正看到View画面**

# 关键时序&重点坑点总结

## 1. 主线只负责：measure layout + 记录绘制指令

measure/layout/onDraw 全部在App主线；
硬件加速模式，**GPU渲染在RenderThread，不在主线**。主线只是记录DisplayList。

## 2. 两个VSync

- App侧VSync：Choreographer收到VSync → 触发performTraversals，App开始准备这一帧内容（measure/layout/draw，生成buffer）
- SurfaceFlinger侧VSync：同一硬件信号，SurfaceFlinger收到后，执行图层合成、输出到屏幕

> 一整个帧流水线：VSync → App主线做measure/layout + 记录绘制指令 → RenderThread GPU渲染buffer → SurfaceFlinger收到buffer → 图层合成 → 屏幕刷新。
> 整个流程目标控制在16ms以内（60Hz），超时就丢帧、卡顿。

## 3. 几个容易混淆的边界

1. performLayout完成：View有位置大小，**但屏幕看不见，像素还不存在**
2. unlockCanvasAndPost：App提交buffer给SurfaceFlinger，**不代表立刻上屏，需要SurfaceFlinger合成+下一次VSync刷新**
3. WMS的relayout：**创建Surface、确定窗口大小**，在measure/layout之前执行！很多人以为measure先执行，实际performTraversals最前面先调用relayout和WMS交互。

## 4. 双缓冲 / BufferQueue

Surface底层是BufferQueue（生产者-消费者模型）

- App = Producer生产者，往队列放GraphicBuffer
- SurfaceFlinger = Consumer消费者，取出buffer做合成

# 完整流水线串联（从VSync到屏幕）

```
硬件VSync信号
    ↓
Choreographer回调 mTraversalRunnable → ViewRootImpl.performTraversals()
    ↓
mWindowSession.relayout() 【Binder和WMS交互，获取窗口大小，创建Surface】
    ↓
performMeasure() → 递归View树，计算mMeasuredWidth/Height
    ↓
performLayout() → 递归View树，分配left/top/right/bottom坐标
    ↓
performDraw()
    → lockCanvas拿到RecordingCanvas
    → DecorView.draw() 递归View树，记录DisplayList绘制指令（HWUI）
    → unlockCanvasAndPost()，将GraphicBuffer入队提交给SurfaceFlinger（BufferQueue）
    ↓
SurfaceFlinger（native系统进程）
    收集所有Layer的GraphicBuffer，按Z序叠加、做透明度裁剪
    HWC硬件合成 / GPU OpenGL合成，生成最终画面buffer
    ↓
显示驱动在VSync消隐期输出像素数据到屏幕面板
    ↓
✅ 用户肉眼看到页面
```

## 高频面试追问

### Q：invalidate()之后的完整流程？

invalidate标记脏区域 → requestLayout不会执行 → scheduleTraversals等待VSync → performTraversals跳过measure/layout，直接performDraw，只重绘。

### Q：requestLayout和invalidate区别放在这个链路怎么理解？

requestLayout：标记需要measure+layout，会完整走measure/layout/draw整套流程；
invalidate：仅标记脏区域，**不触发measure/layout，只执行draw**。

### Q：Surface什么时候销毁？

Activity退出，WMS销毁窗口，Surface被释放，BufferQueue销毁。

### Q：RenderThread作用？

HWUI硬件加速下，主线只记录绘制指令，RenderThread异步执行GPU渲染，减轻主线压力。
