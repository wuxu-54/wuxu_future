# APK签名 V1 / V2 / V3 详细原理 + 升级演进原因
>
> 前置背景：APK本质是ZIP压缩包。
> V1：JAR签名（Java原生jar签名）
> V2：APK全文件签名（APK Signing Block，Android7.0引入）
> V3：V2基础上增加证书轮换（Android9引入）

## 一、V1签名（Jar签名）原理

### 1. 签名文件位置

在APK的 `META-INF/` 目录，生成3个文件：

1. `MANIFEST.MF`：遍历APK内**每一个资源/classes.dex文件**，对**文件内容**计算SHA摘要，记录文件名+摘要。
2. `CERT.SF`：对`MANIFEST.MF`的每一行分段计算摘要，保护MANIFEST.MF本身。
3. `CERT.RSA`：用开发者私钥，对CERT.SF做签名；里面存放签名+开发者证书公钥。

### 2. V1校验流程

1. 读取`MANIFEST.MF`，逐个取出APK内部文件，计算文件哈希，和MANIFEST里记录的摘要比对；
2. 校验`CERT.SF`对MANIFEST.MF的签名；
3. 用证书公钥，验证CERT.SF文件的数字签名，确认没有被篡改。

### 3. V1重大缺陷（核心痛点，催生V2）

V1**只校验ZIP包里面的各个条目内容，不校验ZIP文件本身的元数据（ZIP目录、文件尾部）**
> ZIP结构 = 文件实体 + 中央目录（Central Directory） + 尾部EOCD结束标记

**漏洞场景：**
攻击者拿到V1签名的APK，可以：

1. 不修改APK里面任何文件；
2. 直接修改ZIP中央目录 / EOCD尾部字段；
3. 重新打包。
👉 MANIFEST.MF里面记录的内部文件摘要完全不变，**V1校验依然可以通过**，但是ZIP指向的文件被篡改，系统可能加载恶意内容。

另外缺点：

- 校验时必须遍历APK里所有文件，安装校验慢；
- 无法保护ZIP元信息。

> 一句话总结V1：**签的是包里每一个独立文件，不是整个APK文件。**

## 二、V2签名（APK Signature Scheme v2，Android7.0 Nougat引入）

### 2.1 核心设计：APK签名块 APK Signing Block

V2不再使用META-INF。
在ZIP的 **中央目录前面**，插入一块独立区域，叫做 **APK Signing Block**。
APK整体文件被划分成3个区域：

1. 【区域1】ZIP文件内容（所有APK的文件数据：dex、资源、so）
2. 【区域2】APK Signing Block（签名块，保存哈希、签名、证书链）
3. 【区域3】ZIP中央目录 + EOCD（ZIP尾部）

> 规则：**V2签名对【区域1 + 区域3】全部字节计算哈希，排除签名块本身。**

### 2.2 V2签名生成流程

1. 将APK文件划分成连续的块，对所有ZIP内容（除签名块）分段计算哈希；
2. 将全部哈希结果打包，用开发者**私钥做数字签名**；
3. 将：分段哈希列表、签名、证书链，全部存入APK Signing Block；
4. 把签名块插入到ZIP中央目录之前，写入APK。

### 2.3 V2校验原理（安装阶段PMS调用apksig库）

1. 读取APK尾部EOCD，找到APK Signing Block；
2. 提取证书公钥 + 预先保存的哈希摘要；
3. 重新计算APK（除签名块）全部字节的哈希；
4. 比对哈希，然后用公钥验签。
✅ 只要APK任意位置（dex、资源、ZIP中央目录、EOCD）任何1字节改动 → 整体哈希改变，校验直接失败。

### 2.4 V2相比V1的优点

1. 保护**整个APK二进制文件**，包括ZIP元数据，修复V1的ZIP目录篡改漏洞；
2. 分块并行计算哈希，校验速度更快；
3. 签名块独立，不会占用META-INF资源。

### 2.5 V2的遗留痛点（催生V3）

**V2不支持证书轮换！**

- 覆盖安装要求：新版本APK的证书公钥必须和旧版本完全一模一样；
- 如果开发者私钥丢失、证书泄露，**无法更换证书**。
一旦私钥丢了，后续新版本无法覆盖升级旧App，只能让用户卸载重装，损失用户数据。

> 这就是V2最大硬伤，Android 9推出V3解决这个问题。

## 三、V3签名（APK Signature Scheme v3，Android9 Pie引入）

### 3.1 核心新增能力：证书轮换（Signing Certificate Rotation）

V3在V2的APK Signing Block基础上，**扩展签名块，增加证书轮换历史链表**。
签名块里维护一条证书链表：`旧证书 → 新证书`。

### 3.2 V3原理

1. 签名块除了保存当前版本的签名信息，额外增加**签名证书历史记录**；
2. 链表记录：之前旧证书公钥、切换证书的授权证明（旧私钥签名，证明允许换成新证书）；
3. 升级安装校验逻辑发生变化：
    安装程序可以沿着证书链表追溯：
    > 新证书 ←（旧私钥授权）← 旧证书（当初安装旧APK用的证书）
    只要链表可以追溯到原来App安装时的原始证书，就允许覆盖安装。

> 前提：**证书轮换操作，必须使用旧私钥签名授权这条轮换记录**。不能随便拿一个新证书冒充。

### 3.3 V3校验流程

1. 找到APK Signing Block，校验V3签名完整性（和V2一样，全文件哈希保护）；
2. 取出证书轮换链表；
3. 覆盖安装场景：
    读取系统packages.xml中保存的**原始旧公钥**；
    遍历证书链表，只要链表能够追溯到这个旧公钥 → 校验通过，可以覆盖升级；
4. 全新安装：直接使用当前证书保存到packages.xml。

### 3.4 V3保留V2全部能力

- 依然对整个APK文件做哈希保护，ZIP元数据防篡改；
- 支持分块哈希，校验速度快；
- 同时兼容旧设备：打包时可以同时携带V2+V3签名。

### 3.5 V3局限

证书轮换**只能单向、一次性**；证书一旦轮换，旧证书只能用于追溯，不能反过来用新证书签旧包。

## 四、版本总结对比

| 版本 | 引入版本 | 保护范围 | 核心特点 | 致命短板 |
|---|---|---|---|---|
| V1 | Android 1.0 | APK内部每个独立文件（不保护ZIP元信息） | Jar签名，META-INF | ZIP目录可篡改，不安全；不支持证书轮换 |
| V2 | Android7.0 | **整个APK二进制（除签名块）** | APK签名块，全文件哈希 | 不支持证书轮换，私钥丢失无法升级 |
| V3 | Android9.0 | **整个APK二进制**，同V2 | 增加证书轮换链表 | 必须旧私钥授权轮换记录 |

## 五、为什么要持续升级签名方案（面试总结版）

1. **V1升级V2：解决安全漏洞**
V1只能校验包内文件，ZIP元数据可以被篡改，存在安全漏洞。V2保护整个APK二进制，防止篡改ZIP目录、EOCD，提升安全性，同时提升校验速度。

2. **V2升级V3：解决业务痛点（证书丢失风险）**
V2强制要求新旧版本公钥完全一致。一旦开发者签名私钥泄露/丢失，App无法发更新包覆盖升级，用户只能卸载重装，丢失数据。V3引入证书轮换，在旧私钥授权前提下更换签名证书，实现平滑升级。

> 打包实践：现代打包一般**同时打V2+V3**。Android9+设备识别V3；7~8识别V2；更低版本降级使用V1兜底。

## 高频面试追问

1. 问：V2/V3校验的时候会不会校验META-INF里面V1签名？
答：**高版本Android如果检测到V2/V3签名存在，直接忽略V1，不再校验V1**，只走V2/V3校验。只有不存在V2/V3才降级V1。

2. 问：证书轮换是可以随便换证书吗？
答：不行。轮换记录必须**使用旧的私钥签名授权**，证明这次证书变更合法；攻击者无法凭空构造证书链表。

3. 问：V3的哈希校验和V2一样吗？
答：**哈希保护逻辑完全一样**，V3只是在签名块里额外增加证书轮换链表，完整性校验机制继承V2。

# APK V2、V3 签名方案详细原理
>
> 前提：APK本质是ZIP文件。V2和V3都引入了**APK Signing Block（APK签名块）**，不再依赖V1的`META-INF`目录。
> V2：Android 7.0，**全文件哈希保护**；
> V3：Android 9.0，**复用V2的文件完整性校验逻辑，仅在签名块增加证书轮换链表**。

## 一、APK文件结构（V2/V3共用）

标准ZIP原始结构：
> ZIP实体数据 → 中央目录（Central Directory） → EOCD（End of Central Directory，ZIP尾部结束记录）

V2/V3改造后的APK结构：

1. **块1：ZIP文件内容**（所有dex、资源、so等原始文件二进制）
2. **块2：APK Signing Block【新增】** 签名块
3. **块3：ZIP中央目录 + EOCD**

> 核心规则：**签名校验时，跳过APK Signing Block，对【块1 + 块3】全部字节做哈希校验。签名块本身不受哈希保护**。
> EOCD里会记录APK Signing Block的偏移地址，系统从文件末尾EOCD反向查找签名块。

## 二、V2签名（APK Signature Scheme v2）原理

### 2.1 签名生成流程（打包阶段）

1. **分块**：把【块1+块3】的APK二进制数据切分成若干连续分片（默认1MB一块）
    > 分块目的：支持多线程并行计算哈希，提升打包和校验速度。
2. **对每一个分片计算哈希**（SHA256/SHA512），得到分片哈希列表。
3. 将分片哈希列表、签名算法标识、证书链组装成**签名payload**。
4. 使用开发者**私钥**对payload进行数字签名，得到签名值。
5. 将下面全部信息存入APK Signing Block：
    - 分片哈希列表
    - 数字签名结果
    - 开发者证书公钥证书链
    - 使用的签名算法
6. 将这个完整签名块插入到「ZIP内容」和「ZIP中央目录」中间，写入APK。

> ⚠️ 注意：V2的签名保护的是**APK二进制流**，不是APK里面独立文件。哪怕修改ZIP元数据、EOCD里一个字节，整体哈希全部失效。V1做不到这点。

### 2.2 V2校验流程（安装阶段，PMS调用apksig库）

1. 读取APK最末尾EOCD，解析EOCD，找到APK Signing Block的起始偏移。
2. 解析签名块，取出：证书链、分片哈希列表、签名值、签名算法。
3. 重新对APK【块1+块3】做同样分块，逐段计算哈希，生成新的payload。
4. **第一步：完整性校验**，对比新算出来的分片哈希列表 和 签名块里保存的哈希列表。
    任何一处字节改动，哈希不一致 → 校验失败。
5. **第二步：数字签名验签**：使用证书中的**公钥**，校验签名块内的签名值，验证payload没有被伪造。
    > 完整性校验：文件有没有被篡改；验签：确认这个哈希payload是私钥持有者生成的，防止伪造哈希。
6. 校验全部通过：取出公钥存入Package对象，后续packages.xml持久化保存。

### 2.3 V2的核心限制

**V2没有证书轮换机制，覆盖安装强制要求：新版本APK的签名公钥必须和旧版本完全一致。**

- 如果私钥丢失、泄露，开发者无法使用新证书发布新版本APK；
- 用户只能卸载重装，丢失App本地数据；
- 不能平滑更换签名证书。

> 这就是V3诞生的根本原因。

## 三、V3签名（APK Signature Scheme v3）原理
>
> 一句话：**V3的APK文件完整性校验逻辑和V2完全一模一样，只是扩展了APK Signing Block，增加了证书轮换链表结构。**

### 3.1 V3签名块新增内容

V3在原有V2的签名信息基础上，在APK Signing Block中新增 **Signing Certificate Rotation（证书轮换链表）**。
链表结构：
> `原始证书公钥 ←（旧私钥签名授权）← 中间证书 ←（旧私钥签名授权）← 当前新证书`

链表每一条记录包含：

1. 旧证书公钥
2. 授权证明：**用旧私钥签名的授权记录**，代表旧证书持有者允许切换到下一级新证书

> 重点：**轮换记录必须用旧私钥签名，攻击者不能凭空构造证书链**。不是随便写一个新证书就能替换。

### 3.2 V3打包分两种场景

#### 场景A：不做证书轮换（普通打包）

链表里面只有当前这一个证书。此时行为**完全等价V2**。覆盖安装必须公钥一致。

#### 场景B：证书轮换打包（私钥迁移场景）

1. 开发者持有旧私钥，生成轮换授权记录，声明：允许从旧证书切换到新证书；
2. 用**旧私钥对这条轮换记录签名**；
3. 将轮换链表写入APK签名块；
4. 使用**新私钥**对APK文件做V3完整性签名。

> 最终APK签名块：V2风格的APK全文件签名（使用新私钥） + 证书轮换链表（记录旧证书+授权签名）

### 3.3 V3安装校验逻辑（安装阶段PMS）

**完整性校验部分，和V2完全相同：**

1. EOCD找到签名块；分块计算APK【块1+块3】哈希；对比分片哈希；
2. 使用当前签名块里的公钥做数字验签，确认APK文件没有被篡改、签名没有伪造。

**新增：覆盖安装时证书链追溯校验（V3独有）**

1. 覆盖安装：PMS读取packages.xml中**旧应用保存的原始公钥**；
2. 读取V3签名块内的证书轮换链表；
3. 沿着链表反向追溯，判断链表中**是否包含旧应用的原始公钥，并且授权记录合法**（授权记录的签名校验通过）；
4. ✅ 能追溯到旧公钥：校验通过，允许覆盖升级；
5. ❌ 链表追溯不到旧公钥：签名不匹配，`INSTALL_FAILED_UPDATE_INCOMPATIBLE`。

全新安装场景：直接取当前证书公钥保存到packages.xml，链表仅作为历史记录。

### 3.4 V3证书轮换的约束（面试高频）

1. **单向链表，只能向后轮换**：旧证书可以授权切换新证书；不能拿新证书授权切换回旧证书。
2. **轮换授权记录必须由旧私钥签名**。如果旧私钥已经丢失，无法生成轮换链表，不能做证书迁移。
3. 证书轮换是一次性的。多次轮换会形成一条完整的历史链。
4. 证书轮换**不改变APK文件完整性校验规则**，安全强度和V2一致。

## 四、V2 vs V3对比总结

1. **文件完整性哈希算法、APK签名块结构基础：V3完全继承V2**
2. **V2：证书是单一的，覆盖安装严格匹配公钥**
3. **V3：增加证书轮换链表，在旧私钥授权前提下，支持更换签名证书，实现平滑升级**
4. 兼容性：打包时一般同时嵌入V2+V3签名。Android9+识别V3；Android7~8识别V2；更低版本走V1兜底。

## 五、高频面试问题

### Q1：V3校验APK完整性的时候，会去校验链表里面所有证书吗？

A：**不会**。文件完整性校验只用当前APK的签名证书；证书链表**只在覆盖安装、对比新旧包签名的时候才会遍历追溯**。

### Q2：V3是不是替代V2，哈希算法更强？

A：**不是**。哈希保护逻辑完全一致，安全级别相同。V2解决的是V1的ZIP元数据篡改漏洞；V3解决**业务层面证书私钥丢失无法升级**的痛点，不是提升哈希安全强度。

### Q3：如果我打包V3，但没有做证书轮换，和V2有区别吗？

A：校验行为几乎没有区别。覆盖安装依旧要求公钥完全一致，链表只有一条记录。

### Q4：V2/V3签名块是放在ZIP的什么位置？

A：在ZIP的文件内容 和 ZIP中央目录之间。通过文件末尾EOCD找到签名块偏移。
