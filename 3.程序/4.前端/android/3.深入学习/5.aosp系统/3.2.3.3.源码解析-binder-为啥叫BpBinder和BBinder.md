# BpBinder / BBinder 含义、缩写、命名由来
>
> 注意：**BpBinder、BBinder 是 Android Native（C++）层的类**，来自早期 OpenBinder 项目；Java 层对应的是 `BinderProxy` 和 `Binder`。
> 二者都继承顶层接口 **IBinder**。

## 1. BpBinder

- **Bp = Binder Proxy**
  - `B` = Binder
  - `p` = **Proxy（代理）**
- **含义：客户端代理对象**
    客户端进程拿到远端服务的句柄`handle`，封装成BpBinder。
    作用：调用`transact()`，把IPC请求发给Binder驱动，**发起跨进程调用**。
    内部持有`mHandle`整数，用来在内核查找目标binder_node。

> Java层对应：`BinderProxy`（Java层封装，底层JNI最终包装BpBinder）

## 2. BBinder

- **BB = Binder Base（Binder实体基类）**
    原始OpenBinder的命名：**B + Binder**，第二个B代表Base，指Binder实体、本地真正的服务对象。
    > 简单记：BBinder = Binder实体（Server端本体）
- **含义：服务端实体对象**
    服务进程里真正的Binder对象，**服务端需要继承BBinder**。
    驱动收到IPC事务后，回调BBinder的`onTransact()`处理请求。

> Java层对应：`Binder`类（Java Binder底层JNI就是BBinder）

## 3. 配套命名体系（一起记，面试常考）

Native层业务接口还有一套配套命名规则：

1. **BpXXX**：业务代理（Client），`Bp`=Binder Proxy
    例：`BpServiceManager`，客户端访问ServiceManager
2. **BnXXX**：业务Stub（Server），`Bn`= Binder Native（Binder本地实体）
    例：`BnServiceManager`，ServiceManager服务端，继承BBinder

```
IBinder
├─ BpBinder（Client代理，p=Proxy）
└─ BBinder（Server实体基类）

IServiceManager
├─ BpServiceManager（Bp + 业务名） → 持有BpBinder
└─ BnServiceManager（Bn + 业务名） → 继承BBinder
```

## 4. 为什么这么命名（历史：OpenBinder）

这套命名不是Google凭空设计，来自 **Be公司 OpenBinder**（Android Binder的前身）。

- OpenBinder当年定下：
  - Proxy侧：`BpXXXX`
  - Native实体侧：`BnXXXX`
  - 基础实体类叫`BBinder`

> 设计思想：
>
> - BpBinder：**远程代理，只知道handle，不知道真实对象**；
> - BBinder：**本地实体，对应内核binder_node**，真正实现业务onTransact。

## 5. 一句话区分

- **BpBinder（Binder Proxy）：Client客户端，代理，发起IPC**
- **BBinder（Binder Base实体）：Server服务端，实体，接收并处理IPC请求**

## 6. 容易踩坑的对比

- Native：`BpBinder` ↔ `BBinder`
- Java：`BinderProxy` ↔ `Binder`
- Java的`BinderProxy`底层JNI就是封装了Native层BpBinder；
- Java的`Binder`底层JNI创建Native BBinder。

## 7. 面试简答版
>
> BpBinder：Bp 是 Binder Proxy，客户端代理，用于发起IPC；
> BBinder：Binder Base，服务端Binder实体基类，接收驱动回调onTransact；
> 源自OpenBinder的命名规范；配套BpXXX/BnXXX是业务层代理和Stub。
