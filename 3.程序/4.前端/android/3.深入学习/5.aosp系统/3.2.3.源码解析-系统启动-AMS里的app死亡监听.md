# AMS里attachApplicationLoced监听APP的Binder对象的死亡

**给App端的 `ApplicationThread` Binder对象注册死亡监听：如果App进程挂掉（crash/exit），system_server这边的 `AppDeathRecipient` 会被Binder驱动回调，AMS就可以做App死亡后的清理工作。**
> 这段代码运行在 **system_server（AMS）**。
> `thread` 就是App传过来的 `ApplicationThread` 远程Binder引用（BpBinder）。

```java
AppDeathRecipient adr = new AppDeathRecipient(app, pid, thread); 
thread.asBinder().linkToDeath(adr, 0); 
app.setDeathRecipient(adr);
```

## 逐行拆解

### 1. `AppDeathRecipient adr = new AppDeathRecipient(app, pid, thread);`

`AppDeathRecipient` 是**继承 IBinder.DeathRecipient** 的自定义类。
构造保存3个信息：

- `app`：AMS里代表这个App的记录（`ProcessRecord`）
- `pid`：App进程pid
- `thread`：App的`IApplicationThread`远程Binder引用

`DeathRecipient` 是**死亡回调接口**，只有一个方法：

```java
public void binderDied()
```

当远端Binder所在进程死亡，Binder驱动会触发这个回调。

### 2. `thread.asBinder().linkToDeath(adr, 0);`

```java
thread // IApplicationThread（IInterface）
thread.asBinder() // 获取底层IBinder（BpBinder，App端ApplicationThread的远程代理）
linkToDeath(adr, 0)
```

`linkToDeath` 是 **IBinder接口方法**。
作用：
> 向Binder驱动**注册死亡监听**：监听这个IBinder对应的远端Binder实体（App进程里的`ApplicationThread`）。
> 一旦App进程死亡，Binder驱动通知system_server，调用`adr.binderDied()`。

参数：

- 第1个参数：死亡回调对象 `adr`
- 第2个flags：0，保留标记，一般填0

> ⚠️ 关键点：监听的是**App进程里面那个Binder实体**。只要App进程退出/crash，不管是正常退出还是崩溃，内核Binder驱动检测到进程销毁，就触发死亡通知。

### 3. `app.setDeathRecipient(adr);`

把这个死亡监听对象保存到`ProcessRecord(app)`成员变量。
用途：

1. 后续如果AMS**主动解除监听**（App正常退出、清理），可以拿到adr调用`unlinkToDeath`，防止binderDied回调还跑；
2. 避免adr被GC回收：**如果adr没有强引用保存，Java GC会把它回收，死亡通知就不会触发！**

> 这个是高频坑：DeathRecipient必须持有强引用，否则GC回收后收不到binderDied。

## 当App进程死亡后发生了什么（完整链路）

1. App进程退出 / crash，内核销毁App进程所有资源；
2. Binder驱动发现：App进程里的`binder_node`（ApplicationThread本地Binder）所属进程死亡；
3. Binder驱动遍历**所有注册了linkToDeath监听这个node的进程**（也就是system_server）；
4. 在system_server的 **Binder线程池** 线程，执行 `AppDeathRecipient.binderDied()`；
5. 在`binderDied()`里面，AMS执行App死亡逻辑：
    - 标记ProcessRecord为死亡；
    - 清理进程记录；
    - 清理Activity、Service、广播相关状态；
    - 回收内存，更新LRU，通知其他组件App挂了。

## 重要细节

1. **binderDied 运行在Binder线程池，不是AMS主线程！**
   回调里不能直接执行耗时操作，源码里一般会发消息到AMS Handler主线程处理。
2. **死亡通知只会触发一次**
   触发之后这个监听自动失效；如果后续重新启动App，需要**重新linkToDeath注册新的DeathRecipient**。
3. 区分：
    - `linkToDeath`：**监听远端进程死亡**（AMS监听App）
    - 不是App监听system_server，方向不要搞反。
4. 如果App是正常退出，AMS会提前主动调用`unlinkToDeath`取消监听，就不会再收到binderDied。

## 和你前面代码上下文关联（attachApplication）

就是你前面看的：
App调用AMS `attachApplication(mAppThread)`，把App本地Binder `ApplicationThread` 传给AMS；
AMS拿到这个远程IBinder之后，**立刻注册这个死亡监听**。
> 目的：AMS必须感知App进程什么时候死掉，才能管理四大组件生命周期。

## 常见坑

1. 忘记保存DeathRecipient强引用 → GC回收，收不到死亡回调；
2. binderDied跑在binder子线程，直接操作AMS数据，不加同步锁，并发异常；
3. 收到binderDied之后没有去unlinkToDeath，虽然通知一次性，但最好手动解绑。

## 一句话浓缩

AMS拿到App传过来的ApplicationThread远程Binder，注册死亡监听器。App进程一旦死亡，Binder驱动回调`binderDied`，AMS执行App进程销毁后的清理工作。
