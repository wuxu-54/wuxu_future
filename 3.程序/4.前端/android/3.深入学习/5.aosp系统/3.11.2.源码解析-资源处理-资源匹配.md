# Android 资源匹配机制（分辨率、语言、版本等）+ 源码层面解析

>
> 核心一句话：**资源匹配是在 `AssetManager` native 层完成的；`resources.arsc` 里记录了每一份资源对应的 qualifier（修饰符，如`-xxhdpi`、`-zh`），App运行时拿着当前设备的配置，按一套固定优先级规则，选出最合适的资源条目。**

## 一、基础概念：资源修饰符 Qualifier

res目录命名格式：`资源类型-修饰符1-修饰符2-修饰符3`
示例：

```
res/drawable-xxhdpi/
res/drawable-xhdpi/
res/values-zh-rCN/
res/values-v21/
res/layout-land/
```

每一个文件夹后缀就是**Qualifier（限定符）**，可以组合。
限定符分为很多类别：屏幕密度dpi、语言、地区、横竖屏、Android版本、屏幕宽高、方向等。

>
> aapt2 link阶段，会把**每一个资源文件对应的全部qualifier**写入`resources.arsc`。
> 资源ID是唯一的，同一个资源名（比如`icon`），在不同qualifier目录下是**同一个资源ID，不同资源实体**。

## 二、设备当前配置：`Configuration`

Java层 `android.content.res.Configuration`，保存当前设备所有环境信息：

```
// 简化字段
public class Configuration {
    // 语言地区
    public Locale locale;
    // 屏幕方向 ORIENTATION_PORTRAIT / ORIENTATION_LANDSCAPE
    public int orientation;
    // 屏幕密度 DENSITY_XXHPI / DENSITY_XHDPI
    public int densityDpi;
    // 系统版本
    public int sdkVersion;
    // 屏幕尺寸、宽高、Night模式等
    public int uiMode;
}
```

>
> 来源：`ActivityThread`初始化时，从系统`WindowManagerService`读取设备硬件配置，生成Configuration，传给`Resources`。
> `Resources`持有Configuration，当系统配置变化（切换语言、旋转屏幕）会回调`onConfigurationChanged`，更新Configuration，重新查找资源。

## 三、资源匹配核心流程（完整链路）

```
业务代码：getResources().getDrawable(R.drawable.icon)
        ↓
Resources.java → ResourcesImpl → AssetManager(native)
        ↓
native层拿着【资源ID + 当前Configuration】遍历resources.arsc里面该资源的所有候选qualifier列表
        ↓
按照Android固定的**qualifier优先级顺序**，淘汰不匹配的候选，选出最优一条资源条目
        ↓
拿到资源在APK中的文件路径，mmap读取文件，解码返回Drawable
```

>
> ⚠️ 重点：**匹配逻辑全部在native AssetManager，Java层只是封装API，Java没有做资源匹配。**

## 四、Qualifier 优先级（面试必背，从高到低）

匹配规则：**按类别依次淘汰候选，高优先级类别先筛选，低优先级后筛选**

1. MCC/MNC（移动国家码）
2. 语言 & 地区 locale（values-zh-rCN）
3. 布局方向 ltr/rtl
4. 屏幕最小宽度 smallestWidth `sw600dp`
5. 可用屏幕宽度 availableWidth `w800dp`
6. 可用屏幕高度 availableHeight `h1280dp`
7. 屏幕尺寸 size（small/normal/large/xlarge）
8. 屏幕方向 orientation（portrait/land）
9. UI模式 uiMode（night暗色模式）
10. 屏幕密度 dpi（xxhdpi/xhdpi/mdpi）
11. 平台SDK版本 vXX（v21）

>
> 规则解读：**先筛高优先级限定符，不匹配的直接淘汰；剩下候选再进入下一级筛选**
> ❗ 不是“匹配最多修饰符就选中谁”，是**按顺序逐级淘汰**！

### 举例子：dpi分辨率匹配

候选资源：

- drawable-xxhdpi
- drawable-xhdpi
- drawable-mdpi
设备：屏幕密度 xxhdpi（480dpi）

1. 进入dpi这一级筛选
2. 完全匹配xxhdpi → 直接选中 drawable-xxhdpi/icon.png

如果设备是 360dpi（xhdpi），没有xhdpi资源，有xxhdpi和mdpi：

>
> Android不会取平均值，**优先找最接近、不大于？不对，dpi是特殊规则**
> dpi是唯一一类：**优先找大于等于当前密度中最小的；没有更大的，则选最大的更小的**，并且自动缩放。

>
> dpi特殊：资源图片加载后系统会自动缩放Bitmap。比如mdpi图片放到xxhdpi设备，会放大3倍。

## 五、源码解析（Android AOSP 简化，分 Java + Native）

### 1. Java层入口 Resources.java

```
public class Resources {
    private final ResourcesImpl mResourcesImpl;

    public Drawable getDrawable(int id) throws NotFoundException {
        return mResourcesImpl.getDrawable(id, null);
    }
}
```

ResourcesImpl.java

```
final class ResourcesImpl {
    private AssetManager mAssets;
    private Configuration mConfiguration;

    Drawable getDrawable(int resId, Theme theme) {
        // native层查询资源value，拿到资源文件路径
        TypedValue value = obtainTypedValue();
        // 【关键】调用native方法，根据resId + 当前Configuration查找资源
        boolean found = mAssets.getResourceValue(resId, 0, value, true);
        if (!found) {
            throw new NotFoundException("Resource ID #0x" + Integer.toHexString(resId));
        }
        // value.string 就是资源在apk中的路径，比如 "res/drawable-xxhdpi/icon.png"
        return loadDrawable(value, theme);
    }
}
```

`mAssets.getResourceValue` 是**JNI方法，进入native AssetManager**，真正的qualifier匹配逻辑在这里。

### 2. Native 核心：AssetManager.cpp / ResourceTable.cpp（AOSP简化伪代码）

>
> AOSP源码路径：`frameworks/base/libs/androidfw/ResourceTable.cpp`
> 伪代码还原核心匹配函数 `findBestEntry()`

```
// resId对应的资源，有多个候选ConfigEntry（每一条对应一套qualifier）
std::vector<ConfigEntry> candidates = getAllEntriesForResId(resId);

// 当前设备配置
const Configuration& deviceConfig = mCurrentConfiguration;

// 1. 按qualifier优先级依次过滤候选列表
// qualifierPriority[] 就是前面说的优先级顺序
for (auto qualifierClass : qualifierPriority) {
    if (candidates.size() == 1) break; //只剩一个，直接退出

    std::vector<ConfigEntry> remaining;
    for (auto& entry : candidates) {
        // 判断当前候选entry的qualifier 是否匹配设备该类配置
        if (isQualifierMatch(entry.config, deviceConfig, qualifierClass)) {
            remaining.push_back(entry);
        }
    }
    if (!remaining.empty()) {
        // 保留匹配的，淘汰不匹配
        candidates = remaining;
    }
    // 如果全部都不匹配，本轮不淘汰，进入下一级qualifier
}

// 2. 剩下多个候选，使用微调打分机制（tie-breaker）选出最优
ConfigEntry best = selectBestTieBreaker(candidates, deviceConfig);

// 3. 返回资源的路径、类型等信息，给到Java层
return best;
```

>
> 重点：`isQualifierMatch` 针对dpi有单独分支逻辑。
> dpi匹配的特殊逻辑伪代码：

```
// dpi匹配逻辑
if (qualifierClass == DENSITY) {
    int targetDpi = deviceConfig.densityDpi;
    // 收集所有候选的dpi值
    vector<int> availableDpi;
    for (auto &e : candidates) availableDpi.push_back(e.config.density);

    // 优先选择 >= targetDpi 的最小dpi；不存在，则选最大的小于targetDpi
    int bestDpi = findClosestDpi(availableDpi, targetDpi);
    filterCandidatesByDpi(&candidates, bestDpi);
}
```

### 3. TypedValue 是什么？

native匹配完成后，把结果写入`TypedValue`，传回Java层：

- `resourceId`
- `type`：string/drawable/layout
- `string`：资源在APK内的文件路径
- `data`：基础值（颜色、简单数值）

拿到路径后，AssetManager mmap APK读取二进制文件，解码。

## 六、实战案例演示匹配过程

目录结构：

```
res/
├─drawable-xxhdpi/icon.png
├─drawable-xhdpi/icon.png
└─drawable-mdpi/icon.png
```

设备：`densityDpi=360`（xhdpi=320，xxhdpi=480）

1. 资源ID对应的候选列表：xxhdpi、xhdpi、mdpi
2. 前面的qualifier（语言、横竖屏等全部完全一致，不淘汰任何候选）
3. 进入dpi筛选：target=360
   - 候选dpi：480,320,160
   - 大于等于360：只有480(xxhdpi)
   - 选中 xxhdpi/icon.png>
   > 图片会被系统自动缩放：480原图缩小到360密度展示。

案例2：没有xxhdpi，只有xhdpi(320)和mdpi(160)，设备360dpi

- 没有>=360的资源，就选最大的小于目标的：320 xhdpi，图片放大。

## 七、Configuration 变更，资源重载源码逻辑

比如App切换系统语言 / 旋转屏幕：
WMS → ActivityThread收到 `onConfigurationChanged`
ActivityThread.java

```
@Override
public void handleConfigurationChanged(Configuration newConfig) {
    // 更新全局配置
    mResourcesManager.applyConfigurationToResources(newConfig);
    // Resources 内部更新 mConfiguration
    // 之后再调用getDrawable/getString，AssetManager会用新的配置重新执行资源匹配
}
```

>
> 注意：**不会重新读取resources.arsc，arsc只加载一次；只是拿着新Configuration，重新跑一遍native匹配算法**。

## 八、和插件化、Split APK关联

1. Split APK：每个split拥有独立ResourceTable，系统合并进同一个AssetManager，资源匹配逻辑不变，只是候选资源来自多个APK。
2. 插件化：插件AssetManager加载插件apk，插件内部资源匹配**逻辑完全一样**，只是匹配在插件自己的ResourceTable中查找。

## 九、常见误区

1. ❌ 不是**匹配修饰符数量最多**的资源，是**按qualifier优先级逐级淘汰**
2. ❌ dpi不是找差值最小，有特殊规则（优先取更高密度）
3. ❌ 资源匹配不是在Java层，是native AssetManager
4. ❌ resources.arsc不会在每次getDrawable重新加载，App启动加载一次常驻内存

## 十、面试口述精简版

资源匹配信息存储在`resources.arsc`，每个资源条目附带qualifier限定符。App启动时，从系统读取设备信息生成`Configuration`。调用`getResources()`加载资源时，最终调用native层AssetManager。native按照固定优先级顺序，逐级淘汰不匹配的资源候选，dpi有特殊的就近选择规则，选出最优资源。返回资源文件路径，mmap读取资源。配置变更会更新Configuration，下次获取资源会重新走一遍匹配流程，不需要重读arsc。
