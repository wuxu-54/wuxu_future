# ActivityThread-handleApplicantion方法

## VMRuntime.registerSensitiveThread() 作用

```java
// Register the UI Thread as a sensitive thread to the runtime.
VMRuntime.registerSensitiveThread();
```

> 源码位置：`ActivityThread.java` main() 主线程入口，**Android App主线程（UI线程）初始化时调用**。

### 一句话作用

**告诉ART运行时：当前这个线程是「敏感线程」，不要在这个线程上做阻塞式GC、不要在这个线程触发GC停顿，尽量避免UI线程被GC卡住造成卡顿/掉帧。**

#### 1. VMRuntime 是什么

`VMRuntime` 是应用和ART虚拟机交互的Java层API，用来控制虚拟机行为（GC、内存、编译等）。
`registerSensitiveThread()` 是native方法，底层通知ART。

### 2. sensitive thread（敏感线程）含义

ART里把线程分成两类：

1. **普通线程**：GC发生时，如果需要STW（Stop-The-World），可以暂停这个线程；也可以在这个线程上执行GC相关任务。
2. **Sensitive Thread（敏感线程，这里就是UI主线程）**
    - GC**不会在该线程上执行GC标记/清扫等GC工作**；
    - 尽量**避免在这个线程上触发GC阻塞**；
    - GC的STW暂停依然会暂停它（STW是全局的，没法完全跳过），**但不会安排GC任务跑在UI线程**。

> 重点区分：
> ✅ 不能消除全局STW（所有线程都要停，包括UI线程）
> ❗ 只是**不让ART把GC工作任务调度到UI线程执行**，减少UI线程额外负载。

### 3. 为什么UI线程要标记成sensitive

Android主线程职责：View绘制、事件、组件生命周期。
如果ART把GC标记任务放到UI线程跑，会抢占UI线程时间，直接造成卡顿、丢帧、ANR风险。

ART的并行GC有GC工作线程池，默认会分配GC任务到各个线程；
调用`registerSensitiveThread()` 就是给ART打标记：**这个线程是UI线程，不要给它派发GC任务**。

### 4. 底层native逻辑（简单）

`VMRuntime.registerSensitiveThread()` native入口，调用ART runtime：

```c++
void RegisterSensitiveThread() {
  Thread* self = Thread::Current();
  self->SetIsSensitiveThread(true);
}
```

线程对象上标记 `is_sensitive_thread_ = true`。
ART在GC任务分发逻辑里判断：如果当前线程是sensitive，**跳过GC任务执行**。

### 5. 重要误区澄清（高频）

1. ❌ 不是“这个线程不会被GC暂停（STW）”
   STW是全局的，GC需要暂停所有Java线程，**UI线程照样会被暂停**。
   这个API只是**不把GC任务分配给UI线程**，不能消除STW停顿。
2. ❌ 不是保护这个线程不被GC回收对象
   完全无关，只是线程属性标记，和对象GC回收无关。
3. ❌ 只有UI主线程会标记，其他子线程默认不是sensitive。

### 6. 源码上下文（ActivityThread.main）

```java
public static void main(String[] args) {
    // ...
    Looper.prepareMainLooper();
    ActivityThread thread = new ActivityThread();
    thread.attach(false, startSeq);

    // Register the UI Thread as a sensitive thread to the runtime.
    VMRuntime.registerSensitiveThread();

    Looper.loop();
}
```

在主线程准备好Looper之后、进入消息循环之前，标记当前主线程为敏感线程。

### 7. 还有谁会用这个API？

系统内部少数对延迟极其敏感的线程也会标记：

- SurfaceFlinger相关线程、音频线程等，**普通App业务子线程不要随便调用**。
业务子线程调用这个API会干扰ART GC任务调度，不推荐。

### 总结

`VMRuntime.registerSensitiveThread()` 给ART标记**当前线程是敏感线程（UI主线程）**，ART GC任务调度器**不会把GC工作分配到这个线程执行**，减少主线程的额外开销，降低UI卡顿风险；**但是无法避免GC全局STW暂停主线程**。

## handleAttachAgent

```java
if (agent != null) {
handleAttachAgent(agent, data.info);
}
```

### 代码位置

这段代码在 **`ActivityThread.java` 的 `bindApplication`** 里面：

```java
if (agent != null) { 
    handleAttachAgent(agent, data.info); 
}
```

> **低版本Android源码（Android11及更早）没有；Android12/13才加入的新逻辑**，所以你看旧版本源码的时候看不到。

### agent是什么

`agent` = **JVMTI agent（ART TI代理库，.so）**
Android的JVMTI/ART TI：给profiler、调试器、插桩工具用的native代理库（libxxx.so），可以在App进程里做：

- 方法插桩、trace性能、内存分析、字节码instrument、调试。

> 只有 `debuggable=true` 的App才允许attach agent，正式release包不允许加载。

### 触发来源

AMS在启动App的时候，可以带上 `--attach-agent` 参数：

```
adb shell cmd activity attach-agent
```

AMS把agent路径、参数，通过 `bindApplication` 的数据带到App进程，赋值给变量`agent`。

### handleAttachAgent 作用

```java
private void handleAttachAgent(String agent, ApplicationInfo appInfo) {
    // agent字符串格式：path.so=参数
    // 调用 Debug.attachJvmtiAgent 加载JVMTI agent
}
```

一句话：
**如果AMS传递过来了JVMTI agent，就在bindApplication阶段（Application创建之前）加载这个native agent库，注入到当前App进程ART虚拟机。**

#### 执行时机（非常关键）

`bindApplication` 流程顺序：

1. AMS发送BIND_APPLICATION消息到App主线程H handler
2. 准备data.info（ApplicationInfo）
3. **【这里执行handleAttachAgent】加载JVMTI agent** ✅
4. 创建LoadedApk
5. 创建Application对象，调用 `Application.attachBaseContext()`
6. Application.onCreate()

👉 **agent在Application创建之前就注入进ART**，所以agent可以hook/Instrument Application、所有类加载、方法。

### 为什么旧源码没有

1. Android 11及之前：**只支持进程启动前提前指定agent，不支持bindApplication阶段动态attach-agent**；
2. Android12+ 新增这个能力：**App进程已经fork起来、还没跑Application.onCreate之前，动态注入JVMTI agent**。
所以你拿Android10/11的ActivityThread源码，看不到这一段。

### 工作链路

1. adb/工具向AMS发起attach-agent命令，指定目标进程+agent.so路径
2. AMS在启动App的时候，把agent信息打包，通过Binder调用 `ApplicationThread.scheduleBindApplication`
3. App主线程收到BIND_APPLICATION消息，进入bindApplication
4. 判断agent != null → `handleAttachAgent`
5. 内部调用native ART接口，加载libagent.so，执行 `Agent_OnAttach`（JVMTI标准入口）
6. agent在App进程内生效，开始插桩/采集trace等

### 安全限制（重点）

1. **只能debuggable应用**，正式release包拒绝attach agent；
2. 需要系统权限，普通第三方App不能随便注入别的进程agent；
3. 只能在 `bindApplication` 这个时机或者adb attach-agent命令触发；

### 常见用途

- Android Studio Profiler（性能分析、内存分析）
- 自动化测试插桩、代码覆盖率工具
- 动态trace、方法耗时采集
- 一些调试、逆向分析工具（仅限debug包）

### 一句话总结

`handleAttachAgent` 是Android12新增的代码，**在App的Application初始化之前，加载JVMTI native代理库，注入ART虚拟机，用于调试、性能分析、代码插桩**。旧版本AOSP没有这段，所以你对比老源码会觉得突然冒出来。
