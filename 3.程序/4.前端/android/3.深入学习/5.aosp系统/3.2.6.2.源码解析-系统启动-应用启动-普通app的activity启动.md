# 场景描述

**A（前台普通Activity）调用 startActivity() 启动 B**
> 两种情况：A和B在**同一个进程** / A、B**不同进程**；ATMS/ATSupervisor整体流程大体一致，差别只在进程是否存活。
> 沿用 Android P+ ClientTransaction 这套模型，和前面我们聊的启动流程完全复用。

## 整体大链路（A startActivity → B 显示）

```
A Activity 调用 startActivity()
    → Activity.startActivity → Instrumentation
    → IActivityManager（Binder） → ATMS startActivity()
        → ActivityStarter.startActivityUnchecked() 【决策层】
            解析Intent、launchFlags、launchMode
            找/创建TaskRecord、创建B的ActivityRecord
            决定：B放到哪个Task，是否新建Task
        → RootWindowContainer.resumeFocusedTasksTopActivities()
            → Task.resumeTopActivityUncheckedLocked()
                → Task.resumeTopActivityInnerLocked()
                    → mTaskSupervisor.startSpecificActivity(B的ActivityRecord, andResume=true, ...)
```

> 到这里就接上咱们前面讲的 `ActivityTaskSupervisor.startSpecificActivity`

## 重点：**启动新B之前，要先pause当前前台A**

这是页面跳转最关键的一步，很多人忽略：
`resumeTopActivityInnerLocked` 里面，**先暂停旧的前台Activity A，pause完成之后，才允许启动B**

1. ATMS 发起 pause A：构造PauseActivityItem，打包事务发给A所在App进程
2. App主线执行 pause Item → `onPause()`
3. App pause完成后，**回调ATMS（通过IActivityClientController）通知：A已经pause完成**
4. ATMS收到pause完成回调，才继续往下走，执行 `startSpecificActivity` 去启动B

> 一句话：**先pause旧页面A，pause成功，才启动新页面B**

## startSpecificActivity 分两种场景

### 场景1：B和A在**同一个App进程（最常见）**

1. `proc = WindowProcessController`，进程已经存在，`hasThread() = true`
2. 进入 `realStartActivityLocked(B, proc, andResume=true, checkConfig)`
3. 组装 ClientTransaction：
   - LaunchActivityItem（B：new Activity、attach、onCreate、onStart）
   - ResumeActivityItem（B：onResume）
4. 一次Binder把事务发给App进程的ActivityThread
5. App主线程 TransactionExecutor 顺序执行两个Item
    - LaunchItem → B.onCreate、B.onStart
    - ResumeItem → B.onResume
6. handleResumeActivity里 addView(DecorView)，B页面渲染显示

✅ 生命周期顺序：
**A.onPause → B.onCreate → B.onStart → B.onResume**
> A的onStop**不是立刻执行**，A的onStop会在B完全resume之后，ATMS再发StopActivityItem，A才走onStop。

### 场景2：B属于**另外App（跨进程）**

1. `startSpecificActivity` 发现目标进程不存在，调用`startProcessAsync` fork Zygote创建B应用进程
2. B进程启动后，ActivityThread.attach()，把ApplicationThread Binder传给ATMS，WPC保存mThread
3. ATMS再次回调 `startSpecificActivity`，此时进程就绪，执行realStartActivityLocked，发送ClientTransaction启动B
生命周期：
**A.onPause → B（新进程）：onCreate → onStart → onResume**，之后A.onStop

# 👉 A.onStop 什么时候执行？

很多人误区：A onPause完就onStop。**不是！**

1. B成功走到onResume，B页面窗口可见
2. ATMS才会发送StopActivityItem给A所在进程
3. App执行A.onStop
完整生命周期时序（A启动B）：

```
A.onPause
B.onCreate
B.onStart
B.onResume
A.onStop
```

> 如果B是透明/对话框Activity，A不会走onStop，只会onPause。

## 旧版本Android O对比（无ClientTransaction）

A startActivity → ATMS(AMS)

1. 通知A pause（单独Binder schedulePauseActivity）→ A.onPause
2. pause回调回来，AMS调用scheduleLaunchActivity(B) → B onCreate/onStart
3. AMS再调用scheduleResumeActivity(B) → B onResume
4. B resume后，AMS发送scheduleStopActivity → A onStop

## 面试重点坑点

1. **A调用startActivity只是发起Binder请求，A不会直接调用B的任何生命周期**；所有B的生命周期由system_server(ATMS)调度。
2. A.onPause是**同步还是异步？**
    异步。ATMS发起pause之后，等待App回调pause完成，才继续启动B。如果A pause卡住，B就起不来。
3. 为什么B的onCreate在A.onPause之后，但A.onStop在B.onResume之后？
    系统设计：保证新页面成功显示之后，旧页面才完全停止。万一B启动失败，还可以切回A，不用恢复A的onStart。
4. 同进程和跨进程的**生命周期顺序是一样的**，区别仅仅是是否需要fork进程。

## 补充：如果launchMode特殊，比如singleTop / singleTask

ActivityStarter阶段就会处理：

- singleTop：复用B实例，不走onCreate，只会触发onNewIntent，然后resume
- singleTask：会把B上面所有Activity出栈（触发它们onPause、onStop、onDestroy），再resume B
