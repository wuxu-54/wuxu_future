# R8 / Proguard 完整详解（原理、流程、区别，结合前面ReDex对照）

>
> 一句话定位：**Proguard 是老版Java class优化器；R8是Google新一代，替代Proguard，直接把class优化+转dex一步完成；两者都工作在 `.class` 阶段，**不能跨dex全局分析**，这是和ReDex最大分水岭。

## 一、Proguard（前身，AGP3.4之前Android默认）

Proguard 是 **Guardsquare** 开发的通用Java字节码（class）工具，不是Android专属。

### 四大核心阶段（固定流水线）

1. **Shrink 代码缩减（摇树 Tree Shaking）**
 从**入口种子(seed)**开始做可达性分析：Android四大组件、Application、JNI、反射类。
 递归遍历引用图，**没有可达路径的class/method/field全部标记为死代码删除**。>

> 局限：**静态分析，看不懂反射、动态代理、JNI动态调用**，这类代码必须手写 `-keep` 保留。

2. **Optimize 字节码优化**
 对JVM class字节码做重写：
   - 方法内联、死分支删除、常量传播、无用变量消除
   - 简化控制流、删除无用super调用、简化get/put静态字段
   - 多次迭代优化，反复精简
3. **Obfuscate 混淆（名字缩短）**
 保留下来的类、方法、字段，重命名为简短无意义名字：`com.xxx.UserInfo` → `a.b.c`
 好处：
   - 减少字符串长度，class→dex后string_ids体积下降
   - 增加逆向阅读难度
4. **Preverify 预校验**
 给class添加预校验信息，JavaME/高版本JVM需要；Android打包时这个结果基本会被丢弃。

### Proguard 在Android编译链路

```
java/kotlin → javac/kotlinc → .class文件 → Proguard（shrink/optimize/obfuscate）→优化后的.class → dx工具 → classes.dex
```

✅优点：成熟，规则体系（proguard-rules.pro）生态完善。
❌缺点：

1. **只处理class，优化完还要单独dx转dex，两段式，编译慢**
2. 优化目标是JVM栈字节码，**不感知dex、不感知65536方法限制**
3. 不能跨多个最终dex做全局分析（multidex拆分是dx/d8后面才做）
4. 部分JVM优化在转dex后会失效，做了无用功

>
> AGP3.4.0之后Google正式废弃Proguard作为默认，换成R8。**Proguard规则语法R8完全兼容**。

## 二、R8（Android现在默认，minifyEnabled=true开启）

R8是Google自研，**合并了「class优化 + DEX编译」，一步到位，替代Proguard + dx**。

>
> 重点：R8输入是class，输出直接是dex；不再分开两步。

### R8 完整流水线 & 核心原理

```
Java/Kotlin → javac/kotlinc → .class → R8 → classes.dex（可自动multidex拆分）
```

R8 也包含三大核心能力：**代码缩减(shrink)、代码优化(optimize)、混淆(obfuscate)**，同时内置Dex生成器。

#### Step1：收集入口点 + 构建引用图（摇树，和Proguard相似，但更强）

入口种子：AndroidManifest四大组件、Application、keep规则标记的类、native/JNI/反射类。
从种子出发，遍历所有代码引用，建立可达图，**不可达代码全部删除**。

>
> R8会自动带上Android平台默认keep规则，不用手动写四大组件keep。

#### Step2：字节码优化（R8的优化比Proguard更面向Android/DEX）

R8不是优化JVM字节码，**直接在中间IR做优化，最后生成dex指令**，优化更贴合Dalvik/ART：

1. 方法内联：小方法直接把方法体嵌入调用处，消除method引用，减少method_ids条目（直接缓解65536方法超限）
2. 类合并 Class Merging：把无继承关系、简单的多个类合并成一个，减少class数量、减少type_id
3. 虚方法去虚拟化 Devirtualization：如果虚方法没有重写，改成直接方法调用，减少虚表开销
4. 常量传播、死代码分支删除、无用字段消除、删除空类
5. 接口剥离：只做标记的空接口直接移除
6. 控制流简化，减少指令数量

>
> 这里的优化，**天然会减少method/field/type数量，直接降低dex体积**。

#### Step3：混淆（重命名）

和Proguard语法完全一致，`-keep` `-keepclassmembers` 等规则通用。
将类、方法、字段重命名短名字，减少字符串常量体积，增加逆向难度。

#### Step4：生成DEX，自动multidex拆分（D8能力，R8内置D8）

如果优化后总method_ids超过65535，R8内置D8，自动拆分为classes.dex、classes2.dex。
⚠️**重点坑：R8/D8拆分multidex的策略是简单贪心，只保证main dex放四大组件，不会做跨dex引用聚类**
👉这就是为什么大App做完R8之后，multidex依然存在大量跨dex引用，**ReDex的InterDexPass才有上场空间**。

### R8 和 D8 的区分（面试高频）

- **D8：只做class→dex编译，不做代码缩减、混淆、高级优化；只基础精简**
- **R8 = D8 + 代码缩减 + 代码优化 + 混淆**
`minifyEnabled true` 开启R8；false，只启用D8。

## 三、R8 vs Proguard 对比表

| 项目 | Proguard | R8 |
| --- | --- | --- |
| 开发方 | Guardsquare | Google |
| 处理对象 | JVM .class字节码 | 内部IR，直接输出DEX |
| 编译链路 | class→Proguard→class→dx→dex | class→R8→直接dex，一体化 |
| Android适配 | 通用Java工具，后适配Android | 专为Android/ART设计 |
| multidex | 不处理，dx后续拆分 | 内置D8，自动拆分多dex |
| 优化针对性 | JVM栈虚拟机优化 | 面向Dalvik寄存器虚拟机，优化更贴合dex |
| keep规则 | proguard规则 | **完全兼容Proguard规则** |
| AGP版本 | 3.4之前默认 | 3.4+ 默认，minifyEnabled=true启用 |
| 编译速度 | 慢（两段流程） | 更快，减少中间IO |

## 四、R8 / Proguard 与 ReDex 的本质区别（非常关键，串联你前面问的dex重排）

>
> 很多面试会一起问：R8和ReDex的区别

1. **阶段不同**
   - R8/Proguard：**Class阶段**。在生成dex**之前**，删除代码、内联、混淆，**控制每个类内部代码**；输出dex。
   - ReDex：**DEX阶段**。R8已经生成好dex之后，读取全部dex，**跨多个dex全局分析**，重新把类分配到不同dex（InterDexPass）。
2. **能力边界**
   - R8：可以删代码、合并类、减少method总数；**但是一旦拆分成多个dex，R8不会再调整类在各个dex之间的分布**。R8的multidex拆分只是简单划分，不考虑跨dex引用冗余。
   - ReDex：**不能删除代码**（一般不会做摇树）；核心是**重排多dex之间的类归属，降低跨dex引用，消除多个dex重复的type/method/string索引**。
3. **收益侧重点**
   - R8：减少**总方法/类数量**，从源头减少代码总量。
   - ReDex：**总类/方法数量不变**，只是重新分组，消除多dex索引重复，减少dex文件体积；附带FDO类顺序重排优化冷启动。

>
> 完整大厂打包链路（抖音/FB）：
> `源码 → javac → class → R8（摇树、内联、混淆，输出多dex）→ ReDex（InterDex重排聚类、dex优化）→ APK → zipalign+签名`

## 五、R8 核心keep规则原理（为什么反射会崩）

R8做可达性分析是**静态字节码分析**：

- 直接代码调用（`obj.foo()`）可以识别并保留；
- 反射 `Class.forName` / `getDeclaredMethod`、JNI、动态代理、WebView JS调用：**R8无法静态知道哪些类会被动态加载**，会认为这些类不可达，直接删除或者混淆名字，运行就崩溃。

因此必须用 `-keep` 规则告诉R8：**不要删除、不要重命名这些类/成员**
常用规则：

```
# 保留类，类名不混淆，类里面成员也保留
-keep class com.xxx.bean.** { *; }
# 保留类的成员，类名可以混淆
-keepclassmembers class com.xxx.** {
   @android.webkit.JavascriptInterface <methods>;
}
```

>
> keep规则粒度越宽泛（`{*;}`），R8摇树收益越小，包体积越大。

## 六、R8的局限

1. **没有跨dex全局分析能力**，multidex拆分策略简单，多dex场景会产生大量跨dex引用冗余（ReDex解决这个）
2. 静态分析，无法识别反射、动态代码，需要大量维护keep规则
3. **不能修改同一个dex内部class的顺序，不能做FDO类布局**（Baseline Profile可以做dex内类顺序优化，ReDex也支持FDO）
4. 优化发生在dex生成前；dex一旦生成，R8不再介入

## 七、一句话极简总结

1. **Proguard：老的class级Java优化器，class优化完交给dx转dex，AGP3.4前使用**；
2. **R8：新一代一体化工具，替代Proguard+dx；输入class，做摇树、代码优化、混淆，直接输出dex；可以自动multidex，但不会全局跨dex聚类**；
3. **R8在dex生成前做代码瘦身；ReDex在dex生成后，做多dex之间类重排，消除索引冗余，两者是互补关系，不是替代。**
