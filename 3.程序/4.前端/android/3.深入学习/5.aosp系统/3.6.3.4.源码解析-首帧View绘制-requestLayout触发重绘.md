# requestLayout 百分百会触发measure和layout吗？

## 一句话结论

**不是百分百一定会完整执行整棵View树的 measure + layout；requestLayout只是打标记，最终是否执行、遍历多少View，由`performTraversals`和View的标记位控制。**
> 很多面试坑：requestLayout**一定会设置PFLAG_FORCE_LAYOUT标记**，向上递归父View直到ViewRootImpl，标记`mLayoutRequested=true`，并且调用`scheduleTraversals`等待VSync。
> 但有**短路跳过、部分遍历、提前返回**场景。

## 一、requestLayout 内部做了什么（源码）

```java
public void requestLayout() {
    if (!isLayoutRequested()) {
        mPrivateFlags |= PFLAG_FORCE_LAYOUT;
        mPrivateFlags |= PFLAG_INVALIDATED;
        if (mParent != null && !mParent.isLayoutRequested()) {
            mParent.requestLayout(); // 向上传递
        }
    }
}
```

1. 给自己打上 `PFLAG_FORCE_LAYOUT`（强制layout标记）；
2. 如果父View还没有标记，递归向上调用父View.requestLayout，**一直传到ViewRootImpl**；
3. ViewRootImpl收到后，标记 `mLayoutRequested = true`，调用`scheduleTraversals()`，注册VSync回调。

> ⚠️ 重点：**requestLayout本身不会立刻执行measure/layout，只是打标记，等待下一次VSync触发performTraversals**。

## 二、performTraversals 里判断是否走measure、layout

`performTraversals`里面：

```java
if (mLayoutRequested) {
    // 需要执行measure+layout
    performMeasure(...);
    performLayout(...);
    mLayoutRequested = false;
}
```

**只要 mLayoutRequested=true，根DecorView一定会走一次measure和layout遍历**，但这里还有两个重要细节：

### 1. 不是所有子View都会执行onMeasure

measure是自上而下递归，但每个View内部会判断：
`View.measure()` 里面判断：如果**没有PFLAG_FORCE_LAYOUT，并且尺寸约束没有变化，就可以直接跳过onMeasure，复用旧的mMeasuredWidth/mMeasuredHeight**。
> requestLayout只会给**调用requestLayout的View以及它所有祖先**打上PFLAG_FORCE_LAYOUT，**不会给全部子View强制打标记**。
> 子View如果没有这个标记，且MeasureSpec没变，就直接跳过onMeasure。

👉 举例：
LinearLayout里有3个子View，只给子ViewA调用`requestLayout()`

- ViewA、LinearLayout、DecorView 打上 PFLAG_FORCE_LAYOUT
- performMeasure开始遍历
- 走到ViewA：有标记 → 执行onMeasure
- 子ViewB、C：没有PFLAG_FORCE_LAYOUT，MeasureSpec不变 → **直接跳过onMeasure**

**所以：整棵树的measure方法会递归走一遍，但很多子View的onMeasure可以被跳过。**

### 2. layout阶段：同理，PFLAG_FORCE_LAYOUT控制是否执行onLayout

performLayout调用`decorView.layout()`，递归子View。

- 只有带PFLAG_FORCE_LAYOUT的View，才会真正执行onLayout；
- 普通子View如果位置没有变化，可以跳过onLayout。

## 三、requestLayout 被短路、完全不执行measure/layout的场景（高频考点）

### 场景1：**正在layout过程中，重复调用requestLayout**

当当前正在执行layout遍历（onLayout执行期间），此时mParent.isLayoutRequested()已经=true，requestLayout里的判断直接return，**不会重复打标记、不会再scheduleTraversals**。
> 也就是：**layout流程还没结束的时候多次requestLayout，只会生效一次，多余的直接丢弃，不会触发新一轮measure/layout**。

```java
// requestLayout第一行判断
if (!isLayoutRequested()) {
    // 才打标记向上传递
}
```

如果`isLayoutRequested() = true`，直接return，啥也不干。

### 场景2：View已经 detached，没有父View（mParent==null）

比如View还没addView，或者已经removeView，mParent=null，requestLayout打标记后，**不会向上走到ViewRootImpl，不会scheduleTraversals，后续不会触发任何measure/layout**。

### 场景3：窗口不可见、ViewRootImpl被暂停，traversals被阻塞

窗口不可见时，scheduleTraversals不会执行doTraversal，标记虽然打上，但`performTraversals`不会被执行，measure/layout不会跑。

## 四、requestLayout 和 invalidate 的关键对比（顺带巩固）

1. **requestLayout**：打`PFLAG_FORCE_LAYOUT`、`mLayoutRequested=true`，**触发measure+layout；draw不一定执行**。只有layout前后View的l,t,r,b坐标发生变化，才会自动invalidate触发draw。
2. **invalidate**：打PFLAG_INVALIDATED，**只触发draw，不会走measure/layout**。

## 五、面试标准答案（精简背诵）

1. `requestLayout()` 本身**不会立刻执行measure/layout**，只是给当前View和向上所有父View打上`PFLAG_FORCE_LAYOUT`标记，一直到ViewRootImpl，标记`mLayoutRequested=true`，并且调度下一次VSync回调执行`performTraversals()`。
2. 若在layout过程中重复调用requestLayout，因为`isLayoutRequested()`已经为true，**直接短路丢弃，不会新增一轮measure/layout**。
3. VSync到来，`performTraversals`发现`mLayoutRequested=true`，会启动根View的measure、layout遍历；**但不是所有子View都一定会执行onMeasure/onLayout**，子View若无FORCE_LAYOUT标记、MeasureSpec不变，则直接跳过onMeasure复用旧尺寸。
4. 如果View没有挂载到窗口（mParent=null），requestLayout打标记但**永远不会执行measure/layout**。

> 一句话精简版：
> requestLayout**会标记需要布局，在下一帧触发根View的measure+layout遍历；但重复调用会被短路，子View不一定全部执行onMeasure，View未挂载时完全不执行。所以不能说百分百完整重走全部View的measure和layout**。
