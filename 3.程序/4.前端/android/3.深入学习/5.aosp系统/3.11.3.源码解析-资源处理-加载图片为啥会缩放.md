# 一句话核心原因

**mdpi、hdpi这些标记，定义的是：这张图片设计时，对应的基准物理密度。系统会根据【图片的基准密度】和【当前手机屏幕密度】，算出缩放比例，自动缩放Bitmap，保证图片在不同设备上，视觉尺寸（dp）一样大。**

> dp：密度无关像素。`1dp` 在 mdpi(160dpi) 上 = 1px；
> 公式：`px = dp * (dpi / 160)`

## 1. 先定义两个关键值

- **inDensity**：图片资源本身的基准密度（文件夹对应的dpi）
  - drawable-mdpi → inDensity = 160
  - drawable-hdpi → inDensity = 240
  - drawable-xhdpi → inDensity = 320
  - drawable-xxhdpi → inDensity = 480
- **inTargetDensity**：当前设备屏幕的 densityDpi（目标密度）

**缩放比例 scale = inTargetDensity / inDensity**
> 加载Bitmap的时候，系统底层会把这个scale传给BitmapFactory，自动缩放像素。

## 2. 例子：mdpi图片放到xxhdpi手机

mdpi图片：inDensity=160
xxhdpi设备：inTargetDpi=480
scale = 480 / 160 = **3倍**

- 假设原图是 100px ×100px（放在mdpi，设计目标是 100dp ×100dp）
- 在xxhdpi设备加载后，Bitmap像素变成 300px × 300px

> 视觉大小不变：都是100dp，但是像素被放大3倍。
> ⚠️ 缺点：原图像素不够，放大后模糊。

再举个反向例子：
xxhdpi图片（inDensity=480），xhdpi设备 target=320
scale = 320 / 480 = 0.666，图片缩小。像素变少，清晰度几乎不受影响。

## 3. 为什么Android要做自动缩放？目标：统一dp尺寸

设计师画图标，用dp来定**视觉大小**，而不是固定像素px。

- 目标：**同一个图标，在160dpi手机和480dpi手机，看起来一样大**
- mdpi 100px = 100dp
- 在xxhdpi屏幕，想要保持100dp，就需要300px的像素。

如果你只放mdpi一套图：
原图只有100px，系统只能把像素拉伸到300px，填满100dp的区域。

> 如果系统**不自动缩放**会发生什么？
> mdpi的100px图片，在xxhdpi手机上，1px依然占屏幕1个物理像素，图片只会显示很小，只有原来1/3视觉大小。用户看图标就会特别小。

## 4. 源码层面简单看 BitmapFactory 缩放逻辑

```java
// Resources 加载图片底层逻辑简化
BitmapFactory.Options opts = new BitmapFactory.Options();
// 资源文件夹带来的基准密度
opts.inDensity = 160; // mdpi
// 当前设备屏幕密度
opts.inTargetDensity = 480;
// 开启自动缩放，默认true
opts.inScaled = true; 

Bitmap bitmap = BitmapFactory.decodeResource(res, id, opts);
```

`inScaled=true` 是默认开启。
BitmapFactory 内部计算缩放比例，解码图片的时候直接生成缩放后的Bitmap。
> 注意：**缩放是解码图片的时候就做了，不是绘制的时候动态拉伸。会占用更大内存！**
> mdpi 100×100图片加载到xxhdpi设备，解码出来是300×300像素，内存占用是9倍！

## 5. 特殊情况：关闭自动缩放

- 如果把 `inScaled = false`，系统**不再自动缩放Bitmap**。
  inDensity、inTargetDensity失效，图片原始像素不变。
  此时100px mdpi图片，在xxhdpi屏幕上，视觉尺寸会变小。

## 6. 结合前面DPI资源选择规则串起来

1. 运行时根据设备densityDpi，按特殊规则挑选图片（优先大图缩小）
2. 拿到图片后，读取这个图片所在drawable文件夹对应的inDensity
3. 用 `scale = targetDensity / inDensity`，解码Bitmap自动缩放
4. 保证最终渲染出来的**dp尺寸保持一致**

## 面试精简口述

自动缩放的目的：保证图片在不同密度屏幕上**视觉dp大小一致**。
系统会拿到图片文件夹对应的基准密度inDensity，以及设备屏幕目标密度inTargetDensity，缩放比例 = targetDensity / inDensity。
mdpi（160）图片在xxhdpi(480)设备，比例等于3，图片像素放大3倍。放大图片会模糊，同时占用更多内存；所以资源匹配规则优先选择更高密度原图，做缩小而不是放大。
BitmapFactory的inScaled默认true，解码图片阶段就完成像素缩放。

# 为什么推荐以 xxhdpi（480dpi）作为主力资源图，以及对应的内存坑

## 1. 先回顾基础

- xxhdpi = 480dpi，`inDensity=480`
- 当前绝大多数手机屏幕密度落在 **360～480dpi** 区间（国内主流安卓手机）

> 按照前面DPI资源选择规则：设备360dpi，会优先选 >=360dpi 里最小的图，也就是 xxhdpi(480)，然后**缩小渲染**。

### ✅ 选xxhdpi原图的好处

1. **缩小不会模糊**
图片缩小是像素采样压缩，信息损失很小；反过来小图放大是插值补像素，容易发虚、有锯齿。
设计师给xxhdpi图，在大多数手机上是**缩小展示**，图标清晰。

2. 覆盖绝大多数主流机型
市面上大部分手机densityDpi：360、400、420、440、480，xxhdpi都能覆盖。

> 设备480dpi：刚好1:1使用原图，不缩放。
> 设备360dpi：480原图缩小到360，清晰度保留。

3. 减少多套图片维护成本
如果只放一套xxhdpi图，不用维护mdpi/xhdpi多套图片，减少包体积。

> 很多App现在策略：**只保留一套xxhdpi drawable资源**，删掉mdpi、hdpi、xhdpi。

# ⚠️ 巨大内存坑（面试高频重点）
>
> 关键点：**缩放发生在Bitmap解码阶段；解码生成的Bitmap像素大小 = 原图像素 × scale**
> scale = targetDensity / inDensity

举例子：
xxhdpi目录下一张原图：**480 × 480 px**
inDensity=480

场景1：设备480dpi
scale = 480 / 480 = 1
解码出来Bitmap：480 × 480。
内存：480*480*4字节(ARGB8888) ≈ 921KB

场景2：设备360dpi
scale = 360 / 480 = 0.75
解码Bitmap：480 * 0.75 = 360px → 360×360。
内存：360*360*4 ≈ 518KB。
👉 这是好情况，缩小，内存更小。

> 很多人以为坑在这里结束，**真正坑：如果你把xxhdpi图，放到mdpi目录！**
图片文件本身是480×480px，但是放在 `drawable-mdpi`，inDensity=160，跑在480dpi手机：
scale = 480 / 160 =3
Bitmap像素 = 480 × 3 = 1440 ×1440
内存：1440*1440*4 ≈ **8MB**
图片文件本身只有几十KB，加载进内存暴涨十几倍，极易OOM！

## 重点：只保留xxhdpi一套资源的内存风险

如果项目**全部图片只放xxhdpi**，遇到超高密度设备，比如部分旗舰机 `densityDpi=560 / 640`（xxxhdpi级别）：

- 设备560dpi，资源只有xxhdpi(480)
- 资源选择规则：没有>=560的图，只能选现有最大的480。
- scale = 560 / 480 = 1.166倍
- 原图480×480 → 解码出来 560×560，**图片被放大**，内存变大，画质轻微损失。

> 这种机型占比少，业务上可以接受。

## 另一个坑：大图（背景图、banner）

比如一张xxhdpi的banner原图：1080 × 1920
在480dpi设备，解码出来就是1080×1920，ARGB8888内存：
1080*1920*4 ≈ **8MB**
如果没有做inSampleSize采样压缩，页面很多大图叠加，很容易OOM。

> 划重点区分两个概念：
>
> 1. **资源自动缩放（inScaled=true）**：是系统根据density自动做，**针对Resources.getDrawable加载资源图片**
> 2. **inSampleSize**：手动采样压缩，**手动decodeStream时自己控制**，二者互不冲突。

## 关闭自动缩放的使用场景（inScaled=false）

```java
BitmapFactory.Options opts = new BitmapFactory.Options();
opts.inScaled = false;
```

此时`inDensity/inTargetDensity`不再生效，解码出来就是图片原始像素，**不会自动缩放**。
适合场景：

- 图片本身是作为原始素材，不需要适配dp尺寸（地图纹理、自定义滤镜素材）
⚠️ 弊端：在高DPI手机上，图片视觉尺寸会变小，需要自己手动处理缩放。

## 工程上的优化方案（实际项目怎么做）

1. 小图标：统一放xxhdpi一套，删除其他dpi目录，减少APK包体积。图标尺寸不大，内存压力可控。
2. 大图、banner、背景图：**不要放在res/drawable**，放到assets目录。
    assets里的图片**不会走资源自动缩放**！
    assets读取是自己用BitmapFactory.decodeStream，自己通过inSampleSize手动采样控制内存。
3. 大图优先使用webp，减少安装包体积。
4. 图片Glide/Coil加载：图片框架内部会override缩放逻辑，做采样、内存复用，进一步规避OOM。

## 面试一句话总结

现在主流方案用xxhdpi做主图，因为大部分手机屏幕密度≤480，资源匹配后是**大图缩小展示，画质好**。
但要注意内存：res下drawable图片加载会根据inDensity自动缩放生成Bitmap；如果放错文件夹，高倍放大后内存会爆炸。
大尺寸背景图不要放在drawable，建议放到assets，规避系统自动缩放，自己手动采样压缩，防止OOM。

## 配套面试追问预判

1. 问：assets里图片会不会触发inDensity自动缩放？

> 答：不会。assets不是aapt管理的资源，没有绑定inDensity，BitmapFactory默认不会自动缩放，像素是原图大小。

2. 问：Glide加载res/drawable图片，还会触发系统自动缩放吗？

> Glide会读取资源的inDensity，但是内部会做采样和降采样，控制最终Bitmap内存，避免原生Resources加载的内存坑。
