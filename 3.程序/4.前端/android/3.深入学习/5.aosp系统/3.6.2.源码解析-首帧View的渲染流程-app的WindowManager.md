# APP的WindowManager

APP会创建一个全局的Context，这个Context维护很多服务接口
>注意这是本地接口，其内部有引用到SystemServer的本地binder代理。不是全部代理都有类似的接口写法，这么做只是为了做封装。

1. PhoneWindow在Activity的attach方法里创建，并设定WindowManager(这是个接口，具体实现类是WindowManagerImpl)
2. WindowManagerImpl 有WindowManagerGlobal实例（这个内部有SystemServer里WindowManagerService的BinderProxy）
3. Activity的SetContentView调用到PhoneWindow的同名方法，创建DecorView对象。

# 一句话答案

Q:

(WindowManager)context.getSystemService(Context.WINDOW_SERVICE),

这个是在 Activity 里获取 system server 进程的 WindowManagerService 的 binderproxy 吗？

A：

**不是每个远程服务，都会在App进程侧单独有一个包装门面类（你说的不是底层 BinderProxy，是上层Java封装门面，类似 WindowManagerImpl）；看系统服务的设计方式，分两种风格：**

> 先把概念对齐，区分三层（非常关键）

1. **底层：BinderProxy（native层）**
    ServiceManager拿到远程服务的binder句柄，在app进程native层生成`BinderProxy`，是AIDL Stub对应的跨进程底层代理，**所有Binder跨进程调用最终都走它**，这个一定存在。
2. **AIDL生成的Java接口代理（`XXX.Stub.Proxy`，Java层AIDL代理）**
    只要用AIDL定义跨进程接口，编译自动生成 `XXX.Stub.Proxy` 类。这一层**只要是AIDL服务就一定有**。它调用底层BinderProxy做IPC。
3. **上层门面包装类（你关心的：类似 WindowManagerImpl、ActivityManagerImpl）**
    👉 **这个不是必有的！属于Android系统额外封装，AIDL本身不会自动生成。**

## 两种系统服务模式

### 模式1：有额外上层门面包装类（WindowManager、ActivityManager）

例子：

```java
// getSystemService拿到的
WindowManager → WindowManagerImpl
ActivityManager → ActivityManagerImpl
```

结构：
`App代码` → 门面包装类（WindowManagerImpl，本地Java对象，App进程） → AIDL Proxy(IWindowManager / IWindowSession) → BinderProxy → system_server的WMS/AMS

特点：

- 对外暴露**简化后的高层接口**（WindowManager，ActivityManager），隐藏AIDL原生复杂接口；
- 在门面类里面做本地缓存、参数校验、统一管理资源（比如WindowManagerGlobal管理ViewRootImpl）；
- 属于Android Framework为了方便开发者，**手动写的封装，AIDL不自动生成**。

### 模式2：**没有上层门面包装类，直接使用AIDL Proxy**

很多系统服务没有这一层包装，App拿到就是AIDL的`XXX.Stub.Proxy`，没有额外门面。

举例子：
`IBatteryService`、`ISensorService`、`IMediaPlayerService`。
用法一般是：

```java
// 直接从ServiceManager获取，拿到的就是AIDL Proxy，没有额外包装门面
IBatteryService batteryService = IBatteryService.Stub.asInterface(
        ServiceManager.getService("battery"));
batteryService.getBatteryCapacity();
```

调用链路：
`App代码` → AIDL Proxy → BinderProxy → system_server里面的BatteryService
✅ 中间**没有类似WindowManagerImpl的包装类**。

# 总结规则

1. **AIDL生成的 `XXX.Stub.Proxy`：只要AIDL远程服务，一定存在（Java层AIDL代理）**
2. **你问的这种高层门面包装类（WindowManagerImpl这种）：不是必须的，看Framework设计**
    - 面向App开发者、API复杂、需要本地资源管理（窗口、Activity管理） → 加门面包装（WindowManagerImpl / ActivityManagerImpl）
    - 底层硬件/简单服务，接口少，不需要本地缓存管理 → **直接暴露AIDL Proxy，不加门面**

## 再澄清容易混淆的点
>
> WindowManagerImpl ≠ BinderProxy，也不等于 IWindowManager.Stub.Proxy
> WindowManagerImpl：纯本地Java包装对象，**没有跨进程能力**，内部持有AIDL代理对象。

```
getSystemService(WINDOW_SERVICE) → WindowManagerImpl（门面包装，可选层）
    内部用到 IWindowSession（AIDL Stub.Proxy，AIDL自动生成，必有的一层）
        底层调用 native BinderProxy（内核binder通信底层，必有的）
```

## 面试精简一句话背诵

AIDL定义的远程服务，**一定会有AIDL自动生成的`XXX.Stub.Proxy`**；但是像`WindowManagerImpl`这种框架手动写的上层门面包装类，**不是每个远程服务都具备，是Android为简化上层API、增加本地管理能力而额外封装的**。

## 延伸追问（你大概率会遇到）

Q：为什么AMS/WMS这种复杂系统服务要多加一层门面类？

1. 封装复杂AIDL接口，对外提供简单易用API；
2. 在App进程维护本地缓存、资源管理（ViewRootImpl、进程记录）；
3. 做参数校验、异常统一处理，减少跨进程无效调用；
4. 接口兼容、版本适配，把AIDL底层变更屏蔽在上层门面内部。
