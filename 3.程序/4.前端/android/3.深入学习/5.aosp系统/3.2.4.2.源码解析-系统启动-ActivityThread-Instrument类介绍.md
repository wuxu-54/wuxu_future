# Instrumentation 类介绍

`android.app.Instrumentation`，**Android App的“插桩/监控外壳”**，核心定位：**接管应用整个生命周期与组件的创建、启动，在四大组件执行前后插入自定义逻辑**。

>
> 它是Android框架层的类，不是App普通业务类；**默认每个App启动都会有一个Instrumentation实例**，ActivityThread持有它。

## 一句话作用

**框架在创建Activity、启动组件、调用生命周期方法时，不直接new/调用，而是交给Instrumentation去执行。你可以替换这个Instrumentation，实现AOP：监听、拦截、替换组件行为。**

## 在哪里初始化（和前面ActivityThread串联）

`ActivityThread` 里面持有成员：

```
Instrumentation mInstrumentation;
```

App启动流程：
`ActivityThread.main()` → 创建ActivityThread → `thread.attach()` → **初始化mInstrumentation**。
默认用 `android.app.Instrumentation` 原生实现；
**测试框架（JUnit、Espresso、AndroidX test）会替换成自定义Instrumentation**。

## 核心职责（原生Instrumentation默认实现）

原生Instrumentation就是一个代理，**默认只是透传，不做额外操作**。

### 1. 创建Activity（最重要方法）

```
public Activity newActivity(ClassLoader cl, String className, Intent intent)
```

AMS通知App启动Activity时，ActivityThread不会直接new Activity；
**调用 mInstrumentation.newActivity() 来实例化Activity对象**。
👉 自定义Instrumentation可以在这里：拦截、替换类、包装Activity。

### 2. 调用Activity生命周期

```
public void callActivityOnCreate(Activity activity, Bundle icicle)
public void callActivityOnStart(Activity activity)
public void callActivityOnResume(Activity activity)
public void callActivityOnPause(Activity activity)
public void callActivityOnDestroy(Activity activity)
```

Activity的`onCreate/onStart/onResume`**不是ActivityThread直接调用，全部走Instrumentation**。

>
> 这就是测试框架能在生命周期前后插桩的根源。

### 3. Application创建与生命周期

```
public Application newApplication(ClassLoader cl, String className, Context context)
public void callApplicationOnCreate(Application app)
```

Application对象也是Instrumentation负责实例化，调用`onCreate`。

### 4. 启动Activity、发送Intent

```
public ActivityResult execStartActivity(
        Context who, IBinder contextThread, IBinder token, Activity target,
        Intent intent, int requestCode, Bundle options)
```

App里调用`startActivity`，底层最终走到Instrumentation.execStartActivity，再通过Binder调用AMS。

>
> 可以拦截startActivity，修改Intent、阻止跳转。

### 5. 监控事件、注入按键事件

```
public boolean sendKeySync(KeyEvent event)
```

可以模拟按键、触摸事件注入，自动化测试靠这个。

## 两大使用场景

### 场景1：Android自动化测试（最常用）

Espresso / AndroidJUnitRunner 的原理：

1. 测试apk指定**自定义InstrumentationRunner**
2. App进程启动时，替换系统默认Instrumentation为自定义TestInstrumentation
3. 拦截Activity创建、生命周期、startActivity
4. 注入点击、输入事件，断言页面UI，做自动化测试

>
> 这种叫 **Instrumentation测试**，跑在**同一个App进程里面**，和App代码同进程，所以可以直接访问App内部变量。
> 区别：UiAutomator是跨进程。

### 场景2：业务/监控SDK，自定义Instrumentation（埋点、AOP）

很多性能监控、页面埋点框架，**自定义Instrumentation**，用来：

- 监听Activity创建、onCreate、onResume，自动统计页面启动耗时、页面埋点
- 拦截startActivity，统一拦截路由、日志上报
- 替换Application/Activity类，做hook

>
> ⚠️ 限制：**普通release App不能直接随便替换Instrumentation！**
> 想要替换Instrumentation，需要在AndroidManifest配置`<instrumentation>`标签；普通第三方App动态替换Instrumentation属于非官方hack，高版本Android会限制。

## 关键执行时序，绑定你前面ActivityThread整套流程

```
bindApplication()
    → mInstrumentation = new Instrumentation() // 初始化
    → mInstrumentation.newApplication()  // 创建Application对象
    → mInstrumentation.callApplicationOnCreate(app) // 调用Application.onCreate

启动Activity时：
ActivityThread.handleLaunchActivity
    → mInstrumentation.newActivity() // new Activity实例
    → mInstrumentation.callActivityOnCreate()
    → mInstrumentation.callActivityOnStart()
    → mInstrumentation.callActivityOnResume()
```

✅ 所有组件实例创建、生命周期回调，**全部经过Instrumentation代理层**。

## Instrumentation 和你前面学的几个概念对比

1. **JVMTI Agent（handleAttachAgent）**：ART虚拟机层面插桩，hook方法字节码；
2. **Instrumentation**：**Framework组件层面AOP**，在四大组件创建、生命周期、启动入口拦截，**不是字节码插桩**，是框架设计好的代理点。

>
> 两者可以搭配使用：Instrumentation监听组件，JVMTI做方法级插桩。

## 重要限制 & 误区

1. ❌ 不是随便就能替换
自定义Instrumentation需要manifest声明，一般用于测试；普通线上App不能轻易替换。
2. ❌ 只能拦截四大组件相关入口
普通业务方法、子线程逻辑它管不到，这部分要靠JVMTI/ASM。
3. ❌ Instrumentation跑在App主线程
拦截逻辑不要做耗时操作，否则会ANR。
4. ✅ 原生默认Instrumentation只是透传，没有任何拦截逻辑，只是预留扩展点。

## 精简总结

1. `Instrumentation`是Android框架提供的**组件代理层**，ActivityThread持有它。
2. Application、Activity实例创建，所有生命周期回调、startActivity调用，**都由Instrumentation负责执行**。
3. 原生实现只是透传；替换自定义Instrumentation可以实现组件AOP。
4. 主要用途：**Instrumentation自动化测试；页面监控/埋点SDK**。
