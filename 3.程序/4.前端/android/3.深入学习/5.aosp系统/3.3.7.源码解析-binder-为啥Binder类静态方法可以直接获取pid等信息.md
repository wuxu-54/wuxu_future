# 一、Binder 驱动是什么

Binder 是 **Android 内核中的字符设备驱动**，设备文件 `/dev/binder`（新版 binderfs：`/dev/binderfs/binder`），是 Android 整套 IPC 的内核基础设施，专门用来做跨进程通信。
> 传统 Linux IPC：pipe、socket、mmap、消息队列；Android 单独自研 Binder，核心优势：**一次内存拷贝、内核自带身份校验、支持传递对象引用、服务注册查找（ServiceManager）**。

Binder整体分层：

1. **内核层：binder驱动（binder.c）**，`/dev/binder`，负责内存映射、事务转发、进程/线程管理、身份记录；
2. **Native层：libbinder.so**（`IPCThreadState`、`ProcessState`），封装驱动ioctl，Binder线程池；
3. **Java层：android.os.Binder / IBinder**，JNI桥接到libbinder，AIDL基于它生成Stub/Proxy。

# 二、android.os.Binder 类【静态方法大全 + 作用】

`android.os.Binder`：**Binder服务端本地对象基类（Stub继承它）**，里面一批**静态native方法**，就是你前面问的 `getCallingPid` 所在类。
> 重点重申：**静态方法本身不存储数据；读取的信息保存在当前线程TLS的IPCThreadState，所以并发多个AIDL事务互不干扰**。

## ✅ Binder 静态方法（Framework常用）

```java
// 1. 获取本次IPC调用方PID（内核自动填充到事务，存入TLS）
public static native int getCallingPid();

// 2. 获取本次IPC调用方UID（权限校验核心，不可伪造）
public static native int getCallingUid();

// 3. 清空当前线程的IPC调用身份，返回token；用于权限降级
public static native long clearCallingIdentity();

// 4. 配合上面，恢复之前保存的调用身份，必须finally里面调用，成对使用
public static native void restoreCallingIdentity(long token);

// 5. 清除work source（用于功耗统计，追踪是谁触发的Binder调用）
public static native long clearCallingWorkSource();
// 6. 恢复work source
public static native void restoreCallingWorkSource(long token);

// 7. 判断当前线程是否正在处理Binder IPC事务
public static native boolean isBinderThread();

// 8. 把Binder对象转为弱引用（death通知相关）
public static native void flushPendingCommands();

// 9. 等待Binder驱动pending指令
public static native void joinThreadPool();
```

### 核心4个重点静态方法（AMS/WMS/PMS高频）

1. **getCallingPid()**：拿到发起IPC的远程进程PID；**仅在Binder事务栈内有效**，普通线程拿到自己pid。
2. **getCallingUid()**：远程调用方UID，**权限校验优先用UID**，内核不可篡改。
3. **clearCallingIdentity()**
    场景：AMS收到App的IPC，AMS内部又去调用其他本地服务，如果不清身份，**内部调用会继承App的UID，权限越界**。

    ```java
    long token = Binder.clearCallingIdentity();
    try {
        // 这里getCallingUid变成system_server自己的uid(1000)
        // 执行系统内部逻辑
    } finally {
        Binder.restoreCallingIdentity(token);
    }
    ```

4. **restoreCallingIdentity(token)**：恢复TLS里保存的calling uid/pid。

> 一句话理解静态API：这些静态native方法，底层都是调用 `IPCThreadState::self()`，拿到**当前线程TLS的IPCThreadState实例**，读写里面保存的本次IPC事务信息。
> 静态只是**方法属于类，不属于实例**；**数据在线程私有TLS，不是全局static变量**，多线程并发AIDL不会串数据。

# 三、Binder内核驱动工作原理（核心）

## 3.1 进程打开 /dev/binder + mmap（最关键：一次拷贝来源）

1. 进程打开 `/dev/binder`，拿到fd；
2. 调用 `mmap`，在内核分配一块内核缓冲区，**映射到本进程用户虚拟地址空间**；

> ✅ 这块内核缓冲区，是客户端、内核共享的内存区域。
> IPC数据：**只从客户端用户空间拷贝1次到内核这块共享缓冲区**；服务端进程直接访问这块内核映射内存，**不再二次拷贝** → 这就是Binder著名的**一次拷贝**。

## 3.2 驱动核心内核结构体（binder.c）

1. `struct binder_proc`：**每打开/dev/binder的进程，内核创建一个binder_proc**，保存进程所有binder信息、mmap内存、binder_node链表、binder_ref链表。
2. `struct binder_thread`：**进程里每一个binder工作线程，内核对应一个binder_thread**；每个线程有等待队列，阻塞等待binder事务。
3. `struct binder_node`：**服务端Binder实体（Stub对象）在内核的代表**。
    当system_server注册AMS服务，驱动创建binder_node；代表这个本地Binder对象。
4. `struct binder_ref`：**客户端侧对远端binder_node的引用（句柄handle）**。客户端拿到的IBinder代理，内部持有handle，内核通过handle找到远端binder_node。
5. `struct binder_transaction`：**一次IPC事务**，保存：源进程、目标进程、目标binder_node、calling_pid、calling_uid、数据、flags。

> 内核在收到客户端IPC请求时，**自动提取调用方task_struct里pid、uid写入binder_transaction**。事务被送到目标进程的todo队列。

## 3.3 一次完整Binder IPC流程（App调用 AMS.attachApplication）
>
> 客户端：App进程；服务端：system_server（AMS）

1. **App（客户端）**
    - `IActivityManager.Proxy.attachApplication` → 打包参数到Parcel；
    - 调用 `transact`，libbinder封装`binder_write_read`，ioctl发给binder驱动；
    - 驱动把App用户态数据**拷贝一次**到内核mmap共享缓冲区；
    - 内核构建 `binder_transaction`，填入**callingPid、callingUid（App的pid/uid）**；
    - 根据handle找到目标进程system_server的binder_proc；
    - 将这个transaction放入system_server进程的todo任务队列；
    - 唤醒system_server里空闲binder线程；App线程阻塞（非oneway）等待返回结果。

2. **system_server（服务端，binder线程池）**
    - binder_thread被唤醒，从todo队列取出binder_transaction；
    - libbinder把事务内callingPid/callingUid写入**当前binder线程TLS的IPCThreadState**；
    - 进入Stub.onTransact → Java层AIDL方法 `attachApplication`；
    - 在这个调用栈内，`Binder.getCallingPid()` / `getCallingUid()` 就读TLS里面保存的值；
    - AMS执行业务逻辑；

3. **返回结果**
    - AMS业务执行完成，返回结果，构造反向transaction；
    - 驱动把返回数据放到共享缓冲区；唤醒App阻塞线程；
    - 服务端本次事务结束，**libbinder清空当前线程TLS里面calling身份信息**；binder线程回到阻塞，等待下一个IPC任务。

> oneway（异步Binder）：客户端发送完事务不阻塞等待返回；callingPid可能为0。

## 3.4 Binder线程池（system_server）

system_server启动时，启动Binder线程池，默认多个worker线程：

- 每个线程调用 `ioctl(BINDER_THREAD_READ)`，阻塞在驱动；
- 事务到来唤醒一个空闲线程，**一个线程同一时刻只处理1个IPC事务，串行执行**；
- 多个线程并行处理多个AIDL请求；每个线程独立TLS，各自IPCThreadState；

> 这就是为什么多个AIDL并发不会混乱：不同事务跑在不同binder线程，TLS隔离。

## 3.5 Binder对象跨进程传递（你前面attachApplication的mAppThread）

当App把`mAppThread（ApplicationThread Binder对象）`作为参数传给AMS：

1. App进程：mAppThread是本地Binder，内核在App的binder_proc中存在对应的binder_node；
2. 打包到Parcel，驱动识别这是本地Binder实体；
3. 在目标进程system_server的binder_proc，**新建binder_ref（handle引用）**；
4. 把这个handle传给system_server；AMS保存这个handle，后续AMS主动调用App的bindApplication，通过这个handle找到App端binder_node，反向IPC。

> 也就是Binder驱动支持**跨进程传递Binder实体引用**，建立双向通道。

# 四、重点再串：为什么静态API不会多AIDL混乱？

1. `Binder.getCallingPid()` 静态native方法，**没有全局static变量保存pid**；
2. `IPCThreadState::self()` 通过pthread TLS拿到**当前正在执行代码的线程**独有的IPCThreadState；
3. Binder事务开始：libbinder把本次事务caller信息写入**这个线程的TLS**；
4. 事务结束：清空TLS caller信息；
5. system_server线程池：多个binder线程，每个线程TLS独立；不同AIDL事务跑在不同线程，互不覆盖；
6. 如果在Binder事务内新建子线程：**TLS不继承**，子线程调用getCallingPid拿到system_server自己pid。

# 五、ServiceManager 和 Binder驱动关系补充

ServiceManager 是**特殊Binder服务**，负责管理所有系统服务的注册、查询：

1. ServiceManager是第一个注册到Binder驱动的服务，固定handle=0；
2. AMS启动时调用 `ServiceManager.addService("activity", amsBinder)`，向驱动注册AMS的binder_node；
3. App调用 `ServiceManager.getService("activity")`，查询AMS，拿到AMS的handle，创建IActivityManager.Proxy。

> ServiceManager本身也是跑在Binder驱动上的普通Binder服务。

# 六、Binder驱动核心功能总结

1. 设备管理：打开、关闭进程binder上下文；
2. 内存管理：mmap，实现一次拷贝；
3. IPC事务管理：构建、分发 `binder_transaction`；
4. 对象管理：binder_node（本地实体）、binder_ref（远端引用），支持Binder跨进程传递；
5. 身份记录：IPC事务自动记录callingPid/callingUid；
6. 线程调度：todo任务队列、阻塞/唤醒binder线程；
7. 死亡通知（DeathRecipient）：监听远端进程死亡。
