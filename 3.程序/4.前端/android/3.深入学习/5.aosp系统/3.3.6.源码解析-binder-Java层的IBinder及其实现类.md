# android.os.IBinder + android.os.Binder 完整详解（Java层）
>
> 一句话总览
> **`IBinder`：接口，定义Binder跨进程通信的统一能力规范（契约）；`Binder`：IBinder的基础实现类，代表【本地Binder实体（Stub）】，也就是服务端对象。**
> AIDL自动生成的 `Stub` 继承 `Binder`；客户端拿到的远程代理对象，**同样实现IBinder接口，但不是Binder类实例**。

## 一、IBinder 接口（interface）

`public interface IBinder`
IBinder是**所有Binder对象的统一抽象**。
不管是：

1. 本进程本地Binder实体（Binder对象，AMS/ApplicationThread）
2. 跨进程远程代理Proxy对象（IActivityManager.Proxy）

**全都实现IBinder接口**。只要是IBinder，就具备跨进程传递、远程调用能力。

### IBinder 核心方法

```java
// 发起远程调用，核心方法
boolean transact(int code, Parcel data, Parcel reply, int flags) throws RemoteException;

// 获取本地接口：同进程直接拿到原始对象；跨进程返回null
IInterface queryLocalInterface(String descriptor);

// 死亡通知：监听远端Binder所在进程死亡
void linkToDeath(DeathRecipient recipient, int flags) throws RemoteException;
void unlinkToDeath(DeathRecipient recipient, int flags) throws RemoteException;

// 检测Binder是否存活
boolean isBinderAlive();
boolean pingBinder();
```

#### 逐个解释

1. **transact(int code, Parcel data, Parcel reply, int flags)**
    远程调用入口：
    - `code`：方法编号，AIDL生成，区分是哪一个接口函数；
    - `data`：入参，序列化到Parcel；
    - `reply`：返回结果，服务端写入；
    - `flags`：最常用 `FLAG_ONEWAY` 异步调用，客户端不阻塞等待返回。
    > 客户端Proxy调用`transact` → 交给native层，通过Binder驱动发给服务端。

2. **queryLocalInterface(String descriptor)**
    用来判断当前IBinder是本地还是远程：
    - 如果是**同进程本地Binder实体**：返回IInterface（AIDL接口对象），**不走IPC，直接本地方法调用**；
    - 如果是**跨进程远程Proxy**：返回null → 创建Proxy代理。
    > AIDL生成的 `Stub.asInterface(IBinder obj)` 里面第一行就是这个判断。

    ```java
    public static IActivityManager asInterface(IBinder obj) {
        if (obj == null) return null;
        IActivityManager in = (IActivityManager) obj.queryLocalInterface(DESCRIPTOR);
        if (in != null) return in;
        return new Proxy(obj);
    }
    ```

3. **linkToDeath / unlinkToDeath（DeathRecipient）**
    死亡监听。客户端注册回调，**当远端进程死亡，Binder驱动主动回调DeathRecipient.binderDied()**。
    用途：AMS监听App进程死亡；App监听system_server崩溃；释放资源、清理引用，防止内存泄漏。
    > 注意：死亡通知是**一次性**，触发后需要重新注册。

4. pingBinder() / isBinderAlive()
    pingBinder：发送空事务，探测远端Binder是否还活着；
    isBinderAlive：判断本地Binder对象是否还存在（仅本地对象有效）。

> IBinder 只是**能力契约**，本身不包含业务方法（业务方法写在AIDL生成的IInterface，例如IActivityManager）。
> IInterface：AIDL生成的业务接口，只有 `asBinder()` 方法，返回IBinder。

## 二、android.os.Binder 类（class，实现IBinder）

```java
public class Binder implements IBinder
```

`Binder` = **本地Binder实体（服务端基类，对应native层 BBinder）**
> 你写的AIDL Stub、AMS、ApplicationThread 全部继承这个Binder。

### Binder实例的含义

当new Binder()，JNI层会创建native BBinder对象，在内核binder驱动生成**binder_node**（Binder实体节点），可以注册到ServiceManager，接收其他进程的IPC调用。

### Binder 实例方法（非静态，服务端用）

1. `protected boolean onTransact(int code, Parcel data, Parcel reply, int flags)`
**服务端接收IPC请求的回调！**
客户端调用transact → Binder驱动投递事务 → 服务端Binder线程唤醒 → 进入`onTransact`。
AIDL生成的Stub会重写onTransact，用switch(code)匹配对应的业务方法，反序列化参数、执行业务、把返回值写入reply。
返回`true`代表处理成功；`false`代表不识别这个code，抛出异常。

2. `void attachInterface(IInterface owner, String descriptor)`
AIDL Stub构造函数调用，**绑定IInterface业务对象和接口唯一描述符（DESCRIPTOR字符串）**，供`queryLocalInterface`使用。

3. `IInterface getInterface()`
获取attachInterface绑定的IInterface。

### Binder 静态方法（你前面重点聊的！！）

全部native静态方法，读取**当前线程TLS（IPCThreadState）**里的Binder事务上下文：

```java
// 获取本次IPC调用方PID（仅Binder事务栈内有效）
public static native int getCallingPid();
// 获取本次IPC调用方UID，鉴权核心，内核不可伪造
public static native int getCallingUid();

// 身份切换，成对使用 try-finally
public static native long clearCallingIdentity();
public static native void restoreCallingIdentity(long token);

// work source，功耗统计
public static native long clearCallingWorkSource();
public static native void restoreCallingWorkSource(long token);

// 判断当前线程是否是Binder线程池线程
public static native boolean isBinderThread();

// Binder线程池相关
public static native void joinThreadPool();
public static native void flushPendingCommands();
```

> ⚠️ 重点再次强调：**静态方法不属于某个Binder实例，读取的是当前执行线程TLS中的IPC事务信息；多AIDL并发不会串数据，因为TLS线程隔离。**

## 三、IBinder、Binder、Stub、Proxy、IInterface 关系（AIDL模型）

举AMS例子 `IActivityManager`

1. `IActivityManager`：**IInterface业务接口**，定义所有业务方法（attachApplication、startActivity），只有`asBinder()`方法返回IBinder。
2. `IActivityManager.Stub`：**继承 android.os.Binder，实现 IActivityManager** → 本地服务实体（BBinder），跑在system_server。
    - 重写onTransact，接收App的IPC请求；
    - `Stub.asInterface(IBinder obj)`：静态工具方法，判断本地/远程。
3. `IActivityManager.Proxy`：**实现 IActivityManager**，客户端代理对象，内部持有IBinder（远程句柄，native BpBinder），**Proxy不是Binder子类！**
    - Proxy调用业务方法时，内部打包Parcel，调用`mRemote.transact()`发起IPC；
    - Proxy的mRemote是IBinder类型，底层native是BpBinder（远程引用，handle句柄）。

```
┌─────────────────────────────────────────────┐
│ IBinder (interface) 契约：transact、linkToDeath
        ▲                  ▲
        │                  │
┌───────┴──────┐    ┌─────┴────────┐
│ Binder类     │    │ Proxy内部mRemote IBinder
│(本地实体)    │    │(远程BpBinder，不是Binder实例)
└──────────────┘
        ▲
        │
IActivityManager.Stub  extends Binder implements IActivityManager
```

> 一句话区分：
>
> - Stub：`Binder子类`，**服务端本地对象，内核binder_node**
> - Proxy：客户端代理，**持有IBinder（远程引用BpBinder），不是Binder实例**

## 四、同进程调用 vs 跨进程调用（queryLocalInterface的作用）

### 场景1：同进程（system_server内部直接调用AMS）

```java
IActivityManager am = IActivityManager.Stub.asInterface(amsBinder);
```

`obj.queryLocalInterface` 返回IActivityManager实例，**直接本地方法调用，不走Binder驱动，不发生IPC，不会触发onTransact，getCallingUid拿到system自己uid**。

### 场景2：跨进程（App调用AMS）

App拿到IBinder（BpBinder远程引用），`queryLocalInterface`返回null → new Proxy。
调用Proxy.attachApplication → proxy.mRemote.transact → IPC进入system_server，进入Stub.onTransact。

## 五、JNI层映射（Java ↔ Native）

- Java `android.os.Binder`  ↔  Native `BBinder`（本地实体）
- Java IBinder（远程Proxy里面的mRemote） ↔ Native `BpBinder`（远程代理，带handle句柄）
- Java `Binder.getCallingPid()` → JNI调用 `IPCThreadState::self()->getCallingPid()`，读线程TLS

> 当跨进程传递Binder对象（比如你前面 `mAppThread`传给AMS）：
> `mAppThread`是App进程的Binder实例（BBinder，binder_node），打包进Parcel；Binder驱动在目标进程system_server创建`binder_ref`引用（handle）；在system_server侧包装成IBinder（BpBinder），AMS保存这个IBinder，用来反向IPC调用App。

## 六、DeathRecipient 工作原理（IBinder能力）

`linkToDeath` 是IBinder接口方法，**本地Binder实体、远程Proxy都可以调用**。

1. 客户端（App）拿到AMS的IBinder，调用`linkToDeath`注册recipient；
2. Binder驱动内部记录这个监听关系；
3. 如果system_server进程crash，内核Binder驱动扫描所有引用这个binder_node的进程；
4. 在App进程binder线程回调 `binderDied()`。

> 注意：**DeathRecipient回调跑在Binder线程池，不是主线程！**

## 七、容易踩坑的关键点

1. **Binder实例只能在服务端！Proxy不是Binder对象，只是持有IBinder引用**
    客户端拿到的IBinder（远程），`instanceof Binder` → false。
2. 静态API `Binder.getCallingPid()`，**是类静态方法，不是实例方法，不需要Binder对象**；
    但是**只有正在处理Binder IPC事务时才有意义**，普通线程拿到自身pid。
3. IBinder可以跨进程传递：这是Binder最强大特性，也就是**双向通道**（App传给AMS mAppThread）。
4. `onTransact` 运行在**服务端Binder线程池**，不是主线程；业务代码要注意线程安全。
5. oneway（FLAG_ONEWAY）：transact立刻返回，客户端不阻塞；服务端onTransact依然在binder线程执行。

## 八、结合你前面attachApplication整条链路串一遍

1. App进程创建 `mAppThread = new ApplicationThread()`，**ApplicationThread extends Binder，实现IApplicationThread**；这是App本地Binder实体，内核生成binder_node。
2. App调用 `mgr.attachApplication(mAppThread, startSeq)`；`mgr` = IActivityManager.Proxy，Proxy内部持有IBinder（AMS远程BpBinder）。
3. `attachApplication`内部调用 `mRemote.transact()`，把`mAppThread`（IBinder）放入Parcel。
4. Binder驱动识别这是本地Binder实体，在system_server创建binder_ref（handle引用）。
5. IPC事务投递到system_server的AMS Stub（IActivityManager.Stub extends Binder）。
6. system_server Binder线程进入AMS的`onTransact`，在里面调用`Binder.getCallingUid()`读取TLS的App身份。
7. AMS拿到传过来的IBinder（包装后的BpBinder，代表App的ApplicationThread）保存到ProcessRecord.thread；
8. AMS使用这个IBinder，调用 `thread.bindApplication()` 反向IPC，回调App进程。

## 九、精简总结

1. **IBinder**：接口，Binder通信的统一抽象，定义transact、死亡监听等基础能力；本地实体、远程代理都实现IBinder。
2. **android.os.Binder**：IBinder的实现类，**代表本地服务实体（Stub父类）**；重写onTransact接收IPC；附带一批静态native方法读取当前Binder事务的身份信息。
3. **Stub**：AIDL生成，继承Binder，服务端本地对象；onTransact分发远程调用。
4. **Proxy**：AIDL生成，客户端代理，持有IBinder远程引用，**不是Binder子类**，打包参数调用transact发起IPC。
5. **IInterface**：AIDL业务接口，定义业务方法，只有`asBinder()`返回IBinder。
