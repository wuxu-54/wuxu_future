# ReDex（Facebook DEX优化工具）核心原理 + 接入
>
> ReDex 是 Meta(Facebook) 开源、C++ 实现的 **DEX全局字节码优化器**。**作用在D8生成dex之后、APK打包之前**，直接对dex做全局跨类优化，目标：**包体积减小 + App冷启动更快**
> R8/Proguard 是class阶段优化；ReDex是**dex全局IR层面优化**，可以做多dex之间的全局分析（这是R8做不到的）

## 一、核心原理（整体架构：Pass流水线模型）

ReDex 采用**Pipeline + Pass**架构：每一项优化是独立Pass，按顺序串行执行；输入APK，解析全部dex到内存IR，依次跑所有Pass，最后序列化回dex、输出新APK。

### 1. 基础流程

原始APK(含classes.dex/classes2.dex)
→ 解析全部dex，加载到内部IR（DexClass / DexMethod / DexField），**把多dex所有类合并成全局类池**
→ 依次执行一组优化Pass
→ 把IR重新序列化成新dex集合
→ 输出优化后的APK

> 重点区分两类Pass：**体积优化Pass**、**启动性能Pass**

### 2. 最核心Pass（你前面关心的dex重排：InterDexPass）

**InterDexPass：多dex类重排，解决multidex索引冗余，减少dex体积（仅multidex生效）**
背景：原生D8拆分multidex，每个dex拥有独立一套`string_ids/type_ids/method_ids`，**跨dex引用会造成索引重复，体积膨胀**。
原理步骤：

1. 全局扫描所有类的字节码，构建**类引用有向图**，method引用权重最高；
2. 标记约束：main-dex强制类、反射/JNI/动态代理黑名单类，不能随便移动；
3. 贪心聚类算法`CrossDexRefMinimizer`：在**单个dex 65535 method_id上限**约束下，优先将**互相引用强的类分到同一个dex**；
4. 类分配完成，**每个dex独立重建全套索引表**；
5. 减少跨dex引用，消除大量重复type/method/string索引，dex总二进制体积下降。

> 注意：**单dex项目，InterDexPass无收益**

### 3. 其他重要Pass（配套体积优化）

1. `ReBindRefsPass`：引用重绑定，优化虚引用，减少跨dex引用
2. `SimpleInlinePass`：小方法内联，减少method数量
3. `DelSuperPass`：删除多余super调用
4. `RemoveEmptyClassesPass`：删除空类
5. `DevirtualizePass`：虚方法去虚拟化，减少虚方法数量
6. `RenameClassesPass`：类名简短混淆（⚠️一般放在InterDex之后，提前混淆会破坏引用权重，降低InterDex收益）

### 4. FDO反馈重排Pass（冷启动优化，附带少量zip压缩收益）

`LayoutBasedRedexPass`：**同dex内部类顺序重排，不改变dex划分**

1. 真机采集冷启动trace，拿到启动加载类序列；
2. 将冷启动需要的类放到dex靠前位置，code_item在data区靠前；
3. 闪存顺序IO提升冷启动；同时连续字节更多，APK的zip压缩率变好，带来少量包体积下降。

### 5. ReDex vs R8/Proguard 一句话区别

- R8/Proguard：**class文件阶段**，做本地类的代码压缩、混淆、优化；**没有跨dex全局分析能力，不能重新划分multidex**
- ReDex：**dex阶段全局IR分析**，可以跨所有dex做类聚类重排；适合大型multidex项目（Facebook、抖音这类超大App）

## 二、ReDex接入方式（Gradle项目接入）

### 1. 编译环境准备

ReDex是C++程序，需要先编译ReDex可执行文件（macOS/Linux，Windows需要WSL）。

```bash
# 拉源码
git clone [https://github.com/facebook/redex.git](https://github.com/facebook/redex.git)
cd redex
./build.sh
```

编译完成得到 `redex` 二进制可执行文件。

### 2. Android编译链路插入位置

```
Java/Kotlin → javac → class → D8/R8 → 生成多dex → 打包生成未签名APK
→【ReDex执行】→优化后的APK → zipalign + apksigner签名
```

> ⚠️ ReDex输入必须是**未签名APK**，处理完成后再签名。

### 3. 两种接入方案

#### 方案A：命令行直接调用（最简单，验证效果首选）

准备`redex-config.json`配置文件，开启需要的Pass（InterDex、方法内联等）

```bash
redex input.apk -o output_redex.apk --config redex-config.json
```

配置文件要点：

- 开启`InterDexPass`；
- 配置`main-dex`强制类列表；
- 配置keep规则（反射、JNI类，防止移动后崩溃）；
- 开启/关闭RenameClasses。

#### 方案B：Gradle Task集成（CI流水线自动化）

自定义gradle task：

1. 在`package`任务执行完成后，拿到打包产出的unsigned apk；
2. 调用`redex`二进制，传入配置；
3. 替换apk，执行zipalign + apksigner签名；
4. 后续assemble任务直接产出redex优化后的包。

### 4. 关键配置要点 & 风险（接入踩坑重点）

1. **keep规则**：反射、动态代理、JNI、四大组件类必须配置keep，禁止被移动/删除，否则运行崩溃；
2. **main dex约束**：Android5及以下，四大组件必须在main dex，InterDex不能把它们移到secondary dex；
3. **编译耗时**：全局引用图分析+贪心聚类，**编译时间明显变长**；
4. **65536上限**：聚类分配时，严格控制每个dex method_ids条目上限；
5. **先做灰度验证**：接入后必须全量回归测试，类重排会改变类加载顺序，部分反射/动态代码容易踩坑。

## 三、收益与局限

✅收益

1. multidex大App：InterDexPass减少dex几百KB原始体积；
2. 方法内联、死代码删除，进一步减少字节码；
3. FDO重排可降低冷启动耗时（Facebook当年冷启动提速约20%）

❌局限

1. **单dex项目无InterDex收益**；
2. 编译速度慢；
3. 对反射、动态加载类敏感，需要大量keep维护；
4. 现代Google Baseline Profile只能做dex内部类顺序，**无法替代InterDex跨dex聚类**

## 四、极简总结

1. **原理**：ReDex是DEX全局优化流水线，把所有dex加载到内存IR，多个Pass依次优化；最核心InterDexPass做**多dex类聚类重排，减少跨dex引用，消除索引冗余，压缩dex体积**；FDO重排优化冷启动；
2. **接入**：编译redex二进制，插在D8打包出APK之后、签名之前；通过json配置开启pass，配置keep黑名单；在gradle增加自定义task集成到CI。
