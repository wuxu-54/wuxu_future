# Android API37（Android17）DeliQueue 完整改动、优化细节 + Legacy老版本深度对比
>
> 核心一句话：**API37不是改Handler/Looper/Message上层API，而是完全重写MessageQueue内部实现，新增DeliQueue无锁队列；targetSdk >=37自动启用DeliQueue，target<37继续走legacy老链表**
> 源码入口就是你看到的分支：

```java
Message next() {
    if (sUseDeliQueue) {
        return nextDeliQueue();
    } else {
        return nextLegacy();
    }
}
boolean enqueueMessage(Message msg, long when) {
    if (sUseDeliQueue) {
        return enqueueMessageDeliQueue(msg, when);
    } else {
        return enqueueMessageLegacy(msg, when);
    }
}
```

`sUseDeliQueue`是进程静态标记，App启动阶段由`ActivityThread`传入参数决定，一旦进程启动就固定，运行时不能动态切换。

## 一、Legacy老版本（API ≤36，nextLegacy）完整回顾

### 架构：**全局synchronized锁 + 单向有序链表**

1. **数据结构**：`mMessages` 是单向链表，链表**在入队的时候排序**。
`enqueueMessage` 全程包裹在 `synchronized(this)` 大锁里面。
2. **入队流程（子线程sendMessage）**
    子线程进来，抢占MessageQueue对象锁：
    - 拿到锁，校验消息状态、队列是否退出；
    - 遍历链表，根据`when`（触发时间）找到插入位置；
    - 插入链表节点；
    - 判断是否需要唤醒Looper，调用nativeWake；
    - **释放锁**。

> 痛点：**只要有一个子线程持有这个锁，主线程Looper在next()里就会被block，等待锁释放**。主线程本来在next()里面要拿锁取消息，被后台子线程阻塞，直接造成UI卡顿、丢帧。

3. **nextLegacy() 出队流程（Looper主线程）**

```java
Message nextLegacy() {
    for(;;) {
        nativePollOnce(..., timeout); // 阻塞等待epoll事件
        synchronized(this) { // 主线程也要抢同一把全局锁！
            // 从mMessages链表读取消息
            // 处理同步屏障：遇到target==null屏障，跳过所有同步消息，找异步消息
            // 判断消息时间是否到期
            // 到期取出msg；没到期，计算timeout，继续nativePollOnce
        }
    }
}
```

4. 同步屏障实现：直接插入一个`target=null`的Message到链表；遍历链表识别屏障。
5. IdleHandler：队列无到期消息时，在锁内执行IdleHandler回调。

**老版本核心缺陷**

- 唯一一把对象锁，生产者（所有子线程）、消费者（主线程Looper）争抢同一锁；
- 高并发场景（大量子线程频繁post消息）主线程极易被锁阻塞；
- 插入消息要遍历链表，插入耗时随队列长度线性增长 O(n)；
- 链表存储，第三方库可以反射`mMessages`遍历消息做监控、泄漏检测。

## 二、API37 DeliQueue（nextDeliQueue / enqueueMessageDeliQueue）改动细节

### 核心设计思想：**生产者、消费者数据分离，解除全局锁竞争**

DeliQueue把消息存储拆成两块：

1. **Treiber Stack（无锁栈，CAS，所有生产者写入）**
    所有子线程`sendMessage`只需要把Message push进Treiber无锁栈，**全程没有synchronized锁，只用VarHandle+CAS原子操作**，多个子线程并发入队互不阻塞。
    Treiber栈是后进先出LIFO，**入栈时不做时间排序**，只快速把消息丢进来。
2. **Looper独占最小堆 min-heap（只有主线程Looper访问）**
    堆按照`when`小顶堆排序，堆顶是最近要执行的消息。**只有Looper主线程访问堆，没有多线程竞争，不需要锁**。

### DeliQueue 完整消息流转

1. **子线程入队 enqueueMessageDeliQueue**
    - 校验msg、队列quit状态；
    - CAS把消息push进Treiber无锁栈；
    - 原子更新`mWaitState`标记，判断是否需要唤醒Looper；
    - 调用nativeWake唤醒（必要时）；
    ✅ **全程无synchronized锁**，不会卡住主线程。

2. **主线程 nextDeliQueue() 循环**

```
for(;;) {
    nativePollOnce(ptr, timeout); // 底层epoll阻塞逻辑保留，和老版本一样
    // 【关键一步】把Treiber栈里面积攒的所有消息一次性全部迁移到最小堆
    moveStackToHeap();
    // 从最小堆取出when最小的消息
    msg = heap.top();
    // 处理同步屏障逻辑、判断消息是否到期
    if(消息到期) {
        heap.pop();
        return msg;
    } else {
        // 未到期，计算timeout，继续阻塞
    }
}
```

> 排序**不再在入队阶段做，而是Looper消费前批量迁移、构建堆**；堆取最小元素是O(1)，插入堆O(logN)。

> 同步屏障、异步消息逻辑**上层行为完全保留不变**，只是屏障不再插入单向链表，而是在堆中维护屏障标记，同样：遇到屏障，跳过同步消息，优先执行异步消息。
> IdleHandler逻辑也保留，在堆为空、没有到期消息时执行Idle回调。

### DeliQueue 新增的原子状态控制

引入原子变量`mWaitState`、序列号，用来安全控制：

- Looper阻塞/唤醒状态；
- 避免重复wake、丢失唤醒信号；
- CAS保证Treiber栈并发push的线程安全。

> native层：**nativePollOnce / nativeWake / epoll管道机制完全复用，没有改动底层Linux阻塞模型**，只是Java层队列模型重写。

## 三、关键指标与官方性能数据

官方测试数据：

1. 多线程并发入队场景：DeliQueue入队速度相比legacy链表**最高提升5000倍**（高并发压测场景）
2. 主线程在锁竞争上消耗的时间减少**15%**
3. App丢帧减少约4%；系统UI/Launcher场景丢帧减少7.7%
4. App启动首帧渲染95分位耗时下降9.1%

原理：消除主线程被后台线程锁阻塞这个卡顿源。

## 四、Legacy vs DeliQueue 逐项详细对比表

|对比项| Legacy(nextLegacy, API<=36) | DeliQueue(nextDeliQueue API37+ targetSdk>=37)|
|---|---|---|
|**同步机制**|全局`synchronized(this)`大锁，生产者、消费者抢同一把锁|无全局锁；生产者CAS Treiber栈；最小堆仅Looper单线程独占，无需锁|
|数据结构|单向有序链表，入队遍历链表插入排序|Treiber无锁栈（生产者写入） + Looper独占最小堆（消费、按时间排序）|
|入队时间复杂度|O(n)，队列越长插入越慢|O(1) CAS入栈；排序延迟到Looper消费时批量迁移，堆操作O(logN)|
|主线程阻塞风险|高：后台子线程持有锁，主线程next()会被阻塞|几乎消除锁争用；子线程入队不会卡住主线程|
|同步屏障实现|链表插入target=null特殊消息，遍历链表识别|堆内维护屏障标记，逻辑行为对齐，底层存储不同|
|IdleHandler|锁内执行|迁移消息后，堆空闲时执行，行为不变|
|mMessages字段|有效，指向链表头，反射可读|mMessages永久为null！不再使用链表存储，反射读取失效|
|消息入队顺序|按when在链表有序排列|入栈是LIFO，迁移到堆之后再按when重新排序；对外表现的消息执行顺序完全不变|
|native底层|epoll + pipe，nativePollOnce/nativeWake|**native底层epoll完全复用，无改动**|
|上层API|Handler/Looper/Message所有API|**对外API完全兼容，业务代码一行不用改**|
|启用条件|targetSdk < 37 或者系统参数关闭DeliQueue|targetSdk >=37默认开启；可通过系统启动参数强制关闭，切回legacy|

## 五、API37改动带来的兼容性坑（重点，面试常问）
>
> 上层业务写Handler、post、sendMessage、postDelay、同步屏障、IdleHandler**行为对外完全一致**，应用正常业务代码无感知。问题全部来自**反射MessageQueue内部私有字段**的第三方SDK/性能监控库。

1. **反射 mMessages 失效**
    legacy中`MessageQueue.mMessages`是链表头；DeliQueue模式下mMessages恒等于null。
    很多ANR监控、卡顿检测、内存泄漏框架通过反射`mMessages`遍历队列消息，在API37 targetSdk37上直接失效，空指针。
2. 反射访问MessageQueue其他私有成员、内部方法，大概率失效。
3. 注意：**只是内部存储变了，Message对象本身、消息池obtain/recycle逻辑没有改动**。
4. 同步屏障行为不变：`postSyncBarrier()` / `removeSyncBarrier()` API不变，View绘制异步消息依然优先执行，UI渲染逻辑不受影响。

## 六、容易混淆的两个版本改动区分（面试高频）

1. **API29 Android10**：**没有DeliQueue**。改动点：新增`Handler.createAsync()`、加强Message状态校验、加固消息复用，MessageQueue仍然是legacy单锁链表。
2. **API37 Android17**：**MessageQueue内部完全重构，DeliQueue无锁队列**；上层Handler、Looper、Message公开API不变。

## 七、DeliQueue仍然存在的限制 & 没有解决的问题

⚠️ 不是万能优化：

1. **消息执行超时导致ANR的问题没有变化**
DeliQueue解决的是**主线程被锁阻塞**，**不解决消息本身回调执行耗时过长导致ANR**。如果handleMessage里面做耗时操作，照样ANR。
2. postDelay的延时精度逻辑不变：when仍然是计划取出时间，不是保证精确执行，前面消息排队依然会延后。
3. nativePollOnce阻塞机制不变，消息队列为空主线程依旧休眠。
4. 多线程并发发送极大量消息，堆迁移、堆排序依然有开销，只是相比链表遍历好很多。

## 八、源码分支切换逻辑补充

```java
// MessageQueue静态变量，进程全局唯一
private static boolean sUseDeliQueue;

// 进程启动阶段由ActivityThread初始化参数设置
public static void setUseDeliQueue(boolean useDeliQueue) {
    sUseDeliQueue = useDeliQueue;
}
```

这个标记是**进程级别**，一个App进程内所有MessageQueue（主线程+子线程Looper对应的MessageQueue）统一全部使用DeliQueue或者全部legacy，**不能单个Looper单独切换**。

## 九、一句话总结DeliQueue优化本质

老版本：**所有线程抢同一把锁，插入消息时链表遍历排序，主线程容易被后台线程阻塞**
API37 DeliQueue：**生产者直接CAS推消息进无锁栈，不抢锁；只有Looper主线程单独维护最小堆，在消费前一次性迁移消息并排序，彻底消除全局锁竞争，减少UI卡顿丢帧；对外上层API行为完全不变**
