# Android 触摸事件与按键事件冲突处理（承接前面 InputStage + 焦点寻焦）

>
> **根本冲突来源：触摸模式（Touch Mode）**
> Android 有全局的**触摸模式状态**，这个状态是触摸、按键两套事件互相打架的根源：

1. **触摸屏幕 → 进入触摸模式 `isInTouchMode()=true`**
 此时：**只有 `focusableInTouchMode=true` 的View才能持有焦点**（EditText默认true；Button、TextView默认false，触摸点击不会获取焦点，只会触发onClick）
2. **按下Dpad/方向按键 → 退出触摸模式 `isInTouchMode()=false`**
 系统自动触发寻焦，必须存在一个带焦点的View来接收KeyEvent；普通Button此时可以获取焦点。

>
> 典型冲突现象（TV/车机/平板外接遥控器高频问题）

- 触摸点按钮后，遥控器方向键焦点找不到、焦点乱跑
- 触摸点击控件后，控件意外拿到焦点，后续按键逻辑错乱
- 遥控器移动焦点后，再触摸页面，焦点还残留在旧View，点击和按键两套逻辑不同步
- 同时支持触摸+遥控器的页面：触摸滑动时，方向按键误触发焦点跳转

## 一、先理清两套事件分发差异（冲突底层）

- **Touch事件**：坐标命中View树，和焦点无关；触摸模式开启
- **KeyEvent**：投递到**当前焦点View**；方向键未消费 → 触发 `focusSearch` 寻焦；**依赖非触摸模式**>

> 两套事件走的是**同一套ViewRootImpl InputStage主线程链路**，但是两套独立分发逻辑，**共享全局触摸模式状态**，状态切换就容易冲突。

## 二、分类冲突场景 + 解决方案

### 场景1：触摸后残留焦点 / 触摸点击意外获取焦点（最常见）

原因：View设置了 `focusableInTouchMode="true"`，**触摸点击时View拿到焦点**，后续遥控器按键全部作用在这个View上，造成按键逻辑异常。

✅ 解决方案

1. 普通按钮：**不要随便开启 focusableInTouchMode**

```
<!-- 普通Button，触摸时不要获取焦点 -->
<Button
    android:focusable="true"
    android:focusableInTouchMode="false"/>
```

>
> focusable=true：遥控器导航（非触摸模式）可以获得焦点；focusableInTouchMode=false：触屏点击不会拿到焦点，只触发点击事件。

2. 只有输入框EditText才保留 `focusableInTouchMode="true"`（原生默认）
3. 触摸点击后主动清理焦点：

```
// 触摸操作完成后清除页面焦点
window.clearFocus()
```

4. 如果需要触摸后**保留遥控器焦点体系**：触摸点击View时，**不调用requestFocus()**，只响应点击，不修改焦点。

### 场景2：遥控器移动焦点后，触摸屏幕，焦点状态混乱

现象：遥控器把焦点移到A按钮，用户直接触摸B区域，焦点还留在A，再按遥控器方向键，从A开始寻焦，用户预期应该从B。

✅ 方案：触摸按下时，**主动同步焦点到触摸点击的View（按需）**
在 `Activity.dispatchTouchEvent` 或者DecorView的分发处，在ACTION_DOWN时，拿到点击坐标命中View，按需调用 `requestFocusFromTouch()`

>
> `requestFocusFromTouch()`：先退出触摸模式，再请求焦点，专门用于**触摸场景下主动设置焦点**，普通requestFocus在touchMode下无效

```
override fun dispatchTouchEvent(ev: MotionEvent): Boolean {
    if (ev.action == MotionEvent.ACTION_DOWN) {
        val hitView = findViewAtTouch(ev.x, ev.y)
        hitView?.requestFocusFromTouch()
    }
    return super.dispatchTouchEvent(ev)
}
```

>
> 注意：**不要全局无脑加**；纯手机App不需要；TV/车机这种同时支持触摸+遥控器才需要。

### 场景3：触摸滑动时，方向按键误触发焦点跳转

原因：滑动过程中焦点View还存在，此时按Dpad，View没有消费KeyEvent，进入focusSearch寻焦，焦点跳走打断滑动。

✅ 方案：**滑动期间临时拦截方向按键**

1. 在 `ViewPostImeInputStage` 上层或者Activity.dispatchKeyEvent拦截
2. 通过 `GestureDetector` / OnTouchListener 标记**是否正在滑动**

```
override fun dispatchKeyEvent(event: KeyEvent): Boolean {
    // 如果正在触摸滑动，拦截Dpad方向键，不做焦点导航
    if (isScrolling && isDpadKey(event.keyCode)) {
        return true; // 消费掉，不再进入寻焦
    }
    return super.dispatchKeyEvent(event)
}
```

### 场景4：焦点寻焦算法和触摸布局不一致，焦点跳去看不见的View

原因：FocusFinder几何寻焦只看View矩形，触摸布局可见区域和焦点候选View集合不一致。
✅ 方案：

1. 用`nextFocusUp/Down/Left/Right`手动指定焦点跳转，**覆盖FocusFinder自动算法**（TV常用）
2. 过滤候选焦点：重写ViewGroup `focusSearch`，在父层过滤掉触摸区域外、不需要参与寻焦的View
3. 控制可聚焦集合：GONE/INVISIBLE控件自动被FocusFinder过滤；不要把装饰View设置focusable=true

## 三、事件拦截的几个关键钩子（控制冲突，按优先级）

>
> 和前面InputStage链路对齐，拦截位置从上到下：

1. **Activity.dispatchTouchEvent / dispatchKeyEvent**
 最高层统一拦截、过滤、同步触摸模式/焦点状态；适合全局控制触摸、按键互斥逻辑。
   - 返回true：消费事件，不再往下分发
2. **DecorView / PhoneWindow Callback**
3. View层级：
   - View.OnTouchListener、View.OnKeyListener（优先级高于onTouchEvent/onKeyDown）
   - 重写ViewGroup `onInterceptTouchEvent`（触摸父子冲突）
   - 重写 `focusSearch()`：**控制按键寻焦逻辑**，这是按键焦点冲突的核心钩子
4. InputStage层（ViewRootImpl内部，App层不建议修改）

>
> 最佳实践：**优先在Activity做全局的触摸/按键状态同步，不要大量重写每个子View的focusSearch**

## 四、触摸模式状态管理（核心API）

```
// 判断当前全局是否触摸模式
View.isInTouchMode()

// 触摸模式下请求焦点（会自动退出touch mode）
view.requestFocusFromTouch()

// 清除窗口焦点
window.clearFocus()
```

>
> 重要：触摸模式是**整个系统全局状态**，不是单窗口状态；切换触摸/遥控器会影响所有窗口。

## 五、架构策略（双输入设备：触摸+遥控器）

两种主流设计，二选一，避免混用造成冲突

### 策略A：两套交互隔离（推荐，简单稳定）

- 触摸操作：**不维护焦点**，focusableInTouchMode全部false；触摸点击只响应onClick，不改变焦点
- 遥控器Dpad操作：**维护焦点体系**，退出触摸模式，焦点导航、高亮框正常
- 切换规则：**一旦用户触摸，不再显示焦点高亮；一旦按下方向键，开启焦点高亮**
检测：`isInTouchMode()` 来控制焦点框显示/隐藏。

### 策略B：两套交互联动（TV/车机，复杂）

触摸点击View时自动把焦点切到当前触摸View；遥控器移动焦点后，点击屏幕时焦点跟随触摸位置；
**缺点：极易出现焦点状态不同步，需要在ACTION_DOWN统一同步焦点**。

## 六、高频面试考点

1. **冲突根源：TouchMode全局状态**，触摸进入TouchMode，按键退出TouchMode，两套事件对焦点的可用性规则不一样。
2. `focusable` vs `focusableInTouchMode`：
   - focusable：非触摸模式（遥控器）能否获取焦点
   - focusableInTouchMode：触摸模式下能否获取焦点；**普通按钮不要开启**，否则触摸会抢焦点
3. `requestFocus()` 在触摸模式下无效，要用 `requestFocusFromTouch()`
4. KeyEvent的寻焦只有**方向键未被消费时**才触发；触摸事件完全不走寻焦。
5. 触摸事件命中View是坐标；KeyEvent是投递到当前焦点View，两套分发逻辑独立。
6. 解决冲突的核心思路：**统一管理TouchMode状态，控制触摸操作是否修改焦点**。

## 七、排查手段

1. 日志打印 `isInTouchMode()` 和 `findFocus()`，看触摸/按键切换时焦点View是否符合预期
2. 检查是否有View意外设置 `focusableInTouchMode=true`
3. 看按键分发：`Activity.dispatchKeyEvent` 是否被提前消费，阻止进入ViewPostImeInputStage寻焦逻辑
4. 触摸ACTION_DOWN时，检查有没有代码调用 `requestFocus()` 错误设置焦点
