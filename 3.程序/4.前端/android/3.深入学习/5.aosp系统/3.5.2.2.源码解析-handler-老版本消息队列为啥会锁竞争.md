# 老版本队列为啥会有锁竞争

>我的理解：老版本在入队列时进行排序等操作，并且`synchronized(this)`包裹，当子线程使用handler的sendMessage向主线程发送消息时会导致主线程的UI刷新需要同样等待锁，因此导致了UI的卡顿。

Legacy MessageQueue 里 `enqueueMessage` 和 `nextLegacy()` 操作消息链表，**都包裹在 `synchronized (this)` 里面**，锁对象就是当前 `MessageQueue` 实例对象。
> `synchronized(this)`：this 就是 MessageQueue 对象，**同一个对象锁**。
> 生产者（子线程 sendMessage → enqueueMessage）、消费者（主线程 Looper nextLegacy()），只要要访问消息链表 `mMessages`，都必须争抢这**同一把锁**。

下面拆开源码+时序场景讲清楚。

## 1. 先看 enqueueMessage（生产者，子线程）源码片段

```java
boolean enqueueMessage(Message msg, long when) {
    if (msg.target == null) {
        throw new IllegalArgumentException("Message must have a target.");
    }
    synchronized (this) {  // 锁：MessageQueue this
        if (msg.isInUse()) {
            throw new IllegalStateException(...);
        }
        msg.markInUse();
        msg.when = when;
        Message p = mMessages;
        boolean needWake;
        // 遍历链表，找到插入位置，O(n)
        if (p == null || when == 0 || when < p.when) {
            msg.next = p;
            mMessages = msg;
            needWake = mBlocked;
        } else {
            // 循环遍历链表找插入点
            Message prev;
            for (;;) {
                prev = p;
                p = p.next;
                if (p == null || when < p.when) {
                    break;
                }
                ...
            }
            msg.next = p;
            prev.next = msg;
        }
        if (needWake) {
            nativeWake(mPtr);
        }
    } // 离开synchronized，释放锁
    return true;
}
```

只要子线程调用 `sendMessage/post/postDelay`，最终走到 `enqueueMessage`，**必须获取 MessageQueue 对象锁**，拿到锁之后才能读写 `mMessages` 链表。
> 生产者：子线程，竞争锁来**写链表**。

## 2. nextLegacy()（消费者，主线程Looper）源码片段

```java
private Message nextLegacy() {
    for (;;) {
        // nativePollOnce 阻塞，此时**没有持有锁**！
        nativePollOnce(mPtr, nextPollTimeoutMillis);

        synchronized (this) { // 【重点】主线程也要拿同一个MessageQueue对象锁！
            // 开始访问mMessages链表
            long now = SystemClock.uptimeMillis();
            Message prevMsg = null;
            Message msg = mMessages;

            // 处理同步屏障逻辑，遍历链表
            if (msg != null && msg.target == null) {
                // 遇到同步屏障，跳过同步消息，找异步消息
                do {
                    prevMsg = msg;
                    msg = msg.next;
                } while (msg != null && !msg.isAsynchronous());
            }

            if (msg != null) {
                if (now < msg.when) {
                    // 消息还没到时间，设置超时
                    nextPollTimeoutMillis = (int) (msg.when - now);
                } else {
                    // 消息到期，取出消息返回给Looper
                    msg.markInUse();
                    mBlocked = false;
                    Message p = msg.next;
                    msg.next = null;
                    return msg;
                }
            } else {
                nextPollTimeoutMillis = -1;
            }

            // 处理IdleHandler...
        } // 释放锁
    }
}
```

### nextLegacy 锁行为拆解（非常关键，很多人误解）

1. `nativePollOnce`：**阻塞等待的时候，不持有锁**，主线程休眠，锁是释放的，子线程可以正常enqueue；
2. 一旦被唤醒（管道事件/超时到了），代码继续往下执行，**进入 `synchronized(this)`，尝试获取MessageQueue这把对象锁**；
3. 在锁保护区间内：遍历链表、处理同步屏障、取出到期消息；
4. 退出代码块，释放锁。

> 消费者：主线程Looper，竞争同一把锁来**读/修改链表**。

## 3. 为什么生产者、消费者争抢同一把锁？

- 锁对象是 `MessageQueue` 实例本身 `this`；
- 生产者写链表（enqueue）、消费者读/修改链表（nextLegacy），**操作的是同一个共享变量 `mMessages` 单向链表**；
- 为了防止并发读写链表出现数据错乱（比如子线程正在插入节点，主线程同时遍历链表，链表断链、空指针），Java用同一把synchronized锁保护这个共享链表。

### 典型阻塞场景（痛点）
>
> 场景：子线程A正在执行 enqueueMessage，已经拿到 `synchronized(this)` 锁，正在遍历链表插入消息（队列很长，遍历耗时）。
> 这时：Looper被nativeWake唤醒，进入nextLegacy，尝试进入 `synchronized(this)`。
> ✅ **主线程（消费者）被卡住，等待子线程A释放锁！**
> UI主线程卡在抢锁，没法取出消息，UI卡顿、丢帧。

这个就是 Legacy 最大问题：
**主线程从nativePollOnce唤醒之后，必须跟所有后台子线程抢同一把锁。后台线程持有锁的期间，主线程被阻塞。**

> 补充：很多人误以为 loop 死循环一直拿着锁。❌
> nativePollOnce阻塞阶段，主线程**不持有锁**，只有唤醒后进入同步块的时候才去抢锁。

## 4. 时序例子（Legacy）

1. 主线程Looper：调用 `nativePollOnce` → 休眠，锁释放 ✅
2. 子线程A：sendMessage → enqueueMessage，成功拿到 `synchronized(this)` 锁，开始遍历长链表插入消息（耗时几百微秒）
3. 此时管道被唤醒，nativePollOnce返回，主线程继续执行，尝试进入 `synchronized(this)`
4. 子线程A还没执行完链表遍历，**锁还没释放** → 主线程阻塞在锁上，等待子线程A
5. 子线程A执行完毕，退出同步块，释放锁
6. 主线程拿到锁，遍历mMessages，取出消息

👉 主线程明明已经被唤醒，但是**拿不到锁，卡住**，这就是锁竞争卡顿。

## 5. DeliQueue怎么解决这个争抢？

DeliQueue 不再用**同一把锁保护读写**：

- 生产者：消息CAS推入Treiber无锁栈，**完全没有synchronized(this)**，生产者之间用CAS；生产者**不会持有任何锁**。
- 消费者：只有主线程Looper独占最小堆，**没有多线程同时访问堆，根本不需要锁**。
生产者写入的数据结构（Treiber栈） 和 消费者读取的数据结构（min-heap）做了隔离。
自然就不存在「子线程持有锁，主线程抢锁被阻塞」的场景。

## 6. 容易踩坑的理解误区

1. ❌ 误区：Looper.loop()全程持有锁
✅ 正确：nativePollOnce阻塞时**释放锁**，唤醒后才去抢锁。
2. ❌ 误区：锁只是保护入队操作
✅ 正确：**入队写链表、next读链表、同步屏障遍历链表**，都操作共享mMessages，都用同一把MessageQueue对象锁。
3. ❌ 误区：子线程enqueue的时候主线程一定阻塞
✅ 正确：只有当主线程刚好唤醒，并且**同时子线程已经抢占了锁**，主线程才会阻塞等待锁。队列短的时候，这个问题不明显；大量并发post消息场景，锁竞争才会暴露。
