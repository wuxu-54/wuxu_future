# Android 资源管理完整详解（打包 → 安装 → 运行，附带插件化资源方案）

> 
> 核心：Android 的资源体系核心是 **`AssetManager` + `Resources` + `resources.arsc`**；资源分两大类：
> 
> 
> 1. **编译资源 res/**：会被 aapt2 编译，生成资源ID（`R.xxx`），存在 `resources.arsc`；
> 2. **原始资源 assets/**：不编译、不生成资源ID，只能通过 `AssetManager` 流式读取。

## 一、APK打包阶段：aapt2 处理资源（重点）

源码目录：`src/main/res/`（layout/drawable/string/values等）
打包工具：**aapt2（Android Asset Packaging Tool 2）**，AGP默认使用aapt2。

### aapt2 完整工作流（compile + link）

1. **aapt2 compile（编译单个资源文件）**
 把每一个xml、png、svg、字符串文件，编译成独立的`.flat`中间文件。
   - xml布局：解析标签、压缩，生成二进制xml（AndroidManifest.xml也在这里编译成二进制xml，不是明文）
   - 图片：不解析内容，只记录元信息
   - values/strings.xml：提取字符串、样式，保存资源条目信息> 
   > ⚠️ res下xml最终打包进APK都是**二进制XML**，不是可读文本。
2. **aapt2 link（链接，核心步骤，生成 resources.arsc）**
 合并所有编译后的资源flat文件，做几件关键事情：
   - **分配资源ID**：资源ID是32位整数 `0xPPTTNNNN`
     - PP：Package ID（系统资源是0x01，当前App默认0x7F）
     - TT：Type ID（string=02，drawable=01，layout=03）
     - NNNN：资源条目序号> 
     > 代码中 `R.drawable.icon` 本质就是这个32位int常量，**编译期就写死到class/dex中**
   - 生成 **`resources.arsc`**：资源索引表（核心文件！）> 
   > `resources.arsc` 是一张大索引表：保存【资源ID → 文件路径 + 多语言/屏幕适配配置信息】。AssetManager靠这张表做资源查找、适配（不同dpi、语言自动选对应资源）。
   - 合并所有二进制xml，生成**二进制AndroidManifest.xml**。
   - 输出：编译好的资源文件 + resources.arsc + 二进制Manifest，进入APK打包。
3. zipalign 对齐
 将APK内的so、大资源4字节对齐，方便mmap内存映射，减少内存开销。

> 
> 打包产物（APK内资源相关文件）
> 
> 
> - `resources.arsc`：资源索引总表（二进制）
> - res/***.xml：二进制布局xml
> - res/drawable/**.png：图片原始文件
> - assets/：原样打包，aapt2不处理，不分配资源ID
> - AndroidManifest.xml：二进制清单

> 
> 关键点：**R.java是aapt2 link阶段生成的Java类，里面全是static final int常量，R类会被javac编译进class，R8混淆/压缩时可以把R内联、删除**。

## 二、APK安装阶段（PackageManagerService，PMS）对资源的处理

> 
> 安装阶段**不会解压APK**，APK全程保存在 `/data/app/<package>/base.apk`，Android采用mmap直接映射APK，不需要解压到磁盘。
> 安装流程资源相关动作：

1. PMS读取APK里**二进制AndroidManifest.xml**：获取包名、版本、权限、四大组件。
2. PMS读取`resources.arsc`，解析资源包信息、配置（支持的语言、dpi），把**应用基础资源元信息**存入`packages.xml`（系统数据库）。
3. 校验签名，完成安装。

✅ **安装阶段不会加载图片/布局等实际资源！**
安装只读取清单和arsc索引；**真正资源加载，发生在App进程启动、AssetManager初始化阶段**。

> 
> 补充Split APK（AAB）安装：
> base.apk + 多个split apk，每一个split都拥有独立`resources.arsc`。系统会把**所有split的资源合并到同一个AssetManager**，资源ID隔离。

## 三、App运行时：资源加载机制（核心：AssetManager + Resources）

### 类关系

`AssetManager`：底层native层核心，负责**读取APK压缩包、mmap、查找资源文件、读二进制流**。
`Resources`：Java层封装，基于AssetManager，提供 `getDrawable()/getString()/inflate布局` 等API。
`ResourcesImpl`：Resources的实现类，Android7+之后拆出来。

### 启动流程

1. App进程创建，ActivityThread初始化。
2. 创建 `AssetManager`，调用native方法，**把当前APK路径(base.apk)add到AssetManager**；如果是split APK，会add所有split的apk路径。
3. AssetManager读取`resources.arsc`到内存，建立资源索引。
4. 构造`Resources`对象，持有AssetManager引用，App中`context.getResources()`拿到的就是这个实例。

### 根据资源ID加载资源完整过程（R.xxx）

```
context.getResources().getDrawable(R.drawable.icon);
```

1. 传入32位资源ID；
2. Resources → AssetManager，拿着ID查内存中的`resources.arsc`索引表；
3. 根据当前设备配置（dpi、语言、横竖屏），匹配最合适的资源文件路径；
4. AssetManager通过mmap，直接从APK中读取对应文件的二进制数据；
5. 解码成Drawable返回。

> 
> 重点：**全程不解压APK，mmap直接映射APK文件，按需读取字节**。

### assets目录读取（无资源ID）

```
getAssets().open("test.txt");
```

AssetManager直接在APK内查找assets下文件名，打开文件流，**不走resources.arsc**。

### 资源适配原理（多dpi/多语言）

全部写在`resources.arsc`的索引表。当设备配置变更（切换语言），Resources会重新根据新配置，用同一个arsc表选择对应资源文件，不需要重新加载APK。

## 四、资源ID冲突的根源（面试高频）

资源ID格式 `0xPPTTNNNN`

- 主App packageId默认 **0x7F**
- 所有主App res资源ID都是以0x7F开头。> 
> 如果插件（插件APK）资源packageId也是0x7F，**主App和插件资源ID完全可能重复，直接冲突，加载资源错乱**！
> 👉 这就是插件化资源最大的坑。

## 五、插件化中的资源管理（重点）

插件化：插件是独立APK（plugin.apk），没有安装到系统PMS，由宿主App动态加载。

> 
> 难点：
> 
> 
> 1. 插件本身有独立resources.arsc和res资源；
> 2. 宿主AssetManager默认只加载宿主base.apk；
> 3. 资源ID冲突问题；
> 4. 插件的R类里面的资源ID，是编译插件时生成的，默认也是0x7F。

### 插件化资源主流3套解决方案

### 方案1：合并AssetManager（最经典，老方案：DroidPlugin早期、VirtualAPK）

原理：

1. 宿主启动后，创建AssetManager，**反射调用addAssetPath，把插件apk路径添加进宿主的AssetManager**；```
// 伪代码，反射native方法
assetManager.addAssetPath(pluginApkPath);
```
2. 插件的resources.arsc被合并到同一个AssetManager；
3. 插件构造独立Resources对象，共用这个合并后的AssetManager。

问题：**资源ID冲突！宿主和插件都是0x7F，资源ID重复，读错资源**。
解决手段：**编译插件时修改aapt，修改插件PackageId，改成非0x7F（0x80、0x81）**。

> 
> 修改packageId，插件所有资源ID前缀变成0x80，和宿主0x7F隔离，不再冲突。
> 缺点：需要修改aapt/aapt2，编译链路改造大；aapt2之后改造难度提升，AGP高版本很难做。

### 方案2：独立AssetManager（RePlugin方案）

宿主、插件各自独立AssetManager、独立Resources。

- 宿主AssetManager只加载宿主apk；
- 每一个插件单独创建新AssetManager，单独add插件apk路径；
- 插件使用自己的Resources实例。

✅优点：天然隔离，**完全没有资源ID冲突**，不用修改aapt、不用改packageId。
❌缺点：系统限制，Android高版本对多AssetManager有兼容性坑；内存开销更大；插件之间资源不能互相直接访问。

### 方案3：资源重定向 / 资源静态合并（轻量化插件、组件化）

不动态加载插件APK资源。打包阶段，把插件资源**编译合并进宿主，统一分配资源ID**，插件R类和宿主R合并。

> 
> 本质已经不是运行时插件化，是编译期组件化。无法做到下发插件apk动态更新。

### 插件化资源另外几个配套问题

1. **插件二进制AndroidManifest**
 插件APK自带自己的Manifest，但**插件没有安装到PMS**，系统PMS不知道插件的四大组件。
 解决方案：
   - 宿主Manifest预注册占位Activity；
   - 插件启动Activity时，宿主代理跳转，代理Activity接管生命周期。
2. 插件assets资源
 addAssetPath之后，AssetManager可以直接读取插件assets文件，assets天然不容易冲突。
3. 插件资源更新：直接下发新版plugin.apk，替换本地文件，重新addAssetPath即可。

> 
> 区分：**组件化 ≠ 插件化**
> 组件化：编译期所有代码、资源打包进宿主APK，资源ID统一分配，运行无隔离。
> 插件化：插件APK独立打包，运行时动态加载资源/代码，资源隔离要额外处理。

## 六、Split APK（AAB）资源管理 和插件化对比（容易混淆）

Split APK是**系统原生支持**：

1. 所有split都安装到PMS；
2. 系统自动把base + 所有split的apk路径，自动add进同一个系统AssetManager；
3. 每个模块有独立packageId，资源ID天然隔离，不会冲突。> 
> AAB动态feature split，本质是系统原生插件，PMS感知这个模块，和**非安装的自研插件化完全不同**。

## 七、加固场景联动（结合上一问）

加固壳也是动态加载dex，壳资源属于壳APK（base.apk）。
如果业务资源加密：

- 壳hook AssetManager，拦截资源读取；
- AssetManager去读加密资源时，壳解密内存返回；
- resources.arsc基础索引表保持明文，供系统初始化AssetManager。

## 八、高频面试总结

1. 打包：aapt2 compile编译资源，link生成resources.arsc，分配32位资源ID，生成R.java，打包进APK；res变成二进制xml；assets原样打包。
2. 安装：PMS读取Manifest、resources.arsc元信息存入系统数据库；**不解压APK，不加载图片资源**。
3. 运行：App创建AssetManager，addApk路径，mmap读取APK；Resources封装API，根据资源ID查arsc，匹配设备配置，加载资源。
4. 插件化核心痛点：资源ID冲突；主流方案：①修改插件PackageId+合并AssetManager；②每个插件独立AssetManager隔离资源。
