# Facebook ReDex DEX重排（InterDexPass）压缩原理
>
> Facebook开源 **ReDex**，核心做dex全局字节码优化；**InterDexPass** 就是大名鼎鼎的**dex重排/类分组重排**，专门解决**multidex多dex场景**下包体积变大的问题；单dex下这个Pass几乎没有收益。

> 一句话：**不是压缩dex内部二进制，而是重新把类分到不同dex，最小化跨dex引用，减少多个dex里重复的string_ids/type_ids/method_ids，从而减小总dex体积；同时附带FDO类顺序重排提升冷启动**。

## 背景：为什么多dex天然会膨胀？

默认D8打包multidex规则：

- main dex放四大组件、依赖类；剩下类按简单贪心切分到classes2.dex、classes3.dex……
- **每个dex都拥有独立一套string_ids、type_ids、field_ids、method_ids索引表**
- 如果类A在dex0，类B在dex1，B引用A：
  dex1必须**在自己的索引表里复制一份A的type_id、method_id**。

> 跨dex引用越多，多个dex重复的常量/索引条目就越多，APK体积就越大。
> InterDexPass目标：**把互相引用多的类放在同一个dex，减少跨dex引用数量，减少重复索引**

## 1. InterDexPass 重排完整流程（核心）

### Step1：全局静态分析，构建类引用图

扫描全部dex所有class_defs：

- 统计每个类对外引用：type、method、field引用
- 建立有向图：节点=Java类；边=类之间的引用关系
- 给不同引用类型设置权重：method引用权重最高，其次type、field（可配置）

### Step2：贪心聚类算法 CrossDexRefMinimizer

目标：在不突破单个dex **65536 method_id上限** 的约束下，把**引用紧密的类尽量塞进同一个dex**。
算法思路（贪心）：

1. 初始所有类是待分配集合
2. 每次挑选一个**代价最优类**加入当前dex
   > 代价：放到当前dex可以减少多少跨dex引用
3. 加入后，更新剩余所有类的权重
4. 填满当前dex（快触达65536方法上限），新开下一个dex，循环直到全部分类

> 不是全局最优解，是工程上快速收敛的贪心近似解，降低编译耗时

### Step3：重写全部dex的class分布 + 重建各个id表

类被重新分到新dex后：

- 每个dex内部重新生成 string_ids / type_ids / method_ids / field_ids
- 大量原本跨dex的引用变成dex内部引用，**不再需要在多个dex重复存储id条目**
- 减少所有dex的索引表总大小 → 整体dex体积下降

> 收益：Facebook当年生产环境，InterDexPass一般能减几百KB，视项目依赖耦合度而定。

## 2. 另一套重排：FDO反馈驱动类内顺序（提升启动速度，附带少量压缩收益）

除了跨dex类分组，ReDex还支持**单个dex内部class_defs顺序重排**（Feedback-directed class layout）：

1. 真机压测冷启动，trace记录**启动阶段加载的类序列**
2. 将trace日志喂给ReDex
3. 在同一个dex里，**冷启动需要的类放在dex靠前位置（class_defs靠前 + 类的code_item数据放在data区靠前）**

- 原理：闪存顺序IO更快，减少随机seek；同时zip压缩时连续相似字节更多，**zip压缩率变好，APK压缩包更小**（这个是间接压缩收益）

> 区分两个概念：
>
> - InterDexPass：**类分到不同dex（多dex拆分重排，主收益：dex原始体积减小）**
> - FDO class layout：**同一个dex内部类的先后顺序（主要收益：启动速度，少量zip压缩增益）**

## 3. ReDex配套其他和体积相关Pass（不是重排，但一起配合）

1. **RenameClassesPass**：类名混淆缩短，减少string_ids字符串长度（`La/b/c;`→`LX/a;`），但会破坏InterDex的引用权重，两者不能同时全开，会抵消收益
2. **ReBindRefsPass**：引用重绑定，进一步精简索引引用
3. 字节码优化：死代码删除、方法内联、虚方法去虚拟化(devirtualization)、常量传播，减少方法/指令数量，间接降低method_ids数量

## 4. 容易混淆：Superpack（Meta后续更强压缩，不属于ReDex dex重排）

Meta后来推出Superpack，是更高级的代码压缩，**不是简单类重排**：
把dex里大量引用（method/type id）转换成delta差分编码，利用引用局部性，再配合LZ+熵编码，进一步压缩dex字节流，是在ReDex之后做的上层压缩方案。

## 5. 和R8/Google的Startup Profile对比

- ReDex InterDexPass：**全局跨dex类聚类，减少跨dex引用**（Facebook独创）
- Google R8 Startup Profiles / Baseline Profiles：只做**dex内部类顺序重排（FDO）**，不改变多dex的类拆分方案，**不能减少跨dex引用**

## 6. 关键局限

1. **单dex App，InterDexPass完全无效**；必须multidex才有收益
2. 受65536方法上限硬约束，聚类不能无限塞类
3. 类混淆RenameClassesPass会降低InterDex收益，需要取舍
4. 编译时间明显变长，需要全局分析所有类引用图

# 整体打包链路（插入ReDex的位置）

`.java` → javac → class → D8 → raw classes.dex/classes2.dex → **ReDex（InterDex重排+各类优化Pass）** → 优化后的dex → aapt打包APK → zipalign + 签名

## 总结

Facebook的dex重排核心是 **InterDexPass**：

1. 分析全应用类引用图；
2. 贪心算法把互相引用强的类分到同一个dex；
3. 大幅减少跨dex引用，消除多个dex重复的type/method/string索引条目，减小dex总大小；
4. 配套FDO类顺序重排，改善zip压缩率、提升冷启动速度。
