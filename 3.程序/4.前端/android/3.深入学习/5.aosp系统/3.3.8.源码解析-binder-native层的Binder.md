# libbinder Native IPC 源码详解

源码路径：`frameworks/native/libs/binder/`
核心头文件：

- `ProcessState.h/cpp` 进程全局Binder环境（**进程单例**）
- `IPCThreadState.h/cpp` 线程Binder状态（**TLS线程私有**，你前面`getCallingPid`底层就在这里）
    >TLS：Thread Local Storage，**线程局部存储**
- `IBinder.h`：Native层IBinder接口
- `BBinder.cpp`：服务端本地Binder实体（native服务基类，Java层`android.os.Binder` JNI映射到JavaBBinder，继承BBinder）
- `BpBinder.cpp`：客户端远程Binder代理，持有handle句柄
- `Parcel.h/cpp`：native序列化载体，和Java Parcel一一对应

>
> Native层整体关系：
> `ProcessState`（进程全局：打开驱动、mmap） + 每个线程`IPCThreadState`（TLS，和驱动ioctl交互，保存callingPid/callingUid）
> `IBinder`有两个实现：**BBinder(本地实体服务端) / BpBinder(远程代理客户端)**

## 一、ProcessState：进程全局单例，进程只创建1个

>
> 作用：打开 `/dev/binder`、mmap内核缓冲区、记录驱动fd、管理binder线程池上限。**一个进程全局唯一**。

```
// ProcessState.cpp
sp<ProcessState> ProcessState::self()
{
    Mutex::Autolock _l(gProcessMutex);
    if (gProcess != nullptr) {
        return gProcess;
    }
    gProcess = new ProcessState("/dev/binder");
    return gProcess;
}

// 构造函数
ProcessState::ProcessState(const char *driver)
    : mDriverName(String8(driver))
    , mDriverFD(open_driver(driver)) // open("/dev/binder")
    , mVMStart(MAP_FAILED)
{
    // mmap 1M-8k 共享内存缓冲区，一次拷贝核心
    mVMStart = mmap(nullptr, BINDER_VM_SIZE, PROT_READ, MAP_PRIVATE | MAP_NORESERVE, mDriverFD, 0);
}
```

1. `open_driver`：调用`open("/dev/binder")`拿到fd；
2. `mmap`：映射内核binder buffer到本进程用户虚拟地址，**Binder一次拷贝的根源**；
3. 成员变量`mDriverFD`：所有线程IPCThreadState都复用这同一个fd和同一块mmap内存；
4. `setThreadPoolMaxThreadCount(15)`：设置binder线程池最大线程数，system_server默认15个binder worker线程；
5. `startThreadPool()`：启动binder池线程，线程执行`IPCThreadState::self()->joinThreadPool()`循环等待binder事务。

>
> 一句话：**ProcessState = 进程和binder驱动的连接底座，全局唯一。**

## 二、IPCThreadState（重中之重，TLS线程私有，callingPid/callingUid保存在这里）

>
> 每个线程有独立IPCThreadState，存在**pthread TLS（线程局部存储）**，这就是前面回答为什么静态API不会多AIDL并发混乱的底层根源。

### 2.1 self() 获取当前线程IPCThreadState源码

```
// IPCThreadState.cpp
IPCThreadState* IPCThreadState::self()
{
    if (gHaveTLS) {
restart:
        IPCThreadState* st = (IPCThreadState*)pthread_getspecific(gTLS);
        if (st) return st;
        // 当前线程TLS为空，新建IPCThreadState并挂载到本线程TLS
        return new IPCThreadState;
    }
    // 首次初始化TLS key
    pthread_mutex_lock(&gTLSMutex);
    if (!gHaveTLS) {
        pthread_key_create(&gTLS, threadDestructor);
        gHaveTLS = true;
    }
    pthread_mutex_unlock(&gTLSMutex);
    goto restart;
}

// 构造函数
IPCThreadState::IPCThreadState()
    : mProcess(ProcessState::self()),
      mMyThreadId(gettid())
{
    pthread_setspecific(gTLS, this); // 把当前实例存入本线程TLS
    clearCaller(); // 清空callingPid/callingUid
    mIn.setDataCapacity(256);
    mOut.setDataCapacity(256);
}

// clearCaller：清空调用方身份
void IPCThreadState::clearCaller()
{
    mCallingPid = 0;
    mCallingUid = 0;
}
```

- `pthread_getspecific / pthread_setspecific`：Linux TLS API；
- 不同线程调用`self()`拿到各自独立IPCThreadState对象；
- 成员：`mCallingPid` / `mCallingUid`，**就是Binder.getCallingPid()读取的变量！**

JNI方法`android_os_Binder_getCallingPid`：

```
static jint android_os_Binder_getCallingPid(JNIEnv* env, jclass clazz)
{
    return IPCThreadState::self()->getCallingPid();
}
```

### 2.2 transact() 客户端发起IPC（BpBinder调用它）

```
status_t IPCThreadState::transact(int32_t handle,
                                  uint32_t code,
                                  const Parcel& data,
                                  Parcel* reply,
                                  uint32_t flags)
{
    status_t err = data.errorCheck();
    flags |= TF_ACCEPT_FDS;

    if (err == NO_ERROR) {
        // 把BC_TRANSACTION命令+数据写入mOut缓冲区
        err = writeTransactionData(BC_TRANSACTION, flags, handle, code, data, NULL);
    }

    if (err != NO_ERROR) {
        if (reply) reply->setError(err);
        return (mLastError = err);
    }

    // talkWithDriver：调用ioctl和binder驱动交互，发送事务
    err = waitForResponse(reply);
    return err;
}
```

- `handle`：目标远程Binder的句柄；
- `writeTransactionData`：组装`binder_transaction_data`，写入`mOut`（发送Parcel）；
- `waitForResponse`内部调用`talkWithDriver()`，执行`ioctl(BINDER_WRITE_READ)`，把命令发给内核binder驱动；
- **同步调用（非oneway）：线程阻塞在这里，等待驱动返回BR_REPLY；oneway不阻塞。**

### 2.3 talkWithDriver()：直接和binder驱动ioctl交互

```
status_t IPCThreadState::talkWithDriver(bool doReceive)
{
    binder_write_read bwr;
    bwr.write_buffer = mOut.data();
    bwr.write_size = mOut.dataSize();
    bwr.read_buffer = mIn.data();
    bwr.read_size = mIn.dataCapacity();

    // ioctl 进入内核binder驱动
    status_t ret = ioctl(mProcess->mDriverFD, BINDER_WRITE_READ, &bwr);
    if (ret < 0) return -errno;

    // 驱动返回数据读到mIn缓冲区
    mIn.setDataSize(bwr.read_consumed);
    mOut.setDataSize(bwr.write_consumed);
    return NO_ERROR;
}
```

`binder_write_read`是用户态与binder驱动交互核心结构体，一次ioctl可以**同时写请求、读返回**。

### 2.4 joinThreadPool() 服务端binder线程循环（system_server binder worker线程跑这个）

```
void IPCThreadState::joinThreadPool(bool isMain)
{
    // 向驱动注册本线程为binder looper
    mOut.writeInt32(isMain ? BC_ENTER_LOOPER : BC_REGISTER_LOOPER);
    status_t result;
    do {
        // 阻塞，等待驱动发来binder事务
        result = getAndExecuteCommand();
    } while (result != NO_ERROR);
}

status_t IPCThreadState::getAndExecuteCommand()
{
    status_t result;
    int32_t cmd;
    // 和驱动通信，拿到内核返回命令（BR_TRANSACTION、BR_REPLY等）
    result = talkWithDriver();
    if (result >= NO_ERROR) {
        cmd = mIn.readInt32();
        // 解析内核返回命令，执行事务
        result = executeCommand(cmd);
    }
    return result;
}
```

`joinThreadPool`是死循环：线程阻塞在binder驱动，**收到BR_TRANSACTION事务后唤醒**，调用`executeCommand`处理。

### 2.5 executeCommand()：解析内核返回命令（重点 BR_TRANSACTION）

```
status_t IPCThreadState::executeCommand(int32_t cmd)
{
    BBinder* obj;
    RefBase::weakref_type* refs;
    status_t result = NO_ERROR;

    switch (cmd) {
        case BR_TRANSACTION:
        {
            binder_transaction_data tr;
            result = mIn.read(&tr, sizeof(tr));
            // ========== 重点 ==========
            // 从内核事务tr取出callingPid/callingUid，存入当前线程IPCThreadState
            mCallingPid = tr.sender_pid;
            mCallingUid = tr.sender_euid;

            Parcel buffer;
            buffer.setData(tr.data.ptr, tr.data_size);
            Parcel reply;

            // tr.target.ptr 指向BBinder（本地binder实体）
            obj = (BBinder*)tr.target.ptr;
            // 调用BBinder::transact，进入服务端onTransact
            status_t status = obj->transact(tr.code, buffer, &reply, tr.flags);

            // 把结果打包成BC_REPLY发回驱动
            if (!(tr.flags & TF_ONE_WAY)) {
                writeTransactionData(BC_REPLY, 0, 0, 0, reply, nullptr);
            }
            break;
        }
        case BR_DEAD_REPLY:
        // 死亡通知、引用计数等其它命令
        break;
    }
    return result;
}
```

✅ **这里就是内核callingPid/callingUid写入TLS的位置！**
当binder驱动投递事务到system_server，`executeCommand`读取`binder_transaction_data`，把`sender_pid / sender_euid`赋值给当前线程`mCallingPid/mCallingUid`；**当前binder线程整个事务栈内，调用`getCallingPid()`拿到的就是这组值；事务处理完毕，下一轮循环或者clearCaller清空**。

## 三、IBinder / BBinder / BpBinder（Native层IBinder体系）

### 3.1 IBinder（native接口）

```
class IBinder : public virtual RefBase
{
public:
    virtual status_t transact(uint32_t code,
                               const Parcel& data,
                               Parcel* reply,
                               uint32_t flags = 0) = 0;

    virtual sp<IInterface> queryLocalInterface(const String16& descriptor) = 0;
    virtual status_t linkToDeath(const sp<DeathRecipient>& recipient, void* cookie, uint32_t flags) = 0;
};
```

RefBase：Android native智能指针sp/wp引用计数基类。
IBinder有两个实现：

1. `BBinder`：本地实体，服务端；
2. `BpBinder`：远程代理，客户端，持有handle。

### 3.2 BBinder（服务端本地Binder实体，JavaBBinder继承BBinder）

```
class BBinder : public IBinder
{
public:
    virtual status_t transact(uint32_t code, const Parcel& data, Parcel* reply, uint32_t flags)
    {
        return onTransact(code, data, reply, flags);
    }
protected:
    virtual status_t onTransact(uint32_t code, const Parcel& data, Parcel* reply, uint32_t flags);
};
```

- `transact`直接调用`onTransact`；
- 业务服务（native BnXXX、Java层Binder通过JNI JavaBBinder）**重写onTransact**，分发不同code对应的业务函数；
- new BBinder的时候，libbinder内部调用驱动，在内核创建`binder_node`；

>
> Java层`new Binder()`，JNI创建`JavaBBinder`，`JavaBBinder : public BBinder`，重写onTransact，回调Java层Binder.onTransact。

### 3.3 BpBinder（客户端远程代理）

```
class BpBinder : public IBinder
{
public:
    BpBinder(int32_t handle);
    virtual status_t transact(uint32_t code, const Parcel& data, Parcel* reply, uint32_t flags)
    {
        // 调用IPCThreadState发起IPC
        return IPCThreadState::self()->transact(mHandle, code, data, reply, flags);
    }
private:
    int32_t mHandle; // 远程binder在内核的引用句柄
};
```

BpBinder内部**只有一个handle**，不保存任何业务对象；`transact`直接交给IPCThreadState，通过handle告诉驱动要访问哪一个远端binder_node。

## 四、BnInterface / BpInterface（native AIDL模板类，对应Java Stub/Proxy）

native AIDL自动生成Bn（服务端）、Bp（客户端）：

```
template<typename INTERFACE>
class BnInterface : public INTERFACE, public BBinder
{
    virtual sp<IInterface> queryLocalInterface(const String16& _descriptor);
    virtual String16 getInterfaceDescriptor() const;
};

template<typename INTERFACE>
class BpInterface : public INTERFACE, public BpInterface<INTERFACE>
{
protected:
    inline sp<IBinder> remote() const { return mRemote; }
private:
    sp<IBinder> mRemote; // BpBinder
};
```

- `BnXXX`：继承BBinder，服务端，重写onTransact；
- `BpXXX`：持有BpBinder(mRemote)，业务方法内部调用`remote()->transact()`；

## 五、完整一次IPC流程（App调用AMS attachApplication，native链路串联）

>
> App进程客户端 → system_server服务端

### 【客户端：App进程】

1. App Java层 `IActivityManager.Proxy.attachApplication`
2. JNI调用 → native BpBinder::transact
3. `IPCThreadState::self()->transact()`
4. writeTransactionData组装BC_TRANSACTION + Parcel参数（包含mAppThread这个BBinder对象）
5. talkWithDriver ioctl，发送事务到binder驱动；驱动拷贝数据到内核缓冲区，构造`binder_transaction`，填入callingPid/callingUid，投递到system_server todo队列。
6. 非oneway：App线程阻塞等待BR_REPLY。

### 【服务端：system_server，binder worker线程】

1. binder线程阻塞在`joinThreadPool`，驱动唤醒；
2. `getAndExecuteCommand` → talkWithDriver读取内核返回命令`BR_TRANSACTION`；
3. `executeCommand`：从binder_transaction_data取出sender_pid/sender_euid，**写入当前线程IPCThreadState.mCallingPid/mCallingUid**；
4. 拿到BBinder（AMS的BnActivityManager），调用`BBinder::transact` → `BnActivityManager::onTransact`；
5. native onTransact反序列化参数，调用JNI，进入Java层 `IActivityManager.Stub.onTransact`；
6. Java代码执行`Binder.getCallingPid()`，JNI读取当前线程IPCThreadState里面mCallingPid；
7. AMS执行业务逻辑 attachApplication；
8. 业务返回，构造reply数据包，`BC_REPLY`发送回驱动；
9. IPCThreadState清空caller身份，binder线程回到joinThreadPool循环阻塞，等待下一个事务。

## 六、clearCallingIdentity native源码（身份切换底层）

```
// IPCThreadState
uint64_t IPCThreadState::clearCallingIdentity()
{
    uint64_t token = ((uint64_t)mCallingUid << 32) | mCallingPid;
    // 清空当前线程TLS内的calling身份
    mCallingUid = getuid();
    mCallingPid = gettid();
    return token;
}

void IPCThreadState::restoreCallingIdentity(uint64_t token)
{
    mCallingUid = (uint32_t)(token >> 32);
    mCallingPid = (uint32_t)token;
}
```

>
> 核心：只是读写**当前线程TLS的IPCThreadState里面的mCallingUid/mCallingPid**，**不会修改内核task_struct真实uid**，只影响嵌套IPC的身份继承。
> Java `Binder.clearCallingIdentity()` JNI就是调用这个native方法。

## 七、Parcel native层

`Parcel`：序列化缓冲区，Java Parcel和native Parcel是一一映射，JNI互相转换。
`writeStrongBinder`：写入IBinder对象；

- 如果写入**BBinder（本地实体，如mAppThread）**：驱动识别，在目标进程新建binder_ref；
- 如果写入**BpBinder（远程代理）**：直接传递handle。

## 八、关键要点总结（和你前面Java层知识联动）

1. **ProcessState：进程单例，打开/dev/binder、mmap；一个进程一份。**
2. **IPCThreadState：线程TLS私有对象，每个binder线程独立；mCallingPid/mCallingUid在这里，是getCallingPid的数据源。**
3. `BBinder`：native本地Binder实体（服务端）；Java Binder(JavBBinder)继承它；内核生成binder_node。
4. `BpBinder`：native远程代理，只持有handle；客户端Proxy内部的mRemote就是BpBinder。
5. 一次IPC：客户端`BpBinder.transact` → IPCThreadState发送BC_TRANSACTION；驱动投递BR_TRANSACTION到服务端；服务端executeCommand填充calling身份，调用BBinder.onTransact。
6. 静态API不混乱根源：**身份数据保存在线程TLS，不是全局static变量**，多个binder线程各自独立IPCThreadState。
7. `clearCallingIdentity`只是修改TLS内缓存的calling uid/pid，**不修改内核真实进程身份**。

## 九、JNI桥梁（Java ↔ Native）

`android_util_Binder.cpp`：

- Java `android.os.Binder` JNI映射到`JavaBBinder`（BBinder子类）
- Java静态native方法`getCallingPid/getCallingUid/clearCallingIdentity`全部调用`IPCThreadState::self()`。
- Java IBinder（BinderProxy）对应native BpBinder。
