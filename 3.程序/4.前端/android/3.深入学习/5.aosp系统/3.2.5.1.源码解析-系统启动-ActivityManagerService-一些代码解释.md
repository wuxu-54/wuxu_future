# mServices.attachApplicationLocked(app, processName); 啥作用

这段代码在 **AMS（ActivityManagerService）** 的 `finishAttachApplicationInner` 方法，运行在 system_server 的 AMS 主线程。

```java
// Find any services that should be running in this process... 
if (!badApp) { 
    try { 
        didSomething |= mServices.attachApplicationLocked(app, processName); 
        checkTime(startTime, "finishAttachApplicationInner: " 
                + "after mServices.attachApplicationLocked"); 
    } catch (Exception e) { 
        Slog.wtf(TAG, "Exception thrown starting services in " + app, e); 
        badApp = true; 
    } 
}
```

> 前置背景：App进程fork成功，App调用AMS `attachApplication`，AMS经过一系列处理，进入 `finishAttachApplicationInner`。
> 前面已经处理了Activity相关的逻辑，**现在轮到Service**。

## 逐行拆解

### 注释

`// Find any services that should be running in this process...`
> 查找**归属这个App进程（pid）** 的Service，如果有需要运行的，就把Service拉起来。

### `if (!badApp)`

`badApp` 标记：前面流程有没有发生严重异常。

- 如果前面已经出错（比如Application信息异常），`badApp=true`，**不再尝试启动Service**，跳过这段。

### `mServices`

`mServices` 是 AMS 的成员 `ActiveServices`，AMS里面**专门管理所有Service**的管理器。
`ActiveServices` 负责：Service记录、启停、绑定、进程托管、oom管理。

### `mServices.attachApplicationLocked(app, processName)`

**核心方法：ActiveServices.attachApplicationLocked()**
> 含义：App进程已经就绪（attach成功），检查：**哪些Service属于这个应用包名，并且需要运行在当前这个进程里**，然后调度启动这些Service。

#### 什么时候会触发启动Service？

1. **Manifest里面声明的 `persistent=true` 常驻Service**，进程起来就要启动；
2. **之前AMS已经收到过启动Service请求（startService），但当时进程没起来，AMS把请求暂存了**。

> 场景举例：
> 你调用`startService`，但App进程还没创建 → AMS保存这个Service任务；
> 等到App fork出来、attach AMS成功之后，就在这里**补发启动Service**。

返回值：`boolean`

- `true`：确实启动了Service（做了事）
- `false`：没有任何Service需要在这个进程启动

### `didSomething |= ...`

`didSomething` 是一个布尔标记。
`|=` 按位或赋值：只要这一步**启动了Service**，`didSomething`就变成true。
AMS后面会根据`didSomething`判断：本次attach有没有执行实际组件启动工作，用于进程优先级、LRU、OOM调整。

### `checkTime(...)`

性能埋点，记录耗时。打印日志，看 `attachApplicationLocked` 花了多久，用于系统性能分析，看App启动耗时瓶颈。

### try-catch + Slog.wtf + badApp=true

- 如果启动Service过程抛出异常，`Slog.wtf` 打印严重日志（wtf = what a terrible failure）
- 设置 `badApp=true`：标记这个App进程异常。后续AMS会做容错，比如杀掉这个进程，防止坏进程持续占用资源。

## 完整时序（串联前面你学的attachApplication整条链路）

1. App进程启动，`ActivityThread.main()`
2. App端 `ApplicationThread` Binder调用 AMS `attachApplication()`
3. AMS `attachApplication` → `attachApplicationLocked` → `finishAttachApplicationInner`
4. AMS先处理**Activity相关**（如果这个进程是为了启动Activity而创建）
5. ✅ **执行这段代码：ActiveServices.attachApplicationLocked**
   查找待启动Service，在这个新App进程里面拉起Service
6. 之后AMS再通知App进程的`ApplicationThread`执行 `bindApplication`（你前面看的ActivityThread.bindApplication那一大段）

> 关键点：**AMS在system_server侧先决定要启动哪些Service，再通知App进程去执行组件创建**。

## 核心逻辑一句话

App进程attach到AMS之后，AMS的ActiveServices检查有没有**待启动、归属这个进程的Service**，有的话就启动它们；如果启动Service时发生异常，标记App为坏App。

## 容易混淆的点

1. ❗ **这里是system_server（AMS）去决定要启动Service，不是App自己主动启动**
   App进程刚fork，还没走到Application.onCreate；AMS先把积压的startService任务，在这个时机唤醒。
2. 这是**进程attach的一次性时机**：进程刚就绪，补发之前排队的Service任务。
3. `persistent`服务：只要进程启动，每次attach都会在这里被拉起。

## 和你前面知识点联动

- `mServices.attachApplicationLocked` 执行完成后，AMS 发 Binder 回调给 `ApplicationThread.scheduleBindApplication`
- App收到scheduleBindApplication，进入ActivityThread.bindApplication：
  - handleAttachAgent（加载JVMTI agent）
  - 创建Application，Instrumentation.newApplication
  - Application.attachBaseContext / onCreate
  - 然后App内部才会去创建Service实例，执行Service.onCreate

> 简单区分：
> AMS侧：`attachApplicationLocked` → **决定要启动哪个Service**
> App进程侧：收到消息后，才去实例化Service对象、走Service生命周期
