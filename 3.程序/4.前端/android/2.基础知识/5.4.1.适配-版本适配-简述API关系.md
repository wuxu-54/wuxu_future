# SDK API关系

要理解Android高版本系统SDK与应用引入的SDK之间的关系，以及系统API版本与应用开发中使用的Android API版本的关系，需要从**运行时环境**（设备系统）和**开发时依赖**（应用及第三方库）两个维度展开分析。以下是详细说明：

## 一、Android系统SDK（设备端）与应用引入的SDK（开发时）的关系及影响

### 1. 核心概念区分

- **系统SDK（设备端）**：指设备上安装的Android系统框架（如`framework.jar`），包含该系统版本（如Android 12）对应的API实现、系统服务、行为规则等，是应用实际运行的底层环境。其版本由设备的Android系统版本决定（如Android 12对应API 31，Android 13对应API 33）。  
- **应用引入的SDK**：指应用开发时依赖的第三方库（如Glide、Retrofit）或官方库（如AndroidX、Play Services），这些SDK本质是预编译的代码集合，可能包含对特定Android API的调用。  

### 2. 两者的依赖关系

应用引入的SDK最终会被打包到APK中，与应用自身代码一起在设备的**系统SDK**上运行。因此，应用引入的SDK的功能能否正常工作，取决于：  

- 该SDK调用的Android API是否在设备的系统SDK中存在（即设备API版本 ≥ SDK所需的最低API版本）；  
- 该SDK是否适配了设备系统的行为变更（如权限、安全限制等）。  

### 3. 关键影响场景

#### （1）应用引入的SDK依赖高版本系统API  

若第三方SDK使用了高于设备系统版本的API（如SDK中调用了API 31的`Notification.Builder.setForegroundServiceBehavior()`），而应用运行在API 30（Android 11）的设备上：  

- **直接后果**：运行时会抛出`NoSuchMethodError`或`ClassNotFoundException`，导致功能崩溃（如通知无法显示）。  
- **解决方式**：  
  - 应用需确保引入的SDK的`minSdkVersion` ≤ 应用自身的`minSdkVersion`（通过Gradle依赖树检查，如`./gradlew app:dependencies`）；  
  - 若SDK必须使用高版本API，需要求SDK提供兼容层（如通过`@RequiresApi`注解+低版本替代实现），或应用在调用SDK前通过`Build.VERSION.SDK_INT`判断版本并降级处理。  

#### （2）系统SDK行为变更导致引入的SDK失效  

高版本系统SDK可能修改旧API的行为（如权限收紧、功能限制），而应用引入的SDK若未适配这些变更，即使调用的API存在，功能也可能异常。  

- **例子**：Android 12（API 31）新增“通知跳转限制”（禁止从通知直接启动后台Activity，即trampoline限制）。若应用引入的推送SDK（如某厂商推送）未适配此变更，当应用运行在Android 12设备上时，点击通知可能无法跳转至目标页面（系统会拦截跳转）。  
- **解决方式**：选择已适配高版本系统的SDK版本（如查看SDK更新日志，确认支持API 31+），或手动修改SDK调用逻辑（如通过`PendingIntent.FLAG_IMMUTABLE`适配通知跳转）。  

#### （3）引入的SDK与系统SDK存在冲突  

极少数情况下，第三方SDK可能通过反射等方式修改系统SDK的内部逻辑（如Hook系统服务），而高版本系统SDK可能修复了相关漏洞或限制了反射权限，导致SDK功能异常。  

- **例子**：Android 11（API 30）限制了对非公开API的反射调用（通过`hiddenapi`机制）。若某SDK通过反射调用`ActivityThread`的非公开方法，在Android 11+设备上会被系统拦截，导致初始化失败。  
- **解决方式**：避免使用依赖非公开API的SDK，或要求SDK厂商替换为公开API实现。  

## 二、Android系统API版本与应用开发引入的Android API版本的关系及影响

应用开发中引入的Android API版本由`compileSdkVersion`（编译时API）和`targetSdkVersion`（目标行为API）决定，而设备的系统API版本是应用实际运行的环境（如Android 12对应API 31）。两者的匹配关系直接影响应用的**功能可用性**和**系统行为兼容性**。

### 1. 核心逻辑：“声明适配”与“实际运行环境”的互动  

- 应用通过`compileSdkVersion`声明编译时使用的最高API（如`compileSdk 31`表示使用Android 12的SDK编译）；  
- 通过`targetSdkVersion`声明“已适配的目标系统行为”（如`targetSdk 31`表示应用已适配Android 12的行为变更）；  
- 设备的系统API版本（如API 31）决定了实际可用的API和默认行为规则。  

### 2. 关键影响场景（以Android 12（API 31）与`targetSdk 31`为例）  

#### （1）应用`targetSdk 31`运行在Android 12（API 31）设备上  

此时应用的“声明适配版本”与系统实际版本一致，系统会**严格启用该版本的行为限制**，应用必须遵守所有Android 12的特性和限制：  

- **强制适配的行为**：  
  - 通知必须指定`NotificationChannel`（否则无法显示）；  
  - 前台服务必须在通知中显式声明类型（通过`setForegroundServiceBehavior()`）；  
  - 禁止Activity从后台启动（如通过`PendingIntent`从服务启动Activity会被拦截）。  
- **影响**：若应用未适配这些行为，会直接出现功能异常（如通知不显示、跳转失败）。  

#### （2）应用`targetSdk 31`运行在Android 13（API 33）设备上  

系统API版本（33）高于应用的`targetSdk`（31），此时系统会**部分兼容旧行为**，但仍可能启用高版本的强制限制：  

- **兼容部分**：系统会按`targetSdk 31`的规则运行应用（如不强制要求Android 13的“通知权限申请”，因为`targetSdk < 33`）；  
- **强制限制**：Android 13的某些安全限制（如对`READ_MEDIA_IMAGES`等分区存储权限的细化）即使`targetSdk < 33`也可能生效，若应用未处理，会导致权限申请失败。  
- **影响**：应用需同时适配`targetSdk`版本的行为和更高系统版本的强制变更（需通过版本判断兼容）。  

#### （3）应用`targetSdk 30`运行在Android 12（API 31）设备上  

系统API版本（31）高于应用的`targetSdk`（30），系统会启用“兼容性模式”，**弱化部分新行为限制**，但仍有风险：  

- **兼容部分**：系统会按`targetSdk 30`的规则运行（如允许通知trampoline跳转，不强制前台服务声明类型）；  
- **潜在问题**：Android 12的某些新API（如`ActivityResultContracts`的扩展）应用无法使用（因`compileSdk`若为30，编译时无法访问API 31）；且系统可能对低`targetSdk`应用施加限制（如Google Play要求新应用在2023年起`targetSdk`≥31，否则无法上架）。  

#### （4）应用`targetSdk 31`运行在Android 11（API 30）设备上  

系统API版本（30）低于应用的`targetSdk`（31），此时需满足`minSdkVersion ≤ 30`（否则无法安装），但应用中调用的API 31特性必须有兼容处理：  

- **直接调用API 31方法**：会抛出`NoSuchMethodError`（如调用`Notification.Builder.setForegroundServiceBehavior()`在API 30设备上）；  
- **解决方式**：通过`Build.VERSION.SDK_INT >= 31`判断，对高版本API提供低版本替代实现（如API 30及以下用旧的前台服务逻辑）。  

## 总结

1. **系统SDK与引入的SDK**：应用引入的SDK需适配设备系统SDK的API版本和行为，否则可能因API不存在或行为变更导致崩溃。  
2. **系统API版本与应用开发API版本**：  
   - `compileSdk`决定开发时可用的最高API，需≥`targetSdk`；  
   - `targetSdk`决定系统对应用的行为限制，需与目标用户的系统版本匹配；  
   - 系统API版本是实际运行环境，应用需通过版本判断兼容“高版本系统运行低targetSdk应用”和“低版本系统运行高targetSdk应用”的场景。  

例如，当应用`targetSdk 31`（适配Android 12）时，需确保：在Android 12上遵守其行为限制，在Android 13上兼容新强制特性，在Android 11及以下对API 31方法做降级处理——这是版本适配的核心逻辑。
