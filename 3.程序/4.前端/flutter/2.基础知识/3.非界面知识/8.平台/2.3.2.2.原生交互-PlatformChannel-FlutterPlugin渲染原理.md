# FlutterPlugin渲染过程

从 Dart 代码中的 `Text("hello")` 变成屏幕上可见的像素，中间经过了一系列精心设计的数据流转和渲染管线。我们把这个过程拆成 **Dart 层构建、数据跨语言传递、C++ 引擎接收并光栅化** 三大阶段，把所有细节串联起来。

---

## 一、Dart 层：构建 Layer 树，而不是直接绘制

### 1. Widget → Element → RenderObject → Layer

当你的 Widget 树构建完毕后，每个 `Widget` 都有对应的 `Element`，而最终负责布局和绘制的对象是 `RenderObject`。  
每帧需要更新时，脏 `RenderObject` 会依次执行：

- **layout**：计算自己的大小和位置。
- **paint**：通过 `PaintingContext` 将绘制命令录制到 `PictureLayer` 中。

这些绘制命令通过 `Canvas` 对象发出，比如 `canvas.drawRect(...)`, `canvas.drawText(...)`。这个 `Canvas` 本质上是 `PictureRecorder` 创建的，它最终会生成一个 `Picture` 对象。

### 2. Picture 与 Layer 的关系

`Picture` 内部保存了一份**平台无关的绘制指令列表**（具体实现就是 `DisplayList`）。  
`RenderObject.paint` 方法将 `Picture` 放入一个 `PictureLayer`，并构建出一棵以 `ContainerLayer` 为根的 **Layer 树**。树的节点类型包括：

- `PictureLayer`：携带一份绘制记录。
- `TransformLayer`、`OpacityLayer`、`ClipRectLayer`：合成属性层，不直接绘图，描述变换、透明度和裁剪。
- `TextureLayer`、`PlatformViewLayer`：外部纹理或原生视图的占位。

这棵树在 Dart 层的最终形态就是 **Scene** 对象，它包装了整棵 Layer 树。

---

## 二、跨越 Dart 与 C++ 的边界：dart:ui 的魔法

`dart:ui` 中的很多类并不是纯 Dart 实现，而是直接通过 **native 绑定** 调用 C++ 引擎。

### 1. 关键绑定类

- `Canvas` → C++ 的 `DartCanvas`
- `PictureRecorder` → `DartPictureRecorder`
- `Picture` → `DartPicture`
- `SceneBuilder` → `SceneBuilder`
- `Scene` → `Scene`
- `Window` (或 `PlatformDispatcher`) → `RuntimeController`

当 Dart 代码调用 `window.render(scene)` 时，实际上触发了：

```dart
// 简化后的 Dart 端代码
void render(Scene scene) native 'PlatformConfiguration_render';
```

这个 native 函数在 C++ 中是这样绑定的（通过 tonic，Dart VM 的绑定库）：

```cpp
void PlatformConfiguration::Render(Dart_Handle scene_handle) {
  Scene* scene = tonic::DartConverter<Scene*>::FromDart(scene_handle);
  // ... 将 scene 提交给引擎
}
```

### 2. 数据如何传递？

传递的不是数据拷贝，而是 **指针**。`Scene` 在 Dart 层是一个薄包装，内部持有一个指向 C++ `Scene` 对象的指针。Native 绑定直接将这个指针取出，**Dart 层放弃所有权**，控制权完全交给 C++。

### 3. Picture 的录制：DisplayList 的产生

当我们在 Dart 中用 `Canvas` 绘制时，例如 `canvas.drawRect(...)`，该调用直接进入 C++：

```cpp
void DartCanvas::drawRect(double left, double top, double right, double bottom, Paint* paint) {
  // 将参数转换为引擎内部的 Rect, Paint 对象
  display_list_builder_->DrawRect(rect, paint->ToDisplayListPaint());
}
```

**`DisplayListBuilder`** 是一个 C++ 类，它逐条记录所有绘制指令，形成一个 **DisplayList**（平台无关的轻量级记录格式）。  
当 `PictureRecorder.endRecording()` 被调用时，Builder 将当前的 DisplayList 打包成一个不可变的 `DisplayList` 对象，并存入 `Picture`，最终这个 `Picture` 被放入 `PictureLayer`。

**DisplayList 包含的命令有**：`DrawRect`, `DrawPath`, `DrawTextBlob`, `SaveLayer`, `ClipRect`, `Translate`, `Concat` 等，都是序列化的数据结构，不依赖任何特定的渲染 API。

## 三、C++ 引擎端：UI 线程的接收与提交

当 Dart 调用 `window.render(scene)` 后，C++ 的 `RuntimeController::Render` 被触发：

```cpp
void RuntimeController::Render(std::unique_ptr<Scene> scene) {
  // 从 Scene 中取出 Layer 树（所有权转移）
  auto layer_tree = scene->takeLayerTree();
  
  // 包装成 Frame，交给 Animator
  auto frame = std::make_unique<Frame>(std::move(layer_tree), target_time);
  animator_->EnqueueFrame(std::move(frame));
}
```

- `Animator` 负责帧调度，它将 `Frame` 通过 **TaskRunner** 发送到 **Raster 线程**。
- `Frame` 对象内包含了整个 Layer 树的根节点（一个 `Layer` 指针），以及帧的目标时间戳。

**这里没有绘制**，UI 线程只是把 Layer 树的所有权传递给了 Raster 线程。

---

## 四、Raster 线程：合成与光栅化

Raster 线程的主循环收到 `Frame` 后，调用 `Rasterizer::Draw`。整个过程分为 **合成（Compositing）** 和 **光栅化（Rasterization）** 两步。

### 1. 合成（Compositing）

`Rasterizer` 创建一个 `CompositorContext`，遍历 Layer 树：

- 对于 **PictureLayer**，如果被标记为可缓存且内容未变，就用之前缓存的 GPU 纹理（`LayerSnapshot`），跳过重录。
- 对于 **TransformLayer / OpacityLayer / ClipRectLayer**，动态合并它们的变换、透明度和裁剪，并决定是否需要离屏渲染。
- 整个遍历过程会产生一个**绘制顺序**，并确定每个 PictureLayer 最终要被光栅化的时机和上下文。

合成的目的是 **最小化实际需要重绘的内容**，并正确处理图层间的混合。

### 2. 光栅化（Rasterization）

当确定某个 PictureLayer 需要重新绘制时，Rasterizer 调用：

```cpp
void PictureLayer::Paint(PaintContext& context) const {
  SkCanvas* canvas = context.canvas;  // 或 Impeller 的 Aiks Canvas
  display_list_->RenderTo(canvas);   // 把 DisplayList 的命令“回放”到 Canvas 上
}
```

这里就分流了，取决于当前用的是 Skia 还是 Impeller。

#### a) Skia 路径

`DisplayList` 对象调用 `RenderTo(SkCanvas*)`，遍历内部指令，逐条转换为 Skia API 调用：

```
for (auto& op : display_list_ops) {
  switch (op.type) {
    case DrawRect: canvas->drawRect(...); break;
    case DrawTextBlob: canvas->drawTextBlob(...); break;
    // ...
  }
}
```

Skia 在自己的 `SkCanvas` 实现中产生具体的 GPU 命令（通常通过 OpenGL/Vulkan backend），将矢量图形变成纹理上的像素。

#### b) Impeller 路径

Impeller 不使用 SkCanvas，而是将 `DisplayList` 交给 `AiksContext`：

```cpp
auto aiks_canvas = aiks_context_->MakeCanvas(render_target);
display_list_->RenderTo(aiks_canvas);
aiks_canvas->Flush();
```

Impeller 内部的 `AiksCanvas` 将 `DisplayList` 操作转化为 **Entity** 对象（一个绘制实体，包含几何、着色器、混合模式等），构建一个不变的 `Frame` 对象，然后通过 Hardware Abstraction Layer (HAL) 提交到 Metal 或 Vulkan。  
**着色器全部 AOT 编译**，运行时无任何编译开销。

### 3. 最终上屏

无论 Skia 还是 Impeller，光栅化完成后，渲染目标（`SurfaceFrame`）被提交给平台层：

- Android 上调用 `ANativeWindow_lock/ unlockAndPost`。
- iOS 上调用 Metal 的 `presentDrawable:` 或 OpenGL 的 `presentRenderbuffer`。

系统合成器（SurfaceFlinger / CoreAnimation）再将这张纹理与屏幕上其他窗口混合，最终显示。

## 五、完整数据流总结

1. **Dart UI**：RenderObject.paint 使用 PictureRecorder 录制绘制命令，生成 DisplayList，放入 PictureLayer。
2. **Dart → C++ 跨语言**：`window.render(scene)` 通过 native binding 将 Layer 树的所有权交给 C++ 的 `RuntimeController`。
3. **C++ UI 线程**：`Scene` 取出 `LayerTree`，包装为 `Frame`，通过 `Animator` 提交给 Raster 线程。
4. **C++ Raster 线程**：`Rasterizer` 遍历 Layer 树，对每个 `PictureLayer` 调用 `display_list->RenderTo(canvas)`。
5. **渲染后端**：Skia 或 Impeller 将 DisplayList 指令转化为 GPU 命令，光栅化到纹理，最终提交到 Surface。

**核心设计理念**：

- **分层与复用**：Layer 树让不变的 PictureLayer 可以缓存，避免重录。
- **平台无关表示**：DisplayList 抽象了所有绘制操作，使得切换渲染后端（Skia/Impeller）无需修改 Dart 上层。
- **线程分工**：UI 线程只构建描述“画什么”，Raster 线程只负责“怎么画”，并行高效。

理解这条链路，你就能准确把握性能瓶颈的位置（是 Dart 层构建慢？还是 DisplayList 回放慢？还是 GPU 着色器复杂？），并采取相应的优化措施。
