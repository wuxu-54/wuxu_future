# 原生交互两大方式：FFI和PlatformChannels

在 Flutter 中，Dart 代码与原生代码交互有两大核心方案：**Platform Channel** 和 **dart:ffi**。它们的设计哲学、通信机制、性能边界和适用场景截然不同。下面从原理到实战，逐项对比。

---

## 一、核心本质对比

| 维度 | Platform Channel | dart:ffi |
|------|------------------|----------|
| **交互对象** | Android (Java/Kotlin)、iOS (ObjC/Swift) 等平台层代码 | C 语言函数（或任何能导出 C ABI 的库） |
| **通信模型** | 异步消息传递（序列化 → 跨线程转发 → 反序列化） | 同步/异步直接函数调用，操作内存 |
| **性能** | 中等，存在序列化开销和线程跳转 | 极高，接近纯 C 调用，无额外序列化 |
| **数据类型** | 标准编解码器定义的有限类型（bool、int、String、List、Map 等） | C 基本类型、结构体、指针；需手动内存管理 |
| **调用方代码** | Dart 端 + 平台端（Java/Kotlin/Swift/ObjC）都要写代码 | 只需 Dart + C，不需要 Java/Swift 层 |
| **平台依赖** | 强依赖 Flutter 引擎的平台嵌入层 | 直接依赖动态库，与 Flutter 引擎无关 |
| **线程/异步** | 强制异步，原生回调在主线程 | 可以同步，可以在任意 Isolate 调用 |
| **内存安全** | 自动管理，无指针暴露 | 手动管理，易出内存泄漏或野指针错误 |

---

## 二、通信原理展开

### Platform Channel 数据流

```
Dart (UI Isolate)
  → invokeMethod (序列化为二进制)
    → Engine (C++) 跨线程传递
      → Android/iOS 平台主线程 (反序列化为原生对象)
        → 原生方法执行 → 返回结果 (序列化)
          → 反向路径回到 Dart
```

- **所有数据都要经过编解码**（默认为 `StandardMessageCodec`），不支持自定义内存布局。
- **调用一定是异步**，返回 Future，无法同步获取结果。
- 原生端代码必须运行在平台主线程（引擎自动处理）。

### dart:ffi 数据流

```
Dart (任意 Isolate)
  → 直接加载动态库 (.so/.dylib/.dll)
  → 通过 Dart FFI 绑定 C 函数签名
  → 调用 C 函数（直接 CPU 指令跳转，无中间层）
  → C 函数操作内存，返回基本类型或通过指针写入数据
```

- **零序列化**：传递的是原始二进制值（int、double）或指针。
- **可以同步调用**（阻塞 Dart 线程直到 C 返回），也可通过 `NativeCallable` 等实现异步。
- **可以直接操作堆内存**，共享大块数据（如视频帧）无需拷贝。

## 三、性能差异与高频场景

### 1. 调用开销

一个简单的 `int add(int a, int b)` 调用：

- Platform Channel：约 **500 µs ~ 1 ms**（主线程切换 + 序列化）。
- dart:ffi：约 **< 1 µs**（仅函数调用开销）。

### 2. 大数据传输

例如一张 1920×1080 的 RGBA 帧（约 8 MB）：

- Platform Channel 传递 `Uint8List`：数据会被拷贝到引擎内部缓冲区，再跨线程传送，两次内存拷贝起步，延迟 > 10 ms。
- dart:ffi 传递 `Pointer<Uint8>`：Dart 端可以直接把一块通过 `malloc` 分配的 C 内存指针传给 Dart，通过 `Pointer` 操作，**零拷贝**，延迟 < 1 ms。

### 3. 实时音视频、游戏引擎、图像处理

必须用 FFI，否则性能瓶颈明显。OpenCV、TensorFlow Lite、FFmpeg 等 C/C++ 库的 Flutter 绑定几乎全部基于 FFI。

## 四、开发复杂度与安全性

### Platform Channel

- **优点**：与 Flutter 框架深度集成，有官方插件模板，可以方便地使用 Android/iOS 所有平台 API（相机、GPS、蓝牙）。异常会被封装成 `PlatformException`，Dart 侧可用 try/catch。
- **缺点**：需要在两个平台分别写实现（即使逻辑相同），不同语言的类型映射要手动保证一致。
- **安全性**：内存由运行时管理，几乎不会崩溃，除非原生端写了错误代码。

### dart:ffi

- **优点**：一次写 C 代码，跨平台编译成 .so/.dylib/.dll，Dart 侧绑定一次即可。非常适合复用现有 C 库，或者编写高性能算法。
- **缺点**：
  - 必须管理内存：`malloc`/`calloc`/`free`，忘记释放会泄漏，重复释放会崩溃。
  - C 函数指针错误（如空指针解引用）会直接导致应用闪退，无法被 Dart 捕获。
  - 结构体对齐、大小端问题需开发者处理。
  - 需要熟悉 C 语言和 FFI 类型映射（`Int8`, `Pointer<Void>`, `Struct` 等）。
- **调试难度**：需要借助原生调试器（lldb/gdb），Dart DevTools 只能看到 FFI 调用边界。

---

## 五、与平台 API 的交互能力

- **Platform Channel**：可以直接调用 Android 的 `Activity`, `Context`, `Intent`, iOS 的 `UIApplication`, `UIDevice` 等，因为原生代码运行在平台层，有完整权限。
- **dart:ffi**：只能调用 C 函数。如果想调用 Java/Kotlin API（比如弹出通知），FFI 无法直接做到。需要通过以下间接方式：
  1. 在 C 代码里通过 **JNI** 调用 Java 方法（极大增加复杂度）。
  2. 使用 Dart 的 `Platform Channel` 与 FFI 结合：FFI 处理高性能部分，需要调用平台 API 时再通过 Channel 通知原生端。
  
反之，Platform Channel 也无法直接操作 C 库，除非在原生端（Java/Swift）封装一层 JNI 或 C API 调用。

## 六、典型应用场景

### 首选 Platform Channel

- 使用平台专有能力：相机、GPS、蓝牙、文件选择器、通知、电池信息等。
- 需要与原生 UI 组件混合（Platform View）。
- 与现有 Java/Kotlin/Swift 库集成，且不想封装成 C 接口（如支付 SDK、地图 SDK 通常会提供原生的 Android/iOS 库，适合 Channel）。
- 简单的数据请求，如获取设备型号、系统版本。

### 首选 dart:ffi

- CPU 密集型算法（加密解密、压缩解压、图像滤波、音视频编解码）。
- 已有 C/C++ 库需要复用（OpenCV, FFmpeg, TensorFlow Lite C API, SQLite 等）。
- 需要实时处理大块连续内存（如音频流、摄像头原始帧）。
- 游戏引擎底层（如通过 FFI 调用 C 实现的物理引擎）。
- 需要高频率调用（如 60 fps 逐帧处理）。

## 七、两者能否混用？

**完全可以，且推荐**。很多高性能 Flutter 插件会混合使用：

- 使用 `dart:ffi` 调用 C 库处理核心逻辑（如美颜滤镜）。
- 使用 `MethodChannel` 获取相机纹理（`TextureRegistry`）和显示结果。
- 用 `EventChannel` 将 C 处理后的帧回调给 Dart。

例如，一个实时滤镜插件架构：

```
Dart 端 → MethodChannel 开启相机 (原生) → 原生将帧通过 FFI 传入 C 滤镜库处理 → 返回给 Dart 或直接渲染
```

```
                                 Yes ↓                  No ↓

                                         └──────────────┘ └──────────────────┘
```

## 九、简单代码对比

### Platform Channel 调用原生 `int add(int a, int b)`

**Dart:**

```dart
static const channel = MethodChannel('math');
Future<int> add(int a, int b) async {
  return await channel.invokeMethod<int>('add', {'a': a, 'b': b});
}
```

**Android (Kotlin):**

```kotlin
MethodChannel(flutterEngine.dartExecutor.binaryMessenger, "math")
    .setMethodCallHandler { call, result ->
        if (call.method == "add") {
            val a = call.argument<Int>("a")!!
            val b = call.argument<Int>("b")!!
            result.success(a + b)
        }
    }
```

### dart:ffi 调用 C `int add(int a, int b)`

**C 代码 (math.c):**

```c
#include <stdint.h>
int add(int a, int b) {
    return a + b;
}
```

**Dart:**

```dart
import 'dart:ffi';

final DynamicLibrary lib = Platform.isAndroid
    ? DynamicLibrary.open("libmath.so")
    : DynamicLibrary.process();

final int Function(int, int) add = lib
    .lookup<NativeFunction<Int32 Function(Int32, Int32)>>("add")
    .asFunction();
    
void main() {
  print(add(3, 4)); // 同步输出 7
}
```

## 十、总结

- **Platform Channel** 是连接 Dart 与平台生态的“翻译官”，简单安全，适合大多数非性能敏感的平台功能调用。
- **dart:ffi** 是 Dart 直通 C 世界的“特快列车”，零开销，适合高性能计算和复用 C 库，但需要小心内存管理。
- 实际工程中，复杂插件往往会**两者结合**，用 FFI 做重活，用 Channel 调度和传递结果。

理解这两者的边界，就能在 Flutter 中自由驾驭原生能力了。
