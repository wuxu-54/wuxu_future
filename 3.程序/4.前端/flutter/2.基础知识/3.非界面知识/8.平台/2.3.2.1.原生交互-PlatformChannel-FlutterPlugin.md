# Flutter Engine

想真正把 Flutter 性能做到极致、解决一些诡异的渲染问题，或者只是好奇“框架之下发生了什么”，就需要深入 **Flutter Engine**。它是一套用 C++ 实现的高性能运行时和渲染库，上接 Dart 框架，下接操作系统。

下面我用一个递进的结构，带你从外到内，拆解引擎的核心。

---

## 1. 引擎在 Flutter 三层架构中的位置

Flutter 的经典分层：

- **Framework（Dart）**：`material`、`cupertino`、`widgets`、`rendering`、`animation`、`painting`、`gestures` 等。
- **Engine（C++）**：提供 `dart:ui` 的所有底层实现，执行 Dart 代码、合成与光栅化、处理文本、调用系统 API。
- **Embedder（平台语言）**：为引擎创建 Shell，管理事件循环、原生窗口、输入与平台通道，是“发动机的底座”。

你写的每一个 `Container`、`Text`，最终都会落到 `RenderObject.layout` / `paint` 并生成 `Layer` 树，然后通过 `dart:ui` 提交给 C++ 引擎去“画出来”。

---

## 2. 引擎仓库与构建产物

引擎源代码在 [flutter/engine](https://github.com/flutter/engine) 仓库，主要目录：

- `shell/`：引擎壳（Platform、UI、Raster、IO 线程的管理）。
- `lib/ui/`：`dart:ui` 的 C++ 实现（绘制的钩子、窗口、帧回调等）。
- `flow/`：图层组合与渲染管线（Layer tree → 合成）。
- `runtime/`：Dart VM 的集成和启动。
- `third_party/dart/`：Dart SDK 副本。
- `impeller/`：新一代渲染器，逐渐替代 Skia。
- `display_list/`：显示列表记录与回放。
- `txt/`：文本排版引擎（基于 SkParagraph / libtxt / HarfBuzz）。
- `fml/`：基础工具库（消息循环、文件、线程等）。

构建引擎后得到 `libflutter.so`（Android）、`Flutter.framework`（iOS）、或用于桌面嵌入的库。它们包含整个 C++ 引擎和 Dart VM。

---

## 3. 线程模型：四个主要线程

引擎将工作拆分到独立的线程上，保障 UI 的 60/120fps 流畅度。线程间通过 **任务队列（MessageLoop）** 异步通信。

| 线程 | 职责 | 注意 |
|------|------|------|
| **Platform Thread** | 对应平台的主线程。处理原生交互（平台通道、插件方法调用）、接收输入事件。 | 不跑 Dart 代码。阻塞它仍可能影响引擎与平台的通信，但不直接卡 UI 渲染。 |
| **UI Thread** | 引擎的心脏。运行 **Dart 代码**（`main()`、build、layout、paint），生成 Layer 树。同时处理 Dart 微任务和定时器。 | 这里是“帧构建”的地方。Dart 执行太久就会导致掉帧。 |
| **Raster Thread** | 接收 Layer 树，将其光栅化为像素（GPU 纹理或 PixelBuffer）。执行 Skia/Impeller 的绘制命令。 | 以前叫 GPU Thread。复杂的绘制可能阻塞这里，触发“着色器编译卡顿”。 |
| **IO Thread** | 异步图片解码、纹理上传等耗时 I/O 操作，防止阻塞 UI 或光栅化线程。 | 图片解码操作通过 `ImageCache` 和 `MultiFrameCodec` 运行在此线程。 |

**它们如何协作完成一帧？**

1. **Vsync 信号** 来自系统，唤醒 UI Thread。
2. UI Thread 执行 Dart 的 `_beginFrame` → `build` → `layout` → `paint` → `compositing`，生成 **Scene**（内含 Layer 树），提交给 Raster Thread。
3. Raster Thread 对 Scene 进行遍历，合成各个图层，并发出 GPU 绘制命令，最终上屏。
4. 期间，IO Thread 可能被要求解码下一帧要用的图片资源，解码完上传至 GPU 纹理，并通知 UI Thread 可以重绘。

## 4. 渲染管线：从 Widget 到像素

### 4.1 框架层（Dart）

你的 Widget 树经 Element 树转换为 RenderObject 树。  
对每个脏 RenderObject：

- 执行 `layout`（规定大小/位置）
- 执行 `paint`，将绘制命令记录到 `PaintingContext` 里（本质是向 `Layer` 添加绘制操作）。

根据图层复杂度和复用情况，生成一堆层：

- `PictureLayer`：包含一次录制的 `Picture`（矢量绘制命令）。
- `TextureLayer`：外接纹理（如视频、地图）。
- `PlatformViewLayer`：原生视图的占位。
- `TransformLayer`、`OpacityLayer`、`ClipRectLayer` 等。

### 4.2 UI Thread 产出：Scene 与 DisplayList

Dart 侧通过 `SceneBuilder` 将 Layer 树打包为 `Scene` 对象，调用 `window.render(scene)` 提交给引擎。

引擎内部，`Picture` 会被序列化为 **DisplayList**，这是一种平台无关、保留模式的绘制记录结构。它既可以交给 Skia，也可以由 Impeller 直接执行，是渲染器切换的关键抽象。

### 4.3 光栅化（Raster Thread）

Rasterizer 拿到 Layer 树，执行：

- 对每一帧的所有层进行 **合成策略**，尝试缓存不变内容（`RepaintBoundary` 导致生成独立 PictureLayer，便于复用以避免重录）。
- 遍历 DisplayList，调用底层 2D API（Skia 的 `SkCanvas` 或 Impeller 的 `Aiks`）发出 GPU 绘制命令。
- 合成后的最终纹理被交给 Embedder 显示（对于 Android 是 `ANativeWindow`，iOS 是 `CAEAGLLayer`/Metal Drawable）。

## 5. 新一代渲染器：Impeller

Skia 作为通用 2D 引擎，在移动端尤其在着色器编译上会引入卡顿（首次渲染时生成 GPU 着色器）。Impeller 是 Google 专门为 Flutter 打造的 AOT 友好渲染器，设计目标：**消除着色器编译卡顿，提供可预测的 GPU 行为**。

**与 Skia 的关键差异：**

- **提前编译着色器**：Impeller 的所有着色器在引擎构建时就由 GLSL/MSL 编译为中间表示（SPIRV），运行时没有任何着色器生成，完全无 Jank。
- **不录制 SKPicture**：Impeller 不使用显示列表再去“回放”生成命令，而是由 **Aiks** 直接将 DisplayList 转换为一系列不可变的 GPU 命令快照。更贴近现代图形 API (Metal/Vulkan)。
- **简化 API Surface**：仅支持 Flutter 所需的功能子集，移除了 Skia 作为通用库带来的庞大 API，体量更小。
- **默认后端**：iOS 已默认启用，Android Vulkan/Metal 后端也在推进。很快会成为全平台统一渲染器。

深入理解 Impeller 能帮你理解为什么某些自定义 `Canvas` 绘制在 Skia 和 Impeller 下表现可能不同（尽管官方极力保持兼容）。

## 6. Dart VM 在引擎中的角色

引擎中内嵌了 Dart VM（AOT 或 JIT 模式）。

- **Debug/JIT 模式**：VM 使用解释器和 JIT 编译器，支持热重载。引擎暴露 Dart VM Service，接收热重载请求。
- **Release/AOT 模式**：Dart 代码预先编译为原生 ARM/x86 机器码，由引擎直接加载，无 JIT，体积更小，启动更快。
- **Isolate 与引擎**：Flutter 的 UI Isolate 是引擎创建的，所有 `dart:ui` API 都绑定到此 Isolate。引擎还支持辅助 Isolate 执行计算，但默认不能直接调用 UI 方法，必须通过 Port 通讯。

`dart:ui` 的 C++ 实现通过 **tonic** 库将 Dart 类型映射到 C++。当你调用 `Canvas.drawRect`，实际上触发了 C++ 引擎侧的 `DisplayListBuilder`，最终加入绘制指令。

## 7. 文本渲染管线

文本是 Flutter 最复杂子系统之一，路径如下：

1. Dart 层使用 `TextPainter`（依赖 `text` 库，底层用 C++ 引擎的 `txt` 库）。
2. `txt` 库内部使用 **HarfBuzz** 做文本塑形（shaping），使用 **Minikin** 做断行。
3. 早期基于 libtxt，现在已逐步迁移至 **SkParagraph**，提供更好的排版功能，且与 Impeller 适配。
4. 字形渲染：由 FreeType 或 CoreText/DirectWrite 提供字型数据，最终转为路径或位图交给 Canvas。

---

## 8. 平台通道与嵌入层交互

**Platform Channel** 是 Dart 与原生代码通信的核心，底层全部由引擎处理。

- 调用 `MethodChannel.invokeMethod` 时，消息在 UI Thread 上编码为二进制（StandardMessageCodec），通过引擎放入 Platform Thread 的任务队列。
- 原生接收到调用，执行后返回结果，引擎再将结果回传 Dart 的 Future。
- 所有编解码逻辑实现在引擎 C++ 层（`flutter/lib/ui/semantics/...`），保证高效。

**Embedder** 提供五个核心回调给引擎：

- 提供渲染表面的创建/销毁
- 平台消息发送
- vsync 信号分发
- 输入事件转送
- 生命周期管理

自定义嵌入（如把 Flutter 嵌入车载系统）实质上就是实现这些 Embedder API。

---

## 9. 引擎的启动与热启动

第一次加载引擎时，主要耗时操作：

- 加载 Dart VM 或 AOT 快照
- 初始化 Isolate
- 编译/加载 Kernel 文件
- 启动引擎线程和 Shell
- 创建第一帧

缓存引擎（Warm Engine）或使用 `FlutterEngineGroup` 可以复用 Isolate，让第二、三个引擎几乎零开销启动。这些都依赖引擎内部对 Isolate、Shell 的生命周期管理。

---

## 10. 深入引擎你需要关注的几个调试入口

- **`--enable-dart-profiling`**：CPU 时间消耗在 Dart 还是引擎 C++ 一目了然。
- **Timeline 事件**：引擎在关键点（FrameRequest、Layout、Build、Paint、Rasterizer）插入跟踪点，可在 DevTools 中查看每个线程的耗时。
- **Skia/Impeller 调试**：Impeller 可以使用 `--enable-impeller-vulkan-validation`；Skia 可开启 `trace`。
- **`flutter run --verbose`**：可以看到引擎日志、Vsync 回调、光栅化耗时等信息。

---

## 总结

Flutter Engine 是一个：

- 极度 **异步多线程** 的渲染架构（Platform、UI、Raster、IO）；
- 基于 **Layer 树合成** 和 **DisplayList** 的记录/回放模型；
- 正在从 **Skia 迁移到 Impeller** 以消除着色器编译卡顿；
- 深度集成了 **Dart VM** 并提供 `dart:ui` 作为桥接；
- 通过 **Embedder** 实现跨平台能力。

理解了引擎，你就知道：

- 为什么 `RepaintBoundary` 能优化性能（减少不必要的重录和合成）；
- 为什么复杂的自定义 `Paint` 或着色器会带来第一帧卡顿；
- 为什么频繁的 `platform channel` 调用需要在 Isolate 间调度；
- 以及为什么 Impeller 是 Flutter 未来高性能的基石。
