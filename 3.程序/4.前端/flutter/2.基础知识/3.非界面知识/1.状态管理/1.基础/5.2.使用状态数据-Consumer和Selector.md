# Consumer 和 Selector

在 `ChangeNotifierProvider` 注入状态后，子组件消费状态最常用的两个组件就是 **Consumer** 和 **Selector**。两者都能获取状态并监听更新，但**监听粒度和性能表现差异极大**，也是 Provider 性能优化的核心抓手。

下面我们从用法、原理、区别、优化技巧四个维度详细拆解。

## 一、Consumer：基础全量监听组件

### 1. 核心定位

`Consumer` 是 Provider 提供的基础消费 Widget，作用是**从父级 Provider 中获取指定类型的状态实例，并自动监听状态的全量变化**——只要状态调用了 `notifyListeners()`，Consumer 包裹的子树就会触发重建。

它解决了两个核心问题：

- 避免子组件 context 层级过深，找不到 Provider 的问题
- 可以精准控制**重建的范围**，不需要整个页面 `build` 都跟着刷新

### 2. 标准用法

`Consumer` 是一个泛型组件，泛型参数就是你要监听的状态类型，核心是 `builder` 回调：

```
Consumer<CounterModel>(
  // 状态变化时，builder 会重新执行，子 Widget 重建
  builder: (BuildContext context, CounterModel counter, Widget? child) {
    // counter 就是拿到的状态实例
    return Text('当前计数：${counter.count}');
  },
)
```

`builder` 的三个参数：

- `context`：当前 Widget 的上下文
- `counter`：从 Provider 中获取到的状态实例
- `child`：用于缓存不需要重建的静态子组件（性能优化关键）

### 3. 关键优化点：child 参数

绝大多数人使用 Consumer 都会忽略 `child` 参数，但它是最基础的性能优化手段：
**`child` 包裹的 Widget 不会随状态变化而重建**，适合放置不依赖该状态的静态组件。

#### 优化示例

```
Consumer<CounterModel>(
  builder: (context, counter, child) {
    return Column(
      children: [
        Text('计数：${counter.count}'), // 依赖状态，需要重建
        const SizedBox(height: 20),
        child!, // 静态按钮组，永远不会重建
      ],
    );
  },
  // 这部分 Widget 只会在初始化时构建一次
  child: const _StaticButtonGroup(),
)

// 静态不变的组件
class _StaticButtonGroup extends StatelessWidget {
  const _StaticButtonGroup();

  @override
  Widget build(BuildContext context) {
    return Row(
      children: [
        ElevatedButton(onPressed: () {}, child: const Text('按钮1')),
        ElevatedButton(onPressed: () {}, child: const Text('按钮2')),
      ],
    );
  }
}
```

### 4. 优缺点

- ✅ 写法简单，直接拿到完整状态实例
- ✅ 支持通过 child 缓存静态子组件
- ❌ 粒度粗：状态里任何一个字段变化，都会触发整个子树重建
- ❌ 状态字段很多时，容易产生大量不必要的重建

## 二、Selector：精准粒度监听组件

### 1. 核心定位

`Selector` 是 Consumer 的进阶版本，核心能力是\*\*「筛选+定向监听」\*\*：它不会监听整个状态对象，而是从状态中提取出你关心的某一部分数据，只有当这部分数据发生变化时，才会触发子树重建。

简单说：**Consumer 是状态一变就全更，Selector 是只盯着你关心的字段变了才更**。

### 2. 标准用法

`Selector` 有两个泛型参数：

- 第一个 `S`：原始状态的类型（比如 `CounterModel`）
- 第二个 `A`：筛选后的数据类型（比如 `int`，只提取 count 字段）

核心有两个参数：

- `selector`：数据筛选函数，从完整状态中提取你关心的部分
- `builder`：和 Consumer 一致，只有筛选后的数据变化时才会执行

```
Selector<CounterModel, int>(
  // 筛选逻辑：只提取 count 字段
  selector: (BuildContext context, CounterModel counter) => counter.count,
  
  // 只有 count 发生变化时，builder 才会重新执行
  builder: (BuildContext context, int count, Widget? child) {
    return Text('当前计数：$count');
  },
)
```

### 3. 核心原理：判等机制

Selector 内部会维护上一次 `selector` 返回的值，每次状态触发 `notifyListeners` 后：

1. 重新执行 `selector` 函数，拿到新值
2. 用 `==` 比较新值和旧值是否相等
3. 相等 → 不重建；不相等 → 触发 builder 重建

这也是为什么 Selector 能精准控制重建：它在全量通知的基础上，做了一层「值变化校验」的过滤。

### 4. 进阶：筛选多个字段

如果需要同时监听多个字段，可以返回元组、列表或自定义对象，只要保证可以通过 `==` 判等即可。

```
// 用 List 同时监听 name 和 age 两个字段
Selector<UserModel, List<dynamic>>(
  selector: (ctx, user) => [user.name, user.age],
  builder: (ctx, data, child) {
    return Text('${data[0]}，${data[1]}岁');
  },
)
```

### 5. 优缺点

- ✅ 粒度极细：只订阅关心的数据，大幅减少不必要重建
- ✅ 同样支持 child 参数缓存静态组件
- ✅ 是 Provider 性能优化的核心手段
- ❌ 写法稍繁琐，每个需要的字段都要写筛选逻辑
- ❌ 筛选结果如果是复杂对象，需要注意判等问题

## 三、Consumer vs Selector 核心区别对比

| 对比维度 | Consumer | Selector<S, A> |
| --- | --- | --- |
| 监听粒度 | 监听整个状态对象，任何字段变化都触发重建 | 只监听筛选出的部分数据，仅该部分变化才重建 |
| 拿到的数据 | 完整的状态实例，可以直接调用所有方法 | 筛选后的特定数据，默认拿不到完整状态 |
| 性能表现 | 状态字段越多、变化越频繁，无效重建越多 | 性能更优，尤其适合大状态、多字段的场景 |
| 写法复杂度 | 简单直观 | 稍复杂，需要定义筛选逻辑 |
| 适用场景 | 小型状态、子树大部分都依赖状态变化 | 大型状态、只依赖少数几个字段的局部组件 |

>
> 补充：`Provider.of<T>(context)` 和 Consumer 本质完全一致，都是全量监听整个状态；区别只是前者是直接通过 context 获取，后者是通过 Widget 构建。

## 四、Provider 性能优化完整指南

掌握 Consumer 和 Selector 的区别后，结合以下 7 条实践原则，可以把 Provider 的性能优化到最优。

### 1. 原则一：尽量缩小监听范围，不要整页包裹

最常见的错误就是把整个页面 Scaffold 都包在 Consumer 里，导致一个数字变化就整页重建。

❌ 错误写法：

```
@override
Widget build(BuildContext context) {
  return Consumer<CounterModel>(
    builder: (_, counter, __) {
      return Scaffold(
        appBar: AppBar(title: const Text('计数器')), // 完全不需要重建
        body: Center(child: Text('${counter.count}')),
      );
    },
  );
}
```

✅ 正确写法：只包裹真正依赖状态的 Widget

```
@override
Widget build(BuildContext context) {
  return Scaffold(
    appBar: AppBar(title: const Text('计数器')),
    body: Center(
      // 只包裹 Text
      child: Consumer<CounterModel>(
        builder: (_, counter, __) => Text('${counter.count}'),
      ),
    ),
  );
}
```

### 2. 原则二：只调用方法的地方，关闭监听

对于按钮点击、初始化逻辑等**只需要调用状态方法、不需要展示状态数据**的场景，一定要加 `listen: false`，避免订阅更新。

❌ 错误写法：每次状态变化，按钮都跟着重建

```
ElevatedButton(
  onPressed: () {
    Provider.of<CounterModel>(context).increment();
  },
  child: const Text('+1'),
)
```

✅ 正确写法：只获取实例，不订阅更新

```
ElevatedButton(
  onPressed: () {
    Provider.of<CounterModel>(context, listen: false).increment();
  },
  child: const Text('+1'),
)
```

### 3. 原则三：优先用 Selector，只订阅需要的字段

当状态类字段较多时，优先用 Selector 精准订阅，避免无关字段变化触发重建。

比如一个用户状态包含 name、age、avatar、address 等 10 个字段，某个组件只显示年龄：

```
// ✅ 只有 age 变化时才重建，其他9个字段变化完全不受影响
Selector<UserModel, int>(
  selector: (_, user) => user.age,
  builder: (_, age, __) => Text('年龄：$age岁'),
)
```

### 4. 原则四：善用 Consumer/Selector 的 child 缓存

对于不依赖状态的静态子组件，通过 `child` 参数缓存，避免重复构建，这个优化在子组件较重时收益非常明显。

### 5. 原则五：避免 selector 返回新对象实例

Selector 靠 `==` 判等，如果 selector 每次都返回一个新的对象/集合，哪怕内容完全一样，也会因为引用不同而判定为「变化」，导致每次都重建，失去优化意义。

❌ 典型踩坑（每次都返回新 List）：

```
Selector<OrderModel, List<Order>>(
  // 每次调用 toList() 都会生成新的 List 实例，引用永远不等
  selector: (_, model) => model.orderList.toList(),
  builder: (_, list, __) => OrderList(list: list),
)
```

✅ 正确做法：

- 直接返回状态中持有的原集合引用
- 如果必须生成新对象，使用 `Equatable` 重写 `==`
- 集合比较可以使用 `collection` 包的 `DeepCollectionEquality`

### 6. 原则六：拆分大状态，避免单类臃肿

不要把整个页面的所有状态都塞进一个 ChangeNotifier 里。状态越大、字段越多，`notifyListeners()` 触发的影响面就越广。

推荐按业务模块拆分：

- 列表状态 → `ListNotifier`
- 筛选条件 → `FilterNotifier`
- 输入表单 → `FormNotifier`

拆分后，每个状态只负责自己的逻辑，变化时只会影响自己的订阅者，大幅降低重建范围。

### 7. 原则七：状态放在最小必要节点，不要全塞根节点

很多图省事的做法是把所有 Provider 都放在 `main.dart` 的根节点，这会导致状态生命周期和应用一样长，内存占用高，且全局可访问容易造成滥用。

正确做法是**状态就近放置**：

- 页面级状态 → 放在页面入口的 Widget 上
- 模块级状态 → 放在模块的共同父节点
- 全局状态（如用户登录态、主题）→ 才放在根节点

---

## 五、常见踩坑总结

1. **Selector 筛选了对象，但没重写 ==**：自定义类必须重写 `==` 和 `hashCode`（或继承 Equatable），否则 Selector 无法正确判等。
2. **在 build 中创建 Provider**：不要在 build 方法里用 `ChangeNotifierProvider.value` 动态创建实例，会导致状态丢失或重复创建。
3. **滥用 Consumer2/Consumer3**：多状态嵌套优先用 Selector 分别订阅，不要一股脑用多 Consumer 全量监听。
4. **忘记 dispose**：ChangeNotifier 中如果有定时器、流订阅，一定要在 `dispose` 方法中取消，ChangeNotifierProvider 只会调用 dispose，不会自动清理内部资源。

---

## 最后：选型建议

- 状态字段少、子树整体都依赖状态 → 用 `Consumer`，简单直接
- 状态字段多、组件只依赖少数字段 → 用 `Selector`，性能优先
- 只调用方法、不展示数据 → 用 `Provider.of<T>(context, listen: false)`
